
**Разделение путей (уже существует в крейте — изобретать не нужно):**

| Путь | Семантика | Кому |
|---|---|---|
| `segments()` / `stream()` / `list_segments` | **строгий, fail-closed** | потребителям данных: кокпит, research, бэктест |
| `iter_segments_sorted()` / `recover()` / `read_all()` | **терпимый, диагностический** | офлайн-работе; наружу данные не отдаёт |

строгий путь ради неё ЗАПРЕЩЕНО. Оракул `ti_6` это пиннит: при повреждённом сегменте

## Objective

`resolve_next_seq_with` берёт `tail_last_seq_of(последний сегмент)` и при `Ok(None)` молча
падает на `meta_seq`. Но `tail_last_seq_of` возвращает `Ok(None)` в **восьми** случаях, из
которых легитимны только два (файла нет; файл нулевой длины). Остальные — порча: битый
v2-заголовок сжатого сегмента, обрыв zstd-потока, полностью невалидный хвост сырого
сегмента. Все они трактуются вызывающим как «сегментов нет, начинай с меты».

**При restore из холодного хранилища `journal.meta` ОТСУТСТВУЕТ** (ретеншен выгружает
сегменты, не мету — замерено в M-40) ⇒ `meta_seq = 0` ⇒ запись идёт с нуля поверх истории.

## Замеры architect'а (main @ ddc105c, ПОСЛЕ мержа M-40)

```text
история 0..341 в сжатых сегментах, journal.meta отсутствует (прод-режим restore)

усечённый .zst (обрыв выкачки)      → open_with = Ok, новые seq [0, 1]  ← перекрытие 342 событий
валидный zstd + битый v2-заголовок  → open_with = Ok, новый seq  [0]    ← то же
сырой сегмент с битым хвостом       → open_with = Ok, seq 342           ← КОРРЕКТНО (ресинк нашёл 341)
```

**Уточнение к формулировке TD-049.** Reviewer описал дефект как «recorder НЕ СТАРТУЕТ»
(асимметрия терпимости raw/zst, `?` пробрасывает Err). Замер это **опроверг**: recorder
стартует в обоих случаях порчи. Реальное последствие ХУЖЕ отказа — молчаливый seq-reuse.
Отказ старта был бы громким и исправимым; порча append-only журнала — необратима, и реплей
воспроизведёт её бит-в-бит.

## Контракт (architect)

**JR-I-8 (честность `next_seq`).** `open_with` не имеет права начать запись с `seq`,
меньшего либо равного максимальному `seq`, уже присутствующему в журнале. Если сегмент с
максимальным индексом СУЩЕСТВУЕТ и НЕ ПУСТ, но его последний `seq` установить НЕ УДАЛОСЬ —
`open_with` обязан вернуть `Err` с диагностикой (файл + причина + действие), а не стартовать
с `meta_seq`.

**Легитимных `Ok(None)` ровно три:**
1. файла нет;
2. файл нулевой длины;
3. **валидный заголовок, ноль событий** — recorder создал сегмент и упал до первой записи
   (найдено architect'ом при вычитке собственного оракула: без этого случая ужесточение
   сломало бы штатный перезапуск; закрыто `ti_4` п. «д»).

**Почему fail-closed, а не терпимость.** Терпимость = запись поверх существующего диапазона
`seq` = необратимая порча. Отказ = минуты простоя сбора. Выбор зафиксирован, а не оставлен
на усмотрение реализации.

**Что НЕ ужесточается.** Ресинхронизация сырого хвоста (побайтовый поиск последнего
ВАЛИДНОГО фрейма) сохраняется: она возвращает конкретный `seq`, позиция известна, reuse
невозможен. Ломать работающее поведение не нужно (`ti_4` п. «г»).

**Операторский выход обязателен.** Fail-closed без выхода = вечно остановленный сбор данных,
и единственный доступный оператору шаг — удалить каталог, то есть потерять историю (ровно
то, от чего защищаемся). Форма — **файловая декларация**
`journal.force-next-seq.json` (не новый Rust-API): повторяет знакомый оператору
`journal.legacy.json`, не расширяет публичный API крейта, остаётся следом для аудита.

```json
{ "next_seq": 512,
  "reason": "segment-00000001.jrnl.zst невосстановим: bit-rot, холодной копии нет",
  "declared_at_ms": 1785362203969 }
```

Правила декларации (все под оракулами): действует ТОЛЬКО при нечитаемом хвосте (иначе
забытый файл молча переопределял бы честный `next_seq`); `next_seq` строго больше
максимального ЧИТАЕМОГО `seq` (иначе escape-hatch сам станет каналом seq-reuse);
одноразовая (после применения → `journal.force-next-seq.applied.json` с сохранением
`reason`). Тот же принцип, что `pruned_without_checkpoint_coverage` в M-38b: обход разрешён,
но обязан быть НАЗВАН и не может быть тихим.

## rev5 — дизайн защиты (блокер R-002, Находка 1)

### Дефект (описан reviewer'ом, воспроизведён на прод-форме)

После 4a появился новый повод для `Err` из `tail_last_seq_of`: **сырой сегмент больше
`TAIL_SCAN_CHUNK` (4 MiB), у которого в хвостовом окне нет валидных фреймов, но заголовок цел
и префикс полон читаемых событий.** `readable_max_seq` (4b) вызывает на нём тот же
`tail_last_seq_of`, получает тот же `Err` и отбрасывает сегмент ЦЕЛИКОМ вместе с читаемым
префиксом. Прежняя реализация читала его терпимо (`read_segment_events(p, false)`, байт-ресинк)
и знала настоящий пол.

Итог: пол падает до максимума предыдущего сегмента, а если повреждённый сегмент один — до
`None` ⇒ `unwrap_or(0)` ⇒ **защиты нет вообще**. Замер reviewer'а: сегмент 9 981 549 B,
читаемый максимум `seq = 95141`, декларация `next_seq = 1` ПРИНЯТА.

Прод-форма совпадает: активный сегмент **сырой**, 868 MB → 1 GiB, окно скана 4 MiB.

### Контракт rev5 — три состояния вместо `Option`

Корень дефекта глубже 4b: `Option<u64>` не различает **«сегментов нет»** и **«сегменты есть,
но максимум установить не удалось»**, а `unwrap_or(0)` схлопывает второе в первое. Отсутствие
знания трактуется как разрешение — это противоречит fail-closed всего milestone'а.

`readable_max_seq` обязан возвращать ТРИ состояния, и валидация декларации обязана их различать:

| Состояние | Когда | Валидация `journal.force-next-seq.json` |
|---|---|---|
| `Known(max)` | удалось установить максимальный `seq` (в т.ч. по ЧИТАЕМОМУ ПРЕФИКСУ повреждённого сегмента) | принять только `next_seq > max` |
| `NoSegments` | сегментов нет / все нулевой длины | пол = 0, любой `next_seq` законен (легитимный restore с нуля) |
| `Unknown` | сегменты ЕСТЬ и непусты, но ни в одном не удалось прочитать ни одного валидного фрейма | **ОТКАЗ** с диагностикой: пол неизвестен, декларация не может быть проверена |

`Unknown` — не тупик для оператора: runbook уже требует восстановить сегмент из холодной копии
или отправить его в карантин РУКАМИ. После карантина каталог переходит в `NoSegments`/`Known`,
и декларация проверяема. Тупиком была бы противоположность — молча пропустить `next_seq` при
неизвестном поле, то есть выдать seq-reuse с формальным одобрением оператора.

### Требование к вычислению `Known` — терпимо И ограниченно по памяти

Оба свойства обязательны одновременно (иначе чинится один дефект ценой другого):
- **терпимо** — читаемый префикс повреждённого сегмента УЧАСТВУЕТ в поле (иначе Находка 1);
- **ограниченно** — без `Vec<Event>` на весь сегмент и без полной распаковки `.zst` в память
  (иначе возвращается NOTE 2 / класс TD-011: 1 GiB в момент разбора инцидента).

То есть нужен потоковый скан с начала файла, отслеживающий максимальный `seq` валидных
фреймов при постоянной памяти. Для `.zst` — потоковая распаковка чанками, не `read_to_end`.
Способ выбирает dev; оба свойства проверяются оракулами и не подлежат размену.

### Что вскрыл прогон фикстур (обязательно к прочтению перед 5b)

Усечение и порча сжатого сегмента дают РАЗНЫЕ состояния — измерено, не выведено:

| Форма | Поведение `open_with` | Читаемый префикс |
|---|---|---|
| одноблочный `.zst`, усечён | `Err` (поток не открывается) | нет |
| **много**блочный `.zst`, усечён | **`Ok`** — декодер трактует обрыв как штатный конец | есть, но путь декларации НЕ входится |
| **много**блочный `.zst`, ИСПОРЧЕН (bit-rot) | `Err` | **есть** — на этой форме и стоит `op_2` |

Средняя строка — это уже зафиксированное §«Известное ограничение» («тихо короче»), а не
предмет 5b. Фикстура `restored_with_unreadable_tail` переведена на нижнюю строку и несёт
setup-guard: если измеренный эталон не превысил `first_seq(жертвы)−1`, фикстура объявляется
выродившейся и падает — вернуться в rev4-слепоту молча больше нельзя.

### Дефект оракула, вскрытый R-002 (исправляет architect, НЕ dev)

`restored_with_unreadable_tail()` вычисляет эталон как `first_seq(жертвы) − 1` — то есть
**по построению исключает читаемый префикс жертвы** из ожидаемого пола. Оракул закодировал
дефект в ожидание и поэтому не мог поймать регресс 4b. Эталон переписывается на фактически
читаемый максимум; `op_2` после этого обязан утверждать защиту, которая реально существует.
