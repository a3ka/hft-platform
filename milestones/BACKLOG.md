## Очередь

### M-09 — Data safety net (бэкап + recon + метрики) 🔴 ПЕРВЫЙ
**Почему первым.** Пять инцидентов подряд (TD-011/013/014/016 + C1) нашли **глазами**, ни один —
автоматикой; при этом 15.0 GB боевых данных лежат **в одном экземпляре на одном диске**.
Мы строим торговую систему на активе, который (а) не защищён от потери, (б) не проверяется на
правильность. Всё остальное можно потерять и переписать — данные нельзя.

- Cold-copy журнала offsite (Storage Box) + **restore-drill** («бэкап, который не восстанавливали,
  — не бэкап», `OPS-I-2/3`). Legacy-сегмент 15.0 GB — первым.
- **Recon с биржей** (`OPS-I-1`): REST-снапшот vs локальная книга, расхождение > ε → алерт +
  ресинк + `Sys`-событие. **Это единственная проверка, которая ловит C1-класс** (порча данных
  при зелёном healthcheck).
- `/metrics` + алерты P0/P1/P2 (`docs/fa/ops.md` §3/§7 + матрица §7.1).
- **БЛОКИРУЮЩАЯ подзадача: `CT-RFC-03`** (T1) — аудит-событие recon/ресинка в журнал требует
  нового варианта `SysEvent`; `EventKind` — T1, значит atomic contract-RFC обязателен
  (C-006 M5: «возможно нужен» — недопустимая формулировка для милестоуна, который будет писать
  RED-тесты). Без RFC подзадача recon не стартует.
- Гейты: **contract-RFC + critic** (T1-триггер, `gates.md` §1.1); **прод не инертен** → §8.
- Acceptance (исполняемые ворота, C-006 M4/M6/M7):
  1. **`ε_test`** (не калибруется): инъецированная порча книги — удалённый/искажённый уровень,
     расхождение best bid/ask — ОБЯЗАНА поднять алерт. `ε_prod` калибруется отдельно, но не
     выше `ε_max` (fail-closed потолок).
  2. **`OPS-I-9` rate-budget/backoff:** инъецированный поток REST-ошибок НЕ даёт hot-loop;
     418/429/`Retry-After` соблюдаются; бюджет запросов на venue не превышается (урок TD-013 —
     recon добавляет ровно тот трафик, который нас уже банил).
  3. **restore-drill:** холодная копия СКАЧИВАЕТСЯ и ЧИТАЕТСЯ (`journal::stream`, `seq`
     непрерывен) — на реальном сегменте, а не на фикстуре.
  4. **Двусторонний паритет алертов:** каждая строка матрицы §7.1 имеет правило; каждое
     правило ссылается на существующую метрику.
- **Хвост M-09 (НЕ блокирует закрытие task 2 / дефекта B): офлайн объёмная сверка** — `research-dev`,
  `research/data-quality/**`. После B2 (founder ★ 2026-07-18, `docs/fa/ops.md` §4.3.2) near-touch ОБЪЁМ
  снят с рантайм-recon (REST-неверифицируем: систематический WS(T1)-vs-REST(T2) bias, три §8-провала).
  Объёмную сверку вести ОФЛАЙН над записанной книгой из журнала (полная книга/объёмы/глубина пишутся БЕЗ
  изменений): реконструкция книги + объёмная дельта как ТРЕНД/диагностика рядом с gap-статистикой (M-08).
  **Прото-дизайн — `ops.md` §4.3** (дискриминатор churn↔порча по персистентности знака), НО фикстуры
  ОБЯЗАНЫ быть ПРОД-ПОДОБНЫМИ (ненулевой остаточный bias), а не синтетический zero-mean churn — ровно то,
  что дало green-unit/live-flood в рантайме (`testing.md` урок B2). Возможный platform-reference для
  глубоких 6–60% полос (§5.1 магнитудная загадка) — сюда же. Отдельная RED-спека research-dev, когда
  дойдёт очередь; НЕ P2.5-блокер.

### M-10 — Отчёт R-001 (валидация OBI) 🟠
**Почему рано, хотя «просто прогон».** У нас есть grid, walk-forward, trials-ledger, deflated
Sharpe, стресс-режимы — и **ни одного отчёта**. Пока нет ни одного R-*, весь research-стек
недоказан, а мы уже строим на нём торговлю. Даже «сигнал мёртв» — ценный результат за дёшево.

- Прогон OBI (Трек A/B) на strategy-пайплайне; TD-015 (эпохи ledger'а) соблюсти.
- Обязательно: gap-артефакт эпохи (E8) + `data_span_days` + SE(Sharpe) в отчёте — на 3–7 днях
  данных вердикт «PASS» физически недостоверен (SE годового Sharpe ≈ ±11), поэтому **kill-screen,
  без касания test-окна и без подписи**.
- Гейты: risk-critic (анти-оверфит §6) → founder ★ (принять/убить по пре-рег. критериям).

### M-11 — Risk + Killswitch + OMS 🔴 (дорогой, но неизбежный)
Единственный путь к деньгам. `RiskApproved<Order>` встаёт **между** `strategy` и `oms`;
`portfolio::size` — это pre-trade sanity, а **не** риск-гейт.
- RISK-BLOCK (`gates.md` §5): critic + **risk-critic** обязательны; RED-suite `RK-I-1..10` +
  `INTG-I-*` обязан падать на заглушках.
- Killswitch — **отдельный процесс** со своими кредами (работает при мёртвом движке).
- **Acceptance (исправлено, C-006 M8):** `RK-I-1..10` + `INTG-I-*` GREEN (падали на заглушках);
  disconnect-drill (после разрыва наших заявок на бирже нет); kill-switch срабатывает при
  мёртвом движке. **48 ч живого testnet — ПЕРЕЕХАЛО в M-12**, потому что для торговли нужен
  `runner` (композиция режимов + arming), а он живёт в M-12. Прежняя формулировка требовала
  торговать раньше, чем появится то, чем торгуют, — и толкала к временному harness'у в обход
  `runner`-инвариантов, то есть к разрыву «backtest == paper == live».

### M-12 — Runner (paper/testnet) + границы B/C (подпись Ed25519) 🟠
- `runner`: композиция режимов (backtest/paper/live), arming; исполняется **только**
  `status==live && weight>0` (граница B).
- **48 ч HL testnet** (переехало из M-11): первая живая торговля идёт ЧЕРЕЗ `runner`, а не через
  временный harness — иначе мы валидируем не тот код, который пойдёт в live.
- **Подпись решений** (граница C): `Ctl(ParamChange{signed})` + `decisions/D-NNN.md`. Без неё
  любое изменение весов/лимитов — «на доверии», то есть ровно тот путь, который заканчивается
  правкой параметра на живом процессе.
- Paper-карантин обязателен (`02-quant-desk.md` §4.5): ни один сигнал не идёт train→live.

### M-13 — Hyperliquid depth 🔴 ПРЕДУСЛОВИЕ, а не «потом» (исправлено, C-006 M9)
**Валидируем сигнал на Binance, а торговать собираемся на HL**, где книга ≤20 уровней и полосы
OBI **невычислимы** (TD-005). Это не уборка после P3 — это **предусловие любого testnet/live с
OBI-полосами**: иначе на HL нечего считать.

**Развилка (решение founder'а ★, обе ветки честны):**
- **(а) закрыть глубину HL** (другой эндпоинт / `nSigFigs` / иной источник) — тогда OBI-полосы
  остаются первым сигналом, и M-13 обязан стоять **ПЕРЕД** живой торговлей (M-12);
- **(б) сменить первый сигнал/площадку** — торговать на Binance (там книга есть) ЛИБО взять на
  HL сигнал, не требующий глубины (top-N imbalance, funding/basis, liquidation-flow). Тогда
  M-13 можно отложить, но это надо ЗАПИСАТЬ как решение, а не «получиться само».

Пока развилка не выбрана, M-11/M-12 не могут честно назвать свой первый live-сигнал.

### M-14 — DET-I-1 полностью (`state_hash` + снапшоты) 🟡
«`replay(journal) == реальность`» сейчас держится на честном слове: бит-идентичность не
проверяется (TD-007). Это фундамент форензики («каждый цент объясняется реплеем») и обязателен
до live-micro (P4), но не блокирует research.

### M-15 — Импорт купленной истории 🟡
Форма готова (CT-RFC-02: `Vendor`-эпохи, манифест, fail-closed классификация). Нужен парсер
вендора + **per-source артефакты латентности/издержек** (у вендора другая глубина и другие часы —
одна `sim`-таблица на две эпохи = ложь). Триггер: founder называет поставщика.
Обязательное условие: `schemars` → JSON Schema 2020-12 (D-1) — первый момент, когда схему читает
не наш код.

### Order-flow трек (данные Фабио + фронт) — данные-first, founder ★ приоритет 🟠
Разбивка build-vs-integrate (анализ architect 2026-07-20): внешние MCP/сервисы — просмотрщики с
лицензией «не хранить»; владеть order-flow можно только СВОИМ захватом. Историч. данные для бэктеста —
бесплатны/дёшевы (Binance `data.binance.vision` free; HL CC0-зеркала). Сторону агрессора мы УЖЕ пишем →
trade-flow сигналы вычислимы сейчас; book-дельты (absorption/DOM) выбрасываем → нужен захват.

- **M-16 — историч. импорт** (research-only): Binance free + HL CC0 → журнал-формат. Шире окно M-10 +

- **M-17 — order-flow Phase A (бэкенд):** trade-flow сигналы (footprint/cumulative delta, чистые

- **M-18 — order-flow Phase B (захват, BUILD):** персист сырых @depth book-дельт (`CT-RFC-04 L2Delta`) →

  теряются ежедневно). → не написан.
- **M-19 — frontend cockpit (ПОЗЖЕ, после бэка):** дорабатываем `a3ka/code2alpha` (Next+lightweight-charts

- **Новые venue** — пока не закрыт разрыв «валидируем на Binance / торгуем на HL».

## Правило очереди

Приоритет = **цена ошибки**, не близость к прибыли. Данные (M-09) → доказательство сигнала (M-10)
→ барьер к деньгам (M-11) → исполнение (M-12). Любая перестановка означает: мы торгуем на
активе, который не защищён, сигналом, который не проверен, через путь, у которого нет тормоза.
