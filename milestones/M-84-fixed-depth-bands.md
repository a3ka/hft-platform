# M-84 — глубина считается ФИКСИРОВАННЫМ набором из семи полос

STATUS: PROPOSED (2026-09-11, architect). Дом решения `П-029` (граница C, founder 2026-09-10).
Предмет — `TD-198` (закрывается исчезновением), `П-010` (стоимость от числа инструментов),
`П-009` (десятки тысяч сессий). Перепроверка записи решения — `R-179`, четыре круга, APPROVE.

## Objective

**Сервер ВСЕГДА считает продуктовый набор из семи полос** — `1.5 / 3 / 5 / 8 / 15 / 30 / 60 %`,
обе стороны на каждую. **Клиент НЕ задаёт сетку**: он выбирает, какие из готовых строк
ОТОБРАЖАТЬ.

UX founder'а дословно и без изменений: «пользователь задаёт например 15 % BID и получает
график на этом уровне во времени. И также со всеми остальными бидами и асками на всех
уровнях». Галочка переключает ОТОБРАЖЕНИЕ, а не заказывает ВЫЧИСЛЕНИЕ.

## Почему — замер, а не рассуждение

| факт | где снят |
|---|---|
| набор полос входит в отпечаток селектора | `crates/gateway/src/lib.rs:3449-3462` |
| ⇒ разные наборы = разные отпечатки = разные расчёты и РАЗНЫЕ чекпоинты | там же |
| имя слепка детерминировано отпечатком (`ckpt-<fp_hex16>.bin`) | `crates/gateway/src/lib.rs:3305-3314` |
| обе стороны считаются ОДНИМ проходом на полосу | `crates/gateway/src/lib.rs:1425-1440` |
| **цена такта НЕ множится на число полос** — один проход уровней для ВСЕХ полос | `crates/gateway/src/lib.rs:1388-1391` (`C-156` F1) |
| продуктовый набор — семь полос, включение подписано `П-014` | `docs/fa/viz-backend.md:42` |
| охват источника 50–59 %, эмиссия режется `MAX_REL_DIST = 0.60` | `docs/fa/viz-backend.md:80-84`, `crates/venue-binance/src/lib.rs:33` |

**Следствие, сформулированное ТОЧНО (`R-179` Б-3).** Решение убирает ОДНУ из ШЕСТИ осей
отпечатка (venue, symbol, `timeframe_ms`, `window_ms`, полосы, `depth_cadence_ms`). Две оси —
`timeframe_ms` и `window_ms` — присылает КЛИЕНТ, и они остаются. Разделяемой проекции в `main`
нет. Поэтому решение даёт **необходимое условие** `П-010`, а не его исполнение: общую ось
ключа и **общий чекпоинт**. Писать «один расчёт на инструмент» нельзя.

## ЗАМЕР ЦЕНЫ — СНЯТ 2026-09-10, ЧИСЛА НИЖЕ ОБЯЗАТЕЛЬНЫ К ПРОВЕРКЕ

```
$ живые слепки на проде
  ckpt-b0f1ed89ec2ec142.bin  3 350 601 Б  (живой)
  ckpt-2a00318f774d9689.bin  2 516 926 Б  (брошен 30.08 — отпечаток уже менялся однажды,
                                           миграции не было, старый просто осиротел)
$ ХОЛОДНАЯ пересборка слепка в ОТДЕЛЬНОМ томе (прод не тронут):
  965 с = 16.1 мин, exit=0, achieved_cursor=532411199
$ интервал чекпоинтера на проде: */15 = 900 с
$ вес депт-серии в кадре: 7 полос × 2 стороны × 60 точек ≈ 13.1 КиБ против 1.9 КиБ у одной
```

**Главный вывод замера: 965 с > 900 с.** Холодная пересборка ДОЛЬШЕ интервала между
запусками чекпоинтера. Наивная выкатка («поменяли набор — ждём, пока соберётся») даёт окно,
в котором КАЖДОЕ подключение идёт полным проходом журнала, и окно не закрывается само.

**Развязка найдена тем же замером и стоит НОЛЬ.** Имя слепка есть отпечаток, поэтому слепки
разных наборов СОСУЩЕСТВУЮТ — на проде их сейчас два. Значит новый собирается ЗАРАНЕЕ, рядом
со старым, и переключение происходит на ГОТОВЫЙ. Окно нулевое. Порядок — задача 5.

## COMPILE-RED — санкционированное состояние, объявленное ЗАРАНЕЕ

**На этой ветке `cargo test --all` и `cargo clippy --all-targets` КРАСНЫ НАМЕРЕННО:** три
RED-файла ссылаются на `gateway::CANONICAL_DEPTH_BANDS`, которого ещё нет (его вносит
engine-dev задачей 2). Это `A-028` §1 — стандарт полноты набора: оракул пишется ДО кода.

**Причина отказа у каждого файла РОВНО ОДНА и она объявлена** — проверено прогоном:
```
red_fixed_bands_canonical    причин: 1 | error[E0425]: cannot find value `CANONICAL_DEPTH_BANDS`
red_fixed_bands_fingerprint  причин: 1 | error[E0425]: cannot find value `CANONICAL_DEPTH_BANDS`
red_fixed_bands_wire         причин: 1 | error[E0425]: cannot find value `CANONICAL_DEPTH_BANDS`
```
Первая редакция давала ДВЕ причины (ещё `enum Venue is private` — мой неверный импорт, `Venue`
живёт в `contracts`, не в `gateway`). Исправлено до коммита: «красное по построению» обязано
означать «падает по ВЕРНОЙ причине», а не «падает».

**Следствие для merge, названное заранее:** ветка НЕ вливается в `main`, пока задача 2 не
закрыта (`gates.md` §8 — «RED до реализации не живёт в `main`»; санкционированный путь —
feat-ветка, которую мержат уже зелёной). Тот же режим был у `M-74`, и там он растянулся —
здесь это названо, чтобы срок был осознанным, а не обнаруженным.
