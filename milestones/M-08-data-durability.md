## Objective

Три измеренных факта (VPS, 2026-07-13) делают текущее состояние тупиковым:

| Факт | Число | Следствие |
|---|---|---|
| Скорость записи | **2.8 GB/сутки** (15.0 GB за 3 суток) | — |
| Свободно на диске | 120 GB из 150 GB | **сбор встанет через ~43 дня** (плюс докупленная история — раньше) |
| Ротация/ретеншен | **нет** (`journal/src/lib.rs:24` — имя сегмента захардкожено), TD-006 | некуда расти |
| Чтение журнала | `journal::read_all() -> Vec<Event>`, `research-cli/src/main.rs:54` | **грид на 15.0 GB не запустится** — весь журнал в RAM (класс TD-011, этажом выше) |
| `schema_version` в сегменте | **не пишется** (`journal.meta` = только `next_seq`) | `CT-I-6` формально не выполнен; provenance некуда положить |
| Память recorder | дрейф 5–9 → **48 MiB** за ~5 ч (наблюдение reviewer'а) | лик не доказан, но healthcheck такое маскирует (TD-011) |

M-08 делает сбор **бесконечным по времени** (ротация + ретеншен + cold-выгрузка), чтение —
**bounded по памяти** (стрим вместо `Vec<Event>`), а происхождение данных — **читаемым
фактом** (CT-RFC-02), чтобы купленная история не смешалась с собственным захватом.

Авторитетные док-и: `docs/06-data-layer-and-storage.md` (retention/cold), `docs/fa/journal.md`
(`JR-I-*`, `DET-I-1`), `docs/05-contract-layer.md` §4/§6, `docs/rfc/CT-RFC-02-*`.

## Архитектурные решения

| # | Вопрос | Решение M-08 |
|---|---|---|
| E1 | Где живёт provenance | В **заголовке сегмента**, не в `Event` (при 2.8 GB/сут тег в каждом событии — гигабайты мусора; писатель сегмента ровно один, `JR-I-1`). CT-RFC-02 §2 |
| E2 | Порог ротации | Сегмент закрывается по размеру (**1 GiB**, конфиг) ИЛИ при рестарте писателя. Имя `segment-NNNNNNNN.jrnl`, монотонный индекс; `seq` продолжается СКВОЗЬ сегменты (тотальный порядок — один на журнал, `JR-I-1`) |
| E3 | Ретеншен | Политика: горячие сегменты на диске (окно `retention_days`, дефолт 14), холодные — выгрузка в Storage Box + удаление локально **ТОЛЬКО после подтверждённой выгрузки** (checksum совпал). Удаление невыгруженного сегмента невозможно выразить в API (типовой барьер, не дисциплина) |
| E4 | **Fail-closed по диску** | Свободного места < `min_free_bytes` (дефолт 10 GiB) → `append` возвращает storage-guard-ошибку, **ни один байт и ни один `seq` не тратятся**; состояние наблюдаемо через `storage_status().writable == false` (recorder публикует его в heartbeat → видно без ssh) + лог/алерт. **`Sys`-событие в журнал НЕ пишется** (обещание снято, C-005 M4): писать в журнал в момент, когда запись запрещена, — самопротиворечие. Тихо переполнить диск и умереть запрещено |
| E5 | Чтение | `journal::stream(dir, EpochFilter) -> io::Result<(Vec<SegmentHeader>, impl Iterator<Item=io::Result<Event>>)>` — **итератор**, O(1) памяти на сегмент-буфер. `read_all` остаётся ТОЛЬКО для тестов/малых фикстур и помечается `#[deprecated]`-комментарием в docs; прод-путь research — стрим |
| E6 | Эпохи | Читатель обязан назвать `EpochFilter` (`OwnCaptureOnly` / `Explicit(vec![epoch_id])`). Дефолт `OwnCaptureOnly` — вендор/синтетика в обучение по умолчанию НЕ попадают (CT-RFC02-3/4) |
| E7 | Память (TD-016) | **Корень найден по коду:** `venue-binance::apply_diff_to_book` вставляет уровни в `BTreeMap` и удаляет только при `size==0` — уровни, из которых цена ушла, апдейтов больше не получают и живут ВЕЧНО (`MAX_REL_DIST` применяется лишь к ЭМИССИИ). Измерено оракулом: 50k→200k диффов = 100k→400k уровней (линейно). Контракт: **кап `MAX_BOOK_LEVELS_PER_SIDE = 5000`** (глубина REST-снапшота), эвикция дальних от mid; топ книги не трогается. Writer-цикл recorder'а отдельным оракулом проверен и НЕ течёт (регресс-guard остаётся) |
| E8 | Gap-статистика | Инструмент считает разрывы записи (по `Sys::ConnDown/ConnUp` + монотонности `ts_wall_ms` между соседними событиями) → `research/data-quality/gaps-<epoch>.json`. Любой отчёт (R-NNN) обязан ссылаться на него (иначе метрики считаются по дырявым данным) |
| E9 | Deploy-гейт | `deploy.yml` получает `needs: ci` — красный CI больше не может выкатить прод (находка reviewer'а 2026-07-13: Deploy зеленел, пока CI ещё шёл) |

  (сдвиг превратил бы наш захват в вендорские данные при чтении старых сегментов).
- `crates/journal/tests/red_rotation.rs` — E2/CT-I-6: несколько сегментов; индексы без дыр;
  **заголовок в КАЖДОМ сегменте**; `seq` сквозной через границы (ни потерь, ни дублей);
  рестарт писателя не переиспользует `seq`.
- `crates/journal/tests/red_stream_bounded.rs` — **E5, ПРОД-МАСШТАБ** (16/64 MiB, counting-
  allocator): стрим отдаёт все события по порядку; пик < 8 MiB; **память O(1) по размеру
  журнала** (ловит и `read_all`, и «читаем долю файла» — на 15.0 GB доля снова убьёт машину).
  Анти-плацебо: контрольное полное чтение сегмента обязано превышать бюджет.
- `crates/journal/tests/red_segments_epochs.rs` — CT-RFC02-1..4: боевой сегмент БЕЗ заголовка
  (байт-в-байт формат VPS) читается вечно ТОЛЬКО по декларации; незадекларированный/битый/
  с чужим префиксом/**усечённый ниже `size_bytes_at_decl`** → `Err`; **дефолт `OwnCaptureOnly`
  исключает `Vendor`/`Synthetic`** (наивное «читаем все сегменты каталога» падает);
  смешение эпох — только явным перечислением; `headers()` доносит provenance до отчёта.
- `crates/journal/tests/red_retention.rs` — E3/E4: **disk-guard fail-closed** (мало места →
  `append` → `Err`, а не тихая смерть); `free_bytes` — реальное место, не заглушка;
  **`prune_segment` требует `ColdCopyProof`** (приватный конструктор → «удалить невыгруженное»
  нельзя ВЫРАЗИТЬ; `compile_fail`-доктест); **битая холодная копия → сверка Err, proof не
  выдан, сегмент остаётся на диске**.
- `crates/research-cli/tests/red_stream_grid.rs` — E5: грид на журнале, который не влезает
  в бюджет как `Vec<Event>`, отрабатывает bounded-memory; **ЭКВИВАЛЕНТНОСТЬ**: стрим-грид
  даёт РОВНО те же `CellResult` (PnL до цента, интенты, филлы, длина returns), что in-memory
  `run_grid` — «оптимизация» не смеет тихо изменить измеряемую логику (урок M-07).

**Bounded-RSS recorder'а (E7)** покрывается тем же counting-allocator оракулом на writer-пути
(`red_stream_bounded` + `red_rotation` гоняют десятки тысяч `append` через ротацию) плюс §8
eyes-on на VPS (RSS после суток аптайма). Отдельный recorder-оракул заводится, ЕСЛИ §8 покажет
рост — сейчас лик не доказан (одна точка 48 MiB), а тест на «5 часов аптайма» в CI не живёт.

## N1 (вопрос reviewer'а): кап 5000 уровней vs полосы OBI — ОТВЕТ

**Кап по числу уровней — неверный контракт.** Эмиссия в журнал bucketed по полосам до ±60%
от mid, и в сумму полосы входят ВСЕ уровни внутри окна. Число уровней ничего не говорит о
дистанции (тик-плотность разная), поэтому «5000/сторону» резало бы ровно то, из чего считается
сигнал. Граница переформулирована в терминах **дистанции** (контракт v2 §B); кап остаётся
только как аварийный backstop (50k/сторону) с логом-тревогой при срабатывании.

**Открытое следствие (D):** если после band-эвикции память ВСЁ РАВНО растёт — значит уровни
внутри окна реальны, и хранить сырую книгу нельзя вовсе: правильный фикс — инкрементальные
bucket-агрегаты вместо полной книги (дизайн M-09). Поэтому §8 обязан измерить **число in-band
уровней**, а не только RSS: атрибуция лика к книге пока сделана по коду, а не доказана на проде.

## Контракт доставки ретеншена (задача 14, architect)

**D1. Один образ, а не два.** `Dockerfile` собирает и копирует **оба** бинаря
(`--bin recorder --bin journal-retention`). Отдельный образ для уборки отвергнут: ретеншен
читает/удаляет сегменты того же формата, что пишет recorder — **расхождение версий кода
журнала между образами = порча/потеря данных**. Один образ ⇒ формат всегда один.

**D2. Сбор важнее уборки.** `ENTRYPOINT` остаётся `recorder`; ретеншен — отдельный
compose-сервис `journal-retention` под `profiles: ["ops"]`: он **не поднимается** вместе с
recorder'ом и не может его уронить. Запуск: `docker compose run --rm journal-retention …`.

**D3. Холодное хранилище.** Hetzner Storage Box монтируется на ХОСТЕ в `/mnt/journal-cold`
(CIFS, `fstab`), в контейнер прокидывается bind-mount'ом `${JOURNAL_COLD_DIR:-/mnt/journal-cold}:/cold`.
Хранилище недоступно → `verify_cold_copy` падает → **exit 2, prune НЕ выполняется** (fail-closed:
`ColdCopyProof` не выдан ⇒ удалить нечего). Данные никогда не удаляются «в никуда».

**D4. Планировщик — в РЕПО, а не в голове оператора.** `deploy/cron.d/journal-retention`:
ежедневный **`--mode dry-run`** (дефолт бинаря уже такой), лог в файл, **алерт на exit≠0**.
`--mode apply` включается ОТДЕЛЬНО, оператором, после того как он глазами прочитал отчёт
dry-run'а (и остаётся ручным до появления алертинга P2.5/M-09).

**D5. Контракт exit-кодов (на них вешается алерт):**

| Код | Значение | Реакция |
|---|---|---|
| 0 | план выполнен (или dry-run отработал) | — |
| 1 | ошибка аргументов/план не построен | чинить вызов |
| 2 | **сверка холодной копии не прошла** — сегменты остались горячими | P0: холодное хранилище сломано, данные не выгружаются |
| 3 | **disk_pressure**: места мало, а выгружать нечего | P0: сбор данных остановится по disk-guard |

**D6. `deploy/README.md`** — runbook: как смонтировать Storage Box, как прочитать отчёт
dry-run'а, как включить `apply`, что означают коды 2/3.

**Почему гейт — сборка образа, а не греп по Dockerfile.** Греп удовлетворяется текстом; TD-020
дважды родился именно из «написано, но не доставлено». CI-job `delivery` **собирает прод-образ и
ЗАПУСКАЕТ `journal-retention --help` внутри него**; §8 — реальный `dry-run` на VPS. Только запуск
доказывает существование.

## Контракт компакции (задача 15, architect)

**Порядок обязателен — данные незаменимы:**
1. **Активный сегмент не сжимается никогда** (в него пишут прямо сейчас) → `Err`.
2. Пишем во временный `*.jrnl.zst.tmp` — падение на середине оставляет оригинал целым.
3. **Верификация ДО удаления:** временный файл распаковывается и сверяется по sha256 с
   оригиналом. Расхождение → `Err`, оригинал остаётся. Тот же принцип, что `ColdCopyProof`:
   удалить можно лишь то, чья копия **доказано** читается.
4. `fsync` + атомарный `rename` → и только потом удаление оригинала.
5. `keep_raw` последних закрытых сегментов остаются несжатыми (свежее читают чаще).
6. Чтение (`stream`) — **потоковое**: сжатый сегмент НЕ распаковывается в память целиком
   (на боевом 1 GiB сегменте это OOM — класс TD-011).

**Взаимодействие с ретеншеном:** в холодное хранилище уезжает уже сжатый `.zst` (9× экономии
трафика и места). `verify_cold_copy` сверяет хэш сжатого файла.
