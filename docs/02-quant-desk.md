# 02 — LLM-квант-деск: команда агентов и исследовательский цикл

STATUS: DESIGN v1 (2026-07-10, Fable). Родственные: 01 (движок), 03 (интеграция).
Принцип №1: **LLM только на краях цикла** (гипотеза, код сигнала, интерпретация);
вся ОЦЕНКА — детерминированный Rust-compute (`research-cli`), ноль токенов.
Принцип №2: **LLM никогда не оценивает собственную работу** — оценивают движок,
независимый критик и человек (паттерн proposer → validator → operator).

---

## §1. Роли (агентные профили)

| Роль | Модель-класс | Что делает | Что НЕ делает |
|---|---|---|---|
| `quant-pm` | дешёвая/или founder сам | ведёт бэклог гипотез, приоритезация (идеи founder'а — приоритет), диспетчеризация | не решает промоушены |
| `hypothesis-researcher` | средняя | Hypothesis-карточки: из литературы, из аномалий в журналах, из идей founder'а; ПРЕ-РЕГИСТРАЦИЯ критериев фальсификации | не пишет код, не видит test-данных |
| `signal-engineer` | средняя/кодовая | SignalSpec → Rust-модуль в `crates/signals/` + unit-тесты + детерминизм-тест | не трогает risk/oms/journal/venues (scope-guard) |
| `backtest-runner` | скрипт (не LLM) / дешёвая | гоняет гриды через `research-cli`, собирает metrics.json, обновляет trials-ledger | не интерпретирует |
| `risk-critic` | **сильная** (тут не экономим) | адверсарий: обязан попытаться убить каждый отчёт (чек-лист §4) | не предлагает стратегий (независимость) |
| `portfolio-analyst` | средняя | корреляции с live-набором, предложение веса/размера, capacity-оценка | не подписывает |
| **founder** | человек | ЕДИНСТВЕННАЯ подпись на промоушенах и весах (HDP) | — |

Инфраструктурно — те же механики, что в EINHARD: агентные профили с зонами доступа,
sacred-тесты, verify-гейты. Экономия: Fable не участвует в рутине цикла вообще;
дорогая модель только у risk-critic (ложноположительная стратегия стоит депозита,
это asymmetric cost — как security-review).

## §2. Артефакты (файловые контракты)

```
research/
├── backlog.md                      # очередь гипотез с приоритетами (quant-pm)
├── trials-ledger.json              # ГЛОБАЛЬНЫЙ счётчик всех испробованных вариантов (append-only)
├── hypotheses/H-YYYYMMDD-<slug>.md # Hypothesis-карточка (ПРЕ-РЕГИСТРАЦИЯ, см. §3)
├── specs/S-NNN-<name>.md           # SignalSpec: формула, параметры+диапазоны, данные, издержки
├── reports/R-NNN-<run>.md + .json  # валидационный отчёт (генерит research-cli + интерпретация)
├── critiques/C-NNN.md              # вердикт risk-critic (KILL | CONCERNS | PASS)
├── decisions/D-NNN.md              # подписанные решения founder'а (промоушен/вес/ретайр)
└── registry/signals.json           # Реестр сигналов — стык с движком (03 §2)
```

## §3. Цикл (одна гипотеза от идеи до live)

1. **Гипотеза (пре-регистрация).** Карточка ДО касания test-данных: идея, механизм
   («почему это должно работать — кто на другой стороне и почему он платит»),
   данные, параметры и их диапазоны, **критерии фальсификации** (при каких числах
   гипотеза считается мёртвой), ожидаемая ёмкость. Идеи founder'а входят сюда же
   (пример: H-20260710-obi-asym — «имбаланс depth-полос 3%/8% ≥ θ → BUY»).
2. **SignalSpec + код.** signal-engineer: формализация → Rust-модуль (чистый,
   детерминированный) + unit-тесты + тест детерминизма. Код-ревью гейт: никакого
   доступа к будущему (только `Event`-поток), никакого I/O.
3. **Грид на train.** backtest-runner: `research-cli grid` по диапазонам ТОЛЬКО на
   train-периоде; каждая ячейка грида → +1 в trials-ledger. Отбор топ-K конфигураций.
4. **Валидация.** Только топ-K: OOS-период + walk-forward + стресс-срезы (по режимам
   волы, по времени суток, по дням фандинга) + чувствительность к издержкам ×1.5 и
   к латентности ×2. Метрики: net PnL, Sharpe, **deflated Sharpe с учётом trials-ledger**,
   max DD, fill-rate, turnover, capacity, decay-кривая.
5. **Критика.** risk-critic по чек-листу §4 → KILL / CONCERNS / PASS. KILL —
   мотивированный, в карточку гипотезы (отрицательные результаты ХРАНИМ — они
   экономят будущие токены).
6. **Решение founder'а №1** → статус `paper`. Сигнал крутится в paper-режиме N недель
   (движок 01 §8-9); авто-отчёт sim-vs-paper дивергенции.
7. **Решение founder'а №2** → статус `live` с весом от portfolio-analyst, через
   очередь решений (03 §3) → live-micro.
8. **Мониторинг и смерть.** decay-watch: скользящая метрика vs валидационная;
   пробой → авто-предложение `retired` → подпись. Смерть сигнала — штатное событие.

## §4. Анти-оверфит дисциплина (жёсткая, встроенная в гейты)

1. **Пре-регистрация** критериев фальсификации до теста (§3.1) — иначе отчёт невалиден.
2. **Time-split навсегда**: train / validation / test; test-период трогается ОДИН раз
   на финальной валидации; никакого подбора на OOS.
3. **Trials-ledger глобален**: каждая ячейка каждого грида каждой гипотезы; deflated
   Sharpe / поправка на множественные сравнения считается от него. Ledger append-only.
4. **Чек-лист критика** (минимум): lookahead/leakage (фичи из будущего? метки из
   будущего?); survivorship (выбор пары/периода задним числом?); издержки и латентность
   честные? режимная зависимость (работает только в одном квартале?); ёмкость реальна
   для наших размеров? корреляция с уже-live сигналами (это новая альфа или та же)?
5. **Paper — обязательный карантин.** Ни один сигнал не идёт train→live напрямую.
6. **Founder подписывает дважды** (paper, live) — HDP-гейт, как в EINHARD.

## §5. Экономика цикла

- Оценка (гриды/валидация) = Rust-compute: тысячи прогонов за копейки, 0 токенов.
- LLM-токены: карточка (~1 запуск средней модели), код сигнала (1-2), интерпретация
  отчёта (~1), критика (1 сильной). Порядок: единицы запусков на гипотезу.
- Хранение отрицательных результатов + trials-ledger предотвращают повторную оплату
  одних и тех же идей.
- Fable — только: этот дизайн, эволюция чек-листов/гейтов, разбор спорных вердиктов.
