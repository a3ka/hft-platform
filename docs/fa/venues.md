## §2. Стратегическая роль
`venues` — единственная дверь между платформой и внешним миром бирж: он подписывается
на рыночные данные и исполняет ордера через биржевые API, нормализуя ВСЁ в канонический
`Event`/`EventKind` (05 §2) до того, как что-либо попадёт в журнал. Позиция в потоке:
`[venues] → book → signals → alpha → portfolio → strategy → risk → [venues]` (обратная
дуга — исполнение уже одобренных ордеров). `venues` — единственный компонент, которому
разрешено знать о конкретной бирже (WS-схема, REST-эндпоинты, подпись действий,
rate-лимиты); всё выше по конвейеру говорит только на языке `Event`, никогда на языке
Hyperliquid или Binance. Это структурный барьер, не соглашение: novel venue = новый
адаптер-крейт + запись в реестре, ноль правок в `book`/`signals`/`risk`/`oms`.

**Emitter, не owner** (зеркало `integrations` INTEG-I-8 из EINHARD): `venues` нормализует
и эмитит события в журнал — он никогда не держит авторитетное состояние миссии, позиций
или риска. Позиции/PnL считает `risk` (recon читает биржу read-only, но владение — у
`risk`); что торговать — решает `strategy`. `venues` — труба, не мозг.

## §3. Что модуль ЕСТЬ
**Онион-подструктура:**
- core (без I/O): `traits/` — `MarketDataFeed`, `OrderGateway` (сигнатуры, §6); `registry/` —
  чистая таблица `venue_id → adapter constructor` (данные, не сеть).
- mid: `normalize/` — чистые функции перевода venue-специфичного сырья (уже распарсенного)
  в канонический `EventKind`; тестируемо без сети (вход — venue JSON-фикстура, выход —
  `Event`).
- outer: `venue-hyperliquid/`, `venue-binance/` — фактические I/O-адаптеры: WS-клиент,
  REST-клиент, подпись действий, reconnect/backoff, rate-limit учёт на своей стороне.

**Доменный словарь (T2/T3, владеет крейт):**
- `trait MarketDataFeed` / `trait OrderGateway` — контракты адаптера (§6).
- `VenueId` — типизированный идентификатор (`"hyperliquid"`, `"binance"`), НЕ строка
  сравниваемая в core-логике (см. VN-I-3).
- `AdapterRegistry` — `VenueId → Box<dyn Fn() -> Adapter>`, наполняется на старте движка
  из конфига (какие venue активны в этом запуске).
- `ClientOrderId` — детерминированный `hash(strategy_id, seq, nonce)` (§9).
- `VenueCredentials` — держится ТОЛЬКО внутри конкретного адаптера, никогда не журналится
  и не логируется в открытом виде.
- `RateLimitBudget` (T3, внутри адаптера) — venue-специфичный учёт квоты запросов;
  НЕ авторитетный бюджет ордер-скорости для риск-гейта (тот считает `risk` независимо,
  RK §5 п.4 — намеренное дублирование двух разных вещей: биржевой rate-limit ≠ риск-лимит
  на скорость торговли).

**Обработка отказов/деградации:**
| Условие | Детерминированный исход |
|---|---|
| WS-разрыв | `Sys(ConnDown)` в журнал СИНХРОННО, до попытки reconnect (VN-I-6); авто-reconnect с exp backoff + jitter |
| Реконнект успешен | Запрос свежего снапшота у биржи → `Md(L2Snapshot)`; recon (risk) сверяет позиции/ордера отдельно |
| Venue REST rate-limit достигнут (со стороны биржи) | Явный `Ord(Reject{reason: rate_limited})`, НЕ тихий drop намерения (VN-I-9) |
| Ключ подписи недоступен | `OrderGateway::place` отказывает немедленно (fail-closed; нет подписи — нет ордера) |
| Malformed/непарсибельное сообщение биржи | Событие дропается + логируется как integrity-warning; НИКОГДА не фабрикуется правдоподобное значение (VN-I-7) |
| Дублирующийся/не-по-порядку seq от биржи | Передаётся в журнал ЧЕСТНО как есть — детекцию гэпа и реакцию на неё делает `book` (§4 п.1), не `venues` |
| Ресинк-намерение от `book` (§6 `book.md`) получено | `venues` выполняет REST-запрос снапшота, пишет `Md(L2Snapshot)` в журнал |
| Биржа сообщает fill, расходящийся с локальным ожиданием | `venues` пишет `Ord(Fill)` КАК СООБЩИЛА биржа (источник правды — биржа); расхождение ловит `risk` recon, не `venues` |

## §4. Что модуль НЕ ЕСТЬ
1. **НЕ book-builder** — не реконструирует L2-состояние и не считает microprice/depth;
   только нормализует сырые дельты в события. Книгу строит `book`.
2. **НЕ сигнал/стратегия** — не имеет мнения, что и когда торговать; это `signals`/`strategy`.
3. **НЕ risk-гейт** — не решает, безопасен ли ордер; `OrderGateway::place` принимает ТОЛЬКО
   уже одобренный `risk::RiskApproved<Order>` (§6, зеркало RK-I-1 со стороны `venues`) —
   `venues` физически не может отправить неодобренный ордер, потому что тип неодобренного
   ордера не компилируется в вызов `place`.
4. **НЕ owner состояния миссии/риска/позиций** — emitter-not-owner (§2); авторитетные
   позиции/PnL держит `risk`, не `venues` (даже recon-чтение у биржи — read-only проверка,
   не источник истины для собственного состояния `venues`).
5. **НЕ принимает решение о ресинке** — `book` детектирует гэп и заявляет намерение;
   `venues` только ИСПОЛНЯЕТ REST-запрос по этому намерению (см. `book.md` §6).
6. **НЕ угадывает/фабрикует данные** — на malformed-сообщении или таймауте дропает и
   логирует, никогда не интерполирует правдоподобное значение (анти-`rand()`/анти-
   «фейк-контекст» урок hft-core-rs, DESIGN §9).

## §5. Реестр адаптеров (паттерн EINHARD R-CANON-6 / SD-1)
Новый venue = (1) новый крейт `venue-<name>`, реализующий `MarketDataFeed` + `OrderGateway`;
(2) одна запись в `AdapterRegistry` (`venue_id → constructor`). **Ноль правок** в `book`,
`signals`, `risk`, `oms` — они видят только канонические `Event`, никогда venue-специфику.
Core-крейт `venues` НЕ содержит ветвления по имени venue (`if venue_id == "hyperliquid"`
в core-логике запрещено; grep-канарейка VN-I-3) — вся venue-специфика заперта внутри
адаптер-крейта. Это прямой перенос `integrations`-паттерна EINHARD (SD-1 замороженный
реестр адаптеров): расширяемость без ревью центральной логики, при этом добавление venue
всё равно проходит обычный PR-ревью (новый крейт, новые тесты) — просто не трогает чужой код.

## §6. Трейты `MarketDataFeed` / `OrderGateway`
```
trait MarketDataFeed {
    fn subscribe(&mut self, instruments: &[Instrument],
                 channels: &[Channel]) -> Result<EventStream, VenueError>;
    // channels: l2, trades, funding, mark, userFills — нормализованные в Md(...)/Ord(...)
}

trait OrderGateway {
    fn place(&self, order: risk::RiskApproved<Order>) -> Result<ClientOrderId, VenueError>;
    fn cancel(&self, id: ClientOrderId) -> Result<(), VenueError>;
    fn batch(&self, ops: &[GatewayOp]) -> Result<Vec<Result<(), VenueError>>, VenueError>;
    fn cancel_all(&self, instrument: Option<Instrument>) -> Result<(), VenueError>;
}
```
`place` — единственный публичный путь размещения ордера в любом адаптере; сигнатура
буквально требует `risk::RiskApproved<Order>` (не `Order`), поэтому байпас риск-гейта не
выражается в системе типов (VN-I-1). Это зависимость `venues → risk` ПО ТИПУ (не по
поведению/состоянию) — допустимо, потому что `risk` сам не зависит ни от чего, кроме
журнальных типов (risk.md §1), т.е. граф остаётся ациклическим (см. §O — подлежит
подтверждению arch-lint DAG-проверкой на реализации). `cancel_all` — используется
`killswitch`-протоколом (risk.md §7) как основной механизм при разрыве.

## §7. venue-hyperliquid (первый адаптер) `[verify-at-impl]`
- **MD:** WS-каналы `l2Book`, `trades`, `userFills`, `funding` + REST `info`/`exchange`
  для снапшотов и служебных запросов.
- **Подпись действий:** класс EIP-712 (точная схема подписи — `[verify-at-impl]`, сверяется
  с актуальной документацией HL на входе в P1/P3).
- **Rate limits:** точные значения по эндпоинту — `[verify-at-impl]`; бюджетируются со
  стороны `oms` (01 §6) для решений о торговле, и локально в адаптере для собственно
  HTTP/WS-квоты (две разные книги учёта, см. §3 `RateLimitBudget`).
- **Cancel-on-disconnect:** есть ли нативный биржевой механизм — `[verify-at-impl]`;
  независимо от ответа, `killswitch`-sweep (risk.md §7) остаётся линией страховки —
  адаптер не полагается ИСКЛЮЧИТЕЛЬНО на биржевой CoD.
- **Testnet:** отдельный конфигурационный профиль (эндпоинты + креды), обязателен для P3
  (48ч чистого testnet-MM — DESIGN §10 ворота P3) до выхода на live-micro.

## §8. venue-binance (P5, деферред)
Тот же трейт-контракт (`MarketDataFeed`/`OrderGateway`); мотивация появляется раньше
собственно ордер-стороны — сигнал №3 (cross-exchange lead-lag, DESIGN §8 п.3) хочет
MD-фид Binance до того, как OMS-сторона активна на нём. Разрешено включать
`venue-binance` как MD-only адаптер раньше P5, если `signals`/`research` запросят —
`OrderGateway`-часть остаётся неактивной (нет testnet-подготовки/лимит-профиля) до P5.
Полная спецификация — отдельный milestone на входе в P5, не в этом FA.

## §9. Детерминизм и идемпотентность
`client_order_id = hash(strategy_id, seq, nonce)` — чистая функция от журнальных величин
(`seq` — sequence-номер события-намерения, не wall-clock). Следствия:
- Реплей журнала воспроизводит ТЕ ЖЕ `client_order_id`, что и вживую (равенство №1,
  DESIGN §1) — форензика может однозначно сопоставить намерение и фактический ордер.
- Ретрай на сетевой сбой с ТЕМИ ЖЕ входами даёт ТОТ ЖЕ id → биржа (если поддерживает
  идемпотентность по client-id) естественно дедуплицирует повторную отправку.
- Никакого UUID/timestamp-based id — оба являются недетерминированными по определению и
  ломают равенство №1 (тот же класс урока, что и `rand()`-гэп-детекция, DESIGN §9).

## §N. Интерфейсные контракты
- **Consumed:** `risk::RiskApproved<Order>` (T2 ← `risk`, ТОЛЬКО как тип аргумента `place`,
  не как поведенческая зависимость); собственные `Sys(ConnDown)`/`Ctl(Disarm)` (T1, читает
  свои же эмиссии для внутренней логики reconnect); ресинк-намерение от `book` (рабочий
  T1-кандидат, см. `book.md` §O — совместно не зафиксирован).
- **Produced:** `Md(L2Delta|L2Snapshot|Trade|Funding|MarkPx)` (T1 → журнал → `book`,
  `signals`, `research-cli`); `Ord(Ack|Reject|Cancelled|Fill{maker|taker}|Expire)` (T1 →
  журнал → `oms`, `risk`); `Sys(ConnUp|ConnDown|Heartbeat)` (T1 → журнал).
- **Refused:** любой путь размещения ордера, принимающий сырой `Order` без обёртки
  `RiskApproved` (не компилируется); venue-специфичные типы, покидающие адаптер-крейт
  (нормализация обязана произойти внутри адаптера); прямые вызовы из `signals`/`strategy`
  в `venues` (эти крейты не видят `venues` вовсе — только журнал).

## §I. Инварианты (`VN-I-1..9` + `VN-I-Z`) — RED-оракулы (тест падает на заглушке)
1. **VN-I-1** `OrderGateway::place` принимает ТОЛЬКО `risk::RiskApproved<Order>`; ни в одном
   адаптере нет второго публичного метода размещения, принимающего сырой `Order` (типовой
   барьер + grep-канарейка по всем `venue-*` крейтам).
2. **VN-I-2** `client_order_id` — чистая функция `hash(strategy_id, seq, nonce)`; НИКОГДА
   не включает wall-clock или источник случайности (property-test: одинаковый вход → одинаковый id).
3. **VN-I-3** Core-крейт `venues` не содержит ветвления по конкретному `venue_id`
   (`if venue == "hyperliquid"` и подобные — запрещены вне адаптер-крейта; grep-канарейка).
4. **VN-I-4** `venues` не владеет авторитетным состоянием миссии/риска/позиций (grep/тип-тест:
   ни `RiskState`, ни `Position`-подобная структура не инстанциируется в крейте `venues`).
5. **VN-I-5** Venue-специфичные wire-типы не покидают адаптер-крейт; наружу — только
   канонический `Event` (публичный API-surface тест на `venue-hyperliquid`/`venue-binance`).
6. **VN-I-6** На WS-разрыве `Sys(ConnDown)` эмитится СИНХРОННО, до попытки reconnect —
   не существует окна, где соединение уже мертво, но консюмеры считают его живым.
7. **VN-I-7** Malformed/непарсибельное сообщение биржи дропается и логируется, НИКОГДА не
   фабрикуется в правдоподобное значение (анти-«фейк-контекст», DESIGN §9).
8. **VN-I-8** Backoff реконнекта детерминированно воспроизводим в тестах (seed из
   attempt-count/событийного времени, не голый wall-clock `rand()`) `[verify-at-impl]`
   точный источник jitter.
9. **VN-I-9** При достижении venue-стороннего rate-limit — явный `Ord(Reject{reason:
   rate_limited})`, НИКОГДА тихий drop намерения ордера (зеркало духа RK-I-5 «никаких
   проглоченных ошибок»).
- **VN-I-Z** Cornerstone-citability: §§ этого FA STABLE/APPEND-ONLY; правки — named amendment.

## §P. Фаза реализации
**P1 (Data plane, MD-сторона venue-hyperliquid)** — блокируется P0 (журнал/EventKind).
**P3 (Risk+OMS, OrderGateway-сторона venue-hyperliquid)** — размещение ордеров активируется
вместе с `risk`/`oms`/testnet-торговлей (DESIGN §10). `venue-binance` — P5, MD-часть может
стартовать раньше по запросу `signals`/`research`(§8). Блокирует: `book` (P1, читает `Md`),
`research-cli` grid-раннер (P2, читает 7 дней записанных P1-данных), testnet-торговлю (P3).
Mock-точка: пока `venue-hyperliquid` не полностью готов, `book`/`signals` работают против
recorder-фикстур (записанный поток, DESIGN §10 P1 «recorder-демон»); `OrderGateway`-сторона
может разрабатываться против `sim`-крейта (paper/mock gateway) до реальной подписи/testnet.

## §O. Открытые вопросы
- `[verify-at-impl]` HL: точная схема WS-каналов (`l2Book`/`trades`/`userFills`/`funding`),
  формат EIP-712-подписи действий, точные rate-лимиты по эндпоинту, наличие нативного
  cancel-on-disconnect, testnet-эндпоинты/faucet — сверяется с докой HL на входе в P1/P3.
- Конкретный `EventKind` для ресинк-намерения от `book` (совместный вопрос с `book.md` §O) —
  требует contract-RFC до конца P1.
- Зависимость `venues → risk` ПО ТИПУ (`RiskApproved<Order>` в сигнатуре `place`) требует
  явного подтверждения arch-lint DAG-проверкой на реализации: граф ациклический (risk не
  зависит от venues), но текстовое «зависимости только вниз» в DESIGN §2 сформулировано по
  номеру пайплайн-слоя, а не по факту графа — стоит явно закрепить правило проверки, чтобы
  не спутать с реальным нарушением направления.
- Источник jitter для backoff (VN-I-8) — конкретный алгоритм не выбран.
- `venue-binance` MD-only early-start (§8) — решение о том, нужен ли он раньше P5, зависит
  от того, когда `signals`/`research` реально начнут калибровать lead-lag сигнал (DESIGN §8 п.3).

## §A. Антитезис (steelman против дизайна)
- «Реестр адаптеров ради одного venue (HL) на старте — преждевременная абстракция; проще
  захардкодить HL и обобщить, когда реально появится Binance.» — Контр: цена реестра сейчас
  — один trait plus одна строка регистрации; hft-core-rs накопил ИМЕННО такой долг (три
  несовместимых wire-формата, DESIGN §9), потому что абстракцию откладывали до «когда
  реально понадобится». Дёшево сейчас, дорого после того, как P5-код уже насажен на
  HL-специфику.
- «`OrderGateway::place` требует `risk::RiskApproved<Order>` прямо в сигнатуре трейта,
  определённого в `venues` — это протаскивает знание о `risk` в слой 1, размывая
  онион-историю "venues не видит стратегию".» — Контр: `risk` — намеренно near-leaf крейт
  (risk.md §1: не зависит ни от чего, кроме журнальных типов), так что зависимость
  `venues → risk` по одному маркерному типу не создаёт цикла и не тянет за собой ни
  `strategy`, ни `oms`. Альтернатива (барьер только на уровне `oms`, `venues::place`
  принимает сырой `Order`) слабее: гипотетическая ошибка в `oms`-диспетчинге всё ещё могла
  бы вызвать `place` в обход риска, если бы такой путь физически существовал в `venues`.
- «Честный `Ord(Reject{rate_limited})` вместо тихого drop — лишний шум в журнале при
  всплеске активности.» — Контр: тихий drop — это ровно тот способ, которым `oms` теряет
  представление о реальном состоянии намерения (заявка ушла в никуда, но никто не узнал).
  Явный reject — дешёвое событие; `oms` решает, ретраить или эскалировать, вместо того
  чтобы навсегда потерять след ордера.
