## §1. Идентичность модуля
- **Имя / крейт:** `journal` (`crates/journal/`).
- **Язык:** Rust (канон); Python-research читает журнал через сгенерированную JSON Schema.
- **Слой:** 0 (ядро; зависит только от `contracts`-типов).
- **Deploy:** in-process движка (единственный писатель) + off-line читатель (research).
- **Статус:** ACCEPTED 2026-07-10 (v1).
- **Карта секций:** §1 идентичность · §2 роль · §3 IS · §4 IS NOT · §5 событийная модель ·
  §6 запись/durability · §7 снапшоты и state_hash · §8 replay · §N контракты · §I инварианты
  (JR-I + DET-I-1) · §T RED · §P фаза · §O открытые · §A антитезис.

## §2. Стратегическая роль
`journal` материализует стержневой принцип платформы (DESIGN §1): **единый упорядоченный
поток событий с тотальным порядком**, из которого следуют три равенства —
`replay==реальность`, `backtest==paper==live`, `failover==replay`. Это не «логирование»:
журнал — ЕДИНСТВЕННЫЙ источник истины о состоянии; всякое состояние (`RiskState`, `Book`,
`RiskState`, позиции OMS) — детерминированная функция префикса журнала. Если журнал врёт
или недетерминирован, рушится вся система доказуемости (аудит каждого цента, форензика
убытка, честный бэктест). Поэтому это Layer 0 и cornerstone.

## §3. Что модуль ЕСТЬ
**Онион-подструктура:**
- core (без I/O): `event/` — типы `Event`/`EventKind` (реэкспорт T1 из `contracts`);
  `reduce/`-контракт (trait `Reducer`: чистая свёртка `(State, &Event) -> State`);
  `hash/` — детерминированный `state_hash` (канонический порядок полей).
- mid: `segment/` — сегментация лога, индекс по seq/времени.
- outer (I/O): `writer/` — append-only запись с fsync-политикой; `reader/` — итератор
  событий; `snapshot/` — периодические снапшоты состояния на диск.

**Доменный словарь (T1, определён в `contracts`, здесь используется):**
- `Event { seq: u64, ts_mono_ns: u64, ts_wall_ms: i64, kind: EventKind }` — единица потока;
  `seq` монотонен, единственный писатель.
- `EventKind` — закрытый версионируемый enum: `Md(...)`, `Ord(...)`, `Risk(...)`, `Recon(...)`,
  `Ctl(...)`, `Sys(...)` (полный состав — 01 §3 / 05 §2).
- `state_hash: [u8;32]` — sha256 канонической сериализации состояния; пишется в журнал
  каждые M событий (якорь детерминизма).
- `Snapshot { seq, state_bytes, state_hash }` — восстановительная точка.

**Обработка отказов/деградации (fail-closed):**
| Условие | Исход |
|---|---|
| Отказ записи/ fsync события класса Ord/Risk/Ctl | Halt движка (RK-I-5 — журнал не пишется = торговля стоит) |
| crc32 фрейма не сошлась при чтении | ошибка чтения, не «пропустить фрейм» (целостность > доступность) |
| Разрыв последовательности seq при replay | abort replay + алерт (журнал повреждён) |
| state_hash при replay ≠ записанному | abort + алерт (недетерминизм/повреждение — критично) |

## §4. Что модуль НЕ ЕСТЬ
1. **НЕ шина/брокер** — это НЕ event_bus hft-core-rs (там 3 wire-формата, `$`-баг, пустые
   DLQ). Один процесс-писатель, один формат, append-only файл. Никаких consumer-групп в
   рантайме торговли.
2. **НЕ база данных запросов** — не индексирует по произвольным полям, не отвечает на
   аналитические запросы (это research-cli читает журнал off-line).
3. **НЕ бизнес-логика** — не считает риск/книгу/сигналы; предоставляет поток и контракт
   свёртки, редьюсеры живут в своих крейтах (`risk`, `book`, ...).
4. **НЕ транспорт между модулями** — модули общаются через типы, а не через журнал как
   очередь; журнал — запись истины, не IPC.
5. **НЕ источник времени для логики** — логика берёт время ИЗ событий (`ts_*`), не из
   системных часов; журнал лишь проставляет метки при записи.

## §5. Событийная модель
- **Тотальный порядок:** единственный писатель присваивает `seq` монотонно; порядок =
  порядок присвоения seq (не wall-clock — часы неупорядочены на границах).
- **Время:** `ts_mono_ns` — для внутренней длительности/порядка; `ts_wall_ms` (int64 UTC) —
  для отчётов/сверок. Логика упорядочивает по seq, отображает по wall.
- **Деньги/цены:** fixed-point i64/u64 ×1e8 в payload (не f64 — детерминизм и точность).
- **Закрытый enum:** новые виды событий добавляются только через contract-RFC (CT-I-2),
  аддитивно (новый вариант в конце), со `schema_version` в сегменте (CT-I-6).

## §6. Запись и durability
- Формат фрейма: `postcard(Event)` + `crc32` + длина; сегментированные файлы (ротация по
  размеру/времени).
- **fsync-политика по классу события:** `Ord`/`Risk`/`Ctl`/`Recon` — синхронно (потеря
  ордера/решения недопустима); `Md`/`Sys(Heartbeat)` — батчем (объём высок, потеря тика
  восстановима переподпиской). Политика — часть контракта durability, не тюнинг.
- Единственный писатель: конкурентная запись запрещена (иначе seq неупорядочен); резерв
  читает, не пишет (failover = replay, §8).

## §7. Снапшоты и state_hash
- Каждый редьюсер-владелец (risk/book/...) умеет отдать сериализованное состояние; `snapshot/`
  пишет `Snapshot{seq, state, state_hash}` каждые N событий.
- **Инвариант согласованности:** `replay(snapshot_k) + tail(k+1..n) == replay(full 0..n)` —
  проверяется равенством `state_hash` (JR-I-4). Снапшот — оптимизация старта, НЕ
  альтернативная истина: если снапшот и полный replay разошлись — снапшот отбрасывается,
  источник правды = полный журнал.
- `state_hash` каждые M событий пишется в журнал как якорь: повреждение/недетерминизм
  ловится в точке, а не «где-то».

## §8. Replay
- `replay(range, reducer) -> State` — чистая детерминированная свёртка; одинаковый журнал →
  одинаковое состояние + одинаковые state_hash (DET-I-1 — центральный инвариант всей платформы).
- Режимы (01 §9) — это replay с разным источником/приёмником: backtest = replay
  исторического журнала в sim; live = свёртка живого потока; failover = резерв догоняет
  журнал первичного. ОДИН механизм.
- EOD-контроль: прогон дневного журнала → сверка `state_hash` → совпал = день аудитопригоден.

## §N. Интерфейсные контракты
- **Consumed:** `Event` от продюсеров (все модули эмитят события через writer); типы — из
  `contracts` (T1).
- **Produced:** упорядоченный поток `Event` (reader); `Snapshot`; `state_hash`-якоря. Всё T1.
- **Refused:** запись из >1 писателя; произвольные (не-`EventKind`) записи; f64 в денежном payload.

## §I. Инварианты (JR-I + DET-I-1) — RED-оракулы
1. **DET-I-1 (центральный)** replay одного журнала трижды → бит-идентичное состояние +
   равные `state_hash` (тест обязан падать на недетерминированной заглушке — напр. reducer
   с HashMap-итерацией без сортировки).
2. **JR-I-1** Единственный писатель; конкурентная запись невозможна (типовой/тест).
3. **JR-I-2** `seq` строго монотонен без дыр; разрыв при чтении → abort (не «пропустить»).
4. **JR-I-3** Класс Ord/Risk/Ctl fsync-нут до подтверждения записи (durability-тест).
5. **JR-I-4** `snapshot + tail == full replay` по `state_hash` (тест на рассогласование).
6. **JR-I-5** Отказ записи → Halt (зеркало RK-I-5; журнал не пишется = торговля стоит).
7. **JR-I-6** Старый журнал читается новым кодом навсегда (миграции; зеркало CT-I-3) —
   роундтрип-фикстуры прошлых `schema_version`.
8. **JR-I-7** Деньги/цены в payload — fixed-point, не f64 (grep/тип-канарейка).

## §P. Фаза реализации
**P0 (M-01)** — самый первый код платформы, ДО data-plane. Ничем не блокируется (зависит
только от `contracts`, M-00). Блокирует ВСЁ (никакой модуль не осмыслен без журнала).
Acceptance P0: 24ч записи реального HL-фида (через recorder P1-preview) + `replay ×3`
бит-идентичен (DET-I-1). Мок-точек нет — это фундамент.

## §O. Открытые вопросы
- Гранулярность снапшотов N и якорей M (баланс скорости старта vs объём) — калибровка на P1.
- Политика ротации сегментов (размер vs время) и архивации старых (hot/warm/cold — DESIGN §9).
- Сжатие сегментов at-rest: допустимо только с сохранением бит-идентичности после
  распаковки (SHA-совпадение) — иначе рушится DET-I-1; codec-решение отложено.
- Формат канонической сериализации для `state_hash` (детерминированный порядок полей всех
  редьюсеров) — зафиксировать до первого редьюсера.

## §A. Антитезис (steelman против дизайна)
- «Единственный писатель — узкое место по throughput на быстром рынке.» — Контр: mid-freq
  (ms–sec) далёк от лимитов append-only записи; single-writer покупает тотальный порядок
  бесплатно, а он — основа всех трёх равенств; при доказанной нужде (P5+) writer шардится
  по инструменту с отдельными журналами, но это преждевременно.
- «state_hash каждые M событий дорог.» — Контр: sha256 состояния редок (раз в M) и дёшев
  против стоимости необнаруженного недетерминизма (день торговли, который нельзя
  воспроизвести = нельзя объяснить убыток). Якорь — страховка, а не hot-path.
- «Бессмертие старого формата (JR-I-6) сковывает эволюцию схемы.» — Контр: это цена
  `replay==реальность`; альтернатива (сломать чтение старых журналов) уничтожает
  аудитопригодность истории — недопустимо для торговой системы. Миграции — управляемая
  дисциплина (contract-RFC), не блокер.
