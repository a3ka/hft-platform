# research-cli — Functional Architecture (FA)

> CORNERSTONE FA (мост движок↔деск). Authored by architect (Fable) 2026-07-10.
> STABLE/APPEND-ONLY. Единственный компонент, который держит И Rust-типы для быстрого
> чтения журнала, И продюсит T1 текстовые отчёты, которые читают LLM квант-агенты
> (03 §7 "research-cli (мост, 03)"). Здесь МЕХАНИЗИРОВАНА анти-оверфит дисциплина (02 §4) —
> гейты в инструменте, не в prose-чеклисте.

## §1. Идентичность модуля
- **Имя / крейт:** `research-cli` (`crates/research-cli/`).
- **Язык:** Rust (бинарь + библиотека); Python-research-тулинг — КОНСЮМЕР его T1-выходов
  (05 §5), не часть этого крейта.
- **Слой:** 7 (DESIGN §2).
- **Deploy:** dev-time / scheduled batch-процесс (cron/ad hoc CLI-вызов
  `backtest-runner`'ом или человеком) — НЕ часть торгового рантайма, не имеет процесса
  в горячем пути.
- **Статус:** DRAFT (первая версия FA).
- **Карта секций:** §1 идентичность · §2 роль · §3 IS · §4 IS NOT · §5 grid/walk-forward
  движок · §6 дисциплина trials-ledger · §7 ValidationReport/metrics.json · §8
  механизированные анти-оверфит гейты · §N контракты · §I инварианты RC-I-1..11 +
  RC-I-Z · §T RED-маппинг · §P фаза · §O открытые · §A антитезис.

## §2. Стратегическая роль
`research-cli` — **сама граница A/B данных** (03 §1): единственный компонент системы,
который одновременно (а) держит Rust-типы движка для БЫСТРОГО прямого чтения журнала
(`journal` крейт, T1 `Event`), и (б) продюсит T1-артефакты в текстовой/JSON форме
(`ValidationReport`/`metrics.json`), которые дальше читают LLM-агенты квант-деска
(`risk-critic`, `portfolio-analyst`, founder) БЕЗ необходимости самим парсить бинарный
журнал. Это буквально МОСТ (03) — по обе стороны разные исполнители (Rust-движок,
LLM-агенты), разные языки, разные жизненные циклы; `research-cli` — единственная точка,
где они физически встречаются.

Второе назначение — экономика (DESIGN §7, 02 §5): гриды и walk-forward — это ТЫСЯЧИ
прогонов симуляции по историческим данным; если бы это делал LLM-агент напрямую
(итеративно спрашивая модель "попробуй параметр X"), стоимость в токенах была бы
непомерной. `research-cli` — ЧИСТЫЙ Rust-compute: ноль LLM-токенов на сам перебор/оценку;
LLM тратится ТОЛЬКО на дизайн гипотезы, интерпретацию готового отчёта и критику —
единицы запусков на гипотезу (02 §5), а не на ячейку грида.

Третье назначение — анти-оверфит НЕ как договорённость, а как МЕХАНИЗМ: чек-лист 02 §4
(пре-регистрация, time-split, trials-ledger, честные издержки/латентность) реализован
как код, который ФИЗИЧЕСКИ не даёт обойти дисциплину (например, тестовый сегмент
структурно недостижим до прохождения val-гейта), а не как пункт в промпте LLM-агента,
который тот может забыть выполнить.

Позиция в потоке: ВНЕ горячего торгового конвейера `book→...→oms`. Читает `journal`
(read-only), пишет в `research/` (trials-ledger, reports). НЕ в реплей-пути движка.

## §3. Что модуль ЕСТЬ
**Онион-подструктура:**
- core (без I/O): `metrics/` — чистые функции над временными рядами fill/PnL-событий:
  Sharpe, deflated-Sharpe (с поправкой на счётчик из trials-ledger), maxDD, fill-rate,
  turnover, capacity-оценка, decay-кривая; `split/` — чистая логика time-split
  (train/val/test границы, "test уже тронут?" как явное булево состояние, не побочный
  эффект).
- mid: `grid/` — оркестрация перебора параметров `SignalSpec` через `sim`-модель
  fill'ов над историческим сегментом журнала (train), инстанцирует `Signal` для каждой
  ячейки; `walkforward/` — оконный перебор поверх `grid`; `ledger/` — читатель+аппендер
  trials-ledger (единственная точка записи, append-only, §6).
- outer: `main.rs` — CLI (`research-cli grid ...`, `research-cli validate ...`,
  `research-cli report ...`), чтение конфигов гипотез/спеков (`research/hypotheses/`,
  `research/specs/`), запись `metrics.json`/`R-NNN.md`, чтение журнала через
  `journal::Reader` (read-only handle).

**Доменный словарь (T2/T3):**
- `GridSpec` — диапазоны параметров `SignalSpec` + сегмент журнала (train) + режим
  издержек/латентности (baseline | ×1.5-cost | ×2-latency стресс-варианты).
- `TrialRecord` — {signal_id, params_hash, split, ts_wall_ms, code_hash, result_ref} —
  единица trials-ledger, append-only (T1, 05 §2).
- `TimeSplit` — {train_range, val_range, test_range, test_touched: bool} — явное
  состояние, не подразумеваемое.
- `WalkForwardWindow` — {train_window, test_window, step} — скользящее окно валидации.
- `ValidationReport`/`metrics.json` (T1, 05 §2) — итоговый детерминированный отчёт.

**Обработка отказов/деградации:**
| Условие | Детерминированный исход |
|---|---|
| Повреждённый/неполный сегмент журнала при чтении | abort с явной ошибкой; НИКАКИХ частичных/сфабрикованных результатов |
| Попытка повторно тронуть уже отмеченный `test_touched=true` сегмент без явного override+обоснования | отказ; требуется явный флаг + запись причины (аудит) |
| Отказ записи в trials-ledger (диск/permissions) | abort ВСЕГО grid-прогона (не продолжает "неучтённым" — испортило бы deflated-Sharpe глобально) |
| Дрейф версии схемы журнала vs ожидаемая инструментом | отказ вычисления, эскалация (не тихая деградация формата) |
| Недостаточно данных для окна walk-forward | явное поле метрики `N/A` (не экстраполяция, не ноль по умолчанию) |
| `SignalSpec` ссылается на несуществующий/устаревший `code_hash` в `crates/signals/` | отказ (зеркало CT-I-4/INTG-I-4 на стороне `research-cli`) |

## §4. Что модуль НЕ ЕСТЬ
1. **НЕ сигнал** — не производит торговую логику; код сигнала живёт в
   `crates/signals/`, пишет его `signal-engineer` через границу A (03 §4).
   `research-cli` лишь ИСПОЛНЯЕТ уже написанный сигнал по сетке параметров.
2. **НЕ орган промоушена** — не может менять `status` в
   `research/registry/signals.json` (граница B, 03 §2); промоушен candidate→paper→live
   — исключительно через подписанное `decisions/D-NNN` founder'а (INTG-I-2).
   `research-cli` производит ДОКАЗАТЕЛЬСТВО (`ValidationReport`), не решение.
3. **НЕ LLM** — детерминированный compute; ни одна ветка кода не делает вызов к LLM-
   провайдеру (RC-I-1). `risk-critic`/`portfolio-analyst`/founder ЧИТАЮТ его выход —
   `research-cli` не участвует в интерпретации, не пишет prose-нарратив сам.
4. **НЕ торговый движок** — не подключён к `venue`, не имеет пути к `Ctl(Arm)`/
   `OrderGateway`; читает журнал read-only, никогда не пишет в него события горячего
   пути (RC-I-7).
5. **НЕ risk-гейт** — анти-оверфит дисциплина — это СТАТИСТИЧЕСКАЯ валидация (годится
   ли сигнал), а не pre-trade проверка денежного риска (можно ли отправить ЭТОТ ордер
   сейчас); это разные оси, `risk` (крейт) не пересекается с `research-cli` по коду.
6. **НЕ рантайм-компонент** — нет латентностного бюджета в торговом пути; гриды могут
   идти часами/сутками — это ЦЕНА, которую платит research-time, а не хот-путь.

## §5. Grid/walk-forward движок (чистый compute)
`research-cli grid --spec S-NNN --split train` инстанцирует `Signal`-реализацию (из
`crates/signals/`, по `code_hash`, сверенному с реестром) для КАЖДОЙ ячейки сетки
параметров `SignalSpec`, прогоняет её через `sim`-модель fill'ов (01 §8) НАД
ИСТОРИЧЕСКИМ сегментом журнала, ограниченным `train`-диапазоном `TimeSplit`. Каждая
ячейка = один прогон = одна запись в trials-ledger (§6), НЕЗАВИСИМО от того, попала ли
она в топ-K (§3.3 отбор). Это ключевое отличие от "тихого" гиперпараметр-серча:
СЧИТАЕТСЯ КАЖДАЯ ПОПЫТКА, даже отброшенная — иначе deflated-Sharpe лжёт.

`walkforward` — то же самое поверх скользящих окон (`WalkForwardWindow`): вместо
единого train/val среза — серия окон, оценивающих устойчивость сигнала во времени
(режимная зависимость — пункт чек-листа критика 02 §4.4). Стресс-варианты (издержки
×1.5, латентность ×2) — ОТДЕЛЬНЫЕ grid-прогоны с собственными параметрами `sim`, а НЕ
пост-обработка готовых чисел (RC-I-10) — это гарантирует, что стресс честно проходит
через ту же модель fill'ов, а не через ручную аппроксимацию.

Топ-K отбор (после train-грида) — механическая сортировка по предварительной метрике
(например net PnL или Sharpe без deflation — deflation считается только на финальной
валидации, где известно полное N попыток); отбор НЕ трогает val/test-сегменты.

## §6. Дисциплина trials-ledger (append-only, глобальный)
`research/trials-ledger.json` — единственный глобальный источник "сколько всего попыток
было сделано" (05 §2). `research-cli` — ЕДИНСТВЕННЫЙ писатель (append-only handle;
никакого API для удаления/перезаписи существующей записи — RC-I-2). Каждая ячейка
каждого грида каждой гипотезы — плюс одна запись `TrialRecord`, независимо от исхода
(включая явный KILL — отрицательные результаты НЕ удаляются, INTG-I-7/RC-I-9).

deflated-Sharpe (§7) читает счётчик попыток СТРОГО из этого глобального ledger'а для
релевантного семейства сигналов — НИКОГДА из локального счётчика текущего прогона
(RC-I-3): иначе агент мог бы "обнулить" историю, запустив новый инструмент/процесс, и
deflation стала бы фиктивной. Целостность ledger'а защищена append-only дисциплиной
на уровне файловой операции (только `O_APPEND`) + опциональной hash-chain записью
(каждая запись содержит хэш предыдущей — аналог `state_hash` журнала, `[verify-at-impl]`
точный формат) для обнаружения ручного редактирования файла в обход инструмента.

## §7. ValidationReport / metrics.json
Финальный выход валидации (топ-K на val/test, стресс-варианты) — `ValidationReport`
(T1, 05 §2): net PnL, Sharpe, **deflated-Sharpe** (с trials-ledger, §6), max DD,
fill-rate, turnover, capacity-оценка, decay-кривая. Ключевое свойство — ДЕТЕРМИНИЗМ
(RC-I-5, зеркало DET-I-1 журнала): те же входы (хэш сегмента журнала + параметры +
`code_hash` + состояние ledger'а на момент запуска) → байт-идентичный `metrics.json` при
повторном запуске. Это то, что делает отчёт ДОКАЗАТЕЛЬСТВОМ, а не "результатом одного
прогона, который не воспроизвести" — критик и founder должны иметь возможность
перепроверить число самостоятельно.

Человекочитаемый нарратив (`research/reports/R-NNN.md`) сопровождает `metrics.json`, но
интерпретационный текст — НЕ продукт `research-cli` как LLM-вывод (§4.3); либо это
шаблонная генерация из чисел (детерминированная, без LLM), либо отдельно пишется
`backtest-runner`/`signal-engineer` поверх готовых чисел — сам `research-cli` остаётся
источником только МАШИННО-ПРОВЕРЯЕМЫХ метрик.

## §8. Механизированные анти-оверфит гейты (маппинг 02 §4)
Каждый пункт чек-листа 02 §4 реализован как код-гейт, а не prose-напоминание:

| 02 §4 пункт | Механизм в research-cli |
|---|---|
| (1) Пре-регистрация критериев ДО теста | `research-cli validate` отказывается запускать финальную валидацию без ссылки на `hypotheses/H-*.md` с заполненным разделом критериев фальсификации (парсинг + explicit-required поле) |
| (2) Time-split, test трогается один раз | `TimeSplit.test_touched` — явный флаг в состоянии прогона по гипотезе; вторая попытка чтения test-диапазона без override+обоснования отклоняется (§3 таблица отказов) |
| (3) Глобальный trials-ledger, deflated Sharpe от него | §6 — append-only, единственный писатель, deflation читает ТОЛЬКО из него (RC-I-3) |
| (4) Честные издержки+латентность, режимная зависимость | стресс-варианты — отдельные grid-прогоны через `sim` (§5), walk-forward окна ловят режимную зависимость (§5) |
| (5) Paper-карантин обязателен | `research-cli` НЕ имеет пути к `live`-`EventSink` вообще (§4.4) — карантин структурный, не дисциплинарный |
| (6) Двойная подпись founder'а | вне `research-cli` (граница C, 03 §3) — `research-cli` лишь производит `validation_report`-ссылку, которую HDP требует для промоушена (INTG-I-2) |

Капасити-оценка (§7) и корреляция с уже-live сигналами (чек-лист 02 §4.4 последний
пункт) считаются той же детерминированной машиной над журналом — НЕ LLM-прикидкой.

## §N. Интерфейсные контракты
- **Consumed:** `Event`/журнал (T1, read-only ← `journal`); `SignalSpec` карточки (T1,
  05 §2, ← `signal-engineer` через границу A); `crates/signals/` реализации (по
  `code_hash`, сверка с реестром); `trials-ledger.json` (T1, читается для deflation,
  05 §2); `Hypothesis` карточки (`research/hypotheses/*.md`, критерии фальсификации).
- **Produced:** `ValidationReport`/`metrics.json` (T1 → `risk-critic` + founder читают,
  05 §2); `TrialsLedger` записи (T1, append → глобальный, консюмится будущими
  deflated-Sharpe расчётами); `reports/R-NNN.md` (текстовый слой, детерминированно
  генерируемый или сопровождаемый человеком поверх чисел).
- **Refused:** запись в `research/registry/signals.json` (граница B — HDP-gated в
  другом месте, RC-I-6); эмиссия `Ctl(ParamChange)` или любого журнального события
  торгового пути (RC-I-7); чтение test-сегмента до прохождения val-гейта (RC-I-8);
  удаление/перезапись существующей записи trials-ledger (RC-I-2).

## §I. Инварианты (RC-I-1..11 + RC-I-Z) — RED-оракулы (тест падает на заглушке)
1. **RC-I-1** Ноль LLM-вызовов: ни одна зависимость/импорт крейта не является клиентом
   LLM-провайдера (grep-канарейка по `Cargo.toml` + исходникам).
2. **RC-I-2** trials-ledger append-only (материализует сквозной **INTG-I-6**, 03/05): нет
   функции/метода API, удаляющего или перезаписывающего существующую запись (тест: попытка
   мутации недостижима по типам; файловый уровень — только `O_APPEND`).
3. **RC-I-3** deflated-Sharpe считается СТРОГО из глобального trials-ledger счётчика
   для релевантного семейства сигналов, никогда из литерала/локального счётчика
   (сигнатура функции требует ledger-производного N).
4. **RC-I-4** test-сегмент трогается не более одного раза за цикл валидации гипотезы
   без явного override+записанного обоснования (тест: вторая попытка без override
   отклонена).
5. **RC-I-5** Генерация `ValidationReport` детерминирована: идентичные входы (хэш
   сегмента журнала + параметры + `code_hash` + состояние ledger'а) → байт-идентичный
   `metrics.json` (тест: два запуска, diff пуст).
6. **RC-I-6** `research-cli` никогда не пишет в `research/registry/signals.json`
   (grep/fs-permission тест — файл открывается read-only, если вообще открывается).
7. **RC-I-7** `research-cli` никогда не эмитирует `Ctl(ParamChange)` или иное
   журнальное событие торгового пути — read-only journal-хэндл на уровне типов (нет
   writer-а в области видимости).
8. **RC-I-8** Код-путь, читающий test-сегмент, структурно недостижим до прохождения
   val-гейта (не просто конвенция — компиляционная/рантайм-граница).
9. **RC-I-9** Отрицательные результаты (KILL) не удаляются — append-only зеркалит
   INTG-I-7 на уровне trials-ledger + critiques.
10. **RC-I-10** Стресс-варианты (издержки ×1.5, латентность ×2) — отдельные grid-прогоны
    через `sim`, не пост-обработка/ручная правка готовых чисел отчёта (тест: стресс-
    метрика имеет собственную ledger-запись с отличным `params_hash`).
11. **RC-I-11** Capacity/decay метрики считаются той же детерминированной машиной
    (§5/§7), не эвристикой/LLM-прикидкой (grep-тест: нет LLM-зависимости в пути
    вычисления capacity/decay, зеркало RC-I-1 локально для этих метрик).
- **RC-I-Z** Cornerstone-citability: §§ этого FA STABLE/APPEND-ONLY; правки — только
  named amendment-записью.

## §A. Антитезис (steelman против дизайна)
- «Ноль LLM-токенов на оценку — экономия, но теряется нюанс: чистые числа могут
  скрывать качественные проблемы (странная форма equity curve, режимные артефакты),
  которые видит только человек/LLM.» — Контр: именно поэтому есть §7 нарративный слой
  и `risk-critic` — `research-cli` намеренно НЕ пытается заменить интерпретацию, только
  делает её ДЕШЁВОЙ и ВОСПРОИЗВОДИМОЙ; нюанс — работа критика, не инструмента.
- «Глобальный trials-ledger создаёт трение — каждая идея "стоит" будущего deflation
  бюджета, это может отпугнуть от исследования.» — Контр: это НАМЕРЕННЫЙ анти-оверфит
  налог (02 §4.3) — deflated-Sharpe ЦЕЛЕНАПРАВЛЕННО наказывает множественные сравнения;
  трение — не баг, это единственная защита от "нашли прибыльную стратегию перебором".
- «Read-only доступ к журналу через 'типовой уровень' — не абсолютная защита,
  решительный разработчик всё равно может добавить writer-хэндл.» — Контр: тот же
  паттерн, что и `RiskApproved`-барьер в `risk` — не крипто-абсолют, а поднятие цены
  обхода до "намеренно, под ревью" (grep-канарейка RC-I-7 + scope-guard: агенты
  `research-cli` не имеют scope на journal writer-код).
- «Механизация чек-листа критика (§8) рискует создать ложное чувство полноты — гейты
  ловят ФОРМАЛЬНЫЕ нарушения (test тронут дважды), но не ловят содержательный оверфит
  (например, p-hacking внутри одного "легального" грида).» — Контр: справедливо и не
  скрыто — §O признаёт это как открытый риск; механизация закрывает ДЕШЁВЫЕ
  дисциплинарные дыры (забыл посчитать trial, тронул test дважды), содержательную
  оценку по-прежнему делает `risk-critic` — это разделение труда, не претензия на
  полноту.
