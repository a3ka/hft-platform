## §1. Идентичность модуля
- **Имя / крейт:** `contracts` (`crates/contracts/` + `contracts/schemas/` JSON Schema).
- **Язык:** Rust канон (типы + `serde` + `schemars` → JSON Schema 2020-12); Python-консюмер
  валидирует против сгенерированной схемы.
- **Слой:** cross-cutting (под слоем 0; всё зависит от него, он не зависит ни от кого).
- **Deploy:** библиотека, линкуется во все крейты движка; схемы читаются research-тулингом.
- **Статус:** ACCEPTED 2026-07-10 (v1).
- **Карта секций:** §1 идентичность · §2 роль · §3 IS · §4 IS NOT · §5 T1-состав · §6
  кодировки · §7 дисциплина изменения (contract-RFC) · §8 биндинги/кросс-язык · §N контракты
  · §I инварианты CT-I · §T RED · §P фаза · §O открытые · §A антитезис.

## §2. Стратегическая роль
`contracts` — **единый источник правды для всех форм, пересекающих границу движок↔деск**
и между крейтами движка. Материализует три границы интеграции (03): A (код сигнала оперирует
`Event`), B (`SignalRegistry`), C (`Ctl(ParamChange)`). Болезнь hft-core-rs (три несовместимых
wire-формата, разошедшиеся консюмеры) лечится структурно: одна форма, одно определение, одна
дисциплина изменения. Если контракт дрейфует бесконтрольно — рушится и детерминизм журнала
(разные версии читают по-разному), и интеграция (движок и деск расходятся).

## §3. Что модуль ЕСТЬ
**Онион-подструктура:**
- core: `types/` — канонические Rust-типы T1 (`Event`/`EventKind`, `SignalRegistryEntry`,
  `ParamChange`, `SignalSpec`, `ValidationReport`, `TrialsLedgerEntry`, `Decision`).
- mid: `schema/` — генерация JSON Schema из типов (`schemars`); `version/` — `schema_version`.
- outer: `schemas/*.json` (сгенерированные, в репо), `fixtures/{valid,invalid}/` (общие для
  Rust-тестов и Python-валидации).

**Доменный словарь = T1-состав (§5).**

**Обработка отказов/деградации:**
| Условие | Исход |
|---|---|
| Правка T1 вне contract-RFC | reject (ревьюер Block-C; CT-I-2) |
| JSON Schema разошлась с Rust-типом | verify-гейт FAIL (CT-I-4) |
| Старый журнал не читается новым кодом | блокирующая ошибка миграции (CT-I-3) |
| `EventKind` определён в >1 месте | grep-канарейка FAIL (CT-I-1) |

## §4. Что модуль НЕ ЕСТЬ
1. **НЕ бизнес-логика** — только формы и их версии; не считает риск/сигналы/книгу.
2. **НЕ владелец T2/T3** — модульно-ограниченные типы (`Order`, `RiskApproved`, `Book`,
   `Forecast`) живут в своих крейтах и меняются без RFC; `contracts` держит ТОЛЬКО T1.
3. **НЕ рантайм-компонент** — не пишет журнал, не исполняет; предоставляет типы/схемы.
4. **НЕ произвольно-изменяемый** — не «просто ещё один крейт»; правки — только атомарным
   contract-RFC (§7), как EINHARD `contracts/` через §5b RFC.
5. **НЕ Python-владелец** — Python читает/валидирует, но канон — Rust; Python не определяет
   T1.

## §5. T1-состав (единый источник правды)
| T1 | Что | Продюсер / консюмер | Граница |
|---|---|---|---|
| `Event`/`EventKind` | журнальный wire-формат | движок пишет; движок+research читают | журнал |
| `SignalRegistryEntry` | что движок исполняет | деск (через подпись) / движок | B |
| `ParamChange` | подписанное изменение весов/лимитов/параметров | очередь решений / движок | C |
| `SignalSpec` | формула+параметры+диапазоны+издержки | signal-engineer / движок+critic | A |
| `ValidationReport` | выход research-cli (метрики) | research-cli / critic+founder | — |
| `TrialsLedgerEntry` | глобальный счётчик проб | backtest-runner / deflated-Sharpe | — |
| `Decision` | подписанное решение founder'а | founder / движок+реестр | B/C |

## §6. Кодировки (locked — не переоткрываются без RFC)
Деньги/цены: fixed-point i64/u64 ×1e8. Время: `ts_mono_ns` (порядок) + `ts_wall_ms` int64
UTC (отчёты). Бинарь журнала: postcard + crc32/фрейм. Идентификаторы: `signal_id`,
`client_order_id = hash(strategy_id, seq, nonce)`. Хэши: sha256 (`code_hash`, `state_hash`).
ОДИН формат навсегда.

## §7. Дисциплина изменения (contract-RFC — сердце governance)
Изменение любой T1-формы = **атомарный contract-RFC в ОДНОМ PR**: (1) правка Rust-типа;
(2) перегенерированная JSON Schema; (3) bump `schema_version`; (4) миграционная заметка
(как читать старые журналы/реестры); (5) фикстуры valid/invalid; (6) CHANGELOG; (7) ≥1 тест
на новую форму. Аддитивное (новое опциональное поле, новый вариант enum в конце) — minor;
ломающее (удаление/переименование/смена типа/порядок enum) — major + миграция старых
журналов (журнал бессмертен — CT-I-3/JR-I-6). Rationale-only и schema-only PR не ревьюятся.
Ревьюер Block-C: правка `contracts/` вне RFC → авто-reject.

## §8. Биндинги и кросс-язык
Rust — канон (типы напрямую). Python — консюмер: читает журнал/отчёты, валидируя против
сгенерированной JSON Schema; НЕ пишет T1 в рантайм (только текстовые T1 `ValidationReport`/
`SignalSpec` через границы A/B). Гейт паритета `verify_contracts.sh`: Rust-типы ↔ JSON Schema
↔ фикстуры согласованы + роундтрип сериализации (аналог EINHARD tri-binding parity, здесь 2 языка).

## §N. Интерфейсные контракты
- **Consumed:** ничего (DAG-корень; зависит только от stdlib + serde/schemars).
- **Produced:** T1-типы (Rust) + JSON Schema + фикстуры → все крейты движка + research-тулинг.
- **Refused:** T2/T3 типы (не его зона); правки вне contract-RFC; определение T1 в Python.

## §I. Инварианты (CT-I) — RED-оракулы
1. **CT-I-1** `EventKind` (и каждый T1) определён ровно в одном крейте (`contracts`) —
   grep-канарейка против локального переопределения.
2. **CT-I-2** Правка T1 вне contract-RFC → reject (ревьюер Block-C).
3. **CT-I-3** Старый журнал читается новым кодом (миграция обязательна; роундтрип-фикстуры
   прошлых версий; зеркало JR-I-6).
4. **CT-I-4** JSON Schema сгенерирована из Rust-типов и согласована (verify-гейт), не руками.
5. **CT-I-5** Python-тулинг валидирует чтения против той же схемы (общие фикстуры).
6. **CT-I-6** `schema_version` в каждом журнальном сегменте и в `signals.json`.
- **CT-I-Z** Cornerstone-citability: §§ STABLE/APPEND-ONLY; правки named-not-silent.

## §T. RED-тест маппинг (`crates/contracts/tests/` + `verify_contracts.sh`)
- `test_eventkind_single_definition` (CT-I-1, grep) · `test_schema_matches_types` (CT-I-4,
  генерация↔файл) · `test_old_version_roundtrip` (CT-I-3, фикстуры версий) ·
  `test_fixtures_valid_invalid` (CT-I-5, общие с Python) · `test_schema_version_present`
  (CT-I-6). Block-C (CT-I-2) — процессный гейт ревьюера, не unit-тест, но проверяется
  скриптом diff'а против RFC-метки.

## §P. Фаза реализации
**P0 (M-00 bootstrap)** — ПЕРВЫЙ крейт, до журнала (журнал использует его типы). Ничем не
блокируется; блокирует всё. Растёт аддитивно каждую фазу (P0: Event; P2: SignalSpec/
ValidationReport/TrialsLedger; P3: ParamChange для лимитов; каждый add — contract-RFC).
Acceptance M-00: `verify_contracts.sh` GREEN (схема↔типы↔фикстуры) + CT-I-1/4/6.

## §O. Открытые вопросы
- Инструмент генерации JSON Schema (`schemars` версия/настройки) и стабильность вывода
  (детерминированный порядок полей для CT-I-4).
- Python-валидатор (`jsonschema`) и формат общих фикстур.
- Политика версионирования `EventKind` при добавлении вариантов (порядок enum влияет на
  бинарь postcard — добавление строго в конец).
- Хранилище/подпись `Decision` и `ParamChange` (Ed25519 ключ оператора — общий с §killswitch/§risk).

## §A. Антитезис (steelman против дизайна)
- «contract-RFC на каждую правку T1 — тяжёлый процесс для соло-темпа.» — Контр: T1-форм мало
  (7) и они стабилизируются рано; тяжесть — на границе, где ошибка дорога (рассинхрон движка
  и деска, нечитаемый старый журнал); T2/T3 меняются свободно, RFC их не касается — трение
  только там, где оно окупается.
- «Rust-канон + Python-консюмер — дубль поддержки схемы.» — Контр: схема ГЕНЕРИРУЕТСЯ из
  Rust (не пишется дважды), Python лишь валидирует против неё; общие фикстуры ловят
  расхождение механически (CT-I-5) — это дешевле, чем два рукописных определения (болезнь
  hft-core-rs).
- «Бессмертие старого формата сковывает.» — Контр: цена `replay==реальность`; управляемо
  миграциями; альтернатива — потеря аудитопригодности истории — несовместима с торговой
  системой.
