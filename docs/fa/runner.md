# runner — Functional Architecture (FA)

> CORNERSTONE FA (composition root арминга). Authored by architect (Fable) 2026-07-10.
> STABLE/APPEND-ONLY. Крейт `runner` — единственное место, где четыре режима торговли
> (`backtest|paper|live-micro|live`) собираются в ОДИН исполняемый бинарь; это структурная
> материализация равенства #2 из DESIGN §1 (`backtest == paper == live-micro == live`).

## §1. Идентичность модуля
- **Имя / крейт:** `runner` (`crates/runner/`).
- **Язык:** Rust, in-process (композиционный бинарь; главная точка входа движка
  `main.rs` живёт здесь).
- **Слой:** 6 (DESIGN §2).
- **Deploy:** единственный торговый бинарь на все режимы; для `backtest`/`paper` —
  локально/на расчётном сервере, для `live-micro`/`live` — на боевом хосте рядом с
  независимым `killswitch` (отдельный процесс, §7).
- **Статус:** DRAFT (первая версия FA).
- **Карта секций:** §1 идентичность · §2 роль · §3 IS · §4 IS NOT · §5 композиционная
  модель · §6 arming state machine · §7 деградация и re-arm · §8 live-micro как
  подписанный профиль · §9 наблюдаемость/журналирование режима · §N контракты ·
  §I инварианты RN-I-1..11 + RN-I-Z · §T RED-маппинг · §P фаза · §O открытые · §A антитезис.

## §2. Стратегическая роль
`runner` — composition root: единственное место, где инстанцируется ПОЛНЫЙ конвейер
`book → signals → alpha → portfolio → strategy → risk → oms` и подключается к паре
(`EventSource`, `EventSink`), специфичной для режима. Он НЕ участвует в бизнес-логике
конвейера — он его СОБИРАЕТ и управляет ЖИЗНЕННЫМ ЦИКЛОМ (arming, деградация, shutdown).
Без `runner` каждый режим требовал бы отдельного бинаря/форка кода — именно так рождается
расхождение backtest/live, которое хоронит доверие к бэктесту (урок hft-core-rs:
несколько путей исполнения = систематическое расхождение). `runner` — структурная
гарантия того, что ОДИН И ТОТ ЖЕ код стратегии видит ОДИН И ТОТ ЖЕ интерфейс событий
независимо от того, откуда они берутся (исторический журнал или живой фид) и куда уходят
решения (симулятор или боевой gateway).

Позиция в потоке: НЕ внутри конвейера `book→...→oms` — `runner` ОБЁРТЫВАЕТ его. Он —
единственный владелец процесса запуска/армирования/остановки; конвейер работает
одинаково независимо от того, кто его вызывает.

## §3. Что модуль ЕСТЬ
**Онион-подструктура:**
- core (без I/O): `arming/` — чистая машина состояний
  `(ArmingState, ArmingEvent) -> ArmingState` (§6); не знает про сеть/файлы, только
  переходы по событиям.
- mid: `compose/` — сборка конвейера: инстанцирует `book/signals/alpha/portfolio/
  strategy/risk/oms` с общими типами, различается ТОЛЬКО инъекцией `EventSource`/
  `EventSink` по режиму (§5); `degrade/` — редьюсер деградации (ConnDown→Disarm→
  reconnect→snapshot→recon→READY), тоже переиспользуемый для всех режимов, где
  применимо (backtest не деградирует по сети, но структура кода одна).
- outer: `main.rs` — точка входа, парсинг конфига/CLI, загрузка `LimitProfile`,
  подключение реального `EventSource`/`EventSink` (журнал-ридер | venue-адаптер;
  sim-сток | live gateway), обработка сигналов ОС, heartbeat к `killswitch` (только
  live-режимы).

**Доменный словарь (T2):**
- `Mode = Backtest | Paper | LiveMicro | Live` — явный, журналируется на старте (RN-I-7).
- `ArmingState = Init | ConfigLoaded | JournalOpen | FeedsUp | BookReady | ReconOk |
  Ready | Armed | Disarmed | Halted` — детерминированная машина, переходы только вперёд
  по фиксированному порядку (кроме `Disarmed`/`Halted` — reachable из любого состояния).
- `trait EventSource { fn next(&mut self) -> Option<Event>; }` — исторический журнал
  (backtest/paper-replay) ИЛИ живой venue-фид (paper/live-micro/live), нормализованный
  до `Event` ДО попадания в общий конвейер.
- `trait EventSink { fn emit(&mut self, o: RiskApproved<Order>) -> SinkResult; }` — `sim`
  (backtest/paper) ИЛИ реальный `OrderGateway` (live-micro/live). Инвариант: `paper`
  ФИЗИЧЕСКИ подключён к `sim`-стоку, не к боевому (зеркало INTG-I-5, см. RN-I-3/RN-I-8).
- `LimitProfileRef` — ссылка на подписанный лимит-профиль (§8), обязателен для
  `live-micro`/`live` до перехода за `ConfigLoaded`.

**Обработка отказов/деградации:**
| Условие | Детерминированный исход |
|---|---|
| `Sys(ConnDown)` (MD или order gateway, live-режимы) | немедленный `Ctl(Disarm)` → cancel-in-flight через `risk`/`oms` → backoff+jitter reconnect → снапшот → recon → `Ready` (НЕ `Armed`) |
| Журнал не пишется (диск/fsync fail) | `Halt` (зеркало RK-I-5; `runner` не продолжает без надёжного журнала) |
| Свежих MD нет дольше T | `Disarmed` (защитно — конвейер не должен котировать по протухшей книге) |
| Recon-расхождение при re-arm | остаётся в `Ready`, алерт, НЕ переходит в `Armed` автоматически |
| Потерян heartbeat к `killswitch` (live-режимы) | `Disarmed` + проверка halt-замка перед любой попыткой re-arm |
| Невалидная подпись конфига/лимит-профиля | отказ пройти `ConfigLoaded`, старт не происходит (fail at boot) |
| `EventSource` исчерпан (конец журнала, backtest) | штатное чистое завершение: flush → финальный `state_hash` → `Disarmed` → exit(0) |
| Несовпадение заявленного `Mode` с историей журнала (без явного override оператора) | отказ старта, эскалация человеку |

## §4. Что модуль НЕ ЕСТЬ
1. **НЕ стратегия/альфа/портфель** — не решает ЧТО торговать; `runner` инстанцирует
   `strategy`/`alpha`/`portfolio` как чёрные ящики, сам не содержит бизнес-логики сигналов.
2. **НЕ risk** — не оценивает ордера; передаёт их через `risk::gate::evaluate`, сам не
   умеет строить `RiskApproved` (приватный конструктор у `risk`, RK-I-1).
3. **НЕ АВТОРИТЕТ армирования** — `Ctl(Arm)` подписывает/инициирует ЧЕЛОВЕК-оператор
   (двухключевой старт); `runner` лишь ПРОВЕРЯЕТ предусловия и ИСПОЛНЯЕТ переход
   состояния, он не может сам решить «пора торговать».
4. **НЕ killswitch** — независимый рубильник живёт отдельным процессом (01 §7); `runner`
   лишь шлёт heartbeat и уважает halt-замок, не дублирует его функцию.
5. **НЕ venue-адаптер** — сетевой протокол/подпись действий у `venues`; `runner`
   получает уже нормализованный `EventSource`.
6. **НЕ симулятор** — модель исполнения/латентности/комиссий у `sim`; `runner` для
   backtest/paper лишь ПОДКЛЮЧАЕТ `sim` как `EventSink`, не содержит модели fill'ов.
7. **НЕ журнал** — хранение/replay/снапшоты у `journal`; `runner` читает из него (через
   `EventSource`) и уважает его гарантии, не переопределяет формат.
8. **НЕ конфигурируемый обход арминга** — не существует режима/флага, стартующего
   торговлю без прохождения полной цепочки предусловий (RN-I-4).

## §5. Композиционная модель — одна кодовая база, четыре режима
Единственная точка ветвления по режиму — выбор конкретной реализации `EventSource` +
`EventSink` при старте; ВЕСЬ конвейер (`book→signals→alpha→portfolio→strategy→risk→oms`)
инстанцируется идентично для всех режимов из одних и тех же типов и одной и той же
функции сборки `compose::build_pipeline(cfg) -> Pipeline`.

| Режим | EventSource | EventSink | Лимит-профиль |
|---|---|---|---|
| `backtest` | `journal::Reader` (исторический сегмент) | `sim::Sink` | `backtest` (широкий, для замера потенциала) |
| `paper` | `venues::LiveFeed` (нормализованные живые события) | `sim::Sink` (НЕ `venues::Gateway` — INTG-I-5) | `paper` |
| `live-micro` | `venues::LiveFeed` | `venues::Gateway` (боевой, testnet или mainnet по конфигу) | `live-micro` (подписанный, §8) |
| `live` | `venues::LiveFeed` | `venues::Gateway` (mainnet) | `live` (рабочий, P5) |

Запрещено: `#[cfg(mode = "...")]`-ветвление ВНУТРИ `signals/alpha/portfolio/strategy`
крейтов (RN-I-2, grep-канарейка) — если сигнал ведёт себя иначе в paper, чем в live, это
БАГ, а не фича; единственная легитимная разница между режимами — источник/приёмник
событий И применяемый лимит-профиль (портфельный sizing честно видит РАЗНЫЕ лимиты, это
не то же самое, что разное поведение стратегии).

## §6. Arming state machine
Фиксированная последовательность предусловий ДО первого `Armed`:
```
Init → ConfigLoaded → JournalOpen → FeedsUp → BookReady → ReconOk → Ready → [Ctl(Arm)] → Armed
```
- `Init → ConfigLoaded`: конфиг + лимит-профиль загружены; для `live-micro`/`live` —
  подпись профиля проверена (иначе Halt-at-boot, §3 таблица).
- `ConfigLoaded → JournalOpen`: журнал открыт (append-режим), `Mode` записан как первое
  событие сессии (RN-I-7).
- `JournalOpen → FeedsUp`: `EventSource` подключён и отдаёт события (для backtest —
  журнал читается; для live-режимов — `venues::LiveFeed` подписан и получает MD).
- `FeedsUp → BookReady`: `book` восстановлен (снапшот+дельты, целостность зелёная).
- `BookReady → ReconOk`: для live-режимов — сверка позиций/ордеров с биржей (через `risk`
  recon, §6 risk.md) прошла; для backtest/paper — тривиально true (нечего сверять либо
  сверяется с sim-состоянием).
- `ReconOk → Ready`: система готова, НЕ торгует. Каждый переход — событие в журнале
  (`Sys(...)`/`Ctl(...)`), реплеится.
- `Ready → Armed`: ТОЛЬКО по явному `Ctl(Arm)` от оператора (двухключевой старт — ключ
  1: система готова технически; ключ 2: человек решил начать). Никакого auto-arm по
  умолчанию (RN-I-1); auto-rearm ПОСЛЕ деградации — отдельная, явно сконфигурированная
  ветка (§7), НЕ путь `Ready → Armed` для первого старта сессии.

Любое состояние может перейти в `Disarmed` (деградация, §7) или `Halted` (RK-I-4/RK-I-5-
класс отказов, зеркалируемых из `risk`/`journal`); из `Halted` выход — ТОЛЬКО ручной.

## §7. Деградация и re-arm (система стоит, когда не уверена)
```
Armed ──Sys(ConnDown)──▶ Disarmed ──cancel-in-flight(risk/oms)──▶ [ждём reconnect]
Disarmed ──reconnect ok──▶ [snapshot] ──▶ [recon] ──ReconOk──▶ Ready
Ready ──manual Ctl(Arm) ИЛИ auto-rearm(config)+ReconOk──▶ Armed
```
- Деградация ВСЕГДА проходит через `Disarm` перед любой попыткой reconnect — никогда
  не бывает «тихого» продолжения торговли в неопределённом состоянии сети (RN-I-5).
- Cancel-in-flight делегируется в `risk`/`oms` (`runner` не отправляет ордера сам — §4.2);
  `runner` лишь инициирует переход состояния и ждёт подтверждения отмены.
- Reconnect — экспоненциальный backoff + jitter (01 §4); после успешного reconnect
  ОБЯЗАТЕЛЕН снапшот книги + recon позиций перед возвратом в `Ready` (никогда не «просто
  продолжаем с прошлого состояния» — это и есть источник расхождения sim-vs-live при
  плохом ресинке).
- Re-arm после деградации: РУЧНОЙ (`Ctl(Arm)` оператора) ПО УМОЛЧАНИЮ; авто-re-arm —
  явная опция профиля (например для paper, где человек не обязан сидеть 24/7), но
  ВСЕГДА обусловлен успешным `ReconOk` — авто-re-arm без чистого recon запрещён
  структурно (RN-I-6).
- `Halted` (RK-I-9-класс: пробитие дневного loss-лимита, RK-I-8: recon mismatch за
  порогом) — НЕ является «деградацией» в смысле этого раздела: выход из `Halted` только
  ручной, без auto-rearm опции вообще (killswitch halt-замок, §7 risk.md).

## §8. live-micro как подписанный профиль (НЕ флаг)
`live-micro` — ОТДЕЛЬНЫЙ именованный, подписанный `LimitProfile`-артефакт (см. `risk`
FA §8), а не булев CLI-флаг поверх `live`. Практическое следствие: невозможно случайно
«включить микро-режим» правкой строки конфига без прохождения того же подписного пути,
каким живут лимиты (профиль фиксируется на armed-сессию, runtime-смена профиля
запрещена, требует Disarm+рестарт).
- `runner` НЕ хранит собственную копию чисел профиля — только ссылку (`LimitProfileRef`)
  + проверенную подпись; сами числа и их проверка — территория `risk` (RK-I-10).
- Разница `live-micro` vs `live` — ТОЛЬКО параметры лимит-профиля (§4 DESIGN); код
  движка, конвейер, `EventSink` (боевой `venues::Gateway`) — идентичны. Это намеренно:
  доказуемость на малом капитале должна быть доказуемостью РЕАЛЬНОГО кода, не «песочницы».
- Переход `live-micro → live` (P5) — это смена подписанного профиля + возможно смена
  инструментов/капитала, НЕ смена бинаря/кода.

## §9. Наблюдаемость и журналирование режима
- `Mode` пишется как первое событие сессии (`Sys(SessionStart{mode, config_hash,
  limit_profile_id})`), реплей может однозначно определить, каким режимом произведён
  любой сегмент журнала (RN-I-7) — критично для форензики (нельзя перепутать paper-
  сегмент с live при аудите).
- Каждый переход `ArmingState` — событие; полная цепочка arming/degradation/re-arm
  восстанавливается из журнала без внешних логов (принцип DESIGN §1 равенство #1
  `replay(journal) == реальность` распространяется и на lifecycle `runner`, не только
  на торговлю).
- Метрики (`tracing`+Prometheus, 01 §10): `hft_runner_arming_state`, `hft_runner_mode`,
  `hft_runner_degradation_events_total`, `hft_runner_time_to_ready_ms` (время от старта
  до `Ready` — бюджет operational readiness).

## §N. Интерфейсные контракты
- **Consumed:** `EventSource` (T2, реализация зависит от режима — журнал-ридер |
  `venues::LiveFeed`); `Ctl(Arm)`/`Ctl(Disarm)` (T1 события ← оператор/degrade-редьюсер);
  `LimitProfile` подписанный (T2 ← `risk`, ссылка проверяется на старте); heartbeat-канал
  ← `killswitch` (только live-режимы).
- **Produced:** инстанцированный `Pipeline` (внутренний, не публичный контракт —
  сборочная структура); `Sys(SessionStart)`, `ArmingState`-переходы, `Sys(ConnDown/ConnUp)`
  события (T1 → journal → все консюмеры); heartbeat → `killswitch`.
- **Refused:** прямой вызов `venue::place` в обход `risk`/`oms` (архитектурно
  недостижим — `runner` не держит хэндл на `OrderGateway` напрямую, только через
  `EventSink`, который для live-режимов сам укладывается поверх `RiskApproved`-барьера);
  runtime-смена `LimitProfile` без Disarm+рестарт (следствие RN-I-3).

## §I. Инварианты (RN-I-1..11 + RN-I-Z) — RED-оракулы (тест падает на заглушке)
1. **RN-I-1** Ни один ордер не может быть эмитирован до `Ctl(Arm)` от оператора
   (двухключевой старт; тест: попытка эмита в состоянии `Ready` отклоняется структурно).
2. **RN-I-2** Одна кодовая база на все 4 режима: `signals/alpha/portfolio/strategy` не
   содержат mode-специфичного ветвления (grep-канарейка на `Mode::`/`#[cfg(mode`).
3. **RN-I-3** `live-micro` — подписанный `LimitProfile`-артефакт, НЕ флаг (тест
   утверждает отсутствие boolean-флага поверхности + наличие подписи на профиле).
4. **RN-I-4** Arming-последовательность необратима вперёд и не пропускает шаги
   (`Init→...→Ready` — тест перебором недопустимых переходов, все отклонены).
5. **RN-I-5** Деградация ВСЕГДА проходит через `Disarm` перед reconnect (тест: инъекция
   `ConnDown` → следующее наблюдаемое состояние строго `Disarmed`, никогда «тихий» skip).
6. **RN-I-6** Re-arm требует `ReconOk` — ни ручной, ни авто re-arm не достижим без
   успешного recon после reconnect (тест: recon fail → `Armed` недостижим).
7. **RN-I-7** `Mode` явно журналируется как первое событие сессии (тест: `replay`
   первого события сессии восстанавливает `Mode` без внешнего контекста).
8. **RN-I-8** `runner` не конструирует `RiskApproved<Order>` — тип недоступен вне
   `risk` (компиляционный барьер + grep, зеркало RK-I-1 на стороне `runner`).
9. **RN-I-9** Для live-режимов `Armed` недостижим без установленного heartbeat-канала к
   `killswitch` (fail-closed зависимость; тест: отсутствие канала блокирует переход).
10. **RN-I-10** Чистое завершение при исчерпании `EventSource` или отказе `EventSink`:
    flush → `state_hash` → `Disarmed` перед выходом (тест: нет «резкой смерти» с открытым
    ордером в состоянии `Armed`).
11. **RN-I-11** Подпись конфига/лимит-профиля проверяется ДО `ConfigLoaded` для
    `live-micro`/`live`; невалидная подпись блокирует старт (fail-at-boot, не в рантайме).
- **RN-I-Z** Cornerstone-citability: §§ этого FA STABLE/APPEND-ONLY; правки — только
  named amendment-записью.

## §P. Фаза реализации
**P0 (минимальный)** — голый `backtest`-режим: `Init→...→Ready→Armed` без сети,
`EventSource` = журнал-ридер, `EventSink` = `sim::Sink`-заглушка (до полного `sim` —
просто лог решений); цель P0 — доказать саму машину состояний и её журналирование
(зависит от `journal` P0). Блокирует: ничего критического (параллелится с P1 data plane).

**P1-P2** — добавляется `paper` (реальный `EventSource` = `venues::LiveFeed`, `EventSink`
остаётся `sim`); зависит от `venues`/`book` (P1) и полноценного `sim` (P2, зависимость
пересекается с research-cli — paper acceptance ворота P2 согласно DESIGN §10).

**P3** — деградационный редьюсер + heartbeat к `killswitch` включаются полностью
(требует `risk`+`killswitch` P3); testnet-режим — фактически `live-micro` с
testnet-`Gateway`.

**P4 (live-micro)** — полный путь: подписанный лимит-профиль, mainnet
`venues::Gateway`, recon обязателен, disconnect-drill проходит на живом коннекте
(не только testnet). Mock-точки для параллельной разработки: до готовности
`killswitch` можно тестировать arming/degradation с mock-heartbeat-приёмником
(RN-I-9 тест переключается на реальный канал только на P3 close-out).

## §A. Антитезис (steelman против дизайна)
- «Одна кодовая база на 4 режима — красиво на бумаге, но реальность заставит завести
  `if mode == Live` в паре мест ради практичности (rate-limits разные, таймауты
  разные).» — Контр: разница ДОЛЖНА жить в конфиге/лимит-профиле, не в ветвлении кода;
  если находится реальная потребность в разном ПОВЕДЕНИИ (не только числах), это
  сигнал, что абстракция `EventSource`/`EventSink` неполна — тогда правится СТРУКТУРА
  (новый метод трейта), а не добавляется `if mode`. grep-канарейка RN-I-2 ловит именно
  попытку срезать угол.
- «Двухключевой старт (`Ready`→ждём `Ctl(Arm)`) — лишняя задержка для paper/backtest,
  где риска нет.» — Контр: единообразие важнее — если paper armed автоматически, а
  live нет, это уже НЕ «один код», это скрытая ветка поведения; цена (секунды ожидания
  оператора) ничтожна против цены расхождения путей.
- «Fail-at-boot на невалидной подписи профиля (RN-I-11) может заблокировать
  экстренный рестарт в критической ситуации.» — Контр: экстренный рестарт без валидной
  подписи — это ИМЕННО тот случай, когда система должна остановиться, а не догадываться
  о лимитах; человек всегда может пересобрать/переподписать профиль — это дешевле, чем
  торговать на неизвестных лимитах.
