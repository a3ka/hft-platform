# book — Functional Architecture (FA)

> Authored by architect (Fable) 2026-07-10. STABLE/APPEND-ONLY. Слой 1 (data plane),
> сосед `venues` (тот же слой, разные обязанности). Примитив, на котором стоит сигнал
> founder'а №1 (OBI 3%/8%) — глубина этого FA пропорциональна тому, насколько дорого
> будет чинить книгу постфактум, если она соврёт.

## §1. Идентичность модуля
- **Имя / крейт:** `book` (`crates/book/`).
- **Язык:** Rust, in-process движка.
- **Слой:** 1 (data plane, вместе с `venues`; см. DESIGN §2).
- **Deploy:** in-process с движком; отдельного процесса/сокета нет.
- **Статус:** DRAFT.
- **Карта секций:** §1 идентичность · §2 роль · §3 IS · §4 IS NOT · §5 реконструкция
  книги · §6 целостность/ресинк · §7 производные величины · §N контракты ·
  §I инварианты BK-I-1..8 + BK-I-Z · §T RED-маппинг · §P фаза · §O открытые · §A антитезис.

## §2. Стратегическая роль
`book` реконструирует L2-книгу инструмента из нормализованного потока рыночных данных
и считает производные величины (microprice, spread, depth-полосы), которые потребляют
`signals` (в частности сигнал №1 OBI, DESIGN §8) и, ниже по конвейеру, `strategy` (цена
котировки). Позиция в потоке: `venues → [book] → signals → alpha → portfolio → strategy`.
Без честной книги весь дальнейший конвейер считает на выдумке — DESIGN §5 прямо называет
цель: бэктест не должен врать, а он не может не врать, если книга уже соврала на входе.
`book` — единственное место, где сырые дельты становятся структурой, с которой можно
детерминированно работать; он же — единственное место, где решается, что книга **устарела**
и ей нельзя доверять (честная деградация вместо тихой лжи).

## §3. Что модуль ЕСТЬ
**Онион-подструктура:**
- core (без I/O): `reducer/` — чистая функция `(BookState, Event) -> BookState` (применение
  `Md(L2Delta|L2Snapshot|Trade)`), плюс проверка непрерывности sequence-номера (gap-детекция —
  СРАВНЕНИЕ ЧИСЕЛ, не эвристика).
- mid: `derived/` — чистые функции над `BookState`: microprice, spread, `depth(side, pct_band)`;
  `staleness/` — конечный автомат `Live → Stale → Resyncing → Live`, тоже чистый (переход —
  функция события, не таймера с боку).
- outer: `resync/` — единственная нечистая часть: слушает журнал на предмет свежего
  `Md(L2Snapshot)`, приходящего от `venues` в ответ на запрошенный ресинк (§6), и применяет
  его к `BookState`. `book` сам ничего не запрашивает по сети — только эмитит намерение
  в журнал (см. §6, открытый вопрос по EventKind).

**Доменный словарь (T2, владеет крейт):**
- `BookState` — {инструмент, bid-levels, ask-levels (BTreeMap price→size), last_seq,
  staleness}. Внутреннее представление; наружу не течёт напрямую.
- `BookView` — иммутабельный снимок для консюмеров: {best_bid, best_ask, microprice,
  spread, depth_bid[pct_band], depth_ask[pct_band], staleness}. **Staleness — часть типа**,
  не побочная переменная — консюмер не может «забыть» проверить свежесть (материализация BK-I-3).
- `DepthBands` — фиксированный набор процентных полос, конфигурируемый (founder — 3%/8%
  для сигнала №1; другие сигналы могут запросить другие полосы — параметр функции, не
  жёстко зашитые константы в `book`).
- `Staleness = Fresh | Stale{since_seq, reason}`.

**Обработка отказов/деградации:**
| Условие | Детерминированный исход |
|---|---|
| Sequence-гэп (получен seq > last_seq+1) | Немедленно `Stale{reason: SeqGap}` (BK-I-2); ни один `BookView` после этого момента не возвращается как `Fresh` |
| Дублирующийся/более старый seq | Игнорируется как noise-дубликат события транспорта, НЕ триггерит гэп; но логируется (BK-I-7) |
| `Md(L2Snapshot)` от venues (ответ на ресинк-запрос) | Полная замена `BookState`, `staleness → Fresh`, `last_seq` из снапшота |
| Consumer запрашивает `depth()` на `Stale` книге | Возвращается ЧЕСТНО как `Stale`-помеченный `BookView` — `book` НЕ подставляет старое значение под видом свежего и НЕ интерполирует (анти-`rand()`-урок DESIGN §9) |
| Пустой уровень после серии cancel (size→0) | Уровень удаляется из `BTreeMap`, не остаётся «фантомным» нулём |
| Ресинк не пришёл дольше таймаута `[verify-at-impl]` | Остаётся `Stale`; эскалация — задача `ops`/алертов (01 §10 P1-класс: stale book), не `book` |

## §4. Что модуль НЕ ЕСТЬ
1. **НЕ venue-адаптер** — не открывает сокет, не ходит по REST, не парсит биржевой JSON/WS-фрейм;
   это `venues`. `book` потребляет уже нормализованные `Md(...)` события из журнала.
2. **НЕ сигнал** — не решает BUY/SELL/HOLD и не имеет мнения о будущем; отдаёт только текущее
   состояние книги и её производные. Интерпретация — дело `signals` (в частности OBI).
3. **НЕ risk/oms** — не гейтит ордера, не знает о позициях/PnL/лимитах; это `risk`.
4. **НЕ источник sequence-номеров** — не изобретает нумерацию, только проверяет непрерывность
   того, что прислал `venues`.
5. **НЕ владелец решения о ресинке** — детектирует гэп и заявляет о необходимости ресинка
   событием в журнал; ФАКТИЧЕСКИЙ REST-запрос снапшота выполняет `venues` (единственный
   сетевой актор системы, §7 `venues.md`).
6. **НЕ угадывает пропущенные данные** — на гэпе НЕ интерполирует, НЕ использует `rand()`,
   НЕ «сглаживает» книгу правдоподобным значением; единственный честный ответ на гэп —
   пометить `Stale` и ждать снапшота (прямая противоположность урока hft-core-rs
   «rand()-детекция гэпов», DESIGN §9).

## §5. Реконструкция книги
`BookState` восстанавливается редьюсером над потоком `Md`-событий: `L2Snapshot` — полная
инициализация; `L2Delta{price, size, side}` — apply в `BTreeMap` (size=0 → удаление уровня).
Редьюсер **чистый и тотальный**: для любого валидного `Event` есть детерминированный
результат, без побочных эффектов и без чтения времени/сети. Это прямое следствие §1
стержневого принципа платформы (DESIGN §1): `replay(journal) == реальность` включает
книгу — если редьюсер не чист, реплей книги на форензике даст другой результат, чем был
вживую, и вся форензика теряет смысл.

`Trade`-события НЕ двигают уровни книги напрямую (это не L2-дельта), но используются
`derived/` как сверочный сигнал: цена сделки вне текущего best bid/ask — признак, что
книга уже могла разойтись с реальностью (см. §6).

## §6. Целостность и честный ресинк
Gap-детекция — единственный критерий: `received_seq != last_seq + 1` (и не дубликат/не
старее). Никакой эвристики поверх (никаких «выглядит подозрительно» проверок на основе
размера дельты, времени между сообщениями и т.п. — это дверь к тому самому `rand()`-стилю
угадывания, которого DESIGN §9 явно требует избежать).

На гэпе: `staleness → Stale{since_seq, reason: SeqGap}` СИНХРОННО, до применения любого
следующего события (BK-I-2) → `book` эмитит намерение ресинка в журнал (рабочее название
`BookIntegrity(ResyncRequested{instrument, last_good_seq})`, см. §O — конкретный EventKind
ещё не зафиксирован contract-RFC) → `venues` (единственный, кто умеет ходить в REST)
читает это намерение из журнала, делает REST-запрос свежего снапшота, пишет
`Md(L2Snapshot)` обратно в журнал → `book` консюмирует снапшот, `staleness → Fresh`.

Этот путь **весь идёт через журнал**, а не через прямой вызов `book → venues` — иначе
`book` перестаёт быть тем же слоем, что `venues` (DESIGN §2: `venues, book` — оба слой 1,
не подчинены друг другу), и ресинк перестаёт быть частью реплеиуемой истории. Реплей дня
с гэпом должен показать ТОТ ЖЕ ресинк в том же месте — иначе нарушается равенство №1.

## §7. Производные величины
- **microprice** = `(best_bid_px · best_ask_sz + best_ask_px · best_bid_sz) / (best_bid_sz + best_ask_sz)`
  — взвешенная по противоположному объёму середина; чувствительнее к дисбалансу, чем
  простой mid, поэтому предпочтительна как референс-цена для price-deviation guard (RK-I,
  risk.md §8) и для `depth()`.
- **spread** = `best_ask_px − best_bid_px` (fixed-point i64 ×1e8, как всё денежное).
- **`depth(side, pct_band)`** — суммарный размер на стороне `side`, по уровням, чья цена
  отклоняется от референса (microprice) не более чем на `pct_band`% в сторону `side`.
  Формально: `Σ size(level) для level ∈ side, |price(level) − microprice| / microprice ≤ pct_band`.
  Монотонна по `pct_band` (BK-I-6) — более широкая полоса не может дать меньше глубины.
  Сигнал №1 (OBI, DESIGN §8) читает `depth(bid, 3%)`, `depth(bid, 8%)`,
  `depth(ask, 3%)`, `depth(ask, 8%)`; сама формула имбаланса — дело `signals`, `book`
  отдаёт только сырые числа глубины.
- Все производные величины считаются ТОЛЬКО от `BookView`, полученного из ТЕКУЩЕГО
  `BookState` в момент вызова — нет кэша, живущего дольше одного события (иначе staleness
  типа §3 теряет смысл: кэш мог устареть незаметно).

## §N. Интерфейсные контракты
- **Consumed:** `Md(L2Delta|L2Snapshot|Trade|MarkPx)` (T1 ← журнал, продюсер `venues`).
- **Produced:** `BookView`/`DepthBands` (T2 → `signals`, `strategy` — читают напрямую как
  функцию текущего `BookState`, не как событие в журнале — производные не персистятся,
  они выводимы реплеем); намерение ресинка (рабочий T1-кандидат, см. §O) → `venues`.
- **Refused:** прямой сетевой вызов откуда-либо в `book` (архитектурно невозможен — крейт
  не тянет сетевые зависимости, arch-lint проверяет отсутствие `reqwest`/`tokio-tungstenite`
  и любых venue-специфичных крейтов в `Cargo.toml` крейта `book`); подмена `Stale` на
  `Fresh` любым консюмером (`staleness` — не мутабельное поле снаружи типа).

## §I. Инварианты (`BK-I-1..8` + `BK-I-Z`) — RED-оракулы (тест падает на заглушке)
1. **BK-I-1** Gap-детекция — строго сравнение sequence-номеров; НИКАКОЙ эвристики/`rand()`
   поверх (анти-урок hft-core-rs; grep-канарейка на `rand`/`random` в крейте `book`).
2. **BK-I-2** На гэпе `staleness → Stale` СИНХРОННО, до обработки следующего события — не
   существует окна, где книга уже «дырявая», но ещё помечена `Fresh`.
3. **BK-I-3** `BookView` на `Stale` книге возвращается КАК `Stale` (не подставляется старое
   значение под видом свежего; консюмер не может получить `depth()` без явной проверки
   staleness — материализовано типом, не документацией).
4. **BK-I-4** Редьюсер `(BookState, Event) -> BookState` детерминирован: реплей одной и той
   же последовательности `Md`-событий трижды даёт бит-идентичный `BookState` (зеркало DET-I-1).
5. **BK-I-5** `book` не открывает сеть и не импортирует venue-специфичные крейты (arch-lint
   грep на сетевые зависимости в `Cargo.toml` крейта `book`).
6. **BK-I-6** `depth(side, pct_band)` монотонно неубывающая по `pct_band` (property-test:
   случайные книги, `pct_band_2 > pct_band_1 ⟹ depth_2 ≥ depth_1`).
7. **BK-I-7** Дублирующийся/устаревший seq НЕ триггерит ложный гэп (idempotent к
   ретрансмиту транспорта — тест с намеренно задублированным событием).
8. **BK-I-8** `book` не имеет пути записи в состояние `signals`/`strategy`/`risk`/`venues`
   (только читает свой вход из журнала и отдаёт `BookView` по запросу; arch-lint DAG-проверка).
- **BK-I-Z** Cornerstone-citability: §§ этого FA STABLE/APPEND-ONLY; правки — named amendment.

## §P. Фаза реализации
**P1 (Data plane)** — параллельно с `venue-hyperliquid` MD-адаптером; блокируется P0
(журнал/EventKind должны существовать). Блокирует: `signals`/OBI-формализацию (P2) —
сигнал №1 не имеет смысла без честных depth-полос; `research-cli` grid-раннер (P2) читает
книгу через реплей записанных P1-данных. Mock-точка: пока `venue-hyperliquid` не готов
целиком, `book` разрабатывается против recorder-фикстур (записанный WS-поток HL testnet,
DESIGN §1.5/§10 P1). Acceptance ворота P1 (DESIGN §10): 7 дней данных, gap-статистика,
«целостность книги green».

## §O. Открытые вопросы
- Конкретный `EventKind`-вариант для «намерения ресинка» (`BookIntegrity(ResyncRequested)`
  — рабочее название) НЕ зафиксирован; требует contract-RFC (05 §4) до конца P1 — либо
  новый вариант, либо переиспользование `Sys`. Совместно с владельцем `venues`.
- Референс-цена для `depth()` — зафиксирована как microprice в этом FA; подлежит сверке
  с founder'ом при формализации SignalSpec OBI (может оказаться, что нужен параметр —
  microprice vs best vs mid).
- Таймаут `Stale → эскалация в алерт` не зафиксирован числом `[verify-at-impl]`.
- Нужен ли `book` отдельный snapshot каждые N событий для быстрого cold-start (в
  дополнение к in-memory реконструкции) — вероятно нет (венью и так шлёт `L2Snapshot`
  на подписке), но не проверено на реальной задержке HL REST `[verify-at-impl]`.

## §A. Антитезис (steelman против дизайна)
- «Ресинк через журнал (book просит → venues делает) — лишний хоп; проще дать `book`
  прямой хендл на REST-клиент `venues`.» — Контр: прямой вызов делает `book` зависимым от
  `venues` вопреки «оба — слой 1, не подчинены друг другу» (DESIGN §2), и ресинк перестаёт
  быть частью журнала → реплей дня с гэпом не покажет, ЧТО и КОГДА было переспрошено.
  Стоимость (один лишний event-цикл, десятки мс) ничтожна против потери форензики.
- «Staleness как часть типа — церемония; проще глобальный флаг `is_stale` на книге, все
  и так проверят.» — Контр: «все и так проверят» — это ровно то допущение, которое
  привело к тихой лжи в hft-core-rs (стейл-данные, поданные как свежие). Тип, из
  которого нельзя достать `depth()` без явного разбора `Fresh|Stale`, переносит проверку
  с дисциплины разработчика на компилятор.
- «Монотонность `depth()` по `pct_band` — очевидное свойство, не стоит property-теста.» —
  Контр: очевидные свойства — ровно то, что молча ломается при рефакторинге накопительной
  суммы (off-by-one на границе полосы, двойной учёт уровня на стыке). Property-test дёшев
  (одна функция, `proptest`) и ловит именно такой класс регрессии автоматически.
