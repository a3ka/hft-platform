# killswitch — Functional Architecture (FA)

> CORNERSTONE FA (independent safety cutoff, Layer 5). Authored by architect (Fable)
> 2026-07-10. STABLE/APPEND-ONLY. Отдельный ПРОЦЕСС, не поток. Парный к `risk`.
> Источники: DESIGN §2/§4, fa/risk.md §7, 01-engine §7.

## §1. Идентичность модуля
- **Имя / крейт:** `killswitch` (`crates/killswitch/`).
- **Язык:** Rust, **отдельный бинарь/процесс** (не библиотека внутри движка).
- **Слой:** 5 (защищённая зона; квант-агенты НЕ пишут; тесты sacred).
- **Deploy:** отдельный процесс, свой биржевой коннект, свои креды, свой journal-tail-читатель.
- **Статус:** ACCEPTED 2026-07-10 (v1).
- **Карта секций:** §1 идентичность · §2 роль · §3 IS · §4 IS NOT · §5 триггеры и действие ·
  §6 halt-замок · §7 независимость от движка · §N контракты · §I инварианты · §T RED ·
  §P фаза · §O открытые · §A антитезис.

## §2. Стратегическая роль
`killswitch` — **вторая, независимая линия обороны**, работающая даже когда движок мёртв,
завис или сошёл с ума. `risk` (in-process) — первая линия, но паника/зависание внутри
движка убивает и её. `killswitch` живёт отдельным процессом именно чтобы гарантированно
исполнить единственную функцию: **отменить все наши заявки на бирже и заблокировать
торговлю** по команде оператора или по автоматическому триггеру. Это реализация RK-I-6
(рубильник работает при мёртвом движке) и RK-I-7 (после разрыва на бирже нет наших заявок).
Без него «fail-closed» — обещание; с ним — механизм.

## §3. Что модуль ЕСТЬ
**Онион-подструктура:**
- core (без I/O): `policy/` — чистые правила срабатывания (heartbeat-timeout, эскалация
  halt-триггеров).
- mid: `monitor/` — приём heartbeat движка + tail журнала (детекция `Risk(Halt)`,
  `Recon(Mismatch)`); `lock/` — управление halt-замком.
- outer (I/O): `sweep/` — собственный биржевой коннект для `cancel-all`; `operator/` —
  приём ручной команды kill от оператора.

**Доменный словарь (T2):**
- `KillTrigger = HeartbeatLost | OperatorKill | RiskHalt{reason} | ReconMismatch`.
- `HaltLock` — персистентный замок (файл/ключ), который движок обязан проверить при старте.
- `SweepResult` — результат `cancel-all` (сколько заявок отменено, подтверждение биржи).

**Обработка отказов/деградации (fail-closed — здесь абсолютно):**
| Условие | Исход |
|---|---|
| Пропажа heartbeat движка > T | автономный `cancel-all` + `HaltLock` (движок мог зависнуть) |
| Собственный биржевой коннект killswitch упал | повтор + алерт P0; замок ставится в любом случае |
| Неоднозначность (не знаем состояние) | сработать (лучше лишний cancel, чем пропущенный) |
| Движок рестартует при активном `HaltLock` | движок обязан НЕ стартовать торговлю (JR/RK-путь) |

## §4. Что модуль НЕ ЕСТЬ
1. **НЕ pre-trade gate** — не решает по конкретному ордеру (это `risk`); он бинарный
   рубильник «всё стоп», не фильтр.
2. **НЕ часть движка** — не поток, не библиотека in-process; иначе крах движка убил бы и
   его (весь смысл — независимость).
3. **НЕ торговый модуль** — не квотирует, не считает PnL, не строит книгу; читает лишь
   heartbeat + минимум журнала для триггеров.
4. **НЕ конфигурируемый-выключаемый** — нет режима «killswitch off»; он либо запущен, либо
   система не имеет права торговать (arming-предусловие).
5. **НЕ авто-возобновляемый** — снять `HaltLock` может только человек (re-arm), никакой
   автоматической разблокировки после срабатывания (RK-I-9-аналог).

## §5. Триггеры и действие
- **Ручной:** оператор шлёт kill (защищённый канал) → немедленный `cancel-all` + замок.
- **Heartbeat-timeout:** движок шлёт heartbeat каждые h; пропажа > T → killswitch считает
  движок недееспособным → автономный `cancel-all` + замок (RK-I-6/7).
- **Дублированные halt-триггеры:** `risk` при `Recon(Mismatch)` (RK-I-8) или пробитии
  loss-лимита (RK-I-9) эмитит `Risk(Halt)` в журнал И сигналит killswitch; killswitch,
  увидев это в tail'е ИЛИ по прямому сигналу, ставит замок — дублирование, чтобы отказ
  одного пути не снял защиту.
- **Действие всегда:** `cancel-all` по СВОЕМУ коннекту (не через oms/venue движка — они
  могут быть мертвы) + установка `HaltLock`.

## §6. Halt-замок
- Персистентный (файл/ключ) — переживает рестарт процессов. Формат/протокол снятия —
  `[open-question]` (см. §O), но принцип: движок при старте (arming, 01 §9) ОБЯЗАН прочитать
  замок; активен → торговля не начинается до снятия человеком.
- Замок — общий контракт между `killswitch` (ставит) и `runner`/`risk` (уважают при arming).

## §7. Независимость от движка (почему отдельный процесс)
Три независимости (аналог EINHARD Axis-5 deployment independence): (1) **процессная** —
крах/зависание/паника движка не затрагивает killswitch; (2) **коннекта** — свой биржевой
коннект и креды, чтобы `cancel-all` прошёл, даже если коннект движка мёртв; (3) **кода** —
минимальная кодовая база (меньше поверхности для собственных багов), не разделяет сложную
логику с движком. Heartbeat идёт ОТ движка К killswitch (пропажа = тревога), не наоборот —
чтобы «тишина» трактовалась как опасность, а не как норма (fail-closed).

## §N. Интерфейсные контракты
- **Consumed:** heartbeat движка (T2, IPC/loopback); tail журнала (T1 `Risk(Halt)`,
  `Recon(Mismatch)`); ручная kill-команда оператора; позиции/ордера биржи (read для sweep).
- **Produced:** `cancel-all` на биржу (свой коннект); `HaltLock`; `Ctl(KillSwitch)` событие
  (T1 → journal — для реплея: кто/что/когда сработало).
- **Refused:** любое авто-снятие замка; торговые действия кроме отмены; зависимость от
  живости движка для срабатывания.

## §I. Инварианты (KS-I) — RED-оракулы (sacred)
1. **KS-I-1** killswitch — отдельный процесс со своим коннектом/кредами (не in-process) —
   архитектурный тест: убить движок → killswitch жив и отменяет (зеркало RK-I-6).
2. **KS-I-2** Пропажа heartbeat > T → автономный `cancel-all` + замок (тест-drill).
3. **KS-I-3** После срабатывания на бирже нет наших заявок (integration drill, зеркало RK-I-7).
4. **KS-I-4** `HaltLock` переживает рестарт; движок при активном замке не начинает торговлю
   (тест arming-предусловия).
5. **KS-I-5** Снятие замка возможно ТОЛЬКО человеком (нет авто-разблокировки — тест
   отсутствия пути).
6. **KS-I-6** Триггеры дублированы (журнал + прямой сигнал); отказ одного пути не снимает
   защиту (тест: заглушить один путь → срабатывает по другому).
7. **KS-I-7** «Тишина» = опасность: неопределённость состояния → срабатывание (fail-closed).
- **KS-I-Z** Cornerstone-citability: §§ STABLE/APPEND-ONLY; правки named-not-silent.

## §O. Открытые вопросы
- Формат `HaltLock` (файл с подписью vs ключ в хранилище) и протокол снятия человеком.
- Значение T (heartbeat-timeout): слишком мало → ложные срабатывания при джиттере; слишком
  много → окно риска. Калибровка на P3 из измеренных latency (P1).
- Канал ручной kill-команды (защита от случайного/несанкционированного срабатывания vs
  скорость) — `[verify-at-impl]` с учётом HL.
- Есть ли у HL биржевой cancel-on-disconnect, дополняющий KS-sweep (`[verify-at-impl]`);
  если да — используем оба (defense-in-depth).

## §A. Антитезис (steelman против дизайна)
- «Отдельный процесс + свой коннект — сложность и лишние креды.» — Контр: единственный
  сценарий, ради которого он существует — «движок завис с открытыми ордерами» — не крыт
  ничем in-process; стоимость мала, цена отсутствия = неконтролируемая позиция на живом рынке.
- «Дублированные триггеры могут ложно срабатывать и останавливать торговлю зря.» — Контр:
  на этапе доказуемости ($500–2k) ложный halt дёшев; частота — метрика калибровки T/ε, не
  повод убирать дублирование; пропущенное срабатывание несимметрично дороже.
- «Замок, снимаемый только человеком, мешает автономности 24/7.» — Контр: это осознанный
  выбор R-CANON-5-аналога (человек в контуре аварийного возврата); автономен ТОРГОВЫЙ цикл,
  но НЕ возврат из halt — там подпись обязательна, как и промоушен стратегии.
