## §2. Стратегическая роль
`alpha` — детерминированный комбайнер: берёт множество `SignalOut` от `signals` (Layer 2)
и превращает их в ОДИН `Forecast` на инструмент по формуле `forecast = Σ w_i ·
normalize(signal_i)`, где веса `w_i` приходят ИСКЛЮЧИТЕЛЬНО из подписанного
калибровочного артефакта (Ctl(ParamChange), Граница C, `03 §3`). Никакого онлайн-обучения,
никакой адаптации весов в рантайме — это структурный барьер между «квант-деск подобрал
веса на исторических данных и founder подписал» и «движок применяет то, что подписано».

Позиция в потоке: `book → signals → [alpha] → portfolio → strategy → risk → oms → venue`.
`alpha` — первое место в конвейере, где несколько независимых голосов сигналов сходятся в
одно число; это делает его естественной точкой, где различие `paper` vs `live` статуса
ДОЛЖНО стать физическим (не «почти не отправится», а структурно не может, INTG-I-5).

## §3. Что модуль ЕСТЬ
**Онион-подструктура:**
- core (без I/O): `combine.rs` — чистая функция `(Vec<SignalOut>, &WeightTable,
  &NormalizationParams) -> Option<Forecast>`; `normalize.rs` — пер-сигнальная нормализация
  (используя КАЛИБРОВОЧНЫЕ статистики, тоже из подписанного `Ctl(ParamChange)`, не
  вычисляемые на лету).
- mid: `state.rs` — держит `WeightTable` (текущие веса на инструмент/сигнал) + «последний
  известный» `SignalOut` на `signal_id` со staleness-меткой; обновляется ТОЛЬКО
  журнальным редьюсером над `Ctl(ParamChange)` и потоком `SignalOut` (детерминизм —
  зеркало паттерна `risk::RiskState`, `risk.md` §6).
- outer: тонкий — у `alpha` нет сетевого/файлового I/O в принципе; единственная
  «внешняя» операция — восстановление `WeightTable` реплеем журнала при старте движка
  (тот же паттерн, что `RiskState` boot-реплей в `risk.md` §6, не сетевой вызов).

**Доменный словарь (T2, владеет крейт):**
- `Forecast` — `{instrument, ts_event_mono_ns, value: i64 (×1e8), contributing:
  Vec<{signal_id, weight, normalized_value, included: bool}>}`. Поле `contributing`
  ОБЯЗАТЕЛЬНО (не опционально) — держит «реплей объясняет каждый цент» (DESIGN §1)
  на уровне прогноза, не только на уровне PnL.
- `WeightTable` — `{instrument -> {signal_id -> ensemble_weight}}`; **приватный
  конструктор** внутри `alpha` — мутируется ТОЛЬКО редьюсером над `Ctl(ParamChange)`,
  зеркало `RiskApproved<Order>` типового барьера (`risk.md` §3).
- `NormalizationParams` — калибровочные статистики нормализации на сигнал (напр.
  scale/clip), тоже T2, тоже приходят только через `Ctl(ParamChange)`.
- `StaleInputPolicy` — не флаг, а фиксированное поведение (см. §3 таблица деградации) —
  явное исключение из суммы, никогда implicit-redistribution.

**Обработка отказов/деградации (fail-closed, как `risk`):**
| Условие | Детерминированный исход |
|---|---|
| `WeightTable` не заполнена для инструмента (ни одного реплеенного `Ctl(ParamChange)`) | `Forecast` НЕ эмитится («нет мнения», не default-вес; зеркало RK-I-3 fail-closed) |
| `SignalOut` для `live`-сигнала отсутствует/устарел (за пределами `horizon_ms`) на текущий тик | исключается из Σ на ЭТОТ тик; `contributing` явно помечает `included=false` — НЕ трактуется как значение 0, вес НЕ перераспределяется автоматически |
| `SignalOut` помечен `status=paper`/`candidate` | исключается из ЖИВОГО `Forecast` целиком; идёт только в отдельный paper-приёмник (материализация INTG-I-5 здесь, §7) |
| `SignalOut` помечен `status=retired` (защита в глубину — не должен случиться, `signals` их не инстанцирует) | исключается, как paper; лог аномалии |
| новый `Ctl(ParamChange)` посреди потока | применяется атомарно на `seq` этого события — реплей воспроизводит момент перехода бит-в-бит |
| неподписанный/битый `Ctl(ParamChange)` в журнале (по конструкции невозможен, INTG-I-3; защита в глубину) | Reject обработки → Halt-эквивалент (зеркало RK-I-5: `alpha` отказывается работать на испорченной истории весов, не «использует последний хороший») |
| переполнение/NaN в fixed-point арифметике `combine` | тик отклоняется целиком, `Forecast` для него не публикуется (никогда частичный/мусорный прогноз) |

## §4. Что модуль НЕ ЕСТЬ
1. **НЕ генерация сигналов** — не придумывает и не считает ни одного «сырого» сигнала
   сам; строго читает то, что `signals` уже произвёл (это территория `signals`).
2. **НЕ sizing/portfolio** — не решает размер позиции, не знает про капитал/лимиты/
   инвентарь/корреляции между инструментами; `Forecast` — направление+сила, не целевая
   позиция (это `portfolio`).
3. **НЕ калибровочный движок** — не подбирает веса (никакого online learning, градиентов,
   регрессии в hot-path); веса — внешне произведённый подписанный артефакт, который
   `alpha` только ПРИМЕНЯЕТ (подбор — офлайн, `portfolio-analyst`/research-cli, дизайн-тайм).
4. **НЕ risk/execution** — не гейтит ордера, не считает лимиты, не трогает
   `OrderGateway` (территория `risk`/`oms` ниже по потоку).
5. **НЕ реестр-авторитет** — не решает промоушен статуса сигнала (это очередь решений +
   подпись founder'а, Граница C); `alpha` лишь применяет уже подписанный вес, который
   решение УЖЕ назначило.
6. **НЕ сетевой/I/O-компонент** — нет прямых вызовов venue/API; вход строго
   `SignalOut`-поток + журнально-выведенная `WeightTable`, оба источника — журнал.

## §5. Combine (ядро)
```
forecast(instrument, t) = Σ_i  w_i(instrument) · normalize_i(signal_i.value)
    где сумма — только по i, для которых:
      status(signal_i) == live  AND  fresh(signal_i, t)  AND  weight_i > 0
```
- Чистая функция входа `(Vec<SignalOut> на тик, &WeightTable, &NormalizationParams) ->
  Option<Forecast>`; при пустом множестве включённых `i` — `None` (нет прогноза, не 0 —
  0 это валидный прогноз «нейтрально», отсутствие включённых входов — другое состояние).
- Порядок обработки детерминирован (по `seq` события, как везде в журнале) — одинаковая
  последовательность `(SignalOut, Ctl(ParamChange))` → бит-идентичная последовательность
  `Forecast` при повторном прогоне (AL-I-3, зеркало DET-I-1).
- `normalize_i` использует калибровочные статистики ИЗ `NormalizationParams` (тоже
  подписанные, Граница C) — никогда не пересчитывает статистику на лету по скользящему
  окну живых данных (это было бы формой онлайн-адаптации, запрещено AL-I-2).

## §6. WeightTable (Граница C, T2 с типовым барьером)
`WeightTable` — журнальный редьюсер, структурно идентичный `RiskState` в `risk.md` §6:
- Мутируется ТОЛЬКО обработкой `Ctl(ParamChange{signed})` из журнала; других сеттеров
  не существует (приватный конструктор внутри `alpha`, зеркало `RiskApproved`).
- `portfolio-analyst`/founder формируют предложение `{signal_id, instrument, from, to,
  rationale, report_ref}` → очередь решений → подпись Ed25519 → атомарное применение →
  `Ctl(ParamChange{signed})` в журнал (`03 §3`, дословный перенос HDP).
- Реплей журнала с нуля обязан восстановить БИТ-ИДЕНТИЧНУЮ `WeightTable` относительно
  той, что накопилась на живом движке к тому же `seq` (AL-I-9) — иначе `replay==
  реальность` (DESIGN §1) рвётся именно на весах ансамбля, самом чувствительном месте
  для денег после `risk`.
- Реестр (`signals.json`) и `WeightTable` — РАЗНЫЕ артефакты: реестр несёт
  `ensemble_weight` как ПОСЛЕДНЕЕ ПОДПИСАННОЕ значение (снапшот, `03 §2`); `WeightTable`
  внутри `alpha` — живая, журнально-выведенная проекция истории всех `Ctl(ParamChange)`
  для данного инструмента/сигнала. Источник истины для рантайма — журнал, не файл
  реестра (файл — витрина для людей/дэшборда).

## §7. Paper vs live маршрутизация (материализация INTG-I-5)
`alpha` — первое место в конвейере, где сигналы РАЗНЫХ статусов физически сходятся
(`signals` их производит единообразно, см. `signals.md` §7 SG-I-7). Здесь граница
становится структурной, не «по соглашению»:
- ЖИВОЙ `Forecast` (потребляется `portfolio` → … → `venue`) строится Σ ТОЛЬКО по
  `status==live` входам с `weight>0`.
- `paper`/`candidate` входы считаются В ОТДЕЛЬНЫЙ `Forecast` (тот же `combine`, другой
  вызов, другой приёмник) — используется ТОЛЬКО для мониторинга/decay-watch (`02 §3.8`)
  и sim-vs-paper дивергенции; этот `Forecast` НИКОГДА не передаётся `portfolio` в
  live-режиме (типовой барьер на границе `alpha→portfolio`: живой путь принимает только
  тип, помеченный live-происхождением, зеркало `risk::OrderGateway::place` приёма только
  `RiskApproved`).
- Смешение исключено структурно, а не проверкой во время выполнения: если бы `alpha`
  отдавала один недифференцированный `Forecast` и фильтрация случалась ГДЕ-ТО дальше —
  один пропущенный `if` превращал бы paper-сигнал в реальный ордер. Разделение здесь —
  самая ранняя точка, где это ещё дёшево гарантировать типами.

## §8. Explainability / audit
`Forecast.contributing` — не опциональное поле для дебага, а часть контракта: для
КАЖДОГО тика перечисляет, какие `signal_id` вошли, с каким весом, с каким нормализованным
значением, и явно — какие были доступны, но исключены (`included=false`), и почему
(`stale | paper | zero-weight`). Это прямое продолжение тезиса DESIGN §1 «реплей
объясняет каждый цент»: PnL-атрибуция (EOD, `01 §10`) не может честно приписать
результат сигналу, если сам прогноз непрозрачен в момент, когда он породил ордер.

## §N. Интерфейсные контракты
- **Consumed:** `SignalOut` (T2 ← `signals`, с обязательным `status`-тегом); `Ctl(
  ParamChange)` (T1 ← journal, подписанные веса/калибровка, Граница C); собственная
  реплеенная `WeightTable` (внутреннее состояние, не внешний вход).
- **Produced:** `Forecast` (T2 → `portfolio`, единственный живой потребитель) +
  paper-`Forecast` (T2 → paper-мониторинг/decay-watch, НЕ → `portfolio` live-пути).
- **Refused:** любой вес, не выведенный из подписанного `Ctl(ParamChange)` (нет
  публичного сеттера `WeightTable`); прямой проброс `SignalOut` в `portfolio` в обход
  `combine` (portfolio не понимает `SignalOut`, только `Forecast` — типовой барьер);
  paper-`Forecast` на живом пути (см. §7).

## §I. Инварианты (AL-I-1..9 + AL-I-Z) — RED-оракулы (sacred; тест падает на заглушке)
1. **AL-I-1** Веса — ТОЛЬКО через подписанный `Ctl(ParamChange)`: нет альтернативной
   поверхности записи в `WeightTable` (зеркало RK-I-10/INTG-I-3; тест утверждает
   ОТСУТСТВИЕ публичного сеттера, не «default off»).
2. **AL-I-2** Нет онлайн-обучения/фиттинга в рантайме: `combine`/`normalize` — чистые
   функции текущего `(SignalOut[], WeightTable, NormalizationParams)`; grep-канарейка на
   ML-тренировочные крейты/градиентный код в `crates/alpha/src/`.
3. **AL-I-3** `Forecast` детерминирован/реплеится: одинаковая `(Event, Ctl(ParamChange))`
   история → бит-идентичная последовательность `Forecast` (зеркало DET-I-1; тест —
   двойной реплей, сравнение хэшей).
4. **AL-I-4** `paper`/`candidate`-вклады НИКОГДА не входят в живую Σ — только в
   отдельный paper-`Forecast` (материализация INTG-I-5); тест конструирует
   paper-помеченный `SignalOut` и проверяет его отсутствие в живом `contributing` и в Σ.
5. **AL-I-5** Отсутствующий/устаревший `live`-вход никогда не трактуется молча как ноль:
   явное исключение с записью в `contributing` (`included=false` + причина), без
   implicit-перераспределения веса.
6. **AL-I-6** Неизвестный инструмент (нет записи в `WeightTable`) → `Forecast` не
   эмитится (fail-closed, зеркало RK-I-3); никогда fallback на дефолтный/глобальный вес.
7. **AL-I-7** `retired`-статус никогда не комбинируется, даже если устаревший
   `SignalOut` каким-то образом реплеился (защита в глубину поверх SG-I-7).
8. **AL-I-8** `alpha` отказывается комбинировать `SignalOut`, чей `signal_id`+`version`
   не найден в текущем загруженном снапшоте реестра (зеркало INTG-I-4 на стороне
   потребления, не только на стороне `signals`-загрузки).
9. **AL-I-9** Реплей `WeightTable` с нуля бит-в-бит совпадает с живо-накопленной
   `WeightTable` к тому же `seq` (зеркало DET-I-1/CT-I-3, применённое к весам ансамбля).
- **AL-I-Z** Cornerstone-citability: §§ этого FA STABLE/APPEND-ONLY; правки — named,
  не silent (Amendment history внизу).

## §P. Фаза реализации
**Скелет (single-signal, `weight=1.0` identity passthrough) требуется к P3 (M-05/M-06)** —
чтобы собрать полную цепочку `book→signals→alpha→portfolio→strategy→risk→oms→venue` для
testnet-торговли (P3) и live-micro (P4): без хотя бы тривиального `alpha` `strategy`
нечего квотировать. **Полный многосигнальный калиброванно-взвешенный ансамбль матереет
на P4-P5** — когда появляется ≥2 `live`-сигналов с реально откалиброванными весами и
подключается работа `portfolio-analyst` по корреляциям (DESIGN §10 P5 «квант-деск на
полном цикле; корреляции/portfolio»). До P5 корреляция между живыми сигналами НЕ
учитывается этим крейтом (см. §O) — сознательное упрощение, компенсируемое роадмап-гейтом
«≤1-2 сигнала на одну пару» на P4 (DESIGN §4). Блокирует: `portfolio` (Layer 4, читает
`Forecast`). Блокируется: `signals` (P2, `SignalOut`) + Граница C инфраструктура очереди
решений (`03 §3`, нужна раньше `M-05` для первой реальной подписи веса).

## §O. Открытые вопросы
- Точная формула `normalize_i` (z-score vs min-max vs rank-based) и откуда берутся её
  калибровочные статистики (тот же подписанный артефакт, что и вес, или отдельный?) —
  `[verify-at-impl]` до M-04.
- Порог staleness (`fresh(signal_i, t)`) — читается из `horizon_ms` в params сигнала
  (собственность `signals`, см. `signals.md` §O) или отдельный конфиг уровня `alpha`?
  Нужен единый owner до M-04, иначе два крейта могут разойтись в трактовке свежести.
- Корреляция между `live`-сигналами до P5: наивная сумма весов может завысить
  эффективную экспозицию, если два сигнала коррелированы (общая идея под разными
  параметрами). Известный, зафиксированный пробел — закрывается `portfolio`-уровневой
  корреляционной работой P5, роадмап-гейтом ограничен на P4 (≤1-2 сигнала, `04 §4`).
- Тип paper-`Forecast`: переиспользовать тот же T2 `Forecast` с флагом происхождения или
  завести отдельный `PaperForecast` (жёстче разделение типов, ближе к духу INTG-I-5
  «физически не может»)? Решить до M-04 — влияет на то, насколько буквально типовой
  барьер `alpha→portfolio` держит границу live/paper.

## §A. Антитезис (steelman против дизайна)
- «Линейная взвешенная сумма — слишком простая модель комбинации; настоящий альфа-микс
  требует режимной чувствительности/нелинейной комбинации.» — Контр: простота здесь —
  требование безопасности, не ограничение моделирования: нелинейный/адаптивный комбайнер
  либо требует онлайн-фиттинга (запрещено AL-I-2), либо требует куда большей подписанной
  поверхности параметров (реализуемо через `Ctl(ParamChange)`, напр. запечённое дерево
  порогов) — отложено на P5, когда достаточно разнообразия живых сигналов, чтобы
  оправдать сложность; до этого неверное нелинейное правило опаснее неверного веса.
- «Жёсткое исключение устаревших/paper входов (вместо мягкой деградации) выбрасывает
  полезную информацию.» — Контр: тихая деградация (напр. авто-перераспределение веса) —
  ровно тот `fail-open`-паттерн (`risk_guard`, DESIGN §9), который вся платформа
  сознательно отвергает; явное исключение + audit-trail держит прогноз объяснимым ценой
  некоторой негладкости — приемлемо при доктрине «отсутствие ≠ ноль».
- «Держать `alpha` в неведении о корреляции между сигналами (это дело `portfolio`)
  означает garbage-in на стороне sizing, даже если математика `alpha` "верна".» — Контр:
  честное ограничение, признанное в §O, а не спрятанное: до готовности P5-корреляционной
  работы ансамбль из двух коррелированных сигналов будет выглядеть искусственно сильным;
  роадмап-гейт (`04 §4`) намеренно держит ранний live-micro на ≤1-2 сигналах одной пары
  именно чтобы ограничить цену этого пробела, а не притвориться, что его нет.
- Честный худший случай: `alpha` может добросовестно и воспроизводимо скомбинировать
  подписанные веса — и всё равно быть неправым, если сами входные сигналы были
  переобучены на этапе `02 §4`. Инварианты этого FA гарантируют, что шаг КОМБИНАЦИИ
  честен и реплеится, а не что ВХОД хорош — эта ответственность целиком в
  анти-оверфит-процессе `02 §4`, вне досягаемости этого крейта.
