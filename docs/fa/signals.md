## §1. Идентичность модуля
- **Имя / крейт:** `signals` (`crates/signals/`).
- **Язык:** Rust, без `unsafe`, без async в hot-path.
- **Слой:** 2 (`01 §2`).
- **Deploy:** статически слинкован в движок (`runner`/`strategy`, live+paper+backtest); тот
  же крейт линкуется в `sim`/`research-cli` для гридов — ОДИН код исполняется во всех
  четырёх режимах (`backtest == paper == live-micro == live`, DESIGN §1 равенство №2).
- **Статус:** ACCEPTED 2026-07-10 (v1).
- **Карта секций:** §1 идентичность · §2 роль · §3 IS · §4 IS NOT · §5 `Signal` trait и
  жизненный цикл · §6 SignalRegistry (Граница B) · §7 OBI — сигнал №1 · §8 анти-оверфит
  зацепки · §N контракты · §I инварианты SG-I-1..11+Z · §T RED-маппинг · §P фаза ·
  §O открытые · §A антитезис.

## §2. Стратегическая роль
`signals` — **единственная зона кода, куда квант-агенты имеют write-доступ** (Граница A,
`03 §4`). Модуль превращает поток событий (`book`-производные — depth-полосы, microprice,
+ сырые `Md`/`Ord`-события журнала) в дискретный, детерминированный, воспроизводимый сигнал
на инструмент — и ничего больше. Это шов между «квант-деск на дизайн-тайме придумал идею»
и «движок на рантайме безопасно её исполняет»: всё, что квант-агент написал, обязано
пройти через этот крейт (не через `alpha`, не через `portfolio`, не через `risk`).

Позиция в потоке: `book → [signals] → alpha → portfolio → strategy → risk → oms → venue`.
Без этого модуля LLM-агентам просто негде писать код, влияющий на торговлю, — вся
остальная поверхность движка защищена scope-guard'ом (`04 §3`).

## §3. Что модуль ЕСТЬ
**Онион-подструктура:**
- core (без I/O, без часов, без будущего): отдельные реализации `impl Signal for …` —
  каждый сигнал = один модуль в `crates/signals/src/<name>.rs` (напр. `obi.rs`). Чистый
  редьюсер: `(текущее внутреннее состояние, &Event) -> Option<SignalOut>`.
- mid: `bank.rs` — `SignalBank`, держит живые инстансы зарегистрированных сигналов,
  маршрутизирует каждый `Event` во ВСЕ инстансы, собирает `SignalOut`ы; чистая
  оркестрация, сам по себе тоже без I/O (не путать с загрузкой реестра).
- outer: `registry/` — загружает `research/registry/signals.json` РОВНО ОДИН РАЗ при
  старте движка (I/O случается на boot, не в hot-path), валидирует `code_hash` и
  params-schema, инстанцирует `SignalBank` только сигналами со статусом
  `candidate|paper|live` (см. §6).

**Доменный словарь (T2/T3, владеет крейт):**
- `SignalOut` — T2, `{signal_id, ts_event_mono_ns, value: i64 (×1e8 fixed-point), status:
  RegistryStatus, meta}`. Единственная форма, которую `signals` отдаёт наружу.
- `SignalSpecRef` — T2, ссылка-хэндл на карточку `research/specs/S-NNN-<name>.md`
  (id + version), возвращается `spec()`; используется critic'ом/reviewer'ом для
  сопоставления кода и спеки.
- `SignalId` — newtype-обёртка над `String`, формат `S-NNN-<slug>`, валидируется при
  регистрации (не голая строка — опечатка в id не должна тихо создать «новый» сигнал).
- `RegistryStatus` — зеркало поля `status` из `signals.json` (`candidate|paper|live|
  retired`); `signals` крейт его ЧИТАЕТ и пробрасывает в `SignalOut`, но не присваивает.
- Params-структуры (T3) — по одной на сигнал, десериализуются из `signals.json.params`
  и валидируются против params-schema из соответствующего `SignalSpec` при загрузке.

**Обработка отказов/деградации:**
| Условие | Детерминированный исход |
|---|---|
| `signal_id` в реестре ссылается на несуществующий/незарегистрированный модуль | Reject на старте движка (боевой отказ загрузки, не тихий skip; SG-I-6/INTG-I-4) |
| `code_hash` в реестре ≠ хэш скомпилированного модуля | Reject на старте (SG-I-6/INTG-I-4) |
| params не проходят params-schema сигнала | Reject на старте (fail-closed, как `risk` §3 неизвестный инструмент) |
| статус `retired` в реестре | сигнал НЕ инстанцируется (нет лишнего compute, нет случайной утечки в ансамбль) |
| `on_event` возвращает `Err`/паникует | ошибка ИЗОЛИРУЕТСЯ на этот сигнал: для данного тика `SignalOut` не эмитится (явное отсутствие, НЕ ноль); движок и остальные сигналы продолжают работать (SG-I-9) |
| попытка доступа к будущему/часам (структурно невозможна) | закрыта сигнатурой `trait Signal` (только `&Event`) + arch-lint grep-канарейка (SG-I-1/SG-I-4) |
| новый сигнал без unit-теста / детерминизм-теста / SignalSpec-карточки в том же PR | ревью-гейт reject (SG-I-10, материализация `03 §4`) |

## §4. Что модуль НЕ ЕСТЬ
1. **НЕ `alpha`** — не взвешивает и не комбинирует несколько сигналов в прогноз; отдаёт
   каждый сигнал по отдельности, «сырым» (нормализованным внутри себя, но не ансамблем).
2. **НЕ `portfolio`** — не считает размер позиции, не знает про лимиты/инвентарь/капитал;
   это дальше по цепочке.
3. **НЕ `risk`** — не гейтит ордера, не видит `Order`/`RiskState`; `signals` физически не
   способен коснуться биржи (нет зависимости на `oms`/`risk`/`venues`, `01 §2`).
4. **НЕ `book`** — не строит L2/microprice/depth-полосы сам; ПОТРЕБЛЯЕТ их как вход
   (`DepthBands` от `book` приходит внутри/рядом с `Event`, не пересчитывается здесь).
5. **НЕ реестр-авторитет** — не решает, кто получит статус `paper`/`live` (это очередь
   решений + подпись founder'а, Граница C, `03 §3`); `signals` только читает и
   инстанцирует то, что реестр УЖЕ содержит.
6. **НЕ `research-cli`** — не гоняет гриды/walk-forward сам; backtest-runner ПРОГОНЯЕТ этот
   же крейт через исторический журнал (тот же код, другой источник событий — DESIGN §1
   равенство №2), но оркестрация грида — снаружи.

## §5. `Signal` trait и жизненный цикл
```rust
trait Signal {
    fn on_event(&mut self, ev: &Event) -> Option<SignalOut>;
    fn spec(&self) -> SignalSpecRef;
}
```
- Единственный вход — `&Event` (журнальный тип, `05 §2`); никакого `&mut self`-доступа к
  чему-либо внешнему (сети, файлам, системным часам). Время — ТОЛЬКО из
  `Event.ts_mono_ns`/`ts_wall_ms`.
- `on_event` вызывается для КАЖДОГО события в `SignalBank`, независимо от `EventKind` —
  сам сигнал решает, что для него релевантно (напр. OBI реагирует на `Md(L2Delta)`,
  игнорирует `Ord(*)`).
- Жизненный цикл сигнала (`candidate → paper → live → retired`, `02 §3`) НЕ меняет код в
  `signals` — один и тот же `impl Signal` исполняется на всех статусах одинаково;
  различается только МАРШРУТИЗАЦИЯ его `SignalOut` дальше (paper-приёмник vs live-ансамбль,
  решает `alpha`, INTG-I-5). Это сохраняет `backtest == paper == live` равенство: смена
  статуса — событие в реестре/журнале, не перекомпиляция сигнала.
- Промоушен `candidate→paper→live` требует подписанного `decisions/D-NNN` (INTG-I-2);
  `signals` крейт этого не проверяет — он доверяет тому, что УЖЕ прошло верификацию на
  границе загрузки реестра (§6).

## §6. SignalRegistry (Граница B, T1 read-only здесь)
`signals` крейт — консюмер `research/registry/signals.json` (T1, `05 §2`), НЕ продюсер;
запись реестра идёт через квант-деск + подпись founder'а (Граница B/C), не через этот
крейт. При старте движка:
1. Прочитать `signals.json`, для каждой записи со статусом `candidate|paper|live`:
   пересчитать `sha256` соответствующего скомпилированного модуля → сравнить с
   `code_hash` в записи → mismatch = Reject boot (SG-I-6).
2. Десериализовать+провалидировать `params` против params-schema сигнала → mismatch =
   Reject boot.
3. Инстанцировать `Signal` с этими `params`, зарегистрировать в `SignalBank` под
   `signal_id` + текущим `RegistryStatus`.
4. `retired` записи пропускаются (не инстанцируются вовсе).

Реестр перечитывается ТОЛЬКО при рестарте движка (не hot-reload в hot-path — смена
статуса/весов уже сама по себе журналируемое событие через Границу C, `alpha` его
реплеит; `signals` не следит за реестром динамически, только за собственным
`code_hash`/params, зафиксированными на boot).

## §7. OBI — сигнал №1 (пример, `00 §Q1`)
Первое зарегистрированное семейство: **order-book imbalance** — имбаланс depth-полос
`bid(3%)` vs `ask(8%)` ≥ порога `θ` → направленный сигнал. Формализуется как параметрическое
семейство `imbalance(D_bid, D_ask, θ, horizon_ms)`:
- Вход: `book::DepthBands(side, pct_band)` — примитив уже посчитан `book` (Layer 1,
  `01 §4`), `obi.rs` его только читает из `Event` (депф-полосы приходят как производные
  события/поле, не пересчитываются здесь).
- `params`: `{d_bid_pct: 3.0, d_ask_pct: 8.0, theta: 0.62, horizon_ms: 1500}` — в
  `signals.json.params`, приходят через Границу B (см. пример записи в `03 §2`).
- `on_event`: на каждый апдейт книги пересчитывает имбаланс полос; если `≥ θ` — эмитит
  `SignalOut{value: normalized_score, ...}`; иначе `None` (нет сигнала — не «сигнал=0»;
  `alpha`, консюмируя, различает «нет мнения» и «мнение=0», см. `alpha.md` §3 таблица).
- SignalSpec-карточка: `research/specs/S-001-obi-asym.md`; hypothesis-карточка-предок:
  `research/hypotheses/H-20260710-obi-asym.md` (пре-регистрация, `02 §3.1`).
- Асимметрия полос (3%/8%) — сама гипотеза founder'а; `signals` её НЕ интерпретирует,
  просто исполняет параметрическую формулу как написано в спеке.

## §8. Анти-оверфит зацепки (что этот крейт даёт процессу `02 §4`)
- **Детерминизм-тест обязателен на каждый сигнал** (SG-I-2) — без него `backtest-runner`
  не может доверять гриду (повторный прогон с теми же данными обязан давать тот же
  результат; недетерминированный сигнал ломает `trials-ledger`/deflated-Sharpe целиком).
- **Отсутствие доступа к будущему структурно** (SG-I-1) — снимает целый класс
  leakage-багов (критик чек-лист `02 §4.4` пункт 1) на уровне типов, не на уровне
  ревью-глаза.
- **`code_hash`-привязка** (SG-I-6) не даёт «тихо поправить код после валидации» —
  любое изменение сигнала после промоушена = новая `version` = новый цикл валидации,
  не незаметный патч поверх уже подписанного отчёта.

## §N. Интерфейсные контракты
- **Consumed:** `Event` (T1 ← `journal`, включая `book`-производные депф-полосы/microprice
  внутри `Md`-потока); `SignalRegistry` entry (T1 ← `research/registry/signals.json`,
  read-only при старте).
- **Produced:** `SignalOut` (T2 → `alpha`, единственный потребитель).
- **Refused:** прямой доступ к `oms`/`risk`/`venues`/`portfolio`/`strategy` (нет такой
  зависимости, `01 §2` направление вниз); запись в `signals.json` (только чтение —
  запись идёт через Границу B снаружи крейта); любой сетевой/файловый вызов внутри
  `on_event`.

## §I. Инварианты (SG-I-1..11 + SG-I-Z) — RED-оракулы (sacred; тест падает на заглушке)
1. **SG-I-1** No lookahead: `on_event(ev)` для тика T не зависит от событий с `seq > T`
   (тест: реплей с урезанным хвостом журнала даёт тот же `SignalOut` для тика T).
2. **SG-I-2** Purity/determinism: одинаковая последовательность `Event` → бит-идентичная
   последовательность `SignalOut` при повторном прогоне (зеркало DET-I-1).
3. **SG-I-3** No I/O в `on_event`/`spec`: grep-канарейка на `std::fs`/`std::net`/
   `tokio::net`/`reqwest` внутри `crates/signals/src/` (вне тестов).
4. **SG-I-4** No wall-clock: grep-канарейка на `Instant::now|SystemTime::now`; время
   только из `Event.ts_mono_ns`/`ts_wall_ms`.
5. **SG-I-5** Направление зависимостей вниз: `signals` не импортирует `oms|risk|venues|
   strategy|portfolio` (arch-lint, зеркало Границы A `03 §4`); квант-агенты пишут ТОЛЬКО
   `crates/signals/**` + `research/**`.
6. **SG-I-6** `code_hash` в реестре обязан совпадать с хэшем скомпилированного модуля
   (зеркало INTG-I-4); mismatch → Reject на старте, не тихий skip.
7. **SG-I-7** `retired` сигналы не инстанцируются; `candidate|paper|live` инстанцируются
   единообразно, `SignalOut` несёт свой `RegistryStatus` — крейт НЕ фильтрует по
   live/paper сам (фильтрация — граница `alpha`, см. `alpha.md` AL-I-4), но обязан
   пометить каждый выход честно (тест: paper-сигнал даёт `SignalOut` с `status=paper`,
   не безликий/неотмеченный).
8. **SG-I-8** Params, не прошедшие params-schema сигнала, → Reject на старте
   (fail-closed на конфигурацию, не только на рантайм-вход).
9. **SG-I-9** Ошибка/паника внутри ОДНОГО `on_event` не роняет движок и не порождает
   выдуманный `SignalOut`: для этого тика — явное отсутствие, остальные сигналы и
   последующие события продолжают обрабатываться.
10. **SG-I-10** Новый сигнал допускается в дерево ТОЛЬКО с unit-тестами +
    детерминизм-тестом + `SignalSpec`-карточкой в одном PR (структурная проверка:
    `crates/signals/src/<name>.rs` ⇒ обязаны существовать `tests/test_<name>_
    determinism.rs` + `research/specs/S-NNN-<name>.md`).
11. **SG-I-11** `SignalId`/`spec()` не «самозванствуют»: id, под которым сигнал
    зарегистрирован в реестре, обязан совпадать с id, который возвращает его
    собственный `spec()` (нет подмены одного сигнала другим на границе).
- **SG-I-Z** Cornerstone-citability: §§ этого FA STABLE/APPEND-ONLY; правки — named,
  не silent (Amendment history внизу).

## §P. Фаза реализации
**P2 (M-04)** — `trait Signal` + `SignalBank` + `registry/` загрузчик авторятся вместе с
research-cli/sim fill-model; OBI (`S-001-obi-asym`) — первый формализованный+
зарегистрированный сигнал, ворота P2 = OBI-отчёт по пре-регистрированным критериям +
paper-режим работает (DESIGN §10). Блокирует: `alpha` (Layer 3, читает `SignalOut`).
Блокируется: `journal` (P0, `Event`) + `book` (P1, `DepthBands`-примитив). Мок-точка:
до полного `book` P1 сигнал можно разрабатывать/тестировать на записанных фикстурах
депф-полос без живого фида (DESIGN §12 «дешёвый субагент пишет recorder параллельно»).

## §O. Открытые вопросы
- Точный диапазон/нормализация `SignalOut.value` (`[-1e8,+1e8]` направленный score vs
  калиброванная вероятность 0..1e8) — фиксируется до M-04, влияет на `alpha::normalize`.
- Формат params-schema: co-located JSON Schema в `contracts/` (как T1 `SignalSpec` card,
  `05 §2`) vs свободный текст в `research/specs/*.md` с ручной валидацией — нужно решить
  до появления второго сигнала (первый может проехать на честном слове).
- `horizon_ms` в params OBI — это TTL, который проверяет сам `signals` (не эмитить
  устаревший `SignalOut`), или ответственность `alpha` при потреблении? Сейчас
  трактуется как метаданные сигнала для downstream, но нужен явный owner до M-04.
- Реплей ИСТОРИЧЕСКОГО журнала, где сигнал в момент события имел статус `live`, а СЕЙЧАС
  — `retired`: должен ли `signals` уметь инстанцировать по ВЕРСИИ реестра на момент
  события (не по текущему `signals.json`), чтобы `replay(journal)==реальность` держалось
  и для forensics старых live-периодов? Пересекается с CT-I-3 (старый журнал читается
  новым кодом) — вероятно требует версионированного снапшота реестра в журнале, не
  только текущего файла.

## §A. Антитезис (steelman против дизайна)
- «Одна зона записи (`crates/signals`) — слишком узко; квант-агенту иногда реально нужен
  новый примитив в `book` (напр. новая depth-полоса).» — Контр: `book` — Layer 1,
  фундамент под несколько потребителей; если примитива не хватает, это `!!! SCOPE
  VIOLATION REQUEST !!!` к architect, а не рутинная работа агента — держит blast radius
  LLM-PR в одном ревьюабельном юнит-тестируемом крейте, а не размазывает его по движку.
- «No I/O запрещает полезные вещи — напр. закэшировать дорогое промежуточное вычисление
  на диск между тиками.» — Контр: кэширование дорогих вычислений — задача
  `research-cli`/грид-раннера (offline compute-слой), не hot-path на живом тике с
  ms-бюджетом; если сигнал дорог, дороговизна калибруется/предвычисляется офлайн и
  запекается в `params`, а не пересчитывается на лету.
- «Пробрасывать `RegistryStatus` в `SignalOut` вместо фильтрации на источнике —
  перекладывание безопасности на `alpha`, дублирование ответственности.» — Контр: та же
  логика типового барьера, что и `RiskApproved` в `risk` (`risk.md` §5) — граница с
  властью над деньгами (`alpha`→`portfolio`→`risk`) и есть правильное место
  структурного гейта; `signals`, оставаясь единообразным для всех статусов, держит
  свой контракт простым и дешёвым для unit-тестов (соответствие backtest==paper==live).
- Честный худший случай: SG-I-инварианты гарантируют ВОСПРОИЗВОДИМОСТЬ и ЧИСТОТУ кода,
  но НЕ прибыльность и НЕ отсутствие оверфита — субтильно переобученный, но формально
  «легальный» (детерминированный, без lookahead) сигнал пройдёт все проверки этого FA и
  всё равно потеряет деньги на live. Анти-оверфит защита живёт в процессе `02 §4`
  (пре-регистрация, trials-ledger, критик), не в этом крейте — `signals` может
  структурно гарантировать честность теста, не качество идеи.
