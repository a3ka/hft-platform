## §1. Почему этот слой обязан появиться раньше торговли

Факт, который стоит признать прямо: **за пять инцидентов подряд ни один не был пойман нашей
автоматикой.**

| Инцидент | Что было | Кто поймал |
|---|---|---|
| TD-011 | `open()` читал 2.65 GiB в RAM → recorder не писал | человек, ssh |
| TD-013 | 133 × HTTP 418 за 25 с (IP-бан Binance) | человек, ssh |
| TD-014 | 0 Funding-событий в журнале при «успешном» деплое | человек, ssh |

Во всех случаях: контейнер `healthy`, heartbeat свежий, CI зелёный, Deploy success. **Наш
healthcheck проверяет, что процесс жив, а не что он делает то, что должен.** Пока мы возим
только данные, цена — испорченный датасет. Как только появится `oms`, та же слепота будет
стоить деньги.

**Тезис слоя:** система обязана сама сообщать о тихой деградации. «Глаза оператора» (гейт §8) —
последний рубеж, а не первый.

## §2. Три подсистемы

```
   ┌─ A. МЕТРИКИ + АЛЕРТЫ ──────────────┐   ┌─ B. СВЕРКА С БИРЖЕЙ ───────────────┐
   │ /metrics (Prometheus text)         │   │ periodic REST snapshot             │
   │ recorder + venue-* + journal       │   │   vs локальная книга               │
   │ → правила алертов P0/P1/P2         │   │ расхождение > ε → alert + resync   │
   └────────────────┬───────────────────┘   │ + событие в журнал (аудит)         │
                    │                       └────────────────┬───────────────────┘
                    └───────────┬────────────────────────────┘
                                ▼
                    ┌─ C. СОХРАННОСТЬ ДАННЫХ ───────────────┐
                    │ cold-copy журнала (offsite) + verify  │
                    │ ColdCopyProof (уже есть в journal)    │
                    │ restore-drill: раз в N — проверка,    │
                    │ что копия ЧИТАЕТСЯ, а не просто есть  │
                    └───────────────────────────────────────┘
```

## §4. B — сверка с биржей (то, чего у нас нет и что ловит C1-класс)

> **★ B2 ПРИНЯТ founder ★ 2026-07-18 (§4.3.2) — читать §4/§4.2/§4.3 через эту границу.**
> Рантайм-recon = **best-price per-cycle + seed-gate**. Что recon ОБЕЩАЕТ в рантайме: сверку
> **лучшей цены** (REST-верифицируема — sub-bp skew норма, десинк/C1-стрип best'а → алерт).
> Что recon рантайм НЕ обещает: сверку **near-touch ОБЪЁМА** и глубоких полос — REST-**неверифицируемо**
> (три §8-провала подряд доказали систематический WS(T1)-vs-REST(T2) объёмный bias, §4.3.2). Объёмная
> сверка — **офлайн-трек** (research-dev, необязательный follow-up), БЕЗ рантайм-эмиссии `Sys`. Полная
> книга/объёмы/глубина пишутся в журнал БЕЗ изменений — офлайн-трек работает с ними. §4.3 (оконная
> персистентность) СНЯТА С РАНТАЙМА (сохранена как прото-дизайн для офлайн-трека).

**Инвариант `OPS-I-1` (главный, под B2):** локально реконструированная книга обязана сходиться с
независимым REST-снапшотом биржи **по ЛУЧШЕЙ ЦЕНЕ** (единственная REST-верифицируемая величина в
рантайме). Периодически (по умолчанию раз в 5 мин, per symbol):

1. тянем REST-снапшот (тот же эндпоинт, что для бутстрапа);
2. сравниваем **best bid/ask** С ТОЛЕРАНТНОСТЬЮ к timing-skew (`BEST_SKEW_BPS`, §4.2a): sub-bp shift —
   норма, сверх — десинк/протухшая книга/C1-стрип best'а. **Seed-gate (§4.3.1):** до первого своего
   непустого снапшота recon молчит («моя книга ещё не пришла» ≠ «биржа испортилась»). Near-touch ОБЪЁМ
   считается КАК ГЕЙДЖ `book_divergence_bps` (наблюдаемость, `depth-skip` за REST-reach), но **НЕ
   эмитит `Sys`** (B2: объёмная ветка снята — §4.3.2);
3. **рантайм-выход (ops/engine-dev):** при best-price расхождении → **алерт + принудительный ресинк +
   аудит-`Sys`-событие В ЖУРНАЛ** (CT-RFC-03) + `book_resync_total`++. Журнал — единственный durable-след
   (OPS-I-6: метрики в журнал НЕ пишутся; recon-факт о ДАННЫХ — доменное событие, не метрика). Гейдж
   `book_divergence_bps` обновляется каждый цикл, но алерта не поднимает;
4. **производный офлайн-артефакт (research-dev):** сводка расхождений в `research/data-quality/` рядом с
   gap-статистикой. Под B2 источник — НЕ recon-`Sys` (их по объёму больше нет), а **сама записанная книга
   из журнала**: офлайн-тулинг (`research-cli`) реконструирует книгу и делает объёмную сверку как ТРЕНД/
   диагностику (тот же путь/роль, что пишет gap-статистику M-08). Рантайм туда не пишет; владелец —
   `research-dev` (scope-guard). Это **необязательный follow-up**, НЕ блокирует закрытие дефекта B.

**Порог: два РАЗНЫХ числа, а не одно (исправлено по C-006 M4 — иначе главный инвариант
превращался в пожелание).**

**Под B2 рантайм-гейт — ОДНО число: `BEST_SKEW_BPS` по лучшей цене.** Трёхчисловая машина
(`ε_test`/`ε_prod`/`ε_max`, `ReconThresholds`) сохранена как fail-closed конструктор-инвариант и как
порог для БУДУЩЕГО офлайн-объёмного трека, но в рантайме объёмной эмиссии больше нет, поэтому в
рантайме она не участвует в решении об алерте.

| | Что | Кто задаёт | Статус под B2 |
|---|---|---|---|
| **`BEST_SKEW_BPS`** (рантайм-гейт) | best bid/ask **> `BEST_SKEW_BPS`** per-cycle (§4.2a) | ФИКСИРОВАН в RED-оракуле | Единственный рантайм-триггер `Sys`. Не калибруется: sub-bp skew — норма, сверх — десинк/C1-стрип best'а, immediate |
| **ε_test** (fail-closed гейт) | фикс 50 bps | константа кода | Сохранён для офлайн-трека объёма (§4.3.2) + анти-плацебо `ReconThresholds`. В рантайме объёмной эмиссии нет |
| **ε_prod** (рабочий) | стартово 5 bps | параметр конфига | `ε_prod ≤ ε_max` (конструктор fail-closed). Калибруется офлайн-треком, не рантаймом |
| **ε_max** (fail-closed) | 50 bps | константа кода | `ε_prod` НЕ может быть задан выше: «откалибровали до бесконечности» — не вариант |

«Первые сутки только метрика, без алерта» относилось к калибровке объёмного `ε_prod` — теперь это забота
офлайн-трека. Рантайм-гейт `BEST_SKEW_BPS` действует всегда и с первой минуты (после seed, §4.3.1):
расхождение best bid/ask **сверх `BEST_SKEW_BPS`** — это не мс-skew, это порча/десинк (sub-bp движение
best между WS и REST — норма, §4.2a).

**Зависимость T1 (C-006 M5, названа явно):** «аудит-событие в журнал» требует нового варианта
в `SysEvent` (сейчас там только `Heartbeat`/`ConnUp`/`ConnDown`), а `EventKind` — это T1 →
**обязателен atomic contract-RFC (`CT-RFC-03`) как БЛОКИРУЮЩАЯ подзадача M-09**, а не «возможно
нужен». Альтернатива (записать только в лог/метрику) отвергнута: recon-расхождение — это факт
о ДАННЫХ, и он обязан быть в том же журнале, что и данные, иначе через месяц нельзя ответить
«каким участкам верить».

Почему это важнее, чем кажется: **эвикция C1 стирала лучший bid**, и ни один тест, ни один
healthcheck, ни RSS этого не показывали. Сверка с биржей — единственная проверка, которая
измеряет **правильность данных**, а не живость процесса. Данные — наш единственный актив.

### §4.2 Near-book depth-aware сравнение (redesign 2026-07-17, §8-провал + founder ★)

**Измеренный факт (architect, `api.binance.com/api/v3/depth?limit=5000`, BTCUSDT 2026-07-17):**
REST-снапшот обрезан на 5000 уровней и достаёт лишь **~1.1–1.7% от mid**; локальная книга
реконструирована до **~60%**. Прежние `RECON_BANDS=[1.5%, 3%, 8%]` сравнивали суммы полос ТАМ,
ГДЕ У REFERENCE НЕТ ДАННЫХ → `local≫reference` по построению → §8-флуд `divergence_bps=2436..7754`
на КАЖДОМ цикле здорового рынка. Это АСИММЕТРИЯ ГЛУБИНЫ, а не бакетинг и не timing-skew.

Дополнительно измерено: бакетинг эмита (0.02%-сетка) даёт **0.0 bps** на полосах ≤0.8% и
`best_bid` бакета == сырой best_bid ⇒ сравнивать сырую книгу адаптера НЕ нужно (гипотеза
«сырое-vs-сырое» ОТВЕРГНУТА замером; бакетированный эмит — валидный источник near-book).

**Дизайн recon (founder ★ 2026-07-17 — near-book recon + отдельный трек для 6–60%):**

- **(a) best_price** сравнивается С ТОЛЕРАНТНОСТЬЮ `BEST_SKEW_BPS` (sub-bp skew между WS-книгой и
  REST-моментом — норма; расхождение много bps — реальный десинк/протухшая книга).
- **(b) полосы** — только МЕЛКИЕ, `RECON_BANDS = [0.1%, 0.3%, 0.5%]` (в пределах гарантированного
  REST-reach ~1.1%). Полоса, которую reference НЕ достаёт (`reference.max_reach_pct(side) < band`),
  ПРОПУСКАЕТСЯ: невалидируемо (нет ground truth) ≠ расхождение. Это адаптивно: на тонком/волатильном
  рынке recon сам сузит сравнение до реальной глубины reference, а не будет флудить.
- **(c) пустой/односторонний reference** (REST-halt) при живой local — это расхождение best
  (не «всё сошлось»): невозможность валидировать поднимается, а не глушится.

**Что recon НЕ обещает (честная граница, РАСШИРЕНА B2 2026-07-18):** глубокие полосы **6–60% OBI через
REST НЕ верифицируемы** — независимого ground truth на этой глубине нет (REST обрезан, платформенный
референс = §5.1 магнитудная загадка). **B2 добавил: near-touch ОБЪЁМ (0.1–0.5% полосы) ТОЖЕ
REST-неверифицируем в рантайме** — три §8-провала подряд доказали систематический WS(T1)-vs-REST(T2)
объёмный bias (§4.3.2), включая нетронутый BinanceFutures. Фантом дальних полос (**TD-016**: bid'ы,
из-под которых цена ушла, не обнуляются) и объёмная сверка near-touch — **ОФЛАЙН-трек** (research-dev,
корректность эвикции within-band + возможный platform-reference над записанной книгой), НЕ рантайм.
Рантайм-recon ловит класс **C1** через **best bid** (эвикция стирала именно near-touch best — REST-
верифицируемо), ради чего слой и строится; объёмные проявления C1, не двигающие best, — офлайн.

RED-оракул near-book семантики — `crates/ops/tests/red_recon_live.rs` (sacred): моделирует LIVE-режим
(глубокая local vs обрезанный shallow reference), НЕ книгу-с-собой; падает и против no-skip-impl
(§8-флуд), и против over-skip-impl (пропустил near-book порчу), и против «пустой ref → тишина».

**Дизайн: дискриминатор churn↔порча — НЕ магнитуда, а ПЕРСИСТЕНТНОСТЬ ЗНАКА.** Доказано сменой знака:
churn mean-reverting (оконное знаковое среднее → ~0), порча персистентна (C1-стрип best'а держит знак
цены; TD-016 near-touch фантом = систематический `local>ref` одного знака). Три пути recon:

- **(a) best bid/ask** — толерантно к `BEST_SKEW_BPS` (§4.2a), **PER-CYCLE алерт, immediate** (цена
  стабильна к sub-bp; C1 стирал именно best bid → ловится ценой мгновенно). БЕЗ изменений.
- **(b) объём near-touch** — НЕ per-cycle порог, а **ОКОННОЕ ЗНАКОВОЕ СРЕДНЕЕ** по (полосе,стороне):
  скользящее окно `RECON_WINDOW` циклов; алерт, только когда `|среднее| ≥` порога через ЗАПОЛНЕННОЕ
  окно. Churn (знак гуляет) усредняется в ~0 → **ТИШИНА**; персистентный односторонний сдвиг (порча)
  держит знак → **АЛЕРТ**. Магнитуда per-cycle у churn и порчи МОЖЕТ СОВПАДАТЬ — различает ТОЛЬКО
  персистентность.
- **(c) `book_divergence_bps` per-cycle → ДЕМОТИРОВАН в метрику-гейдж** (§3, полезный наблюдательный
  сигнал), НЕ триггер эмиссии `Sys`. Эмиссию по объёму принимает окно (b).

**Recon становится STATEFUL.** Окно живёт в оркестраторе per (venue,symbol,band,side) — рантайм-
состояние рядом с `ReconBudget`, как и `ReconBudget`. Журнал НЕ трогается (`JR-I-1`: пишет только
recorder; `OPS-I-6`: `crates/ops` не зависит от `journal`). **Детерминизм ЭМИССИЙ сохранён**: окно —
чистое рантайм-состояние (без wall-clock/rand); одинаковая последовательность наблюдений → одинаковая
последовательность вердиктов (per-cycle recon-результаты не журналируются; в журнал идёт только факт
`ReconDivergence`). Интерфейс: `reconcile(local,ref)->ReconOutcome` (per-cycle: best + гейдж) остаётся
чистым; `ReconDetector::observe(local,ref)->ReconVerdict` (stateful) принимает решение об эмиссии.

**Порог окна — та же трёхчисловая fail-closed машина, что и §4.** `ε_test` (окно, фикс 50, гейт: не
калибруется — персистентная порча с `|mean| ≥ 50` алертит всегда), `ε_prod` (окно, калибруется),
`ε_max=50` (потолок). **ПЕРВИЧНЫЙ рычаг подавления churn — ДЛИНА ОКНА `RECON_WINDOW` `K`, а НЕ подъём
порога** (fail-closed: порог до бесконечности запрещён — «если даже длинное окно держит `|mean| ≥ 50`,
это уже НЕ churn, а персистентный сдвиг = порча, и он ОБЯЗАН алертить»). `K` калибруется по живому
churn-остатку (`[verify-at-impl]` + §8): длиннее окно → сильнее гасится churn; дефолт 12 циклов (при
cadence 5 мин — 1 час). **Задержка:** best-порча (C1) — immediate; персистентная ОБЪЁМНАЯ порча (не
двигающая best) — до `K` циклов. Это осознанный размен: единственная альтернатива per-cycle тишине —
флуд (churn до 2007 bps). **§8-тишина «recon молчит на здоровой книге» достижима ТОЛЬКО оконно**;
per-cycle тишина по объёму невозможна физически (принято founder ★ 2026-07-17).

**Открытый вопрос калибровки (для прод-хардненинга).** Знаковое среднее над фиксированным порогом —
минимальный дискриминатор. Более робастный к остаточной дисперсии churn — знаковое среднее, гейтованное
СОГЛАСОВАННОСТЬЮ ЗНАКА (доля одноимённых циклов в окне) или t-подобным отношением `mean/(std/√K)`; это
позволяет короче окно при той же ложно-положительной ставке. RED-оракул пиннит СЕМАНТИКУ (churn mean→0
→ тишина; персистентный сдвиг → алерт) и допускает оба impl; выбор конкретной статистики + `K` —
калибровка на живом churn (`ε_prod`-аналог) + подтверждение §8 на здоровом прогоне.

**RED-оракул (историч.): оконная семантика жила в `crates/ops/tests/red_recon_window.rs`** (churn→тишина,
персистент→алерт, анти-плацебо в обе стороны). **Под B2 (§4.3.2) объёмные оконные оракулы (1–7) СНЯТЫ**
из runtime-sacred; файл переименован в `red_recon_runtime.rs` и держит рантайм-контракт B2 (best-only +
seed-gate + «персистентный объём МОЛЧИТ в рантайме»). Оконная семантика churn↔порча переезжает в
офлайн-спеку research-dev как прото-дизайн (требует переспеки на прод-фикстурах, см. баннер выше).

### §4.3.1 Seed-gate — пустая СВОЯ книга ≠ порча биржи (дефект A, третий §8-провал 2026-07-17)

**Прод-факт (reviewer, §8 eyes-on, `b1adec0`):** на КАЖДЫЙ рестарт recorder'а recon писал **4 стартовых**
`ReconDivergence {best_diverged=true, div_bps=10000, Resynced}` (venue×symbol). Причина — гонка seed'а:
recon-fetcher тянет REST-reference НЕМЕДЛЕННО на старте, а orchestrator берёт local как
`books.get((venue,symbol)).unwrap_or(OrderBook::new())` → **пустую** книгу ДО первого `L2Snapshot`
books-feeder'а. `reconcile(пустая, полный REST)` → best-сторона `Some` только у reference → best
расходится → эмит.

**Инвариант:** «моя книга ещё не пришла» (не seeded) — это НЕ «биржа испортилась». Recon НЕ смеет
эмитить, пока не получил ≥1 свой снапшот. **Дизайн — SELF-SEEDING `ReconDetector`:** держит
`seeded: bool` (per venue/symbol, как окно), ставит `true` на ПЕРВОЙ НЕПУСТОЙ local (`best_bid` или
`best_ask` есть); до seed `observe` возвращает no-alert и НЕ кормит окно (не отравляет пустышкой).
**Пост-seed** внезапно пустая local — это РЕАЛЬНАЯ потеря/порча книги → эмит (best-путь) сохраняется.
Детерминизм эмиссий сохранён (seeded — рантайм-состояние по последовательности наблюдений).
RED-оракулы (sacred): `empty_local_before_first_seed_does_not_emit` (падает против текущего impl),
`empty_local_after_seed_is_corruption_and_emits` (анти-плацебо: seed-gate не over-suppress'ит пост-seed
порчу). Seed-gate ОРТОГОНАЛЕН развилке §4.3.2 — нужен при любом её исходе.

### §4.3.2 Объёмный runtime-recon: ТРИ §8-провала подряд → **B2 ПРИНЯТ founder ★ 2026-07-18** (дефект B)

**Прод-факт (reviewer, `b1adec0`):** помимо стартовых (A), recon писал **12+ ОКОННЫХ**

**Диагноз (architect).** Это ТРЕТИЙ §8-провал ОДНОГО класса (near-touch volume): depth-asymmetry (§4.2)
→ per-cycle volume → windowed volume (§4.3). Корень глубже калибровки: **оконное усреднение гасит
ДИСПЕРСИЮ (zero-mean шум), но НЕ СИСТЕМАТИЧЕСКИЙ сдвиг.** Знаковое среднee 1129 bps за K=12 означает,
что распределение НЕ zero-mean — есть bias. Источник bias: сравниваются РАЗНЫЕ представления одной
истины — local (WS-diff книга, **бакетированная**, момент T1) vs reference (**сырой** REST-снапшот,
момент T2). Best-ЦЕНА совпадает (`best_diverged=false`), а СУММЫ near-touch ОБЪЁМА систематически

СИНТЕТИЧЕСКИЙ zero-mean churn (±1500 идеально балансируется за K) — потому и был GREEN, а прод дал
несбалансированный остаток. Классический green-unit/live-flood, этажом глубже.

### §4.1 Rate-limit и backoff — обязательный гейт recon'а (C-006 M6)

TD-013 родился ровно на этом пути: REST-ресинк без backoff дал **133 × HTTP 418 за 25 с**
и IP-бан, общий со спот-сбором. Recon добавляет НОВЫЙ REST-трафик — значит он обязан нести
защиту не как «здравый смысл», а как проверяемый инвариант (`OPS-I-9`):

- плановый путь (1 запрос / 5 мин / символ) — безопасен и не обсуждается;
- **опасен путь ОШИБКИ**: ресинк по расхождению → снова расхождение → снова ресинк;
- требуется: honor `Retry-After`/418/429 (cooldown), экспоненциальный backoff с cap, **общий
  rate-budget на venue** (recon + бутстрап + ресинки книги считаются ВМЕСТЕ), запрет
  одновременных ресинк-штормов по символам;
- RED-оракул: инъецированный поток REST-ошибок НЕ вызывает hot-loop; частота запросов не
  превышает бюджет; при 418 запросы прекращаются на cooldown.

### §5.1. Runbook: откат ПОСЛЕ schema-forward деплоя журнала (M-18 L2Delta и любой новый вариант)

Источник: CT-RFC-04 §10 + risk-critic C-018. **Проблема:** новый вариант `EventKind`/`MdPayload`
(напр. `MdPayload::L2Delta`, дискриминант 6) в append-only журнале на ОБЩЕМ томе. Бинарь СТАРШЕ
деплоя его не декодит: hot-путь `scan_tail_for_last_seq` пропускает variant-фрейм → `next_seq`
недосчитывается → **тихий SEQ REUSE**; offline `read_all` → hard `Err`. `deploy.yml`
healthcheck→revert **НЕ применять вслепую** к такому журналу.

**Структурная гарантия (RED `red_l2delta_rollback_boundary`):** новый бинарь несёт новый git-sha в
`SegmentHeader.provenance` → `decide_open_segment` открывает НОВЫЙ сегмент. Новый вариант никогда не
дописывается в старый сегмент; post-деплой сегменты идентифицируемы по provenance/`created_wall_ms`.

**Процедура (оператор, при откате на бинарь старше schema-forward деплоя):**
1. `stop` recorder (контейнер down).
2. Выявить post-деплой сегменты: `SegmentHeader.provenance` git-sha == новый ИЛИ `created_wall_ms
   ≥ момент деплоя` (заголовок — первый фрейм `segment-NNNNNNNN.jrnl`).
3. Переместить их в **quarantine ВНЕ journal-тома** (не удалять — там незаменимые данные).
4. Запустить старый бинарь: он видит только ≤деплойные сегменты, `scan_tail` декодит чисто,
   `next_seq` верный, пишет в свежий сегмент. **Без шага 3 — тихая порча `seq`.**
5. При возврате вперёд (re-forward на новый бинарь) — вернуть quarantined сегменты на место;
   `seq` непрерывен (границы сегментов сшиваются по `first_seq`).

**Правило:** НИКОГДА не запускать бинарь старше schema-forward деплоя против журнала, чей
активный/хвостовой сегмент несёт неизвестный ему вариант. Авто-rollback `deploy.yml` для такого
деплоя — не «тихая страховка»; reviewer в §8 подтверждает, что первое новое-событие ушло в НОВЫЙ
сегмент. **Открытый долг:** startup-guard recorder'а, ГРОМКО падающий, если активный сегмент несёт
недекодируемые события (schema-version-aware старт) — общий фикс, отдельный milestone.
