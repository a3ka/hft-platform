## §1. Почему этот слой обязан появиться раньше торговли

Факт, который стоит признать прямо: **за пять инцидентов подряд ни один не был пойман нашей
автоматикой.**

| Инцидент | Что было | Кто поймал |
|---|---|---|
| TD-011 | `open()` читал 2.65 GiB в RAM → recorder не писал | человек, ssh |
| TD-013 | 133 × HTTP 418 за 25 с (IP-бан Binance) | человек, ssh |
| TD-014 | 0 Funding-событий в журнале при «успешном» деплое | человек, ssh |
| TD-016 | лик памяти +6.5 MiB/час | человек, ssh |
| C1 (M-08) | эвикция стирала живые уровни книги → порча данных | человек, code-review |

Во всех случаях: контейнер `healthy`, heartbeat свежий, CI зелёный, Deploy success. **Наш
healthcheck проверяет, что процесс жив, а не что он делает то, что должен.** Пока мы возим
только данные, цена — испорченный датасет. Как только появится `oms`, та же слепота будет
стоить деньги.

**Тезис слоя:** система обязана сама сообщать о тихой деградации. «Глаза оператора» (гейт §8) —
последний рубеж, а не первый.

## §2. Три подсистемы

```
   ┌─ A. МЕТРИКИ + АЛЕРТЫ ──────────────┐   ┌─ B. СВЕРКА С БИРЖЕЙ ───────────────┐
   │ /metrics (Prometheus text)         │   │ periodic REST snapshot             │
   │ recorder + venue-* + journal       │   │   vs локальная книга               │
   │ → правила алертов P0/P1/P2         │   │ расхождение > ε → alert + resync   │
   └────────────────┬───────────────────┘   │ + событие в журнал (аудит)         │
                    │                       └────────────────┬───────────────────┘
                    └───────────┬────────────────────────────┘
                                ▼
                    ┌─ C. СОХРАННОСТЬ ДАННЫХ ───────────────┐
                    │ cold-copy журнала (offsite) + verify  │
                    │ ColdCopyProof (уже есть в journal)    │
                    │ restore-drill: раз в N — проверка,    │
                    │ что копия ЧИТАЕТСЯ, а не просто есть  │
                    └───────────────────────────────────────┘
```

## §3. A — метрики (что именно экспортируем)

Формат: Prometheus text на `/metrics` (recorder-процесс; отдельный порт, без внешнего доступа).
Никаких новых зависимостей в горячем пути: счётчики — атомарные, экспорт — по запросу.

| Метрика | Тип | Зачем (какой инцидент ловит) |
|---|---|---|
| `recorder_rss_anon_bytes` | gauge | TD-016 (рост кучи) — тренд. **ИСТОЧНИК ФИКСИРОВАН: `RssAnon` из `/proc/<pid>/status`** (НЕ `docker stats` и НЕ cgroup `memory.current` — они включают page cache файла журнала ⇒ ложный «лик», TD-021). Мерит анонимную кучу процесса, а НЕ page cache и НЕ рост книги (это `book_levels`) |
| `journal_bytes_written_total` | counter | «пишем ли вообще» (TD-011: heartbeat был, данных не было) |
| `journal_seq_current` | gauge | монотонность/остановка потока |
| `journal_seq_gaps_total` | counter | пропуски в `seq` (дырка в потоке); база P1-правила «gap-доля за сутки» (ratio считается в alert-правиле) |
| `journal_segment_index` | gauge | ротация работает |
| `journal_disk_free_bytes` | gauge | fail-closed по диску (E4) — предупреждать ДО стопа |
| `journal_write_errors_total` | counter | RK-I-5 (отказ записи = halt) |
| `md_events_total{venue,symbol,kind}` | counter | TD-014: 0 Funding — видно за минуту, а не за деплой-цикл |
| `md_event_age_ms{venue}` | gauge | тишина в потоке (гэп «в реальном времени») |
| `venue_ws_reconnects_total{venue}` | counter | стабильность фида |
| `venue_http_status_total{venue,code}` | counter | TD-013: 418/429 видно СРАЗУ |
| `book_levels{venue,symbol,side}` | gauge | TD-016: рост уровней ⇒ лик в книге; стабильность ⇒ лик в другом месте |

## §4. B — сверка с биржей (то, чего у нас нет и что ловит C1-класс)

**Инвариант `OPS-I-1` (главный):** локально реконструированная книга обязана сходиться с
независимым REST-снапшотом биржи **в пределах глубины, которую этот снапшот покрывает**
(near-book). Периодически (по умолчанию раз в 5 мин, per symbol):

1. тянем REST-снапшот (тот же эндпоинт, что для бутстрапа);
2. сравниваем с локальной книгой **на общем префиксе глубины** (см. §4.2): best bid/ask
   С ТОЛЕРАНТНОСТЬЮ к timing-skew + суммы МЕЛКИХ полос (`RECON_BANDS` ≤ REST-reach);
   полосы за пределами reference-глубины ПРОПУСКАЮТСЯ (невалидируемо ≠ расхождение);
3. **рантайм-выход (ops/engine-dev):** живая метрика `book_divergence_bps` + счётчик
   `book_resync_total`; при превышении порога → **алерт + принудительный ресинк + аудит-`Sys`-
   событие В ЖУРНАЛ** (CT-RFC-03). Журнал — единственный durable-след (OPS-I-6: метрики в журнал
   НЕ пишутся; recon-факт о ДАННЫХ — это доменное событие, не метрика);
4. **производный офлайн-артефакт (research-dev):** сводка расхождений в `research/data-quality/`
   рядом с gap-статистикой — это АГРЕГАЦИЯ recon-`Sys`-событий из журнала офлайн-тулингом
   (`research-cli`), ТА ЖЕ роль и путь, что уже пишут gap-статистику (M-08). Рантайм туда не
   пишет; владелец пути — `research-dev` (scope-guard).

**Порог: два РАЗНЫХ числа, а не одно (исправлено по C-006 M4 — иначе главный инвариант
превращался в пожелание).**

| | Что | Кто задаёт | Статус |
|---|---|---|---|
| **ε_test** (гейт) | расхождение best bid/ask **> `BEST_SKEW_BPS`** (timing-skew толерантен, §4.2a) ИЛИ ≥ 50 bps по суммам МЕЛКИХ near-book полос (§4.2b) | ФИКСИРОВАН в RED-оракуле | Не калибруется. Инъецированная порча near-book (удалить/исказить within-reach уровень) ОБЯЗАНА поднять алерт — это acceptance M-09 |
| **ε_prod** (рабочий) | стартово 5 bps по суммам полос | параметр конфига | Калибруется по первым суткам живого распределения |
| **ε_max** (fail-closed) | 50 bps | константа кода | `ε_prod` НЕ может быть задан выше: «откалибровали до бесконечности» — не вариант |

«Первые сутки только метрика, без алерта» относится ТОЛЬКО к `ε_prod`. `ε_test` действует
всегда и с первой минуты: расхождение best bid/ask **сверх `BEST_SKEW_BPS`** — это не мс-skew,
это порча/десинк (sub-bp движение best между WS и REST — норма, §4.2a).

**Зависимость T1 (C-006 M5, названа явно):** «аудит-событие в журнал» требует нового варианта
в `SysEvent` (сейчас там только `Heartbeat`/`ConnUp`/`ConnDown`), а `EventKind` — это T1 →
**обязателен atomic contract-RFC (`CT-RFC-03`) как БЛОКИРУЮЩАЯ подзадача M-09**, а не «возможно
нужен». Альтернатива (записать только в лог/метрику) отвергнута: recon-расхождение — это факт
о ДАННЫХ, и он обязан быть в том же журнале, что и данные, иначе через месяц нельзя ответить
«каким участкам верить».

Почему это важнее, чем кажется: **эвикция C1 стирала лучший bid**, и ни один тест, ни один
healthcheck, ни RSS этого не показывали. Сверка с биржей — единственная проверка, которая
измеряет **правильность данных**, а не живость процесса. Данные — наш единственный актив.

### §4.2 Near-book depth-aware сравнение (redesign 2026-07-17, §8-провал + founder ★)

**Измеренный факт (architect, `api.binance.com/api/v3/depth?limit=5000`, BTCUSDT 2026-07-17):**
REST-снапшот обрезан на 5000 уровней и достаёт лишь **~1.1–1.7% от mid**; локальная книга
реконструирована до **~60%**. Прежние `RECON_BANDS=[1.5%, 3%, 8%]` сравнивали суммы полос ТАМ,
ГДЕ У REFERENCE НЕТ ДАННЫХ → `local≫reference` по построению → §8-флуд `divergence_bps=2436..7754`
на КАЖДОМ цикле здорового рынка. Это АСИММЕТРИЯ ГЛУБИНЫ, а не бакетинг и не timing-skew.

Дополнительно измерено: бакетинг эмита (0.02%-сетка) даёт **0.0 bps** на полосах ≤0.8% и
`best_bid` бакета == сырой best_bid ⇒ сравнивать сырую книгу адаптера НЕ нужно (гипотеза
«сырое-vs-сырое» ОТВЕРГНУТА замером; бакетированный эмит — валидный источник near-book).

**Дизайн recon (founder ★ 2026-07-17 — near-book recon + отдельный трек для 6–60%):**

- **(a) best_price** сравнивается С ТОЛЕРАНТНОСТЬЮ `BEST_SKEW_BPS` (sub-bp skew между WS-книгой и
  REST-моментом — норма; расхождение много bps — реальный десинк/протухшая книга).
- **(b) полосы** — только МЕЛКИЕ, `RECON_BANDS = [0.1%, 0.3%, 0.5%]` (в пределах гарантированного
  REST-reach ~1.1%). Полоса, которую reference НЕ достаёт (`reference.max_reach_pct(side) < band`),
  ПРОПУСКАЕТСЯ: невалидируемо (нет ground truth) ≠ расхождение. Это адаптивно: на тонком/волатильном
  рынке recon сам сузит сравнение до реальной глубины reference, а не будет флудить.
- **(c) пустой/односторонний reference** (REST-halt) при живой local — это расхождение best
  (не «всё сошлось»): невозможность валидировать поднимается, а не глушится.

**Что recon НЕ обещает (честная граница):** глубокие полосы **6–60% OBI через REST НЕ
верифицируемы** — независимого ground truth на этой глубине нет (REST обрезан, платформенный
референс = §5.1 магнитудная загадка). Фантом дальних полос (**TD-016**: bid'ы, из-под которых цена
ушла, не обнуляются) — **ОТДЕЛЬНЫЙ трек** (корректность эвикции within-band + возможный
platform-reference), НЕ этот milestone. Near-book recon ловит именно класс **C1** (эвикция стирала
**best bid** — near-touch), ради которого слой и строится.

RED-оракул near-book семантики — `crates/ops/tests/red_recon_live.rs` (sacred): моделирует LIVE-режим
(глубокая local vs обрезанный shallow reference), НЕ книгу-с-собой; падает и против no-skip-impl
(§8-флуд), и против over-skip-impl (пропустил near-book порчу), и против «пустой ref → тишина».

### §4.1 Rate-limit и backoff — обязательный гейт recon'а (C-006 M6)

TD-013 родился ровно на этом пути: REST-ресинк без backoff дал **133 × HTTP 418 за 25 с**
и IP-бан, общий со спот-сбором. Recon добавляет НОВЫЙ REST-трафик — значит он обязан нести
защиту не как «здравый смысл», а как проверяемый инвариант (`OPS-I-9`):

- плановый путь (1 запрос / 5 мин / символ) — безопасен и не обсуждается;
- **опасен путь ОШИБКИ**: ресинк по расхождению → снова расхождение → снова ресинк;
- требуется: honor `Retry-After`/418/429 (cooldown), экспоненциальный backoff с cap, **общий
  rate-budget на venue** (recon + бутстрап + ресинки книги считаются ВМЕСТЕ), запрет
  одновременных ресинк-штормов по символам;
- RED-оракул: инъецированный поток REST-ошибок НЕ вызывает hot-loop; частота запросов не
  превышает бюджет; при 418 запросы прекращаются на cooldown.

## §5. C — сохранность (сейчас: одна копия 15 GB на одном диске)

**Инвариант `OPS-I-2`:** боевой журнал существует минимум в ДВУХ местах. Сегодня — в одном.
Потеря диска VPS = потеря всего проекта; ретеншен с `ColdCopyProof` написан (M-08), но ни разу
не запускался.

- Холодная копия: Hetzner Storage Box (или S3-совместимое), выгрузка закрытых сегментов;
  удаление горячей копии — только через `ColdCopyProof` (типовой барьер уже есть).
- **`OPS-I-3` restore-drill:** периодически (раз в месяц) холодная копия **скачивается и
  читается** (`journal::stream` на ней отрабатывает, `seq` непрерывен). «Бэкап, который не
  восстанавливали, — это не бэкап».
- Legacy-сегмент (15.0 GB, заморожен после M-08) выгружается ПЕРВЫМ.

## §7. Алерт-таксономия (перенос из hft-core-rs, §9 DESIGN — «лучшее, что там есть»)

- **P0 (немедленно, будит человека):** запись в журнал остановилась; диск < порога; recon-
  расхождение > ε; (с P3) риск-гейт недоступен; kill-switch не отвечает.
- **P1 (в течение часа):** тишина в потоке > 5 мин; **анонимная куча** (`RssAnon`) тренд > порога/час
  (НЕ cgroup/docker — TD-021); 418/429 > N/мин; частые ресинки; gap-доля за сутки > 1%.
- **P2 (в дайджест):** рост числа уровней книги; деградация cadence эмиссии; накопление TD.

P0/P1-правило §7 имеет строку §7.1 и ссылается на СУЩЕСТВУЮЩУЮ метрику §3. P2 (дайджест) — вне
строгого паритета (наблюдательный слой), но метрики его правил (`book_levels`, cadence) тоже в §3.
Эта таблица — ЕДИНСТВЕННАЯ каноническая поверхность паритета: любое P0/P1-правило живёт здесь
строкой, иначе оно вне проверки (ровно дыра, которую закрыл C-007 C1).
