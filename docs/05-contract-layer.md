# 05 — Контрактный слой (governed, аналог EINHARD `contracts/`)

STATUS: DESIGN v1 (2026-07-10, Fable). Источник правды для всех форм, пересекающих
границу движок↔квант-деск. Меняется ТОЛЬКО через contract-RFC (§4). Аналог EINHARD:
JSON Schema — единый источник правды, из него деривируются биндинги; правки — атомарным
RFC-PR; ревьюер-гейт блокирует не-RFC правки.

---

## §1. Зачем отдельный слой

Движок (Rust) и квант-деск (LLM-агенты + Python-research-тулинг) — разные исполнители,
разные языки, разные жизненные циклы. Всё, что течёт между ними, должно иметь ОДНУ
типизированную форму, иначе повторяется болезнь hft-core-rs (три несовместимых wire-формата).
Контрактный слой — это набор версионируемых схем + сгенерированные биндинги + дисциплина
их изменения.

## §2. Что является контрактом (T1) — единый источник правды

`contracts/` (отдельный крейт + схемы). Rust-типы с `serde` + `schemars` — **канонический
источник**; из них генерируется JSON Schema 2020-12; Python-research-тулинг валидирует
свои чтения против той же схемы. Схема-в-репозитории — источник правды пост-мёрж.

| T1-контракт | Что | Кто продюсер / консюмер |
|---|---|---|
| `Event` / `EventKind` | журнальный wire-формат (§01 §3) | движок пишет; движок+research читают |
| `SignalRegistry` entry (`signals.json`) | что движок исполняет (граница B) | деск пишет через подпись; движок читает |
| `Ctl(ParamChange)` | подписанное изменение весов/лимитов/параметров (граница C) | очередь решений пишет; движок применяет |
| `SignalSpec` card | формула+параметры+диапазоны+издержки сигнала | signal-engineer пишет; движок+critic читают |
| `ValidationReport` (`metrics.json`) | выход research-cli (PnL/Sharpe/deflated/decay/…) | research-cli пишет; critic+founder читают |
| `TrialsLedger` entry | глобальный счётчик проб (анти-оверфит) | backtest-runner append; deflated-Sharpe читает |
| `Decision` (`D-NNN`) | подписанное решение founder'а о промоушене | founder подписывает; движок+реестр консюмят |

Всё остальное — **T2** (модульно-ограниченные: `Order`, `RiskApproved`, `Book`, `Forecast`,
`TargetQuotes`, лимит-профили — владеет крейт) и **T3** (внутренние структуры). T2/T3 меняются
свободно внутри крейта-владельца, без RFC.

## §3. Кодировки (locked — не переоткрываются без RFC)

- Деньги/цены: fixed-point `i64`/`u64` ×1e8. Никогда f64 в деньгах.
- Время: `ts_mono_ns` (порядок) + `ts_wall_ms` int64 UTC (отчёты).
- Бинарь журнала: postcard + crc32 на фрейм. ОДИН формат.
- Идентификаторы: `signal_id`, `client_order_id = hash(strategy_id, seq, nonce)` (детерминизм).
- Хэши: sha256 для `code_hash`, `state_hash`.

## §4. Дисциплина изменения (contract-RFC — сердце governance)

Любое изменение T1-формы = **атомарный contract-RFC** (как EINHARD §5b), содержащий В ОДНОМ
PR: (1) изменение Rust-типа в `contracts/`; (2) перегенерированную JSON Schema; (3) bump версии
(`schema_version`); (4) миграционную заметку (как читать старый журнал/реестр); (5) фикстуры
valid/invalid; (6) обновление CHANGELOG; (7) ≥1 тест, ссылающийся на новую форму.

- **Аддитивное** (новое опциональное поле, новый вариант enum в конце) — minor bump.
- **Ломающее** (удаление/переименование поля, смена типа, порядок enum) — major bump +
  миграция старых журналов (журнал бессмертен: старые записи должны читаться навсегда,
  иначе рушится `replay==реальность`).
- Rationale-only PR (текст без схемы) и schema-only PR (без rationale) — не ревьюятся.

**Ревьюер-гейт (Block-C, аналог EINHARD Block B5):** PR, трогающий `contracts/` вне
contract-RFC → авто-REJECT. Крейты движка/деска НЕ переопределяют T1-формы локально
(grep-канарейка: `EventKind` определён ровно в одном месте).

## §5. Биндинги и кросс-язык

- **Rust — канон** (движок): типы напрямую.
- **Python — консюмер** (research-тулинг, ноутбуки анализа): читает журнал/отчёты, валидируя
  против сгенерированной JSON Schema. Python НЕ пишет T1 в рантайм — только читает историю
  и продюсит `ValidationReport`/`SignalSpec` (текстовые T1, идущие через границы A/B).
- Гейт паритета: `verify_contracts.sh` — Rust-типы ↔ JSON Schema ↔ фикстуры согласованы;
  роундтрип-тест сериализации (как EINHARD tri-binding parity, но здесь 2 языка).

## §6. Инварианты контрактного слоя (RED)

| ID | Инвариант |
|---|---|
| CT-I-1 | `EventKind` определён ровно в одном крейте (`contracts/`); grep-канарейка |
| CT-I-2 | Правка T1 вне contract-RFC → reject (ревьюер Block-C) |
| CT-I-3 | Старый журнал читается новым кодом (миграция обязательна; роундтрип-фикстуры старых версий) |
| CT-I-4 | JSON Schema сгенерирована из Rust-типов и согласована (verify-гейт), не написана руками |
| CT-I-5 | Python-тулинг валидирует чтения против той же схемы (общие фикстуры) |
| CT-I-6 | `schema_version` в каждом журнальном сегменте и в `signals.json` |

## §7. Связь с движком и деском

- Движок зависит от `contracts` (крейт) — читает/пишет T1.
- Квант-деск читает журнал и схемы; пишет T1 только через границы A/B/C (03) — т.е.
  контрактный слой И есть материализация этих трёх границ.
- `research-cli` (мост, 03) — единственный компонент, который держит и Rust-типы (для
  быстрого чтения журнала), и продюсит T1-отчёты, которые читают LLM-агенты.
