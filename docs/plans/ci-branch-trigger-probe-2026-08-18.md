# Почему `push.branches: ['**']` в `ci.yml` — нерабочее предписание (замер 2026-08-18)

**Происхождение.** Разведка read-only агентом по заданию architect'а перед исполнением
предписаний `A-010` §F / `docs/plans/fable-e3-f2-2026-08-18.md` §2.3. Оба независимых
Fable-агента предлагали правку `on.push.branches` с `[main]` на `['**']` как «одну строку,
не требующую воли автора». Разведка проверила исполнением — **правка даёт детерминированный
красный набор**, а не вероятностный.

**Почему файл существует.** Отчёт вернулся в переписку (агент упал на API-ошибке, результат
пришёл в уведомлении) и нигде не был закреплён. Норма `gates.md` §4: то, что живёт только в
переписке, аудит-трейлом не является.

---

## 1. Что именно ломается

| # | сценарий | механика |
|---|---|---|
| 1 | **первый push любой новой ветки** | `github.event.before` = zero-SHA → одновременно падают **5 джобов**: `protected-artifacts`, `docs-freeze`, `contracts`, `artifact-ids`, `gate-meta`. Все четыре скрипта и inline-шаг несут один fail-closed каскад: `case "${raw}" in *[!0]*) : ;; *) die "база = zero-SHA…"` |
| 2 | **каждый force-push** (rebase/amend — рутина агентов) | `git merge-base --is-ancestor "${raw}" HEAD` не проходит → те же 5 джобов |
| 3 | **процедура merge `gates.md` §8** | push в ветку с открытым PR даёт два прогона на одном SHA → `gh pr checks --watch` вернёт ненулевой код → `gh pr merge` не выполнится **никогда** |

**Это не дефект барьеров.** Их инвариант «база = состояние до события» осмыслен только для
входа в `main`; на ветке они честно говорят «гарантировать не могу». Чинить надо не барьеры.

## 2. Эмпирика — тропа нехоженая

```
130 push-прогонов  — ВСЕ по `main`
 64 PR-прогона     — с веток
  0 настоящих push-прогонов на ветке
    (единственный кандидат 32071359618 — startup_failure с нулём джобов)
```

`branches: [main]` стоит **с первого коммита репозитория `25fe2c8`** и не менялся ни разу.
`R-051` OBS-1 явно рассмотрел это слепое пятно и оставил как `COGNITIVE-ONLY`.

## 3. `deploy.yml` не задет

`push` жёстко `[main]` + фильтр путей (`crates/**`, `Cargo.*`, `Dockerfile`,
`docker-compose.yml`, `.github/workflows/deploy.yml`); `workflow_run` фильтруется по ветке
породившего прогона. Прод не шелохнётся ни при каком варианте правки.

Отдельно проверено: `scripts/check_deploy_gate.py` (барьер запретного списка Р-4) читает
**только** `.github/workflows/deploy.yml` — новый workflow под его надзор не попадает.

## 4. Рабочая конструкция вместо предписанной

Отдельный workflow, не трогающий `ci.yml`:

```yaml
name: Branch build
on:
  push:
    branches-ignore: [main]
concurrency:
  group: branch-build-${{ github.ref }}
  cancel-in-progress: true
jobs:
  build-test:          # дословно состав `build-test` из ci.yml:
    # cargo fmt --all -- --check
    # cargo clippy --all-targets --all-features -- -D warnings
    # cargo test --all
```

Почему это работает там, где предписание — нет:

- **не читает базу события вовсе** ⇒ zero-SHA и force-push безразличны (снимает 1 и 2);
- **не входит в агрегат `All checks passed`** (`needs` живёт в `ci.yml`) ⇒ merge не блокирует,
  процедура §8 цела (снимает 3);
- `concurrency` + `cancel-in-progress` гасит шторм при серии push'ей;
- воли автора не требуется — событие рождает GitHub.

## 5. Чего это НЕ даёт — названо явно

Push-триггер строит **ветку**, а не дерево слияния. Отставание от `main` он не покажет —
за это отвечает `bash scripts/verify_design_claims.sh --merge-preview origin/main`
(`gates.md` §8; `strict: false` назван там же как принятый предел).

Следствие для практики draft-PR (`A-010` §F-1): она остаётся полезной, но перестаёт быть
несущей — несущую функцию (прогон) забирает триггер. Честное место — строка практики с тегом
`COGNITIVE-ONLY`, без скрипта под неё.
