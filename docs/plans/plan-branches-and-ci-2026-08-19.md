# План: собираемость веток в CI + разбор 24 невлитых веток + защита от рецидива

## Context

**Проблема, замеренная 18.08.** В `origin` 24 ветки помимо `main`. Один предмет живёт в
нескольких копиях: M-66 — четыре ветки (все отстают на 163 коммита), M-65 — три, M-67 — две,
M-68 — две, M-60 — две. Старьё: `feat/M-10-rebased` (27 дней, −1184), `salvage/M-59-*` (−421),
`feat/M-60-mechanisms` (−417).

**Корень назван двумя независимыми Fable-агентами и подтверждён замером:** `ci.yml`
триггерится только на `pull_request` и `push` в `main`. Ветка, на которой предмет живёт все
круги гейта, **не собирается ни разу**. Эмпирика: 130 push-прогонов — все по `main`,
0 настоящих прогонов на ветках; `branches: [main]` стоит с первого коммита `25fe2c8`.

Следствия, стоившие проекту кругов:
- M-69 прошёл ДВА круга критика, ни разу не собравшись; открытие draft-PR за 9 минут дало три
  дефекта, два из которых не нашли оба критика (коллизия `C-100`, врущая таблица `DESIGN` §22);
- «нет прогонов» неотличимо от «не пушили» — состояние ветки невидимо без ручной сборки;
- REJECT → ветка отстаёт → заводится новая → старая остаётся «носителем истории» → отставание
  растёт → следующий круг аудирует несуществующий мир (`C-089` Note по M-66).

**Решения founder'а (18.08):** порядок — CI первым, потом ветки с данными; старые ветки —
сначала проверить, нужны ли и не ломают ли, и только потом вливать; конструкцию по аллокатору
architect решает сам с опорой на вердикт Fable.

## A. CI: собираемость веток — отдельный workflow, НЕ правка триггера

### Почему не «одна строка»

Предписание `A-010`/Fable «`push.branches: [main]` → `['**']`» **нерабочее**, проверено
разведкой:

| что ломается | механика |
|---|---|
| первый push новой ветки | `github.event.before` = zero-SHA → fail-closed каскад `case "${raw}" in *[!0]*) : ;; *) die "база = zero-SHA…"` роняет **5 джобов**: `protected-artifacts`, `docs-freeze`, `contracts`, `artifact-ids`, `gate-meta` |
| любой force-push (rebase/amend — рутина агентов) | `git merge-base --is-ancestor "${raw}" HEAD` не проходит → те же 5 джобов |
| процедура merge `gates.md` §8 | push в ветку с открытым PR → два прогона на одном SHA → `gh pr checks --watch` вернёт ненулевой код → `gh pr merge` не выполнится никогда |

Это не дефект барьеров: их инвариант «база = состояние до события» осмыслен только для входа
в `main`. На ветке они честно говорят «гарантировать не могу».

### Что делать вместо

**Новый workflow `.github/workflows/branch-build.yml`** — только сборка, без гейтов базы:

```yaml
name: Branch build
on:
  push:
    branches-ignore: [main]
concurrency:
  group: branch-build-${{ github.ref }}
  cancel-in-progress: true
jobs:
  build-test:
    # тот же состав, что job `build-test` в ci.yml:
    #   cargo fmt --all -- --check
    #   cargo clippy --all-targets --all-features -- -D warnings
    #   cargo test --all
```

Свойства:
- **воли автора не требуется** — событие рождает GitHub; забыть нечего (это и было целью §F);
- отвечает ровно на вопрос «собирается ли предмет», ради которого всё затевалось;
- **не входит в агрегат `All checks passed`** (он в `ci.yml`, свой список `needs`) ⇒ merge не
  блокирует и процедуру §8 не ломает;
- `concurrency` с `cancel-in-progress` гасит шторм при серии push'ей;
- `deploy.yml` не задет: у него `push: branches: [main]` + фильтр путей (проверено чтением).

**Зона:** `.github/workflows/**` в замок §11 не входит (`check_docs_freeze.sh:63`) ⇒ токен
founder'а не нужен. Идёт харнесс-треком (`harness-track.md`): барьер + проба + адверсарий.

### Чего это НЕ даёт — назвать явно

Push-триггер строит **ветку**, а не дерево слияния. Отставание от `main` он не покажет — это
остаётся за `bash scripts/verify_design_claims.sh --merge-preview origin/main` (`gates.md` §8,
`strict: false` назван там же как принятый предел).

### Файлы

- создать `.github/workflows/branch-build.yml`
- проба: `scripts/tests/red_branch_build.sh` — проверяет, что workflow не входит в `needs`
  агрегата `status-check` и что его триггер исключает `main`
- `docs/workflow/harness-track.md` — строкой в реестр механизмов (вне замка §11)

## B. Разбор 24 веток — с данными CI на руках

Порядок founder'а: CI первым, потом ветки. После §A каждый push даёт прогон, и состояние
ветки видно списком `gh run list --branch <ветка>` без ручной сборки.

### B.0 ПРЕДШЕСТВЕННИК — половина работы уже сделана 13.08

`docs/plans/stale-branches-audit-2026-08-13.md` (28 KB) — полный аудит пяти веток со сводной
таблицей §7 и вердиктом: **ни одна не подлежит закрытию**; три «ДОВЕСТИ», одна — сейф фикса,
одна — ждёт founder'а. План НЕ переоткрывает эти вердикты, а проверяет, что изменилось за пять
дней, и распространяет ту же методику (отставание / свои коммиты / конфликты / чего не хватает)
на 19 веток, появившихся после.

Аудит содержит и невыполненные предписания — их надо исполнить, а не пересматривать:
§6в (правка `TECH-DEBT.md` про `TD-016`/M-31, зона reviewer), §8.1–8.2 (`SESSION-HANDOFF`
утверждает про удалённые ветки, что они живы — зона architect, частично закрыто §0ter).

### B.2 Правило разбора

| класс | что делать |
|---|---|
| содержимое поглощено `main` (проверено по содержимому) | удалить без потерь |
| кластер одного предмета | оставить самую полную; перенести уникальное ФАЙЛАМИ; удалить остальные |
| отстаёт >100 коммитов, круги идут | **пересобрать от `main`** (`A-010` §B для M-66); PR #6 закрыть, ветку держать до слияния преемника |
| `feat/M-10-rebased`, `salvage/*`, `feat/M-60-mechanisms` | founder: **сначала проверить**, нужны ли и не ломают ли, и только потом вливать — процедура §B.3 |

### B.2 Процедура проверки старых веток (ответ на «не ломают ли»)

Для каждой: собрать merge-preview и прогнать на нём базовую тройку CI —
```
git merge-tree / worktree на дереве слияния
cargo fmt --all -- --check ; cargo clippy --all-targets --all-features -- -D warnings ; cargo test --all
bash scripts/verify_design_claims.sh --merge-preview origin/main
```
Красное → не вливать, вернуть founder'у с причиной. Зелёное → влить как исторический артефакт
с пометкой в теле коммита (для `M-10-rebased` — `retired/defective`, не подключая к CI).

### B.3 Сохранность перед удалением

`branch-hygiene.md` п.6: снос только с сохранением. Уникальное содержимое переносится ФАЙЛАМИ
в ветку-преемника (вердикты гейтов обязаны существовать на HEAD —
`check_protected_artifacts.sh`), а не патчем в `/tmp`: патч вне репозитория уже терялся.

## C. Чтобы не повторялось — три механизма

### C.1 Наблюдение за ветками (нет вовсе, нужен)

`scripts/check_branch_health.sh` + джоб, печатающий по каждой `origin/*`: возраст, отставание
от `main`, число НОВЫХ файлов, наличие открытого PR, наличие прогона CI. Выше порога — `NOTE`,
не `FAIL` («наблюдает, не блокирует» — уровень 5 `binding-requires-mechanism.md`). Сегодня эту
величину не видит никто: она получена впервые за сессию командой, которую никто не запускал, —
и сразу показала кластеры-дубликаты.

**Переиспользовать две готовые конструкции, а не изобретать:**

| прецедент | что берём |
|---|---|
| `scripts/deploy_catchup.py` + джоб `deploy-catchup` (`ci.yml:303`) | образец «сторож наблюдает ОТСУТСТВИЕ события»; его проба ГЕРМЕТИЧНА — строит свой git-репозиторий в `/tmp` и в сеть не ходит, иначе мерила бы доступность GitHub, а не свой инвариант (`TD-135`). Наблюдатель веток обязан быть таким же |
| `scripts/gc_worktrees.sh` | три условия безопасного удаления: дерево чистое · нет только-локальных коммитов · `merge-base --is-ancestor HEAD origin/main`. Плюс `--dry-run` как обязательный режим. Тот же контракт переносится на удаление веток |

Инвентарь проводки (замер): в CI заведены 6 из 7 `check_*.sh` и 12 из 14 `red_*.sh`;
не заведены `check_disk_budget.sh` и `red_segment_meta_battery.sh`.

### C.2 Аллокатор номеров (решаю сам, по вердикту Fable)

Причина коллизии `C-100` найдена не там, где предполагалось: в обвязке зашит неверный вызов.

| # | файл:строка | сейчас | станет | зона |
|---|---|---|---|---|
| M1 | `.claude/wrappers/codex-critic.sh:105` | `next_artifact_id.sh C` | `reserve_artifact_id.sh C` | замок §11 ⇒ **токен** |
| M1 | `.claude/skills/harness-track/SKILL.md:111` | `next_artifact_id.sh C` | `reserve_artifact_id.sh C` | вне замка |
| M2 | `.claude/hooks/alloc-reserve-gate.py` + `settings.json` | — | `deny` на голый вызов без маркера `ALLOC_RAW=1` | замок §11 ⇒ **токен** |

Предписание арбитра (`next` делегирует в `reserve`) **отклонено**: `reserve_artifact_id.sh:5`
сам зовёт `next` (`ALLOC="${ALLOC:-…/next_artifact_id.sh}"`) — рекурсия, проверено исполнением.

**Условие поставки M2 (Fable):** хук приезжает В ПАРЕ с джобом, наблюдающим его наличие и
проводку. Иначе лечим болезнь механизмом с той же болезнью.

### C.3 Находка вне мандата — дыра в замке

`.claude/hooks/**` и `.claude/settings.json` **намеренно исключены** из замка §11
(`check_docs_freeze.sh:63`, сценарий `red_docs_freeze.sh:427` это закрепляет) и **не
наблюдаются ни одним джобом**. Единственный существующий механизм класса «блокирует действие»

Расширение зоны §11 — **вопрос founder'а**, зона правится только им.

## Верификация

| что | как проверяется |
|---|---|
| §A workflow работает | push в тестовую ветку → `gh run list --branch <ветка>` показывает прогон `Branch build`; на `main` — не появляется |
| §A не сломал merge | открыть PR на тестовой ветке → `gh pr checks <N> --watch` возвращает 0 при зелёном; агрегат `All checks passed` в списке |
