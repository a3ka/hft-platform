# Архитектура масштаба read-path: независимая проверка и решение

**Автор:** независимый architect (Fable, свежий контекст — по мандату founder'а 2026-08-03).
**Статус:** 🟢 rev3 — критик-гейт пройден ДВУМЯ независимыми критиками
(`research/critiques/C-058-scale-architecture.md` — **NOTE**, центральное утверждение §0
подтверждено по коду; `research/critiques/C-058-addendum-critic2.md` — присоединился к
NOTE, +3 находки). Все находки внесены: rev2 — N2 (§0 причина пересканирования), N3
(§4.4(в) методология счётчика), N4 (§4.4(д)+§7 п.7 partial-failure follower'а), N5
(§4.1 п.6+§7 п.8 per-key чекпоинт); rev3 — addendum №1 (§4.2/§4.3 множитель темпа кадров
и честная вилка потолка NIC), №2 (§4.1 п.5 cursor-resume требует RFC-аддендума), №3
(§2 строка Pub/Sub). Открыты подписи founder'а — §6.
**Предмет.** Founder предложил: «дневной кеш на Redis, кеш передаёт данные пользователям,
и не будет постоянной новой подгрузки каждым». Действующий architect в
`docs/plans/scale-10k-sessions.md` (ветка `feat/M-54-connect-cost`) ответил: «единственный
путь — in-process разделяемая проекция». Этот документ проверяет обе позиции замерами
и выносит решение.

**Главный вывод одной строкой.** Гипотеза действующего architect'а по направлению ВЕРНА
(разделяемая проекция), но его арифметика потолка неверна в важную сторону: реальная стена
сегодня — не память (~700 сессий), а **CPU: пять одновременных сессий съедают все четыре
ядра** (замерено, 399 %). Redis на одной машине отклоняется — он хранилище, а не
вычислитель, и не убирает ни одну из двух настоящих стен; его сильные стороны либо уже
закрыты чекпоинтом, либо относятся к фазе горизонтального масштабирования, до которой мы
не дошли. Рациональное зерно предложения founder'а («считать один раз, раздавать многим»)
— ровно то, что реализует разделяемая проекция; спор только о том, где живёт результат.

### Проверено по коду (origin/main aeb409b)

- Состояние — НА СЕССИЮ: `run_authorized_session` создаёт свой `LiveReducer` c
  персистентным `full: Reducer` на каждое соединение
  (`crates/gateway-serve/src/lib.rs:348-424`, `crates/gateway/src/lib.rs:2847-2877`).
- Push-цикл каждой сессии каждые 250 ms заново вызывает `journal::stream_from`
  (`crates/gateway/src/lib.rs:2997`), а `stream_from` НИКОГДА не пропускает активный
  (последний) сегмент (`crates/journal/src/segments.rs:996-1046`). События
  `seq <= cursor` декодируются и отбрасываются (`lib.rs:3008`).
- Причина непропуска — СТРУКТУРНАЯ, не формат (уточнено по C-058 N2): активный сегмент
  на проде — СЫРОЙ `.jrnl` (компакция в `.zst` явно пропускает его: «writer holds it
  open», `segments.rs:2504`), т.е. технически Seek-способный файл. Пересканирование
  происходит потому, что (а) сегмент можно пропустить целиком только по границе
  `next_seg.first_seq`, которой у последнего сегмента нет, и (б) между вызовами
  `stream_from` не сохраняется byte-offset — каждый вызов открывает `EventStream` с
  нуля. Решение §4.1 п.1 (персистентная позиция сегмент+оффсет) бьёт ровно в (б) и
  формат-агностично.
- Сегменты ротируются по ~1 GiB (`segment-00000166.jrnl` = 1 073 737 798 B); активный на
  момент замера — 153.7 MB и растёт.

### Следствие, которое отсутствует в плане действующего architect'а

Каждая сессия в steady-state **передекодирует активный сегмент с нуля каждый тик**.
Прямое наблюдение: один подключённый клиент держит CPU ≈100 % одного ядра; пять — 399 %
из 400 доступных; фактический темп кадров деградирует уже при одном клиенте (28 кадров
за 25 s вместо ~100 при номинале 4 Гц). Оценка (производная, не прямой замер):
153 MB × ~4 Гц ≈ 600 MB/s декодирования на сессию; к моменту заполнения сегмента до 1 GiB
один тик стоит секунды, и даже одна сессия не удерживает номинальный темп.

## §2. Предложение founder'а (Redis) — честный разбор

Предложение: «дневной кеш на Redis; кеш передаёт данные дальше пользователям; нет
постоянной новой подгрузки каждым». Разбираю всерьёз, по осям.

### Что в предложении ПРАВИЛЬНО (и принимается)

1. **Диагноз верен полностью:** «не должно быть так, чтобы каждый пользователь отдельно
   подгружал» — ровно это подтверждено замером (каждая сессия = свой реплей + свой
   пересканируемый хвост). Считать один раз и раздавать многим — принимаемое ядро решения.
2. **История неизменна и кешируема навсегда** — рациональное зерно «дневного кеша».
   Журнал append-only: всё, что старше активного хвоста, можно предпосчитать один раз
   и никогда не пересчитывать. Этот принцип входит в решение (§4, чекпоинт + в будущем
   immutable-history API).

### Что Redis даёт и что стоит — по осям, с числами

| Ось | Redis-кеш снапшотов | In-process разделяемая проекция |
|---|---|---|
| Кто СЧИТАЕТ проекцию | всё равно нужен процесс-вычислитель с теми же редьюсерами; Redis не решает «кто считает», только «где лежит» | тот же процесс, что раздаёт |
| Цена обновления (4 Гц × ключ) | serialize (2.4 MB snapshot или дельта) + сеть/loopback + память Redis = ВТОРАЯ копия состояния | мутация in-place, ноль сериализаций до момента отдачи |
| Цена отдачи снапшота клиенту | GET 2.4 MB (или 452 KB gzip) из Redis → в процесс → в сокет: те же байты проходят машину ДВАЖДЫ | байты из RAM процесса в сокет, один раз |
| Согласованность snapshot→frames (клиент обязан получить поток без дыр, GW-I-3/8) | снапшот на курсоре K из кеша + кадры после K: раздающему процессу ВСЁ РАВНО нужен живой редьюсер/хвост рядом с сокетом — Redis не снимает эту обязанность | тривиальна: снапшот и кадры из одного состояния под одним курсором (ровно так уже сделан M-54) |
| Переживает рестарт процесса | да — но это УЖЕ ЗАКРЫТО: `gateway-ckpt` (файл 1.78 MB, cron */15, GW-I-9 с байт-идентичностью и tamper-оракулами). Redis был бы ВТОРЫМ, более слабым чекпоинтом без CRC/lineage-дисциплины | да, через существующий чекпоинт |
| Несколько процессов/машин | ✅ настоящее преимущество | ❌ не даёт (одна машина) |
| Redis Pub/Sub / Streams как broadcast (добавлено по C-058-addendum №3) | ближайший Redis-аналог fan-out'а §4: но те же байты идут через машину дважды (процесс→Redis→процесс→клиент), состояние всё равно живёт у раздатчика (согласованность snapshot→frames), а bounded-очереди/slow-consumer политику Pub/Sub не даёт (at-most-once без backpressure per-подписчик) | in-process broadcast-канал: ноль лишних копий, backpressure свой |
| Операционная цена | новый прод-сервис: точка отказа, память (дублирование состояния), персистентность (AOF/RDB), бэкап, мониторинг, версия | ноль новых сервисов |
| Риск для инвариантов | кеш может стать вторым источником правды; инвалидация — новый класс багов; оракулы live≡replay пришлось бы тянуть через границу процесса | журнал остаётся единственным источником; проекция производна и восстановима (уже доказано чекпоинт-оракулами) |

### Вердикт по Redis

**На одной машине (сегодня и ближайшая фаза) — отклонить.** Обе реальные стены — CPU
(пересканирование хвоста) и egress (полоса NIC, §4) — Redis'ом не двигаются: он не
уменьшает ни число декодирований, ни байты к клиентам, а добавляет вторую копию состояния
и хоп. Его уникальное преимущество — разделение состояния МЕЖДУ процессами/машинами —
понадобится только в фазе горизонтали, и там его нужно будет сравнить с альтернативой
«fan-out-узлы тейлят реплику журнала» (`DESIGN.md` §16 последний пункт: журнал один —
читающих узлов сколько нужно; реплика журнала сохраняет DET-I-1-свойство «каждая цифра
выводится реплеем» на каждом узле, чего Redis-снапшоты не дают). Решение о горизонтали —
ПО ЗАМЕРУ, когда одна машина упрётся (§4, триггеры), и новая прод-зависимость — подпись
founder'а (§6).

«Дневной кеш» как идея не отклоняется, а переадресуется: неизменяемая история living в
файлах/HTTP с ETag/CDN (кешируется бесконечно и бесплатно У КЛИЕНТА и на edge), а не в
RAM Redis. Сегодняшний продукт истории ещё не отдаёт (окно снапшота — 60 s live-хвоста),
поэтому это отдельный будущий milestone; состав данных — граница C.

| # | Вариант | Вердикт | Почему |
|---|---|---|---|
| 1 | In-process разделяемая проекция (действующий architect) | ✅ ПРИНЯТ как ядро | единственный вариант, убирающий обе стены сразу; см. §4 |
| 2 | Redis-кеш (founder) | ❌ сейчас; пересмотр на фазе горизонтали | §2: не двигает ни CPU-, ни egress-стену на одной машине; рестарт уже закрыт чекпоинтом |

Оправдан, когда раздатчиков станет >1 на машине; форма зафиксирована в §16 («shared tailer» может быть вынесен), решение отложено до замера |

## §4. РЕШЕНИЕ — с числами

**Принимается: in-process разделяемая проекция + fan-out предсериализованных байтов +
сжатие на проводе + cursor-resume.** Четыре элемента — это ОДНО решение; по отдельности
каждый оставляет стену (замеры/оценки ниже).

### 4.1 Конструкция (реализация DESIGN.md §16, уточнённая замерами)

1. **Один tail-follower на процесс** — единственный читатель журнала: держит позицию
   (сегмент + байтовый оффсет) между тиками и декодирует ТОЛЬКО новые байты. Это убирает
   найденное в §0 пересканирование: сегодня N сессий × ~600 MB/s, станет — один поток
   ~десятки KB/s (темп записи recorder'а). Требование к оракулу: счётчик декодированных
   событий за тик ≈ новым событиям, НЕ размеру сегмента (расширение GW-I-11 на живой путь).
2. **Per-key редьюсеры** (`Selector` = ключ): follower маршрутизирует событие во все
   активные ключи его `(venue,symbol)`. Проекция создаётся при первом подписчике,
   умирает по TTL после ухода последнего. **Cap активных ключей — fail-closed** (отказ
   новой подписки с кодом из CT-RFC-09 §2.6, не деградация всех): бюджет памяти
   7.5 GB − ОС/recorder ≈ 5 GB ⇒ при ~20 MiB/ключ — **~250 активных ключей** сегодня.
3. **Fan-out байтов, не объектов:** кадр сериализуется (и сжимается) ОДИН раз на ключ на
   тик; подписчикам рассылаются готовые байты через broadcast-канал с per-conn bounded
   queue. Slow consumer → drop дельт + ресинк снапшотом (лестница §16, ступень 1), НЕ
   буферизация до OOM. Цена сессии падает до буферов сокета: ~десятки–сотня KB ⇒ 10 000
   сессий ≈ 0.5–1 GB (оценка; проверяется стендом).
4. **Сжатие на проводе** (permessage-deflate или предсжатые shared-байты). Замер №1:
   кадры жмутся ×9, снапшот ×5.4. Без сжатия 10 000 клиентов недостижимы ФИЗИЧЕСКИ
   (ниже); со сжатием — в пределах NIC.
5. **Cursor-resume при переподключении:** `subscribe` с курсором → клиент получает
   кадры от курсора, не снапшот. **Требует RFC-аддендума к CT-RFC-09** (уточнено по
   C-058-addendum №2): в нормативной схеме `subscribe` (§2.2) поля `cursor` НЕТ;
   добавление — аддитивное изменение wire-формы и идёт contract-RFC-путём, тем же,
   каким прошёл мультиплекс. Гасит шторм рестарта: без него рестарт при 10 000
   подключённых = повторная раздача 10 000 снапшотов.
6. **Чекпоинт остаётся единственным персистентным кешем** (cold-start пути); Redis не
   вводится. Журнал — единственный источник правды; проекция и все её байты производны
   и восстановимы реплеем (инвариант сохраняется существующими GW-I-9 оракулами).
   **Обязательное расширение (C-058 N5): чекпоинт должен стать per-key.** Сегодняшний
   `gateway-checkpoint-cron.sh` жёстко одноключевой (`Binance/BTCUSDT`, один
   timeframe/bands/window) — аргумент «рестарт закрыт чекпоинтом» верен для СЕГОДНЯШНЕЙ
   архитектуры и требует этой работы для целевой: без per-key чекпоинтов рестарт
   процесса с ~250 активными ключами = до 250 последовательных полных реплеев журнала
   (29 GB и растёт). До реализации per-key cron'а цена cold-start НОВОГО/эвикнутого
   ключа = один полный реплей на создание ключа — принимается явно и меряется стендом
   (§5 п.6); порог, после которого per-key чекпоинт обязателен, — десятки активных
   ключей.

### 4.2 Арифметика «отдать первый экран 10 000 клиентам» (одна машина)

Помечено: [З] — замерено сегодня, [О] — оценка, проверить стендом.

| Ресурс | Сегодня (на сессию) | После решения | 10 000 сессий после решения |
|---|---|---|---|
| Память состояния | ~20 MiB [З] | 0 на сессию; ~20 MiB на КЛЮЧ [З] | ~250 активных ключей в 5 GB [О]; сессии — 0.5–1 GB буферов [О] |
| CPU steady-state | ~1 ядро (пересканирование сегмента) [З] | один follower: декод только новых байт; сериализация ×ключи, не ×клиенты | [О] единицы % на follower + fan-out; стенд обязателен |
| Egress steady-state | ~11 KB/s/клиент raw [З]*; gzip ~1.2 KB/s [З]* | то же на клиента (данные те же) | raw: 110–440 MB/s ≈ **0.9–3.5 Гбит/с — НЕ ЛЕЗЕТ в 1 Гбит NIC**; gzip: 12–48 MB/s ≈ 100–380 Мбит/с [О] |

\* Оговорка к [З] (внесено по C-058-addendum №1): 11 KB/s снято с СЕГОДНЯШНЕГО сервера,
который отдавал кадры в 1.12 Гц вместо номинальных 4 Гц (28 кадров/25 s — деградация из-за
CPU-стены §0). Данные при этом не терялись — события упаковывались в более крупные кадры,
где обновления ОДНОГО бакета/уровня дедуплицируются. Здоровый сервер на 4 Гц отдаст те же
события в 3.6× большем числе кадров с меньшей дедупликацией: байты/с вырастут в
**1–4× (множитель не замерен — [О], меряется стендом §5 п.6)**. Диапазоны в таблице и
потолки §4.3 считаны от этой вилки 11–44 KB/s.
| Снапшот-шторм (все 10 000 разом) | невозможен (CPU-стена на ~4) | 2.42 MB raw / 452 KB gzip на клиента [З] | raw 24 GB (~3.5 мин на 1 Гбит) vs gzip 4.5 GB (~40 s) [О]; с cursor-resume у переживших рестарт — мегабайты |

Сжатие — не оптимизация, а условие существования 10 000 на одной машине (0.9 Гбит/с raw
против полосы NIC). Совпадает с независимой оценкой `DESIGN.md` §16 (160–320 Мбит/с на
бинарных сериях — и там же вывод об агрегированных разрешениях для дешёвых тарифов).

### 4.3 Где проходит граница одной машины (честно)

- **~2.8–11 тыс. одновременных** — потолок БЕЗ сжатия (NIC 1 Гбит / 11–44 KB/s,
  вилка по множителю темпа кадров — сноска §4.2). Нижняя граница вилки означает, что
  цель 10 000 без сжатия не гарантирована, поэтому сжатие остаётся условием цели,
  а не оптимизацией. [О]
- **~10–20 тыс. одновременных** — потолок СО сжатием при сегодняшнем составе данных
  (60-секундное окно, 1 инструмент-класс на подписку); упор — egress + ядро TCP. [О]
- **~250 одновременно АКТИВНЫХ ключей проекции** — потолок по памяти 7.5 GB; рост окна
  (продукт захочет часы, не 60 s) снижает это число пропорционально росту состояния. [О]
- Дальше — либо вертикаль (RAM/NIC), либо fan-out-узлы (§16: тейлят реплику журнала или
  реплицируют HOT-состояние). **Триггер выделения узла:** замеренный egress > ~50 %
  NIC в пике ИЛИ подключения > cap'а узла. Там же — момент честного сравнения
  «Redis-класс vs реплика журнала» (§2), не раньше.

### 4.4 Инварианты (что НЕ ломается)

- **DET-I-1** не затрагивается: журнал и запись не меняются вовсе.
- **live≡replay (GW-I-3/4/9)**: проекция использует ТОТ ЖЕ `Reducer`; оракулы сверки
  WS-выдачи с независимым реплеем переезжают с «на сессию» на «на ключ» без ослабления.
  Новые обязательные оракулы (RED, до реализации): (а) два подписчика одного ключа
  получают байт-идентичные последовательности кадров от своего курсора; (б) ресинк
  slow-consumer'а не создаёт дыры (`f[i].to == f[i+1].from` по каждой подписке);
  (в) follower декодирует за тик O(новых событий), не O(сегмента) — анти-регресс к
  сегодняшнему поведению. **Методология счётчика для (в) — обязательная (C-058 N3):**
  существующий `ReadStats.events_decoded` считает ТОЛЬКО yielded-события (прошедшие
  `seq > after`), а декодированные-и-отброшенные форвард-сканом активного сегмента НЕ
  считает — поэтому `pump_at_tail_is_bounded` (`red_frames_seek_bound.rs:198-238`)
  СЕГОДНЯ зелёный на коде, который по замеру §0 декодирует ~150 MB/тик. Оракул (в)
  обязан либо (i) считать физически распарсенные фреймы, включая отброшенные фильтром,
  либо (ii) иметь парный оракул на прод-масштабной фикстуре (активный сегмент в сотни
  MB, прирост в единицы событий; НЕ 16 KB-сегменты) с бюджетом wall-clock/аллокаций —
  иначе он унаследует ровно ту тавтологию, которую сам должен ловить;
  (г) эталон — независимый `gateway::snapshot`, НЕ повторный вызов конвейера (урок
  C-057 §5.1 о тавтологичных оракулах); (д) partial-failure изоляция по ключу
  (C-058 N4): битое событие / паника редьюсера ОДНОГО ключа не останавливает fan-out
  остальных ключей — деградирует один ключ с явной stale-меткой (лестница §16 ст. 4).
- **Fail-closed**: невалидный/отсутствующий cap = отказ старта (урок R7, PL-I-5).
- **LLM не в горячем цикле; граница C** — не затрагиваются.

## §5. Порядок работ

1. **Устранение per-tick пересканирования** (byte-offset tail-follower, пока хотя бы
   per-session) — самый большой выигрыш (~×100 steady-state CPU [О]) и предпосылка
   shared-tailer'а. Может идти как срочный milestone до полного R7: сегодняшний прод
   деградирует уже при 1–2 зрителях, к заполнению сегмента до 1 GiB — и при одном.
2. **M-55 многопоточный рантайм** — согласен с действующим architect'ом, что дёшево и
   полезно (замер §0: даже после M-53/54 connect-фаза сериализуется), но эффект ×4;
   без п.1 стена остаётся.
3. **RFC на разделяемую проекцию** (форма: контракт внутренних инвариантов GW-I-13+,
   cap'ы, TTL, ресинк-семантика; wire-форма УЖЕ покрыта CT-RFC-09 — мультиплекс §2.1
   сознательно оставлял место для R7). RED-оракулы §4.4 — до dev'а.
   *(Номер «GW-I-13+» датирован 03.08 и протух: M-69 занял `GW-I-14`, перескочив
   тринадцатый; по `gates.md` §12 разрывы не занимаются, значит RFC берёт `GW-I-15+`.
   Замер и предел — `docs/plans/gateway-ws-contract.md`, врезка «Обновлено 2026-08-24»;
   основание — `R-128` §9 NOTE-1.)*
4. **Сжатие на проводе** (может идти параллельно 3: это транспортный слой).
5. **Cursor-resume** в `subscribe` (расширение CT-RFC-09; аддитивно к его форме).
6. **Нагрузочный стенд НЕ на прод-VPS** (нагрузка в 10⁴ сокетов на живой recorder —
   недопустимый риск записи): арендная машина + копия журнала; методика замера — из
   `scale-10k-sessions.md` §4, все [О] из §4.2/§4.3 переводятся в [З].
7. После стенда — решение о фазе горизонтали ТОЛЬКО при срабатывании триггеров §4.3.

Замер после каждого шага; число без записанных условий (CPU до, backlog, число клиентов,
размер активного сегмента) — недействительно.

## §6. Что требует подписи founder'а

1. **Отклонение Redis на текущей фазе** — founder предложил его прямо, отклонение должно
   быть принято им явно (этот документ — обоснование), с зафиксированным условием
   пересмотра (§4.3: горизонталь).
2. **Cap'ы продуктового смысла:** максимум активных ключей проекции (≈ «сколько разных
   инструментов×таймфреймов онлайн одновременно бесплатно»), cap соединений на узел,
   политика тарифных разрешений (Free = грубее кадры — §16). Это «чего мы хотим», не
   «как правильно».
3. **«Десятки тысяч» = сколько одновременных?** — открытый вопрос действующего
   architect'а remains; проектируем под 10 000 одновременных как строгий случай.
4. **Состав записи** (сколько инструментов пишем — упомянутые «300») — граница C,
   влияет на число ключей и бюджет памяти.

## §7. Риски и что мы НЕ узнаем до реализации

1. **CPU редьюсеров на сотни ключей не замерен** — сегодня ключ один (env). Оценка
   «follower дешёвый» держится на том, что recorder пишет те же события за ~1.4 % CPU;
   но ×250 редьюсеров может быть дороже — только стенд покажет.
2. **Память ключа растёт** с окном и активностью инструмента; «~20 MiB» — сегодняшний
   BTCUSDT с окном 60 s. Продуктовое окно в часы изменит бюджет §4.3 в разы.
3. **Поведение tungstenite/ядра на 10⁴ сокетов** (fd-лимиты, память соединения,
   write-backpressure) — не проверялось вовсе; 0.5–1 GB на буферы — оценка.
4. **Фактическая полоса NIC Hetzner** под длительной нагрузкой — заявленная ≠ доступная.
5. **Гонка follower'а с ротацией/ретеншеном сегмента** (журнал живёт: ротация по 1 GiB,
   ретеншен удаляет старые) — семантика «сегмент исчез под ногами» требует явного
   оракула; сегодняшние пути это переживают через полный rebuild, у follower'а такого
   пути нет по построению.
6. **Замеры сняты в момент низкой волатильности** — 11 KB/s/клиент кадров может
   вырастать в разы на всплеске; стенд обязан включать replay высоковолатильного окна.
7. **Единый tail-follower — смена радиуса отказа (C-058 N4).** Сегодня сбой чтения
   журнала деградирует ОДНУ сессию (изоляция per-session `LiveReducer`); после решения
   затор/паника ЕДИНСТВЕННОГО follower'а (битый фрейм, патологически дорогой редьюсер
   одного ключа) стопорит live-push для ВСЕХ ключей и всех подписчиков процесса. Это
   осознанная цена разделения работы; компенсации обязательны: partial-failure изоляция
   по ключу (оракул §4.4(д)), stale-метка вместо тихого молчания (лестница §16 ст. 4),
   watchdog на прогресс курсора follower'а. Полная изоляция (follower в отдельном
   процессе) — вариант §3 п.7, отложен до замера.
8. **Bootstrap состояния нового ключа** (C-058 N5) — цена и механика per-key
   чекпоинтов (§4.1 п.6) не замерены; до стенда неизвестно, где проходит порог «полный
   реплей на создание ключа приемлем».
