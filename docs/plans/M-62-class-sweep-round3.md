### minimal_sequence

  такт 1 — вызван, когда на диске лежат ОБА файла жертвы (шаг 6 компакции: rename .tmp→.zst сделан, remove .jrnl ещё нет — segments.rs:3998-4011);
  такт 2 — вызван после исчезновения ОДНОГО из двух (шаг 7 remove .jrnl; либо self-heal-удаление оригинала через ЧАСЫ — segments.rs:3956-3957; либо, симметрично, уборка .zst при живом .jrnl).

Ни одного холостого такта не требуется: в тестах `indep_b4_minimal_and_persistence` и сценарии B такт 0 отсутствует, порча возникает всё равно. Меньше двух тактов недостаточно — контрольный прогон показывает, что один такт, накрывающий ОБА файловых события сразу, кеш не портит (это и починил `a5e63df` перестановкой remove перед add).

Условия на жертву: закрытый сегмент, НЕ последний по индексу. Если жертва — `latest_path`, её исчезновение ловит `fs::metadata` в `is_fresh` (segments.rs:244-258) и уводит в полный `refresh()` — порчи нет. Индекс 0 годится, ограничение только на «не latest».

Такт 0 (каталог не менялся): `true`, ops=3 — ранний выход `cur_names == self.file_names` (segments.rs:263-265).

Такт 1 (оба файла рядом): `true`, ops=6 — инкрементальная ветка, added=[.zst], removed=[]. НО в конце ветки `self.file_names = cur_names` (segments.rs:341) — имя `.zst` записывается в кеш имён.

Такт 2 (.jrnl удалён): `true`, ops=4 — added=[] (`.zst` уже в `file_names`, значит НЕ «added»), removed=[.jrnl]. Цикл segments.rs:293-298 делает `self.segments.retain(|s| s.index != idx)` ПО ИНДЕКСУ, не спрашивая, остался ли на диске другой файл этого же индекса. Запись сегмента удалена, вернуть её некому. `small_change` = true (added≤2, removed≤2), поэтому возврат `true`.

Такты 3+: `true` — `cur_names == self.file_names`, дифа больше нет.

ПОЧЕМУ ЭТО РЕШАЮЩЕЕ. `true` означает, что вызывающий (`stream_from_at_with_catalog`, segments.rs:1792-1798) НЕ зовёт `refresh()`. А переписанные на такте 2 `file_names` означают, что механизм больше НИКОГДА не увидит расхождения сам: порча не просто не исправляется — она становится ненаблюдаемой изнутри. Сессия отдаёт укороченный поток при зелёном healthcheck (класс TD-031).

SETUP-GUARD (обязательный по условию задачи): во ВСЕХ сценариях A/B/минимальном `is_fresh` вернул `true` на КАЖДОМ такте — значит померена именно ИНКРЕМЕНТАЛЬНАЯ ветка, а не полный refresh. Проба падает с явным «SETUP-GUARD: is_fresh=false ⇒ померян ПОЛНЫЙ refresh» — и этот страж реально сработал при проверке варианта фикса 2, что доказывает: он не декоративный.

То есть на проде (1 новый сегмент ~2 ч) fail-open живёт всю сессию — до перезапуска, батч-компакции или ретеншена. Регрессия именно M-62: до него `stream_from_at` звал `segments(dir)` каждый тик (это и записано в TD-120: «ЭТО ЖЕ НАСЛЕДУЕТ guard JR-I-11»). Компенсации нет ни в спеке (`grep -n монотон milestones/M-62-segment-metadata.md` — пусто), ни в оракулах (`grep -rli monotonic crates/gateway/tests/` не даёт `red_segment_meta_bound.rs`), ни в R-053.

ЧТО ОПРОВЕРГНУТО — заявление «порча молча отдаётся клиенту» (P6: «Ok, 376 событий, регрессий seq: 1»). Через прод-путь НЕ ВОСПРОИЗВОДИТСЯ: во всех трёх формах нарушения выдано 0 некорректных событий, курсор не сдвинут, кадры не испорчены. Причина — ДВА независимых фильтра ниже по стеку, которых нет в конфигурации пробы автора находки:
(1) `pump` (gateway/src/lib.rs:3166) пропускает `event.seq <= self.cursor.upto_seq`; догнавшая сессия (а `pump` дренирует ВЕСЬ backlog за один вызов, поэтому курсор всегда на голове) имеет курсор = max seq, и любой переприкреплённый сегмент ТОГО ЖЕ seq-пространства несёт seq ≤ головы ⇒ выдача 0;
(2) сегментный пропуск в `stream_from_at_with_catalog` (:1819-1836, `next_first - 1 <= after`) систематически ВЫБРАСЫВАЕТ именно неправильно вставленный сегмент: у его правого соседа `first_seq` маленький. Замер C (архив чужого пространства, first_seq=100 > головы 59, вставлен под индексом 2): `decoded=0`, курсор Some(59) не сдвинулся.
Конфигурация автора (кеш есть + `after_seq=None`) для `pump` недостижима: `after_seq=None` означает «ни одного события не выдано», а кеш появляется только после первого тика, который на непустом журнале сразу двигает курсор. Отсюда же снимается «регрессия seq у клиента»: курсор монотонен по конструкции, клиент регрессию не увидит никогда.
Опровергнута и заявленная достижимость «достаточно ОДНОГО файла между тиками, все 20+ сессий»: нарушение требует не появления файла как такового (ротация, компакция, restore под родным индексом монотонность НЕ ломают — проверено сценарием A/B), а именно ошибочного re-attach архива под ЧУЖИМ индексом — действия, которое runbook `docs/ops-journal-tail-unreadable.md` §4 прямо запрещает, и которое сам проект в TD-030 оценил как MINOR («требует нарушения явного письменного запрета из runbook»). `journal.force-next-seq.json` таким генератором не является: он применяется только при нечитаемом хвосте (`resolve_next_seq_or_declared`, :2952-2996) и двигает seq только ВВЕРХ, монотонность не ломая.

ИТОГ: находка — не «утечка порчи в выдачу», а ПОТЕРЯ СИГНАЛА. Гейт JR-I-11, объявленный fail-closed для трёх путей чтения, на gateway-пути после M-62 молчит: кокпит остаётся зелёным на каталоге, который research/backtest/CLI (полный путь) уже отвергают, — ровно тот сигнал, на который runbook опирается в R-001 NOTE 3 («recorder поднялся ≠ инцидент закрыт»). Класс — MAJOR по контракту (sacred-инвариант перестал держаться на одном из своих трёх путей), но не по данным.
- цена: НЕ теряются и не дублируются события (замерено: 0 некорректно выданных событий во всех формах, регрессий seq у клиента 0, живые данные продолжают доходить). Теряется СИГНАЛ fail-closed:

Точная величина окна: от момента появления нарушающего файла до перезапуска сессии ИЛИ до между-тикового изменения >2 файлов (батч-компакция/ретеншен). - Новая сессия при этом ложится (`resume` → Err) — то есть система в противоречивом состоянии: старые сессии обслуживают, новые не поднимаются.

### [L3-1] Удаление ПО ИНДЕКСУ не проверяет, остался ли у индекса второй файл: любое одиночное удаление в паре .jrnl/.jrnl.zst стирает ЖИВОЙ сегмент из кеша (self-heal, mismatch-ветка, prune, ручная уборка)

- линза: retention-restart
- место: crates/journal/src/segments.rs:296
- механизм: Инкрементальная ветка удаляет запись кеша по ИНДЕКСУ (`self.segments.retain(|s| s.index != idx)`, :293-298), не сверяя ни ПУТЬ удалённого файла с путём кешированной записи, ни того, остался ли у этого индекса другой файл на диске. Добавление (:299-338) при этом эмулирует D-COMP-1 и в файл, лежавший на диске ДО такта, вообще не заглядывает — «added» вычисляется как разница ИМЁН, а не как «что сейчас есть у индекса». Пара .jrnl + .jrnl.zst одного индекса — штатно распознаваемое состояние (dedup_indexed_paths :1002-1018 «побеждает СЫРОЙ»; комментарий :320 прямо называет возврат сырого из бэкапа), и прод удаляет из неё РОВНО ОДИН файл ТРЕМЯ разными путями: (а) self-heal D-COMP-2 при совпавшем sha удаляет ТОЛЬКО оригинал (:3956-3957) — .zst остаётся, но он лежал рядом часами, в `added` не попадёт и в кеш не вернётся; (б) ветка расхождения sha удаляет ТОЛЬКО .zst (:3947), оставляя сырой ГОРЯЧИМ, — а кеш держал именно сырой, и retain по индексу сносит его; (в) prune_segment ретеншена (:1986-1988) удаляет путь-победитель дедупликации, оставляя второй файл. Во всех трёх случаях is_fresh возвращает true и переписывает file_names — расхождение больше никогда не наблюдаемо. Отдельная неприятность той же природы: latest_path в scan_dir_layout выбирается строгим `idx > cur` (:541-546), поэтому при паре на МАКСИМАЛЬНОМ индексе победитель зависит от порядка fs::read_dir — одно и то же состояние диска то уходит в refresh (безопасно), то в инкрементальную ветку (порча). Замер (проба lens3_probe.rs на 3115628, N=20 сегментов, смешанный каталог): A (удалён только .jrnl, .zst на месте) — cache=[...18,20...], truth=[...18,19,20...], is_fresh=true; B (удалён только .zst, живой .jrnl на месте) — тот же результат, сегмент 19 исчез из кеша при целом сыром файле; D (контроль: удалён единственный файл индекса) — ЗЕЛЁН, то есть сломана именно пара, а не удаление вообще.
- последовательность: Такт 0: сессия строит кеш на каталоге, где у индекса N лежат ОБА файла (пара живёт часами/сутками — см. reachability). Кеш держит сырой (D-COMP-1), file_names содержит ОБА имени. Такт 1..k: каталог не меняется, is_fresh=true по быстрому пути. Такт k+1: cron 03:50 (или оператор) выполняет ОДНО удаление — self-heal сносит .jrnl (:3957) либо mismatch-ветка сносит .zst (:3947). Сессия видит removed=[один файл], added=[] ⇒ small_change=true ⇒ retain(s.index != N) стирает запись, цикл added пуст (второй файл в file_names с самого начала) ⇒ сегмент N исчез из кеша. is_fresh=true, file_names перезаписан. Такты k+2..∞: расхождения не видно, refresh не зовётся (ротация и посегментная компакция дают diff ≤2 и не инвалидируют кеш) — сессия молча недоотдаёт ВСЕ события сегмента N (на проде 1 GiB ≈ 10.7 млн событий) при зелёном healthcheck. Сценарий C пробы подтвердил липучесть через 4 последующих такта, включая рост активного сегмента.
- достижимость: Триггер (одиночное удаление) — не гонка, а ОДНО событие каталога: попадание в него гарантировано для КАЖДОЙ живой сессии, а не вероятностно, как в Б-4 (там окно rename→unlink :4003-4011 микросекундное). Требуется предусловие — пара на диске. Прод-замер сегодня: пар нет, компакция шла успешно (12.08 03:50, 11 сегментов, alert'ов нет). Пара возникает: (i) при смерти/сбое процесса компакции между :4003 и :4011 либо при ОТКАЗЕ fs::remove_file(src) на :4011 (том ушёл в ro по I/O-ошибке, EACCES) — тогда пара живёт НЕОГРАНИЧЕННО, до следующего ночного прогона, который и выполнит self-heal; (ii) при возврате сырого сегмента из бэкапа/холодного хранилища — сценарий, ЯВНО заложенный в код (:320); (iii) при ручной операции — deploy/README.md:347 отдельно предупреждает «не удалять .zst руками, не зная, что оригинал тоже удалён», то есть такие действия оператора предполагаются. Сам факт существования ветки self-heal D-COMP-2 (:3927-3957) — признание проекта, что состояние-сирота на проде случалось (её ввели после блокера M-08 rev 9 «3000 событий читались как 3172», где оригинал-сирота жил НАВСЕГДА). - severity: потеря данных
- адверсарий: ЯДРО НАХОДКИ ВЫЖИЛО (механизм воспроизведён детерминированно, 3 прогона × 2 направления), но ТРИ её утверждения опровергнуты замером, и одно уточнено в сторону ухудшения.

ЧТО ОПРОВЕРГНУТО.
(1) ЦЕНА. Заявлено «сессия молча недоотдаёт ВСЕ события сегмента N (≈10.7 млн)». На ПРОД-ФОРМЕ вызова (`stream_from_at_with_catalog` — ровно то, что зовёт `LiveReducer::pump`, gateway/src/lib.rs:3150) с испорченным кешем расхождение с независимым эталоном РАВНО НУЛЮ при курсоре у хвоста — единственном положении курсора, которое даёт прод-путь. Причина не «повезло», а конструкция: жертвой одиночного удаления всегда оказывается СТАРЫЙ сегмент (компакция/self-heal трогают только закрытые старше `COMPACTION_KEEP_RAW=2`, т.е. ≥2 ротаций назад), а отбор по `after_seq` (`segments.rs:1819-1836`) такие сегменты и так выбрасывает. Потеря появляется ТОЛЬКО при курсоре в жертве или до неё: −3 из 19 и −4 из 20 событий (весь остаток сегмента), при полном реплее −4 из 128 (весь сегмент).
(2) ДОСТИЖИМОСТЬ отставшего курсора прод-путём НЕ ПРЕДЪЯВЛЕНА, и код против неё: gateway-serve создаёт `LiveReducer` НА КАЖДОЕ соединение (`gateway-serve/src/lib.rs:380`) через `resume` от чекпоинта (cron `*/15`, т.е. отставание ≤15 мин ⇒ курсор внутри АКТИВНОГО сегмента), а первый же `pump(usize::MAX)` (`:400`) идёт с `catalog_in=None` (`LiveReducer` инициализирует `segment_catalog: None`, gateway/src/lib.rs:3037,3087) — то есть догон истории всегда работает на СВЕЖЕПОСТРОЕННОМ каталоге и дренирует весь backlog за один тик. Разрыв между курсором (≤15 мин) и жертвой (≥2 ротации ≈ ≥2.4 ч на замере прода) — два порядка. Остаточный путь к отставанию (многочасовая серия `Err` из `pump` при живом соединении, `gateway-serve/src/lib.rs:563`) находкой не назван и мной не воспроизведён.
(3) «ТРИ пути на проде» — завышение. (в) `prune_segment` по cron'у НЕ исполняется: `deploy/cron.d/journal-retention` задаёт `RETENTION_MODE=dry-run` с явным «по cron'у НИКОГДА apply», apply — ручная операция оператора. (б) mismatch-ветка требует предварительно битого `.zst` и завершается `Err` ⇒ compaction-cron поднимает alert, т.е. состояние наблюдаемо. Реально автоматический путь один — (а) self-heal, и он требует предусловия «пара на диске», которого на проде СЕЙЧАС нет (замер ниже).
(4) НОВИЗНА относительно уже принятого блокера Б-4 — тонкая. `R-056` §Условие APPROVED п.1 формулирует фикс в общем виде («удаление из кеша не смеет оставлять индекс без записи, пока на диске есть файл этого индекса»), а п.2 прямо требует «тот же сценарий с удалением .zst при живом .jrnl — корень один: удаление по индексу не проверяет ВЫЖИВШИХ» (R-056:126,174-182). ### [L3-2] Два одновременных прогона компакции делят ДЕТЕРМИНИРОВАННЫЙ путь `.jrnl.zst.tmp` без единой блокировки: File::create второго обнуляет уже проверенный .tmp первого между sha-верификацией и rename, после чего первый переименовывает порченый .zst и удаляет 1 GiB оригинала

- линза: retention-restart
- место: crates/journal/src/segments.rs:4003
- механизм: Имя временного файла строится из имени сегмента и НИЧЕМ больше (`let tmp = src.with_file_name(format!("{base}.zst.tmp"))`, :3925) — оно одинаково для любого числа процессов. Порядок в compact_segment: sha256 оригинала (:3969) → compress_to_tmp с `File::create(tmp)` (:4093, ТРУНКАЦИЯ) → sha256_decompressed(&tmp) (:3980) → File::open+sync_all (:3999-4002, для 100-200 MB это заметное время) → rename(tmp, dst) (:4003) → fs::remove_file(src) (:4011). Верификация «доказанной копии» (принцип ColdCopyProof) относится к СОДЕРЖИМОМУ .tmp в момент чтения, а переименовывается файл ПО ИМЕНИ позже — между этими двумя моментами второй процесс, дошедший до своего compress_to_tmp по тому же сегменту, обнуляет файл. Тогда прогон A переименовывает в .zst огрызок чужого потока и на следующей строке безвозвратно удаляет 1 GiB сырого сегмента; прогон B затем не находит свой .tmp (он переименован) и падает с Err — то есть оба «отчитались об ошибке», а данных уже нет. Обратная фазировка (B труncует ДО верификации A) безопасна: A ловит несовпадение sha и оставляет оригинал. Это НЕ класс M-62 (код M-08, инкрементальной ветки не касается) — привожу, потому что линза требует осмотреть операции вне горячего пути, а цена ошибки здесь выше всех прочих находок.
- последовательность: Не такты сессии, а такты двух писателей: t0 — прогон A начал compress_to_tmp для segment-N (1 GiB, десятки секунд); t1 — прогон B стартовал, дошёл до segment-N, dst ещё нет (A не переименовал) ⇒ B идёт обычной веткой и считает sha оригинала (~секунды); t2 — A закончил verify (sha .tmp совпал) и вошёл в fsync; t3 — B выполнил `File::create(tmp)` ⇒ проверенный .tmp обнулён; t4 — A выполнил rename(tmp→.zst) на обнулённом/частичном файле; t5 — A выполнил fs::remove_file(src) ⇒ сырой сегмент уничтожен; t6 — B пишет в inode, уже переименованный в .zst, затем падает на sha256_decompressed по несуществующему пути.
- достижимость: Замер: ни `deploy/bin/journal-compaction-cron.sh`, ни `deploy/bin/journal-retention-cron.sh` не содержат ни `flock`, ни какой-либо блокировки (grep — 0 совпадений), тогда как соседняя запись того же cron-файла для чекпоинтера ЯВНО обёрнута в `flock -n` с объяснением «без неё учащение даёт накладывающиеся запуски». Прод-путь запуска — `docker compose --profile ops run --rm journal-compaction`, каждый вызов создаёт НОВЫЙ контейнер (в логе: `Container hft-platform-journal-compaction-run-0d4cc7cd7ce7 Creating`), одновременность ничем не ограничена. Ручной прогон той же команды документирован в deploy/README.md как штатное операторское действие при разборе алерта; ночной прогон занимает единицы минут (11-12 сегментов по 1 GiB), и оператор, запускающий компакцию руками в это окно, воспроизводит сценарий. Честная оговорка: экспериментально я это НЕ воспроизводил (нужна инструментированная пауза между :3996 и :4003), вывод сделан чтением кода + замером отсутствия блокировки; вероятность зависит от действий оператора, а не от нагрузки.
- severity: потеря данных
- адверсарий: Механизм ВЫЖИЛ, но заявленная ЦЕНА ОПРОВЕРГНУТА замером: «A переименовывает огрызок и безвозвратно удаляет 1 GiB» в базовом случае НЕ происходит.

(б) «Порча живёт до конца жизни сессии» верно лишь при ДОЛГОЖИВУЩЕМ recorder'е. Тик с изменением >2 файлов (массовый retention/компакция) даёт `small_change=false` → `refresh()` → guard → громкий `Err`.

ЧТО ВЫЖИЛО (истинный механизм — ПОТЕРЯ/ЗАСТОЙ, не дубли)
Отсев по `after_seq` (:1819-1836) роняет сегмент, если `next_first - 1 <= after`. Подложенный архив с малым `first_seq`, стоящий ПОСЛЕДНИМ по индексу, делает условие истинным для АКТИВНОГО хвоста — тёплая сессия перестаёт видеть активный сегмент. `Journal::rotate` берёт индекс из своего счётчика (`self.seg_index + 1`, lib.rs:269), поэтому живой recorder НИКОГДА не перепрыгивает инъекцию сам: 99→100→…→144 при инъекции на 149.
Прод-верный замер (P-5, один долгоживущий писатель, здоровый близнец рядом): 60/60 тиков отставания, худшее = содержимое целого активного сегмента, Err = 0. Побочно: `latest_path` навсегда пришпилен к подложенному файлу (максимальный индекс), то есть рычаг инвалидации «хвост усечён/исчез» тоже мёртв.

ДОСТИЖИМОСТЬ — честно. Триггер операторский: неверный индекс при `cp` из холодного хранилища (docs/ops-journal-tail-unreadable.md, Шаг 3, строка 63) или возврат из карантина (Шаг 4). Не рутина. Но это РОВНО тот сценарий, под который JR-I-11/TD-030 был смержен, и текст диагностики guard'а адресован именно ему. Находка — не ставка на вероятность, а снятие смерженного fail-closed инварианта с прод-пути без строки в §5, без TD и без оракула.
- цена: Тёплая gateway-сессия перестаёт видеть АКТИВНЫЙ сегмент и застывает на «всё, кроме последних ≤2 часов» — молча.

Перевод в прод-величины (замер §1.1 M-62: активный сегмент ~473 MB→1 GiB, ротация ~2 ч, ~10.7 млн событий на сегмент): каждая тёплая сессия отдаёт клиенту данные с задержкой до одной ротации, то есть до ~2 часов, и держит эту задержку, пока индекс писателя не догонит индекс подложенного файла (при типовом промахе на +50 — ~100 часов, ~4 суток) либо пока сессия не перезапустится.

Все три liveness-проверки `gates.md` §8 при этом ЗЕЛЁНЫЕ: контейнер healthy, heartbeat свежий, журнал растёт. Ровно класс «тихая деградация», под который §8 и писался (прецеденты TD-011/TD-031).

Асимметрия, которая и есть предмет: на ОДНОМ каталоге в ОДИН момент холодная сессия отказывает громко, с именами обоих файлов и инструкцией оператору, а тёплая молча отдаёт устаревшую картину. Что получит клиент — определяется только временем старта его сессии.

Чего НЕ теряется (вопреки находке): дубли до потребителя gateway не доезжают — их срезает курсорный фильтр `pump`. Цифра «204 против 200» жива только на сыром journal-API, куда прод в тёплом состоянии не ходит.

### [L5-1] Тёплый кеш обходит fail-closed guard монотонности first_seq (JR-I-11): каталог, который прод-путь ОТКАЗЫВАЕТСЯ читать, живая сессия принимает молча

- линза: consumer-side
- место: crates/journal/src/segments.rs:292
- механизм: Полное наблюдение каталога (`segments_counted`, :1056-1088) заканчивается guard'ом `check_first_seq_monotonic` (:1083-1085, JR-I-11 / TD-030): если `first_seq` не возрастает по индексу сегмента, функция возвращает Err с операторской диагностикой, и НИ ОДНО событие наружу не выдаётся. Инкрементальная ветка `is_fresh` (:292-344) строит новое состояние кеша сама — `retain` + `classify_segment` + `push` + `sort_by_key(index)` — и guard НЕ зовёт ни разу; она возвращает `Ok((true, ops))` (:344), после чего `stream_from_at_with_catalog` (:1794) НЕ идёт в `refresh()` (единственное место, где guard был бы восстановлен). То есть валидация, которую полное наблюдение выполняет ОБЯЗАТЕЛЬНО, при инкрементальном наблюдении не выполняется вовсе — ровно класс «событие каталога принято за полное наблюдение состояния». Последствие для потребителя вытекает из арифметики пропуска (:1819-1836), которая работает поверх принятого каталога: сегмент i выбрасывается ЦЕЛИКОМ, если `first_seq(i+1) - 1 <= after`. Сегмент с низким `first_seq`, приехавший под старшим индексом, делает это условие истинным для всех предшественников — выдача режется молча, а его собственные события отфильтровываются в pump как `seq <= cursor` (gateway:3168). Итог: сессия перестаёт отдавать данные НАВСЕГДА при зелёном healthcheck, тогда как холодная сессия/реплей/отчёт на том же каталоге громко отказывают с инструкцией оператору. Это ровно тот вред, который называет собственный ассерт существующего оракула mn_2: «`stream_from` … ещё и ПРОПУСКАЕТ сегменты по `first_seq`, то есть на немонотонном каталоге режет данные молча».
- последовательность: тик 1: сессия подключена, кеш построен через `SegmentCatalog::open` → guard отработал, каталог монотонен. Между тиками: recorder перезапущен после инцидента «нечитаемый хвост» — оператор применяет штатный выход `journal.force-next-seq.json` (:2273, M-49/JR-I-8) или возвращает карантинный сегмент по `docs/ops-journal-tail-unreadable.md`; в каталоге появляется НОВЫЙ `segment-NNNNNNNN.jrnl`, чей `first_seq` НИЖЕ, чем у предыдущего по индексу. тик 2: `is_fresh` видит added=[новый .jrnl], removed=[] ⇒ `small_change` ⇒ `classify_segment` ⇒ push ⇒ sort ⇒ `file_names = cur_names` ⇒ `Ok((true, ops))`. Guard не вызван, `refresh()` не вызван. тик 3…N: `is_fresh` сравнивает имена, они совпадают ⇒ ранний `return Ok((true, ops))` (:263) ⇒ кеш и его немонотонность живут до конца сессии; предшественники нового сегмента выбрасываются пропуском, его события режутся фильтром `seq <= cursor` — клиент получает пустые тики бесконечно.
- достижимость: (а) Путь входа — САМЫЙ ЧАСТЫЙ из всех: инкрементальный `add` исполняется на КАЖДОЙ ротации (прод ≈ каждые 2 ч на каждую живую сессию), т.е. новый сегмент штатно входит в кеш вообще без проверки монотонности; до M-62 guard переоценивался на КАЖДОМ тике (410+ syscall'ов), теперь — только при подключении. (б) Триггер немонотонности — не гипотеза: под него в коде существуют два операторских механизма (`journal.force-next-seq.json` с одноразовым переименованием в `.applied.json`, :2273-2275; карантин/возврат сегмента) и два оплаченных инцидента (TD-030/M-52 — «архив вернули под старшим индексом», JR-I-8/M-49 — потеря `journal.meta` ⇒ seq-reuse при рестарте recorder'а). (в) Асимметрия окна: gateway-serve и recorder — разные контейнеры, рестарт ОДНОГО recorder'а живые WS-сессии переживают, поэтому именно тёплые кеши и увидят новый сегмент инкрементально. (г) Цена ошибки максимальна там, где guard и ставили: он fail-closed именно потому, что перемешанный seq «уходит во все проекции сразу».
- severity: потеря данных
- адверсарий: ЯДРО ВЫЖИЛО, но три заявления находки опровергнуты замером.

ВЫЖИЛО (доказано прогоном). Тёплый `SegmentCatalog` действительно обходит guard JR-I-11 целиком. На одном и том же каталоге: `SegmentCatalog::open` → Err, `stream_from` → Err, `read_all` → Err, `stream_from_at` (прод-путь ДО M-62) → Err, а `stream_from_at_with_catalog` с тёплым кешем → **Ok**. Ok сам по себе есть доказательство, что `is_fresh` вернул true и `refresh()` не звался: `refresh()` идёт в `segments_counted`, где guard инлайн (segments.rs:1083), и вернул бы тот же Err. Это РЕГРЕССИЯ, введённая M-62: до неё `pump` звал `stream_from_at`, который переоценивал guard каждый тик (gateway/src/lib.rs:3150 против прежнего вызова). Ни один оракул набора её не ловит — grep `monotonic|first_seq` пуст и в `crates/gateway/tests/red_segment_meta_bound.rs` (SM-1..SM-10), и в `scripts/tests/red_segment_meta_battery.sh`, и в `scripts/verify_M-62.sh`. Оракулы JR-I-11 (`red_stitch_monotonic.rs` mn_1/mn_2/mn_3) все идут холодными путями.

ОПРОВЕРГНУТО-1 — «клиент получает пустые тики БЕСКОНЕЧНО». Неверно. Ротация ЛЕЧИТ выдачу: замер STEP6–STEP7 — после появления сегмента с высоким `first_seq` ПОСЛЕ битого сессия снова отдаёт данные (60 событий, 400..459). Арифметика пропуска (:1819-1836) смотрит только на НЕПОСРЕДСТВЕННОГО соседа, поэтому битый сегмент гасит ровно ОДНОГО предшественника, а не «всех». Реальная цена — не вечная тишина, а безвозвратная молчаливая потеря непрочитанного хвоста ОДНОГО сегмента плюс тишина до ближайшей ротации.

ОПРОВЕРГНУТО-2 — «путь входа самый частый из всех». Подменены две разные частоты. Часто исполняется ОБХОД guard'а (каждая ротация), но ТРИГГЕР немонотонности автоматического пути не имеет вовсе. Оба названных находкой механизма закрыты: (а) `journal.force-next-seq.json` не может дать низкий `first_seq` — `resolve_next_seq_or_declared` (:2986-2994) отвергает декларацию с `next_seq <= readable_max`, а `ReadableFloor::Unknown` тоже отказ; (б) штатный рестарт recorder'а после потери `journal.meta` тоже не может — `resolve_next_seq_with` (:2251-2261) берёт `max(meta_seq, tail_last_seq+1)`, то есть игнорирует потерянную meta в пользу фактического хвоста; нечитаемый хвост даёт fail-closed. Автоматического копирования сегментов в каталог в коде нет (grep по `crates/ops`, `crates/recorder` — ни `fs::copy`, ни restore). Остаётся ТОЛЬКО ручное действие оператора класса TD-030 («архив вернули под старшим индексом») — реальный, один раз оплаченный класс, ради которого guard и заводился, но операторский и редкий, а не «на каждой ротации».

ОПРОВЕРГНУТО-3 — «порча ненаблюдаема при зелёном healthcheck». Частично. Любая НОВАЯ сессия на испорченном каталоге падает ГРОМКО: первый тик идёт в `SegmentCatalog::open` → Err → `?` в gateway-serve/src/lib.rs:400. Тихо деградируют только уже-тёплые сессии. Оператор узнаёт о проблеме от первого же переподключившегося клиента.

НАЙДЕНО СВЕРХ находки (сужает её): вред требует `first_seq` битого сегмента СТРОГО > 0. Условие пропуска несёт carve-out `next_first > 0` (:1830). Первый прогон, где возвращали копию `segment-00000000.jrnl` (`first_seq=0`), дал потерю РОВНО НОЛЬ (58 событий до, 58 после) при том же обойдённом guard'е. Значение оси должно называть это: «возвращён НЕ-первый сегмент».
- цена: ТЕРЯЕТСЯ: непрочитанный хвост РОВНО ОДНОГО сегмента — того, который был активным в момент возврата архива, — безвозвратно и молча, у каждой тёплой сессии. Плюс полная тишина сессии от момента порчи до ближайшей ротации.

### [L5-2] pump не транзакционен: ошибка в середине прохода фиксирует СОСТОЯНИЕ, но не КУРСОР — прод по RN-21 повторяет тик и применяет те же события второй раз

- линза: consumer-side
- место: crates/gateway/src/lib.rs:3167
- механизм: В цикле pump персистентные аккумуляторы мутируются ПОСЕОБЫТИЙНО: `self.full.apply(&event)` (:3193) и `self.vwap.sum_pv/sum_v` (:3198-3199), а `self.cursor = cursor` присваивается ТОЛЬКО после нормального выхода из цикла (:3216). Любая ошибка чтения внутри прохода уходит через `let event = event?` (:3167) — состояние уже сдвинуто, курсор нет. Кеш при этом уже сохранён ДО цикла (`self.segment_catalog = catalog_out`, :3157), т.е. переживает ошибку. Прод намеренно не рвёт соединение: `Ok(Err(boxed))` возвращает `live` обратно, пишет `tracing::error!` и делает `continue` (gateway-serve:549-565, RN-21). Через 250 мс тот же диапазон читается снова, события проходят фильтр `seq <= cursor` (курсор не сдвинулся) и применяются ВТОРОЙ раз к `self.full` и к `self.vwap`. Клиент ошибочный кадр не получил (он утерян вместе с Err), поэтому наружу это выходит не дублем сообщений, а ЗАВЫШЕННЫМИ суммами: `vwap.sum_pv/sum_v` — persistent seed КАЖДОГО последующего batch'а (:3162-3163), значит искажение уезжает во все дальнейшие кадры и не самоизлечивается до переподключения. Связь с M-62 двойная и обе стороны важны: (1) кеш ПРОДЛЕВАЕТ жизнь пути к файлу, который сессия принимает на веру между тиками, — до M-62 состав переоценивался каждый тик, теперь устаревшая запись живёт до `refresh()`; (2) замороженный этой ошибкой курсор — единственный ДОЛГОЖИВУЩИЙ прод-режим, в котором сессия читает СТАРЫЕ сегменты, то есть ровно тот режим, где Б-4 превращается из невидимой порчи кеша в реальный обрез выдачи (см. §lens).
- последовательность: тик k: сессия без чекпоинта (или с замороженным курсором) идёт полным проходом; ночной cron компакции 03:50 (`deploy/cron.d/journal-retention`, KEEP_RAW=2) в этот момент выполняет шаг 7 `fs::remove_file(src)` (:4011) над сегментом, который в кеше сессии значится СЫРЫМ (D-COMP-1). `open_next_segment` делает `File::open(&seg.path)` (:1406/1413/1417) → NotFound → `next()` отдаёт Some(Err) → pump возвращает Err. Состояние: `full`/`vwap` вобрали все события до жертвы, `self.cursor` — прежний, кеш сохранён. тик k+1 (через 250 мс): соединение живо (RN-21), `is_fresh` видит removed=[.jrnl] (а .zst уже в `file_names` с прошлого тика) → Б-4: индекс исчезает из кеша → тик проходит УСПЕШНО, но короче на один сегмент. Итог одним заходом: те же события применены дважды (завышенный vwap/объём) И события жертвы не применены ни разу (потеря), при этом клиент не видит ни ошибки, ни разрыва.
- достижимость: Окно ошибки не миллисекундное: у догоняющей сессии проход по 27 GB длится минуты, и cron компакции удаляет `.jrnl` по одному в течение всего прогона — вероятность пересечения высокая, а не «теоретическая». Второй, не требующий гонки путь — тот же, что назвал R-056: прерванная компакция оставляет `.jrnl`+`.zst` рядом на ЧАСЫ, и self-heal (:3956-3957) удаляет оригинал в произвольный момент. Третий вход в ту же ошибку — любой транзиентный I/O (EROFS/EIO/NotFound на `journal.legacy.json`), для него достаточно одного сбоя. Прод-поведение при этом задано явно и намеренно: соединение НЕ закрывается, значит повтор тика гарантирован конструкцией.

- адверсарий: ВЫЖИЛ МЕХАНИЗМ, ОПРОВЕРГНУТО ВСЁ ОСТАЛЬНОЕ: причинная цепочка, достижимость, связь с M-62, описание симптома и цена. ОПРОВЕРГНУТО 1 — ЗАЯВЛЕННЫЙ ТРИГГЕР (компакция/self-heal) НЕДОСТИЖИМ в push-цикле. Догнавшая сессия открывает 1 сегмент на установившемся такте и 2 сразу после ротации (E1: `segments_opened=1`, после ротации `=2`). Старые сегменты выброшены сегментным пропуском `stream_from_at_with_catalog` (segments.rs:1819-1836) и НЕ ОТКРЫВАЮТСЯ ВООБЩЕ: я физически снёс 15 из 16 старых сегментов у догнавшей сессии — `pump` вернул Ok. А `compact_closed_segments` (segments.rs:4045-4060) защищает активный + `keep_raw` новейших закрытых raw, и на проде `COMPACTION_KEEP_RAW=2` (deploy/bin/journal-compaction-cron.sh:40, docker-compose.yml:96). То есть компакция физически не может удалить файл, который догнавшая сессия откроет: её жертвы — индексы ≤ N−3, а сессия трогает только N и N−1. Тот же аргумент закрывает retention и self-heal (:3956-3957).

ОПРОВЕРГНУТА СВЯЗЬ С M-62 (обе половины). (1) «Кеш продлевает жизнь пути между тиками» — нет: `is_fresh` безусловно делает `scan_dir_layout` КАЖДЫЙ такт (segments.rs:259), исчезнувший файл замечен на следующем же такте; а внутритактовое окно (снимок путей при конструировании → ленивый `open_next_segment`) было ТАКИМ ЖЕ до M-62, потому что `stream_from_at`→`segments(dir)` тоже возвращал пути, а открывал их лениво тем же `EventStream`. (2) «Замороженный курсор — долгоживущий режим чтения старых сегментов» — самопротиворечиво: повреждённый фрейм не «залечивается», значит каждый такт падает на нём же и сессия молчит навсегда (это другой, более простой дефект), а транзиентная ошибка снимается следующим тактом и накопления отставания не даёт.

ЦЕНА НА ПРОДЕ — ПРЕНЕБРЕЖИМА (главное количественное опровержение). На выжившем call-site'е проход покрывает не 27 GB, а прирост за один такт. Замер E5 при 20 000 событий базы и 370 за такт дал перекос VWAP +12.3 % — и он в точности лёг на замкнутую формулу skew = [(T_pv+P_pv)/(T_v+P_v)]/[T_pv/T_v] − 1 (предсказание 1.122 против замеренных 1.1231), то есть модель провалидирована замером. Прод: активный сегмент 10.7 млн событий за ~2 ч ротации (M-57 §71) ⇒ ~370 событий на 250-мс такт, при since-genesis базе в миллионы-сотни миллионов сделок P_v/T_v ~1e-4…1e-6. Даже при 10-кратном расхождении цены такта с VWAP-с-генезиса перекос ~1e-3…1e-5 %. Заявленное «искажение уезжает во все дальнейшие кадры» формально верно, но величина ниже шума фиксированной точки.   1. **вердикт**: `warm.is_ok() == journal::list_segments(dir).is_ok()` — ловит класс B целиком, не зная, какой guard нарушен;
  2. **состав**: индексы И ПУТИ == `list_segments` (пути обязательны — развязка №1 оставляет путь на удалённый файл, ENOENT при ЗЕЛЁНЫХ 10/10 SM);
  3. **выдача**: против полного реплея **с курсором ПЕРЕД жертвой** (при курсоре у хвоста расхождение = 0 — это setup-guard, а не подразумеваемое);
  4. **бюджет**: `<= BUDGET_META` на установившемся такте (иначе «всегда refresh» проходит эквивалентность) и `>= N` на первом.

Почему он: каждая выжившая находка — экземпляр «warm ≠ cold», а (1)-(4) исчерпывают наблюдаемые различия у потребителя; не умирает на setup-guard'ах, фикс-агностичен, даёт двустороннюю анти-плацебо (`staleforever` падает на (2)/(3), `nocache` — на (4)).

**Требуют ОТДЕЛЬНОГО оракула:** G2 (позиционный инвариант — состав может быть идеален при неверном смещении); L5-2 («`pump`, вернувший `Err`, оставляет `full`/`vwap`/`cursor` как до вызова» + «молчащая сессия наблюдаема»); L3-2 (писательская гонка — `flock -n` + `create_new` на `{base}.zst.{pid}.tmp`); G3/G4 (бюджет на ПОСЛЕДОВАТЕЛЬНОСТИ, худший такт серии).

## 4. Ось изменчивости: нужна НОВАЯ

Нового значения оси 4 недостаточно — **неполон сам инвариант §4.1**.

- §4.1 — предложение **о ЦЕНЕ и только о цене**; пять осей суть его члены.
- Б-4/зеркало ещё натягиваются на ось 4 (R-056 так и сделал, для Б-4 защитимо).
- **Класс B на осях 1-5 не выражается в принципе:** событие каталога легитимно, N любое, режим установившийся, сессия одна, счётчик верен — а тёплая сессия отдаёт каталог, который холодная ОТВЕРГАЕТ. То же с G1: изменений имён ноль, значения оси 4 для него не существует.

**Рекомендация:** конъюнкция — **I1 (цена, оси 1-5 как есть)** + **I2 (правдивость): «после ЛЮБОЙ последовательности событий тёплый кеш наблюдательно эквивалентен холодному: тот же вердикт, тот же состав (индексы И пути), та же выдача»**, с **осью 6 «длина и композиция ИСТОРИИ между полными наблюдениями»**: `одно событие — ДВА такта` · `два события — один такт` · `k тактов без refresh, включая ротацию` (замерено: ротация НЕ лечит, `:278`) · `содержимое изменилось без имён` · `граница 2/2 против 3`; легитимные — `refresh обнуляет историю`, `каталог не менялся`. «Вердикт/состав/выдача» — само утверждение, не оси.

**Процедурное следствие.** Оставить всё значением оси 4 ⇒ круг **четвёртый по одному предмету** ⇒ `gates.md` §0 триггер 2, арбитр. Объявить I2 ⇒ круг 3 закрывает I1+Б-4, а I2 — **первый круг по члену инварианта, который никогда не был записан**. Набор четырежды сертифицировал ЦЕНУ и ни разу — ПРАВДИВОСТЬ.

**Блокер в тексте Условия APPROVED.** Развязка №2 («при коллизии индекса **в diff'е** уходить в `refresh()`») буквально Б-4 НЕ чинит: на такте 2 `removed=[.jrnl]`, `added=[]`, коллизии внутри дифа нет. Работает только предикат «индекс удаляемого имени ещё присутствует в `cur_names`» — сверка с ДИСКОМ. Независимое воспроизведение мерило именно эту интерпретацию, отсюда его «вариант 2 корректен». Формулировку надо привести к диску, иначе dev реализует буквальную и вернётся с тем же дефектом.

## 5. Мутант для батареи

Мутант обязан оставить инкрементальную ветку ДОСТИЖИМОЙ (`is_fresh == true`, ops в бюджете), иначе повторит `nocache` (смерть на setup-guard'е, `red_segment_meta_battery.sh:19-26`).

### Мутант 1 — `blindremove` (КЛАСС A), фикс-агностичен

Якорь уникален (`segments.rs:340`, 8 пробелов отступа; `out.sort_by_key` в `segments_counted` — другой текст). Вставить **перед** `        self.segments.sort_by_key(|s| s.index);`:

```rust
        // МУТАНТ blindremove: удаление по индексу, слепое к ВЫЖИВШИМ на диске
        for removed_name in &removed {
            if let Some(idx) = parse_segment_index_any(removed_name) {
                if !added
                    .iter()
                    .any(|a| parse_segment_index_any(a) == Some(idx))
                {
                    self.segments.retain(|s| s.index != idx);
                }
            }
        }
```

- `!added.contains(idx)` оставляет нетронутым однотактовый случай (`sm8`) — мутант не сломан сверх своей оси;
- воспроизводит семантику Б-4 и зеркала: удаление, чей индекс не переиздан В ТОМ ЖЕ ТАКТЕ, стирает живую запись;
- ноль syscall'ов ⇒ `sm2`/`sm3`/`sm6` не трогает; `sm4`/`sm5`/`sm10` не трогает;
- **kill-set: ровно `SM-11` + зеркальный сценарий** — красен ПО ИНВАРИАНТУ, а не по недостижимости предпосылки. Это закрытие N-1 из R-056.

### Мутант 2 — `noguard` (КЛАСС B), требование к ФОРМЕ фикса

Валидация вносится **одним именованным вызовом** перед `self.file_names = cur_names;` (`:341`), напр. `self.validate_like_full_path(&mut ops)?;`. Мутант — одна строка:

```
sed -i '/validate_like_full_path/d' "${TREE}/crates/journal/src/segments.rs"
```

Kill-set: только пункт (1) «вердикт». Без единой точки вызова мутация класса B неформулируема.

Цена числом: `check_first_seq_monotonic` работает над готовыми `(имя, schema_version, first_seq)` и делает **0 syscall'ов на здоровом каталоге** (§1.1) — `BUDGET_META=8` не двигает. Проверки внутри `classify_segment` стоят I/O на каждый сегмент и per-tick унаследованы быть не могут: либо ограничить их файлами из дифа, либо явно объявить пониженными в §5 + TD (G6).
