## Р-1 — Гонка за номерами артефактов: резервирование ref-пушем, но НЕ в наивной форме

### Факт

`scripts/next_artifact_id.sh` — `max+1` по `refs/remotes/origin ∪ refs/heads` (строка 27:
`refs_all()`). Между выдачей номера и push'ем носителя проходят минуты; параллельная роль
в этом окне получает ТОТ ЖЕ номер. За двое суток — пять срабатываний (`R-065` ×2,
`TD-130`/`TD-131`, `R-069`/`R-067`), одно — прямо внутри выноса вердикта (`R-068` §4bis:
номер, выданный в 22:44, занят чужим merge'ем до публикации). Барьер
`check_artifact_ids.sh` ловит всё это ПОСТФАКТУМ — работа уже сделана, файл переименовывается.

### Замер 1 — кандидат мандата в наивной форме ДЫРЯВ (no-op-дыра)

Песочница: bare-origin + два клона (`a`, `b`). Три сценария плюс одновременность:

```text
== E1: РАЗНЫЕ SHA, plain push, одно имя refs/reserved/R-100 ==
A: * [new reference]  bf95e31 -> refs/reserved/R-100        exit=0
B: hint: ... 'Note about fast-forwards' ...                  exit=1   ← отвергнут

== E2: ОДИНАКОВЫЙ SHA (вершина main), plain push, оба клона ==
A: * [new reference]  b5977c2 -> refs/reserved/R-101         exit=0
B: Everything up-to-date                                     exit=0   ← ЛОЖНЫЙ УСПЕХ

== E3: CAS --force-with-lease=refs/reserved/R-102: (ожидание отсутствия), тот же SHA ==
A: * [new reference]  -> refs/reserved/R-102                 exit=0
B: Everything up-to-date                                     exit=0   ← lease НЕ спасает:
                                    no-op обрезается клиентом ДО проверки lease

== E5: ОДНОВРЕМЕННЫЕ пуши разных SHA в одно имя (фоном, wait) ==
A exit=0 · B exit=1 · на origin ровно SHA победителя         ← сервер-сайд лок, один победитель

== E6: уборка — push-delete без force ==
- [deleted] refs/reserved/R-100                              exit=0
```

**Вывод E2/E3 опровергает конструкцию мандата в её очевидной реализации.** «`git push`
атомарен и отвергает занятый ref» — верно ТОЛЬКО для другого SHA. Типовой случай двух
параллельных ролей — обе бутстрапятся от одной вершины `origin/main`; резерв
`push origin <вершина>:refs/reserved/R-069` у ВТОРОЙ роли даёт «Everything up-to-date»,
exit 0 — обе считают резерв взятым, гонка воспроизводится в полный рост.
`--force-with-lease` с пустым ожиданием это НЕ закрывает (E3).

**Починка — уникальный SHA на резервирующего.** Бесхозный коммит без родителя от уже
существующего на origin дерева: `git commit-tree origin/main^{tree} -m "reserve <ID>
<роль> <UTC> <pid> <nonce>"`. SHA уникален по сообщению ⇒ случай «тот же SHA» недостижим
по построению, работает отклонение E1. Никаких force-флагов. Payload — один объект-коммит
(~200 байт), дерево уже на сервере.

### Замер 2 — реальный GitHub-origin ведёт себя как песочница (это надо было проверить: политика сервера ≠ семантика git)

Временный ref `refs/reserved-probe/zz-probe-…`, после замера удалён (ls-remote → 0):

```text
P1 создание:   * [new reference] bbff5aa -> refs/reserved-probe/zz-probe-…   exit=0  real 2.608s
P2 конфликт (другой SHA):  hint: ... fast-forwards ...                       exit=1  real 0.641s
P3 тот же SHA повторно:    Everything up-to-date                             exit=0  ← дыра есть и на GitHub
P5 уборка:     - [deleted]                                                   exit=0
```

### Замер 3 — сегодняшние аллокатор и барьер резервов НЕ ВИДЯТ, и это правильно оставить как есть

```text
$ git config remote.origin.fetch        → +refs/heads/*:refs/remotes/origin/*
$ git for-each-ref refs/remotes/origin refs/heads | grep reserved   → (пусто)
```

`refs/reserved/*` дефолтным fetch'ем не приезжают и в паттерны `refs_all()` обоих скриптов
не попадают. Следствия:

- **ничего не ломается** от появления резервов: ни аллокатор (78 ref'ов в скане сейчас),
  ни барьер, ни verify их не заметят;
- **чистый аллокатор трогать НЕЛЬЗЯ**: учёт резервов означал бы сеть (`ls-remote`) внутри
  `next_artifact_id.sh` — а он гоняется в шаге N `verify_M-61.sh` против независимого
  максимума. Сеть в гейте — ровно класс `TD-135` («проба меряет ОКРУЖЕНИЕ»): исход стал бы
  зависеть от доступности origin. Герметичность дороже симметрии;
- гонку закрывает **ОБЁРТКА**, а не аллокатор: резерв сам себе арбитр (CAS-петля ниже),
  знать «сколько зарезервировано» чистой выдаче не нужно.

### Замер 4 — цена

```text
push создания: 2.6 s · отклонение занятого: 0.64 s · ls-remote: 0.685 s
против самого аллокатора: 98–154 s (три точки мандата)                     → <3 %
CI-стоимость: ноль — ci.yml и deploy.yml триггерятся ТОЛЬКО branches:[main]
              (push произвольного ref'а не запускает ни одного workflow)
```

### Альтернативы, с ценой

- **(а) номер назначает диспетчер.** Работает сегодня вручную, механизм — ноль. Цена:
  человек в горячем цикле на каждый артефакт (в параллельных сессиях — десятки выдач в
  сутки), и ГЛАВНОЕ — смешение форм возвращает гонку: номер диспетчера ничем не
  зарезервирован против параллельного аллокатора. (а) работоспособен только ЦЕЛИКОМ
  (аллокатор у ролей выключен), что делает founder'а узким местом — тратой единственного
  невозобновимого ресурса (`gates.md` §0, тот же аргумент, что породил арбитра).
- **(б) статус-кво.** Измерено: 5 срабатываний / 2 суток; корпус ни разу не испорчен
  (барьер ловил всё), цена каждого — перевыдача + переименование (минуты). Цена растёт с
  параллелизмом (сегодня одновременно работают 3 клона), а случай `R-067` показал: окна
  в минуты уже достаточно.

### РЕШЕНИЕ

**(в) — резервирование CAS-пушем УНИКАЛЬНОГО SHA в `refs/reserved/<ID>`, обёрткой
`scripts/reserve_artifact_id.sh <класс>`; чистый аллокатор и барьер не меняются ни строкой.**

Конструкция обёртки (спека будущего milestone'а, не реализация):

1. `n ← bash scripts/next_artifact_id.sh <класс>` (локально, герметично, как сегодня);
2. уникальный коммит: `sha ← git commit-tree origin/main^{tree} -m "reserve <n> <роль> <UTC> <pid> <nonce>"`;
3. `git push origin "$sha:refs/reserved/<n>"` — exit 0 ⇒ резерв взят, печатаем `<n>`;
4. exit ≠ 0 ⇒ номер занят резервом соседа: `n ← max(n, номера из ls-remote 'refs/reserved/<класс>-*') + 1`,
   на шаг 2; попыток — ограниченное число, исчерпание — FAIL (fail-closed, не молчание).
5. **Уборка:** ref удаляет тот, кто приземлил носитель в `origin`
   (`git push origin :refs/reserved/<ID>` тем же ответом, что push ветки; строка в Done Block).
6. **Протухший резерв (работа брошена) НЕ удаляется автоматически:** удаление возвращает
   номер в оборот, а «брошенность» доказывается только по `branch-hygiene.md` §8 (молчание,
   не снимок). Цена хранения — пропущенный номер (§12: «разрывы не занимаются») и один
   лишний CAS-круг у следующего резервирующего. Ручной свип — по решению founder'а.
7. **Резерв необязателен.** Барьер остаётся бэкстопом для нерезервированных коллизий —
   защита эшелонируется, а не заменяется; (а) остаётся законной ручной формой (диспетчер,
   назначив номер, может взять резерв той же командой — одна строка).

Исполнение — малый milestone (номер выдаст аллокатор в момент создания файла; резервировать
номера ЗАРАНЕЕ в этом документе было бы нарушением §12): RED-проба на обёртку по образцу
`red_artifact_ids.sh` — сценарии: успешный резерв; занятость (E1); **мутант «резерв SHA
вершины вместо уникального» обязан падать на no-op-дыре (E2)** — это анти-плацебо всего
механизма; перевыдача после отклонения; уборка; fail-closed на исчерпании попыток. Проба —
на локальном bare-origin (герметично, без сети).

### Точный дифф правил (`gates.md` §12 — зона §11, коммитит носитель токена)

```diff
 Идентификатор — `КЛАСС-НОМЕР` с необязательной буквой (`M-60`, `M-60a`, `C-058b`), и он
 УНИКАЛЕН: …
 она часть идентификатора. Механизм — `scripts/check_artifact_ids.sh` + джоб `artifact-ids`.
+Под параллельные сессии номер РЕЗЕРВИРУЕТСЯ: `scripts/reserve_artifact_id.sh <класс>` —
+CAS-push УНИКАЛЬНОГО SHA в `refs/reserved/<ID>` (git отвергает второй push ДРУГОГО SHA в
+занятое имя; push ТОГО ЖЕ SHA — no-op-«успех», поэтому SHA обязан быть уникальным на
+резервирующего — бесхозный `commit-tree` с ролью и nonce). Резерв убирает приземливший
+носитель; протухший резерв не переиспользуется — номер пропускается. Резерв необязателен:
+барьер остаётся бэкстопом постфактум.
```

*(До появления обёртки дифф не вносится: правило не смеет называть механизм, которого нет —
дифф прилагается к milestone'у и коммитится вместе с его merge.)*

## Р-2 — Ретроспективный §9-круг на смерженный `docs/M-61-md-binding`

### Факт — картина полнее, чем в постановке вопроса

Постановка называет непокрытым вердиктом только `C-079`. Замер даёт больше:

```text
$ git merge-base --is-ancestor 4c2574f origin/main && echo IN   → IN (предмет в main)
$ git log --oneline -1 origin/main -- research/reviews/R-068-M-61-md-binding-recheck.md
9601f42 docs(review): R-068 — M-61 круг 5-fix, независимая перепроверка R-065 [reviewer]
```

Существует **`R-068`** — НЕЗАВИСИМАЯ вторая сессия, свежий контекст, перепроверка
ИСПОЛНЕНИЕМ, а не чтением: мутация РЕАЛЬНОГО барьера (падение ровно на `L1JSON`),
контрфакт на `origin/main` (та же мутация → 47/47 зелёных — дыра `R-063` NOTE-1
воспроизведена), батарея 28/28, block-scope/замок §11/граница C проверены (§1). По пункту
(а) §9 это покрытие СИЛЬНЕЕ среднего §9-круга; (б) покрыто.

Чего действительно НЕТ ни в `R-065`, ни в `R-068`, ни в `C-079` (grep по файлам):

1. **названной модели** — слово «Fable» встречается один раз, цитатой чужого commit-subject;
   §9 требует Fable явно и несимметричен («вердикт критика … засчитывается; обратное — НЕТ»);
2. **пункта (в)** — связность/висячие ссылки как отдельный пункт не проверялись.

Уточнение зоны: из дифа предмета в §9-зону входят только `scripts/tests/mk_ref_artifact_ids.sh`
и `scripts/tests/red_artifact_ids.sh` (харнесс). `milestones/M-61-artifact-ids.md` в списке
зоны §9 НЕ значится — нормативные секции спеки шли маршрутом критика и закрыты `C-079`
(post-merge NOTE, сам по себе долг процесса, но другой нормы).

Смягчающие факты, названные честно: предмет — барьер с тихим дефектом («не покраснеет»),
НО (i) CI гоняет пробу И батарею на каждом push (`ci.yml:200-201`) — покрытие переисполняется
непрерывно; (ii) барьер поймал четвёртую боевую коллизию прямо во время круга `R-068` (§4bis).

### Варианты

- **(а) полный ретро-круг.** Всё, что он бы исполнил, исполнено дважды независимо
  (`R-065`, `R-068`) и переисполняется CI. Полный повтор — ритуал; §9 сам воюет с подменой
  сути формой.
- **(б) записать пропуск как принятый долг.** Долг без закрывающего действия — шум; долг
  С действием («проверить (в)») — это отложенный узкий круг, а отложенный аудит барьера с
  тихим дефектом — худшая из форм.
- **(в) амнистия, §9 вперёд-смотрящий.** Прецедентно ядовита: §9 рождён тремя находками за
  один день 11.08 ровно на «очевидных» пропусках; амнистия учит будущие сессии, что
  смерженное непроверяемо. Отвергается сильнее всего.

### РЕШЕНИЕ — (а) в УЗКОЙ форме: круг проводится, его предмет — ДЕЛЬТА, не повтор

Чтобы круг не был ритуалом, он делает ТОЛЬКО непокрытое:

1. **(в) связность на дереве `main`:** ссылки трёх вердиктов и спеки живы (`C-079`/`R-065`/
   `R-068` цитируют строки `M-61-artifact-ids.md` и скриптов — сверить, что адресаты
   разрешаются в `main`); сверка СПЕКА⇄МАНИФЕСТ уже механизирована — прогнать
   `red_artifact_ids.sh` и предъявить строку;
2. **один якорь ре-экзекуции** (не пересдача): `red_artifact_ids.sh --battery` на `main` —
   `mdblind → уронил ровно L1JSON` (подтверждает, что покрытие, на которое ссылаются
   R-065/R-068, живо в текущем дереве, а не было живо тогда);
3. **вердикт-файл `research/reviews/R-NNN` с НАЗВАННОЙ моделью** (`[fable-recheck]` в
   subject), номер — аллокатором в момент создания; вердикт вправе ЗАСЧИТАТЬ `R-068` по
   пунктам (а)/(б) со ссылкой на его замеры — пересдача не требуется, требуется СУЖДЕНИЕ
   о покрытии, подписанное той моделью и той свежестью, которых требует §9.

Цена: один запуск Fable-клона, меньше часа. Не-ритуальность предъявима: у круга есть
непокрытый предмет ((в) + атрибуция модели), и только он и делается.

**Почему не «зачесть `R-068` решением architect'а и закрыть»:** §9 называет условие зачёта
(критик на сильной модели, покрывший (а)–(в)) и прямо говорит «обратное неверно». `R-068` —
reviewer без названной модели и без (в). Расширять исключение §9 своим решением — значит
судить норму, в которой architect сторона (пропуск круга — его).

**Прецедент-граница (обязана быть названа, иначе ретро-круги станут нормой):** ретро-круг —
исключение, оправданное тем, что гейт рассыпался диспетчерской коллизией двух живых
reviewer-сессий (`R-068` §3: merge удержан, close-out передан) — а не новая норма
«проверим после merge». Правки правил НЕ требуется: §9 уже говорит всё нужное, отказ (в)
был исполнительским, не нормативным.

## Р-4 — Деплой-модель: упавший деплой не добирается никем (`П-008` п.3)

### Факт — три эпизода, все добраны рукой, процедура нигде не записана

```text
$ gh run list --workflow=deploy.yml … (событие / исход / SHA)
2026-08-14T12:13Z  workflow_dispatch  success  c6c62b8   ← добор рукой, ~13 ч спустя
2026-08-13T23:19Z  push               failure  d564617   ← merge M-62; CI красен (TD-135)
2026-08-08T23:08Z  workflow_dispatch  success  650f22d   ← добор рукой, ~32 ч спустя
2026-08-07T15:21Z  push               failure  710b1ad   ← merge M-57
2026-08-03T13:50Z  workflow_dispatch  success  e8d039e   ← добор рукой (после гонки TD-086)
2026-08-03T09:02–09:16Z  push ×4      failure            ← гонка деплоев, TD-086
```

Прод в окно 13–14.08 жил на сборке от деплоя 08.08 (`650f22d`) при 12 кодовых коммитах
M-62, лежащих в `main`.

### Диагноз — дыра структурная, а не «агент забыл»

1. **Фильтр путей `deploy.yml` смотрит не туда, куда падает фикс.** Деплой триггерится
   push'ем по кодовым путям (`crates/**`, `Cargo.*`, …, `!crates/*/tests/**`). Красный CI
   на кодовом merge'е блокирует деплой fail-closed (верно). Но фикс, делающий CI зелёным,
   кодовых путей часто не трогает — фикс `TD-135` лежал в `scripts/tests/**`, который
   фильтром ИСКЛЮЧЁН, — его push деплой не триггерит, а упавший ран сам не перезапускается.
   **Никакой пуш в этой цепочке не обязан был выпустить прод — класс «наблюдается сбой, не
   наблюдается ОТСУТСТВИЕ»** (`testing.md`, свойство 4).
2. **§8 адресует не того агента.** «Дождаться CI+Deploy» обязан ПУШЕР — но пушер красного
   merge'а и автор зелёного фикса — разные агенты в разных сессиях; между ними обязанность
   не передаётся ничем.
3. **Сторожа свежести не существует** (grep по `crates/ops/`, `scripts/watchdog_cron.sh` —
   пусто): ops-watchdog смотрит heartbeat/журнал/диск, но не «VPS отстал от `main`».
   Telegram-транспорт к тому же без токена (`П-003`) — no-op.
4. **Блокировать нечем** (`TD-124`: branch protection 403) — контур предупреждающий.
   > **СНЯТО 2026-08-15** (пометка, а не переписывание: документ — датированный журнал решений).
   > Репозиторий переведён в public, защита `main` включена, `docs-freeze` входит в
   > обязательный агрегат `All checks passed` — контур стал барьерным (`R-085` N-5).

### Варианты

- **(а) записать текущую модель нормой.** Необходимо (процедура должна существовать
  текстом), но НЕ достаточно: измеренная эффективность текста-в-правилах на дисциплине
  исполнения — ноль (замер аудита 13.08, `SESSION-HANDOFF` §0bis); оба поздних эпизода
  случились при живом §8 п.1.
- **(б) сторож-алерт** (schedule-джоб, красный при «кодовая вершина `main` не задеплоена
  при зелёном CI»). Наблюдает отсутствие, но красный джоб в Actions никто не смотрит —
  это та же слепота, что сейчас; Telegram — no-op без токена.
- **(в) catch-up деплой:** триггер `workflow_run` на завершение CI (`main`, `success`) +
  условие «между SHA на VPS и вершиной `main` есть кодовая дельта» → тот же деплой-скрипт.
  Убирает класс ПО ПОСТРОЕНИЮ: выпуск перестаёт зависеть от того, КАКОЙ push сделал CI
  зелёным.

### Анализ (в) — почему он безопасен и что в нём обязано быть запрещено

- **Частота рестартов рекордера не растёт** (каждый деплой = гэп forward-only записи,
  `TD-086`): catch-up срабатывает только когда кодовая вершина ДОЛЖНА быть выкачена и не
  выкачена — сегодняшний push-триггер при этом можно снять вовсе: «деплой по факту
  зелёного CI» строго корректнее «деплоя по факту пуша» и попутно убирает 20-минутный
  polling-гейт с его таймаут-фейлом.
- **Fail-closed сохраняется и УТОЧНЯЕТСЯ:** авто-добор — только для класса «деплой не
  СТАРТОВАЛ» (CI-гейт красен / фильтр путей). Деплой, уже УПАВШИЙ на VPS-шаге для той же
  вершины, повторно автоматом НЕ добирается (авто-ретрай детерминированной ошибки молотил
  бы прод rollback-циклами на каждый docs-push) — там остаётся человек и §8 «немедленный
  фикс или revert». Различитель реализуем: `gh api` по последнему Deploy-рану этой вершины
  (permissions `actions: read` уже выданы, `TD-018`).
- **`concurrency: deploy-main, cancel-in-progress: false` сохраняется** — защита от гонки
  деплоев (`TD-086`) распространяется и на catch-up.
- **Совместимость с открытым `П-008` п.3:** выбор founder'а «пуш-деплой vs явный промоушен»
  НЕ предрешается. Catch-up — механизм доставки согласованного состояния; при переходе на
  промоушен меняется определение «что должно быть на VPS» (promoted SHA вместо вершины
  `main`), сам механизм остаётся тем же.

### РЕШЕНИЕ — (а)+(в): норма записывается сейчас, механизм — milestone'ом

**Норма** (дифф ниже): добор — явная обязанность агента, чей коммит сделал CI на `main`
зелёным; пруф в close-out. **Механизм**: milestone «deploy catch-up» — `workflow_run`-триггер
+ страж дельты; RED-first по `testing.md` §«Механизм несущего пути»: оракул точки входа
(состав шагов, условие дельты, различитель «не стартовал/упал» — проверяемы локально;
сам `workflow_run` — прод-формой в CI). Спека обязана нести запретный список: не трогать
rollback-ветку, не ослаблять fail-closed CI-гейт, не менять `concurrency`, не расширять
права `GITHUB_TOKEN`. `deploy.yml` — зона §9 (харнесс), НЕ §11: правка идёт обычным
маршрутом с Fable-перепроверкой, токена не требует.

### Точный дифф правил (`gates.md` §8 п.1 — зона §11, коммитит носитель токена)

```diff
 1. **Дождаться CI + Deploy** до терминального статуса (`gh run watch <id> --exit-status`).
    Красный → немедленный фикс или revert; milestone не закрывается поверх красного прода.
+   **Непроизошедший деплой ДОБИРАЕТСЯ явно** (замер 14.08: три эпизода — 03.08, 07–08.08,
+   13–14.08, — каждый добран ручным `workflow_dispatch`, нигде не записанным): как только
+   CI на `main` снова зелёный, агент, чей коммит сделал его зелёным, запускает
+   `gh workflow run deploy.yml --ref main` и проходит п.1–3 заново — фильтр путей
+   `deploy.yml` его фикс-коммит не триггерит, если фикс лежал вне кодовых путей (случай
+   TD-135: фикс в `scripts/tests/**`). Кодовая вершина `main`, не доехавшая до VPS при
+   зелёном CI, — КРАСНОЕ состояние гейта, а не «деплоя просто не было». Пруф в close-out:
+   строка `gh run list` с `workflow_dispatch … success` + ssh-проверка п.2.
```
