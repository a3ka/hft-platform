# Инвентаризация контрактного слоя einhard-runtime + план переноса

STATUS: research/inventory (не design, не RFC). Автор: инженер-исследователь, 2026-07-31.
Объект: `~/einhard-runtime/contracts/` (read-only; ~923 MB на диске, из них подавляющая
масса — `node_modules/` + `rust/target/` + `.pytest_cache/`, **не** сами схемы — фактических
`*.schema.json` файлов **38**, не 486; расхождение с брифом фиксирую как факт, не «нашёл
486 и не показываю» — вероятно, 486 включает `.audit-allow-list.txt`/тестовые фикстуры RFC
из других модулей монорепо вне `contracts/`, я это не проверял за пределами `contracts/`).
Три языка подтверждены: JSON Schema (канон) → Python (`python/`) + TypeScript (`typescript/`)
+ Rust (`rust/`, дата модификации свежее остальных — самый новый биндинг).

## 1. Как устроено у них

### 1.1 Структура пакета

Корень `contracts/`: `README.md`, `CLAUDE.md` (frontmatter говорит «устарел, но сохранён
для контекста» — реальные правила теперь в `.claude/agents/architect.md` +
`.claude/modules/contracts.md` + `.claude/rules/contract-governance.md`, т.е. правила
**мигрировали из README самого пакета в agent-инфраструктуру монорепо** — важный сигнал:
контрактный слой воспринимается не как «ещё один крейт», а как governance-объект со своей
персоной-владельцем), `CHANGELOG.md` (959 KB текста, одна секция на RFC, `## Unreleased —
RFC-NNN <slug> — vX.Y.Z`), `pyproject.toml` + `package.json` (версия пакета **единая**,
`0.10.0`, синхронно бампается в обоих — т.е. весь пакет versioned целиком, не отдельные
схемы), `docs/governance.md` (959 строк — единственный источник правды по процессу),
`docs/rfcs/` (22 файла, `RFC-NNN-<slug>.md`, включая `RFC-000-reorg-...md` — миграционный).

Схемы разложены по доменам `schemas/<domain>/<name>.schema.json` — **один тип на файл**
(жёсткое правило governance §4: «no bundled multi-type files»). Фактические домены:
`degradation/`, `evidence/`, `integration/`, `mission/`, `navigation/`, `replay/`, `swarm/`,
`trust/` (README у них **устарел** — перечисляет старые `core/navigation/evidence/swarm/
operator/`, реальность разошлась; сам README это не признаёт — везде документация отстаёт
от кода, у них тоже). Каждый домен имеет свой `README.md` внутри `schemas/<domain>/`.

### 1.2 Генерация кода

**Направление генерации — ОБРАТНОЕ нашему.** У них канон — JSON Schema, из неё генерируются
и Python, и TypeScript, и Rust. У нас канон — Rust-типы (`schemars`), из них генерируется
JSON Schema. Это не деталь, а инверсия архитектуры — см. §3 «Риски».

- `scripts/generate_typescript.sh` — гоняет `json2ts` (`json-schema-to-typescript`, npm-пакет)
  по каждому `schemas/*/*.schema.json`, входя в директорию схемы (чтобы относительные `$ref`
  резолвились), пишет `typescript/src/generated/<name>.ts`, затем **перегенерирует целиком**
  `typescript/src/index.ts` (ре-экспорты) — этот файл каждый раз переписывается скриптом
  ЦЕЛИКОМ (не патчится), список экспортов **хардкожен внутри bash-скрипта** через heredoc:
  ```bash
  cat > typescript/src/index.ts <<'EOF'
  export type { NavState } from "./generated/nav_state.js";
  ...
  EOF
  ```
  т.е. добавление нового типа в реэкспорт — ручной шаг после генерации, не автоматический
  discovery. Затем `npx tsc --noEmit` для проверки, что сгенерированное компилируется.

- `scripts/generate_rust.sh` — Python-подскрипт (embedded heredoc) обходит те же схемы,
  инлайнит `$ref` (сплющивает внешние ссылки в один файл — Rust-биндинг не поддерживает
  runtime-резолюцию `$ref`), рендерит на каждый файл `rust/src/generated/<name>.rs` с:
  `pub const <NAME>_SCHEMA: &str` (сырой JSON как строка), `SchemaValidator` (обёртка над
  `jsonschema::JSONSchema`, компилируется лениво через `OnceLock`), `pub static <NAME>_VALIDATOR`.
  То есть Rust-биндинг здесь — **не native struct**, а строка JSON + рантайм-валидатор
  (`jsonschema` крейт компилирует Draft 2020-12 в рантайме) — там, где Python и TS дают
  типизированные структуры/интерфейсы, Rust у них даёт validate-by-schema, а не
  deserialize-into-struct. Это осознанный выбор (см. governance §1: «classes encode
  behavior», схема — единственная каноническая форма; Rust struct с `serde` считался бы
  «ещё одним классом»).

- Проверка «сгенерированное == закоммиченное»: **да, есть, и это отдельный гейт**:
  `scripts/verify_ts_in_sync.sh` — копирует текущий `typescript/src/generated/` во
  временную директорию, перегенерирует, `diff -rq` против снапшота, FAIL если разошлось.
  Для Rust — судя по `rust-bindings.yml` CI, эквивалентного `verify_rust_in_sync.sh` **нет**:
  CI лишь `cargo check`/`build`/`test` сгенерированного кода, но не проверяет, что
  закоммиченный `.rs` совпадает с тем, что выдаст `generate_rust.sh` сейчас (разрыв в их
  собственной дисциплине — TS отдельно защищена, Rust — нет).

### 1.3 Фикстуры

`fixtures/<domain>/<name>/{valid,invalid}/*.json` — 96 файлов, зеркалит структуру `schemas/`.
Правило (мандаторное, `verify_atomic_schema_change.py` проверяет за CI): каждый новый/
изменённый тип обязан иметь `valid/canonical.json` **и минимум один** `invalid/<reason>.json`
(например `missing_required_field.json`). Используются `tests/test_schema_validation.py`
(Python — валидирует `valid/` против `<X>_VALIDATOR`, ожидает reject на `invalid/`) — язык
явно один (Python/pytest), TS/Rust фикстуры **не гоняют отдельно** (TS проверяется на уровне
`tsc --noEmit` компиляции сгенерированных типов, не на runtime-валидации фикстур; Rust —
через собственные `rust/tests/`, но состав/полнота не подтверждена в рамках этого просмотра
— файлы `rust/tests/data/` существуют, не читал их содержимое детально).

### 1.4 Проверка датафлоу — самое интересное, как просили

`scripts/generate_dataflow.py` (~150 строк) читает **аннотации внутри самих схем**:
каждый `*.schema.json` обязан нести `x-einhard-producer` (dotted module ID, например
`runtime.navigation`), `x-einhard-consumers` (список module ID), `x-einhard-frequency`,
`x-einhard-channel`. Скрипт собирает эти рёбра (`producer → consumer`, подписано именем
схемы) со ВСЕХ схем и рендерит Mermaid-граф (`graph LR`) в `docs/dataflow/dataflow.mmd`,
плюс параллельно `generate_architecture_map.py` строит `docs/architecture-map.md`.

Ключевой механизм — `scripts/verify_dataflow_in_sync.sh`: **регенерирует оба артефакта из
текущих схем и делает `git diff --stat` против закоммиченной версии; FAIL при любом diff.**
Это НЕ проверка корректности графа — это проверка того, что **никто не поменял
`x-einhard-producer/consumers` в схеме и забыл перегенерировать документ**. Механизм тот же,
что `verify_ts_in_sync.sh` (§1.2), только выход — не код, а документация датафлоу. Именно
это founder называет «датафлоу жёстко зависит от контрактов»: датафлоу-диаграмма не
рисуется руками НИКОГДА — она **производная функция от аннотаций в схемах**, и CI не даёт
ей разойтись с источником (governance §19, «atomic-PR rule»: PR, меняющий producer/consumer
аннотацию, обязан в ТОМ ЖЕ PR нести перегенерированный `dataflow.mmd`).

Практическое следствие: у них НЕЛЬЗЯ добавить консюмера типа без объявления этого в самой
схеме — граф зависимостей модулей монорепо не поддерживается отдельно вручную, он
**вычисляется** из `contracts/`. Это единственное место, где у них реально «два продукта,
если говорят, — говорят через типы отсюда»: сама возможность появления нового ребра в графе
физически проходит через правку JSON Schema файла.

### 1.5 Дисциплина изменений

Три уровня машинных проверок поверх изменения схемы:

1. **`lint_schemas.py`** — статические правила формы (запускается на КАЖДОЙ схеме, не на
   диффе): dialect == Draft 2020-12, `snake_case` свойства, нетривиальный `description`
   на каждом поле, `additionalProperties: false` по умолчанию (opt-out только через
   `x-allow-additional: true` — явный флаг, не тихий пропуск), формат `$id`, обязательные
   `x-einhard-*` аннотации (см. §1.4) + жёсткий формат dotted module ID (regex), плюс
   **доменные канонические типы (§4d governance)**: `timestamp` должен быть `int64 ms`
   (запрещены суффиксы `_sec`/`_posix`), lat/lon — WGS84 с фиксированными `minimum`/
   `maximum`, altitude — WGS84 ellipsoidal (АМSL **запрещён по имени поля** — `alt_msl`
   ловится и FAIL'ится), heading — nullable `[0, 360)`, бинарь — обязан быть
   `contentEncoding: base64`. Это доменные инварианты конкретно ИХ предметной области
   (авиация/навигация) — переносить их бессмысленно, но **механизм** («канонические типы —
   не соглашение, а лint-проверяемое правило с regex на имя поля») переносим.

2. **`diff_schemas.py <base_ref> [<head_ref>]`** — классифицирует изменение схемы между
   двумя git-ref как `additive`/`breaking`/`none`: удалённая схема/поле → breaking; новое
   required-поле у существующего свойства → breaking; сужение `enum`/`minimum`/`maximum` →
   breaking; `additionalProperties: true→false` → breaking; всё остальное — additive. Это
   **чистая функция над двумя JSON-снапшотами схемы через `git show`**, без внешних
   зависимостей — легко переносимый паттерн.

3. **`verify_atomic_schema_change.py --pr-root <dir>`** — самый строгий гейт: проверяет,
   что PR, трогающий `schemas/`, содержит ВСЕ 7 обязательных артефактов одним пакетом:
   RFC-документ (`docs/rfcs/RFC-NNN-*.md` с обязательным YAML frontmatter — `producer`,
   `consumers` (список, не плейсхолдер `TBD`/`@TBD`/пусто — отдельная проверка
   `5c-speculative` REJECT'ит спекулятивные RFC без реальных консюмеров), `target_version`);
   изменение `.schema.json`; обновление `tests/test_schema_validation.py`; `valid/
   canonical.json`; `invalid/<reason>.json`; обновление Python-биндинга (проверяет ПО ИМЕНИ
   константы — `<STEM>_SCHEMA`/`<STEM>_VALIDATOR` строкой должны встречаться в
   `__init__.py`, не просто «файл тронут»); `CHANGELOG.md` с секцией `Unreleased`. Модуль
   написан в чисто-функциональном стиле (`RfcPrState` — frozen dataclass, `_check_5b_*`
   функции без побочных эффектов над иммутабельным состоянием) — сознательный архитектурный
   выбор, тестируемость гейта: у них есть `tests/fixtures/atomic_rfc/{good_pr_v1,
   bad_pr_missing_*}/` — синтетические PR-фикстуры, доказывающие, что каждый недостающий
   артефакт РЕАЛЬНО ловится гейтом (анти-плацебо для самого гейта, тот же принцип, что наш
   `.claude/rules/testing.md`).

4. **`verify_version_bump.py <base_ref>`** — если `schemas/` изменились, `pyproject.toml`
   версия ОБЯЗАНА измениться (сравнение строкой через `git show <ref>:pyproject.toml`);
   не проверяет, что это ИМЕННО правильный уровень бампа (major/minor) — это отдельно
   полагается на человека/reviewer через commit-prefix `BREAKING:` — т.е. автоматика ловит
   «забыли бампнуть», но не «бампнули не туда».

### 1.6 CI-интеграция

`.github/workflows/smoke.yml` — центральный gate-файл монорепо (Phase 3.5→7.2, накопил много
комментариев про TD-*). Внутри job `schema-lint` (path-filtered, срабатывает при изменении
`contracts/**`): `python3 contracts/scripts/lint_schemas.py` → `bash
contracts/scripts/verify_dataflow_in_sync.sh`. Отдельный job (не увидел его целиком в срезе,
но виден заголовок) `atomic-rfc-pr-lint`. Отдельные workflow-файлы: `rust-bindings.yml`
(триггерится на изменение `contracts/rust/**` ИЛИ `contracts/schemas/**` ИЛИ
`contracts/scripts/generate_rust.sh` — path-filter привязан к тройке источник/генератор/
выход; `cargo check`+`build`+`test`+повторный `test --features libsodium`), плюс отдельные
Rust-CI-лейны для каждого КОНСЮМЕРА биндинга (`orchestration-rust.yml`,
`tak-cot-rust.yml` — каждый триггерится в том числе на `contracts/rust/**`, т.е. правка
контракта automatически перезапускает CI смежных модулей). Примечательный комментарий в
`smoke.yml`: branch protection физически недоступен (GitHub Free план) — гейты работают, но
не принудительны как required-check; они держатся дисциплиной, не платформой. **Урок:
CI-гейт без repo-enforced required-status — это тоже реальный (хотя и более слабый) гейт,
если культура его соблюдает; но founder явно пометил это как известный технический долг у
себя (`TD-MIG-PROTECT`), не выдавал за полное решение.**

## 3. План переноса (приоритизировано: эффект / стоимость)

Порядок — от «дешёвого и закрывающего уже найденный долг» к «дорогому и упреждающему».

### П1 — Закрыть CT-RFC-05 retro-doc (не перенос механизма, а немедленное применение найденного здесь принципа §1.5.3)
Не про перенос из einhard — это независимо уже в `TECH-DEBT.md`/`plan-design-migration.md`
Б2.3. Упоминаю, потому что einhard's `verify_atomic_schema_change.py` — это ИМЕННО тот
гейт, который **не позволил бы** CT-RFC-05 попасть в код без документа. Наибольший
непосредственный эффект — не копия их скрипта, а факт: у нас нет машинного аналога,
поэтому такой разрыв (код есть, документа нет) прошёл все гейты и был найден только
ретроспективно critic'ом/reviewer'ом. Это довод «за» пункт П2 ниже, не отдельная задача
переноса.

### П2 — `diff_schemas.py`-аналог: additive/breaking классификатор для наших JSON Schema (высокий эффект, низкая стоимость)
Наша JSON Schema генерируется `schemars` в `crates/contracts/schema/*.json` — уже git-
отслеживаемый артефакт. Перенос: чистая функция (Python или небольшой Rust-бинарь),
сравнивающая `schema/*.json` между `<base_ref>` и `HEAD` тем же алгоритмом (removed
property/schema → breaking; new required на существующем поле → breaking; enum сужение →
breaking; всё остальное → additive). **Адаптация:** у нас breaking-changes и так должны
сопровождаться bump'ом `SCHEMA_VERSION` (счётчик эпох, не semver) — скрипт может выдавать
не «git-ref класс», а прямую проверку «если диф breaking, `SCHEMA_VERSION` в HEAD обязан
быть больше, чем в base_ref» — это сильнее, чем у einhard (у них `verify_version_bump.py`
проверяет ЛЮБОЙ бамп при ЛЮБОМ изменении школы, не связывая класс изменения с уровнем
бампа). **Не переносим:** их доменные §4d правила (lat/lon/heading/alt WGS84) — не наша
предметная область.

### П3 — Атомарный RFC-гейт (`verify_atomic_schema_change.py`-аналог) — высокий эффект, средняя стоимость
Формализовать словесное правило `docs/05-contract-layer.md` §4 (7 пунктов в одном PR) как
скрипт `scripts/verify_ct_rfc_atomic.sh`/`.py`, проверяющий по факту диффа PR-а, трогающего
`crates/contracts/**`: (1) есть `docs/rfc/CT-RFC-NNN-*.md`; (2) правка `src/lib.rs`
Т1-типов; (3) правка/регенерация `schema/*.json`; (4) правка `CHANGELOG.md` с записью;
(5) ≥1 valid + ≥1 invalid фикстура на изменённый вариант; (6) ≥1 тест, ссылающийся на новую
форму. **Адаптация:** у нас нет отдельного Python-биндинга для проверки экспортов по имени
константы (§1.5.3 п.6 у них) — вместо этого можно проверять, что `SCHEMA_VERSION` bump
присутствует при breaking (переиспользует П2). Их приём «good/bad PR синтетические
фикстуры, доказывающие, что каждый недостающий артефакт реально ловится» — переносим как
методологию тестирования САМОГО гейта, это прямое применение нашего же анти-плацебо
принципа (`.claude/rules/testing.md`) к скрипту гейта, которого у нас пока просто нет.

### П4 — `verify_contracts.sh` — реализовать обещанное (высокий эффект, средняя стоимость, УЖЕ ОБЕЩАНО)
`docs/05-contract-layer.md` §5 явно обещает этот файл («Гейт паритета: `verify_contracts.sh`
— Rust-типы ↔ JSON Schema ↔ фикстуры согласованы; роундтрип-тест сериализации»), но
`scripts/verify_contracts.sh` **не существует**. У einhard прямого аналога тоже нет для
Rust (только для TS — `verify_ts_in_sync.sh`), но принцип регенерируй-и-diff (§1.2, §1.4)
прямо переносим: `cargo run --example gen_schema` (уже существует —
`crates/contracts/examples/gen_schema.rs`) → сравнить вывод с закоммиченным `schema/*.json`
через `diff`. Это дешевле, чем кажется — генератор уже есть, не хватает только обёртки
«прогнать и сравнить» + место в CI. Наибольшая практическая ценность из всего списка,
потому что закрывает разрыв, который уже задокументирован как обещание, но не выполнен.

### П5 — Датафлоу-как-производная (высокий стратегический эффект founder'у, дорого, делать ПОСЛЕ П2-П4)
Это то, что founder называет «жёсткая зависимость». Перенос: (a) добавить в JSON Schema
T1-типов аннотации-эквивалент `x-einhard-producer`/`x-einhard-consumers` (у нас это уже ЕСТЬ
как текст в таблице `docs/fa/contracts.md` §5 и `05-contract-layer.md` §2 — перенос
означает переместить эту информацию ИЗ прозы В машинно-читаемые поля схемы, скорее всего
через `schemars`-атрибуты на Rust-типах, раз канон — Rust, не JSON Schema напрямую, как у
einhard); (b) генератор `docs/dataflow.mmd`/аналог из этих аннотаций; (c) verify-скрипт
regenerate+diff. **Почему не П1-приоритет:** у нас пока 2 продюсера/консюмера (движок +
research-cli/деск), не N модулей монорепо — граф тривиален и рисуется руками без потери
точности при текущем масштабе. Ценность механизма растёт с числом консюмеров; она станет
реальной ПОСЛЕ появления TS-фронта (Next.js) — тогда граф перестанет быть тривиальным.
Рекомендация: не делать сейчас, но зафиксировать как «готовим почву» — если Т1-типы уже
получат producer/consumer поля в П2-П4 работе, П5 станет дешёвым довеском, а не отдельным
проектом.

### П6 — TS-генератор (по брифу — фронт Next.js «появится») — средний эффект сейчас, станет высоким
`generate_typescript.sh` — прямой перенос паттерна (`json-schema-to-typescript`/`json2ts`
npm-пакет, тот же генератор) поверх УЖЕ существующих `crates/contracts/schema/*.json`.
**Отличие:** у einhard TS — консюмер JSON Schema (та же схема, что Python/Rust). У нас
JSON Schema — уже производная от Rust; TS будет консюмером производной, не канона
напрямую — тройная цепочка Rust→Schema→TS вместо их прямой Schema→{Python,TS,Rust}. Не
проблема, но три уровня трансляции = три места для рассинхрона; `verify_ts_in_sync.sh`-
аналог (regenerate+diff) становится ОБЯЗАТЕЛЕН с первого дня TS-кода, не «добавим потом».
**Делать только когда Next.js реально стартует** — раньше нет консюмера, нечего верифицировать.

### Явно НЕ переносим (и почему)
- **Три-язычный build (`node_modules` 923MB, `pyproject.toml`+`package.json` пакет)** —
  бриф это и так исключил («923 MB не нужны»); наш пакет — Rust workspace crate, не
  отдельно версionируемый npm/pip пакет; syncing двух версий полей (`version` в
  `pyproject.toml`/`package.json`) не применимо, пока у нас нет отдельно паблишащегося
  пакета контрактов.
- **`x-einhard-*` доменные §4d канонические типы (lat/lon/heading/alt/CEP)** — их
  предметная область (навигация/дроны), не наша (финансы/ордербук). Механизм «доменные
  канонические поля — лint-проверяемое правило по regex имени, не соглашение в голове» —
  ценность, сами regex — нет.
- **T-B behavioral contracts registry (§2bis governance)** — решает проблему N≥2
  ИСПОЛНИТЕЛЕЙ одного алгоритма на разных языковых рантаймах (например, canonical-JSON
  подпись, которую и Python, и Rust, и TS обязаны посчитать байт-в-байт одинаково). У нас
  пока один исполнитель (Rust) для всей торговой логики; когда/если появится второй
  runtime, реально исполняющий тот же алгоритм (не просто читающий готовый результат) —
  тогда это станет актуально. Пока — over-engineering.
- **Core-architect как отдельная персона/агент, физически отделённая от project architect**
  — у einhard это буквально другой субагент с другим `CLAUDE.md`, не имеющий доступа
  писать вне `contracts/`. У нас это уже РЕАЛИЗОВАНО другим механизмом: `crates/contracts/**`
  — architect-only по `.claude/rules/scope-guard.md` (SACRED), без необходимости заводить
  отдельного «core-architect» агента — один architect уже единственный, кто пишет T1.
  Дублировать персону не нужно, инвариант уже держится другим способом.

## 4. Риски и несоответствия

**Инверсия направления генерации — главный несовместимый момент.** У einhard JSON Schema
— рукописный канон (человек пишет `.schema.json` напрямую, RFC материализуется как правка
схемы). У нас канон — Rust-типы, JSON Schema — производная (`schemars`, `examples/
gen_schema.rs`). Это значит: их `lint_schemas.py` (snake_case, description-обязателен,
`additionalProperties: false`) бессмысленно переносить как есть — эти инварианты у нас
либо гарантируются Rust-типом по построению (нет "лишнего" поля, `#[serde(deny_unknown_
fields)]` — тот же эффект, что `additionalProperties: false`, но выражен в другом слое),
либо должны проверяться на **сгенерированной** схеме, а не служить источником правки. Их
`verify_atomic_schema_change.py` тоже нужно адаптировать: у них RFC = правка `.schema.json`
+ derived-биндинги; у нас RFC = правка `.rs` + derived-схема. Артефакт №2 в их списке
(«изменение `.schema.json`») у нас — не то, что редактируется вручную, а то, что
**регенерируется** и коммитится — проверка гейта должна требовать «схема регенерирована и
совпадает с тем, что выдаёт `gen_schema` example», а не «схема правлена человеком».

**Генератор Rust у einhard не type-safe (validate-by-schema, не deserialize-into-struct)
— это НЕ модель, которую нам стоит копировать.** У нас Rust уже канон и уже typed —
переносить их подход (JSON-строка + рантайм-`jsonschema`-валидатор вместо структуры) было
бы шагом НАЗАД по типобезопасности. Единственное, что стоит взять — паттерн `OnceLock`
lazy-compile для ВАЛИДАТОРА Python/TS-стороны читателей журнала (research-tooling), не для
Rust-стороны движка.

**Масштаб governance-документа не соразмерен.** `docs/governance.md` — 959 строк, накопил
несколько «Phase N update» слоёв истории переименований (aletheia→einhard), что сделало
документ трудным для чтения (сам документ честно об этом пишет в шапке). Наш
`05-contract-layer.md` на порядок компактнее — это преимущество, не недостаток; при
переносе механизмов НЕ стоит копировать структуру документа, только исполняемые скрипты и
конкретные проверяемые правила.

**CI required-status недоступен на их стороне (GitHub Free), у нас — не проверял в рамках
этой задачи**, но если аналогичное ограничение есть — все верификации из §3 остаются
полезны локально/в `verify_M-NN.sh`, даже без repo-enforced branch protection; ценность
гейта не обнуляется отсутствием принудительности на уровне платформы, но дисциплина должна
компенсировать явно (как и у них помечено TD).

**Fixture-организация по домену/типу vs по файлу.** Их `fixtures/<domain>/<name>/{valid,
invalid}/` даёт 1:1 маппинг тип↔директория, что упрощает машинную проверку «есть ли у
каждого типа обе фикстуры». Наша плоская `fixtures/{valid,invalid}/*.json` (имя файла =
тип+вариант) тоже проверяема, но потребует явного соглашения по именованию файлов, если
П3/П4 будут автоматически сверять «на каждый вариант T1-enum есть валидная+невалидная
фикстура» — сейчас это соглашение неформальное.

## 5. Открытые вопросы к architect'у

1. **П2/П3 (additive/breaking классификатор + атомарный RFC-гейт) — Python или Rust?**
   einhard пишет их на Python (независимо от языка канона — у них это тоже несоответствие,
   т.к. Python не канон нигде в их системе, просто исторически tooling-язык). У нас weight
   склоняется к Rust (единый язык, cargo test инфраструктура уже есть) или к bash+jq для
   простоты — нужно архитектурное решение по tooling-языку для `scripts/verify_*`, которое
   пока не зафиксировано явно нигде в докс.

2. **`SCHEMA_VERSION`-счётчик эпох vs bump-требование при breaking — формализовать как RED-
   тест или как скрипт-гейт?** У einhard это `verify_version_bump.py`, отдельный скрипт;
   у нас частично уже живёт как sacred-тест (`red_rfc04.rs::schema_epoch_tripwire`,
   `ct_rfc05.rs` содержит `assert_eq!(SCHEMA_VERSION, 4, ...)`). Нужно решение: продолжать
   класть эту проверку в Rust sacred-тесты (уже устоявшийся паттерн, TD-031 упомянут) или
   вынести в отдельный внешний verify-скрипт, дублирующий их `diff_schemas.py`-подход —
   дублирование логики в двух местах или единая точка правды?

3. **Producer/consumer-аннотации T1-типов (П5, датафлоу) — на уровне Rust-атрибута
   (`#[schemars(...)]`-extension) или отдельный ручной YAML/JSON-манифест рядом с
   `crates/contracts/`?** Прямой перенос их подхода (аннотация в самой схеме) требует
   расширения `schemars`-деривации кастомными атрибутами (нетривиально технически — не
   факт, что `schemars` поддерживает произвольные `x-*` extension-поля из коробки без
   доп. кода); альтернатива — отдельный файл-манифест, который тоже проверяется на
   актуальность, но не завязан на возможности `schemars`. Это архитектурный выбор, не
   исследовательский — нужна архитекторская оценка, прежде чем писать RFC на П5.

4. **Приоритет П4 (`verify_contracts.sh`) относительно текущего активного milestone'а
   (M-08/ветка `docs/06-volume-truth` судя по git log)** — этот отчёт не оценивал
   срочность в контексте текущего roadmap; чисто с точки зрения «долг vs новая фича»,
   П4 закрывает уже written-but-broken обещание в докс, что обычно приоритетнее новых
   механизмов (П5/П6), но это founder/architect решение по очерёдности milestone'ов, не
   инженерно-исследовательское.
