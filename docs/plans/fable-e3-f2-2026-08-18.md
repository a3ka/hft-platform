## §1. Проблема 1 (§E-3): рекурсия — ПОДТВЕРЖДАЮ, и не по чтению кода, а исполнением

### 1.1 Предписание

> **E-3 — architect.** Механизм, а не проза: `scripts/next_artifact_id.sh` по умолчанию
> делегирует в `reserve_artifact_id.sh` и печатает номер только после взятия резерва; голая
> выдача остаётся под явным флагом `--no-reserve`.

### 1.2 Замер А — резерв зовёт аллокатор ПЕРВЫМ действием

Код:

```
$ grep -n 'ALLOC' scripts/reserve_artifact_id.sh
112:ALLOC="${ALLOC:-${SELF_DIR}/next_artifact_id.sh}"
256:[ -r "${ALLOC}" ] || die "аллокатор '${ALLOC}' не найден"
266:base="$(bash "${ALLOC}" "${CLS}")" || die "аллокатор отказал по классу ${CLS} — резерв не берётся"
```

Исполнение (подменяю аллокатор стабом, который лишь отмечается в stderr и падает):

```
$ ALLOC=<стаб> bash scripts/reserve_artifact_id.sh C; echo exit=$?
STUB-ALLOC-INVOKED args=C
FAIL  аллокатор отказал по классу C — резерв не берётся (номер от сломанного аллокатора хуже отсутствия номера)
exit=1
```

Вызов аллокатора происходит **до всякой сети** — это не деталь реализации, а вход в алгоритм
резерва: резерв обязан знать кандидата, чтобы попытаться его занять.

### 1.3 Замер Б — предписание в его буквальной форме не завершается

Взял **реальные** копии обоих скриптов, применил к копии `next_artifact_id.sh` ровно то, что
велит E-3 (по умолчанию `exec bash reserve_artifact_id.sh "$@"`, `--no-reserve` — старый путь),
и добавил СВОЮ страховку по глубине, чтобы не получить форк-бомбу:

```
$ bash <копия>/next_artifact_id.sh C
next: вызов #1
next: вызов #2
...
next: вызов #13
ГЛУБИНА >12 — рекурсия, обрываю страховкой
FAIL  аллокатор отказал по классу C — резерв не берётся ...   (×6, разматывание стека)
exit=141
```

**Вердикт по факту: дефект подтверждён.** Предписание E-3 в названной форме неисполнимо —
`next → reserve → next → …` не имеет дна. Страховка по глубине — моя, в предписании её нет.

### 1.4 Но рекурсия — не главное возражение

Рекурсию можно развязать выносом ядра (см. M3 ниже). Останутся три следствия, каждое из
которых ломает существующие гейты:

**(а) Гейт `verify_M-61.sh` станет измерителем доступности origin.**
`scripts/verify_M-61.sh:31` — `ALLOC=scripts/next_artifact_id.sh`; шаг N сверяет выдачу
аллокатора с независимо посчитанным «максимум+1». Делегирующий аллокатор требует сети и
CAS-push'а. Причина, по которой этого делать нельзя, **записана заранее в шапке самого
резерва** (`scripts/reserve_artifact_id.sh:44-47`):

> Сделать резерв обязательным нечем: аллокатор герметичен по построению (сеть в нём превратила
> бы гейт `verify_M-61.sh` в измеритель доступности origin — класс `TD-135`), а барьер судит
> СОСТАВ КОММИТА, а не то, каким способом автор узнал номер.

То есть E-3 предписывает ровно то, что автор механизма уже отверг с названной причиной, и эта
причина лежит в первых ста строках предмета. Это, а не рекурсия, — содержательный дефект
предписания.

**(б) Две герметичные пробы получают сеть.** `scripts/tests/red_artifact_ids.sh:80` и
`scripts/tests/red_reserve_id.sh:51` берут аллокатор через `ALLOC`/`ALLOC_SH`. После
делегирования проба АЛЛОКАТОРА становится пробой РЕЗЕРВА — она перестаёт мерить свой предмет
(`testing.md`, целостность гейта, свойство 2).

**(в) CI начнёт брать резервы.** Джоб `artifact-ids` гоняет аллокатор на каждом прогоне.
Каждый прогон занимал бы `refs/reserved/*` и выжигал номера пачками. Операционный хвост,
названный в шапке резерва как принятая цена, умножился бы на число прогонов CI.

### 1.5 Оценка твоей замены — предупреждение в stderr

**Как единственная мера — не годится. Но не по той причине, которой ты опасаешься.**

Чего в ней БОЛЬШЕ, чем в правиле: stderr попадает в вывод инструмента, то есть в контекст
агента **в момент действия**. По иерархии `binding-requires-mechanism.md` это нижняя строка
таблицы — «наблюдает, не блокирует», уровень 5 иерархии `process-layer-audit` §4 она
превосходит: это не «текст во впрыскиваемом ядре», который читается один раз за сессию и
теряется при сжатии. Так что «текст с эффективностью 0» — неточная диагностика.

Чего в ней НЕ хватает:

1. **Номер всё равно напечатан.** Механизм, выдающий то, что запрещает, отбирает только
   невнимательных. Гонка стартует в момент выдачи; предупреждение приходит уже внутри окна.
2. **Адресат мимо.** Оба вердикта `C-100` взял КРИТИК, не architect:
   `18b3655 docs(M-69): C-100 — plan-time REJECT [critic]` (09:21:52) и
   `ec2e5e9 docs(critic): C-100 — REJECT milestone-shape harness [critic]` (09:23:28).
   Критик читает не `gates.md`, а своё задание и свою обвязку. А обвязка сегодня велит ему
   обратное: `.claude/wrappers/codex-critic.sh:105` — `bash scripts/next_artifact_id.sh C`;
   `.claude/skills/harness-track/SKILL.md:111` — «Номер — только
   `bash scripts/next_artifact_id.sh C`». Предупреждение скрипта спорит с инструкцией, которую
   критику вручили как задание, и у него нет основания верить первому.

> Побочно проверено: **E-1 уже исполнен** — на `origin/feat/harness-doc-integrity` файл лежит
> как `research/critiques/C-101-harness-milestone-shape.md`. Коллизия как факт закрыта; открыт

### 2.3 Проблема сформулирована не на том уровне

Требуется не «PR открыт», а **«предмет, предъявляемый гейту, СОБРАН»**. PR — обходной путь к
сборке, потому что `ci.yml` не строит ветки:

```
$ sed -n '3,7p' .github/workflows/ci.yml
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

$ gh run list --limit 12 --json event,headBranch,conclusion
pull_request  feat/M-69-window-guard              failure
workflow_run  main                                success
pull_request  fix/M-65-battery-recalibration      failure
push          main                                success
pull_request  docs/session-handoff-refresh…       success
… (прогонов по событию `push` на ВЕТКЕ — ноль)

$ gh run list --branch feat/M-69-window-guard
… 3 прогона, ВСЕ `pull_request`, первый 09:32 — момент открытия PR, а не push'а набора
```

**Носитель, работающий без воли автора: триггер события в `ci.yml`.**

```yaml
on:
  pull_request:
    branches: [main]
  push:
    branches: ['**']        # было: [main]
```

Свойства:

- **воли не требуется вовсе** — событие рождает GitHub, а не агент; забыть нечего;
- критику предъявляется `gh run list --branch <ветка>` без всякого PR;
- **наблюдает ОТСУТСТВИЕ**: ветка без прогонов теперь означает «не пушили», а не «PR не
  открыли» — сегодня эти два состояния неразличимы;
- `deploy.yml` не задет: у него `push: branches:[main]` + `paths:[crates/**, Cargo.*,
  Dockerfile, docker-compose.yml, .github/workflows/deploy.yml]` (проверено чтением) — ветки
  его не триггерят, прод не шелохнётся;
- **зона:** `.github/workflows/**` в замок §11 не входит (`check_docs_freeze.sh:63`) → токен
  founder'а не нужен, правка идёт харнесс-треком, как и предписывал §E-3 для своей;
- **цена:** репозиторий PUBLIC (`gh repo view` → `PUBLIC`) → минуты Actions бесплатны. В origin
  25 веток. Пока PR открыт, тот же SHA соберётся дважды (push-событие + pull_request-событие);
  это принимается явно либо снимается `concurrency` по SHA отдельной правкой — но не в первом
  заходе: дедупликация по `github.ref` НЕ работает (у push и pull_request разные `ref`), и
  сделанная наспех она даст молчаливую потерю прогонов.

**Чего это НЕ даёт — называю, чтобы не выдать за закрытое:** второй эффект draft-PR из §F —
«немедленно показывает отставание ветки от `main`». Push-триггер строит ВЕТКУ, а не дерево
слияния; отставание он не покажет. Это остаётся за
`bash scripts/verify_design_claims.sh --merge-preview origin/main` (`gates.md` §8) и за
`strict: false`, назван в §8 как принятый предел.

**Следствие для F-1:** практика «открывать draft-PR» остаётся полезной, но перестаёт быть
несущей — несущую функцию (прогон) забирает триггер. Значит её честное место — строка практики
с тегом `COGNITIVE-ONLY`, без скрипта под неё. Это точнее, чем механизировать PR.
