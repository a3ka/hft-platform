## 1. Форма `L2Delta` — поля и обоснование каждого

Форма (T1, `crates/contracts/src/lib.rs:293-300`, введена CT-RFC-04) — **ратифицируется
без изменений**. Каждое поле, и почему без него нельзя / почему лишних нет:

```rust
L2Delta {
    bids: Vec<Level>,
    asks: Vec<Level>,
    first_update_id: u64,
    final_update_id: u64,
    prev_final_update_id: Option<u64>,
    ts_exch_ms: i64,
}
```

| Поле | Обоснование |
|---|---|
| `bids` / `asks: Vec<Level>` | ТОЛЬКО изменившиеся уровни, раздельно по сторонам. Разделение сторон **устраняет** потребность в per-level поле `side` (экономия на каждом уровне каждого события — самый горячий байт-путь журнала, §7). `Level {price, size}` fixed-point ×1e8 — та же дисциплина, что весь `MdPayload`. |
| — признак удаления | **Отдельного поля НЕТ намеренно**: `size == 0` = явный remove от биржи (wire-семантика Binance `@depth`: qty="0"). Doc-comment варианта (lib.rs:281-286) закрепляет и «отсутствие»: уровень, которого в дельте нет, НЕ изменился — дельта не источник истины о неупомянутом (`.claude/rules/testing.md` чек-лист «отсутствие»). Флаг дублировал бы `size==0` и жил бы в T1 вечно. |
| `first_update_id: u64` | Binance `U` — нижняя граница update-id дельты. Вместе с `final_update_id` даёт **gap-детекцию при реплее без обращения к бирже**: для спота непрерывность = `U == prev.u + 1`. Без него пропуск дельт невидим ⇒ тихо испорченная реконструкция книги. |
| `final_update_id: u64` | Binance `u` — верхняя граница; якорение к REST-снапшоту (`lastUpdateId`) при бутстрапе реконструкции. |
| `prev_final_update_id: Option<u64>` | Futures `pu` (чейнится `pu == prev.u`); у спота такого поля в wire НЕТ ⇒ `Option`, `None` для спота. Единый вариант на оба рынка вместо двух вариантов-близнецов — меньше exhaustive-`match`-поверхности (§8). |
| `ts_exch_ms: i64` | Биржевое время события — единая ось `event_data_ts` для ВСЕХ md-вариантов (`crates/journal/src/segments.rs:2566-2580` требует его от каждого варианта); латентность/ретеншен/выравнивание реплея. |

**Чего в форме НЕТ и не будет** (каждое отклонено осознанно — лишнее T1-поле живёт вечно):
`venue`/`symbol` (несёт конверт `MdEvent`), локальный `seq`/`ts_mono_ns` (несёт `Event`),
флаг «это якорь» (якорь — это `L2Snapshot`, отдельный вариант; роль различима по типу),
уровневый кап/метаданные бакетирования (дельта персистится **без потерь**, в этом её смысл —
кап см. §6), номер эпохи (эпоха — свойство сегмента, не события; §3).

**Вывод §1:** форма достаточна и для сегодняшнего BTC-only захвата, и для дельта-первичного
режима. Новых полей НЕ требуется. Открытым остаётся только Hyperliquid (§9.3): HL шлёт
агрегированный `l2Book`-снапшот, не diff — Binance-семантика `U`/`u`/`pu` на него не ложится.

## 2. Класс изменения и `SCHEMA_VERSION`

По правилам `docs/05-contract-layer.md` §4 (не по аналогии):

- **Аддитивный вариант enum в конце = minor bump.** Это изменение **уже совершено**:
  CT-RFC-04 rev2 + TD-031 бампнули `SCHEMA_VERSION` 2→3 (машинная изоляция эпох:
  `decide_open_segment` не переиспользует сегмент чужой schema-эпохи — doc-comment
  `crates/contracts/src/lib.rs:22-23`). Текущее значение — `SCHEMA_VERSION = 4`
  (lib.rs:26; 3→4 — CT-RFC-05 `MarginInventory`).
- **M-45 (расширение allow-list)**: константы `L2DELTA_CAPTURE_SYMBOLS` в venue-крейтах —
  **не T1-изменение**. Форма, дискриминанты, wire-байты не меняются ⇒ **бамп
  `SCHEMA_VERSION` НЕ нужен**, contract-пакет по §4 (schema/CHANGELOG/фикстуры) НЕ нужен.
  Сегменты schema-4 с расширенным набором символов читаются тем же кодом байт-в-байт (CT-I-3).
- **Инверсия ролей** (`DESIGN.md` §17 п.2: якорь 10–30 с вместо 1 Гц) — тоже НЕ меняет
  бинарную форму, но меняет **семантику потока** (консюмер больше не может предполагать
  «свежий снапшот ≤1–2 с»). `SCHEMA_VERSION` защищает бинарную совместимость и для
  семантического сдвига НЕ предназначен; машинный маркер режимного сдвига — `epoch_id`
  сегмента, см. §3. Это ровно урок E-001: семантический сдвиг без изменения формы — тот
  класс, который обязан получить ЯВНЫЙ маркер эпохи, а не бамп схемы «на всякий случай».
- **Если** founder выберет отдельный вариант для HL (§9.3) — это будет НОВЫЙ аддитивный
  вариант ⇒ отдельный атомарный contract-RFC (CT-RFC-07) с полным пакетом §4 и minor bump
  4→5; карта правок для него — готова в §8.2.

## 3. Эпохи: как читатель отличает снапшот-эпоху от дельта-эпохи

**Урок E-001 (`docs/data-epochs.md`), который нельзя повторить:** семантический сдвиг без
машинного маркера. Инверсия сторон HL не меняла форму — и границу эпохи пришлось
ВОССТАНАВЛИВАТЬ постфактум по heartbeat'ам («seq ≈ 123 205 544, ±несколько тысяч событий»).
123 млн событий с машинно-неразличимой эпохой — признанное ограничение. Режимный сдвиг M-45
(какие символы несут дельты; позже — инверсия ролей якоря) — тот же класс: форма не меняется,
семантика потока меняется.

**Механизм уже существует end-to-end — проверено кодом, не по памяти:**

1. `SegmentHeader` (T1, `crates/contracts/src/lib.rs:97-110`, CT-RFC-02) несёт
   `schema_version` И `epoch_id` («стабильный ключ эпохи, по которому research фильтрует
   данные. Смешение эпох — ЯВНОЕ решение»).
2. `decide_open_segment` (`crates/journal/src/segments.rs:1950+`, TD-031/L2D-I-8): reuse
   сегмента требует совпадения **`source && provenance && epoch_id && schema_version`** —
   т.е. смена `epoch_id` конфигурации МАШИННО открывает новый сегмент; смешанный сегмент
   двух эпох невозможен по конструкции.
3. Recorder берёт `epoch_id` из env `EPOCH_ID` (`crates/recorder/src/main.rs:479-482`,
   дефолт `own-<UTC-YYYY-MM>`) — операторский рычаг уже развёрнут в прод.

**Решение (нормативное, новых T1-полей НЕ требует):**

- **Каждое изменение состава/роли L2Delta-эмиссии = новый `epoch_id`, выставляемый ДО
  рестарта с новым allow-list'ом**, плюс запись в `docs/data-epochs.md` (класс «режимный
  сдвиг», не «дефект») **ДО раскатки** — зеркальная противоположность E-001, где запись
  делалась постфактум по памяти рестартов. Конвенция значения: `own-YYYY-MM-m45-<slug>`
  (напр. `own-2026-08-m45-alist2`); деплой-чеклист milestone'а M-45 обязан включать шаг
  «выставить `EPOCH_ID`» и §8-eyes-on проверку «первое L2Delta-событие нового символа лежит
  в сегменте с новым `epoch_id`».
- Читатель различает эпохи ЧТЕНИЕМ `SegmentHeader.epoch_id` + реестром `docs/data-epochs.md`.
  Почему одного факта «в сегменте есть/нет L2Delta по символу X» недостаточно: **отсутствие
  неотличимо от «не было изменений/обрыв потока»** — это то же правило «отсутствие — не
  сигнал» из семантики самой дельты (§1). Отсутствие данных не кодирует намерение;
  намерение кодирует эпоха.
- `schema_version` для режимного сдвига НЕ бампается (§2): он защищает бинарную
  совместимость (TD-031-сценарий), а не семантику потока. Два разных механизма — два
  разных ключа; смешивать их значило бы потерять оба смысла.

## 4. Восстановимость: якорный снапшот vs ретеншен/компакция

Дельта без якоря — мусор: реконструкция книги требует `L2Snapshot` (якорь) + непрерывную
цепочку дельт (`U`/`u`/`pu`, §1) от него. Вопрос: может ли якорь исчезнуть из-под зависящих
от него дельт? Проверено по коду и docs/06 §4:

- **Компакция НЕ удаляет события.** `compact_segment`/`compact_closed_segments`
  (`crates/journal/src/segments.rs:2791+, 2962+`) — zstd-сжатие ЗАКРЫТОГО сегмента целиком
  с sha256 round-trip-проверкой до удаления оригинала. Прунинга событий внутри сегмента не
  существует как операции.
- **Ретеншен — не удаление, а перенос.** `RetentionPlan.offload_and_prune`
  (`segments.rs:2155+`): сегмент СНАЧАЛА выгружается в COLD (Storage Box), потом удаляется
  горячая копия. «Журнал бессмертен» (JR-I-6/CT-I-3, docs/06 §4) — данные меняют tier, не
  существование.
- **Локальный prune — fail-closed за чекпоинтом.** `RetentionPolicy
  .checkpoint_covered_through_seq: Option<u64>` (M-38b/C-030 R1, `segments.rs:2103+`):
  дефолт `None` = никаких prune; prune разрешён только для сегментов, полностью покрытых
  чекпоинтом (`last_seq(seg) <= covered`); escape-hatch `allow_prune_without_checkpoint`
  дефолтно `false`, каждый обход — поимённо в отчёте.

**Следствие: якорь структурно не может быть потерян** — он либо в HOT/WARM, либо в COLD.
Но «не потерян» ≠ «дёшево достижим». Остаточные риски и их закрепление:

**Инвариант (предлагается к закреплению как `JR-I-10`, нумерация: JR-I-8 — M-49,
JR-I-9 — M-50/TD-053):**

> **JR-I-10 (якорная достаточность).** Для любого `seq` S, читаемого из журнала, и любого
> символа, несущего `L2Delta` в эпохе S, существует достижимый якорь: `L2Snapshot` этого
> символа с `seq ≤ S` в читаемом хранилище (HOT/WARM/COLD), либо checkpoint, покрывающий S.
> Ни одна операция ретеншена/компакции не имеет права инвалидировать это свойство.

Чем закрепляется — три слоя, два уже существуют:
1. **Уже в коде:** offload-до-prune (COLD-копия остаётся читаемой) + fail-closed
   checkpoint-gate (сегмент без покрытия не прунится локально). Это делает JR-I-10
   выполнимым сегодня без единой правки.
2. **RED-оракул (architect, milestone инверсии ролей, ДО кода):** тест в
   `crates/journal/tests/` — построить журнал «якорь в сегменте N, дельты в N+1..N+2»,
   прогнать `retention_plan` — план, отправляющий сегмент N в prune при непокрытых
   чекпоинтом дельтах N+1.., обязан не существовать; плюс тест реконструкции с
   произвольного seek: книга достигает `synced` без обращения за пределы читаемого набора.
   Анти-плацебо: оракул падает на реализации, прунящей по одному лишь возрасту.
3. **Каданс якоря — измерение, потом решение (§9.2):** латентность бутстрапа/seek при
   якоре раз в 10–30 с — до 10–30 с дельт реплея вместо ≤1 с — НЕ измерена
   (`m-45-l2delta-impact.md` §4.3). Число фиксируется только после замера; при выборе
   кадансов рассматривается опция «сегмент самодостаточен» (≥1 якорь на символ в каждом
   сегменте с его дельтами) — она сводит seek к одному сегменту, но требует связки
   эмиссии якоря с ротацией сегмента (связывание venue↔journal — цена, которую надо
   взвесить, не платить по умолчанию).

## 5. Детерминизм: `DET-I-1` на смешанном журнале

`DET-I-1/2/3` закреплены M-51 (merge `d896b98`, TD-007 CLOSED — проверено:
`git cat-file -e d896b98^{commit}` OK, `TECH-DEBT.md`). Ломает ли их смешанный журнал
(снапшоты + дельты в одном потоке)? **Нет — по конструкции, и это уже 12 дней прод-факт,
а не прогноз:**

- `DET-I-1` — свойство редьюсера («один и тот же поток событий → бит-идентичный результат»),
  не свойство однородности входа. Смешение типов событий не вводит недетерминизма, если
  редьюсер детерминирован на каждом типе.
- `book::Books::apply` (`crates/book/src/lib.rs:322-350`) обрабатывает ОБА варианта в одном
  `match`: `L2Snapshot → apply_snapshot`, `L2Delta → apply_l2delta` (с sequencing-гейтом
  `U`/`u`/`pu`; на `Gap` книга остаётся `stale` — fail-closed, не «додумать»). BTC получает
  оба типа событий в одном потоке с 2026-07-21 (M-18) — смешанный журнал уже штатный вход
  реплея, M-51 закрепил DET-I-* поверх именно такого журнала.
- `sim` (`crates/sim/src/exchange.rs:283-288`) **намеренно игнорирует** `L2Delta`: честный
  fill-путь ведёт книгу из `L2Snapshot`+`Trade`; учёт дельты поверх снапшота был бы двойным
  счётом. Детерминизм бэктеста не затронут.
- Гэп в цепочке дельт (обрыв WS, потерянный diff) — событие ВХОДА, записанное в журнал;
  реплей воспроизводит и гэп, и `stale`-состояние книги бит-идентично. Недетерминизма нет —
  есть честно записанная неполнота.

**Реальный риск — не детерминизм, а консюмеры, предполагающие snapshot-cadence** (проверено
кодом): `recorder/src/recon_loop.rs:55-61` сверяет книги ТОЛЬКО по `L2Snapshot`
(`_ => return` на всё остальное, включая `L2Delta`). Сегодня (якорь 1 Гц) это верно; при
инверсии ролей (якорь раз в 10–30 с) recon-частота падает на порядок — окно слепоты
recon-класса (родственно RK-I-8 «recon-расхождение → halt») растёт с ~1–2 с до 10–30 с.
