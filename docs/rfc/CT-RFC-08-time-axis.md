# CT-RFC-08 — ось времени: честная семантика `Event.ts_mono_ns`

**Автор:** architect-аудитор (независимая сессия) · **Дата:** 2026-08-03 ·
**Ревизия:** rev1 · **Статус:** **PROPOSED** (гейт: critic на СИЛЬНОЙ модели — RAW,
`gates.md` §1: предмет — T1 `crates/contracts` + порядок/состав записи журнала).
**Block-C:** да — меняется ДОКУМЕНТИРОВАННАЯ семантика T1-поля `Event.ts_mono_ns`
(сериализация НЕ меняется; прецедент — CT-RFC-07 §6 / `SegmentHeader.first_seq`).
**Реализация в dev НЕ диспетчеризуется этим документом** — сначала вердикт критика,
затем milestone обычным циклом.

---

## §0. Факты (все — замером, `origin/main` @ `0b4a398`)

1. **Контракт обещает:** «время — mono_ns для порядка» (`crates/contracts/src/lib.rs:5`);
   `DESIGN.md` §3: «время — mono_ns для порядка + wall_ms для отчётов».
2. **Реализация даёт:** `epoch: SystemTime::now()` при КАЖДОМ открытии журнала
   (`crates/journal/src/lib.rs:110` — `open()`, `:167` — `open_with()`);
   `ts_mono_ns = SystemTime::now().duration_since(self.epoch)` (`:205-213`).
   Следствия:
   - **обнуление на каждом рестарте** recorder'а (а рестарт = каждый деплой,
     `deploy.yml` триггерится на `crates/**` — TD-086);
   - **немонотонность внутри сессии** при NTP-коррекции (`SystemTime` — не steady clock;
     `duration_since` при отводе часов назад даёт `Err` → `unwrap_or(0)` — ноль посреди
     потока);
   - поле НЕ является осью порядка ни в одном смысле: порядок несёт `seq`.
3. **Сломанные консюмеры (три):**
   - `crates/alpha/src/lib.rs:191-192` — stale-expiry (`fresh = ev.ts_mono_ns <=
     sample.ts_event_mono_ns + horizon`): через границу рестарта сэмплы прошлой сессии
     имеют БОЛЬШИЙ mono, чем свежие события → «свежи вечно» (TD-081, AL-I-4);
   - `crates/sim/src/exchange.rs:108,141` — latency-модель (`effective_ts_mono_ns =
     last_ts_mono_ns + delta_ns`, зрелость — сравнением с `ev.ts_mono_ns`): через границу
     рестарта ось падает → pending «не созревают» до конца прогона; бэктест по журналу
     с рестартом тихо искажён (новая находка аудита 2026-08);
   - `crates/signals/src/obi.rs:120` — штампует `ts_event_mono_ns` дальше по конвейеру
     (транзитивный источник для alpha).
4. **Прод-read-path поле НЕ использует:** `grep ts_mono_ns crates/gateway*/src` → 0;
   агрегаты сидят на `ts_exch_ms` (`crates/gateway/src/lib.rs:90,748`) и `seq`.
5. В журнале уже ~157.9M событий с этой семантикой (замер VPS 2026-08-03) — они
   **не переписываются никогда** (append-only, CT-I-3).

## §1. Проблема одним абзацем

T1-поле обещает больше, чем даёт: читатель, поверивший докстроке, пишет корректный код
против несуществующей гарантии — уже трижды (alpha, sim, транзитивно signals). Это класс
«ложное [ЕСТЬ]», только внутри контракта: не документ врёт о коде, а контракт врёт о
данных. Пока execution-фаза отложена, цена — искажённый research; при входе в execution
эта же ось попадает в latency-замеры и SLA — цена станет денежной.

## §2. Решение

### 2.1. Семантика поля (новая докстрока T1, нормативно)

> `ts_mono_ns` — **монотонно неубывающая ось журнала**: для любых событий одного журнала
> `seq_a < seq_b ⇒ ts_mono_ns_a <= ts_mono_ns_b` (JR-I-13). Внутри одной сессии писателя
> разности — физические наносекунды steady-clock; **через границу сессии разность НЕ
> является длительностью** (простой писателя в ось не входит). Физические длительности
> между сессиями — только по `ts_wall_ms`/`ts_exch_ms`. Для сегментов, записанных до
> эпохи честности (§2.4), монотонность через границу сессии НЕ гарантируется.

### 2.2. Реализация записи (вариант O2 — рекомендуемый)

1. При `open`/`open_with`: якорь оси = **high-water предыдущей сессии**:
   `mono_base = ts_mono_ns последнего события хвоста` (хвост уже читается для
   `resolve_next_seq` — M-49-путь; дополнительная цена ≈ 0). Журнал пуст → `mono_base = 0`.
2. Внутри сессии: `ts_mono_ns = mono_base + instant_now.duration_since(instant_at_open)`
   — **`std::time::Instant`** (steady), не `SystemTime`. NTP не влияет по построению.
3. Guard в `append` (fail-closed против любого недосмотра): назначаемый
   `ts_mono_ns < last_assigned` → присвоить `last_assigned` (кламп в неубывание), счётчик
   `mono_clamped_total` в heartbeat — клампы наблюдаемы, не молчат.

### 2.3. Отвергнутые альтернативы (обязательная секция)

- **O1 «только передокументировать»** (поле = session-relative, консюмеры сами не
  сравнивают через сессии): дёшево, но перекладывает инвариант на дисциплину КАЖДОГО
  будущего читателя — ровно та конструкция «правило вместо гейта», которая в этом проекте
  систематически не выдерживает. Отвергнуто.
- **O3 «производная от wall»** (`ts_mono_ns = max(prev+1, ts_wall_ms×1e6)`): даёт
  wall-привязку через сессии, но квантует внутрисессионный шаг до ~мс и искажает
  суб-мс интервалы (latency-модель sim живёт на ns-дельтах). Отвергнуто для основной оси;
  wall-длительности и так доступны из `ts_wall_ms`.
- **Переименование поля / новый вариант схемы:** ломает всех консюмеров ради имени;
  сериализация не меняется — бессмысленная цена. Отвергнуто.

### 2.4. Граница эпох: как читатель отличает честные сегменты

Wire-формат не меняется, но МЕНЯЕТСЯ семантика генерируемых данных ⇒ по действующему
правилу (`contracts/src/lib.rs:13-19`: `SCHEMA_VERSION` — «эпоха эмитируемых вариантов»,
машинный маркер изоляции сегментов, потому что provenance — константа в рантайме, TD-031)
предлагается **бамп `SCHEMA_VERSION` 4 → 5**: сегмент schema-5 = «JR-I-13 держится»,
сегменты ≤4 = «монотонность только внутри сессии, границы сессий видимы по
`SegmentHeader`». Реюз сегмента schema-4 бинарём schema-5 запрещён механикой
`decide_open_segment` — граница честности машинно-читаема, миграция данных не нужна.

*Открытый вопрос критику:* достаточно ли бампа схемы, или расширять правило «bump только
на новый вариант» формулировкой «bump на любое изменение СЕМАНТИКИ эмитируемых данных»
(это одновременно закрывает давний класс Д1 — смена семантики при неизменной форме).

### 2.5. Консюмеры (та же milestone-связка, RED-first)

- **alpha (TD-081/AL-I-4):** детект регрессии оси (`ev.ts_mono_ns < last_seen`) →
  fail-closed: все сэмплы объявляются stale (отсутствие мнения, не edge=0 — существующая
  семантика `den_fresh == 0`). На schema-5 данных ветка мертва; на исторических — впервые
  корректна.
- **sim:** регрессия оси → детерминированная и объявленная политика (предложение:
  `last_ts_mono_ns` не убывает — кламп, pending дозревают по клампнутой оси; точная
  политика — решение milestone'а, RFC требует лишь: поведение определено + оракул).
- **gateway/gateway-serve:** изменений нет (поле не используется — §0.4).

## §3. Оракулы (sacred, architect; падают на текущем коде — анти-плацебо)

| ID | Что доказывает | Прод-форма |
|---|---|---|
| JR-I-13a | open→append→drop→open→append: `ts_mono_ns` строго неубывает через границу сессии | падает на текущем `epoch=now()` |
| JR-I-13b | инжектированный шаг часов назад (clock-абстракция) не даёт регрессию оси; `mono_clamped_total` растёт | падает на `SystemTime`-реализации |
| JR-I-13c | ротация сегмента внутри сессии не рвёт ось | регресс-гвард |
| AL-I-4r | фикстура с границей рестарта (mono падает): сэмплы прошлой сессии stale, форкаст отсутствует | падает на текущем alpha |
| SM-I-x | sim на журнале с регрессией оси: политика зрелости детерминирована, ×2 прогона бит-идентичны | падает на текущем sim |
| CT-канарейка | докстрока `contracts` и `DESIGN.md` §3 совпадают с §2.1 (грепом), «mono_ns для порядка» удалено | текстовый гейт |

Чек-лист деградированных фикстур (`testing.md`): регрессия ПОСРЕДИ сегмента (не только на
границе), два рестарта подряд, пустой журнал, journal только из legacy-сегментов.

## §4. Совместимость и цена

- Wire/postcard: **без изменений** (поле то же, u64). Старые сегменты читаются навсегда
  (CT-I-3). JSON Schema не меняется; меняются докстроки + `SCHEMA_VERSION`.
- Историческая правда: 157.9M событий остаются как есть; их семантика честно названа
  (§2.1 последнее предложение), читатели различают по schema сегмента.
- Цена реализации: чтение хвостового `ts_mono_ns` — на уже существующем M-49-пути;
  `Instant` вместо `SystemTime` — локальная замена; консюмер-фиксы — по одному экрану кода.
  Оценка: 1 milestone, ≤6 коммитов.

## §5. Что этот RFC НЕ решает (явно)

- Кросс-venue выравнивание часов (`ts_exch_ms` разных бирж) — вне предмета.
- Смена `seq`-семантики — не трогается (ось порядка была и остаётся `seq`).
- Ретро-исправление исторических сегментов — запрещено природой журнала.
