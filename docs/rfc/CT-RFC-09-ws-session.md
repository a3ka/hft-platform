# CT-RFC-09 — контракт WS-сессии: подписка как параметр СЕССИИ, а не конфигурация процесса

**Автор:** architect · **Дата:** 2026-08-03 · **Статус:** 🟢 **rev2 — критик-гейт пройден**
(`research/critiques/C-057-ct-rfc-09.md`, вердикт **NOTE**; все семь пунктов §6 закрыты в
rev2). Форма зафиксирована — против неё можно писать фронт. Реализация — Ф2.
**Подписи founder'а получены 2026-08-11** (§6): срок снятия переходного режима §2.5 —
«до первого релиза фронта»; `max_subscriptions_per_connection` = 16. Реализация — `M-65`.
**Основание:** независимый арх-аудит (`feat/arch-audit`, `arch-audit-2026-08.md` §1 п.3,
§5 P0-2) + прямое поручение founder'а (`docs/PENDING-SIGNATURE.md` П-008 п.4: «выполни»).
**Фактура:** `docs/plans/gateway-ws-contract.md` (685 строк, разведка 2026-08-02).

**Почему это RFC, а не milestone.** Меняется контракт с ВНЕШНИМ миром — тем, против которого
дизайнеры напишут фронт. Реализация может подождать (она в Ф2); **фиксация формы ждать не
может**: фронт, написанный против сегодняшней env-модели, придётся переделывать целиком.
Формулировка аудитора: *«самый дешёвый способ застраховать самую дорогую переделку»*.

---

## 1. Проблема

Сегодня `(venue, symbol, timeframe_ms, bands, window_ms)` — **конфигурация ПРОЦЕССА** из env
(`docker-compose.yml:118-128`), а клиентские WS-сообщения читаются и выбрасываются:

```rust
// crates/gateway-serve/src/lib.rs:499-502
Some(Ok(Message::Text(_))) | Some(Ok(Message::Binary(_))) => {
    // MVP: replay-контролы НЕ реализованы (только чтение).
    // Будущие фреймы с cursor/window будут интерпретироваться здесь.
}
```

Для терминала всё перечисленное — **параметры СЕССИИ**: пользователь переключает инструмент,
таймфрейм и глубину, не переставляя сервер. Один процесс на инструмент не масштабируется ни
на 300 инструментов, ни на переключение вкладки.

**Это не дефект реализации, а неверно проведённая граница.** MVP M-28 сознательно упростил;
упрощение пора снимать — до фронта, а не после.

## 2. Решения (нормативная часть)

### 2.1 Мультиплексирование: НЕСКОЛЬКО подписок на одно соединение

**Решение: да, с первой версии.** Причина — **forward-compat, а не экономия сама по себе**
(формулировка уточнена по находке критика, `C-057` §1.1).

Точная логика. Само по себе мультиплексирование сообщений в одном сокете НЕ устраняет N
реплеев: пока состояние на подписку считается отдельно, четыре виджета стоят четыре расчёта
независимо от того, сколько под ними TCP-соединений. Устранит их shared-проекция (R7) —
одно состояние, много потребителей. Но R7 в Ф2 не строится.

Ценность мультиплекса именно в том, что он **оставляет место для R7, не ломая протокол**:
когда разделяемое состояние появится, сервер начнёт обслуживать N подписок из одного расчёта
— и клиент этого не заметит, потому что уже говорит на языке «много подписок в одном
соединении». Альтернатива «одно соединение = одна подписка» дешевле сегодня, но переход к R7
потребовал бы смены формы сообщений, то есть переписывания фронта — ровно той цены, которую
этот RFC и существует, чтобы не платить.

### 2.2 Форма клиентских сообщений

```jsonc
// подписаться / переподписаться
{"op":"subscribe","v":1,"id":"<client-sub-id>","selector":{
   "venue":"Binance","symbol":"BTCUSDT","timeframe_ms":1000,
   "bands":[0.001],"window_ms":60000}}

// отписаться
{"op":"unsubscribe","v":1,"id":"<client-sub-id>"}

// смена параметров существующей подписки = subscribe с ТЕМ ЖЕ id
```

- `id` назначает **клиент** (не сервер): фронт сопоставляет ответы со своими виджетами без
  таблицы соответствий и переживает переподключение, сохранив свои идентификаторы;
- `v` — версия протокола в КАЖДОМ сообщении. Неизвестная версия ⇒ `error`, не молчаливое
  игнорирование (нынешнее поведение «прочитали и выбросили» — худший из возможных вариантов:
  клиент считает, что подписался);
- `selector` — та же форма, что серверный `gateway::Selector` (`crates/gateway/src/lib.rs`),
  чтобы не заводить второй словарь понятий.

### 2.3 Форма серверных сообщений

Каждое сообщение обязано нести `sub` — идентификатор подписки, к которой относится:

```jsonc
{"type":"snapshot","v":1,"sub":"<id>","data":{...}}   // Snapshot как сегодня
{"type":"frame",   "v":1,"sub":"<id>","data":{...}}   // Frame как сегодня
{"type":"error",   "v":1,"sub":"<id>|null","code":"...","message":"..."}
```

**Совместимость с нынешним `ServeMsg`.** Сегодня это `enum {Snapshot, Frame, Error}` в
serde-форме без конверта. Новая форма — **ломающая**, поэтому:
- вводится `GATEWAY_WIRE_VERSION` (значение `1` — эта редакция);
- сервер отдаёт новую форму ТОЛЬКО тем, кто прислал `subscribe` с `v`;
- клиент, не приславший ничего (нынешний `wsprobe`, смоук-тесты), продолжает получать
  старую форму по env-селектору — см. §2.5.

### 2.4 Семантика смены инструмента

`subscribe` с существующим `id` и другим `selector`:
1. сервер прекращает push по старому селектору для этого `id`;
2. отдаёт **новый `snapshot`** с тем же `id`;
3. дальше шлёт `frame` по новому селектору.

**Промежуточных кадров старого селектора после нового снапшота быть не должно** — иначе
виджет смешает две серии, и это будет выглядеть как порча данных. Оракул на это обязателен.

### 2.5 Переходный период и его КОНЕЦ

Клиент, не приславший `subscribe`, обслуживается по env-селектору в старой форме — чтобы не
сломать `wsprobe` и существующие оракулы в момент выката.

**Это временно и обязано иметь срок.** Условие снятия: как только фронт использует `v:1`,
env-селектор становится **fallback только для операторского инструмента** и логируется как
`deprecated` при каждом использовании. Дата/условие снятия фиксируется в milestone
реализации — не «когда-нибудь».

Без этого пункта переходный режим станет вечным: сегодняшний MVP тоже задумывался временным.

### 2.6 Лимиты (fail-closed)

- `max_subscriptions_per_connection` — **АМЕНДМЕНТ 2026-08-22 по арбитражу `A-015`**
  (узкий contract-RFC; правится ТОЛЬКО эта строка, `:123-125` и §6 не тронуты):
  - **отсутствие переменной И пустая строка ⇒ подписанная норма `16`** с наблюдаемой
    записью при старте (`warn`: имя переменной, применённое значение, «продуктовая норма»);
  - **невалидное ЗНАЧЕНИЕ** (`0`, отрицательное, нечисловое) ⇒ **отказ старта** — без
    изменений.

  <details><summary>Прежняя редакция (исходная, `5bf2b4b`) — сохранена как аудит-трейл</summary>

  > `max_subscriptions_per_connection` — конфиг, отсутствие/невалидное значение ⇒ **отказ
  > старта** (`gates.md`: «parse-error → unbounded — запрещено», урок R7);

  </details>

  **Почему амендмент, а не исполнение прежней редакции.** Её обоснование — «parse-error →
  unbounded запрещено, урок R7» — **не покрывает случай отсутствия**: отсутствие даёт `16`,
  величину ОГРАНИЧЕННУЮ и равную подписанной, а unbounded структурно недостижим — мусор,
  `0`, отрицательное и пустая строка отвергаются и после амендмента. Строгость на отсутствие
  была расширением нормы сверх её собственного основания. Сама строка написана в ИСХОДНОЙ
  редакции RFC, ДО подписи founder'а, когда значение лимита ещё не было решено.

  **Что НЕ меняется:** подписанное ЗНАЧЕНИЕ `16` (§6 п.2); поведение прода —
  `docker-compose.yml` подаёт переменную всегда; отказ старта на невалидном значении.
  Поэтому это не граница C (`gates.md` §0.1): меняется поведение бинаря в случае, о котором
  подпись МОЛЧИТ, — вопрос «как ПРАВИЛЬНО», а не «чего мы ХОТИМ». Основание полномочий —
  делегирование founder'а 16.08 («как решите — так и сделайте») и решение независимого
  Fable-клона `0fd7380`, подтверждённое арбитражем `A-015`.

  **Форма T1 не затронута:** ни Rust-тип, ни JSON Schema, ни `SCHEMA_VERSION` не меняются —
  правится норматив поведения при конфигурации. `verify_ct_rfc_atomic.sh` на такой правке
  проходит тривиально, и это названо, а не обойдено молчанием.
- **валидный диапазон — целое `>= 1`** (уточнено по `C-057` §6 п.3). `0` невалиден и
  отказывает старту наравне с мусором: соединение, которому нельзя подписаться ни на что, —
  это не «выключенная функция», а тихо сломанный сервер. Верхней границы контракт не
  назначает (её задаёт тариф), но значение обязано быть представимо в `u32`;
- превышение ⇒ `error` с кодом, НЕ молчаливое игнорирование и не разрыв соединения;
- квоты по тарифу (`JWT claims`) — вне периметра этого RFC, но форма `error` обязана их
  предусматривать (`code`, не свободный текст).

### 2.7 Ошибки клиентского `selector` (добавлено по `C-057` §6 п.1)

Невалидный селектор — **ошибка сессии, а не отказ соединения и не пустой снапшот**. Сервер
отвечает `error` с кодом из таксономии §2.6 и оставляет соединение живым; уже существующие
подписки этого соединения продолжают работать.

| условие | код | почему не иначе |
|---|---|---|
| неизвестный `venue` | `unknown_venue` | клиент опечатался; разрыв соединения убил бы рабочие подписки соседних виджетов |
| пустой/отсутствующий `symbol` | `invalid_selector` | то же |
| `bands` вне `(0, 1)`, `timeframe_ms <= 0`, `window_ms <= 0` | `invalid_selector` | fail-closed: молча подставленный дефолт даёт клиенту данные, которых он не просил |
| `bands` не отсортированы / дублируются | `invalid_selector` | детерминизм окна COB зависит от порядка |
| **инструмент валиден, но в журнале его нет** | — (не ошибка) | приходит **пустой `snapshot`** и подписка живёт: recorder может начать писать этот символ позже, и клиент обязан это увидеть без переподключения |

Последняя строка — сознательное различение: «мы тебя не поняли» (ошибка) против «пока нечего
показать» (пустой снапшот). Оракул: `red_ws_selector_validation_is_error`.

### 2.8 Порядок сообщений в момент подключения (добавлено по `C-057` §6 п.2)

Клиент переходного режима (§2.5) не присылает `subscribe` и получает серию по env-селектору.
Возникает гонка: что если `subscribe` придёт ПОСЛЕ того, как сервер уже отправил первый
снапшот по умолчанию?

**Решение: сервер не отправляет ничего, пока не истечёт `initial_subscribe_grace_ms`
(конфиг, дефолт 250 ms) или не придёт первое клиентское сообщение — что раньше.**
- пришёл `subscribe` в течение окна ⇒ клиент считается v1-клиентом, env-селектор НЕ
  применяется, первым сообщением уходит снапшот запрошенной подписки;
- окно истекло молча ⇒ клиент считается legacy, применяется env-селектор (переходный режим);
- `subscribe` пришёл ПОСЛЕ окна ⇒ обрабатывается как обычная смена инструмента (§2.4): новый
  снапшот, кадры старого селектора после него запрещены.

Так у клиента нет способа получить «чужой» первый снапшот незаметно для себя. Цена — 250 ms
на подключении legacy-клиента, которых по факту нет ни одного (фронт ещё не написан).
Оракул: расширение O-5 на смешанный случай.

### 2.9 Аутентификация в течение сессии (добавлено по `C-057` §6 п.6)

**Решение: токен проверяется ОДИН раз, при установлении соединения; истечение `exp` в
течение сессии соединение не разрывает.**

Обоснование и его граница: read-path отдаёт рыночные данные, а не деньги и не приватное
состояние пользователя; цена «сессия прожила дольше токена» здесь — лишние минуты доступа к
котировкам, тогда как принудительный разрыв посреди торгового дня стоит пользователю
работающего экрана. Это осознанный выбор, а не упущение.

**Граница действия.** Как только по этому же соединению пойдёт что-либо, кроме рыночных
данных (позиции, ордера, приватные балансы), решение недействительно и требует пересмотра
через новый contract-RFC: там цена ошибки асимметрична, и правило `RK-I-*` (fail-closed)
перевешивает удобство. Зафиксировано явно, чтобы будущий автор не унаследовал послабление
вместе с транспортом.

## 3. Что этот RFC НЕ решает (границы)

- **Реализацию** — она в Ф2 (`shared-tailer` + HOT-проекция). Здесь только форма;
- **стоимость подключения** (28–142 s) — это `TD-085`/`TD-093`, отдельная ось;
- **квоты и тарифы** — Ф3;
- **сжатие/бинарный формат** — сегодня JSON; смена кодека потребует бампа `v`, что этот
  контракт и предусматривает.

## 4. Открытые вопросы §10 фактуры — ЗАКРЫТЫ замерами (2026-08-02/03)

`docs/plans/gateway-ws-contract.md` §10 перечислял семь вопросов «чтением кода не
выясняются». Шесть закрыты замерами этой сессии:

**Как читать эту таблицу (уточнено по находке критика, `C-057` §2).** Строки делятся на два
класса, и смешивать их нельзя:

- **Факты конфигурации** (1, 2, 6, 7) — устойчивы, проверяются повторно одной командой.
- **Наблюдения переменной величины** (3, 4, 5) — зависят от момента замера, объёма журнала и
  свежести чекпоинта. Это НЕ контрактные константы: фронт не имеет права на них опираться,
  а RFC не имеет права выдавать их за гарантии. Каждое сопровождается временем замера.

| # | Вопрос | Ответ | Класс / источник |
|---|---|---|---|
| 1 | путь `.env` и секрет | `/root/hft-platform/.env`, права 600, содержит только `GATEWAY_JWT_SECRET` | факт конфигурации |
| 2 | прогрет ли чекпоинт | да; **каденция изменена на `*/15` минут** (`14017a4`, TD-085). Замер 2026-08-03T17:15:18Z: `covered_through_seq=158309045`, отставание от записи ≈50k событий | факт конфигурации (`deploy/cron.d/journal-retention`) |
| 3 | размер `Snapshot` в байтах | ≈**1.60 MiB**, максимальный `Frame` ≈**48.8 KiB** | наблюдение, `R-026` §7 (2026-08-03, журнал 156.9M событий). Растёт с историей — не константа |
| 4 | приходят ли `L2Snapshot` | да. Замер 2026-08-03T17:2xZ: `depth_series`=2, `heatmap`=**3743**, `cob`=39, `volume_bubbles`=218, `ohlcv`=50 | наблюдение. Прежнее «2316-2332» относилось к другому моменту и как контрактное число **отозвано** — величина переменная |
| 5 | сколько клиентов выдержит | 3 подряд — успешно (`R-026`); N>3 не мерялось | **остаётся открытым**, меряется стендом в Ф2 |
| 6 | переопределён ли `GATEWAY_ADDR` | нет: `127.0.0.1:8080` внутри контейнера, `ports` не проброшены | факт конфигурации |
| 7 | почему `current_thread` | **выяснено: это и была причина `TD-083`** — блокирующее чтение монополизировало единственный поток; закрыто `spawn_blocking` (M-53) | факт конфигурации |

Открытым остаётся только п.5 (ёмкость).

**Замер латентности подключения — состояние на 2026-08-03T17:2xZ** (тот же sidecar-метод,
`R-026` §7): **5 096 / 6 498 / 10 263 ms** против **28 488 / 142 469 / 66 290 ms** до
учащения чекпоинта. Второе слагаемое (двойной расчёт состояния) устраняется M-54 и на момент
этого замера ещё присутствовало.

**Дефект инструмента, найденный этим замером (`TD-095`).** `wsprobe --secret` не может
подключиться к проду: `parse_secret` (`crates/gateway-serve/src/bin/wsprobe.rs:155`) считает
строку из одних hex-цифр шестнадцатеричной и декодирует 64 символа в 32 байта, тогда как
сервер берёт секрет как ASCII-байты (`crates/gateway-serve/src/lib.rs:752`,
`DecodingKey::from_secret(secret.as_bytes())`). Прод-секрет — ровно 64 hex-символа, поэтому
ключи расходятся и авторизация отклоняется (`invalid token`). Обход на время: подписывать
токен вручную и передавать `--token`. Чинить в Ф2 — инструмент диагностики обязан говорить
с сервером на одном языке.

| O-5 | `red_ws_legacy_client_still_served` | клиент БЕЗ `subscribe` получает старую форму по env-селектору (§2.5) — переход не ломает `wsprobe` | нынешний `wsprobe` дословно |
| O-6 | `red_ws_error_has_code_not_prose` | все отказы несут машиночитаемый `code`; клиент различает их без разбора текста | все ветки отказа §2.6 |
| **O-7** | `red_ws_selector_validation_is_error` | невалидный селектор ⇒ `error` с кодом, соединение и соседние подписки живы; валидный, но отсутствующий в журнале инструмент ⇒ **пустой snapshot**, а не ошибка (§2.7) | неизвестный `venue`; пустой `symbol`; `bands` вне `(0,1)`, неотсортированные, с дублями; `timeframe_ms <= 0`; символ, которого нет в журнале |

### 5.1 Требование к эталону O-1 (обязательное, `C-057` §6 п.7)

Эталон в O-1 (и в любом оракуле, сверяющем WS-выдачу с «правильным» состоянием) обязан
строиться **независимым путём** — `gateway::snapshot(dir, filter, sel, cursor)` с нуля.
Использовать для эталона повторный вызов того же push-конвейера **запрещено**.

Это не стилистическое пожелание. За одну сессию тавтологичный оракул пойман трижды:
byte-identity сравнивала функцию с собственным результатом; проверка ограниченности мерила
половину работы; сверка серий сравнивала два пустых вектора. Каждый раз тест был зелёный и
не доказывал ничего. Оракул, у которого эталон и предмет происходят из одного кода, зелен
всегда — включая случай, когда оба сломаны одинаково.

## 6. Подписи founder'а — ПОЛУЧЕНЫ 2026-08-11

Оба вопроса закрыты; ответы внесены сюда как факт и продублированы в `milestones/M-65-ws-session.md`
§1.1, где на каждый заведён оракул.

1. **Срок снятия переходного режима §2.5 — «до первого релиза фронта».**
   Привязка к СОБЫТИЮ, а не к дате, поэтому названо условие, без которого решение вырождается
   в бессрочное (та же ловушка, что уже сработала с MVP M-28): в момент, когда дата релиза
   фронта назначена, она вносится в §2.5 и в `TECH-DEBT.md` записью «legacy-путь §2.5 подлежит
   удалению к <дата>». До тех пор legacy-путь ОБЯЗАН жить — на нём стоят `wsprobe` и все
   прод-замеры (оракулы `O-5`/`O-8`).
2. **`max_subscriptions_per_connection = 16.`** Лимит fail-closed в обе стороны: превышение ⇒
   `error` с кодом при живом соединении и живых соседних подписках; невалидное значение в
   конфиге (`0`, отрицательное, нечисловое) ⇒ отказ СТАРТА процесса (оракул `O-4`).
   Основание величины — продуктовое: кокпит с 4-12 виджетами помещается с запасом, а память
   при этом не страдает, потому что состояние планируется на ИНСТРУМЕНТ (~300), а не на
   подписку (`DESIGN.md` §16.1); то есть лимит здесь — защита от злоупотребления и
   справедливость между клиентами, а не борьба за RAM.
