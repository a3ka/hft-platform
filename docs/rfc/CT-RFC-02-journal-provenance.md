# CT-RFC-02 — Provenance и эпохи журнала (сегмент-заголовок), `schema_version` 1 → 2

STATUS: PROPOSED (architect, 2026-07-13). Атомарный contract-RFC per `docs/05-contract-layer.md`
§4. Трогает `crates/contracts/**` (T1) → Block-C, critic обязателен (`gates.md` §1.1).
Ветка: `feat/M-08`.

## §1. Проблема (почему это нельзя отложить)

Founder планирует **докупить историю** и обучать альфы на смеси купленных данных и
собственного захвата. Сегодня журнал этого различить НЕ МОЖЕТ:

- `crates/journal/src/lib.rs:24` — `const SEGMENT = "segment-00000000.jrnl"`: один сегмент,
  ротации нет; `journal.meta` несёт **только `next_seq`**.
- **`CT-I-6` («`schema_version` в каждом сегменте», `05` §6) сейчас НЕ ВЫПОЛНЯЕТСЯ** —
  константа `contracts::SCHEMA_VERSION` существует, но в файл не пишется. Инвариант считался
  закрытым; фактически он не проверялся ни одним тестом. Это находка RFC.
- Следствие: залив вендорских данных в тот же журнал сделает наш собственный захват
  **неотличимым** от чужого. `replay(journal) == реальность` (DESIGN §1) рушится: реальностью
  для купленного сегмента был ЧУЖОЙ снимок рынка с чужой глубиной книги и чужими часами.

Урок TD-015 (эпохи trials-ledger несопоставимы) — тот же класс, но на порядок дороже: там
смешивались метрики, здесь смешаются **обучающие данные**. Ошибка обнаружится не в отчёте,
а в живой торговле.

**Журнал бессмертен: задним числом источник данных не проставить.** Поэтому provenance
вводится ДО первого байта чужих данных, а не «когда выберем вендора».

## §2. Решение: provenance на уровне СЕГМЕНТА, не события

**Отвергнутый вариант:** поле `source` в каждом `Event`. При 2.8 GB/сутки (замер VPS
2026-07-13) это гигабайты дублирующегося тега; при этом внутри одного сегмента источник
никогда не меняется — писатель у сегмента ровно один (`JR-I-1`).

**Принято:** каждый сегмент открывается **заголовочным фреймом** `SegmentHeader` (первый
фрейм файла, тот же postcard+crc32-конверт, что и события):

```rust
// crates/contracts/src/lib.rs (T1)

/// Версия схемы журнального формата. 2: CT-RFC-02 — SegmentHeader + provenance.
pub const SCHEMA_VERSION: u32 = 2;

/// Происхождение данных сегмента. Расширяется СТРОГО в конец (postcard-дискриминанты).
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub enum DataSource {
    /// Наш собственный live-захват (recorder → venue-адаптеры).
    OwnCapture,
    /// Импорт исторических данных стороннего поставщика.
    Vendor,
    /// Синтетика (тесты, стресс-фикстуры). НИКОГДА не смешивается с двумя выше в обучении.
    Synthetic,
}

/// Первый фрейм КАЖДОГО сегмента (CT-I-6). Делает эпоху данных читаемым фактом, а не
/// устной договорённостью.
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct SegmentHeader {
    pub schema_version: u32,
    pub source: DataSource,
    /// Свободнотекстовое происхождение: чем/кем/когда собран (для OwnCapture — версия
    /// recorder'а + git sha; для Vendor — поставщик, датасет, лицензия, дата выгрузки).
    pub provenance: String,
    /// Идентификатор эпохи: стабильный ключ, по которому research фильтрует данные
    /// (`own-2026-07`, `tardis-binance-spot-2024`). Смешение эпох в обучении — решение,
    /// принимаемое ЯВНО, а не по умолчанию.
    pub epoch_id: String,
    /// Часы создания сегмента (отчёты; НЕ участвует в детерминизме реплея).
    pub created_wall_ms: i64,
    /// seq первого события сегмента (сшивка сегментов при ротации).
    pub first_seq: u64,
}
```

`Event` НЕ меняется → все существующие фикстуры/парсеры/сигналы валидны. `EventKind` не
трогается (новых вариантов нет).

## §3. Миграция (журнал бессмертен — `CT-I-3`)

Прод-сегмент `segment-00000000.jrnl` (8.3 GB, пишется с 2026-07-10) заголовка НЕ имеет.

- **Чтение:** ридер пробует разобрать первый фрейм как `SegmentHeader`. Не вышло → сегмент
  трактуется как **schema 1** с **вменённым** заголовком:
  `{schema_version: 1, source: OwnCapture, provenance: "pre-RFC02 recorder capture (implied)",
    epoch_id: "own-legacy-pre-rfc02", created_wall_ms: <mtime>, first_seq: <первый seq>}`.
  Старые данные читаются **навсегда** и не теряют смысла — они наши, это известно
  из истории репозитория, и это фиксируется вменением, а не молчанием.
- **Запись:** новые сегменты (в т.ч. первый после ротации, M-08) ВСЕГДА несут заголовок.
- **Никакой переписи прод-сегмента.** Append-only не нарушается; конвертация 8.3 GB запрещена
  (риск потерять единственную копию боевых данных ради косметики).

Дизъюнкция «есть заголовок / нет заголовка» — единственная развилка совместимости; тест
роундтрипа на обоих вариантах обязателен (`CT-I-3`).

## §4. Инварианты (RED, sacred — падают на текущем коде)

| ID | Инвариант |
|---|---|
| CT-I-6 (наконец-то РЕАЛЬНО) | Каждый НОВЫЙ сегмент несёт `SegmentHeader` первым фреймом; `schema_version` читается из файла, а не из константы кода |
| CT-RFC02-1 | Legacy-сегмент без заголовка читается как schema 1 + вменённый `OwnCapture`-заголовок; события не теряются (роундтрип на фикстуре формата прод-сегмента) |
| CT-RFC02-2 | Ридер отдаёт `(SegmentHeader, events)` — потребитель НЕ МОЖЕТ прочитать события, не увидев эпоху (типовой барьер, а не дисциплина) |
| CT-RFC02-3 | `Vendor`- и `OwnCapture`-сегменты в одном каталоге не «сливаются» молча: чтение по умолчанию требует ЯВНОГО фильтра эпох; смешение — осознанный вызов (`EpochFilter::Explicit(vec![...])`), не дефолт |
| CT-RFC02-4 | `Synthetic` не попадает в обучающую выборку по умолчанию (та же поверхность фильтра) |

Анти-плацебо: CT-I-6 обязан ПАДАТЬ на текущем `journal` (сегмент пишется без заголовка);
CT-RFC02-2 обязан падать на API, где `read_all(dir) -> Vec<Event>` (эпоху можно не заметить).

## §5. Изменения по файлам (атомарно, один PR)

1. `crates/contracts/src/lib.rs` — `DataSource`, `SegmentHeader`, `SCHEMA_VERSION = 2`.
2. Перегенерированная JSON Schema (`CT-I-4`) + фикстуры valid/invalid.
3. `crates/journal` — writer пишет заголовок; ридер возвращает `(SegmentHeader, …)`;
   legacy-путь вменения (реализация — M-08, задача 2; RFC фиксирует ФОРМУ).
4. Потребители (`research-cli`, `book`-примеры) — берут события через API с эпохой.
5. CHANGELOG контрактов + этот файл.
6. Тесты §4.

## §6. Связь с M-08

RFC задаёт форму; **реализация — в `milestones/M-08-data-durability.md`** (ротация сегментов
пишет заголовок в каждый новый файл; стрим-ридер отдаёт заголовок + итератор событий).
Порядок: RFC (contracts+RED) → M-08 задача 2 (journal) → импортёр вендора (отдельный
milestone, когда поставщик назван).

## §7. Что НЕ входит

- Формат/парсер конкретного вендора (Tardis/Kaiko/дампы) — отдельный milestone после выбора.
- Per-source latency/fees-артефакты для `sim` (купленные данные ≠ наши латентности) — задача
  того же импорт-milestone; здесь фиксируется лишь то, что `epoch_id` даёт `sim` ключ, по
  которому честные таблицы можно выбрать.
- Ретеншен/cold-выгрузка — M-08 (durability), не контракт.
