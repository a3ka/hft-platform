## §0. Тезис и не-цели

**Тезис (v2).** **AlphaQuant — многопользовательская SaaS-платформа рыночных данных и
аналитики** с ДНК топ-фирм: единый упорядоченный журнал событий + детерминированные машины
состояний над ним + research-платформа как настоящий moat. Продаётся не «сигнал», а
**доказуемость**: каждая цифра на экране пользователя выводится реплеем из журнала.

То, что делает платформу возможной, — уже построенное ядро: журнал на 137+ млн событий,
бит-идентичный реплей, честные проекции. Продукт — это read-path над ним для десятков тысяч
пользователей, а не новая система.

**Тезис v1 сохраняется как ядро:** независимый fail-closed риск-слой (§4) и отсутствие LLM в
горячем торговом цикле остаются архитектурными законами — они относятся к execution-слою,
который **отложен** (см. §4 и §21), но не отменён и не ослаблен.

**НЕ-цели (явно).** Не ультра-HFT (наносекунды/FPGA/колокация — барьер капекса, соло
не входит). Не «магический набор готовых прибыльных стратегий» (публичная альфа мертва).
Не LLM-в-торговом-цикле (одна галлюцинация в sizing = депозит). Не классические биржи на
старте (крипта — HL/Binance).

**ОТМЕНЕНО (2026-07-29, решение founder'а):** ~~Не многопользовательская SaaS~~ — это ровно то,
чем платформа теперь является. Строка сохранена зачёркнутой намеренно: она процитирована в
подчинённых документах, и молча исчезнувшая НЕ-цель выглядела бы как недосмотр, а не как
осознанный разворот.

**НЕ-цели, добавленные v2:** не копи-трейдинг и не исполнение ордеров пользователей в первых
фазах (§21 — шов предусмотрен, не реализуется); не консультационный сервис («сигнал купить») —
юридически иной режим, чем аналитика; не перепродажа сырых данных биржи без разрешения (§20).

## §1. Стержневой принцип (единый для движка и деска)

Всё — событие в едином журнале с тотальным порядком; вся логика — детерминированные
редьюсеры над потоком событий. Три равенства, ради которых строится система:

1. **`replay(journal) == реальность`** — бит-в-бит. Форензика любого убытка, аудит каждого цента.
2. **`backtest == paper == live-micro == live`** — один код стратегии, четыре источника событий.
3. **`failover == replay`** — резерв догоняет журнал.

Всё, что LLM производит, входит в рантайм ТОЛЬКО через три подписанные границы (§6).

## §1.5. Системная карта — три подсистемы как единое целое

Платформа = ТРИ подсистемы вокруг одного журнала, связанные контрактным слоем и
governance-процессом. Квант-деск — полноправная подсистема, не придаток.

```
                         ┌──────────── GOVERNANCE (04-workflow) ────────────┐
                         │ founder=dispatcher · architect/critic/reviewer/  │
                         │ risk-critic · milestones · RED-first · scope-guard│
                         └──────────────────────┬───────────────────────────┘
                                                │ строит и гейтит всё ниже
   ┌─────────────────────────┐   границы A/B/C  ┌──────────────────────────────┐
   │  КВАНТ-ДЕСК (LLM)        │   (03,05)        │  ТОРГОВЫЙ ДВИЖОК (Rust)       │
   │  02-quant-desk          │◀───читает журнал─│  01-engine                    │
   │                         │                  │                               │
   │ hypothesis→signal-eng   │  A: код сигнала  │ book→signals→alpha→portfolio  │
   │ →backtest→risk-critic   │─▶(crates/signals)│ →strategy→risk→oms→venue      │
   │ →portfolio-analyst      │  B: реестр       │ (детерминизм; журнал пишется) │
   │ →FOUNDER (подпись)      │─▶(signals.json)  │                               │
   │                         │  C: ParamChange  │        │ fills/slippage/       │
   │ research-cli (compute)  │─▶(подпись)───────│        │ sim-vs-live           │
   │  ▲──────────────────────┼──────────────────┼────────┘ (обратная связь)     │
   └──┼──────────────────────┘                  └───────────────┬───────────────┘
      │                                                         │
      └───────────── КОНТРАКТНЫЙ СЛОЙ (05-contract-layer) ──────┘
         единый журнал T1 (Event/Registry/ParamChange/Report) — один формат навсегда
```

**Как это «единое целое»:** движок торгует и пишет журнал → квант-деск читает журнал
(история + собственные fills) → research-cli (compute, без LLM) гоняет гриды → отчёты →
risk-critic → **подпись founder'а** → перекалиброванные сигналы возвращаются в движок
через границы A/B/C. Петля замыкается на СОБСТВЕННОМ исполнении — это moat. research
крутится 24/7 (compute); подписи — по мере созревания (дни/недели); горячий торговый цикл —
миллисекунды, без LLM. Контрактный слой гарантирует, что обе подсистемы говорят на одном
типизированном языке; governance-слой строит и гейтит обе по единому процессу.

## §2. Слои и модульные границы

Онион: зависимости только внутрь. `journal` — ядро; `risk`/`killswitch` — защищённая
зона (агенты не пишут); `signals`+`research` — единственная зона записи квант-агентов.

```
Слой 0  journal        событийная модель, append-only лог, replay, снапшоты, state_hash
Слой 1  venues, book   MD/Order адаптеры (HL→Binance), book builder, depth-полосы, microprice
Слой 2  signals        Signal-модули (ЗОНА КВАНТ-АГЕНТОВ) → SignalRegistry
Слой 3  alpha,portfolio ансамбль калиброванных сигналов → sizing (лимиты/инвентарь/корреляции)
Слой 4  strategy,oms   MM-квотер + diff-квоты; order state machines, идемпотентность, rate-budget
Слой 5  risk,killswitch pre-trade gate (fail-closed) + PnL/позиции/recon + аудит; отдельный KS-процесс
Слой 6  sim,runner     симулятор исполнения; композиция режимов + arming
Слой 7  research-cli,ops грид/walk-forward/отчёты; метрики/алерты/recon-с-биржей/бэкап (FA: docs/fa/ops.md)
Слой 8  viz-backend    дериватив-слой (heatmap/footprint/CVD/VP/VWAP/TPP) + Read Gateway (WS live+replay) + export v2 (FA: docs/fa/viz-backend.md)
Слой 9  ai-copilot     AI-наставник real-time (Event Engine + AI-Context + LLM-сервис + audit), ВНЕ детерминизма (FA: docs/fa/ai-copilot.md)
```

**Слои 8-9 (пивот 2026-07-22, `docs/07-cockpit-backend-roadmap.md`)** — read-only консюмеры журнала
(Граница A): виз-бэкенд и AI-копилот СТОЯТ ПОВЕРХ даталеера (`06`), не пишут journal, T1-ядро не трогают.
Слой 8 детерминирован (live==replay); слой 9 ВНЕ детерминизма (LLM недетерминирован → его выводы вне
journal, `DET-I-1` цел).

Полный список крейтов — `01 §2`. Правило доступа агентов — `03 §4`.

## §3. Контракты данных (T-подобная модель, аналог EINHARD T1/T2/T3)

- **T1 — сквозные, версионируемые, единый источник правды:** `Event`/`EventKind`
  (журнальный формат — ОДИН навсегда), `SignalRegistry` запись (`signals.json`),
  `Ctl(ParamChange{signed})`. Изменение T1 = версия + миграция (как EINHARD RFC-класс);
  меняет их только человек-через-подпись или явный design-review.
- **T2 — модульно-ограниченные:** `Order`, `RiskApproved<Order>` (приватный конструктор в
  `risk`), `Book`/`DepthBands`, `Forecast`, `TargetQuotes`, лимит-профили. Владеет крейт.
- **T3 — внутренние:** промежуточные структуры сигналов, буферы, метрики. Свобода реализации.
- **Кодировки (locked):** деньги/цены — fixed-point i64/u64 ×1e8 (не f64); время — mono_ns
  для порядка + wall_ms для отчётов; wire — postcard + crc32 на фрейм. Урок hft-core-rs:
  один формат, не три.

## §4. Инварианты риск-слоя (RED-оракулы; тест ОБЯЗАН падать на заглушке)

Прямой перенос EINHARD-валидатора в трейдинг, с обратной полярностью risk_guard.

| ID | Инвариант |
|---|---|
| RK-I-1 | Ни один ордер не достигает venue без `RiskApproved` (типовой барьер + grep-тест) |
| RK-I-2 | Байпас-флаг НЕ СУЩЕСТВУЕТ: нет конфиг-поверхности, отключающей gate (тест утверждает отсутствие) |
| RK-I-3 | Неизвестный инструмент/стратегия → Reject (fail-closed, НЕ default-лимиты — анти-risk_guard) |
| RK-I-4 | Gate недоступен/паника → торговля стоит; деградация никогда не «пропускает» |
| RK-I-5 | Отказ записи журнала/аудита → halt (никаких `let _ = ...`) |
| RK-I-6 | Kill switch работает при мёртвом движке (отдельный процесс, свои креды/коннект) |
| RK-I-7 | После разрыва связи на бирже нет наших заявок (CoD и/или KS-sweep drill) |
| RK-I-8 | Recon-расхождение позиции/ордеров > ε → halt + алерт |
| RK-I-9 | Пробитие дневного loss-лимита → halt; re-arm только человеком |
| RK-I-10 | Параметры/веса меняются только подписанным `Ctl(ParamChange)` (зеркало INTG-I-3) |

**Конкретные T-контракты лимитов для первого живого этапа ($500–2k, минимальный профиль).**
Числа — стартовые дефолты профиля `live-micro`, подписываются как обычный ParamChange;
цель профиля — доказуемость, не доход:

| Лимит | Стартовое значение | Обоснование |
|---|---|---|
| Инструменты | ровно 1 пара (HL:BTC или HL:ETH) | минимум поверхности |
| max_position (нотионал) | ≤ 15% капитала (напр. $75–300) | инвентарь мал, MM-нейтральный |
| max_order (нотионал) | ≤ 3% капитала | дробим, не вешаем риск на один ордер |
| дневной loss-лимит | ≤ 2% капитала → halt | ранний стоп важнее прибыли |
| max_orders/sec | консервативно от лимита HL `[verify-at-impl]` | не упираемся в rate-limit |
| price-deviation guard | ≤ X% от mark `[verify-at-impl]` | защита от «толстого пальца»/сбоя книги |
| инвентарь-кап | = max_position; пробитие → одностороннее квотирование → стоп | штатная деградация |

Ёмкость на этом капитале нерелевантна — любой скелет-сигнал «влезает»; поэтому
портфельный sizing на P4 упрощён (одна пара, один-два сигнала), корреляции включаются
на P5 (Binance/мультипара). Каждое решение gate — событие, включая **NearMiss**
(utilization ≥ 80%) — телеметрия «что почти сломалось» (паттерн P-01 из hft-review).

## §5. Честность симулятора (почему бэктест не будет врать)

- Queue position — консервативно: встаём в хвост уровня; maker-fill только когда
  traded-объём превысил глубину впереди; отмены впереди нас не засчитываем (пессимизм).
- Латентность — из ИЗМЕРЕННЫХ на P1 распределений (δ_submit/δ_cancel/δ_md), не из воздуха.
- Комиссии/ребейты HL по тарифу `[verify-at-impl]`; funding по расписанию; taker — с
  проеданием книги.
- `paper` = тот же sim на живом потоке; **дивергенция sim-vs-live (fill-rate, PnL) —
  первоклассная метрика и ворота P4**. Расхождение = сигнал, что модель врёт, а не «шум».

## §6. Интеграция движок ↔ квант-деск (три границы + правило направления)

Единое целое = ОДИН журнал (деск читает для research) + три типизированные границы, через
которые LLM влияет на рантайм только на дизайн-тайме и только с подписью founder'а:

- **Граница A — код сигнала:** агенты пишут только `crates/signals/**` + `research/**`
  (scope-guard, arch-lint + ревью). Sacred: тесты `risk/`. Новый сигнал = PR (модуль +
  unit + детерминизм-тест + SignalSpec-карточка; чистая функция над `Event`, без I/O/часов/будущего).
- **Граница B — SignalRegistry (`research/registry/signals.json`):** источник правды, что
  движок исполняет. Запись = {signal_id, version, code_hash, status(candidate→paper→live→retired),
  params, ensemble_weight, validation_report, promoted_by}. Движок исполняет только
  `status==live && weight>0`; `code_hash` обязан совпадать с модулем (verify-гейт).
- **Граница C — очередь решений (HDP):** веса/лимиты/параметры НЕ правятся у живого
  процесса. Предложение → подпись Ed25519 (ключ у человека) → атомарное применение →
  `Ctl(ParamChange{signed})` в журнал (реплеится: кто/когда/на каком основании).

**INTG-I-1..7** (RED, полностью — `03 §6`): ключевые — INTG-I-1 (LLM влияет на рантайм
только через A/B/C с подписью; иного write-пути нет), INTG-I-5 (paper-сигнал физически
не может отправить ордер — приёмник paper ≠ live gateway), INTG-I-6 (trials-ledger
append-only, deflated Sharpe считается от него).

**Замкнутый цикл (moat):** живая торговля → журнал (наши fills, реальный slippage,
sim-vs-live) → research-cli → отчёты → критик → подпись → перекалиброванные сигналы →
назад в движок. Деск учится на СОБСТВЕННОМ исполнении. research крутится 24/7 (compute);
человеческие подписи — по мере созревания (дни/недели); горячий цикл — миллисекунды, без LLM.

## §7. Квант-деск (команда агентов) и анти-оверфит

Роли (детали `02 §1`): `hypothesis-researcher` (гипотезы из литературы/аномалий/идей
founder'а + пре-регистрация критериев фальсификации), `signal-engineer` (SignalSpec→код),
`backtest-runner` (гриды, не LLM), **`risk-critic` (сильная модель — не экономим:
ложноположительная стратегия = потеря депозита, asymmetric cost)**, `portfolio-analyst`
(веса/корреляции), **founder — единственная подпись**.

Анти-оверфит (встроен в гейты, `02 §4`): (1) пре-регистрация критериев ДО test-данных;
(2) time-split train/val/test, test трогается один раз; (3) **глобальный trials-ledger**,
deflated Sharpe от него; (4) чек-лист критика (leakage / survivorship / честные издержки+латентность
/ режимная зависимость / реальная ёмкость / корреляция с live-набором); (5) обязательный
paper-карантин; (6) двойная подпись founder'а (paper, live). LLM никогда не оценивает свою
работу — оценивают движок + независимый критик + человек.

## §8. Стартовый набор стратегий (бэклог, `00`)

6 семейств-скелетов (edge — в калибровке/исполнении/издержках, не в идее):
**(1) OBI — сигнал founder'а №1** (имбаланс depth-полос 3%/8% ≥ θ → BUY; формализуется
как параметрическое семейство, грид+decay+издержки — из своего L2, внешний сервис не нужен);
(2) passive MM (Avellaneda–Stoikov скелет); (3) cross-exchange lead-lag (Binance ведёт,
HL догоняет — под P5); (4) funding/basis capture; (5) liquidation-flow; (6) short-horizon
mean-reversion. Первая гипотеза `H-20260710-obi-asym` обкатывает весь контракт §6 ещё
до написания движка (на записанных данных с P1).

## §9. Карта reuse / rewrite / delete по hft-core-rs

| Что | Решение | Почему |
|---|---|---|
| Fixed-point цены; идея нормализации в один формат | **reuse-идея** (у нас i64 ×1e8) | верная дисциплина |
| Трёхуровневое хранение + MAXLEN/OOM-уроки | **reuse-концепт** в retention журнала | оплачено их 28.95GB-инцидентом |
| Alert-таксономия P0/P1/P2 + runbooks | **reuse адаптированно** (+ паритет alert↔exporter) | лучшее, что там есть |
| Arena orderbook | **отложенный порт** (P5+, если профилировка потребует) | mid-freq живёт на BTreeMap |

## §13. Модель данных: два источника истины

**Терминологическая коллизия (закрыта жёстко).** В AlphaQuant «Journal» — память решений
ПОЛЬЗОВАТЕЛЯ (§5.1: «глобальная память решений, сделок и AI-разборов»). У нас `journal` —
журнал РЫНОЧНЫХ событий. Правило именования BINDING:
- **`event-store`** — рыночный журнал (Rust; крейт в коде сохраняет имя `journal`,
  переименование крейта не делаем);
- **`decision-journal`** — пользовательская память решений (Postgres). Слово «Journal»
  без префикса в наших доках больше не употребляется.

```
  ИСТОЧНИК ИСТИНЫ №1: EVENT-STORE (Rust)         ИСТОЧНИК ИСТИНЫ №2: POSTGRES (app)
  рыночные события, T1-контракты [ЕСТЬ]          пользовательские сущности [ПЛАН]
 ┌───────────────────────────────────┐          ┌───────────────────────────────────┐
 │ Event{seq, mono_ns, wall_ms,      │          │ users, sessions, billing/tariff   │
 │   venue, symbol, EventKind}       │          │ Profile      (AlphaQuant §5.1)    │
 │  · Trade                          │          │ Workspace / View / Widget layout  │
 │  · L2Snapshot (1 Гц, якорь)       │          │ Replay-закладки пользователя      │
 │  · L2Delta (100 мс; BTC-only →§17) │          │ decision-journal (сделки-паперы,  │
 │  · Funding / OI / Liquidation     │          │   гипотезы, process score, уроки) │
 │  · Sys (gap, recon, checkpoint)   │          │ agents (goal/tools/policy/memory) │
 │ будущее: Ctl(ParamChange{signed}),│          │ policies, approvals, audit_log(AI)│
 │   ордер-события execution (§21)    │          │ alerts, api_keys (наши, не чужие) │
 └────────────┬──────────────────────┘          └────────────┬──────────────────────┘
   append-only│ один писатель: recorder             CRUD     │ один писатель: app
   бэкап:     │ zstd + offsite COLD (R1!)           бэкап:   │ pg_dump/PITR — СВОЙ,
   replay ⇒   │ производные проекции                         │ реплеем НЕ пересобрать
              ▼                                              ▼
 ┌──────────────────────────────┐               ┌──────────────────────────────┐
 │ ПРОЕКЦИИ (производное, §14)   │               │ Читатели: Next.js SSR/API,   │
 │ HOT/WARM/COLD, агрегаты      │               │ Agent Runtime (память/policy)│
 └────────────┬─────────────────┘               └──────────────────────────────┘
              ▼
   Читатели: gateway-serve (WS), Agent Runtime (tools, read-only),
   research-compute (backtest), будущий execution-путь (§21)

  ПОТОК «СКВОЗНОЙ» (единственный санкционированный мост №2→№1 — БУДУЩЕЕ, §21):
  подписанное решение человека (Ctl/ParamChange, approve ордера) → event-store.
  Обратного моста (event-store → Postgres) нет: рынок в Postgres не копируется,
  пользовательские виджеты читают рынок из проекций, а не из своей БД.
```

Правила:
1. **Postgres — НЕ производная.** Его не пересобрать реплеем; у него собственный бэкап
   (PITR) и собственная миграционная дисциплина (Prisma-класс) [ПЛАН].
2. **Рыночные T1-контракты** (`Event`/`EventKind`, кодировки fixed-point i64×1e8,
   mono_ns/wall_ms, postcard+crc32) — без изменений из v1 §3; governance — contract-RFC
   (`05-contract-layer.md`) [ЕСТЬ].
3. **Пользовательские контракты** (Workspace, AI Event, Strategy Definition, policy,
   audit-запись) — версионируемые схемы app-плоскости; кросс-языковой консюмер (Rust ↔
   TS) → промоушен в `crates/contracts` + JSON Schema, как заведено (TD-008-паттерн).
4. **AI-выводы — вне event-store** (недетерминированы): audit-store в Postgres (§19).
   DET-I-1 не разбавляется.

## §14. Проекции (CQRS read-модели)

Производные представления event-store под каждый класс чтения. Идея трёхуровневого
расслоения по возрасту и маршрутизации запроса по возрасту — унаследована от hft-core-rs
(их Data Fabric, §9), но **проекциями от одной истины, а не тремя источниками**.

| Проекция | Из чего | Хранение | Класс чтения | Статус |
|---|---|---|---|---|
| HOT: live-состояние | tail event-store (редьюсеры: book, VWAP, CVD, VP, полосы глубины, funding, event engine) | in-proc RAM (+Redis-класс при мультиноде `[verify-at-impl]`) | WS-подписки кокпита: снапшот+push, окно минуты-часы | [ЧАСТИЧНО]: редьюсеры ЕСТЬ, но каждый клиент сканирует журнал сам (R7); shared-проекция — M-39-класс [ПЛАН] |
| WARM: аналитический индекс | batch-replay закрытых сегментов | ClickHouse-класс / Parquet+DuckDB `[verify-at-impl]` | история для графиков (дни-месяцы), similarity search, quant-датасеты | [ПЛАН] |
| COLD: архив сегментов | закрытые zstd-сегменты, sha256-verified | Storage Box → S3-класс/Parquet | длинные бэктесты, пересборка всего, audit | [ЧАСТИЧНО]: компакция ЕСТЬ; offsite-копии НЕТ (R1 — ретеншен-apply ни разу не выполнялся) |
| Чекпоинты состояния | периодическая свёртка | локально + COLD | быстрый старт проекций (1.06 с vs 382 с) | [ЕСТЬ] (M-48; cron ещё не стрелял по расписанию) |
| Research-датасеты | export v1/v2 (format.md) | файлы/Parquet | backtest/grid | [ЕСТЬ] (батч) |

**Гарантии консистентности:**
- Каждая проекция несёт **watermark**: `(последний применённый seq, версия кода
  редьюсера)`. Ответ клиенту может нести staleness-метку от watermark.
- **Пересборка = replay** от чекпоинта (или с нуля) тем же детерминированным кодом.
  Проекция не бэкапится как истина — бэкапится только event-store (+ чекпоинты как
  ускорение).
- **Расхождение проекции с журналом** (recon-джоб сверяет контрольные свёртки
  `[verify-at-impl]`): проекция объявляется stale (fail-closed: помечаем, не врём),
  алерт P1, автоматическая пересборка от последнего чекпоинта. Никогда не «чиним»
  проекцию ручной записью — правка руками read-модели запрещена (PL-I-2).
- **Смена версии редьюсера** = новая проекция рядом + переключение читателей (blue/green
  на уровне проекции), старая удаляется после сверки.

**Маршрутизация запроса по возрасту данных:**

```
        запрос клиента (WS-подписка / REST история / research job)
                             │
                   ┌─────────┴──────────┐
                   │ роутер по возрасту │  (идея Data Fabric hft-core-rs,
                   └─────────┬──────────┘   реализация — наша, поверх проекций)
        ┌────────────────────┼───────────────────────┐
   «сейчас/минуты»      «дни-месяцы»           «месяцы-годы / полная история»
        │                    │                       │
        ▼                    ▼                       ▼
  HOT-проекция          WARM-индекс             COLD-архив → batch-replay
  RAM, снапшот+push     колоночное чтение       research-compute / пересборка
  p50 &lt; мс `[v-a-i]`    p50 десятки мс `[v-a-i]` минуты-часы, офлайн
```

## §15. Multi-tenancy (изоляция, квоты, тарифы)

Природа данных делает multi-tenancy дешёвым: **рыночные данные общие для всех** (нет
per-tenant рыночного состояния), пользовательские — шардируются тривиально (Postgres,
row-level `user_id`/`org_id`). Изоляция:

1. **Данные.** Postgres: RLS/скоуп по tenant [ПЛАН]. Event-store — общий, read-only для
   всего пользовательского пути; персональных записей там нет (§13).
2. **AuthN/AuthZ.** Auth.js (OAuth/email) → сессия → короткоживущий JWT для gateway-serve
   с claims: `{user_id, tier, allowed_channels, quotas, exp}`. Rust верифицирует подпись
   и применяет claims локально — без похода в БД на каждый фрейм. [ЧАСТИЧНО: JWT HS256
   verify есть; tier-claims нет.] Ротация ключа и переход на Ed25519 `[verify-at-impl]`.
3. **Квоты и rate-limit — на КАЖДОЙ поверхности, fail-closed:**
   - gateway-serve: cap одновременных WS-соединений (глобальный + per-user), cap подписок
     на соединение, bytes/s per-connection budget, slow-consumer policy (§16). Невалидная
     конфигурация лимита = отказ старта (урок R7: parse-error → unbounded — запрещено).
   - app-API: rate-limit per-user/per-key (Fastify/Next middleware) [ПЛАН].
   - Agent Runtime: бюджет tool-calls и LLM-токенов per-user/период; политика агента —
     обязательный блок (AlphaQuant §11.2 Policy) [ПЛАН].
   - research-compute: очередь job'ов с квотами compute-минут по тарифу [ПЛАН].
4. **Тарифная модель (AlphaQuant §15) → технические ручки:**

| Тариф | Ориентир | Что режем технически |
|---|---|---|
| Free / Learn | воронка | delayed/replay-данные (без live WS), базовый chart, лимит Tutor-сессий, decision-journal ограничен |
| Trader | $29–49/мес | real-time order flow: N символов, M соединений, alerts, полный decision-journal |
| Pro | $79–149/мес | multi-exchange, advanced replay (глубина истории), execution-analytics (позже), options (позже) |
| Quant | $199–499/мес | historical event data, compute-квоты backtest, агенты, API |
| B2A / Enterprise | usage+contract | Tool API, agent gateway, SLA — ПОЗЖЕ (§0) |

   Все ограничения enforce'ятся на сервере (claims/квоты), не в UI (PL-I-5).
   *Оговорка прав на данные:* включение ПЛАТНОЙ отдачи рыночных данных зависит от
   отложенного founder-решения по правам (§20); к этому моменту включается
   лицензионный гейт LIC-I (§22) — архитектурно готов заранее, в MVP не блокирует.
5. **Изоляция сбоев между tenant'ами** = изоляция ресурсов: per-connection бюджеты в
   gateway-serve, cgroup-лимиты сервисов (R10a), отдельные пулы app-плоскости. Один
   пользователь (или один агент в цикле) не должен уронить fan-out остальным.

## §16. Read-path под десятки тысяч пользователей

Требование первой версии: десятки тысяч зарегистрированных; допущение по одновременным
live-соединениям — ~10–20% базы, т.е. **порядка 2–10 тыс. одновременных WS**
`[verify-at-impl]`. Сегодняшний gateway-serve это НЕ выдержит (R7: N клиентов = N полных
сканов журнала, соединения без cap) — при SaaS это не HIGH-риск, а **блокер
существования**. Целевая конструкция:

```
                event-store tail (один процесс, один курсор)
                              │
                    ┌─────────▼─────────┐
                    │  SHARED TAILER    │  ОДИН проход по журналу на процесс
                    │  → HOT-редьюсеры  │  (не N; M-39-класс) [ПЛАН]
                    └─────────┬─────────┘
                              │ обновления состояния
              ┌───────────────▼────────────────┐
              │ КАНАЛЫ ПУБЛИКАЦИИ (per topic:  │
              │ venue×symbol×серия×разрешение) │
              │ snapshot-кадр + дельта-поток   │
              └───┬──────────┬──────────┬──────┘
        broadcast │          │          │   fan-out O(topics), НЕ O(clients×журнал)
             ┌────▼───┐ ┌────▼───┐ ┌────▼───┐
             │ conn 1 │ │ conn 2 │ │ conn N │   per-conn: очередь с cap,
             │ queue  │ │ queue  │ │ queue  │   backpressure, slow-consumer:
             └────────┘ └────────┘ └────────┘   drop дельт → пересинхронизация
                                                снапшотом (НЕ буферизация до OOM)
```

Опорные точки (все `[verify-at-impl]`, замерить на нагрузочном стенде до GA):
- **Полоса:** бинарные серии ~1–2 KB/с на подписку ликвидного символа (замер L2Delta
  ~1.5 KB/с) ⇒ 10 тыс. соединений × 2 подписки ≈ 20–40 MB/с ≈ 160–320 Мбит/с — уже
  порог одной cpx32-NIC и аргумент за выделенный fan-out-узел (§23.2) и агрегированные
  разрешения для дешёвых тарифов (Free получает 1-секундные кадры, не 100 мс).
- **Снапшот-при-подключении** — из HOT-проекции (RAM), не сканом журнала; вход новых
  клиентов не создаёт IO-шторма. Чекпоинты [ЕСТЬ] это уже умеют для процесса.
- **Cap'ы точные** (принцип §1): глобальный cap соединений, per-user cap, cap подписок,
  cap очереди фреймов. Переполнение = отказ с кодом, не деградация всех.
- **Деградация по ступеням:** (1) slow consumer → снапшот-ресинк; (2) перегрузка канала →
  укрупнение разрешения (100 мс → 1 с) с явной меткой в фрейме; (3) перегрузка узла →
  отказ новых соединений (cap), существующие живут; (4) отказ HOT-проекции → stale-метка
  + reconnect-план, НЕ выдача устаревшего как живого (класс R5: staleness в типе).
- **Горизонтальное масштабирование:** fan-out-узлы реплицируют HOT-состояние от одного
  shared-tailer'а (или каждый тейлит COLD-реплику журнала `[verify-at-impl]`); клиенты
  распределяются LB по узлам. Журнал один — писатель один; читающие узлы — сколько нужно.

## §17. Формат рыночных данных: L2Delta обязателен (предусловие продукта)

**Факт (замер 2026-07-14, docs/06 §2):** сейчас пишем полный `L2Snapshot` 20–31 KB
(1800–2850 уровней) раз в секунду на каждый поток venue×symbol — это **~96% байт журнала
(8.83 GB/сут сырых)**. Биржа при этом шлёт диффы каждые 100 мс — мы их схлопываем и
**выбрасываем**; исключение — BTC, где M-18 уже пишет сырой `L2Delta` (variant 6 в схеме;
`book` умеет apply_delta).

**Почему это блокер продукта, а не оптимизация хранения.** Первый wedge — AI Tutor +
Scalper Workspace на order-flow ядре. Их несущие виджеты и события — heatmap, footprint,
DOM-replay, «liquidity pull, replenishment, absorption» (AlphaQuant §7.4, §9.1), spoofing
radar и liquidity tracker (docs/07 §14) — существуют **внутри секунды**. На секундных
срезах внутрисекундной динамики книги нет физически; никакой бэктест не восстановит то,
чего нет в журнале. То есть на текущем формате записи **недостижимы ОБА Workspace первого
wedge** — и заодно event-level replay как moat (AlphaQuant §13 «event-level history»).

Решение (связка docs/06 §5.1 — открытый вопрос закрывается так):
1. **`milestones/M-45-persist-l2delta.md` (PLANNED) повышается до ПРЕДУСЛОВИЯ ПРОДУКТА**,
   сразу после M-40/бэкапа: расширить L2Delta-эмиссию с BTC-only на символы кокпита.
   Механизм есть (M-18), CT-RFC не нужен.
2. **Инверсия ролей:** L2Delta (100 мс) — основной поток книги; `L2Snapshot` — редкий
   якорь для ресинка/перемотки (частота якоря 10–30 с — дизайн-решение M-45 п.2).
3. **Побочный эффект — объём ПАДАЕТ:** дифф ~1.5 KB/с против снапшота 20–31 KB/с на
   ликвидный символ (замер M-45: диффы в 5–10× дешевле); с редким якорем журнал сжимается
   при росте fidelity (оценка §5.1: 2.5–3× сверх zstd `[verify-at-impl]`).
4. **Ограничение честности:** Binance/HL не дают MBO (order-level); spoofing/refill —
   навсегда net-level-инференсы, размечаются провенансом `orderflow_inference:
   "net-level, no MBO"`, не выдаются за факт (PL-I-7). Forward-only: прошлую
   суб-секундную историю не восстановить — каждый день промедления теряет данные продукта.

## §18. Source Adapter — заменяемость источника данных (первоклассный шов)

**Решение founder'а (2026-07-29):** права на данные решаются к моменту продакшена
(согласие бирж ЛИБО покупка у провайдера — §20); до этого работаем на текущих данных
(Binance spot/futures + HL). Требование к архитектуре из этого решения: **замена одного
источника данных на другой должна быть ОЧЕНЬ ПРОСТОЙ** — без изменений потребителей и без
миграции журнала. Отсюда шов «Source Adapter»:

```
  ИСТОЧНИКИ (взаимозаменяемы)                 ПОТРЕБИТЕЛИ (не знают источника)
 ┌─────────────────────────┐
 │ прямой WS биржи [ЕСТЬ]  │──┐
 │ (venue-binance, -futures│  │   ┌──────────────────────┐
 │  venue-hyperliquid)     │  │   │   SOURCE ADAPTER     │      ┌────────────────┐
 ├─────────────────────────┤  ├──▶│ один интерфейс:      │─────▶│ event-store    │
 │ лицензированный         │  │   │ поток нормализованных│ T1   │ (сегмент несёт │
 │ провайдер REST/файлы    │──┤   │ T1 `Event` + мета    │      │ source/proven./│
 │ (Amberdata/Kaiko/Tardis)│  │   │ источника в заголовке│      │ epoch_id)      │
 │ [ПЛАН]                  │  │   │ сегмента             │      └───────┬────────┘
 ├─────────────────────────┤  │   └──────────────────────┘              ▼
 │ исторический дамп [ПЛАН]│──┤        замена источника =    book · проекции · кокпит
 │ (M-16-класс импорт)     │  │        замена адаптера +     · research · gateway —
 ├─────────────────────────┤  │        смена метки источника  видят ТОЛЬКО контракт
 │ ончейн-нода (HL) [ПЛАН] │──┘        (потребители и журнал  `Event`, не источник
 └─────────────────────────┘           НЕ меняются)
```

**Что для этого шва УЖЕ есть [ЕСТЬ]** (проверено в коде 2026-07-29 — шов не выдуман,
он достроен из работающих механизмов):
- единая T1-схема `Event` в `crates/contracts`; три venue-адаптера уже живут за одним
  контрактом (`venue-binance`, `venue-binance-futures`, `venue-hyperliquid`);
- `SegmentHeader` несёт `source: DataSource {OwnCapture | Vendor | Synthetic}` +
  `provenance` + `epoch_id` (T1, CT-RFC-02); «журнал бессмертен — задним числом источник
  не проставить» уже записано в контракте;
- **изоляция эпох fail-closed:** reuse сегмента требует совпадения заголовка
  (source/provenance/epoch_id + SCHEMA_VERSION), при несовпадении открывается НОВЫЙ
  сегмент (`decide_open_segment`) — механизм несмешения уже существует;
- **`EpochFilter` обязателен на чтении** (`OwnCaptureOnly` / `Explicit` / `All`,
  `journal::stream`) — читатель обязан НАЗВАТЬ, какие эпохи/источники он согласен
  смешивать; «не заметить» чужой источник нельзя.

**Что достраивается (T1-изменение — ТОЛЬКО через contract-RFC, `05-contract-layer.md`
§4, НЕ свободная правка) [ПЛАН]:**
1. Расширение метаданных источника в `SegmentHeader`: `source_kind`
   (`direct-exchange` / `licensed-provider` / `onchain` / `historical-dump`) и
   `license_class` (`own-onchain` / `licensed-redistribution` / `internal-only`) —
   уточнение существующего `DataSource`, той же RFC-дисциплиной.
2. **Правило несмешения** распространяется на источник: события разных источников не
   смешиваются в одном сегменте — переиспользуется существующий механизм эпох (TD-031/
   M-18-класс), второй механизм НЕ изобретается.
3. `license_class` на первом этапе — **метаданные + задел**: fail-closed проверка
   лицензионного класса на read-path (LIC-I, §22) — требование этапа монетизации данных,
   НЕ MVP; сейчас барьер работе на имеющихся данных не строится.

**Оракул эквивалентности источников (SRC-I, §22) — обязательное условие ЛЮБОЙ смены
источника.** Смена источника без доказательства эквивалентности молча сдвинет все
метрики (наш повторяющийся класс дефекта: «тихая порча, прошедшая зелёные гейты»).
Процедура промоушена нового источника: параллельный сбор из старого и нового источника
на одном интервале → детерминированная сверка потоков (цены, объёмы, тайминги, число
событий) → отчёт о расхождениях против объявленного допуска → расхождение выше допуска =
отказ промоушена (fail-closed), не предупреждение в логе.

## §19. AI-слой: Agent Runtime

Один Agent Runtime (Node/TS [ПЛАН]), разные роли — контрактные конфигурации поверх общих
tools, не отдельные приложения (AlphaQuant §7.1). Роли §7.2: Market Observer, AI Tutor,
Trade Copilot, Risk Guardian, Journal Analyst, Options Analyst (позже), Research Agent,
Execution Agent (позже, §21).

```
   Next.js UI ◀── SSE/WS: AI feed, панель Tutor, chips/annotations
        │ вопросы/выделения (Ask AI, Explain, участок графика)
        ▼
  ┌─────────────────────────── AGENT RUNTIME (Node/TS) ───────────────────────────┐
  │ session manager · role configs · scheduler (continuous/event/manual)          │
  │ policy engine (бюджеты, allowed tools, approvals) · память (Postgres)         │
  │        │                                                                      │
  │        ▼ tool calls (типизированные, ВСЕ через API, ВСЕ аудируются)           │
  │  READ tools               WRITE tools (только в №2)      NEVER                │
  │  · market state/серии ────▶ gateway-serve REST/WS        · запись event-store │
  │  · event engine события    · annotation/alert draft      · отправка ордера    │
  │  · similarity/replay       · decision-journal note       · смена live-параметр│
  │  · backtest job (research) · spec/гипотеза               · чужие API-ключи    │
  │  · decision-journal read   · curriculum update                                │
  │        │                                                                      │
  │        ▼                                                                      │
  │  LLM-сервис (внешний API, мультимодальный опционально) — вне детерминизма    │
  └────────┬──────────────────────────────────────────────────────────────────────┘
           ▼
   AUDIT (Postgres, append-only): tool calls, model+version, evidence, вывод,
   approvals, стоимость — полный trail (AlphaQuant §12.1 Audit)
```

Принципы:
1. **AI Event — единая модель** (AlphaQuant §7.3): один eventId для chip/карточки/полного
   сообщения; поля timestamp, instrument, observation, interpretation, importance,
   horizon, supporting/conflicting evidence, confirmation, **invalidation**, data
   quality, chart annotations. Уверенность — Low/Medium/High + счётчик evidence,
   **никаких необоснованных процентов**. Контракт версионируется (§13 п.3).
2. **LLM не смотрит на пиксели и не считает индикаторы.** Детерминированный слой (event
   engine, Rust [ПЛАН — M-46-класс]) превращает микроструктуру в структурированные
   события (absorption, exhaustion, CVD-divergence...); AI-Context Composer собирает
   компактный снапшот; LLM интерпретирует. Человек и AI видят ОДНИ числа (docs/07 §7).
3. **Границы A/B/C расширяются с «квант-деск founder'а» на «агенты пользователей»**
   (правка `docs/03` — отдельный doc-milestone):
   - **A (код/анализ):** агент читает рынок и пишет ТОЛЬКО в свои зоны (research-spec,
     annotation, note). Для пользовательских агентов зона = их tenant-данные в Postgres.
   - **B (реестр):** то, что «исполняется» (правило, alert, позже стратегия), существует
     только как версионированная запись реестра со статусом и code_hash; движок исполняет
     только записи реестра, не «текст из чата».
   - **C (подписанное решение):** любой переход, двигающий деньги или live-параметры, —
     только явное человеческое подтверждение (для пользователя — approval в UI с
     аудитом; для платформы — Ed25519-подпись founder'а). Расширение C на пользователей:
     human approval для live-ордеров по умолчанию (AlphaQuant §12.2) — актуально в фазе
     execution.
4. **Permission-модель** (AlphaQuant §12.2, принимается как есть): раздельные
   read/write/execute; никаких withdrawal-permissions; блокировка агента при stale data /
   exchange degradation / нарушении risk policy; полный audit и kill switch агента
   (остановка runtime-процесса — НЕ путать с торговым killswitch §21).
5. **Стоимость под контролем:** LLM-вызовы — по бюджету тарифа; тяжёлые роли (Tutor
   continuous) — событийные триггеры + троттлинг, не постоянный полл `[verify-at-impl]`
  (риск Costs из AlphaQuant §17).
