# Runbook — `journal tail unreadable` (recorder не поднялся)

Источник: M-49 (JR-I-8, TD-049). Этот документ — то, на что указывает диагностика
`open_with`, когда хвост журнала физически повреждён и recorder отказался стартовать.
Аудитория — оператор, который увидел в логах/алертах строку с маркером
`journal tail unreadable`.

## Почему recorder отказал (а не стартовал «как есть»)

Журнал append-only. `next_seq` обязан продолжать историю, уже лежащую на диске — иначе
новая запись ляжет ПОВЕРХ уже занятого диапазона `seq`, и реплей воспроизведёт эту порчу
бит-в-бит: откатить нечем. Раньше recorder в этой ситуации молча стартовал с
`journal.meta` (а при восстановлении из холодного хранилища `journal.meta` ОТСУТСТВУЕТ —
ретеншен выгружает сегменты, не мету — так что `meta_seq = 0`), что означало запись с нуля
поверх существующей истории. Замер architect'а: до фикса M-49 усечённый `.zst`-хвост или
битый v2-заголовок давали `open_with = Ok` и перекрывали до нескольких сотен уже
записанных событий без единой ошибки в логе.

Поэтому сейчас: сегмент с максимальным индексом существует и не пуст, но его последний
`seq` установить не удалось → `open_with` возвращает `Err`, сбор данных останавливается
ЯВНО (минуты простоя), а не портится МОЛЧА (необратимо).

Сообщение об ошибке всегда называет конкретный файл, например:

```text
journal tail unreadable: segment-00000007.jrnl.zst — last seq could not be established
(compressed segment header unreadable: ...). Recorder refuses to start: starting from
journal.meta would REUSE seq already present in the log. Action: re-fetch this segment
from cold storage, or declare next_seq explicitly (runbook: docs/ops-journal-tail-unreadable)
```

## Шаг 1 — прочитать ошибку

Имя проблемного файла — в самом сообщении (первое слово после `journal tail unreadable:`).
Это либо `segment-NNNNNNNN.jrnl` (сырой сегмент), либо `segment-NNNNNNNN.jrnl.zst`
(сжатый). Причина отказа — в скобках сразу после имени: усечение (`truncat`), несовпадение
CRC заголовка (`crc mismatch`), обрыв zstd-потока (`unreadable`) и т.п.

## Шаг 2 — проверить целостность файла

Для сжатого сегмента (`.jrnl.zst`):

```bash
zstd -t /path/to/journal/segment-NNNNNNNN.jrnl.zst
echo "exit=$?"
```

`exit=0` и «is compressed» — поток декомпрессируется целиком (порча тогда, скорее всего,
в v2-заголовке ПОСЛЕ распаковки, не в самом zstd-потоке — см. Шаг 3, вариант «частичная
порча»). Ненулевой exit / `Decoding error` — поток физически повреждён или усечён
(обрыв выкачки/копирования).

Для сырого сегмента (`.jrnl`) сравните размер файла с ожидаемым (если есть лог/метрика
прежнего размера) — резкое уменьшение указывает на усечение при копировании/крахе диска.

## Шаг 3 — перекачать сегмент из холодного хранилища

Штатный путь восстановления: у выгруженного (`retention`) сегмента ДОЛЖНА быть холодная
копия (Storage Box / смонтированный путь — `RetentionPolicy.cold_root`). Перекачайте
именно этот файл заново поверх повреждённого:

```bash
cp /cold/root/segment-NNNNNNNN.jrnl.zst /path/to/journal/segment-NNNNNNNN.jrnl.zst
zstd -t /path/to/journal/segment-NNNNNNNN.jrnl.zst && echo OK
```

После успешной перекачки перезапустите recorder — если целостность восстановлена,
`open_with` продолжит историю штатно (`seq` без разрыва), декларация из Шага 4 не нужна.

Если холодной копии нет (сегмент никогда не выгружался, либо сама холодная копия тоже
повреждена) — переходите к Шагу 4.

## Шаг 4 — крайний случай: сегмент невосстановим

Если перекачать нечего (холодной копии нет) или перекачанная копия ТОЖЕ не проходит
`zstd -t` — сегмент признаётся невосстановимым. Это осознанный разрыв в истории `seq`,
а не рутинная операция; выполняется только после того, как вариант из Шага 3 исчерпан.

1. **Карантин.** Уберите повреждённый файл из активного каталога журнала (не удаляйте —
   переместите, он может пригодиться для судебного разбора):
   ```bash
   mkdir -p /path/to/journal/quarantine
   mv /path/to/journal/segment-NNNNNNNN.jrnl.zst /path/to/journal/quarantine/
   ```
   Карантин — ТОЛЬКО ручное действие оператора. `open_with` файлы данных не перемещает,
   не переименовывает и не удаляет (rev3 M-49): горячий путь старта recorder'а не трогает
   состояние каталога, кроме самой декларации из следующего пункта. Выполните этот шаг
   ДО перезапуска recorder'а с декларацией.

2. **Декларация.** Определите, с какого `seq` продолжать (строго больше максимального
   ЧИТАЕМОГО `seq` в оставшейся истории — recorder откажет, если это не так), и положите
   в каталог журнала файл `journal.force-next-seq.json`:
   ```json
   {
     "next_seq": 512,
     "reason": "segment-00000007.jrnl.zst невосстановим: bit-rot, холодной копии нет",
     "declared_at_ms": 1785362203969
   }
   ```
   `reason` — обязателен и осмыслен: он сохранится в аудит-следе
   (`journal.force-next-seq.applied.json`) после применения.

3. **Понимайте последствие.** Эта декларация — явно названный разрыв в `seq`: события
   между максимальным читаемым `seq` и объявленным `next_seq` потеряны безвозвратно (тот
   же класс решения, что `pruned_without_checkpoint_coverage` в ретеншене, M-38b — обход
   разрешён, но обязан быть НАЗВАН, не тихим).

4. Перезапустите recorder. При валидной декларации `open_with` стартует, применяет
   декларацию ОДИН РАЗ (файл переименовывается в `journal.force-next-seq.applied.json`,
   `reason` сохранён), и запись продолжается с объявленного `next_seq`. При невалидной
   декларации (`next_seq` ≤ максимального читаемого `seq`) recorder откажет снова — это
   защита от того, чтобы сама декларация случайно стала каналом seq-reuse под давлением
   инцидента.

## Что НЕ делать

- Не удаляйте каталог журнала целиком — это гарантированная потеря ВСЕЙ истории, а не
  только повреждённого сегмента.
- Не редактируйте повреждённый сегмент вручную (обрезка/дозапись байт) в надежде
  «починить» его — журнал читается по формату (magic + length-prefixed frames + crc32),
  ручная правка почти всегда даёт файл, неотличимый от порчи для парсера.
- Не понижайте `next_seq` в декларации ниже читаемого максимума «чтобы recorder точно
  стартовал» — это ровно тот seq-reuse, от которого защищает весь этот механизм; recorder
  такую декларацию отклонит с объяснением.
