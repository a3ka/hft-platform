# 03 — Контракт интеграции: движок ↔ квант-деск как единое целое

STATUS: DESIGN v1 (2026-07-10, Fable). Родственные: 01 (движок), 02 (квант-деск).
Этот документ — шов. Он отвечает на «как Rust-движок и LLM-команда работают как
единое целое, но безопасно»: **три границы (данные, код, параметры) + одно правило
направления (LLM только на дизайн-тайме; рантайм детерминирован)**.

---

## §1. Единое целое = один журнал + три контролируемые границы

Движок и деск живут вокруг ОДНОГО артефакта — журнала событий. Деск читает его
(история для research), пишет в него не напрямую, а через три типизированные границы:

```
              ┌───────────────── QUANT DESK (LLM, design-time) ─────────────────┐
   журнал ──▶ research-cli (compute) ──▶ reports ──▶ critic ──▶ FOUNDER (подпись)
   (чтение)                                                          │
              граница A: код сигнала        граница B: реестр+веса    │ граница C:
              (PR в crates/signals)         (signals.json)           │ Ctl(ParamChange)
                    │                              │                 │  (подписанное событие)
                    ▼                              ▼                 ▼
   ┌───────────────────────────── ENGINE (Rust, runtime) ──────────────────────────┐
   │  book → signals → alpha(веса) → portfolio(sizing) → strategy → risk → oms → venue │
   │                          всё детерминировано; журнал пишется                      │
   └────────────────────────────────────────────────────────────────────────────────┘
```

Правило направления (**INTG-I-1, BINDING**): информация из LLM попадает в рантайм
ТОЛЬКО через границы A/B/C, каждая — с человеческой подписью на промоушене. LLM
не имеет процесса/сокета/файла, влияющего на живую торговлю в обход A/B/C.

## §2. Граница B — Реестр сигналов (`research/registry/signals.json`)

Единый источник правды, что движок исполняет. Каждая запись:

```json
{
  "signal_id": "S-001-obi-asym",
  "version": 3,
  "code_hash": "<sha256 модуля в crates/signals/>",
  "status": "candidate | paper | live | retired",
  "params": { "d_bid_pct": 3.0, "d_ask_pct": 8.0, "theta": 0.62, "horizon_ms": 1500 },
  "ensemble_weight": 0.0,           // 0 пока не live; меняется только через границу C
  "validation_report": "R-014",
  "promoted_by": "D-009",           // ссылка на подписанное решение
  "venue_scope": ["hyperliquid:BTC"]
}
```

- Движок при старте грузит реестр; исполняет ТОЛЬКО `status==live && weight>0`;
  `paper` сигналы считаются, но их forecast идёт лишь в paper-приёмник (не на биржу).
- `code_hash` в реестре обязан совпадать с хэшем модуля в `crates/signals/`
  (verify-гейт: реестр не ссылается на несуществующий/изменённый код).
- **INTG-I-2:** статус может двигаться candidate→paper→live только при наличии
  ссылки на `decisions/D-NNN` с подписью founder'а (см. §3); движение назад
  (→retired) допускается автоматически decay-watch'ем, но live→retired тоже логируется решением.

## §3. Граница C — изменение параметров/весов в рантайме (очередь решений, HDP)

Ни веса ансамбля, ни лимиты, ни параметры сигнала НЕ меняются правкой конфига у
живого процесса. Механизм (перенос EINHARD human_decision_queue дословно):

1. `portfolio-analyst` или founder формирует **предложение**: `{what, from, to,
   rationale, report_ref}` (напр. «вес S-001 0.0→0.15, основание R-014 + paper 3 нед»).
2. Предложение попадает в очередь решений (файл + дашборд).
3. **Founder подписывает** (Ed25519; ключ у человека). Неподписанное — не применяется.
4. Движок применяет атомарно, эмитит `Ctl(ParamChange{signed})` в журнал; изменение
   попадает в реплей (можно доказать, кто/когда/на каком основании поменял).

**INTG-I-3 (RED, зеркало RK-I-10):** любое изменение весов/лимитов/параметров без
подписанного `Ctl(ParamChange)` в журнале → невозможно (нет иного пути записи в
рантайм-конфиг); тест утверждает отсутствие альтернативной поверхности записи.

## §4. Граница A — код сигнала (scope-guard)

- Квант-агенты (`signal-engineer`) пишут ТОЛЬКО в `crates/signals/**` и `research/**`.
  `journal/venues/book/oms/risk/killswitch/portfolio/strategy` — запрещены (arch-lint +
  reviewer, как EINHARD scope-guard). Sacred: `risk/` тесты (RK-I-*) агенты не трогают.
- Новый сигнал = PR: модуль + unit-тесты + детерминизм-тест + SignalSpec-карточка;
  ревью-гейт: чистая функция над `Event`, без I/O, без часов, без доступа к будущему.
- `code_hash` считается по мёржу; попадает в реестр только через границу B.

## §5. Замкнутый цикл (как это «крутится как единое целое»)

```
[движок live/paper] ─пишет→ journal
       │                        │
       │ (feedback: fills,       └─читает→ research-cli ─→ reports ─→ critic ─→ founder
       │  slippage, sim-vs-live)                                              │
       │                                                              подпись (A/B/C)
       └──────────────────── новые/перекалиброванные сигналы ◀───────────────┘
```

- Живая торговля порождает данные (наши fills, реальный slippage, sim-vs-live
  дивергенция) → деск учится на СВОИХ данных, не только на рыночных → перекалибровка
  → подпись → назад в движок. Это и есть moat: цикл замыкается на собственном
  исполнении.
- Частота петли: research крутится 24/7 (compute); человеческие подписи — по мере
  созревания отчётов (дни/недели). Горячий торговый цикл — миллисекунды, полностью
  внутри движка, без петли LLM.

## §6. Сквозные инварианты интеграции (RED)

| ID | Инвариант | Механизм |
|---|---|---|
| INTG-I-1 | LLM влияет на рантайм только через A/B/C с подписью | нет иного write-пути; arch-lint + типы |
| INTG-I-2 | Промоушен статуса только по подписанному decisions/D-NNN | verify-гейт над реестром |
| INTG-I-3 | Веса/лимиты/параметры — только через подписанный Ctl(ParamChange) | зеркало RK-I-10; тест отсутствия обхода |
| INTG-I-4 | Реестр не ссылается на несуществующий/дрейфнувший код (code_hash) | verify-гейт |
| INTG-I-5 | paper-сигнал физически не может отправить ордер на биржу | приёмник paper ≠ live gateway; типовой барьер |
| INTG-I-6 | trials-ledger append-only; deflated-Sharpe считается от него | verify-гейт над ledger |
| INTG-I-7 | Отрицательные результаты (KILL) не удаляются | append-only critiques/hypotheses |
