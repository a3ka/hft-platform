# Runbook — ops-watchdog алертинг

Источник кода: `crates/ops/src/watchdog.rs` (чистые детекторы), `crates/ops/src/watchdog_cycle.rs`
(слой склейки одного такта cron'а — якорь застоя, история тренда диска, дедуп-дисциплина),
`crates/ops/src/format.rs` (форматирование), `crates/ops/src/transport.rs` (доставка),
`crates/ops/src/state.rs` (дедупликация/состояние), `crates/ops/src/bin/ops-watchdog.rs`
(cron-бинарь, всё I/O).

Переделка по PR-гейту `research/reviews/R-005-alerting.md` (2026-08-01) закрыла семь находок:
интервал-независимость `WD-SEQ-STALLED` (F-1), утечку токена в лог (F-2), ложные тревоги диска
на ночной компакции/ретеншене (F-3), «не смог оценить» больше не стирает дедуп-память (F-5),
новый код `WD-CRON-FAILED` читает `<job>.alert` немедленно (F-6), рестарт-петля продолжает
сообщать вместо однократного сообщения (F-7). Детали — в `research/reviews/R-005-alerting.md`
и doc-комментарии `watchdog_cycle.rs`.

Второй круг (`research/reviews/R-008-alerting-rev2.md`, REJECTED → закрыто) дозакрыл F-2
полностью — ветка неуспешного HTTP-статуса Telegram Bot API тоже больше не печатает тело
ответа (см. «Секреты в логах» ниже).

Тот же второй круг добавил новый код `WD-SEQ-REGRESSED` (F-8): регрессия `next_seq`
(пересозданный/восстановленный том журнала) раньше застревала в вечном ложном
`WD-SEQ-STALLED`, потому что якорь прогресса никогда не переезжал назад.

Мотив (не формальность): предыдущий проект founder'а потерял 14 дней данных и 335 млн
тиков, потому что сбор встал, а никто не узнал — здоровье было видно только по ssh.
`ops-watchdog` — cron-процесс, который читает состояние recorder'а (heartbeat, cron-маркеры,
docker) каждые несколько минут и алертит человека, если что-то из перечисленного ниже
сломалось, ДО того как это станет невосполнимой потерей.

## Что проверяется и почему именно так (пороги — `watchdog::Thresholds::default()`)

| Код | Условие | WARNING | CRITICAL | Обоснование порога |
|---|---|---|---|---|
| `WD-HB-MISSING` | `recorder.heartbeat` отсутствует/не парсится | — | сразу | нет файла → recorder либо не стартовал, либо том пропал |
| `WD-HB-STALE` | heartbeat не обновлялся `now − ts_wall_ms` | 60с | 180с | recorder тикает heartbeat каждые 10с (код: `crates/recorder/src/lib.rs`, `Duration::from_secs(10)`); Docker healthcheck (`docker-compose.yml`) уже считает heartbeat протухшим на 60с — WARNING синхронизирован с этим; CRITICAL — втрое дальше (18 пропущенных тиков) |
| `WD-NOT-WRITABLE` | heartbeat несёт `writable:false` | — | сразу | журнал перестал принимать записи (disk-guard/fs ошибка) |
| `WD-SEQ-STALLED` | `next_seq` не растёт с момента ПОСЛЕДНЕГО НАБЛЮДАВШЕГОСЯ ПРОГРЕССА (якорь, не «прошлая проверка» — R-005 F-1) | — | сразу | САМЫЙ опасный класс: процесс жив (heartbeat свежий), а данные не идут — healthcheck этого не видит вообще. Якорь двигается ТОЛЬКО когда `next_seq` реально вырос, поэтому детектор срабатывает при ЛЮБОМ интервале cron'а (раньше выключался интервалом <60с — воспроизведение в R-005) |
| `WD-SEQ-REGRESSED` | `next_seq` УМЕНЬШИЛСЯ относительно якоря прогресса | — | сразу | R-008 F-8: признак seq-reuse (пересозданный/восстановленный том журнала, откат сегмента — та же категория риска, что закрывали M-49/M-50). Якорь застоя сбрасывается на новое (меньшее) значение в этот же такт, чтобы `WD-SEQ-STALLED` не застревал в вечном CRITICAL, гоняясь за значением, которое сбор физически не может снова достичь. Обходит дедуп-окно целиком (как `WD-CONTAINER-RESTARTED`) — каждое срабатывание уже новый факт |
| `WD-DISK-LOW` | `free_bytes` низко / прогноз по тренду убыли, тренд считается по истории за окно обслуживания (2ч, минимум 30 мин накопленной истории — не по соседней паре сэмплов, R-005 F-3) | < 3×min_free ИЛИ <72ч до min_free | ≤min_free ИЛИ <24ч до min_free | замер на проде 2026-07-31: ~117 КБ/с убыли без ретеншена при free≈77.6 GiB, min_free=10 GiB; 72ч даёт запас поверх суточного ретеншен-цикла (04:07 UTC), 24ч — меньше одного цикла. Всплеск компакции/ретеншена усредняется в 2-часовое окно, не масштабируется на сутки |
| `WD-CONTAINER-MISSING` | контейнер не виден в `docker ps` | — | сразу | не запущен/упал |
| `WD-CONTAINER-UNHEALTHY` | контейнер виден, но не healthy | — | сразу | unhealthy/restarting/exited |
| `WD-CONTAINER-RESTARTED` | `RestartCount` вырос с прошлой проверки | сразу | — | контейнер падал и сам поднялся — human должен знать о факте, даже если сейчас healthy. Обходит дедуп-окно целиком (R-005 F-7): рестарт-петля продолжает сообщать, а не замолкает после первого сообщения |
| `WD-CRON-MISSING` | позитивный маркер cron-задачи (`<job>.last-success`, `job` ∈ `compaction`/`gateway-checkpoint`/`retention`) отсутствует | сразу | — | ни одного успешного прогона не зафиксировано |
| `WD-CRON-STALE` | позитивный маркер старше порога | 26ч | 48ч | задачи ежесуточные; 26ч — конвенция, уже задокументированная в `deploy/bin/journal-retention-cron.sh`; 48ч — двое суток пропущено подряд |
| `WD-CRON-FAILED` | `<job>.alert` присутствует — последний прогон УПАЛ (`deploy/README.md` §5(A)) | — | сразу | R-005 F-6: раньше читался ТОЛЬКО позитивный `.last-success`, упавший прогон был виден лишь через 26ч по `WD-CRON-STALE`. Срабатывает НЕЗАВИСИМО от свежести `.last-success`; нечитаемый таймстамп в маркере не отменяет алерт (fail-closed — сам факт файла = факт сбоя) |

Пороги живут в коде (`Thresholds::default()`), не только здесь — при расхождении код есть
источник правды, этот файл — объяснение "почему".

## Что делать при срабатывании

1. **`WD-HB-STALE` / `WD-SEQ-STALLED` / `WD-NOT-WRITABLE` / `WD-HB-MISSING`** (сбор данных
   под угрозой): зайти на VPS, проверить `docker ps` и `docker logs hft-recorder --tail 200`.
   Если контейнер не healthy/упал — см. п.3. Если контейнер healthy, но `next_seq` не
   растёт — venue-соединение могло замолчать без разрыва TCP; смотреть логи на предмет
   реконнектов/ошибок парсинга.
2. **`WD-SEQ-REGRESSED`**: `next_seq` уменьшился — ожидаемо ТОЛЬКО при осознанном пересоздании
   тома/восстановлении из бэкапа/откате сегмента. Если такого события не было — это
   потенциальный seq-reuse (M-49/M-50), останавливать торговлю и разбирать немедленно,
   реплей журнала после этого момента ненадёжен. Дедуп-окно на этот код не действует —
   сообщение приходит на каждую отдельную регрессию, а не один раз.
3. **`WD-DISK-LOW`**: проверить `df -h` на VPS и свежесть cron-маркеров ретеншена/компакции
   (`WD-CRON-*` — если они ТОЖЕ красные, вот и причина). Если ретеншен молчит — разобраться,
   почему (см. `deploy/README.md`), прежде чем место кончится.
4. **`WD-CONTAINER-MISSING` / `WD-CONTAINER-UNHEALTHY`**: `docker ps -a`, `docker logs`,
   `docker compose up -d` при необходимости. `WD-CONTAINER-MISSING` для `hft-recorder` —
   максимальный приоритет (сбор физически остановлен).
5. **`WD-CONTAINER-RESTARTED`**: не всегда срочно (уже поднялся), но требует разбора причины
   падения — посмотреть логи вокруг момента рестарта.
6. **`WD-CRON-MISSING` / `WD-CRON-STALE`**: проверить `/var/lib/hft/*.last-success` и логи
   соответствующего cron-задания (`/var/log/hft/*.log`), см. `deploy/bin/*-cron.sh`.
7. **`WD-CRON-FAILED`**: `cat /var/lib/hft/<job>.alert` — первая строка таймстамп сбоя, вторая —
   текст (exit-код и причина, разбор кодов — `deploy/README.md` §"Разбор `*.alert`"). Маркер
   гасится следующим успешным прогоном сам; вручную зачищать не нужно.

## Установка (после ревью — не входит в объём задачи engine-dev)

Бинарь: `cargo build --release -p ops --bin ops-watchdog` → `target/release/ops-watchdog`.
Обёртка для cron: `scripts/watchdog_cron.sh` (конвенция — как у `deploy/bin/*-cron.sh`:
позитивный heartbeat `WATCHDOG_LAST_RUN`, ALERT-маркер на сбой самого watchdog'а). Cron-строка
(предлагается, устанавливает reviewer/founder): каждые 5 минут.

```
*/5 * * * * root /root/hft-platform/scripts/watchdog_cron.sh >> /var/log/hft/watchdog.log 2>&1
```

Env для транспорта: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` — как только founder добавит их
в окружение VPS (например `/etc/environment` или systemd-юнит для cron), доставка в Telegram
включится без единой правки кода. До этого момента алерты идут в stdout (лог cron'а,
`/var/log/hft/watchdog.log`) — это уже рабочий канал: `tail -f` / grep по коду инцидента.

## Конфигурация (env, все опциональны — дефолты соответствуют прод-топологии VPS)

- `WATCHDOG_HEARTBEAT_PATH` — путь к `recorder.heartbeat`.
- `WATCHDOG_CRON_DIR` — каталог с `*.last-success` маркерами (по умолчанию `/var/lib/hft`).
- `WATCHDOG_STATE_PATH` — файл дедуп/prev-состояния (по умолчанию `/var/lib/hft/watchdog.state.json`).
- `WATCHDOG_CONTAINERS` — список контейнеров через запятую (по умолчанию `hft-recorder,hft-gateway-serve`).
- `WATCHDOG_HOST_LABEL` — метка хоста в сообщениях.
- `WATCHDOG_DEDUP_WINDOW_MS` — окно дедупликации на инцидент (по умолчанию 30 минут).
- `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` — см. выше.
- `TELEGRAM_API_BASE` — базовый URL Telegram Bot API (по умолчанию `https://api.telegram.org`).
  Опция существует для тестов (подмена мёртвым/локальным эндпоинтом офлайн); на проде не
  задавать.

## Секреты в логах

`TELEGRAM_BOT_TOKEN` вшит в URL запроса (требование Telegram Bot API) — сетевые ошибки
транспорта (DNS/TLS/таймаут/обрыв) редактируются ДО того, как попасть в лог cron'а (R-005 F-2):
сообщение несёт категорию сбоя (`timeout`/`connect`/...), но не сам URL/токен. HTTP-ошибки
САМОГО Telegram API (401/403/429 и т.п.) несут ТОЛЬКО числовой код статуса + каноническую
reason-phrase (генерируются локально, не эхо удалённой стороны) — тело ответа НЕ печатается
вообще (R-008 F-2 rev2): прокси/CDN/captive-portal/неверно настроенный `TELEGRAM_API_BASE`
может эхом вернуть URI запроса (а значит и токен) в теле ответа, и до rev2 это тело шло в лог
без редакции. Если в `/var/log/hft/watchdog.log` всё же обнаружится токен — это регрессия, а
не штатное поведение; см. `crates/ops/tests/red_ops_transport_redaction.rs`.

## Известные ограничения (на утро, честно)

- Watchdog у самого watchdog'а нет: если cron перестанет запускать `ops-watchdog` вовсе
  (crond умер, cron-файл не установлен), тишина будет такой же, как и раньше — backstop
  для ЭТОГО класса вне объёма задачи (аналог `WD-CRON-STALE`, но для самого watchdog'а).
  Обсудить с founder'ом отдельно (кандидат: сторонний внешний heartbeat-пингер вроде
  healthchecks.io, не требует кода в этом репозитории).
- Absolute-порог диска (`< 3×min_free`) на первом прогоне без накопленной 30-минутной истории —
  грубый; после накопления истории в пределах 2-часового горизонта (`disk_history` в состоянии)
  включается прогноз по тренду, устойчивый к разовому всплеску компакции/ретеншена (R-005 F-3).
