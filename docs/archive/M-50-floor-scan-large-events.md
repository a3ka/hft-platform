# M-50 — скан пола видит крупные события: `Known` не занижается размером фрейма (TD-053)

**Статус:** RED-набор ЗАКОММИЧЕН (проходимость доказана прототипом и откачена; ждёт critic → dev)
**Риск:** тот же класс, что закрывал M-49 — занижение пола → валидная «по проверке»
`journal.force-next-seq.json` → **seq-reuse**, необратимая порча append-only журнала.
**Severity:** TD-053 (заведён R-003 NOTE 2 как MINOR) — переоценка по замеру: минимум
**MAJOR** (архитектурно достижим СЕГОДНЯ, тихий fail-open на sacred-пути; смягчение — нужны
два условия одновременно: хвост читаемого префикса из одних крупных событий И ручная
декларация оператора). Формулировка «реальные события на два порядка меньше» **опровергнута
замером**: реальный максимум 68.8% порога, архитектурный потолок — 100.8%.
**Гейты:** critic (касание `crates/journal`, оценка ≥5 коммитов) → engine-dev → tester →
reviewer. risk-critic НЕ требуется (нет order-path; данные/ops — тот же вывод, что M-49).

## Замер (обязательное чтение: `research/measurements/td-053-event-size.md`)

- 4 614 851 реальное прод-событие (3 сегмента, включая 2 самых «тяжёлых» дня): максимум
  **45 113 B = 68.8%** порога 64 KiB. Ноль превышений — эмпирическое совпадение, не гарантия.
- Архитектурный потолок `L2Snapshot` (bucket-cap venue-binance, 3000 уровней/сторона):
  **66 032 B = 100.8%** порога — превышает БЕЗ единого изменения кода.
- `L2Delta` **не ограничен вообще** («персистит diff БЕЗ ПОТЕРЬ») и эмитируется в проде
  с M-18 (2026-07-21). M-45 дефект не создаёт — только увеличивает частоту «бросков костей».
- Синтетическая репродукция (1:1-порт `resync_max_seq`): поток `[Heartbeat seq=1]`
  `[валидный L2Delta seq=999, фрейм 99 031 B]` → скан вернул `Some(1)`. Событие невидимо.

## Дефект

`READABLE_SCAN_MAX_CARRY = 64 KiB` (кап переноса carry в `resync_max_seq`) против
санити-капа штатного ридера `read_frame_payload` = **64 MiB** (`segments.rs:443`). Скан
пола трактует фрейм, чей `len + 8 > 64 KiB`, как порчу и ресинкает на 1 байт ⇒ событие,
которое журнал ЧИТАЕТ, в пол НЕ попадает ⇒ `readable_floor` занижен ⇒ декларация с
`next_seq` внутри занятого диапазона проходит валидацию ⇒ seq-reuse. Доккоммент капа сам
признаёт: порог калиброван по фикстуре (~2.4 KiB `snap`), не по проду.

## Контракт (architect)

**JR-I-9 (полнота пола: размер не есть порча).** Терпимый скан пола
(`readable_floor` → `tolerant_max_seq_from_start` → `resync_max_seq`) **не имеет права
молча исключить из пола валидный фрейм, который штатный ридер крейта принял бы**. Для
любого CRC-валидного фрейма с `len` ≤ санити-капа ридера: либо его `seq` участвует в
`Known`, либо пол деградирует в `Unknown` (существующее состояние rev5 — отказ проверять
декларацию, оператор идёт по runbook). «`Known` с заниженным полом» запрещён. Оба свойства
rev5 — терпимость к порче И ограниченная память — сохраняются и не подлежат размену;
граница памяти распространяется и на РАЗМЕР ФРЕЙМА: пик не растёт ни с размером сегмента,
ни с размером события.

### Разбор проектных вопросов (зафиксировано, не оставлено реализации)

**1. Почему кап вообще 64 KiB и почему его нельзя поднять.** Кап — граница ПАМЯТИ carry
между чанками потокового скана; он несущий для свойства (3) оракула `op_8` (без него
мусорная длина `0x5A5A5A5A` копила бы carry неограниченно). Поднятие до 64 MiB = константный
буфер в 64 MiB на операторском пути = класс TD-011 и запрещённый размен «терпимость против
памяти» (rev5). Кап ОСТАЁТСЯ; меняется не граница памяти, а поведение при её пересечении.

**2. Как отличить «крупный валидный фрейм» от «мусора, похожего на длину».** У фрейма есть
CRC, и он верифицируем БЕЗ буферизации тела: crc32 считается инкрементально по чанкам
(`crc32fast::Hasher`), `seq` — ПЕРВОЕ поле `Event` (postcard: ведущий varint ≤ 10 B) —
извлекается из ограниченного удержанного префикса payload (`postcard::take_from_bytes::<u64>`).
Критерий валидности крупного кандидата = CRC + декодируемый seq-префикс — тот же порядок,
что у штатного ридера (сначала CRC, потом декод); полный postcard-декод тела не требуется:
CRC-валидные фреймы в журнал пишет только наш writer. Мусорная длина CRC не пройдёт →
кандидат отвергнут → скан продолжает байт-ресинк с `i+1`, как сегодня (терпимость не
режется; валидные мелкие фреймы «внутри» фейкового span'а не теряются).

**3. Верхняя граница, дальше которой честно «не знаю».** ЕДИНАЯ именованная константа с
санити-капом ридера (64 MiB) — оба места используют ОДНО имя. `len` > капа = мусор по
определению ОБОИХ путей: такой фрейм не прочитал бы и штатный ридер, поэтому его
невидимость для пола не создаёт расхождения пол↔ридер. Это устраняет корень TD-053 — две
независимые константы, дрейфующие врозь. Отдельное состояние «не знаю» здесь не нужно;
`Unknown` (rev5) остаётся разрешённым выходом для реализации, если верификация кандидата
невозможна в рамках ресурсного бюджета — деградация ТОЛЬКО в сторону отказа (fail-closed),
никогда — в `Known` с заниженным значением.

**4. Событие, превышающее даже санити-кап: `Unknown` или пропуск?** Легитимного такого
события НЕ СУЩЕСТВУЕТ: штатный ридер отказывает на `len > 64 MiB`, значит записать-и-прочитать
его невозможно — его seq недостижим и для потребителей данных. Скан трактует такую длину как
мусор (ресинк), НЕ как повод для `Unknown`: уход в `Unknown` на каждой абсурдной мусорной
длине сделал бы ЛЮБУЮ порчу хвоста непроверяемой и убил бы работающий escape-hatch
(`op_5`/`op_2` — терпимость к порче пиннится оракулами). Цена ошибки: fail-open здесь не
возникает (фрейм невидим ВСЕМУ крейту, расхождения пол↔ридер нет), а отсутствие
writer-side капа — отдельный названный долг (§Известные ограничения).

### Референс-дизайн (свойства обязательны, способ — за dev)

Крупный кандидат (total > капа carry, `len+8` ≤ санити-капа) не ресинкается вслепую:
**side-верификация** span'а вторым источником — сырой формат: позиционное чтение отдельным
дескриптором; `.zst`: повторная потоковая распаковка до offset'а (или эквивалент в рамках
контракта памяти). Успех → `seq` в пол, скан перескакивает фрейм. Провал → байт-ресинк
`i+1` РОВНО как сегодня — основной цикл скана не меняет семантику для мелких фреймов и
мусора (все существующие оракулы M-49 обязаны остаться зелёными без правок).

## Известные ограничения (названы, НЕ закрываются этим milestone'ом)

1. **Writer-side капа нет:** `append` не отклоняет событие, чей фрейм превысил бы санити-кап
   ридера (64 MiB) — такое событие было бы записано, но нечитаемо строгим путём. Сегодня
   недостижимо (потолок L2Snapshot 66 KB; L2Delta без потолка, но реальный максимум 33 KB) —
   кандидат в отдельный TD (writer-side guard), НЕ правится здесь (запретный список).
2. **Окно хвостового скана 4 MiB:** валидное ПОСЛЕДНЕЕ событие крупнее `TAIL_SCAN_CHUNK`
   сделает здоровый хвост «нечитаемым» для штатного старта (страж rev4 сработает ложно).
   Это ДРУГОЙ путь (`tail_last_seq_of`, не скан пола) и другая цена ошибки (отказ старта —
   громкий, не порча). До капа 4 MiB запас ×63 от архитектурного потолка — кандидат в TD
   вместе с writer-side капом, единым числом «максимальный фрейм системы».
3. **Валидность крупного кандидата = CRC + seq-префикс**, полный postcard-декод тела не
   выполняется (мелкие фреймы декодируются полностью, как раньше). CRC-валидный
   не-Event-фрейм мог бы внести мусорный seq — источника таких фреймов в системе нет
   (пишет только наш writer), вероятность случайного прохождения CRC ~2⁻³². Названо ради
   честности контракта, риском не считается.
4. **Время скана** (TD-052) — не расширяется этим milestone'ом: side-верификация добавляет
   повторное чтение span'а на кандидата; на реальных формах порчи (0x5A/усечение) кандидаты
   единичны (фейковая длина почти всегда > санити-капа → мгновенный ресинк). Патологический
   случайный мусор со множеством правдоподобных длин остаётся в границах TD-052 («медленно
   и правильно лучше, чем быстро и неверно»); разрешённый выход при введении бюджета —
   ТОЛЬКО `Unknown`, не занижение.
