## F-1 (БЛОКЕР) — перекасание устаревшего проходного вердикта инвертирует «последний по ключу»

**Где:** `scripts/check_verdict_gate.sh:164-183` (`FILE_ORD` = позиция ПОСЛЕДНЕГО коммита,
тронувшего ФАЙЛ) и `:269-274` (ключ резолвится в вердикт с максимальным `FILE_ORD`).

**Суть.** Барьер обещает: «по каждому ключу берётся ПОСЛЕДНИЙ вердикт диапазона». В качестве
прокси «последний» используется `FILE_ORD[f]` — топологическая позиция последнего коммита,
тронувшего файл `f`. Но «последний КОММИТ, тронувший файл» ≠ «последний по существу вердикт».
Достаточно ТРИВИАЛЬНО перекоснуть (пробел, комментарий) уже лежащий ПРОХОДНОЙ вердикт по
ключу K — его `FILE_ORD` прыгает выше генуинно-более-позднего ОТКАЗА по тому же K, и барьер
объявляет ключ погашенным.

**Воспроизведение (последовательность: APPROVE(1) → REJECT(2) → re-touch стейл-APPROVE(3)):**
```
r1: research/reviews/R-1.md   GATE-META milestone:M-72 verdict:APPROVE   (позиция 1)
r2: research/critiques/C-1.md GATE-META milestone:M-72 verdict:REJECT    (позиция 2, ГЕНУИННО последний)
r3: printf '\n<!-- x -->\n' >> research/reviews/R-1.md                    (позиция 3, пробельная правка стейла)
EVENT_NAME=pull_request PR_BASE_SHA=<base> bash scripts/check_verdict_gate.sh
```
Вывод:
```
вердиктов в диапазоне: судимых 2, без шапки 0; ключей 1; погашено токеном 0
VERDICT: PASS — ни один ключ диапазона не оставлен в отказном состоянии
EXIT=0
```
`FILE_ORD` диагностика: `R-1.md` тронут коммитами 1 и 3 (M) ⇒ ord=3; `C-1.md` — коммитом 2 ⇒
ord=2. `3 > 2` ⇒ ключ M-72 резолвится в APPROVE, `refused=0`.

**Контроль (без re-touch — тот же набор обязан краснеть, и краснеет):**
```
r1 APPROVE M-72 → r2 REJECT M-72 (без r3)
EXIT=1
FAIL  ключ M-72: последний вердикт диапазона — REJECT (research/critiques/C-1.md); проходного по тому же ключу позже НЕТ
```
Разница исхода (1 → 0) держится ИСКЛЮЧИТЕЛЬНО на пробельной правке чужого проходного файла.

**Почему это не «подделываемый токен» (принятый предел), а дефект.** Барьер не просто доверяет
декларации автора СВОЕГО вердикта — он АГРЕГИРУЕТ несколько вердиктов по ключу и выбирает
последний. F-1 ломает саму агрегацию: живой REJECT (позиция 2) проигрывает СТОРОННЕМУ файлу,
чьё единственное «преимущество» — что его строку перечитали позже. Правка стейл-APPROVE не
попадает под subject-lock соседа (`research/reviews/**` не в `is_gate_class`
`check_gate_meta.sh:138-147`), то есть композиция не спасает.

**Условие снятия блокера F-1.** «Последний по ключу» обязан считаться по вердикту, а не по
касанию файла: например, позиция коммита, где ключ K В ЭТОМ ФАЙЛЕ получил СВОЙ ТЕКУЩИЙ исход
(коммит, последним изменившим поле `verdict:`/`milestone:`), а не любой коммит, тронувший
байт файла. Либо: перекасание файла БЕЗ изменения его шапки не должно двигать позицию ключа.
RED-сценарий: воспроизвести APPROVE→REJECT→touch-stale и требовать exit 1.

## F-2 (БЛОКЕР, переживает композицию) — GATE-META внутри код-фенса разбирается как настоящий вердикт

**Где:** `scripts/lib/gate_meta.sh:43` — `gate_meta_block` матчит `/<!-- GATE-META/` как
ПОДСТРОКУ где угодно в файле, включая тело внутри ```-фенса и цитату-пример. Потребляется
`check_verdict_gate.sh:226` (`meta="$(gate_meta_block "${body}")"`).

**Суть.** Файлы вердиктов РУТИННО цитируют шаблон шапки как ПРИМЕР (M-60b спека, этот самый
C-110, десятки вердиктов «формат шапки — §4»). Если файл в каталоге вердиктов несёт GATE-META
блок-ПРИМЕР с ПРОХОДНЫМ исходом и ключом, совпадающим с отказным, — барьер засчитывает пример
как настоящий проходной вердикт и гасит отказ.

**Диагностика разбора (что барьер извлекает из файла-пояснения):**
```
--- extracted meta block ---
milestone: M-73
verdict: APPROVE
--- milestone field: [M-73]  verdict field: [APPROVE]
--- is_passing? --- PASSING (=> clears M-73 refusal)
```

**Воспроизведение (генуинный REJECT + файл-«пояснение», цитирующий APPROVE-пример):**
```
c1: research/critiques/C-2.md  GATE-META milestone:M-73 verdict:REJECT  (настоящий отказ)
c2: research/reviews/R-2.md    — БЕЗ своей шапки, только ```-фенс с примером verdict:APPROVE, milestone:M-73
EVENT_NAME=pull_request PR_BASE_SHA=<base> bash scripts/check_verdict_gate.sh
→ судимых 2, ключей 1; VERDICT: PASS; EXIT=0
```

**Композиция НЕ спасает** (это главное отличие F-2 от «шапка с фейковыми SHA»). Если пример
несёт РЕАЛЬНЫЕ ancestor-SHA (автор скопировал шапку реального смердженного вердикта), сосед
`check_gate_meta.sh` тоже принимает файл как валидный вердикт:
```
=== verdict-gate ===  EXIT=0  VERDICT: PASS — судимых 2, ключей 1
=== gate-meta (sibling) на том же дереве === EXIT=0  VERDICT: PASS — вердиктов проверено: 2
```
С фейковыми SHA (111…/222…) gate-meta ловит файл (`audited_base не существует`), но
verdict-gate ВСЁ РАВНО обманут — а моя ось именно его ложноотрицательная. С реальными
ancestor-SHA не ловит НИКТО.

**Срабатывает без злого умысла.** Достаточно, чтобы пояснительный файл в `research/reviews|
critiques|arbitration` процитировал проходную шапку-пример по ключу, который где-то ещё под
отказом. Это не «автор соврал в своём вердикте» — это ТРЕТИЙ файл, случайно погасивший чужой
отказ.

**Условие снятия блокера F-2.** `gate_meta_block` обязан игнорировать GATE-META внутри
код-фенсов/цитат: например, признавать шапкой только блок, начинающийся с ПЕРВОЙ строки файла
(«первыми строками РОВНО», как требует и сам шаблон §4), а не любой `<!-- GATE-META` в
произвольной позиции. RED-сценарии: (а) файл с примером-шапкой в ```-фенсе не должен
засчитываться как вердикт; (б) настоящая шапка обязана читаться только когда она в голове
файла. Правка живёт в БИБЛИОТЕКЕ — значит бьёт обоих потребителей, проба соседа
`red_gate_meta.sh` тоже обязана получить этот сценарий.

## F-3 (CONCERNS) — удаление отказа + ALLOW-ARTIFACT-DELETE гасит его в обход VERDICT-CLEARED

**Где:** `check_verdict_gate.sh:212` (`git diff --diff-filter=AM` — удаления невидимы; у
барьера нет обработки `D`). Композиция с `check_protected_artifacts.sh:159`
(`ALLOW-ARTIFACT-DELETE`).

**Суть.** Отказ, ДОБАВЛЕННЫЙ в диапазоне (круг 1 на ветке), затем УДАЛЁННЫЙ до merge, для
verdict-gate не существует (нет файла на HEAD ⇒ `--diff-filter=AM` его не видит). Сосед
`check_protected_artifacts.sh` удаление ловит (строит `existed` через `ls-tree` по каждому
коммиту — способ-слепой), НО пропускает при наличии `ALLOW-ARTIFACT-DELETE` в теле.

**Воспроизведение:**
```
c1: research/critiques/C-4.md GATE-META milestone:M-88 verdict:REJECT
c2: git rm C-4.md ; тело коммита несёт "ALLOW-ARTIFACT-DELETE: <причина ≥12>"
verdict-gate:          EXIT=0  VERDICT: PASS (судимых 0)
protected_artifacts:   EXIT=0  NOTE ALLOW-ARTIFACT-DELETE в <sha>; OK
```
Итог: отказ M-88 «погашен» СТИРАНИЕМ, минуя `VERDICT-CLEARED: M-88 — <причина>`.

**Почему это находка, а не принятый предел.** `VERDICT-CLEARED` требует НАЗВАТЬ КЛЮЧ и
причину «находки устранены»; здесь вместо него используется токен ДРУГОГО барьера,
называющий ПУТЬ и причину «почему файл удалён». `gates.md` §5: отказ держит merge «до
устранения находок или founder-override» — стирание не есть ни то, ни другое. Оба токена
подделываемы (принятый класс), но это РАЗНЫЕ токены с разной семантикой; F-3 позволяет
удовлетворить намерение verdict-gate чужим, более слабым токеном.

**Условие снятия.** Либо verdict-gate судит и `D` (отказ, существовавший в диапазоне и
исчезнувший, требует `VERDICT-CLEARED`, а не только `ALLOW-ARTIFACT-DELETE`), либо предел
назван явно в шапке барьера («удаление отказа гасит его через ALLOW-ARTIFACT-DELETE — принято»)
— сейчас он не назван, тогда как соседние пределы (вердикт в базе, подделываемость токена)
названы. Класс severity — CONCERNS, а не блокер: требует токен и стирает артефакт (видимый
след).

## F-4 (NOTE, мелкая) — регистрозависимый `*.md` пропускает `.MD`

**Где:** `check_verdict_gate.sh:223` — `case "${f}" in *.md) ;; *) continue ;; esac`
(регистрозависимо).

**Воспроизведение:**
```
research/critiques/C-5.MD  GATE-META milestone:M-80 verdict:REJECT
verdict-gate: EXIT=0  VERDICT: PASS (судимых 0 — .MD не матчит *.md)
```
Тот же `*.md` glob в `check_gate_meta.sh:180` и `research/critiques/*.md` в
`check_protected_artifacts.sh:70` — то есть `.MD`-вердикт не судится и не защищён нигде.

**Оценка.** Маргинально: вердикты называются `.md` по конвенции. Но контракт барьера — «по
каждому вердикту с шапкой GATE-META», а `.MD`-файл с шапкой ему формально удовлетворяет.
Механический зазор регистра. Условие снятия: нормализовать регистр расширения либо назвать
предел.

## Что ПРОВЕРЕНО и ДЕРЖИТ (не находки)

- **Merge-born отказ (evil merge).** Гипотеза: отказ, рождённый merge'ем, получает `ord=0`
  (fail-closed), а проходной по тому же ключу с `ord>0` его перекрывает при определённом
  порядке сортировки путей (ветвь `check_verdict_gate.sh:255-267`). **Опровергнута
  исполнением:** `git log -m` (`:182`) отдаёт merge-born файлу позицию САМОГО merge-коммита
  (не 0), поэтому REJECT корректно держит merge:
  ```
  evil merge births REJECT M-91 → EXIT=1  FAIL ключ M-91
  ```
  Порядок-зависимый override через `ord=0` в реалистичном merge недостижим — см. пределы.
- **Тай в одном коммите** (проходной+отказной, оба порядка сортировки) — отказ побеждает
  (VG-9/VG-34 честны, перепроверил обе стороны).
- **Токен `VERDICT-CLEARED`**: чужой ключ, граница слова (`M-60` vs `M-60b`), хвостовая
  пунктуация в ключе (`M-60.`≠`M-60`), причина <12, цитата токена в теле файла — всё
  fail-closed (не гасит). Регистр/юникод ключа: сравнение точное байтовое ⇒ fail-closed.
- **Исход вне перечня / пустое поле / нижний регистр вердикта** (`reject`, `approve`) —
  краснеет как НЕИЗВЕСТНО/отказ (перечень регистрозависим, `gate_meta_in_list` точное
  совпадение).
