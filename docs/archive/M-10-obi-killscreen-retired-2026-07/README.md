## 3. Дефект `KS-I-1` — ядро милестоуна фактически defeated (HIGH)

Главная находка `C-020` §A. `report.rs::sharpe_se`:

```rust
fn sharpe_se(returns: &[f64], sharpe: f64) -> f64 {
    let observations = returns.len().max(1) as f64;   // ← ЧИСЛО ШАГОВЫХ доходностей
    (PERIODS_PER_YEAR / observations * (1.0 + 0.5 * sharpe * sharpe)).sqrt()
}
```

`se_sharpe` считается от **количества пошаговых доходностей**, а НЕ от **календарной длины
окна**. Замер: окно = 0.353 дня, `returns.len() ≈ 1.45e4` → `se_sharpe = 0.272`, тогда как
проектная величина по §Objective — «SE годового Sharpe ≈ ±11 на 3–7 днях». Расхождение —
**полтора-два порядка**.

**Последствие.** Гейт PASS в `classify_verdict` — `sharpe − 2·se_sharpe > BAR(0.5)`. При
`se = 0.27` порог PASS ≈ `sharpe > 1.04`, то есть любой сигнал с годовым OOS-Sharpe > ~1.04
на восьмичасовом окне (тривиально достижимо переобучением) получал бы **ложный PASS** —
ровно тот исход, который милестоун объявляет АРХИТЕКТУРНО ЗАПРЕЩЁННЫМ. Здесь ложный PASS не
случился только потому, что `classify_verdict` раньше срабатывает на `oos_sharpe ≤ 0.5 →
Kill`: отрицательный Sharpe замаскировал сломанный `se`. **На положительном сигнале защита
не сработала бы.**

**Почему RED это не поймал** (урок для того, кто будет писать оракул заново):
`red_killscreen.rs` тестирует КЛАССИФИКАТОР — подаёт готовый `se_sharpe` на вход и проверяет
гейт, — но НЕ пиннит МАСШТАБ функции `sharpe_se`. Дефект жил в слепом пятне между
«классификатор протестирован» и «se посчитан честно»; это тот же класс, что happy-path-фикстура
из `.claude/rules/testing.md`.

### Сопутствующие находки `C-020` §B — нефизичные величины стека (MEDIUM)

`fill_rate = 1.990` (метрика считает `fills/intents`, то есть «филлов на интент», а не
вероятность исполнения в [0,1] — пре-рег критерий №5 ссылался на вероятность и мерил НЕ ТО);
`net_pnl ≈ −$18 млрд` под latency×2; `turnover ≈ $10 млрд`; Sharpe семейства до −226;

Для Kill не важны (Sharpe масштаб-инвариантен), но подтверждают: стек как измеритель не
провалидирован.

## 4. Почему код НЕ влит в `crates/` — замер, а не осторожность

Ветка трогает `crates/research-cli` — **живой член workspace**
(`Cargo.toml: [workspace] members`), чьи тесты гоняет `cargo test --all`. Из восьми файлов
**шесть — модификации файлов, существующих на `main` сегодня**:

```
M  crates/research-cli/src/grid.rs          +20  -16
M  crates/research-cli/src/ledger.rs        +30    0
M  crates/research-cli/src/main.rs          +71   -2
M  crates/research-cli/src/report.rs       +541  -15     ← здесь живёт KS-I-1
M  crates/research-cli/src/types.rs         +54   -1
A  crates/research-cli/tests/red_killscreen.rs      +333
M  crates/research-cli/tests/red_research.rs   +9   -1
A  crates/research-cli/tests/red_stack_honesty.rs   +122
```

Код **не изолирован**: это не новый крейт и не отдельные файлы, а правки живого. Поэтому
вариант «оставить в `crates/` с исключением из workspace-членства» неприменим — исключить
из workspace можно КРЕЙТ, а не «правки к файлам включённого крейта»; исключение самого
`research-cli` вынесло бы из CI 16 живых модулей и 16 живых тестов, то есть было бы
регрессом, а не архивацией. Плюс `main` с момента merge-base (`0cd447d`, 2026-07-21) добавил
в этот крейт **+2473 строки** (`depth_lifetime`, `orderflow`, `walkforward`, `depth_series`
и их оракулы).

### Решающий замер: ветка — это НЕЗАКРЫТЫЙ RED, и merge красит `main`

Отсутствие ТЕКСТОВЫХ конфликтов (`git merge-tree` → exit 0, замер
`docs/plans/stale-branches-audit-2026-08-13.md` §4) ничего не решает: «применяется без
конфликта» и «безопасно применять» — разные утверждения. Гипотетическое дерево слияния было
собрано и прогнано (2026-08-15):

```
$ git merge-tree --write-tree origin/main origin/feat/M-10-rebased   # → 61dcf6c, exit=0
$ cargo build --workspace                                            # BUILD_EXIT=0
$ cargo test --all
   Compiling research-cli v0.0.0
error[E0603]: function `sharpe_se` is private
error: could not compile `research-cli` (test "red_killscreen") due to 1 previous error
                                                                     # TEST_EXIT=101
```

Сборка зелёная (она не собирает тест-таргеты), а **`cargo test --all` КРАСНЫЙ**. Причина —
не случайность и не протухание: `red_killscreen.rs` ветки есть **RED-оракул на ФИКС
`KS-I-1`, написанный architect'ом и никогда не закрытый**. Он требует исправленную
сигнатуру

```rust
pub fn sharpe_se(sharpe: f64, data_span_days: f64) -> f64   // se от КАЛЕНДАРНОГО окна
```

и объявлен «компайл-RED против старой сигнатуры (returns)», тогда как `report.rs` той же
ветки всё ещё несёт старую приватную `fn sharpe_se(returns, sharpe)`. То есть ветка умерла
**между спецификацией фикса и его реализацией**.

Вывод: влить этот код в `main` нельзя не только по вердикту `C-020`, но и механически —
`main` немедленно станет красным. Это и есть окончательное обоснование выбора «патч в
архиве» вместо «файлы в `crates/`».

## 6. `trials-ledger` — 276 записей НЕ влиты, и это намеренно

Ветка дописывала 276 строк в `research/trials-ledger.jsonl` (замер: на `main` сейчас
**4** строки — пре-M-07 эпоха `f7f4761`; ветка довела бы до 280). Записи сохранены здесь
отдельным инертным файлом и **в живой ledger не переносятся** по двум причинам:

1. `C-020` §0 (форвардный риск) прямо предупреждает: прогон дописал obi-испытания с
   выбросами Sharpe до **−226.79**; `deflated_sharpe` берёт `variance(family_sharpes)`, и
   выброс раздувает `V[SR]` → раздувает SR₀ → будущие deflated-Sharpe семейства obi
   окажутся искусственно занижены. Здесь роли не играло (raw SR<0 → DSR=0), но всплывёт на
   первой же ячейке с SR>0;
2. ledger — **append-only механизм, а не файл под ручную правку**
   (`.claude/rules/scope-guard.md`, `INTG-I-6`). Дописывание 276 строк docs-коммитом было бы
   именно ручной правкой управляемого артефакта.

Решение о судьбе этих записей (влить механизмом / оставить архивом / винзоризовать V[SR]) —
за founder'ом; кандидат в TD назван в handoff'е архивации.

## 7. `D-001` — черновик решения, подписи НЕТ

`D-001-obi-trackA-kill.DRAFT-UNSIGNED.md` сохранён **как черновик** и намеренно НЕ положен в
`research/decisions/` (каталога на `main` не существует вовсе). Причины:

- сам документ в первой строке объявляет **«СТАТУС: DRAFT — UNSIGNED (ожидает
  founder-аттестации)»**;
- `research/decisions/D-NNN.md` пишет **только founder** (`scope-guard.md`, граница C
  `docs/DESIGN.md` §6/§7, `gates.md` §7). Ни один агент не аттестует за founder'а, а
  архивация — не способ протащить подпись;
- имя файла несёт суффикс `.DRAFT-UNSIGNED`, чтобы его нельзя было принять за состоявшееся
  решение при беглом чтении.

**Открытый вопрос к founder'у:** KILL сигнала признан робастным всеми гейтами, но решение
так и не подписано, и на `main` следа о нём не было вовсе (в `docs/PENDING-SIGNATURE.md`
записи нет — проверено). Либо founder подписывает `D-001` в `research/decisions/`, либо
статус «OBI Трек A мёртв» остаётся зафиксированным только этим архивом.

## 8. Что делать тому, кто вернётся к kill-screen OBI

1. Прочитать `C-020` §A целиком — дефект `KS-I-1` концептуальный, а не опечатка.
2. **Оракул на фикс писать НЕ НУЖНО — он уже написан и лежит в патче.** В
   `crates-research-cli.patch` внутри `red_killscreen.rs` есть готовый RED-набор на масштаб
   `sharpe_se`: `a1_se_is_huge_on_short_window` (реальное окно R-001 = 0.353 дня, требует
   `se > 10`, где step-count даёт 0.27), `a2_se_matches_milestone_premise_on_days`
   (пиннит премиссу «≈±11 на 3 днях, ≈±7 на 7»), `a3_se_decreases_monotonically_with_span`.
   Он задаёт контракт `pub fn sharpe_se(sharpe: f64, data_span_days: f64)` и намеренно
   является компайл-RED против старой сигнатуры. **Это готовая спецификация фикса** —
   осталась только реализация (и решение architect'а, брать ли оракул как есть).
3. Помнить, ПОЧЕМУ прежний оракул пропустил дефект: он тестировал КЛАССИФИКАТОР, подавая
   готовый `se_sharpe` на вход, и был зелёным при сломанном `se`.
4. Перед доверием любой метрике — провалидировать её саму
   (`.claude/rules/testing.md`, «Оракул обязан мерить ТО, ЧТО ОБЕЩАЕТ»): `fill_rate`,
   `capacity`, PnL-аккаунтинг были нефизичны и этого никто не ловил.
5. Не воскрешать сам сигнал без НОВЫХ данных: 276/276 ячеек и 21/21 окон отрицательны.
