  **воспроизведено мутационным прогоном, не рассуждение**). **Severity: MAJOR (направление
  ошибки — к ложному GREEN).**
  **Что.** `crates/gateway/tests/red_snapshot_noclone.rs` меряет пик аллокаций через
  `#[global_allocator]` со статиками `CUR`/`PEAK` — счётчик **глобален на процесс**, а
  `cargo test` гоняет O-1/O-2/O-3 параллельными потоками в ОДНОМ бинаре. Соседние тесты
  аллоцируют внутри окна `peak_delta` и завышают базу O-1.
  **Замер (мутация: возвращён `self.full.clone().finish_with_at()`), несколько прогонов:**
  ```
  набор целиком, 1-й прогон:            аллокации 296025 → 854705 (×2.89)   <- ЗАГРЯЗНЕНО
  набор целиком, последующие прогоны:   аллокации 151089 → 854705 (×5.66)
  фильтр o1_ (в одиночку), 3 прогона:   аллокации 151089 → 854705 (×5.66)
  набор с --test-threads=1:             аллокации 151089 → 854705 (×5.66)
  порог оракула: ratio < 2.5
  ```
  **Загрязнение непостоянно — и это хуже, чем если бы оно было стабильным.** База O-1
  (`alloc_small`) в одном из прогонов оказалась вдвое выше (296 025 против 151 089), потому
  что соседний тест аллоцировал внутри окна `peak_delta`. Воспроизводится не каждый раз:
  зависит от того, как раннер развёл потоки. При `--test-threads=1` — стабильные ×5.66,
  то есть диагноз подтверждается сериализацией.
  **Чем это опасно.** В загрязнённом прогоне запас над порогом падает с 126 % до **16 %**,
  а направление сноса — ВНИЗ, к `ratio < 2.5`, то есть к молчанию оракула на дефектном коде.
  Докстринг же обещает «≈1 честно против ≈8 с клоном, порог 2.5 посередине с запасом в обе
  стороны» — при загрязнении это неверно. Класс тот же, что у первой редакции O-1, которая
  **прошла на коде с клоном** (признано в самом докстринге). Флакающий оракул на
  sacred-пути — ровно то, что проект уже лечил в `TD-094`/`TD-023`.
  **Почему NOTE, а не блокер merge'а.** Корректность влитого кода установлена независимо
