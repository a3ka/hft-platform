## §1. Модель данных: journal-first (НЕ hft three-tier as-a-service)

**Уточнение (2026-07-31, решение founder'а `DESIGN.md` §0/§13–§23).** Ниже описанное «мы НЕ
поднимаем старый стек hft, потому что он для сервиса данных, а мы не сервис данных» —
обоснование БОЛЬШЕ НЕ ДЕЙСТВУЕТ: платформа теперь именно многопользовательский SaaS-сервис
рыночных данных для десятков тысяч пользователей (`DESIGN.md` §0). Технический вывод (не
поднимать Redis/ClickHouse/MinIO в критическом пути) остаётся верным, но по ДРУГОЙ причине —
не «нам не нужно отдавать данные многим», а «мы отдаём данные многим через journal-first +
CQRS-проекции (`DESIGN.md` §13–§14), а не через классическую БД-триаду». Read-path под
десятки тысяч соединений — отдельно спроектирован в `DESIGN.md` §16 (shared-tailer, cap'ы/
квоты, per-topic каналы), не через Redis hot-tier. Второй источник истины — Postgres для
app-плоскости (профили/workspace/decision-journal), НЕ рыночные данные (`DESIGN.md` §13).

Мы НЕ поднимаем старый стек hft (Redis 24GB hot / ClickHouse 31d / MinIO Parquet) в
критическом пути движка. Наша модель:
**append-only журнал событий = единственный источник истины рыночных данных** (fa/journal.md).
Всё состояние (book, risk, oms, CQRS-проекции для read-path) — детерминированная свёртка
журнала. Отсюда storage движка сводится к ДВУМ вещам, а не к трёхкомпонентной БД-инфраструктуре:

1. **Горячий журнал** — то, что пишет recorder/движок прямо сейчас. Растёт линейно во времени.
2. **Research data lake** — архив исторических журналов для бэктестов. Растёт с горизонтом истории.

Никакого Redis/ClickHouse/MinIO в критическом пути движка. (ClickHouse/DuckDB опционально —
только как read-only аналитический индекс над журналом на research-стороне, если понадобится;
НЕ источник истины, НЕ зависимость движка. Решение отложено — §7.) Postgres app-плоскости
(`DESIGN.md` §13, Ф3 `09-roadmap-v2.md`) — отдельный компонент вне этого противопоставления:
он не претендует на роль источника истины по рыночным данным и не входит в горячий путь
движка.

## §2-old. Исходная оценка (историческая, НЕВЕРНА — оставлена как след ошибки) `[verify-at-impl]`

Допущения (уточняются на P1 из реального фида; порядок величины):
- L2-book updates: mid-freq, 1 пара, ~10–50 событий/сек в активные часы, усредн. ~20 ev/s.
- Trades/funding/mark — добавляют скромно (~+20%).
- Сырое событие: ~150–250 B; postcard-фрейм: ~80–150 B; **после zstd сжатия сегмента: ~30–60 B/событие**.

| Метрика (1 пара) | Оценка |
|---|---|
| События/день | ~20 ev/s × 86400 ≈ **1.7M/день** |
| Сырой объём/день | ~0.3–0.5 GB |
| **Сжатый журнал/день** | **~0.1–0.3 GB** |
| P1 (7 дней, 1 пара) | **~1–2 GB** — тривиально при 156 GB free |
| 1 пара × год (сжато) | ~40–110 GB |
| 3 пары × год (сжато) | ~120–330 GB — **вот здесь нужен cold-tier** |

Вывод: **P0/P1/P3/P4 (одна пара, недели-месяцы) помещаются на локальный NVMe с запасом.**
Проблема объёма появляется только на research data lake (много пар × годы истории для
бэктестов) — и это ровно то, подо что предназначен Storage Box.

## §3. Трёхуровневое хранение (наша версия — журнальная, не БД-шная)

| Tier | Что | Где | Ретеншн | Латентность |
|---|---|---|---|---|
| **HOT** | активный сегмент журнала + снапшоты + рабочий набор | локальный NVMe (`/`) | окно (часы-дни) | µs-ms (append/read) |
| **WARM** | недавние журналы для активного бэктеста | локальный NVMe | недели-месяцы | ms |
| **COLD** | архив журналов (долгий горизонт бэктеста + audit-ретеншн) | **Hetzner Storage Box** (SSHFS/SMB) | месяцы-годы | 10–50 ms (read-only) |

- **HOT/WARM пишет только движок/recorder** — append-only, единственный писатель (JR-I-1);
  сжатие сегмента zstd ПОСЛЕ закрытия сегмента (не в hot-path записи).
- **COLD read-only**: закрытые сжатые сегменты переносятся на Storage Box скриптом ретеншена;
  research-cli читает их оттуда для длинных бэктестов (latency 10–50 ms терпима для batch-compute).
- **Storage Box — НЕ block device, НЕ для hot-журнала** (application-level SFTP/SMB, latency).
  Это архивный слой, ровно как рекомендовано в диагностике (BX31 10TB ≈ $14/мес, 10 Gbit в том же ДЦ).

## §4. Ретеншн-дисциплина (governed, не «janitor по крону»)

Урок hft-core-rs (DESIGN §9): их OOM-инцидент (28.95GB/32GB, 6315 несжатых стримов) случился
потому, что полагались на периодический XTRIM-демон при неограниченных продюсерах. **Первичный
контроль — на стороне писателя**, не уборщик:
- Сегменты журнала ротируются по размеру/времени; закрытый сегмент немедленно кандидат на
  сжатие; сжатый и подтверждённый (bit-identical после распаковки — §5) → кандидат на
  перенос в COLD по возрасту.
- Перенос HOT→WARM→COLD — детерминированное правило по возрасту сегмента + свободному месту,
  НЕ «удалить старое». **Журнал бессмертен** (JR-I-6/CT-I-3): старые сегменты уходят в COLD,
  не удаляются (иначе рушится `replay==реальность` и audit-пригодность).
- Диск-бюджет как алерт (не как молчаливый дроп): свободное место < порога → P1-алерт
  оператору + автоперенос COLD, НИКОГДА не тихое удаление данных.

## §5. Сжатие: только с сохранением детерминизма

zstd на закрытых сегментах допустим ТОЛЬКО если распаковка бит-идентична исходнику
(SHA-совпадение) — иначе ломается DET-I-1 (`replay==реальность`). Это уже зафиксировано как
открытый вопрос в fa/journal.md §O; здесь — правило: **compression is transport/at-rest layer
only; распакованные канонические байты обязаны совпадать**. Codec — zstd (level калибруется:
скорость записи vs ratio), тот же выбор, что и в hft, но с обязательной round-trip проверкой.

## §5.1. Формат хранения книги: снапшоты vs диффы (ОТКРЫТЫЙ ВОПРОС, поставлен 2026-07-14)

Замер §2 вскрыл: 96% журнала — секундные снапшоты полной книги. Альтернатива — писать то, что
биржа реально присылает: **diff-поток** (100 мс) + редкий полный снапшот (для быстрой перемотки
и ресинка).

| | Снапшоты 1/с (сейчас) | Диффы + редкий снапшот |
|---|---|---|
| Объём | 8.83 GB/сут (≈1 GB сжато) | оценочно **2.5–3× меньше** сверх zstd |
| Внутрисекундная динамика | **ПОТЕРЯНА** | сохранена (каждое изменение) |
| Реконструкция книги | тривиальна (срез готов) | нужен replay диффов от снапшота |
| Цена | требует `MdPayload::L2Diff` → **T1 contract-RFC** + правки `book`/`sim` | — |

**Оценка architect'а:** переход на диффы — не оптимизация хранения, а **восстановление данных,
которые мы сейчас выбрасываем на этапе записи**. Никакой бэктест не восстановит то, чего нет в
журнале; для горизонтов 0.5–5 с это прямо бьёт по качеству сигнала. Кандидат в `CT-RFC-04`
(после `CT-RFC-03` recon-события). НЕ блокирует компакцию (та даёт 9× без смены формата).

## §6. RAM / «память» (второй смысл вопроса)

Если «ограничения по памяти» — про RAM, а не диск:
- **Состояние мало**: book (1 пара), risk-state, oms — килобайты-мегабайты; в RAM целиком, не проблема.
- **Research не грузит журнал целиком в RAM**: `journal::reader` — итератор (fa/journal.md §3
  outer/reader), research-cli стримит события, а не читает файл в память (RC-I / streaming
  read). Грид по многим конфигурациям параллелит по сегментам, не держит весь lake в RAM.
- **Снапшоты** ограничивают глубину replay при старте (не надо реплеить год, чтобы поднять
  состояние — стартуешь со снапшота + хвост, fa/journal.md §7).
Итог: RAM-давления при mid-freq одной пары нет; масштаб (много пар × long backtest) решается
streaming-чтением + шардированием по сегментам, не наращиванием RAM.

## §7. Deployment: отдельный Hetzner Cloud cpx32 (РЕШЕНО founder 2026-07-10)

**Платформа НЕ живёт на текущем dedicated-сервере.** Тот сервер (RAID1 NVMe 437GB, общий с
einhard/Gazebo/PX4 и другими юзерами) остаётся нетронутым — платформа занимает на нём **ноль GB**.
Причина: recorder работает 24/7, пропуск данных невосстановим (gap в журнале = потерянная
навсегда история); держать такой always-on workload на забитом общем сервере — риск (чужая
чистка / переполнение диска соседним проектом → падение записи JR-I-5 → gap) + IO/CPU-контеншн.

**Целевая машина: Hetzner Cloud `cpx32`** (4 vCPU / 8 GB RAM / **160 GB SSD** / €42.23/мес,
setup fee €0). Одна машина на весь P0–P4:
- recorder (24/7, HL WebSocket → журнал), движок (P3–P4 live), research-cli (бэктест-гриды),
  killswitch — всё in-process/на этой VM.
- **Cloud Volume и Storage Box на старте НЕ нужны** — 160 GB встроенного SSD покрывают
  hot+warm+scratch на 1–3 пары с работающим retention + приличный исторический backfill, на
  месяцы вперёд. Оба добавляются ПОЗЖЕ по триггеру, одним кликом, без даунтайма (§10).
- **mid-freq не требует bare-metal/колокации** — HL это API/WS через интернет; Cloud-VM в ДЦ
  Hetzner по latency с запасом.

**Триггеры добавления (не сейчас):**
- **Cloud Volume** (~€0.05/GB/мес, attach вживую без ребута) — когда рабочий набор + backfill
  перерастёт 160 GB (для 1–3 пар с retention — далеко/возможно никогда).
- **Storage Box** (BX11 1TB ~€3.50 / BX21 5TB ~€11, SSHFS `/mnt/coldstore`) — когда (а) диск
  подходит к ~70–80% из-за накопленной истории, либо (б) нужна копия истории вне машины
  (durability). Ретеншн-скрипт переносит туда закрытые сжатые сегменты по возрасту.
- **Hetzner Backups** (галочка, ~20% цены VM) ИЛИ Storage Box-выгрузка — включить при переходе
  на ценные данные / live (диск VM — не бэкап). На стадии «пишем тестовые данные» — пропускаем.

**Путь расщепления (P5, когда research-гриды станут тяжёлыми):** крохотный always-on VM держит
recorder+движок непрерывно, отдельная (ресайзимая) research-VM гоняет гриды, читая cold с
Storage Box. До P5 — одна cpx32.

**Деплой:** `runner` — composition root (01 §9); перенос = `git clone` + `docker compose up` на
cpx32. Текущий сервер не участвует.

## §10. Storage Box — роль (архив, НЕ «всё сохранение») + локальный бюджет

Уточнение модели (частая ошибка понимания): **не** «поток здесь, всё сохранение на боксе».
- **Локальный NVMe** — путь записи + источник истины: hot-журнал пишется локально (fsync,
  single-writer, durability, детерминизм). Storage Box — не block device, latency 10–50 ms,
  для живой записи непригоден.
- **Storage Box** — только COLD-архив: закрытые, сжатые, round-trip-проверенные сегменты
  переносятся по возрасту; read-only для длинных бэктестов. Переносим ИСТОРИЮ, не живую запись.

**Локальный бюджет (hot+warm+scratch, 1 пара):** hot ~1–2 GB; warm (1–3 пары × ~3 мес) ~10–80
GB; scratch research единицы GB. **cpx32 даёт 160 GB SSD** — покрывает весь бюджет + ОС/docker
+ приличный backfill с большим запасом; Cloud Volume до перерастания 160 GB не нужен (§7).

**Размер Storage Box (когда понадобится) диктуется историей × парами:** BX11 1TB (~€3.50) /
BX21 5TB (~€11) достаточно под 1–3 пары полной глубины; BX31 10TB — избыточно, берём только
если lake реально разрастётся до много-пар × годы.

## §11. Историческая история (backfill для бэктеста/research) — full-depth обязателен

Проверено 2026-07-10: записанных HL-данных от старого hft НА ЭТОМ СЕРВЕРЕ НЕТ (найденные
parquet — ML-датасеты, не рынок). Бесплатного локального бутстрапа нет.

**Жёсткое требование:** OBI-сигнал (полосы 3%/8%, fa/book.md depth-bands) требует ПОЛНОЙ
глубины incremental L2. Трейд-онли / top-of-book / OHLCV — НЕПРИГОДНЫ (depth-имбаланс не
построить). Это отсекает почти всю дешёвую/бесплатную крипто-историю.

Источники (по убыванию для нас):
1. **Запись самими (первично, ground truth, бесплатно вперёд):** recorder P0/P1 пишет HL L2
   полной глубины + trades + funding в НАШ формат журнала → backtest==live идеально. Минус:
   истории до старта нет; lake строится вперёд → запускать recorder немедленно.
2. **Research-grade вендоры full-depth L2 (платно, экономят месяцы):** Tardis.dev (стандарт
   крипты; tick-level incremental book по Hyperliquid+Binance; реплеится 1:1) `[verify-at-impl]`
   охват HL; альт. Kaiko / CoinAPI / Amberdata / CryptoLake.
3. **Собственный архив Hyperliquid** `[verify-at-impl]` — проверить, есть ли ПОЛНАЯ глубина L2
   (не L1/trades). Если да — бесплатный бутстрап.
4. **Конвертер источник→формат журнала** (contract layer; research-cli/tools) — иначе
   backtest≠live. Любая внешняя история нормализуется в наш `Event`, проходит те же схемы.

**План:** recorder свой запускаем сейчас (P0/P1); для валидации OBI параллельно — backfill HL
(+Binance под lead-lag) полной глубины: сперва бесплатный архив HL, при недостатке глубины →
Tardis.dev. Обязательная проверка на входе: источник несёт полную глубину стакана.

## §9. Открытые вопросы
- Реальные rate/объёмы HL (P1 измерит) — от них порог добавления Cloud Volume / Storage Box
  к cpx32 (триггеры §7); при 160 GB SSD этот порог далёкий.
- Нужен ли вообще аналитический индекс (DuckDB-over-journal-Parquet) для research, или
  research-cli стриминга по журналу достаточно — решается на P2 по скорости гридов.
- Политика ретеншн-возрастов (HOT/WARM/COLD дни) — калибруется по §2-измерениям.
- Точка включения Hetzner Backups / Storage Box-выгрузки для durability — при переходе на
  ценные накопленные данные или live (§7).
