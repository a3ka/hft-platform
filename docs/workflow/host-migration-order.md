# Порядок миграции хоста — сначала новый код, потом старая настройка

Урок `M-94` (2026-10-08, `R-247`, `PROJECT-STATE` раздел M-94). Для спек, которые переносят
настройку с хоста (`.env`, `/etc/cron.d`, файлы вне репозитория) в репозиторий.

## Что случилось

Задача 11 `M-94`: строку `GATEWAY_BANDS` из host `.env` удаляли «после merge'а и ДО деплоя» —
так требовала спека, потому что новый гейт деплоя отказывает, если строка на месте.

| время (UTC) | событие |
|---|---|
| 11:59:13 | строка удалена из `.env` |
| 12:00, 12:15 | cron прогревателя — на СТАРОМ образе; без строки он берёт полосы по умолчанию и греет чужой слепок `ckpt-b0f1ed89…` |
| 12:18 | новый образ встал |
| 12:30:05 | первый прогон нового кода прогрел нужный слепок; выдача снова `ready` |

Около 45 минут выдача отвечала `not_ready`. Данные не задеты: прогон 12:30 успел до ночной уборки
журнала (04:07).

## Причина

Окно «после merge, до деплоя» спека считала безопасным, потому что ВЫДАЧА старого кода читает
окружение только на старте и до деплоя не перезапускается. Но старый код живёт не только в выдаче:
**cron запускает старый образ каждые 15 минут и каждый раз заново читает окружение.** Удаление
настройки до замены образа меняет поведение каждого периодического процесса старого кода.

## Правило для следующих спек

1. В спеке миграции перечислить ВСЕ процессы, читающие переносимую настройку: долгоживущие службы
   и периодические (cron, таймеры), и для каждого указать, КОГДА он перечитывает её.
2. Старую настройку убирать только тогда, когда ни один процесс старого кода её больше не прочтёт.
   Удобная форма: новый код ИГНОРИРУЕТ старую настройку с предупреждением, а не отказывает. Тогда
   строку можно удалить ПОСЛЕ деплоя, без окна.
3. Если отказ при наличии старой настройки нужен (как в `M-94`: «наличие — отказ», `П-032` п.1),
   окно указывается явно, с перечнем периодических прогонов, попадающих в него. Выбирается момент
   сразу после очередного прогона cron, и в спеке названа цена: какая выдача и на сколько.

**`COGNITIVE-ONLY`.** Механизма нет: порядок шагов на хосте исполняет человек или роль по ssh, CI
его не видит. Кандидат на механизацию — тело деплоя (`deploy/bin/deploy-apply.sh`), которое само
убирает перенесённые ключи после `healthy` нового образа, а не требует ручного шага до деплоя.
