# Branch hygiene — общий чекаут ≠ общая ветка (инцидент 2026-07-13)

Источник: инциденты «чужие RED-коммиты уехали с чужим push» (2026-07-11), «chain-break
TD-014» (2026-07-12), «reviewer переключил общий чекаут на main поверх ветки architect'а +
вердикт критика остался untracked-файлом» (2026-07-13).

## Проблема

`/home/nous/hft-platform` — ОДИН рабочий каталог, а ролей много. Когда роль делает
`git checkout` в общем чекауте, она меняет состояние под ногами у всех остальных.
Следствия, которые мы уже видели:
- architect работает на `feat/M-NN`; reviewer переключает чекаут на `main` → следующий
  агент видит «пропавшую» работу и/или коммитит не туда;
- вердикт critic'а (`research/critiques/C-NNN.md`) остаётся **untracked** и выглядит как
  «файл чужой параллельной сессии» — хотя параллельных сессий нет;
- незапушенный коммит dev'а живёт только в его worktree → цепочка рвётся.

## Правила (BINDING)

1. **Ветка milestone'а — общая, чекаут — свой.** Роль, которой нужно состояние, отличное
   от текущего HEAD общего чекаута, обязана взять СВОЙ worktree:
   `git worktree add /tmp/hft-<role>-<milestone> <branch>` — и работать там.
   Общий чекаут переключает ветку ТОЛЬКО тот, кто её сейчас ведёт (architect на этапе
   спеки, dev в своей цепочке).
2. **Перед `git checkout` в общем чекауте — проверь, чей HEAD.** `git branch --show-current`
   + `git status --porcelain`. Есть чужие незакоммиченные файлы или ты не знаешь, кто вёл
   ветку → НЕ переключай, возьми worktree.
3. **Артефакт роли коммитится ролью.** Вердикт critic/risk-critic
   (`research/critiques/C-NNN.md`) — это АРТЕФАКТ гейта, а не черновик: критик коммитит его
   на ветку milestone'а (`docs(critic): C-NNN verdict ...`) в том же ответе, где выносит
   вердикт. Untracked-файл = потерянный аудит-трейл.
4. **Push-scope перед КАЖДЫМ push** (`gates.md` §8): `git log origin/<branch>..HEAD` —
   только твои коммиты. Чужие → СТОП.
5. **Незнакомый untracked-файл — не «чужая сессия», а нарушение (1)–(3).** Не удалять,
   не игнорировать: выяснить владельца по `research/critiques/`, `milestones/`, содержимому;
   передать founder'у, если владелец не определяется.
6. **Git identity субагента — `--worktree` или per-commit `--author` (закреплено 2026-07-14,
   инцидент M-18).** `git config user.name <role>` пишет в `.git/config` — ОБЩИЙ для всех worktree
   репозитория. Два субагента, стартовавшие ПАРАЛЛЕЛЬНО в одном репо, гонят этот конфиг: последний
   писатель побеждает → коммиты одного уезжают под identity другого (в M-18 коммиты venue-dev ушли
   автором `engine-dev` → выглядело как scope-violation venue-кода). Роль ОБЯЗАНА задавать identity
   worktree-локально (`git config --worktree user.name/email`, включив `extensions.worktreeConfig`)
   ЛИБО ставить автора на каждый коммит (`git commit --author='<role> <role@noreply.local>'`).
   **Reviewer в Block-scope сверяет `%an` (автор = роль-владелец зоны) против `%cn` (коммиттер):**
   расхождение автора и зоны → выяснить, не identity-гонка ли это, до вердикта scope-violation.
7. **RN-20: перед перезапуском агента доказывай МОЛЧАНИЕ, а не пустоту (закреплено 2026-08-02,
   M-45).** Новая сессия увидела worktree venue-dev'а прошлой сессии чистым на HEAD критика и
   заключила «dev не стартовал» → запустила второго. Через 15 минут в том же worktree стоял
   коммит: первый dev работал всё это время, на момент снимка просто ещё не коммитил. Дубликат
   успел `git worktree add -B feat/M-NN` и перехватить локальную ветку у живого агента.
   - Одиночный `git status`/`git log` — снимок мига, НЕ доказательство смерти.
   - Скан `/proc/*/cwd` по worktree НЕ работает: cwd агента — базовый чекаут, Bash-вызовы
     транзиентны (тот же класс, что ложь `pgrep`).
   - **Работает:** `stat -c '%y' <файлы зоны агента>` + ПОВТОРНЫЙ снимок git через несколько
     минут. Свежий mtime или сдвинувшийся HEAD ⇒ агент жив, второго НЕ запускать.
   Запустил дубликат по ошибке → немедленно останови его, удали его worktree
   (`git worktree remove --force`) и созданную им локальную ветку (`git branch -D`), убедись,
   что он не тронул файлы зоны живого агента.

## Запрет `commit -a` / `add -A` в общем чекауте (закреплено 2026-07-14)

Третий инцидент того же класса: reviewer, находясь в ОБЩЕМ чекауте, который architect переключил
на `docs/doc-gate`, сделал `git commit -am` — и (а) **снёс вердикт критика** `C-006-doc-gate.md`
(198 строк, артефакт гейта), (б) увёл свои §8-правки не в `main`.

**Правила:**
1. **Никогда `git commit -a` / `git add -A` в общем чекауте.** Только явные пути:
   `git commit -- PROJECT-STATE.md TECH-DEBT.md`.
2. Reviewer/critic работают **из своего worktree** (см. выше), а не в общем каталоге.
3. **Коммит НЕ ИМЕЕТ ПРАВА удалять** `research/critiques/*`, `milestones/*`, `docs/rfc/*` —
   это артефакты гейтов и аудит-трейл. Если `git status` показывает их удаление — СТОП, ты не на
   своей ветке. (Механический барьер — pre-commit/CI-проверка — вынесен на doc-гейт: `C-006` re-audit.)

## Worktree lifecycle — рекультивация обязательна (закреплено 2026-07-17, ENFORCED 2026-07-22)

Дисковая протечка повторилась: **61 worktree × ~3.5 GB `target/` ≈ 190 GB** в `/tmp` при том, что
исходник каждого — пара мегабайт. Корень процессный: правило «создай worktree на роль/задачу» (выше)
кодифицировано, а «освободи после» — было записано (2026-07-17) но **не смержено и без enforcement'а** →
мёртвая буква. `git worktree` шарит `.git`, но **не `target/`** — каждый worktree компилирует свой multi-GB
кэш при первом гейте, и никто его не сносит. Фикс на этот раз: правило + **скрипт** + **гейт** (иначе не держится).

**Правила:**
1. **`target/` worktree — эфемерный кэш, не работа.** Регенерируется `cargo`; исходник и `.git` целы при сносе.
2. **Enforcement — `scripts/gc_worktrees.sh`** (безопасен по конструкции): удаляет worktree ТОЛЬКО если
   ВСЕ три: (а) чистый (`git status --porcelain` пусто); (б) нет только-локальных коммитов
   (`git rev-list HEAD --not --remotes` == 0); (в) HEAD целиком на `origin/main` (смержен). Никогда `--force`,
   никогда `rm -rf` вслепую; активные (dirty/unpushed/не-смерженные feat) НЕ трогаются. `--dry-run` — превью.
3. **Reviewer в close-out (после merge feat→main)** ЗАПУСКАЕТ `bash scripts/gc_worktrees.sh` — часть close-out,
   как обновление `PROJECT-STATE.md` (`gates.md` §8). Это снимает worktree'ы только что смерженного милстоуна.
4. **Периодический GC (architect/reviewer)** — тот же скрипт в любой момент; безопасно идемпотентен.
5. **Ручной снос dirty/unpushed — только с сохранением.** Если нужно снести НЕ прошедший gc-скрипт worktree
   (реальные правки/незапушенные коммиты): сперва `git diff HEAD > /tmp/salvage-<name>.patch` (или
   `git push origin HEAD:<branch>`), лишь потом `git worktree remove --force`. Молчаливый снос = потеря работы
   (тот же класс, что «незапушенный коммит уехал»). Скрипт этого НЕ делает — только человек с явным решением.
6. **Владелец GC — reviewer (close-out) + architect (периодический).** «Создал worktree и ушёл, оставив 3.5 GB» —
   такое же незакрытие цикла, как «запушил и ушёл» (`gates.md` §8).
7. **Git identity выставляется ПЕРВЫМ шагом в новом worktree (инцидент 2026-07-26, M-37).** Worktree наследует
   `user.name/email` общего чекаута — роль-создатель ОБЯЗАНА сразу `git config user.name <role>; git config
   user.email <role>@noreply.local`, иначе коммиты несут ЧУЖУЮ identity. Последствие M-37: impl задач #1-4 закоммичен
   под `reviewer` → reviewer не мог независимо заапрувить (gates §4 независимость: КТО ПИСАЛ КОД, а не что в логе).
   **Переклейка авторства (`filter-branch`) НЕ чинит нарушение** — она отмывает метку, оставляя код, написанный
   не той ролью; аудит-трейл становится ложным. Правильная ремедиация — переписать код правильной ролью
   (`gates.md` §4). Bootstrap-промпт dev-агента ОБЯЗАН содержать `git config user.*` первым шагом.

8. **RN-21: не пушь в ветку, на которой РАБОТАЕТ агент, без предупреждения (закреплено
   2026-08-03, M-53).** Architect дописал sacred-оракулы в `feat/TD-083`, пока engine-dev на
   ней работал. У dev'а в ИНДЕКСЕ оказалось удаление этих файлов (`D` на 245 строк оракула и
   `−11` строк гейта) — артефакт синхронизации: он подтянул новые коммиты поверх состояния,
   где файлов ещё не было. Один `git commit -a` — и чужая работа снесена, причём выглядело бы
   это как scope-violation dev'а, хотя виноват был бы порядок действий architect'а.
   - **Architect:** запушил в чужую рабочую ветку — НЕМЕДЛЕННО сообщи агенту (`SendMessage`),
     перечислив добавленные файлы и команду восстановления:
     `git checkout HEAD -- <пути>` + `git status --porcelain` (в выводе не должно быть `D`).
   - **Dev:** перед КАЖДЫМ коммитом — `git status --porcelain`; любое `D` на файле, который ты
     не удалял, значит ветка разошлась под тобой. Не коммить, восстановить, сообщить.
   - Правило push-scope (`git log origin/<branch>..HEAD`) ловит чужие КОММИТЫ, но НЕ ловит
     чужие файлы, попавшие в твой индекс как удаление. Это отдельная проверка.
