# Testing Rules — RED-first TDD

Источник: `docs/04-workflow.md` §2/§3 ("RED-first"), `docs/DESIGN.md` §4 (`RK-I-1..10`),
§1 (`DET-I-1`), `docs/03-integration-contract.md` §6 (`INTG-I-*`). Обязательный порядок:
**Research → Plan → TEST (RED) → Implement (GREEN) → Refactor → Review.** Шаг 3 не
пропускается никогда.

## Тест — это спецификация, не проверка постфактум

Тест пишется architect'ом ДО кода и определяет, ЧТО код обязан делать. Vague-задача
("сделай risk-gate") даёт код, который "выглядит правильно" и может тонко ошибаться.
Конкретный тест не оставляет места для галлюцинации:

```rust
#[test]
fn rk_i_1_no_order_reaches_venue_without_risk_approved() {
    // Типовой барьер: venue-адаптер принимает ТОЛЬКО RiskApproved<Order>,
    // не Order. Компилятор — часть теста.
    let raw = Order::new(/* ... */);
    // let _ = venue.submit(raw); // <- НЕ ДОЛЖНО КОМПИЛИРОВАТЬСЯ
    let approved = risk_gate.check(raw).expect("должно быть Approved");
    assert!(venue.submit(approved).is_ok());
}
```

## Анти-плацебо — тест GREEN против заглушки = дефект

Урок hft-core-rs (`docs/DESIGN.md` §9, risk_guard fail-open инцидент): тест обязан
ПАДАТЬ, если реализация — no-op/заглушка/`Ok(())` без реальной проверки. Перед тем как
считать RED-тест валидным, architect мысленно (или явно) прогоняет его против
заглушечной реализации и убеждается, что он FAIL. Пример неправильного теста:
`assert!(risk_gate.check(order).is_ok())` — проходит даже если `check()` всегда
возвращает `Ok`. Правильно: assert конкретного отказа на конкретном invalid-входе
(`RK-I-3` — неизвестный инструмент → `Reject`, не default-лимиты).

## Sacred RED-оракулы

- **`RK-I-1..10`** (`docs/DESIGN.md` §4) — риск-инварианты. Живут в `crates/risk/tests/`
  и `crates/killswitch/tests/`. Только architect пишет/меняет.
- **`DET-I-1`** (бит-идентичный replay журнала, `docs/DESIGN.md` §1) — детерминизм-тест
  журнала; P0 acceptance-ворота (`docs/DESIGN.md` §10).
- **`INTG-I-1..7`** (`docs/03-integration-contract.md` §6) — границы A/B/C; тест
  подтверждает ОТСУТСТВИЕ альтернативного write-пути в рантайм (не наличие проверки —
  отсутствие обхода).
- **`CT-I-1..6`** (`docs/05-contract-layer.md` §6) — контрактный слой; grep-канарейка
  `EventKind` определён ровно в одном крейте, roundtrip-фикстуры старых версий журнала.

Эти тесты dev НЕ трогает даже при рефакторинге вокруг них. Показался неправильным →
`!!! SCOPE VIOLATION REQUEST !!!` (`.claude/rules/scope-guard.md`).

## Каждая публичная функция — с тестом

- **Домен без I/O** (`crates/journal`, `crates/book`, `crates/signals`, `crates/alpha`,
  `crates/portfolio`) — чистые функции, детерминированные, без wall-clock/`rand()`/
  неупорядоченной итерации по `HashMap` в редьюсерах (журнал-принцип, `docs/DESIGN.md` §1).
  Сигнал не имеет доступа к будущему — только к потоку `Event` до текущего момента.
- **Границы I/O** (`venue-*`, `journal` writer, `oms` submit) — интеграционные тесты,
  явно поименованные (`test_venue_hyperliquid_reconnect_no_orders.rs` и т.п.).
- **Детерминизм-тест обязателен для каждого сигнала**: одинаковый вход → одинаковый
  выход, независимо от порядка вызова (`docs/02-quant-desk.md` §3.2).

## Покрытие

- **80%+** для `crates/risk`, `crates/killswitch`, `crates/oms` (пре-trade path),
  контрактных roundtrip-тестов.
- **60%+** для остального (`signals`, `book`, `alpha`, `portfolio`, `research-cli`).

## Команда прогона

```bash
cargo test -p <crate>              # один крейт
cargo test --workspace             # весь workspace (перед PR-time reviewer)
cargo test -p risk -p killswitch   # sacred-путь явно, при любом касании oms/venues
```

Python research-тулинг (`crates/research-cli` обвязка / ноутбуки, если появятся):
`pytest research/ -v` — только консюмер контрактов (`docs/05-contract-layer.md` §5),
не пишет T1 в рантайм.

## Что нарушение выглядит как

- Реализация закоммичена раньше или в одном коммите с первым RED-тестом.
- Тест дергает `RiskApproved` конструктор напрямую вместо приватного конструктора
  крейта `risk` (обходит типовой барьер `RK-I-1`).
- Тест на сигнал не проверяет детерминизм (два прогона с одним `Event`-потоком дают
  разный результат — незамечено).
- `#[ignore]` или `#[should_panic]` без обоснования на sacred-тесте.

## Прод-масштаб для sacred I/O-путей (урок TD-011, 2026-07-11)

RED-оракул sacred-пути с I/O (journal `open`/`read`/`recover`, recorder writer,
venue book-maintenance) ОБЯЗАН включать **прод-масштабный кейс**, не только крошечные
in-memory фикстуры. Инцидент TD-011: `Journal::open` делал `read_to_end` ВСЕГО сегмента
(прод 2.65 GiB) в RAM → recorder переставал писать (OOM-риск); юнит-RED на фикстурах в
десятки байт этого не поймал, CI зелёный по компиляции + «Deploy success» замаскировали —
регрессию поймал ТОЛЬКО eyes-on §8 на VPS (ssh-проверка живого прода).

Требования к таким оракулам:
- **Граница ресурса, не только корректность.** Для `open()`/загрузки — большой сегмент
  (десятки MiB+) + проверка ОГРАНИЧЕННОЙ памяти (счётчик аллокаций через global allocator)
  и/или времени. Оракул обязан ПАДАТЬ на наивной реализации (full-read) — анти-плацебо
  (пример: `crates/journal/tests/red_open_bounded.rs`).
- **Зелёные юнит-тесты + Deploy-success ≠ рабочий прод.** `.claude/rules/gates.md` §8
  eyes-on (контейнер пишет, heartbeat свежий, сегмент растёт, CPU/MEM в норме) —
  обязателен и решающий; healthcheck можно обмануть тихой деградацией.

## Фикстура «счастливого пути» — дефект оракула (закреплено 2026-07-14)

Два milestone'а подряд дефект прошёл ВСЕ зелёные гейты и был пойман только на PR-гейте
reviewer'ом — оба раза причина одна: **идеальная фикстура**.

- **M-07 (equity-curve):** оракул проверял кривую там, где на событии был РОВНО один филл;
  реализация ломалась на событии с 2+ филлами. Фикстура не содержала мульти-филлового события.
- **M-08 (эвикция книги, TD-016):** оракул «эвикция не режет живую книгу» использовал
  СИММЕТРИЧНЫЙ дифф (обновлялись top-N обеих сторон) → `diff_mid` совпадал с реальным mid и
  дефект не проявлялся. На АСИММЕТРИЧНОМ диффе (лучший bid не менялся — штатная ситуация)
  реализация стирала живые уровни, включая best bid, и порча уходила в журнал навсегда.

**Правило.** Оракул границы ресурса / инварианта данных ОБЯЗАН включать ДЕГРАДИРОВАННЫЙ вход,
а не только идеальный. Минимум, который architect обязан пройти по чек-листу перед коммитом
RED-набора:

1. **Асимметрия.** Вход, где обновляется/приходит только ОДНА сторона (или подмножество
   полей): односторонний дифф, событие без топовых уровней, филл только по одной ноге.
2. **Множественность.** Два и более элемента в одном такте (2 филла на событии, 2 интента,
   2 сегмента) — там, где наивная реализация считает «один».
3. **Отсутствие.** То, чего в сообщении НЕТ, — не сигнал к удалению/обнулению. Проверить, что
   реализация не додумывает за источник (дифф не говорит ничего о неупомянутых уровнях).
4. **Границы.** Пусто / один элемент / переполнение / усечение / переход через границу
   сегмента-окна-капа.
5. **Прод-масштаб** (для sacred I/O — уже обязателен, см. выше).
6. **Прод-РЕЖИМ значения, не фикстура-допущение (урок TD-031, 2026-07-14).** Если инвариант
   зависит от значения, которое в ПРОДЕ имеет конкретный режим, — фикстура ОБЯЗАНА этот режим
   воспроизвести, а не задать «удобное» значение, которое инвариант пред-удовлетворяет. Инцидент:
   оракул изоляции L2Delta (`red_l2delta_rollback_boundary`) задавал в фикстуре РАЗНЫЙ `provenance`
   (P1≠P2) → был зелёным. В проде `provenance` — КОНСТАНТА (recorder считает git-sha в рантайме, а
   контейнер без git → `no-git-info` на всех деплоях), поэтому изоляция реально НЕ работала, а §8
   поймал смешение variant-6 в чужой сегмент. Правило: параметр, от которого зависит sacred-инвариант,
   в оракуле берётся в ПРОД-режиме (здесь — ИДЕНТИЧНЫЙ константный provenance, изоляция обязана
   держаться другим механизмом). Это тот же класс, что «фикстура счастливого пути», но про КОНСТАНТУ
   окружения, а не про форму данных. Симптом: оракул зелёный, потому что фикстура задала различие,
   которого в проде НЕТ.
7. **Точка НАБЛЮДЕНИЯ, не только вход (урок TD-042, 2026-07-27 — ТРЕТИЙ «идеальный фикстур» подряд
   после M-07/M-08).** Чек-лист выше про ВХОДНЫЕ данные; но оракул с состоянием/fold'ом зависит ещё
   и от того, ГДЕ наблюдаем — курсор, окно, точка среза, момент apply. Варьируй vantage, а не только
   данные. Инцидент: `windowed_live_eq_replay` ставил курсор C в СЕРЕДИНУ истории → окно `snapshot(C)`
   не пересекалось с финальным → баг эвикции (сдвиг удержанных значений) шёл по ПУСТОМУ списку →
   зелёный. Штатный live ВСЕГДА даёт пересечение окон. Правило: для инкрементальных/fold-инвариантов
   (live==replay, merge, эвикция) оракул ОБЯЗАН включать наблюдение, где existing-состояние
   ПЕРЕСЕКАЕТСЯ с финальным (не только evict-all/disjoint) + многошаговый fold (накопление ошибки).

Если хотя бы один из пунктов не покрыт — оракул НЕ считается готовым, и milestone не уходит
dev-агенту. Симптом, который должен настораживать: тест зелёный с первого запуска против
кода, который ещё не написан «правильно» — значит фикстура не давит на инвариант.

## Оракул обязан мерить ТО, ЧТО ОБЕЩАЕТ (закреплено 2026-07-14, TD-021)

Третий класс дефекта — после «фикстуры счастливого пути» и «инварианта без проверки»:
**оракул измеряет не ту величину**, и все гейты честно зеленеют поверх реальной проблемы.

Инцидент: TD-016 («лик памяти recorder'а +6.5 MiB/час») был заведён по `docker stats`, который
включает **page cache файла журнала**. Recorder пишет ~30 MB/мин → «память» растёт при нулевом
лике. Реальный рост кучи (`RssAnon`) — +1 MiB/час. По этой метрике был написан RED-оракул, принят
контракт эвикции книги и **сделан фикс, рисковавший порчей первичных данных** — ради экономии
16 MB из 7.5 GiB.

**Правила:**
1. **Метрика, на которой заводится долг/инвариант, сама подлежит валидации.** Прежде чем писать
   оракул: «что именно считает эта цифра?» (`RssAnon` vs `memory.current`; `len()` vs байты;
   wall-clock vs event-time). Если не можешь назвать — оракула ещё нет.
2. **Оракул границы ресурса меряет ресурс, а не прокси.** Память — anon-куча; диск — байты
   сегментов; латентность — измеренные распределения, не «оценка».
3. **Различай РОСТ и СХОДИМОСТЬ.** Монотонный рост на коротком окне может быть выходом на
   плато (пример: книга бутстрапится REST-снапшотом top-5000 и постепенно узнаёт реальные
   дальние уровни из diff-потока). Оракул обязан отличать «растёт без предела» от «сходится к
   реальному размеру» — иначе мы «чиним» корректное поведение.
4. **Цена ошибки решает направление фикса.** Прежде чем ограничивать ресурс, спроси: что дороже —
   ресурс или данные? Память дёшева (7.5 GiB), боевые данные незаменимы. Фикс, экономящий дешёвое
   ценой риска для дорогого, — не фикс.
## Целостность гейта — 4 свойства (закреплено 2026-07-15, ~10 дефектов одной сессии)

За один milestone (M-08 + doc-гейт C-006) **десять** гейтов/оракулов оказались зелёными, пока
защищаемое свойство было сломано. Причина всякий раз — одна из четырёх: гейт проверял не то, не
той формой, не против того или не замечал молчания. Гейт/оракул НЕ считается готовым, пока не
удовлетворяет ВСЕМ четырём. Каждое свойство обязано быть предъявлено (прогоном, не рассуждением).

1. **Прогоняет ПРОД-ФОРМУ, а не суррогат.** Гейт обязан дёргать артефакт ровно так, как его
   дёргает прод — та же форма argv, тот же путь вызова. Гейт, проверенный не тем вызовом, каким
   его зовёт прод, не проверен.
   - `check_protected_artifacts` брал базу из `origin/main`, а CI на push даёт её из события ⇒
     гейт был зелёным ВСЕГДА (ложный гейт хуже отсутствующего).
   - D5a/D7 гоняли argv **cron-скрипта** (раздельная форма), а прод-сервис — compose `command:`
     (equals-форма) ⇒ пропустили TD-024. Фикс — D8: прогон РЕАЛЬНОЙ compose-формы через бинарь.

2. **Меряет СВОЙ инвариант, а не окружение/прокси.** Оракул обязан ассертить ровно ту величину,
   что называет, а не окружающий заменитель. Тест, чей исход зависит от хоста (диск, ядра,
   параллельность) — меряет окружение, это флак.
   - C5 мерил размер результата (`Vec` 60k событий), а не память РАСПАКОВКИ (TD-021-класс).
   - TD-023: глобальный аллокатор считал ВЕСЬ процесс, а нужна была память книги; порог 4 MiB —
     фикция устаревшей эпохи.
   - TD-025: тест зависел от свободного места ХОСТА, а не от корректности миграции.
   - TD-040: counting-allocator процесс-глобален; cargo гонит тесты одного бинаря ПАРАЛЛЕЛЬНО → замер
     `peak` одного теста ловил аллокации другого (dev PASS / CI FAIL, недетерминизм). Фикс: (а)
     сериализовать замеряющие тесты общим `static Mutex` (замер видит только свои аллокации); (б)
     держать конфаундинг-измерение КОНСТАНТНЫМ (размер сегмента), варьируя ТОЛЬКО измеряемое (число
     сегментов) — иначе per-segment буфер коррелирует с размером журнала. Resource-оракул на глобальном
     счётчике ОБЯЗАН быть single-threaded-по-замеру.

3. **Падает против СЛОМАННОГО (анти-плацебо) И против несостоявшегося SETUP.** Гейт обязан
   краснеть (а) против дефекта, который стережёт — прогони его против пред-фиксной реализации;
   (б) если его СОБСТВЕННЫЙ setup не подготовил названное состояние. Проба, молча тестирующая не
   тот сценарий, — плацебо самой себя.
   - Вся сага doc-гейта P1–P17: сценарий с молча-провалившимся `git merge`/`commit`/`mv` рапортует
     PASS, доказывая ДРУГОЙ путь. Лечится setup-guard'ом на КАЖДЫЙ сценарий (доказать форму: есть
     merge-коммит / переименование видно как R / диапазон непуст / blob изменился).
   - D5-стаб глотал любые аргументы ⇒ **застабил ровно тот контракт argv, который и ломался**.
     Следствие-правило: **стаб не смеет подменять проверяемый контракт** — стаб уместен для
     обвязки (реакция на сбой), но саму проверяемую величину гейт гоняет по-настоящему.

4. **Наблюдает ОТСУТСТВИЕ, не только сбой.** Монитор, сигналящий «упало», но не «никогда не
   запускалось», слеп к тихому молчанию. И сбой, И молчание обязаны быть видимы.
   - `*.alert` ловил «прогон упал»; «cron не установлен / crond мёртв / ребут» — нет. Фикс — D9:
     позитивный heartbeat `*.last-success` + монитор по его СВЕЖЕСТИ.
   - Класс TD-011: тихая деградация под зелёным healthcheck'ом — то же отсутствие наблюдаемости.

Симптом, требующий стоп-проверки: гейт зелёный, но ты не можешь предъявить, ЧТО он покраснеет
против конкретного слома. Не можешь — гейт декоративен.

## RED сравнения ДВУХ источников ОБЯЗАН моделировать live-режим (закреплено 2026-07-17)

Инцидент M-09 §8: recon-оракулы (`red_recon_sink::normal_book_is_silent`, `red_recon_wiring`)
сравнивали книгу **С САМОЙ СОБОЙ** (local собран из того же снапшота, что reference) → всегда
GREEN на юнитах → на проде recon флудил `ReconDivergence` на КАЖДОМ цикле здорового рынка
(green-unit/live-flood, класс TD-011/TD-016). Мой wiring-RED сам оказался «фикстурой счастливого
пути» — ровно тот дефект, что мы ловим у других. Корень вскрылся только замером живого источника:
сравниваемые представления НЕСОПОСТАВИМЫ по построению (одна книга глубже/бакетированнее/свежее другой).

**Правило (doc-гейт).** Если RED проверяет СХОДИМОСТЬ/РАСХОЖДЕНИЕ двух источников (recon книги с
биржей, реплики журнала, двух парсеров, локального расчёта с эталоном), фикстура ОБЯЗАНА моделировать
то, чем источники в проде РЕАЛЬНО отличаются, а НЕ сравнивать источник с самим собой:

1. **Разные представления.** Если в проде A бакетирован/усечён/нормализован, а B — сырой, фикстура
   обязана дать A и B в РАЗНОЙ форме (не один и тот же объект дважды). Сначала ИЗМЕРЬ форму каждого
   источника на живых данных (`[verify-at-impl]`), потом пиши фикстуру.
2. **Разная глубина/охват.** Если один источник видит меньше (REST limit, окно, ретеншен), фикстура
   обязана дать асимметрию охвата и проверить, что оракул НЕ считает недостижимое расхождением.
3. **Разные моменты.** Если снимки берутся в разные мс (timing-skew), фикстура обязана сдвинуть один
   и проверить толерантность к норме vs ловлю реального десинка.
   - **Один сдвинутый момент НЕДОСТАТОЧЕН, если величина MEAN-REVERTING** (закреплено 2026-07-17,
     ВТОРОЙ §8-провал M-09). near-touch ОБЪЁМ двух async-снапшотов одной биржи расходится на сотни bps
     со СМЕНОЙ ЗНАКА (замер: `+-+`, `+--`, `---`) — per-cycle сравнение флудит на здоровом рынке, и
     оракул на ОДИН такт этого не ловит. Если источники сравнивают ВЕЛИЧИНУ, которая сама шумит между
     моментами (объём, глубина, count), фикстура ОБЯЗАНА быть ПОСЛЕДОВАТЕЛЬНОСТЬЮ моментов (окно), и
     оракул обязан отличать churn (знак гуляет, mean→0 → тишина) от персистентного сдвига (знак
     держится → алерт). Одинаковая per-cycle магнитуда у churn и порчи — разница ТОЛЬКО в
     персистентности. **⚠ Урок B2 (2026-07-18, ТРЕТИЙ §8-провал того же класса): даже ОКОННЫЙ
     дискриминатор недостаточен, если фикстура — СИНТЕТИЧЕСКИЙ zero-mean churn (±X идеально
     балансируется за K).** Реальный two-source skew может нести СИСТЕМАТИЧЕСКИЙ (не zero-mean) bias:
     усреднение окна гасит дисперсию, но НЕ bias → live-flood при зелёном юните (green-unit заново, этажом
     глубже). Если ground truth второго источника систематически смещён (WS(T1)-бакет vs raw-REST(T2)
     объём), величина в принципе НЕ верифицируема в рантайме — честный ответ «убрать из рантайма»
     (B2, `docs/fa/ops.md` §4.3.2), а не калибровать окно. Фикстура оконного оракула ОБЯЗАНА нести
     ПРОД-ПОДОБНЫЙ ненулевой остаток, не идеальный zero-mean.
4. **Анти-плацебо в ОБЕ стороны.** Набор обязан падать и против «слишком строгого» impl (флудит на
   норме), и против «слишком мягкого» (пропустил реальную порчу) — как в `red_recon_live.rs`
   (no-skip-флуд И over-skip-пропуск И пустой-источник-тишина) и `red_recon_runtime.rs` (B2:
   персистентный объём→тишина ВАЛИТ window-active impl И best-эмит ВАЛИТ always-silent impl).

Симптом нарушения: RED зелёный с первого прогона против кода, который сравнивает two-source, но
фикстура строит оба источника из одного входа. Это НЕ оракул сходимости — это тавтология.

## Мутационный контроль: «тест зелёный» НЕ доказывает, что он что-то пиннит (TD-048, 2026-07-29)

**Оракул инварианта обязан ПАДАТЬ при нейтрализации той самой проверки, которую он якобы пиннит.**
Пока это не измерено, «10 passed» означает лишь «тесты не упали», а не «инвариант защищён».

Цена урока: M-48 задача #3 (gap-детект чекпоинта) была **мёртвым кодом** при `9 passed / 0 failed`.
Reviewer закомментировал спец-проверку разрыва — не упал ни один тест: оракул удовлетворялся
ДРУГОЙ веткой кода. Дефект не нашли ни architect, ни critic (четыре раунда C-032..C-035), ни dev,
ни tester — только мутация на PR-гейте.

Процедура (обязательна для sacred-оракула, дёшева — минуты):
1. Найди в реализации СТРОКИ, которые оракул обязан защищать.
2. Нейтрализуй их (закомментируй / замени на `true` / удали ветку).
3. Прогони оракул. **Не упал → оракул ничего не пиннит**, чини его, а не радуйся зелёному.
4. Верни код. Результат мутации — в Done Block: «нейтрализация X → тест Y FAILED».

Кто делает: architect при написании оракула; dev — при заявлении «задача DONE» на любой задаче,
чей acceptance формулируется как «оракул GREEN»; reviewer — выборочно на PR-гейте.

**Связанное следствие.** Если оракул зелёный ТОЛЬКО в паре с другим изменением (M-48: gap-детект
становится load-bearing лишь после того, как невалидный чекпоинт перестал быть ошибкой), эта
зависимость пишется В САМОМ ТЕСТЕ. Иначе следующий агент ослабит один из пары и не узнает.

## Ассерт «изменилось» обязан называть, ОТ ЧЕГО (закреплено 2026-07-29)

`assert_ne!(after, before)` без явного эталона — источник противоречивых тестов. В M-48 sacred-оракул
снимал `before` ДО порчи файла и требовал, чтобы перезапись дала ДРУГИЕ байты. Но детерминированный
rebuild обязан воспроизвести те же байты — то есть тест требовал **недетерминизма**, прямо
противоположного `DET-I-1` и идемпотентности, которые тот же набор и защищает. Тест был непроходим
ни для какой корректной реализации; поймал это engine-dev через `SCOPE VIOLATION REQUEST` (верное
поведение: он отказался «подогнать» реализацию под противоречивый тест).

Правило: у проверки «состояние изменилось» обязаны быть ДВА именованных эталона, и оба ассертятся:
- `assert_ne!(after, <то, что должно исчезнуть>)` — старое состояние не пережило операцию;
- `assert_eq!(after, <то, что должно получиться>)` — новое состояние ровно такое, как обещано.

Одного `assert_ne` мало: он проходит при ЛЮБОМ изменении, включая недетерминированный мусор.

## Канарейка ops-пути ИСПОЛНЯЕТ вызывателя, а не грепает вызываемое (TD-048, 2026-07-29)

`test -f binary` и `grep name docker-compose.yml` — **не проверки**, а описания намерений. Обе были
зелёными, когда прод-бинарь M-38b не стартовал НИ ПРИ КАКОЙ форме argv, а cron-запись отсутствовала
вовсе. Милстоун смержили с 32/32 PASS и полностью инертной в проде фичей; следом потребовался
отдельный milestone (M-48) и четыре раунда критика.

Для любого шва «есть артефакт + есть тот, кто его зовёт» канарейка обязана:
1. **Запустить вызывателя** (бинарь с argv из `docker-compose.yml`; cron-обёртку через
   `HFT_CRON_PRINT_ARGV=1`, печатающую argv без побочных эффектов) и проверить exit-код;
2. **Проверить КОМПОЗИЦИЮ**, а не звенья по отдельности: путь, куда пишет producer, обязан совпасть
   с путём, откуда читает consumer. Рассогласование двух строк = тихий no-op на проде;
3. **Дойти до доставки:** файл в репозитории при деплое, который его не устанавливает, инертен так
   же, как несуществующий (`deploy.yml` не ставил `cron.d` — `grep -c gateway-checkpoint` на VPS = 0).

Формулировка «канарейка слабая, но честная» — красный флаг: проверь, не является ли она ВАКУУМНОЙ
(в M-48 такая грепала запись, существовавшую до milestone'а, и проходила при полностью отсутствующей
новой).


## Спека правки существующего кода обязана содержать ЗАПРЕТНЫЙ СПИСОК (закреплено 2026-07-31, M-49)

Три REJECT'а подряд на одном milestone'е имели ОДНУ причину: спека перечисляла, **что сделать**,
и не перечисляла, **чего делать нельзя**. Пробел в спеке реализация заполняет по-своему — и
имеет на это право; это не недобросовестность исполнителя, а отсутствие границы.

- **rev1:** не запрещено ослаблять соседние инварианты → ослаблен `segments()` (строгий путь
  чтения стал молча пропускать повреждённый сегмент — «тихая ложь в данных»).
- **rev2:** не запрещены побочные эффекты на файлах → в `open_with` (горячий путь старта)
  появилось физическое перемещение сегмента данных в `quarantine/`, не покрытое ни одним
  оракулом.
- **rev2:** не запрещено менять сигнатуры → перестроен поток данных между функциями, то есть
  принято проектное решение, которое обязан принимать architect.

**Правило.** Спека, изменяющая СУЩЕСТВУЮЩИЙ код, обязана содержать таблицу «Запрещено / Почему»:
какие соседние инварианты трогать нельзя, какие побочные эффекты недопустимы, какие сигнатуры
и потоки данных менять нельзя, где границы зоны. Если задачу иначе не решить — исполнитель
обязан остановиться со `!!! SCOPE VIOLATION REQUEST !!!`, а не расширять область самостоятельно.

## Мутационный контроль: второй вопрос — «что пришлось ослабить рядом» (закреплено 2026-07-31, M-49)

Мутация «откатить фикс → оракул обязан упасть» проверяет, что оракул **привязан к дефекту**.
Она НЕ проверяет, что фикс не куплен ценой соседнего инварианта. На M-49 rev1 первый вопрос
проходил (две мутации подтвердили load-bearing оракулы), а реализация при этом ослабила
`segments()` — и поймал это только человеческий взгляд reviewer'а на PR-гейте.

**Правило.** Мутационный контроль обязан отвечать на ДВА вопроса:
1. падает ли оракул, если откатить фикс (привязка к дефекту);
2. **какой смежный инвариант пришлось ослабить, чтобы пройти оракул** — проверяется обратной
   мутацией: вернуть послабление и убедиться, что его ловит отдельный оракул.
Если на второй вопрос ответа нет — нужен оракул-сторож на соседний инвариант (пример: `ti_6`
«строгий путь чтения остаётся строгим», `op_4` «`open_with` не трогает файлы данных»).
