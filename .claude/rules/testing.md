# Testing Rules — RED-first TDD

Источник: `docs/04-workflow.md` §2/§3 ("RED-first"), `docs/DESIGN.md` §4 (`RK-I-1..10`),
§1 (`DET-I-1`), `docs/03-integration-contract.md` §6 (`INTG-I-*`). Обязательный порядок:
**Research → Plan → TEST (RED) → Implement (GREEN) → Refactor → Review.** Шаг 3 не
пропускается никогда.

## Тест — это спецификация, не проверка постфактум

Тест пишется architect'ом ДО кода и определяет, ЧТО код обязан делать. Vague-задача
("сделай risk-gate") даёт код, который "выглядит правильно" и может тонко ошибаться.
Конкретный тест не оставляет места для галлюцинации:

```rust
#[test]
fn rk_i_1_no_order_reaches_venue_without_risk_approved() {
    // Типовой барьер: venue-адаптер принимает ТОЛЬКО RiskApproved<Order>,
    // не Order. Компилятор — часть теста.
    let raw = Order::new(/* ... */);
    // let _ = venue.submit(raw); // <- НЕ ДОЛЖНО КОМПИЛИРОВАТЬСЯ
    let approved = risk_gate.check(raw).expect("должно быть Approved");
    assert!(venue.submit(approved).is_ok());
}
```

## Анти-плацебо — тест GREEN против заглушки = дефект

Урок hft-core-rs (`docs/DESIGN.md` §9, risk_guard fail-open инцидент): тест обязан
ПАДАТЬ, если реализация — no-op/заглушка/`Ok(())` без реальной проверки. Перед тем как
считать RED-тест валидным, architect мысленно (или явно) прогоняет его против
заглушечной реализации и убеждается, что он FAIL. Пример неправильного теста:
`assert!(risk_gate.check(order).is_ok())` — проходит даже если `check()` всегда
возвращает `Ok`. Правильно: assert конкретного отказа на конкретном invalid-входе
(`RK-I-3` — неизвестный инструмент → `Reject`, не default-лимиты).

## Sacred RED-оракулы

- **`RK-I-1..10`** (`docs/DESIGN.md` §4) — риск-инварианты. Живут в `crates/risk/tests/`
  и `crates/killswitch/tests/`. Только architect пишет/меняет.
- **`DET-I-1`** (бит-идентичный replay журнала, `docs/DESIGN.md` §1) — детерминизм-тест
  журнала; P0 acceptance-ворота (`docs/DESIGN.md` §10).
- **`INTG-I-1..7`** (`docs/03-integration-contract.md` §6) — границы A/B/C; тест
  подтверждает ОТСУТСТВИЕ альтернативного write-пути в рантайм (не наличие проверки —
  отсутствие обхода).
- **`CT-I-1..6`** (`docs/05-contract-layer.md` §6) — контрактный слой; grep-канарейка
  `EventKind` определён ровно в одном крейте, roundtrip-фикстуры старых версий журнала.

Эти тесты dev НЕ трогает даже при рефакторинге вокруг них. Показался неправильным →
`!!! SCOPE VIOLATION REQUEST !!!` (`.claude/rules/scope-guard.md`).

## Каждая публичная функция — с тестом

- **Домен без I/O** (`crates/journal`, `crates/book`, `crates/signals`, `crates/alpha`,
  `crates/portfolio`) — чистые функции, детерминированные, без wall-clock/`rand()`/
  неупорядоченной итерации по `HashMap` в редьюсерах (журнал-принцип, `docs/DESIGN.md` §1).
  Сигнал не имеет доступа к будущему — только к потоку `Event` до текущего момента.
- **Границы I/O** (`venue-*`, `journal` writer, `oms` submit) — интеграционные тесты,
  явно поименованные (`test_venue_hyperliquid_reconnect_no_orders.rs` и т.п.).
- **Детерминизм-тест обязателен для каждого сигнала**: одинаковый вход → одинаковый
  выход, независимо от порядка вызова (`docs/02-quant-desk.md` §3.2).

## Покрытие

- **80%+** для `crates/risk`, `crates/killswitch`, `crates/oms` (пре-trade path),
  контрактных roundtrip-тестов.
- **60%+** для остального (`signals`, `book`, `alpha`, `portfolio`, `research-cli`).

## Команда прогона

```bash
cargo test -p <crate>              # один крейт
cargo test --workspace             # весь workspace (перед PR-time reviewer)
cargo test -p risk -p killswitch   # sacred-путь явно, при любом касании oms/venues
```

Python research-тулинг (`crates/research-cli` обвязка / ноутбуки, если появятся):
`pytest research/ -v` — только консюмер контрактов (`docs/05-contract-layer.md` §5),
не пишет T1 в рантайм.

## Что нарушение выглядит как

- Реализация закоммичена раньше или в одном коммите с первым RED-тестом.
- Тест дергает `RiskApproved` конструктор напрямую вместо приватного конструктора
  крейта `risk` (обходит типовой барьер `RK-I-1`).
- Тест на сигнал не проверяет детерминизм (два прогона с одним `Event`-потоком дают
  разный результат — незамечено).
- `#[ignore]` или `#[should_panic]` без обоснования на sacred-тесте.

## Прод-масштаб для sacred I/O-путей (урок TD-011, 2026-07-11)

RED-оракул sacred-пути с I/O (journal `open`/`read`/`recover`, recorder writer,
venue book-maintenance) ОБЯЗАН включать **прод-масштабный кейс**, не только крошечные
in-memory фикстуры. Инцидент TD-011: `Journal::open` делал `read_to_end` ВСЕГО сегмента
(прод 2.65 GiB) в RAM → recorder переставал писать (OOM-риск); юнит-RED на фикстурах в
десятки байт этого не поймал, CI зелёный по компиляции + «Deploy success» замаскировали —
регрессию поймал ТОЛЬКО eyes-on §8 на VPS (ssh-проверка живого прода).

Требования к таким оракулам:
- **Граница ресурса, не только корректность.** Для `open()`/загрузки — большой сегмент
  (десятки MiB+) + проверка ОГРАНИЧЕННОЙ памяти (счётчик аллокаций через global allocator)
  и/или времени. Оракул обязан ПАДАТЬ на наивной реализации (full-read) — анти-плацебо
  (пример: `crates/journal/tests/red_open_bounded.rs`).
- **Зелёные юнит-тесты + Deploy-success ≠ рабочий прод.** `.claude/rules/gates.md` §8
  eyes-on (контейнер пишет, heartbeat свежий, сегмент растёт, CPU/MEM в норме) —
  обязателен и решающий; healthcheck можно обмануть тихой деградацией.

## Фикстура «счастливого пути» — дефект оракула (закреплено 2026-07-14)

Два milestone'а подряд дефект прошёл ВСЕ зелёные гейты и был пойман только на PR-гейте
reviewer'ом — оба раза причина одна: **идеальная фикстура**.

- **M-07 (equity-curve):** оракул проверял кривую там, где на событии был РОВНО один филл;
  реализация ломалась на событии с 2+ филлами. Фикстура не содержала мульти-филлового события.
- **M-08 (эвикция книги, TD-016):** оракул «эвикция не режет живую книгу» использовал
  СИММЕТРИЧНЫЙ дифф (обновлялись top-N обеих сторон) → `diff_mid` совпадал с реальным mid и
  дефект не проявлялся. На АСИММЕТРИЧНОМ диффе (лучший bid не менялся — штатная ситуация)
  реализация стирала живые уровни, включая best bid, и порча уходила в журнал навсегда.

**Правило.** Оракул границы ресурса / инварианта данных ОБЯЗАН включать ДЕГРАДИРОВАННЫЙ вход,
а не только идеальный. Минимум, который architect обязан пройти по чек-листу перед коммитом
RED-набора:

1. **Асимметрия.** Вход, где обновляется/приходит только ОДНА сторона (или подмножество
   полей): односторонний дифф, событие без топовых уровней, филл только по одной ноге.
2. **Множественность.** Два и более элемента в одном такте (2 филла на событии, 2 интента,
   2 сегмента) — там, где наивная реализация считает «один».
3. **Отсутствие.** То, чего в сообщении НЕТ, — не сигнал к удалению/обнулению. Проверить, что
   реализация не додумывает за источник (дифф не говорит ничего о неупомянутых уровнях).
4. **Границы.** Пусто / один элемент / переполнение / усечение / переход через границу
   сегмента-окна-капа.
5. **Прод-масштаб** (для sacred I/O — уже обязателен, см. выше).

Если хотя бы один из пунктов не покрыт — оракул НЕ считается готовым, и milestone не уходит
dev-агенту. Симптом, который должен настораживать: тест зелёный с первого запуска против
кода, который ещё не написан «правильно» — значит фикстура не давит на инвариант.

## Оракул обязан мерить ТО, ЧТО ОБЕЩАЕТ (закреплено 2026-07-14, TD-021)

Третий класс дефекта — после «фикстуры счастливого пути» и «инварианта без проверки»:
**оракул измеряет не ту величину**, и все гейты честно зеленеют поверх реальной проблемы.

Инцидент: TD-016 («лик памяти recorder'а +6.5 MiB/час») был заведён по `docker stats`, который
включает **page cache файла журнала**. Recorder пишет ~30 MB/мин → «память» растёт при нулевом
лике. Реальный рост кучи (`RssAnon`) — +1 MiB/час. По этой метрике был написан RED-оракул, принят
контракт эвикции книги и **сделан фикс, рисковавший порчей первичных данных** — ради экономии
16 MB из 7.5 GiB.

**Правила:**
1. **Метрика, на которой заводится долг/инвариант, сама подлежит валидации.** Прежде чем писать
   оракул: «что именно считает эта цифра?» (`RssAnon` vs `memory.current`; `len()` vs байты;
   wall-clock vs event-time). Если не можешь назвать — оракула ещё нет.
2. **Оракул границы ресурса меряет ресурс, а не прокси.** Память — anon-куча; диск — байты
   сегментов; латентность — измеренные распределения, не «оценка».
3. **Различай РОСТ и СХОДИМОСТЬ.** Монотонный рост на коротком окне может быть выходом на
   плато (пример: книга бутстрапится REST-снапшотом top-5000 и постепенно узнаёт реальные
   дальние уровни из diff-потока). Оракул обязан отличать «растёт без предела» от «сходится к
   реальному размеру» — иначе мы «чиним» корректное поведение.
4. **Цена ошибки решает направление фикса.** Прежде чем ограничивать ресурс, спроси: что дороже —
   ресурс или данные? Память дёшева (7.5 GiB), боевые данные незаменимы. Фикс, экономящий дешёвое
   ценой риска для дорогого, — не фикс.
## Целостность гейта — 4 свойства (закреплено 2026-07-15, ~10 дефектов одной сессии)

За один milestone (M-08 + doc-гейт C-006) **десять** гейтов/оракулов оказались зелёными, пока
защищаемое свойство было сломано. Причина всякий раз — одна из четырёх: гейт проверял не то, не
той формой, не против того или не замечал молчания. Гейт/оракул НЕ считается готовым, пока не
удовлетворяет ВСЕМ четырём. Каждое свойство обязано быть предъявлено (прогоном, не рассуждением).

1. **Прогоняет ПРОД-ФОРМУ, а не суррогат.** Гейт обязан дёргать артефакт ровно так, как его
   дёргает прод — та же форма argv, тот же путь вызова. Гейт, проверенный не тем вызовом, каким
   его зовёт прод, не проверен.
   - `check_protected_artifacts` брал базу из `origin/main`, а CI на push даёт её из события ⇒
     гейт был зелёным ВСЕГДА (ложный гейт хуже отсутствующего).
   - D5a/D7 гоняли argv **cron-скрипта** (раздельная форма), а прод-сервис — compose `command:`
     (equals-форма) ⇒ пропустили TD-024. Фикс — D8: прогон РЕАЛЬНОЙ compose-формы через бинарь.

2. **Меряет СВОЙ инвариант, а не окружение/прокси.** Оракул обязан ассертить ровно ту величину,
   что называет, а не окружающий заменитель. Тест, чей исход зависит от хоста (диск, ядра,
   параллельность) — меряет окружение, это флак.
   - C5 мерил размер результата (`Vec` 60k событий), а не память РАСПАКОВКИ (TD-021-класс).
   - TD-023: глобальный аллокатор считал ВЕСЬ процесс, а нужна была память книги; порог 4 MiB —
     фикция устаревшей эпохи.
   - TD-025: тест зависел от свободного места ХОСТА, а не от корректности миграции.

3. **Падает против СЛОМАННОГО (анти-плацебо) И против несостоявшегося SETUP.** Гейт обязан
   краснеть (а) против дефекта, который стережёт — прогони его против пред-фиксной реализации;
   (б) если его СОБСТВЕННЫЙ setup не подготовил названное состояние. Проба, молча тестирующая не
   тот сценарий, — плацебо самой себя.
   - Вся сага doc-гейта P1–P17: сценарий с молча-провалившимся `git merge`/`commit`/`mv` рапортует
     PASS, доказывая ДРУГОЙ путь. Лечится setup-guard'ом на КАЖДЫЙ сценарий (доказать форму: есть
     merge-коммит / переименование видно как R / диапазон непуст / blob изменился).
   - D5-стаб глотал любые аргументы ⇒ **застабил ровно тот контракт argv, который и ломался**.
     Следствие-правило: **стаб не смеет подменять проверяемый контракт** — стаб уместен для
     обвязки (реакция на сбой), но саму проверяемую величину гейт гоняет по-настоящему.

4. **Наблюдает ОТСУТСТВИЕ, не только сбой.** Монитор, сигналящий «упало», но не «никогда не
   запускалось», слеп к тихому молчанию. И сбой, И молчание обязаны быть видимы.
   - `*.alert` ловил «прогон упал»; «cron не установлен / crond мёртв / ребут» — нет. Фикс — D9:
     позитивный heartbeat `*.last-success` + монитор по его СВЕЖЕСТИ.
   - Класс TD-011: тихая деградация под зелёным healthcheck'ом — то же отсутствие наблюдаемости.

Симптом, требующий стоп-проверки: гейт зелёный, но ты не можешь предъявить, ЧТО он покраснеет
против конкретного слома. Не можешь — гейт декоративен.
