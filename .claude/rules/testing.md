# Testing Rules — RED-first TDD

Источник: `docs/04-workflow.md` §2/§3, `docs/DESIGN.md` §4 (`RK-I-1..10`), §1 (`DET-I-1`),
`docs/03-integration-contract.md` §6 (`INTG-I-*`). Порядок: **Research → Plan → TEST (RED) →
Implement (GREEN) → Refactor → Review.** Шаг 3 не пропускается никогда.

Истории инцидентов, из которых выросли правила ниже, живут в `git log`, `TECH-DEBT.md` и
`research/{critiques,reviews,arbitration}/` — здесь только сами правила.

## Тест — это спецификация, не проверка постфактум

Тест пишется architect'ом ДО кода и определяет, ЧТО код обязан делать. Vague-задача даёт код,
который «выглядит правильно» и тонко ошибается. Конкретный тест не оставляет места для
галлюцинации:

```rust
#[test]
fn rk_i_1_no_order_reaches_venue_without_risk_approved() {
    let raw = Order::new(/* ... */);
    // let _ = venue.submit(raw);           // <- НЕ ДОЛЖНО КОМПИЛИРОВАТЬСЯ
    let approved = risk_gate.check(raw).expect("должно быть Approved");
    assert!(venue.submit(approved).is_ok());
}
```

**Мандат dev-агенту НИКОГДА не включает написание тестов на собственную реализацию** — даже вне
sacred-зон. Иначе тест описывает то, что получилось, а не то, что требовалось.

## Анти-плацебо — тест GREEN против заглушки = дефект

Тест обязан ПАДАТЬ, если реализация — no-op/заглушка/`Ok(())`. `assert!(gate.check(x).is_ok())`
проходит и при `check()`, всегда возвращающем `Ok`. Правильно — assert конкретного отказа на
конкретном невалидном входе (`RK-I-3`: неизвестный инструмент → `Reject`, не default-лимиты).

Симптом, требующий стоп-проверки: **оракул зелёный с первого запуска против кода, который ещё
не написан правильно** — значит фикстура не давит на инвариант.

## Sacred RED-оракулы

- **`RK-I-1..10`** (`DESIGN.md` §4) — риск-инварианты; `crates/risk/tests/`, `crates/killswitch/tests/`.
- **`DET-I-1`** — бит-идентичный replay журнала; P0 acceptance-ворота.
- **`INTG-I-1..7`** — границы A/B/C; тест подтверждает ОТСУТСТВИЕ альтернативного write-пути.
- **`CT-I-1..6`** — контрактный слой; grep-канарейка `EventKind` + roundtrip старых версий.

Dev их не трогает даже при рефакторинге вокруг. Тест кажется неверным → `!!! SCOPE VIOLATION
REQUEST !!!`, не самостоятельная правка.

## Каждая публичная функция — с тестом

- **Домен без I/O** (`journal`, `book`, `signals`, `alpha`, `portfolio`) — чистые
  детерминированные функции: без wall-clock/`rand()`/неупорядоченной итерации по `HashMap` в
  редьюсерах. Сигнал не имеет доступа к будущему.
- **Границы I/O** (`venue-*`, journal writer, `oms` submit) — интеграционные тесты с явными именами.
- **Детерминизм-тест обязателен для каждого сигнала**: одинаковый вход → одинаковый выход,
  **независимо от порядка вызова** (фикстура обязана варьировать порядок, иначе не проверяет).

**Покрытие:** 80%+ для `risk`, `killswitch`, `oms` (пре-trade path) и контрактных roundtrip'ов;
60%+ для остального.

**Прогон:** `cargo test -p <crate>` · `cargo test --workspace` (перед PR) ·
`cargo test -p risk -p killswitch` при любом касании `oms`/`venues`.

Python-тулинг `research/` (если появится) — `pytest research/ -v`: он ТОЛЬКО консюмер
контрактов (`docs/05-contract-layer.md` §5) и не пишет T1 в рантайм.

## Дегенерированный вход обязателен — фикстура «счастливого пути» есть дефект оракула

Оракул границы ресурса или инварианта данных ОБЯЗАН включать деградированный вход. Чек-лист
architect'а перед коммитом RED-набора; не покрыт хотя бы один пункт — набор не готов:

1. **Асимметрия.** Обновляется только ОДНА сторона / подмножество полей (односторонний дифф,
   филл по одной ноге). Симметричная фикстура прячет дефекты, где стороны расходятся.
2. **Множественность.** Два и более элемента в одном такте — и, отдельно, **несколько ЖИЗНЕЙ
   одной сущности** (цена рождается, отменяется и рождается снова): наивная реализация считает
   «один» и там, и там.
3. **Отсутствие.** Чего в сообщении НЕТ — не сигнал к удалению. Реализация не додумывает за источник.
4. **Границы.** Пусто / один элемент / переполнение / усечение / переход через границу окна.
   Фикстура не должна стоять РОВНО на границе диапазона: округление уводит её в соседний, и
   тест падает по неверной причине.
5. **Прод-масштаб** — для sacred I/O (см. ниже).
6. **Права доступа к носителю.** Фикстура повторяет режим монтирования прода, а не удобный
   для теста. Потребитель, у которого том `:ro`, не создаст ни файла, ни sidecar'а; запись
   упадёт с EROFS и, если её проглотили, механизм тихо исчезнет.
7. **Число одновременных потребителей.** Один курсор в фикстуре против N сессий на проде —
   разные задачи. Состояние, общее на каталог, при двух читателях даёт то же, что полное
   отсутствие механизма.

Пункты 6-7 добавлены 2026-08-06 по решению founder'а. Основание — M-57: обе дыры прошли
двух критиков, арбитра, тестера и гейт 11/11, потому что ВСЕ оракулы гоняли записываемый
каталог с одним курсором. Замер: `:ro` — 8003 события на тик вместо 3; две сессии — 8009.

## Форма прода снимается ЗАМЕРОМ, а не воображается

Для sacred-пути, работающего с прод-данными (журнал, recorder, retention, restore, venue), architect
ОБЯЗАН до коммита RED-набора снять форму прода замером и назвать её в спеке milestone'а:

```bash
ssh -i /home/nous/.ssh/hft_deploy -o IdentitiesOnly=yes root@167.233.192.131 \
  'ls -la /var/lib/docker/volumes/hft-platform_journal-data/_data | tail -5'
```

Фиксируется явно: **тип** носителя (сырой/сжатый — и какой АКТИВЕН), **размер** относительно
внутренних окон и буферов кода, **наличие/отсутствие** служебных файлов, **множественность**
(сколько сегментов участвует). Фикстура воспроизводит эту форму, а не ту, что проще собрать.

Оракул sacred I/O-пути включает прод-масштабный кейс и меряет ГРАНИЦУ РЕСУРСА (счётчик аллокаций,
время), а не только корректность: он обязан падать на наивной реализации (пример —
`crates/journal/tests/red_open_bounded.rs`). Зелёные юниты + «Deploy success» ≠ рабочий прод;
eyes-on по `gates.md` §8 обязателен и решающий.

## Оракул обязан мерить ТО, ЧТО ОБЕЩАЕТ

1. **Метрика, на которой заводится долг или инвариант, сама подлежит валидации.** Назови, что
   именно считает цифра (`RssAnon` vs `memory.current`; `len()` vs байты; wall-clock vs
   event-time; доля ЭПИЗОДОВ vs доля СУЩНОСТЕЙ, хоть раз попавших в состояние). Не можешь
   назвать — оракула ещё нет.
2. **Оракул границы ресурса меряет ресурс, а не прокси.** Память — anon-куча; диск — байты
   сегментов; латентность — измеренные распределения, не оценка.
3. **Различай РОСТ и СХОДИМОСТЬ.** Монотонный рост на коротком окне может быть выходом на плато.
4. **Различай ВЕЛИЧИНУ и ЕЁ НАСЫЩЕНИЕ.** Доля вида «сущность хотя бы раз за окно попала в
   состояние» растёт с длиной окна и плотностью наблюдений; сравнение двух таких величин
   сравнивает насыщение, а не предмет.
5. **Цена ошибки решает направление фикса.** Что дороже — ресурс или данные? Фикс, экономящий
   дешёвое ценой риска для дорогого, — не фикс.

## Целостность гейта — 4 свойства

Гейт/оракул не готов, пока не удовлетворяет ВСЕМ четырём; каждое предъявляется прогоном, не рассуждением.

1. **Прогоняет ПРОД-ФОРМУ, а не суррогат** — та же форма argv, тот же путь вызова, что у прода.
   Гейт, проверенный не тем вызовом, каким его зовёт прод, не проверен.
2. **Меряет СВОЙ инвариант, а не окружение.** Исход, зависящий от хоста (диск, ядра,
   параллельность), — флак. Resource-оракул на глобальном счётчике обязан быть
   single-threaded-по-замеру; конфаундинг-величину держать КОНСТАНТНОЙ, варьировать только измеряемую.
3. **Падает против СЛОМАННОГО и против несостоявшегося SETUP.** Setup-guard на КАЖДЫЙ сценарий:
   проба, молча тестирующая не тот сценарий, — плацебо самой себя. Стаб не смеет подменять
   проверяемый контракт.
4. **Наблюдает ОТСУТСТВИЕ, не только сбой.** Монитор, сигналящий «упало», но не «никогда не
   запускалось», слеп к молчанию. Лечится позитивным heartbeat'ом и проверкой его свежести.

Симптом: гейт зелёный, но ты не можешь предъявить, ЧТО он покраснеет против конкретного слома.

## RED сравнения ДВУХ источников обязан моделировать live-режим

Если оракул проверяет сходимость/расхождение двух источников (recon книги с биржей, две
реализации, локальный расчёт с эталоном), фикстура обязана моделировать то, чем источники
РЕАЛЬНО отличаются в проде, а не сравнивать источник с самим собой:

- **разные представления** (бакетированный vs сырой) — форму каждого сначала ИЗМЕРЬ;
- **разная глубина/охват** — проверить, что оракул не считает недостижимое расхождением;
- **разные моменты** — а если величина шумит между моментами, фикстура обязана быть
  ПОСЛЕДОВАТЕЛЬНОСТЬЮ моментов и отличать churn (знак гуляет) от персистентного сдвига.
  Синтетический zero-mean churn недостаточен: реальный skew несёт систематический bias;
- **анти-плацебо в ОБЕ стороны** — набор падает и против слишком строгой реализации (флудит на
  норме), и против слишком мягкой (пропускает порчу).

Симптом: RED зелёный с первого прогона, а фикстура строит оба источника из одного входа — это
тавтология, а не оракул сходимости.

## Мутационный контроль — обязателен, и вопросов ДВА

«Тесты не упали» ≠ «инвариант защищён». Процедура (минуты):

1. Найди в реализации строки, которые оракул обязан защищать.
2. Нейтрализуй их (закомментируй / замени на `true` / удали ветку).
3. Прогони оракул. Не упал → оракул ничего не пиннит; чини оракул, а не радуйся зелёному.
4. Верни код. Результат — в Done Block: «нейтрализация X → тест Y FAILED».

**Второй вопрос: что пришлось ослабить рядом.** Первый вопрос проверяет привязку к дефекту, но
не то, что фикс не куплен ценой соседнего инварианта. Обратная мутация: вернуть послабление и
убедиться, что его ловит отдельный оракул-сторож. Нет ответа — нужен такой сторож.

**Зависимый эталон мутация ловит плохо.** Оракул `X == Y` невалиден, если `Y` вычисляется через
`X` или делит с ним код на проверяемом свойстве. Эталон берётся из НЕЗАВИСИМОГО пути: полный
реплей, вторая реализация, записанная фикстура. Проверка: «сломай X так, чтобы Y сломался ТЕМ
ЖЕ образом, — покраснеет ли оракул?»

**Ассерт «изменилось» обязан называть, ОТ ЧЕГО.** `assert_ne!(after, before)` без явного эталона
рождает противоречивые тесты — вплоть до требования недетерминизма, прямо противоположного
`DET-I-1`. Называй эталон явно.

## Механизм несущего пути обязан иметь оракул точки входа

`test -f binary` и `grep name docker-compose.yml` — описания намерений, а не проверки: обе бывают
зелёными, когда бинарь не стартует ни при какой форме argv. Несущий путь = код, исполняемый
прод-процессом (recorder / gateway-serve / ops-cron / venue-ingest) вне тестов. RED-набор такого
milestone'а обязан содержать минимум один оракул, ИСПОЛНЯЮЩИЙ границу процесса тем вызовом,
каким её дёргает прод. Канарейка обязана:

1. **запустить вызывателя** (argv из `docker-compose.yml`; cron-обёртку через
   `HFT_CRON_PRINT_ARGV=1`) и проверить exit-код;
2. **проверить КОМПОЗИЦИЮ:** путь, куда пишет producer, совпадает с путём, откуда читает
   consumer — рассогласование двух строк даёт тихий no-op;
3. **дойти до доставки:** файл в репозитории при деплое, который его не устанавливает, инертен.

Формулировка «канарейка слабая, но честная» — красный флаг: проверь, не вакуумна ли она.
Проверка должна быть по ВЫЗОВУ (исполнением/поведением), а не по тексту: grep по имени ловит и
лог-строки.

## Спека правки существующего кода обязана содержать ЗАПРЕТНЫЙ СПИСОК

Пробел в спеке реализация заполняет по-своему — и имеет на это право. Спека, изменяющая
СУЩЕСТВУЮЩИЙ код, обязана содержать таблицу «Запрещено / Почему»: какие соседние инварианты
трогать нельзя, какие побочные эффекты недопустимы, какие сигнатуры и потоки данных менять
нельзя, где границы зоны. Иначе задачу не решить — исполнитель останавливается со `!!! SCOPE
VIOLATION REQUEST !!!`, а не расширяет область сам.

**Исправление по вердикту тоже требует оракула.** Правка, сделанная в ответ на находку гейта, —
такое же изменение поведения: без RED на саму находку следующий круг ловит её же в новой одежде.

## Что нарушение выглядит как

- Реализация закоммичена раньше или в одном коммите с первым RED-тестом.
- Тест дергает `RiskApproved` напрямую в обход приватного конструктора крейта `risk`.
- Тест на сигнал не проверяет детерминизм.
- `#[ignore]` / `#[should_panic]` без обоснования на sacred-тесте.
- Оракул зелёный, а мутация проверяемых строк его не роняет.
