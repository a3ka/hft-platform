# Гейты — plan-time, RED-first, PR-time, риск, анти-оверфит

Источник: `docs/04-workflow.md` §3 + `docs/DESIGN.md` §4/§6/§7 + `docs/05-contract-layer.md`
§4 + `docs/02-quant-desk.md` §4. Каждый milestone проходит через применимые гейты ниже
ДО close-out. Пропуск гейта = находка reviewer'а, откат close-out.

## 1. Plan-time (critic) — триггеры

Architect коммитит milestone + RED-тесты + verify-скрипт + T-контракты **ДО** dev.
Critic обязателен, если сработал ЛЮБОЙ триггер:

1. Milestone трогает `crates/contracts/**` (T1) — всегда contract-RFC + critic.
2. Milestone трогает `crates/risk/**`, `crates/killswitch/**`, `crates/oms/**`,
   `crates/venue-*/**` (safety/деньги) — RISK-BLOCK, см. §5.
3. Оценка ≥5 атомарных коммитов.
4. Новый крейт вводится.
5. Ломающее изменение формы T1 (см. `docs/05-contract-layer.md` §4).

Низкорисковые milestone'ы (один сигнал в `crates/signals/`, отчёт) — без critic'а;
reviewer — бэкстоп на PR-time (гейт 4 ниже всё равно UNCONDITIONAL).

**Документы — НЕ «низкорисковая docs-правка».** Маршрутизация правок документации целиком
делегирована **§9 (doc-гейт)**: класс A (архитектура/правила/милестоуны/роадмап) — critic
обязателен, класс B (бухгалтерия) — без critic'а. Формулировка «docs-правка → без critic»
здесь УБРАНА намеренно: она позволяла прочитать правку DESIGN/FA/правил как низкорисковую
(находка critic C-006 M1).

## 2. RED-first (TDD) — обязательно везде, без исключений

- Architect пишет ПАДАЮЩИЙ тест ПЕРВЫМ. Тест — спецификация, не проверка постфактум.
- Implementation-код без предшествующего RED-теста не пишется НИКЕМ.
- **Анти-плацебо (урок hft-core-rs):** тест, который проходит GREEN против заглушки/
  no-op-стаба, — дефект теста, не готовая фича. Пример: тест `RiskApproved` не должен
  проходить, если risk-gate всегда возвращает `Approve` независимо от входа.
- Каждая публичная функция — с тестом. Риск-инварианты (`RK-I-1..10`,
  `docs/DESIGN.md` §4) и `DET-I-1` (бит-идентичный replay, `docs/DESIGN.md` §1) —
  sacred RED-оракулы: они обязаны падать на заглушке ДО реализации.
- Прогон: `cargo test -p <crate>` (или `cargo test --workspace` для сквозных).

## 3. Acceptance-script-as-real-gate

Каждый milestone — `scripts/verify_M-NN.sh`:

- `set -euo pipefail` ИЛИ явный агрегатор с FAIL-счётчиком + `exit 1` при FAIL>0.
- **Никакого** `cmd && echo PASS || echo FAIL` (маскирует провал).
- Минимум 1 проверка на задачу из §Tasks milestone'а.
- Финальная строка `VERDICT: PASS`/`VERDICT: FAIL`; exit-код соответствует.
- Явный список исключений (T2/T3 типы вне зоны проверки) с комментарием-обоснованием.

Dev перед "готово" запускает `bash scripts/verify_M-NN.sh; echo "exit=$?"` — сырой вывод
идёт в Done Block (`.claude/rules/commit-discipline.md`).

## 4. PR-time (reviewer) — UNCONDITIONAL

Reviewer обязателен для ЛЮБОГО milestone'а, тронувшего код/контракты/риск/докс сверх
tech-debt правок. Блоки:

- **Scope** — диф соответствует `Allowed paths` milestone'а (`.claude/rules/scope-guard.md`).
- **Done Block** — сырой stdout, не пересказ (`.claude/rules/commit-discipline.md`).
- **Contract Block-C** (аналог EINHARD Block B5) — правки `crates/contracts/**` вне
  contract-RFC → авто-REJECT (`docs/05-contract-layer.md` §4).
- **Риск-инварианты** — если milestone трогал `risk`/`killswitch`/`oms`/`venue-*`,
  reviewer проверяет наличие GREEN RED-suite `RK-I-1..10` + `INTG-I-*` в Done Block.

Reviewer не пропускается НИКОГДА для substantive-изменений. После APPROVED reviewer
обновляет `PROJECT-STATE.md` + `TECH-DEBT.md` и делает push (аналог EINHARD F-032 J5).

**Граница reviewer↔architect (закреплено 2026-07-11, инцидент TD-011):** reviewer ОПИСЫВАЕТ
дефект (что/где/симптом/воспроизведение), но НЕ проектирует фикс. Дизайн решения
(напр. tail-scan/seek) + RED-оракул на регресс — зона architect (RED-first). Reviewer
находит проблему → architect проектирует защиту → dev реализует.

## 5. RISK-BLOCK — асимметричная цена ошибки

Любой milestone, трогающий `crates/risk/**`, `crates/killswitch/**`, `crates/oms/**`,
`crates/venue-*/**`, ИЛИ контракты (`crates/contracts/**`) → **обязательный risk-critic**
(сильная модель, не экономим — `docs/02-quant-desk.md` §1, `docs/DESIGN.md` §7). Причина:
ложноположительный risk-gate или пропуск в oms стоит депозита — асимметрия хуже, чем
лишний цикл ревью.

**MD-only carve-out (закреплено 2026-07-11, M-06):** venue-* адаптер, читающий ТОЛЬКО
рыночные данные (WS/REST → нормализация → `MdEvent`, БЕЗ order-egress — никаких
submit/cancel/подписи торговых действий), НЕ требует risk-critic — достаточно reviewer.
risk-critic ОБЯЗАТЕЛЕН, как только venue-* код трогает ORDER-путь (submit/cancel/auth
торговли). Причина: асимметричная цена ошибки живёт на пути к деньгам (ордера), а не на
read-only MD-приёмнике. Reviewer в Block-scope подтверждает, что диф действительно MD-only
(нет order-egress) — иначе RISK-BLOCK применяется полностью.

- risk-critic пишет вердикт в `research/critiques/C-NNN.md` (KILL | CONCERNS | PASS).
- KILL/CONCERNS блокирует merge до устранения находок или явного founder-override
  с именованным обоснованием.
- Risk-инвариантный RED-suite (`RK-I-1..10`, `INTG-I-*`, `CT-I-*`) обязан быть GREEN
  (изначально падал на заглушках — анти-плацебо §2) до любого merge в
  `risk`/`oms`/`venues`/`contracts`.
- Read-only характер risk-critic: не предлагает стратегий (независимость от
  signal-engineer), не пишет код.

## 6. Анти-оверфит гейт — backtest-отчёты (`research/reports/R-NNN`)

Отчёт невалиден без:

1. **Пре-регистрация** критериев фальсификации ДО касания test-данных
   (карточка `research/hypotheses/H-YYYYMMDD-<slug>.md`, `docs/02-quant-desk.md` §3.1).
2. **Time-split**: train/validation/test; test-период трогается ОДИН раз на финальной
   валидации.
3. **Trials-ledger** (`research/trials-ledger.json`, append-only, `INTG-I-6`) — каждая
   ячейка грида инкрементирует счётчик; deflated Sharpe считается от него.
   **Эпохи ledger'а НЕСОПОСТАВИМЫ (TD-015, закреплено 2026-07-13 после M-07).** Ledger
   append-only — записи не удаляются, но и не смешиваются: в метрики/deflated-Sharpe
   берутся ТОЛЬКО записи, сделанные кодом решений `>= 5141fd9` (merge M-07 «strategy
   brain»). **Причина исключения пре-M-07 записей — НЕ «завышенный Sharpe», а то, что они
   меряли ЛОГИКУ, КОТОРОЙ БОЛЬШЕ НЕ СУЩЕСТВУЕТ** (ad-hoc harness: `qty=1.0`, taker-выход по
   horizon; удалён в M-07). Уточнено reviewer'ом по факту: 4 записи, `code_hash f7f4761`,
   Sharpe −1.73..−2.21. Отдельно и по ДРУГОЙ причине невалидны записи из окна equity-бага
   (`37753a6..5141fd9`): фантомные точки кривой занижали σ → **завышенный** Sharpe. В
   репо-ledger'е таких записей НЕТ (проверено reviewer'ом фактически), но всплывшие из
   локальных прогонов отбрасываются. Отчёт обязан НАЗЫВАТЬ свою эпоху (`code_hash` + диапазон записей);
   risk-critic проверяет это как пункт 0 чек-листа ниже — смешение эпох = KILL.
4. **Чек-лист risk-critic**: **(0) эпоха ledger'а** (TD-015: N и V[SR] семейства посчитаны
   ТОЛЬКО по записям кода `>= 5141fd9`; пре-M-07 и bug-window записи исключены — иначе KILL);
   lookahead/leakage, survivorship, честные издержки+латентность
   (чувствительность ×1.5 издержек, ×2 латентности), режимная зависимость, реальная
   ёмкость, корреляция с уже-live сигналами.
5. **Paper-карантин обязателен** — ни один сигнал не идёт train→live напрямую
   (`docs/02-quant-desk.md` §4.5).
6. **Двойная подпись founder'а** (paper, live) через очередь решений — граница C
   (`docs/03-integration-contract.md` §3, `INTG-I-3`).

## 7. Путь к деньгам — единственная founder-подпись

Промоушен `candidate→paper→live` и любое изменение весов/лимитов проходит ТОЛЬКО через
подписанный `Ctl(ParamChange)` (`RK-I-10`/`INTG-I-3`) или `decisions/D-NNN.md`
(`INTG-I-2`). Ни один агент — включая architect — не двигает деньги и не меняет
live-параметры напрямую. Байпас-поверхности не существует (`RK-I-2`) — это не
конфигурируемая опция, а архитектурный факт, проверяемый тестом.

## 8. Post-merge деплой-гейт — прод живёт на ДРУГОМ сервере (добавлено 2026-07-11)

Разработка идёт локально (`/home/nous/hft-platform`), но проект РАБОТАЕТ на VPS
(Hetzner, доступ и схема — `docs/SESSION-HANDOFF.md` §2): push в `main` триггерит
GitHub Actions (`ci.yml` + `deploy.yml` → build на VPS → healthcheck → rollback).
Push — НЕ конец цикла. Агент, сделавший push (reviewer в конце milestone-цикла; architect —
ТОЛЬКО для класса B по §9: статус-колонки, close-out-пруфы, немантические правки), ОБЯЗАН до
закрытия работы:

1. **Дождаться CI + Deploy** до терминального статуса: `gh run watch <id> --exit-status`
   (или `gh run list` до `completed success` обоих). Красный CI/Deploy → немедленный
   фикс или revert; milestone НЕ закрывается поверх красного прода.
2. **Проверить прод на VPS** (минимум):
   `ssh -i /home/nous/.ssh/hft_deploy -o IdentitiesOnly=yes root@167.233.192.131 \
      'docker ps --format "{{.Names}} {{.Status}}"; cat /var/lib/docker/volumes/hft-platform_journal-data/_data/recorder.heartbeat'`
   Ожидание: контейнер(ы) `(healthy)`, heartbeat свежий (мс epoch ≈ сейчас), журнал
   растёт. Если деплой менял поведение данных (парсеры/форматы) — sanity свежих
   событий по мере возможности.
3. **Пруф в close-out**: сырые строки `gh run list` (success) + вывод ssh-проверки —
   в Done Block / §C close-out отчёта. «Запушил и ушёл» = нарушение гейта.

Rollback в `deploy.yml` — страховка, не оправдание: он ловит падение healthcheck,
но не тихую деградацию (контейнер жив, данные испорчены). Глаза обязательны.

### Push-scope дисциплина (инцидент 2026-07-11: чужие RED-коммиты уехали с чужим push)

Основной чекаут ОБЩИЙ для сессий. Перед КАЖДЫМ `git push` — обязательная проверка:
`git log origin/main..HEAD --format='%h %s'` — в списке ТОЛЬКО твои коммиты этой
задачи. Чужие/незнакомые коммиты (другая сессия закоммитила локально и намеренно
НЕ пушила) → СТОП, не пушь, согласуй с founder'ом.

### RED-оракулы до реализации НЕ живут на main (main всегда зелёный)

Compile-RED/раннинг-RED тесты до реализации ломают CI. Два санкционированных пути:
(а) держать RED-коммиты локально до GREEN (паттерн M-04); (б) feat-ветка:
architect пушит `feat/M-NN`, dev-агенты бутстрапятся `pi-<role> --branch feat/M-NN`,
reviewer мержит в main уже GREEN. Прямой push RED-состояния в main = нарушение
этого гейта (кроме явного founder-override).

**Intra-chain push на feat-ветку (закреплено 2026-07-12, инцидент TD-014 chain-break):**
в цепочке на общей feat-ветке (architect→venue/engine-dev→...→reviewer) КАЖДЫЙ dev в
цепочке ПУШИТ свой GREEN-коммит на shared `feat/M-NN` (ff), чтобы следующий агент
забутстрапился на актуальном состоянии. Правило «push — только reviewer после APPROVED»
относится к **main** (merge `feat→main` + §8 деплой-гейт), НЕ к intra-chain push на feat.
Мандат dev-агенту должен явно РАЗРЕШАТЬ push на feat-ветку (иначе коммит виснет в
worktree-ветке, цепочка рвётся — TD-014). Push-scope (`git log origin/feat/M-NN..HEAD` =
только твои коммиты) обязателен по-прежнему.

## 9. DOC-ГЕЙТ — архитектурные и плановые документы (добавлено 2026-07-14)

**Проблема, которую закрываем.** Гейты §1-§8 требуют critic/reviewer для КОДА, а
архитектурные документы architect до сих пор пушил в `main` сам. Это асимметрия:
**документ — источник, из которого агенты исполняют**. Ошибка в спеке не падает в CI —
она тиражируется в код молча, и ловится (если ловится) через два milestone'а. Тот же класс,
что «зелёный оракул против дефектной реализации»: неверная спека = неверный оракул = неверный
код, только на этаж выше.

### Класс A — АРХИТЕКТУРНЫЕ (гейт ОБЯЗАТЕЛЕН)

Правки, меняющие ЧТО мы строим, КАК мы это гейтим или В КАКОМ ПОРЯДКЕ:

- `docs/DESIGN.md` — §-структура, инварианты, **роадмап/фазы**;
- `docs/0N-*.md` (движок, квант-деск, шов, контрактный слой, workflow);
- `docs/fa/*.md` — Functional Architecture любого модуля (**новый FA = всегда класс A**);
- `docs/rfc/*` — contract-RFC (уже покрыт §1.1, здесь только подтверждается);
- `milestones/*.md` — **новый milestone** и любая правка Objective / Allowed paths /
  §Tasks / Acceptance (статус-колонки — класс B);
- `milestones/BACKLOG.md` — очередь и приоритеты;
- `.claude/rules/*`, `.claude/agents/*` — правила процесса и зоны ролей.

**Процедура (та же дисциплина, что для кода):**
1. architect коммитит документ со статусом `PROPOSED` на ветку `feat/<тема>` или
   `docs/<тема>` — **не в `main`**;
2. **critic** — plan-time аудит: внутренняя непротиворечивость, конфликт с DESIGN/FA/правилами,
   отсутствие ложных гарантий («инвариант», который ничем не проверяется), выполнимость
   acceptance-ворот, цена ошибки vs приоритет. Вердикт в `research/critiques/C-NNN.md`
   (коммитится, `branch-hygiene.md`);
3. **reviewer** — PR-гейт: scope (architect не залез в чужую зону), cross-references не
   сломаны, TECH-DEBT/PROJECT-STATE согласованы, статус `PROPOSED → ACTIVE`; **merge и push
   делает reviewer**;
4. **founder ★** — обязателен, если правка меняет ФАЗЫ/ПРИОРИТЕТЫ (роадмап, BACKLOG-очередь,
   границы A/B/C, лимиты): это решения, а не описания.

**risk-critic** дополнительно обязателен, если документ трогает safety-путь: `docs/fa/risk.md`,
`fa/killswitch.md`, `fa/oms.md`, RK-I-*/INTG-I-*, анти-оверфит гейт (§6).

### Класс B — БУХГАЛТЕРИЯ (гейт не нужен, self-push разрешён)

**Только МЕХАНИЧЕСКИ НЕСЕМАНТИЧЕСКИЕ правки** (уточнено по C-006 M2 — прежняя формулировка
«опечатки/битые ссылки» была слишком широка: «опечатка» в пути, команде, пороге, имени роли
или ID инварианта меняет поведение следующего агента):

- статус-колонки §Tasks (`⏳ → 🚧 → ✅`);
- close-out отчёты и добавление ПРУФОВ (сырые логи §8) в уже принятый документ;
- `PROJECT-STATE.md` / `TECH-DEBT.md` (reviewer-owned);
- форматирование, орфография **в прозе**, где не меняются: команда, путь, имя файла/роли,
  числовой порог, ID инварианта (`RK-I-*`, `OPS-I-*`, …), текст задачи/acceptance,
  cross-reference (кто источник правды).

**Класс A, даже если правка в одну строку:** любое изменение команды, пути, порога, имени роли,
ID инварианта, текста §Tasks/Acceptance или перенацеливание cross-reference на другой источник.

**Тест на класс:** «изменит ли этот текст то, что сделает следующий агент?» Да → класс A.
Сомневаешься — класс A (fail-closed: лишний прогон критика дешевле неверной спеки).

### Петля самоправки (C-006 M3)

Doc-гейт применяется и к правкам самого doc-гейта. Чтобы это не порождало бесконечную
вложенность:

- **Правки, сделанные В ОТВЕТ на REJECT doc-гейта, остаются В ТОМ ЖЕ цикле гейта** на той же
  `PROPOSED`-ветке: они требуют RE-critic + reviewer, а НЕ нового вложенного гейта.
- Цикл закрывается, когда critic снимает REJECT и reviewer мержит (`PROPOSED → ACTIVE`).
- **Аварийный обход:** founder может явным решением (записанным в коммит) влить процессную
  правку, чинящую СЛОМАННЫЙ ПРОД или заблокированный пайплайн (пример: TD-018, deploy-гейт
  не мог пропустить деплой НИКОГДА), с обязательным ретро-аудитом critic'ом после.

### Механический барьер против удаления артефактов гейта (C-006 rev2)

Артефакты, по которым исполняют и которыми аудируют, **нельзя потерять молча**:
`research/critiques/*.md` (вердикты critic/risk-critic), `milestones/*.md` (спеки, по которым
работают dev-агенты), `docs/rfc/*` (T1-governance).

Повод: коммит reviewer'а `git commit -am` в общем чекауте **снёс вердикт C-006** (198 строк).
Правило в `branch-hygiene.md` уже было — его нарушили. **Правило, которое можно нарушить молча,
правилом не является.**

- CI-job **`protected-artifacts`** (`scripts/check_protected_artifacts.sh`) валит сборку.
- **База сравнения берётся ИЗ СОБЫТИЯ** (`github.event.before` на push, `pull_request.base.sha`
  на PR) — не из `origin/main`. Первая редакция звала барьер как `check_protected_artifacts.sh
  origin/main` и была **ЛОЖНЫМ ГЕЙТОМ**: на push-событии `actions/checkout` ставит `origin/main`
  на только что запушенный коммит ⇒ `merge-base == HEAD` ⇒ диапазон пуст ⇒ «OK» ВСЕГДА (PR в этом
  репо не используются, все прогоны — event=push). Коммит, сносящий вердикт критика, проходил CI
  зелёным — то есть барьер не поймал бы ровно тот инцидент, ради которого писался (блокер B1,
  найден reviewer'ом на PR-гейте C-006). **Урок — тот же, что у оракулов: гейт, проверенный не тем
  вызовом, каким его дёргает прод, — не проверен.**
- **Fail-closed по базе.** Пустое событие, zero-SHA (создание ветки / force-push), база вне
  истории, база не предок HEAD (история переписана) → **FAIL, а не пропуск**. «Базы нет» не значит
  «проверять нечего» — значит «целостность недоказуема».
- **Артефакт на HEAD = обычный НЕПУСТОЙ ФАЙЛ** (закрыто по rev8 критика). `git cat-file -e` говорит
  «объект есть» и для ДЕРЕВА, и для СИМЛИНКА: на месте вердикта создавался каталог `C-006.md/` или
  симлинк в `/dev/null` — артефакт уничтожен, барьер молчал. Проверяется режим объекта
  (`100644`/`100755`; `040000`/`120000`/`160000` → FAIL) и ненулевой размер: усечение в 0 байт — то же
  удаление, только вежливое.
- **Барьер сам под пробой** — `scripts/tests/red_protected_artifacts.sh` (17 сценариев, зовёт
  барьер ТОЙ ЖЕ проводкой, что CI; отдельный шаг того же job'а). Каждая редакция барьера падала
  против пробы СЛЕДУЮЩЕГО витка — поэтому анти-плацебо здесь не формальность: проба обязана
  краснеть против предыдущей версии барьера, иначе она ничего не доказывает.
- **Чего барьер НЕ ловит (честная граница):** force-push, переписывающий историю `main`, обходит
  ЛЮБОЙ in-branch скрипт — барьер это ДЕТЕКТИРУЕТ (fail-closed), но не предотвращает. Полное
  закрытие требует branch protection «no force-push» на `main` — настройка GitHub, **зона founder**.
  Локальный вызов (не из CI): `bash scripts/check_protected_artifacts.sh $(git merge-base origin/main HEAD)`.
- **Критерий — РЕЗУЛЬТАТ, а не способ** (переписано после трёх итераций критика). Прежние версии
  гонялись за способом исчезновения (`D` в коммите → `R` в коммите → `D` в мерже), и каждый раз
  находился новый: `git mv` внутри merge-коммита (статус `R`, не `D`); `merge -s ours`,
  выбрасывающий файл, живший только в side-ветке (относительно первого родителя удаления нет
  вовсе). Латать частные случаи бесполезно — инвариант формулируется от результата:

  > **Защищённый артефакт, который СУЩЕСТВОВАЛ (в базе или был добавлен в ветке), обязан
  > существовать на HEAD** — либо под тем же именем, либо переехав в ДРУГОЙ защищённый путь,
  > либо его удалил коммит с явным `ALLOW-ARTIFACT-DELETE:` в СВОЁМ теле.

  Любой способ исчезновения (delete, rename-out, add→delete, evil merge, `-s ours`, mv в мерже)
  ловится автоматически: все они дают один результат — файла нет на HEAD.
- **«Существовал» считается по СОСТОЯНИЮ, а не по диффу** (закрыто по rev7 критика). Множество
  защищённых путей собирается через `git ls-tree` по дереву КАЖДОГО коммита диапазона (+ база),
  а не через `git log --diff-filter=AR`: **`git log` не показывает диффы merge-коммитов**, поэтому
  артефакт, рождённый ПРЯМО В ТЕЛЕ мержа, был для барьера невидим — и его последующее удаление
  проходило с exit=0. `ls-tree` смотрит на состояние и слеп к способу по построению.
- Легитимны без override: цепочка переименований внутри защиты (`docs/contract-rfc/` → `docs/rfc/`
  и дальше); удаление, восстановленное позже (артефакт есть на HEAD); честный `merge origin/main`.
- Канонический путь RFC — **`docs/rfc/`**; `docs/contract-rfc/` защищён как исторический.
- Проверено на 9 сценариях: `git mv` в merge → FAIL; `merge -s ours` (side-only вердикт) → FAIL;
  evil merge (`D`) → FAIL; add→delete → FAIL; rename-out → FAIL; override в другом коммите → FAIL;
  override в том же коммите → PASS; цепочка protected→protected → PASS; честный merge → PASS.
  Время прогона: ~40 мс (на +120 коммитов — <1 с).

## 10. Изоляция ролей в общем чекауте (добавлено 2026-07-13)

Общий рабочий каталог + `git checkout` разными ролями = потерянная работа и потерянные
артефакты гейтов. Правила — `.claude/rules/branch-hygiene.md` (worktree на роль; вердикт
критика КОММИТИТСЯ на ветку milestone'а, а не остаётся untracked-файлом).
