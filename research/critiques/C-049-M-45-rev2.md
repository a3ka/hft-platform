## 1. Q1 — REJECT НЕ закрыт: T5 проверяет не то дерево вызовов

Ответ на прямой вопрос задания («может ли dev реализовать `l2delta_emission_for`
корректно, но обработчик оставить на своём отдельном сравнении символов — ловит ли это
T5?»): **нет, не ловит.** Конкретная, воспроизводимая в одну строку дыра.

### 1.1 Что именно проверяет T5 (rev2)

Из `scripts/verify_M-45.sh` (строки 97-115):

1. Первый грэп: количество вызовов `l2delta_event(` в `src/` (исключая объявление
   функции и комментарии) обязано быть РОВНО 1, и этот единственный вызов обязан
   текстуально лежать внутри тела `fn l2delta_emission_for`.
2. Второй грэп: в `src/` не должно быть массива-литерала строк вида
   `&[ "XXXUSDT" , "YYYUSDT" ]` (тикер-подобные строки внутри `&[...]`).

Оба грэпа смотрят на **`l2delta_event`** (низкоуровневый транслятор diff→событие) и на
**форму хардкода конкретно как slice-литерал**. Ни один из них не проверяет:
(а) вызывается ли сам `l2delta_emission_for(` из реального обработчика
(`handle_text_message`/эквивалент), (б) чем конкретно гейтится ЭТОТ вызов, (в) откуда
берётся аргумент `symbols`, переданный в `l2delta_emission_for` на реальном call site.

### 1.2 Три независимых обхода, каждый проходит `verify_M-45.sh` целиком зелёным

Все три сохраняют `l2delta_emission_for` корректно реализованной (O-7 проходит, T3/T4
проходят — они дёргают чистые функции напрямую) и делают ровно один вызов
`l2delta_event(` внутри неё (T5-грэп-1 проходит), не оставляя slice-литерала с тикерами
(T5-грэп-2 проходит) — но обработчик либо не зовёт `l2delta_emission_for` с реальным
env-конфигом, либо зовёт её за хардкод-гейтом:

**(A) Голый литерал-гейт перед вызовом** (наиболее вероятная ленивая правка, не нужно
даже трогать структуру функции):
```rust
} else if stream.contains("@depth") {
    if let Some((symbol, diff)) = parse_depth_diff(stream, data) {
        if symbol == "BTCUSDT" {                       // ← не &[...], T5-грэп-2 не видит
            if let Some(event) = l2delta_emission_for(stream, data, &configured_symbols) {
                if tx.send(event).await.is_err() { return false; }
            }
        }
        let state = states.entry(symbol.clone()).or_insert_with(SymbolState::new);
        handle_diff(state, &symbol, diff, client, pending_snapshots);
    }
}
```
`l2delta_event(` встречается ровно 1 раз, внутри `l2delta_emission_for` — T5-грэп-1
PASS. Нет `&["BTCUSDT"]` — T5-грэп-2 PASS. Раскатка на ETHUSDT после подписи founder'а
молча не работает НИКОГДА (внешний гейт душит вызов раньше, чем `symbols` вообще
учитывается) — тот же класс дефекта, что в C-048 §1, только гейт передвинут с
`l2delta_event` на `l2delta_emission_for`.

**(B) Хардкод аргумента `symbols` инлайн-литералом на самом call site**, без всякого
гейта:
```rust
if let Some(event) = l2delta_emission_for(stream, data, &vec!["BTCUSDT".to_string()]) {
```
Не `&[...]` из строковых литералов (это `vec![...]` с `.to_string()`) — T5-грэп-2 его не
видит. `l2delta_event(` — единственный вызов, внутри `l2delta_emission_for` — T5-грэп-1
PASS. Это даже НЕ адверсариальный обход, а правдоподобная честная ошибка dev'а: забыл
прокинуть результат `parse_capture_symbols(env::var(...))` в аргумент и оставил
плейсхолдер из разработки/дебага.

**(C) `match`/`HashSet`/`.eq_ignore_ascii_case` вместо slice** — та же логика: T5-грэп-2
матчит только буквальный синтаксис `&[ "…" , … ]`; любая другая форма хардкода (match-arm,
`HashSet::from([...])` без `&`, `if !matches!(symbol.as_str(), "BTCUSDT")`) проходит
незамеченной.

Во всех трёх случаях `verify_M-45.sh` печатает `VERDICT: PASS`, §8 eyes-on зелёный
(дефолт не меняется байт-в-байт), и дефект обнаружится строго в момент, когда founder
подпишет состав, а оператор выставит `L2DELTA_CAPTURE_SYMBOLS=ETHUSDT` и перезапустит —
то есть **на том же самом позднем рубеже**, который был центральной претензией C-048.
Формулировка задачи #3 в milestone-файле («обработчик ДЕЛЕГИРУЕТ ей, своего сравнения
символов не имеет») — верная цель, но её не проверяет ни один текущий оракул.

### 1.3 Корневая причина

`l2delta_emission_for` — правильный контракт (единая чистая функция решения), но
дисциплина проверки контракта («вызвана ли она реально, и реально ли её единственный
аргумент `symbols` происходит из env, а не из хардкода на call site») переложена ЦЕЛИКОМ
на текстовые грэпы против низкоуровневого `l2delta_event` и против ОДНОЙ конкретной
синтаксической формы хардкода. Это структурно то же самое, что провалившийся T5 из
C-048 (грэп по имени константы) — просто грэп нацелен на другую строку кода. Ни O-7, ни
любой другой оракул не вызывает `handle_text_message` (реальную точку входа) ни разу —
все семь+пять новых тестов зовут `l2delta_emission_for` напрямую, в обход обработчика,
поэтому реальная проводка (или её хардкод-гейт) в принципе не наблюдаема ни одним
исполняемым тестом, только хрупким грэпом с узким синтаксическим окном.

**Что нужно (architect, до диспетчеризации venue-dev):** либо (1) сделать
`handle_text_message` (или его синхронное решающее ядро) достижимым для интеграционного
теста — `pub(crate)`/тестовый хук — и написать оракул, гоняющий РЕАЛЬНОЕ синтетическое
WS-сообщение через РЕАЛЬНЫЙ обработчик с внедрённым env/списком символов, проверяя, что
именно ушло в `tx`; текстовый грэп такую проводку доказать не может в принципе (только
сужать пространство конкретных обходов, что и произошло дважды подряд). Либо (2), если
architect считает рефакторинг обработчика непропорциональным, минимум — расширить
T5 так, чтобы он матчил call site `l2delta_emission_for(` внутри `handle_text_message`
(или где бы он ни был) И проверял, что аргумент `symbols` — это именованная переменная,
присвоенная РЕЗУЛЬТАТОМ вызова `parse_capture_symbols(` (не литерал/`vec!`/inline-выражение),
И что этот вызов не обёрнут во внешний `if`/`match` по символу. Вариант (2) — латание
дыр той же природы, что уже провалилось; вариант (1) закрывает класс дефекта, а не
конкретный инстанс.

## 2. Q2 — контракт реализуем, не переусложнён

`l2delta_emission_for(stream: &str, data: &serde_json::Value, symbols: &[String]) ->
Option<EventKind>` — чистая синхронная функция; `handle_text_message` уже держит
`stream: &str` и `data: &serde_json::Value` локальными переменными в момент диспетчеризации
(строки 223-236), так что делегирование — естественная правка на месте текущего
`if L2DELTA_CAPTURE_SYMBOLS.contains(...)`, не требует `async`/`reqwest`/`FuturesUnordered`
внутри контракта. Не вижу риска, что dev начнёт «чинить тест» из-за неудобной сигнатуры —
контракт минимален и реализуем буквально на месте старой строки. Замечание §1 не про
сложность контракта, а про то, что его соблюдение обработчиком не верифицируется.

## 4. Q4 — фикстура wire-сообщения совпадает с реальным парсером

Сверено `depth_data()` (O-7, venue-binance) с `parse_depth_diff`
(`crates/venue-binance/src/lib.rs:300-323`):

| Поле фикстуры | Тип в фикстуре | Что читает `parse_depth_diff` | Совпадает |
|---|---|---|---|
| `stream` | `"{sym}@depth@100ms"` | `stream.contains("@depth")` (диспетчер) + fallback-символ через `stream.split('@')` | да |
| `data.s` | строка (upper) | `data.get("s").and_then(as_str)` | да |
| `data.U` | число | `data.get("U")?.as_u64()` | да |
| `data.u` | число | `data.get("u")?.as_u64()` | да |
| `data.b`/`data.a` | `[["цена","размер"], …]`, строки | `parse_diff_levels` — `as_array` → `as_str().parse()` на цену/размер | да |
| `data.E` | опущено в malformed-кейсах | `data.get("E")...unwrap_or(0)` — необязательное | да |

Фикстура — той же формы, что реальный прод-парсер; RED, если случится, будет по
существу (отсутствие функции), не по ложному setup-провалу (`det_22`-класс отсутствует).
Подтверждено и по `venue-binance-futures` — `L2DELTA_CAPTURE_SYMBOLS`/`l2delta_event`
