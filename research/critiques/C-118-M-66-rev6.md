## BLOCKER B-1 — the mandatory battery is red and tests a stale duplicate, not the repaired barrier

`scripts/tests/red_review_fa.sh:992-993` in `emit_ref_barrier` still judges every changed
`crates/**` path. The production barrier's new applicability rule is at
`scripts/check_review_fa.sh:73-85`: test-only changes are explicitly skipped. `run_battery`
then executes that stale generated reference instead of the committed barrier
(`scripts/tests/red_review_fa.sh:1124-1141`). Consequently the legitimate new scenario
`B1TESTSONLY` fails the battery reference, and the required T4 battery invocation at
`scripts/verify_M-66.sh:238` makes acceptance fail.

This is not an advisory discrepancy: the committed command exits 1 with `BATTERY: FAIL (1 из
17)`. The corrected B-1 rule does pass against real history: PR #15's test-only range and the
M-65 test-only range both skip, while a `src/` range still fails. The failure is the stale
oracle that was meant to certify the repair.

**Condition to clear.** Eliminate the divergent generated reference or update it to exactly
model the committed applicability rule. Add a committed regression that proves both directions
against the production barrier: restoring the all-`crates/**` rule must make
`B1TESTSONLY` red, while a range containing `src/` remains judged. The full battery and
`verify_M-66.sh` must then exit 0 apart from no undeclared failure.

## BLOCKER B-2 — guard G has a revert-pair bypass despite the per-commit lock rule

`scripts/verify_M-66.sh:302-304` decides whether to examine commits from the *net* diff of
process-lock paths. Only if that diff is nonempty does it reach the per-commit token loop at
lines 305-320. An unauthorised lock edit followed by its revert has an empty net diff, so line
303 passes and the unauthorised commit is never examined. This contradicts the explicit
per-commit/revert-pair rule in `.claude/rules/gates.md` §11.

I executed the unmodified guard block against an isolated synthetic history containing exactly
that pair. It passed with `guard_failed=0`; the raw reproduction is in the Done Block.

**Condition to clear.** Scan every commit in `BASE..HEAD` for process-lock paths regardless of
the net diff, then require the token for each such commit. Add a persistent RED case that runs
the actual guard form on an unauthorised edit plus revert and expects failure. This must be a
committed oracle, not only a one-off command.

## BLOCKER B-3 — guard G cannot distinguish task-5 authority from a wider tokened lock edit

M-66 task 5 authorises the nine profile files and `.claude/rules/gates.md`
(`milestones/M-66-protocol-attestation.md:357-358`). Guard G accepts any lock path whose own
commit has a syntactically valid token (`scripts/verify_M-66.sh:308-315`). It has no allowed
path set for task 5. A synthetic commit with a valid-looking token that changes only
`docs/04-workflow.md` therefore passes guard G, although that path is outside task 5.

The general lock token remains an audit trail, not a signature. That is not a reason for this
milestone's task-specific acceptance check to label a broader edit as the authorised task-5
form. C-115 required a check that passes the exact authorised form and rejects the
unauthorised one; this guard proves only that some token-shaped text exists.

**Condition to clear.** Define and enforce the task-5 path set for this verifier (or narrow the
claim to the general lock rule and remove the task-5 assertion). Add RED controls for a
tokened in-scope change and a tokened `docs/04-workflow.md` change. The latter must fail.

## BLOCKER B-4 — the actual PR event base is not a valid range for this head

The handoff names `origin/main` at `fbdca10d098fc2d4befced8fa3f641be8ca71b33`. It is not an
ancestor of `650f31b`; the merge base is `41129a98d1421082f5c26595e4083e3de22c56cb`.
Accordingly, the production-form pull-request invocation of `check_review_fa.sh` fails
closed at lines 47-50, and the same base makes `check_gate_meta.sh`, `check_docs_freeze.sh`,
and `check_artifact_ids.sh` fail before judging the artifact set. A merge-preview/CI run cannot
be claimed from this stale branch tip.

**Condition to clear.** Rebase or merge current `origin/main` into the subject branch, push the
result, rerun the complete harness gates using the resulting PR base, and submit that new
committed head for a fresh critic verdict. Do not reuse this verdict as approval of the rebased
tree.

## CONCERN C-1 — the normative milestone text has not adopted its new test-only exception

The new axis at `milestones/M-66-protocol-attestation.md:271` says test-only changes skip.
But the invariant and operational step at lines 159-161 still state that any `crates/**` path
is judged, with no exception. The code and RED table therefore contradict the contract that
the implementation is supposed to realize. The follow-up must define the boundary once,
including its treatment of `Cargo.toml`, `build.rs`, `benches/`, and `examples/`, then test each
chosen classification. The current `src/` control alone is not that classification.
