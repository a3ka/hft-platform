## 2. Ответы на заданные вопросы

1. **§2 / не `crates/contracts`: согласен, не boundary C и не T1-блокер на этот круг.**  
   `docs/03-integration-contract.md:59-73` определяет границу C как веса/лимиты/параметры,
   применяемые через подписанный `Ctl(ParamChange)`. Export форма gateway read-only и не
   меняет runtime-параметры. `docs/05-contract-layer.md:38-43` прямо называет viz/export формы
   `T-DESIGNATE, НЕ T1`, без contract-RFC, до промоушена в T1. Поэтому решение M-64 делать
   отдельную контрактную поверхность корректно. Это не founder-signature boundary.

2. **§4.1 двусторонний инвариант: по тексту да.**  
   Легитимные случаи `поле добавлено`, `поле стало необязательным`, `аддитивное прошло свободно`
   в §4.2 и acceptance `C/F2` не дают реализации "запретить всё" пройти честную батарею, если
   эти cases будут реально исполнены.

3. **§4.2 четыре оси: почти, но не исчерпывают.**  
   Пятая ось не нужна. Нужен отсутствующий атом на оси 2: смена семантики существующего поля
   при неизменной Rust/JSON форме. Это уже случалось в gateway и было breaking для фронта.

4. **§1.1: замер подтверждён.**  
   См. §1 выше.

5. **§5: запретный список недостаточен для соседних CI-барьеров.**  
   Он переносит часть `C-073` F-5, но теряет критичную половину: защиту сверки
   `needs.<job>.result`, а не только членства job в `status-check.needs`.

## 3. Findings

### F1 — BLOCKER: нет значения "семантика поля изменилась при той же форме"

M-64 §4.2 ось 2 перечисляет синтаксические изменения: `поле удалено`, `поле переименовано`,
`тип поля изменён`, `поле стало обязательным`, плюс аддитивные варианты
(`milestones/M-64-export-contract.md:96-99`). Но текущая история gateway уже содержит
ломающее изменение, которое не меняло JSON/Rust форму поля:

- `crates/gateway/src/lib.rs:44-49` — `SeriesBundle.vwap` остался `Vec<(i64,i64)>`, но
  семантика сменилась с session-anchored на journal-cumulative; комментарий требует bump
  `5 -> 6`.
- `docs/fa/viz-backend.md:120` закрепляет тот же класс: смена семантики VWAP и переход CVD
  single-running -> session-ledger требуют `GATEWAY_SCHEMA_VERSION` bump.

Текущие acceptance-строки M-64 проверяют schema/classifier дифы: удаление, переименование,
сужение типа, добавление (`milestones/M-64-export-contract.md:132-137`). Реализация, которая
меняет meaning/anchor/provenance существующего поля без изменения схемы, пройдет такой
schema-only classifier как `none`, хотя фронт сломается так же реально, как при rename.

**Требование к architect:** добавить значение на ось 2, например
`семантика поля изменилась при той же форме`, и соответствующий mutant/RED case в §4.4/§6:
semantic-only change обязан классифицироваться как breaking и требовать bump + RFC по норме
M-64. Если architect хочет исключить semantics из M-64, это должно быть явной нормой, но она
конфликтует с уже существующим `GATEWAY_SCHEMA_VERSION` v5->v6 precedent.

### F2 — BLOCKER: §5 теряет половину `C-073` F-5 для `ci.yml`

M-64 task 4 меняет `.github/workflows/ci.yml`: добавляет job `export-contract`, включает его
в `status-check.needs` и сверяет `needs.<job>.result` (`milestones/M-64-export-contract.md:68`).
Это ровно соседняя зона `C-073` F-5.

Но запретный список M-64 защищает только "существующие джобы CI и их членство в
`status-check.needs`" (`milestones/M-64-export-contract.md:121`). Он не запрещает ослабить
shell guard `status-check`, который при `if: always()` является реальным блокирующим механизмом.
На M-63 итоговая формулировка после `C-073` F-5 была шире: нельзя удалять/ослаблять job, его
членство в `status-check.needs` **или сверку `needs.<job>.result`**
(`origin/feat/M-63-ci-cost:milestones/M-63-ci-cost.md:118`).

Следствие: dev может сохранить все existing jobs в `needs`, но переписать guard так, что
`contracts` или `docs-freeze` больше не участвуют в условии `!= success`. GitHub job останется
в DAG, а красный результат перестанет блокировать merge.

**Требование к architect:** перенести `C-073` F-5 полностью: запретить удалять, переименовывать,
ослаблять и выводить из блокировки любой существующий barrier job/step, включая
`status-check.needs` **и** каждую сверку `${{ needs.<job>.result }}`. Acceptance `W` должен
проверять не только новый `export-contract`, но и сохранение существующих checks как
исполняемого guard'а.

### F3 — MAJOR: dev scope для task 2-4 не задан как path-carve-out

`scope-guard.md` даёт `engine-dev` standing scope на `crates/gateway/src/**` среди прочих
engine crates, но не на root `contracts/export/**`, scripts или `.github/workflows/ci.yml`.
M-64 task 1 частично записывает carve-out только в одной строке:
`contracts/export/**`, `crates/gateway/src/**` (`milestones/M-64-export-contract.md:65`).
Tasks 2-4 дальше говорят только `dev` (`milestones/M-64-export-contract.md:66-68`), хотя
требуют:

- `scripts/verify_export_contract.sh`
- `scripts/diff_export_schema.sh`
- `.github/workflows/ci.yml`

Без явного allowed-path блока dev либо остановится по scope-guard, либо сочтет `dev` широкой
лицензией на scripts/CI. Оба исхода плохие.

**Требование к architect:** добавить явный `Allowed paths` / `Forbidden paths` блок. Минимум:
engine-dev carve-out только для `contracts/export/**`, `crates/gateway/src/**`,
`scripts/verify_export_contract.sh`, `scripts/diff_export_schema.sh` (и helper `.py`, если
он нужен), `.github/workflows/ci.yml` additive-only для job `export-contract` и
`status-check`. Architect-owned оставить `crates/gateway/tests/red_export_contract.rs`,
`scripts/tests/red_export_schema.sh`, `scripts/verify_M-64.sh`, `.claude/rules/gates.md`.
