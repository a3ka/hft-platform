## Why rev3's PASS had to be re-opened (the defect that fired in prod)

rev3 (`de8629c`) granted PASS on the claim that L2Delta is machine-isolated because the M-18 binary
carries a NEW `SegmentHeader.provenance` (git-sha) → `decide_open_segment` sees a provenance-mismatch →
opens a new segment → variant-6 never lands in a pre-M18 schema-2 segment.

**That claim was false on the deploy target.** `recorder` computes provenance via `git rev-parse` **at
runtime** (`main.rs`), but the runtime container has **no git** → provenance degrades to the CONSTANT
`"recorder v0.0.0 (git:no-git-info)"` on *every* deploy. Identical provenance across epochs →
`decide_open_segment` reuse condition (`source && provenance && epoch_id`) matched the pre-M18 active
segment → the first live L2Delta (variant-6) was appended into **schema-2 `segment-00000055`** →
mixed segment, quarantine impossible (TD-031).

rev3's oracle passed only because its FIXTURE set a DIFFERENT provenance per phase — it encoded the
happy-path assumption, not the prod regime (`.claude/rules/testing.md`: happy-path fixture = oracle
defect). This is exactly the failure class the testing rules warn about, and it slipped rev3.

## The fix under audit

`SCHEMA_VERSION` 2 → 3, and `decide_open_segment` reuse now additionally requires
`header.schema_version == contracts::SCHEMA_VERSION` (`crates/journal/src/segments.rs`, engine-dev
`e13e686`, +9/-1). Isolation is held by the **schema epoch**, which is a **compile-time constant**, not
by a runtime-derived value.

## Checklist (rev4 focus: schema-gate prod-adequacy + anti-placebo)

### 0. Root-cause adequacy — is the schema gate immune to the prod-degradation that killed provenance?

**PASS — verified against code.** `pub const SCHEMA_VERSION: u32 = 3;` (`crates/contracts/src/lib.rs:24`)
is a compile-time constant baked into the binary. It is NOT read from git / env / filesystem / clock at
runtime. Therefore it **cannot** degrade to a wrong constant in a no-git container — which is precisely
why it is the correct isolation marker where provenance failed. This is a genuine root-cause fix, not a
patch over the symptom.

### 1. Reuse-condition logic in prod steady state — no segment-churn

**PASS — verified.** New segments are stamped with `schema_version: contracts::SCHEMA_VERSION`
(`crates/journal/src/lib.rs:139` and `:266`). So after the fix deploy:
- Fix binary vs mixed `segment-55` (schema-2 header): `2 == 3` false → **new `segment-56`** (schema-3). ✓
- Fix binary restart vs `segment-56` (schema-3 header): `3 == 3` true, constant provenance also matches →
  **reuse**, no new segment per restart (no churn). ✓
The schema clause is ANDed onto the existing clauses; it only *adds* an isolation condition at the epoch
boundary and does not change intra-epoch reuse.

### 2. Edge cases in the sacred live-path

**PASS — verified in code + milestone task 9 wording.**
- **Legacy headerless active segment** (TD-011-era, no magic/header): `read_v2_header_and_skip` → `None`
  → `decide_open_segment` returns a NEW segment *before* reaching the schema clause (`segments.rs:1160-1174`).
  Fail-safe: an unidentifiable active segment is never appended to. ✓
- **Forward decode of mixed segment-55:** the schema-3 binary CAN decode variant-6, so `tail_last_seq_of`
  / `resolve_next_seq_with` compute `next_seq` correctly against the tail of the mixed segment before
  opening 56. The forward path has no seq defect; the un-decodable-variant seq-reuse risk is a PRE-M18

## Non-blocking notes (defense-in-depth; do not gate merge)

- **N1 — schema-epoch isolation depends on the discipline "new emitted variant ⇒ bump SCHEMA_VERSION"**
  (RFC §3). It is a documented standing rule (like frozen discriminants), but has NO machine enforcement:
  a future variant added without a bump would re-open epoch mixing. Recommend it stay an explicit,
  enforced rule at the contract-RFC gate. Non-blocking.
- **N2 — segment-55 is permanently tainted** (schema-2 header + variant-6 content). The task-10 §8
  re-check MUST confirm the active append target after the fix deploy is `segment-56` (schema-3), not
  still `segment-55`. Already gated by milestone task 10; flagged so reviewer treats it as a hard check.
- **N3 — TD-b (reader `first_seq`-guard) remains the only missing machine barrier against operator
  re-stitch.** TD-031 does not change that posture (correctly deferred; TD-011-class change to the sacred
  read-path, must respect legacy `first_seq=0` sentinel — own milestone, not M-18).
- **N4 — torn-flush window** (`flush()` `sync_data` before `write_meta`) → cross-epoch value-reuse
  possible but benign under never-merge (per-epoch monotonicity holds). Unchanged from rev3.
