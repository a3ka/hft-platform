### Ф2 (пункт 1 ТЗ, критик находка — ГЛАВНАЯ, обосновывает REJECT) — §5.2 расходится с §2/§1.2 по обязательности risk-critic на `crates/contracts/**`

Сырое сравнение (§5.2 плана, дословно):

```
├─ ПАРАЛЛЕЛЬНО (независимые RFC, разные формы) ────────────────────────────
│   Б2.4 CT-RFC-06 wire-контракт кокпита    architect(RED+типы) → engine-dev

└─ СТРОГО ПОСЛЕ Б2.2 и в одиночку (трогает журнальный заголовок) ──────────
    Б2.5 CT-RFC-07 source_kind/license_class, SCHEMA_VERSION→5
           architect(RED, вкл. роундтрип на реальном хвосте прода)
           → engine-dev → tester → risk-critic → reviewer → §8 деплой-гейт
```

Б2.5 — единственная строка, где явно прописаны `tester → risk-critic → reviewer`. Б2.4/Б2.6/
Б2.7 обрываются на `engine-dev`. Б2.2 (`verify_contracts.sh` + CT-I-9/10/14 — оракулы ложатся в
`crates/contracts/tests/`, судя по прецеденту `ct_rfc01.rs`, т.е. это ТОЖЕ касание
`crates/contracts/**`) вообще не показывает ни critic, ни risk-critic, ни reviewer:

```
Б2.2 verify_contracts.sh + CT-I-9/10/14 (зеркало)       architect(RED) → engine-dev(GREEN)
```

Это прямо противоречит:
- §2 плана, п.4 (BINDING): «Каждое касание `crates/contracts/**` = отдельный contract-RFC с
  полным набором из 7 пунктов + critic + **risk-critic** + reviewer Block-C.»
- Собственной фактуре плана §1.2: «`gates.md` §1.1 + §5: любое касание `crates/contracts/**` =
  contract-RFC + critic **И** risk-critic (RISK-BLOCK; MD-only carve-out на contracts НЕ
  распространяется).»
- Проверено мной напрямую на `origin/main` `.claude/rules/gates.md` §5 (сырой вывод — см. раздел
  «Проверенная фактура» ниже): risk-critic обязателен безусловно на `crates/contracts/**`, без
  исключений по типу правки.

Особенно чувствительно для **Б2.7 (JWT-claims + tariff enforcement)** — сам план в §4.1 (строка
К6) пишет: «форма на границе двух языков с security-последствиями ⇒ **risk-critic обязателен**»
— то есть план ЗНАЕТ, что здесь нужен risk-critic, но §5.2 (единственная секция, которую
дословно копирует founder/dispatcher в paste-ready промпт по формату `handoff-block.md`) этого
не показывает. Диаграмма §5.2 — фактически операционный рантайм плана; несовпадение с §2/§1.2 —
не редакционная мелочь, это ровно тот класс «заявлено ⟹ не проверено», для защиты от которого
план сам предлагает `CT-I-14`.

**Это блокирующая находка.** Механический фикс — architect явно прописывает
`→ critic → risk-critic → reviewer` в каждой строке Б2.2/Б2.4/Б2.5/Б2.6/Б2.7 §5.2 (и сверяет с
Б2.1/Б2.3, которые прописаны корректно), без изменения содержательной части плана.

### Ф3 (пункт 2 ТЗ — анти-плацебо оракулов CT-I-7..15)

Проверил каждый оракул на «упадёт ли ПРЯМО СЕЙЧАС против сегодняшнего кода» — да для всех
девяти (подтверждено фактурой ниже: типы вне `contracts`, версии без RFC, канарейка не
покрывает `EventKind`, golden-фикстур нет). Ни один не зелёный с первого запуска — анти-плацебо
по букве `testing.md` соблюдён на уровне «упадёт ли». Но три оракула имеют скрытый риск стать
плацебо/неисполнимыми на этапе ДИЗАЙНА (не блокер, но architect обязан закрыть до реализации
Б2.2/Б2.4):

1. **CT-I-7** (нет типов вне `crates/contracts` на внешней границе) держится на «whitelist,
   ведётся явно и коротко» — план не говорит, КТО и ПО КАКОМУ ПРАВИЛУ добавляет запись в
   whitelist. Без RFC-гейта на сам whitelist канарейка вырождается в «допишем исключение и
   тест снова зелёный» — ровно та эволюция, которая уже породила `T-designate` (комментарий
   `crates/gateway/src/lib.rs:39` — это и есть готовый, уже существующий de-facto whitelist без
   процедуры). Architect обязан явно определить: запись в whitelist = отдельный
   commit с обоснованием + reviewer, или whitelist закрыт до Б2.4 и после — 0 новых записей без
   contract-RFC.
2. **CT-I-10 / CT-I-14** («каждая T1-форма определена ровно в `contracts`» / «заявлено ⟹
   проверено») — обе логически требуют статус-поля (`ACTIVE` vs `PENDING`) у каждого ID в
   машиночитаемой таблице `docs/05` §2, иначе они НИКОГДА не позеленеют, пока K9
   (`SignalSpec`/`Ctl(ParamChange)`/`Decision`) сознательно остаются PENDING/DEFERRED (§4.1,
   приоритет P3/DEFERRED) — план сам вводит понятие `PENDING`-метки в критерии готовности Б1.5
   («каждый INTG-I-1..7 несёт либо путь к оракулу, либо метку PENDING»), но **не переносит это
   явно в определение CT-I-10/CT-I-14 в §4.3** — там написано «сверка таблиц… против git grep»
   без упоминания PENDING-исключения. Не REJECT (это деталь дизайна оракула, зона architect'а
   по `gates.md` §4 «критик описывает, architect проектирует»), но фиксирую явно: если
   architect забудет протащить PENDING-статус в реализацию CT-I-10/CT-I-14, оба оракула станут
   **невозможными к закрытию** (перманентный FAIL — это уже не «реальный гейт» в смысле
   `gates.md` §3, а сломанный гейт).
3. **CT-I-15** (golden-фикстуры «на каждую живую версию» против тихой смены семантики) —
   формулировка «на КАЖДУЮ живую версию» физически невыполнима для v5/v6/v7: код, реализовывавший
   их семантику (session-anchored VWAP и т.п.), уже переписан in-place (не аддитивно, `docs/05`

   `cvd_session_base`) — из ТЕКУЩЕГО кода нельзя регенерировать «выход v6-семантики». Реально
   выполнимо и полезно — заморозить golden ТОЛЬКО для текущей (v8) семантики как якорь ВПЕРЁД
   («с этого момента смысл не должен тихо меняться»), не как ретроактивную пломбу на историю.
   Architect обязан переформулировать критерий CT-I-15 в терминах «текущая live-версия», не
   «каждая живая версия».

### Ф5 (пункт 3 ТЗ — критерий T1, §4.2) — критерий, вероятно, СЛИШКОМ ШИРОК без явного среднего яруса; голос критика здесь решающий

Условие 3 («отдаётся наружу платящему клиенту») в буквальном прочтении тянет в T1 **любую**
форму, когда-либо показанную платящему пользователю — включая высокочастотно меняющиеся
UI-специфичные структуры (layout виджетов, настройки, косметические поля), не только
рыночные/финансовые/security-формы. Полный contract-RFC (`docs/05` §4: 7 пунктов — тип, схема,
bump, миграционная заметка, valid/invalid фикстуры, CHANGELOG, тест) — тяжёлый процесс,
оправданный для К1 (wire кокпита), К3 (watermark), К4 (AI Event), К6 (JWT claims) — форм с
реальной ценой дрейфа (ровно случай v5→v6 VWAP). Для К5 (`Workspace`/`View`/`Widget`-layout)
план сам констатирует T1-статус «по правилу TD-008 (кросс-языковой консюмер ⇒ contracts)» без
дифференциации по риску.

**Риск конкретный, не гипотетический**: тяжёлый governance уже один раз спровоцировал побег —
`GATEWAY_SCHEMA_VERSION`/`T-designate` в `crates/gateway/src/lib.rs` дословно существует
КАК ОТДЕЛЬНЫЙ, более лёгкий канал именно потому, что полный `contracts`-RFC для
высокочастотно эволюционирующих viz-форм был/показался слишком тяжёл. Критерий T1 из §4.2,
принятый как есть, накрывает СВОИМ же новым правилом ровно то, от чего гейт когда-то сбежал —
без предложения более лёгкого, но всё же governed, среднего яруса, высок риск повторения:
разработчики (или сам architect под давлением скорости SaaS-итераций) заново изобретут
«T-designate-2» для форм, которые технически T1 по букве критерия, но не несут асимметричной
цены рыночных/денежных/security форм.

**Рекомендация (не проектирую решение — называю развилку для architect'а):** рассмотреть
двухъярусную модель — **T1-full** (RFC из 7 пунктов, для К1/К3/К4/К6/К6b — денежные/
рыночные/security формы) vs **T1-lite/registered** (упрощённая процедура — тип в `contracts`,
`schemars`-схема, но БЕЗ полного RFC-ритуала — для layout/preference-форм вроде К5), с явным
критерием разделения. Если architect после рассмотрения сознательно отклонит двухъярусную
модель и оставит единый T1, это ДОЛЖНО быть явным решением с обоснованием в `docs/05` §2 (не
молчаливым унаследованием TD-008), потому что тяжесть процесса — это то, что уже один раз
спровоцировало обход governance в этом же репозитории.
