## §2. БЛОКИРУЮЩИЕ находки (CT-RFC-08 rev1)

### B1. Заявленное закрытие TD-081/AL-I-4 — ЛОЖНАЯ ГАРАНТИЯ: на данных новой эпохи фикс не работает

RFC §2.5 фиксит alpha детектом **регрессии** оси (`ev.ts_mono_ns < last_seen`) и сам же признаёт:
«**На schema-5 данных ветка мертва**». Но исходный дефект TD-081 — не регрессия как таковая,
а то, что **сэмпл переживает простой писателя**. O2 регрессию убирает, а простой в ось не
включает (§2.1 прямым текстом: «простой писателя в ось не входит»). Значит на schema-5:

- `mono_base` = high-water хвоста ⇒ сэмпл, снятый последним перед остановкой, имеет
  `ts_event_mono_ns ≈ mono_base`;
- после рестарта (пауза 3 дня — деплой, инцидент, ретеншен) первые события имеют
  `ts_mono_ns = mono_base + ε`, где ε — наносекунды с момента open;
- `fresh = ev.ts_mono_ns <= sample.ts_event_mono_ns + horizon_ns`
  (`crates/alpha/src/lib.rs:191-192`) → **true** в течение всего `horizon_ms` осевого времени
  после рестарта, независимо от реальной трёхдневной паузы.

Дефект сужается («вечно свежи» → «свежи ещё horizon_ms после рестарта»), но НЕ исчезает, и
детект регрессии его не ловит **по построению**. Milestone по этому RFC закрыл бы TD-081 ложно —
ровно класс «ложное [ЕСТЬ]», против которого написан сам RFC (§1).

**Что требуется от rev2.** Stale-expiry по смыслу требует ФИЗИЧЕСКОГО времени: либо
`ts_wall_ms` (уже в каждом событии, DESIGN §3 «wall_ms для отчётов» — здесь это не отчёт, а
измерение давности данных), либо явный маркер границы сессии в потоке. Второго СЕЙЧАС НЕТ:
`SysEvent` = `Heartbeat | ConnUp | ConnDown | ReconDivergence`
(`crates/contracts/src/lib.rs:157-167`) — «писатель перезапустился» не эмитируется, а
`SegmentHeader` — не `Event` и до консюмера не доходит. Если выбран путь маркера — это НОВЫЙ
вариант enum, то есть настоящее аддитивное изменение T1 со своей ценой; если `ts_wall_ms` — надо
назвать поведение при отводе часов. Любой из вариантов меняет §2.5 и оценку «≤6 коммитов».

### B3. Якорь `mono_base` НЕ ОПРЕДЕЛЁН на двух реальных путях `open` — обоих, введённых ради выживания при порче

RFC §2.2 п.1 знает ровно два случая: «хвост читается» и «журнал пуст → 0». Код знает больше:

**(а) Операторская декларация (M-49).** `resolve_next_seq_or_declared`
(`crates/journal/src/segments.rs:2158-2200`) существует ИМЕННО для случая, когда хвост
**нечитаем** (`is_tail_unreadable`) — тогда `next_seq` берётся из
`journal.force-next-seq.json`. На этом пути «`ts_mono_ns` последнего события хвоста» физически
недоступен. Естественный дефолт (`0`) даёт разрыв оси там, где доверие к данным и так подорвано.
RFC обязан сказать явно: декларация несёт и `mono_base`, либо open на этом пути отказывает,
либо ось получает другой якорь.

**(б) `meta` может быть ВПЕРЕДИ читаемого хвоста.**
```
crates/journal/src/segments.rs:1466-1476
pub(crate) fn resolve_next_seq_with(dir, meta_path) -> io::Result<u64> {
    match latest_segment(dir)? {
        None => Ok(meta_seq),                     // сегментов нет, но seq ПРОДОЛЖАЕТСЯ с меты
        Some((_idx, path)) => Ok(meta_seq.max(tail_last_seq_of(&path)? + 1)),
    }
}
```
У `seq` есть ВТОРОЙ durable источник (`journal.meta`), у оси времени — нет. Каталог, где мета
есть, а сегментов нет (restore из холодной копии, ручной карантин сегментов по
`docs/ops-journal-tail-unreadable.md`), даёт `next_seq > 0` и `mono_base = 0` ⇒
`seq_a < seq_b ∧ ts_mono_a > ts_mono_b` — **JR-I-13 нарушен ровно в том сценарии, ради которого
инвариант и вводится**. Симметричное решение: high-water оси persist'ится там же, где `next_seq`
(мета + декларация), и восстанавливается как `max(мета_high_water, хвост)`.

### B4. Якорь «последнее событие хвоста» ≠ high-water: на боевом журнале JR-I-13 ложен с первого же дня

Прод-журнал (157.9M событий, schema ≤4) состоит из сессий, каждая из которых считала mono с нуля.
Значение последнего события хвоста — это mono ПОСЛЕДНЕЙ (возможно, короткой) сессии, то есть
маленькое; при этом в журнале ранее лежат события с mono на порядки больше (длинная сессия →
десятки суток в наносекундах). Первый schema-5 сегмент стартует НИЖЕ исторического максимума, и
формулировка §2.1 — «для любых событий **одного журнала** `seq_a < seq_b ⇒ mono_a <= mono_b`» —
на реальном каталоге ложна сразу после включения. Оговорка §2.1 про «сегменты до эпохи честности»
спасает чтение старого, но не спасает СШИВКУ старого с новым.

Требуется одно из: (i) якорь = `max` по читаемому хвосту (и честная цена скана в §4), либо
(ii) JR-I-13 явно сужается до «событий эпохи ≥ 5», а оракул **JR-I-13a обязан гоняться на
СМЕШАННОМ каталоге (legacy-сегменты + новые)**, иначе это фикстура счастливого пути — тот самый
класс, который `testing.md` §«Фикстура „счастливого пути“» запрещает.

### B5. Атомарный CT-RFC-пакет: §4 «JSON Schema не меняется» неверно и не сходится с МАШИННЫМ гейтом

`docs/05-contract-layer.md` §4 требует в ОДНОМ PR семь артефактов, и это уже машинный
блокирующий job: `.github/workflows/ci.yml:111-112` → `scripts/verify_ct_rfc_atomic.sh`. Скрипт
при любом касании `crates/contracts/src/**` требует в диффе: `docs/rfc/CT-RFC-NNN-*.md`,
`crates/contracts/schema/*.json`, `CHANGELOG.md`, `fixtures/valid/*.json`,
`fixtures/invalid/*.json`, `crates/contracts/tests/*.rs`. Против этого:

- **§4 RFC утверждает «JSON Schema не меняется» — фактически неверно.** Схема генерируется
  schemars из докстрок: `crates/contracts/schema/event.schema.json:4` — это докстрока структуры
  `Event`. Нормативная докстрока §2.1, повешенная на поле `ts_mono_ns` (сейчас поле в схеме без
  `description`, `event.schema.json:21-25`), схему ИЗМЕНИТ. Если dev поверит §4 и докстроку
  повесит не туда/не регенерирует — гейт красный.
- **`fixtures/invalid/*.json` для семантического изменения естественным образом не выражается**
  (межсобытийную монотонность JSON Schema не описывает). Планировать это надо в RFC, а не
  оставлять dev'у выбор между красным CI и фиктивной фикстурой.

## §7. Блокеры rev2

### B7. `force_mono_floor_ns` — fail-OPEN там, где `force_next_seq` fail-closed (регресс внутри закрытия B3)

§2.2 п.2 объявляет: «операторская декларация … расширяется полем `force_mono_floor_ns` (**та
же дисциплина, что `force_next_seq`**)». Дисциплина `force_next_seq` — это НЕ «поле в файле»,
а МАШИННАЯ ВАЛИДАЦИЯ против читаемых данных:

```
crates/journal/src/segments.rs:2187-2196
if decl.next_seq <= readable_max {
    return Err(... "next_seq={} must be strictly greater than the maximum READABLE seq={} ...")
}
```
где `readable_max` берётся из `readable_floor` (`segments.rs:1616+`), который толерантно
сканирует ЧИТАЕМЫЕ ПРЕФИКСЫ повреждённых сегментов (`tolerant_max_seq_from_start`), а
состояние `Unknown` даёт отказ, а не разрешение (M-49 rev5, блокер R-002).

Для `force_mono_floor_ns` rev2 не задаёт ни валидации, ни источника значения:
- оператор не знает, откуда взять число (для `next_seq` его печатает диагностика отказа);
- объявленный floor НИЖЕ максимального ЧИТАЕМОГО `ts_mono_ns` даёт события эпохи 5 с
  `seq_b > seq_a` и `mono_b < mono_a` — **JR-I-13 нарушен ровно в честной эпохе**, молча;
- оракул JR-I-13e, как он описан в §3 («без поля — отказ; с декларацией — ось ≥ floor»),
  ДЫРУ КОДИФИЦИРУЕТ: он зелёный и при заниженном floor.

Это тот же класс, что закрывал R-002 в M-49: «отсутствие знания трактуется как разрешение».
Фикс дешёвый и симметричный: `readable_floor` уже читает фреймы, поэтому максимум
`ts_mono_ns` по читаемым префиксам берётся тем же проходом; декларация валидируется
`force_mono_floor_ns >= readable_max_mono` (иначе отказ с печатью нужного числа), а
`ReadableFloor::Unknown` → отказ. Оракул JR-I-13e обязан получить анти-плацебо-ветку:
**декларация с ЗАНИЖЕННЫМ floor обязана быть отвергнута**.

### B8. sim: формула §2.5 underflow'ит ровно на тех данных, ради которых введена; SM-I-x не содержит legacy-фикстуры

§2.5 задаёт `mono_gap = (ev.ts_mono_ns − prev.ts_mono_ns)/1e6`. Основной вход sim — 157.9M
исторических событий эпохи ≤4, где ось РЕГРЕССИРУЕТ по определению (§2.1). `ts_mono_ns` —
`u64` ⇒ на регрессии выражение даёт панику в debug и **тихое заворачивание в release**
(гигантский `mono_gap` ⇒ `wall_gap − mono_gap` отрицателен ⇒ **разрыв не детектируется
никогда**). То есть на legacy-данных механизм честности sim не просто ошибается — он молча
выключается, а бэктест продолжает печатать метрики.

Деградированная форма `SM-I-x` в §3 («разрыв ПОСРЕДИ пачки pending; разрыв без pending»)
legacy-регрессию не содержит — тот самый класс «фикстура счастливого пути» (`testing.md`).

Требуется: (а) знаковая арифметика (`i128`/`saturating`) с объявленной политикой на
регрессию оси как на разрыв; (б) в `SM-I-x` — фикстура журнала эпохи ≤4 с регрессией оси
ПОСРЕДИ прогона (это, а не синтетический wall-гэп, — прод-форма входа sim, `testing.md`
«Форма прода снимается ЗАМЕРОМ»).

## §13. N18 (ОБЯЗАТЕЛЬНЫЙ перенос в RED-набор milestone'а) — «тем же проходом» неверно для КРУПНЫХ фреймов

Единственная остаточная находка. Формулировка §2.2 п.2 «`readable_floor` … тем же проходом
снимается `readable_max_mono`» держится для основного пути скана, но НЕ для ветви крупных
фреймов, которая в `readable_floor` существует специально (JR-I-9/TD-053):

```
crates/journal/src/segments.rs:1866   const SEQ_PREFIX_CAP: usize = 10;
crates/journal/src/segments.rs:1930   match postcard::take_from_bytes::<u64>(&prefix) {
                                          Ok((seq, _rest)) => VerifyOutcome::Accepted(seq),
```
Крупный кандидат (`len+8 > READABLE_SCAN_MAX_CARRY`) верифицируется потоково БЕЗ буферизации
тела: удерживается префикс ≤10 байт, из него декодируется ТОЛЬКО `seq` (первое поле `Event`).
`ts_mono_ns` — второе поле, до 10 байт varint'а дальше, в префикс не попадает.

Следствие, если реализовать §2.2 буквально: `readable_max_mono` занижен ровно на крупных
фреймах ⇒ операторская декларация с floor ниже реального максимума будет ПРИНЯТА ⇒ молчаливое
нарушение JR-I-13 в честной эпохе — то есть та самая дыра B7, сузившаяся до случая «нечитаемый
хвост + читаемый префикс содержит крупные фреймы». Класс не гипотетический: ветвь крупных
фреймов и заведена потому, что такие события в проде есть (TD-053).

Требование (одна константа + один шаг декодирования):
1. `SEQ_PREFIX_CAP` расширяется до объёма, достаточного для ДВУХ varint-полей (`seq` +
   `ts_mono_ns`), и `verify_large_frame` возвращает пару, а не только `seq`;
2. фикстура оракула JR-I-13e ОБЯЗАНА содержать крупный фрейм в читаемом префиксе — иначе
   ветвь не покрыта и это снова фикстура счастливого пути (`testing.md`);
3. если п.1 по каким-то причинам отвергается — единственная допустимая альтернатива
   fail-closed: наличие крупного фрейма в читаемом префиксе ⇒ `Unknown` ⇒ отказ, но НЕ
   заниженный максимум.

Проверяется на plan-time гейте milestone'а поимённо.
