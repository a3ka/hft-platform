## Blocking Findings

### B1 — `EpochFilter` / `journal::stream` is specified but not proven

Evidence:

- M-22 design requires the production path to be `journal::stream(dir, EpochFilter)`, with default
  `OwnCaptureOnly` and no silent vendor/synthetic mixing:
  `milestones/M-22-read-gateway.md:30-36`.
- Datalayer already makes epoch mixing an explicit type-level decision:
  `crates/journal/src/segments.rs:81-104`.
- The canonical bounded production reader is `journal::stream`:
  `crates/journal/src/segments.rs:844-846`.
- The verify positive canary is `grep -rqE 'journal::stream|::stream\(' $SRC_FILES`
  (`scripts/verify_M-22.sh:35-36`), but it passes today on doc-comments in
  `crates/gateway/src/lib.rs:12` and `crates/gateway/src/lib.rs:134-135`; no implementation call exists.
- All gateway RED fixtures create only `DataSource::OwnCapture` segments:
  `red_gateway_bounded.rs:85`, `red_gateway_live_eq_replay.rs:61`,
  `red_gateway_readonly.rs:19`, `red_gateway_export_v2.rs:34`.

Why this blocks:

A gateway implementation that ignores the passed `EpochFilter`, or reads through a manual bounded
segment path instead of `journal::stream`, can still satisfy the current test data because there is
no excluded epoch to observe. This violates the datalayer contract (`docs/06` journal-first,
epochs/provenance discipline) and re-opens the C-021 NOTE-2 failure mode at the exact path M-22 is
supposed to close.

### B2 — Cursor semantics are not an oracle

Evidence:

- The public contract defines `Cursor { upto_seq }`, `Snapshot.cursor`, `Frame { from, to }`, and
  `frames_since(...) -> (Vec<Frame>, Cursor)`:
  `crates/gateway/src/lib.rs:36-65`, `crates/gateway/src/lib.rs:102-119`,
  `crates/gateway/src/lib.rs:146-155`.
- The skeleton docs and milestone say snapshot and live tail must form a non-overlapping cover over `seq`:
  `crates/gateway/src/lib.rs:36-40` and `milestones/M-22-read-gateway.md:37-40`.
- The live/replay tests compare only `series` JSON after folding:
  `crates/gateway/tests/red_gateway_live_eq_replay.rs:160-164` and
  `crates/gateway/tests/red_gateway_live_eq_replay.rs:183-187`.
- The returned cursor from `frames_since` is ignored:
  `crates/gateway/tests/red_gateway_live_eq_replay.rs:180-181`.

Why this blocks:

An implementation can produce correct-looking series while leaving `Snapshot.cursor`, `Frame.from`,
`Frame.to`, or the returned `frames_since` cursor stale/wrong. That would break live clients
immediately: reconnect/tail reads can duplicate frames, skip frames, or never advance, while the
current oracle remains GREEN.

### B3 — GW-I-2 names `frames_since`, but bounded-memory is only tested for `snapshot`

Evidence:

- GW-I-2 states `snapshot`/`frames_since` over the journal must be O(1) memory and catch `read_all`:
  `milestones/M-22-read-gateway.md:63`.
- The bounded-memory oracle only measures `gateway::snapshot(...)`:
  `crates/gateway/tests/red_gateway_bounded.rs:131-148`.
- `frames_since` and `replay` are exercised only on small fixtures in
  `red_gateway_live_eq_replay.rs`.

Why this blocks:

The live tail path can materialize a long history or collect the whole stream into an intermediate
buffer and still pass the current resource oracle. The grep canary catches literal `read_all` and
literal `Vec<Event>`, but it does not catch equivalent materialization such as collecting the stream
before reducing it. This leaves the TD-011/C-021 production-scale failure mode open for the actual
live path.
