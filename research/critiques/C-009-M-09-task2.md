## Findings

### MAJOR

**M1 — OPS-I-5 verifier does not detect missing §7.1 incident rows.**

- Evidence: `scripts/verify_M-09.sh:53-61` checks only `§7.1 metric names -> METRIC_NAMES` and `METRIC_NAMES -> §3`.
- Evidence: `docs/fa/ops.md:182-188` requires the opposite class too: a P0/P1 incident class without a §7.1 row is a hole; §7.1 is the canonical parity surface.
- Execution evidence: removing the `C1-M08` row from §7.1 did not produce an OPS-I-5 failure; both parity lines still printed PASS.
- Impact: the exact C-007 C1 regression can recur. A future edit can drop the book-corruption P0 class while the gate remains "green" for OPS-I-5.
- Required fix: make `verify_M-09.sh` fail when required P0/P1 incident IDs or rule classes disappear from §7.1. At minimum, compare a canonical expected incident set from the FA/committed list against parsed §7.1 rows, or encode stable required IDs and fail on any missing row. Re-run the "remove `C1-M08` row" mutation and show an explicit OPS-I-5 FAIL line.

**M2 — Metrics RED tests pass against no-op static unlabeled metrics.**

- Evidence: `crates/ops/tests/red_ops_metrics.rs:17-30` only checks that output contains each base name.
- Evidence: `crates/ops/tests/red_ops_metrics.rs:37-54` calls `inc` from threads but never asserts that the value changes.
- Evidence: `docs/fa/ops.md:69-75` requires label-bearing Prometheus series such as `md_events_total{venue,symbol,kind}`, `venue_http_status_total{venue,code}`, and `book_divergence_bps{venue,symbol}`.
- Evidence: `crates/ops/src/metrics.rs:30-55` fixes an API with `inc(&self, name, by)` / `set(&self, name, value)` and says labels are an implementation concern, but the signature has no structured label surface.
- Execution evidence: a mutation with static `<name> 0` output, no-op `inc`/`set`, and no labels passed all `red_ops_metrics` tests.
- Impact: `OPS-I-4` can pass while metrics are decorative and unlabeled; `OPS-I-7` can pass while counters do not update. This violates `testing.md` gate-integrity rules that an oracle must measure its own invariant and fail against the broken implementation.
- Required fix: either change the API now to include structured labels, or explicitly define a safe label encoding contract in the signature and tests. Add RED assertions that:
  - incrementing a counter changes the exported value;
  - setting a gauge changes the exported value;
  - at least the label-bearing metrics render required labels (`venue`, `symbol`, `kind`, `code`, `side`) in Prometheus form;
  - no-op `inc`/`set` and static name-only output fail.

### MINOR / Notes

**N1 — Recon RED covers degraded inputs, but not production scale.**

- Evidence: `red_ops_recon.rs:24-35` uses ±100 levels.
- Assessment: this is not the blocker for task-2 RED because the current recon oracle is pure comparator logic and already covers asymmetry, absence, multiplicity, and empty-book boundaries. Still, live Binance books are thousands of levels; add a prod-scale bounded-time case before or during implementation if the comparator touches all levels/bands. This is a NOTE unless the implementation chooses an algorithm with unbounded allocation or time.
