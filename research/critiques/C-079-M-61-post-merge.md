## Проверка по существу

### 1. §4.1 — инвариант исполним на живом корпусе

Инвариант сформулирован не как абсолютное "в корпусе нет двух носителей под ID", а как
"коммит диапазона не вводит второго носителя под уже занятый ID"
(`milestones/M-61-artifact-ids.md:233-254`). Это принципиально: абсолютная формулировка
неисполнима, потому что существующие множественности уже есть и переименованию не подлежат
(`milestones/M-61-artifact-ids.md:265-270`).

Код соответствует этой семантике. `introduced()` смотрит только `raw..HEAD`, только `A`
без rename-folding, и только то, что дожило до `HEAD` (`scripts/check_artifact_ids.sh:151-190`).
Сравнение делает ровно P4: тот же class/number/letter и другой carrier
(`scripts/check_artifact_ids.sh:199-218`). Значит законные операции не становятся
невозможными: правка существующего carrier не считается новым carrier, исправленная внутри
диапазона ошибка не краснеет, а старые множественности не требуют переписывания истории.

### 2. §4.2 — семь осей полны относительно инварианта

Семь осей больше не являются мешком случаев: §4.2 прямо говорит, что это члены предложения
§4.1 (`milestones/M-61-artifact-ids.md:278-298`). Относительно текущего инварианта не вижу
члена без оси:

- class/carrier map: ось 1;
- где номер реально несётся: ось 2;
- в каких refs искать занятость: ось 3;
- что считается введением/занятием: ось 4;
- проверяемый диапазон: ось 5;
- разбор `CLASS-NUMBER[LETTER]` и отказ от subject/body: ось 6;
- форма входных данных, где ломались shell/awk/grep доказательства A-007: ось 7.

Механическая проверка состава прошла:

```text

PASS  МАНИФЕСТ ⇄ исполнение: 48 сценариев, состав совпал в обе стороны
PASS  СПЕКА⇄МАНИФЕСТ: 47 пар (ось,вид,значение) совпали в обе стороны
PASS  §4.3(2): у каждой оси есть легитимный сценарий
PASS  §4.3(4): у каждого из 4 мест сравнения §4.6 есть исполненный сценарий
```

Kill-set count в §4.5 также не расходится с таблицей: 40 сценариев из 48 закреплены
kill-set'ами; оставшиеся 8 — legit/setup coverage, а не скрытые значения инварианта.

### 3. §4.4 — правило остановки после A-007 работает

Текущий §4.4 переносит решение A-007 по существу: блокирует false green, предъявленный
исполнением; false red блокирует только если достижим на измеренной прод-форме; остальное
идёт в NOTE/TD (`milestones/M-61-artifact-ids.md:366-382`,
`research/arbitration/A-007-m61-five-rounds.md:334-342`). Главное исправление против
старой ошибки: полнота теперь считается по четырём местам сравнения §4.6, а не по
подвижному перечню осей.

По этому правилу найденное `R-063` NOTE-1 было reachable false red на штатной форме
`metrics.json + R-NNN.md`, поэтому требовало fix-on-top. После fix-пары оно больше не
блокер.

### 4. Founder decision о единственности ID не ломает реальный корпус

`gates.md` §12 теперь говорит: ID — `CLASS-NUMBER[LETTER]`, два разных carrier под одним ID
запрещены, allocator выдаёт следующий номер; второй critic, revision и повторный круг берут
свой следующий номер, а буква резервируется за дроблением milestone на части
(`.claude/rules/gates.md:400-409`). Это меняет будущую конвенцию, но не требует
переписывать корпус.

Если смотреть старым, letter-blind замером, "множественность несут 9 номеров"; это уже не
ключ решения Б. Под текущим letter-aware ключом `M-38` и `M-60` перестают быть
множественностями по построению, а §4.1 оставляет семь существующих file-множественностей
как предсуществующие факты вне проверяемого диапазона
(`milestones/M-61-artifact-ids.md:80-95`, `milestones/M-61-artifact-ids.md:252-270`).
Новый старостильный "второй критик под тем же ID" будет красным не потому, что законное
сломали, а потому что founder decision запретил такую множественность вперёд.

### 5. §7 — список "чего milestone НЕ делает" честен

Пункт 0 честно называет silent ignore: имя в зоне carrier, не разбираемое `id_of`,
игнорируется молча, и это не спрятано как "зелёный успех"
(`milestones/M-61-artifact-ids.md:644-658`). Важна и причина: fail-closed на этом месте
сегодня красил бы легитимные `CT-RFC`/`BACKLOG` формы, то есть ломал бы прод-форму.

Это не blocker, потому что §4.1 определяет идентификатор через грамматику
`CLASS-NUMBER[LETTER]`, а не через любое похожее имя. Цена ограничения названа: двухбуквенный
suffix / uppercase suffix вне предмета M-61 и потребуют отдельного изменения grammar или
выноса этих файлов из зоны.

## R-063 NOTE-1

Пара "легитимный сценарий + мутант" достаточна.

`L1JSON` является легитимным сценарием оси 1: `.json`-спутник в `research/reports/` не
carrier, если рядом уже есть настоящий `R-070-*.md` carrier
(`scripts/tests/red_artifact_ids.sh:110`, `scripts/tests/red_artifact_ids.sh:521-535`).
`mdblind` снимает `.md` из `id_of` case-шаблонов и ровно поэтому должен упасть
(`scripts/tests/mk_ref_artifact_ids.sh:402-414`,
`scripts/tests/mk_ref_artifact_ids.sh:492`).

Исполнение mutant battery на этом же `52bec1b`:

```text
PASS  mdblind → exit=1, ось 1, уронил ровно объявленное: L1JSON
BATTERY: PASS (28/28)
exit=0
```

Это закрывает именно риск `R-063` NOTE-1: до пары снятие `.md` из реального барьера оставляло
все сценарии зелёными; после пары такой барьер красится на штатном `.json` companion.

## Non-blocking note

TD широкая, введение TD узкое. Код это проводит явно (`TD_HOLD_RE` против `TD_CANON_RE`,

убрать возможность узкого чтения §4.1 в будущем, это docs cleanup/TD, не revert и не
блокер для ветки `docs/M-61-md-binding`.
