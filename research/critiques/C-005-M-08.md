## Findings

### CRITICAL @ HIGH-confidence

**C1 — CT-RFC-02 touches T1 but omits required JSON Schema, fixtures, and CHANGELOG.**

- Evidence: `docs/05-contract-layer.md:48-51` requires an atomic contract-RFC containing
  generated JSON Schema, valid/invalid fixtures, CHANGELOG, and tests in the same PR.
- Evidence: `docs/fa/contracts.md:71-77` repeats the same requirement and says
  rationale-only/schema-only PRs are not reviewed.
- Evidence: `docs/rfc/CT-RFC-02-journal-provenance.md:107-115` itself lists generated
  JSON Schema, fixtures, and CHANGELOG as part of this atomic change.
- Evidence: `crates/contracts/Cargo.toml:10-15` has `serde`, `serde_json`, and `postcard`,
  but no `schemars`; `find . -maxdepth 5 ... schemas/fixtures/CHANGELOG` returned no
  CT-RFC-02 schema, fixtures, or changelog artifacts.
- Required fix: before dev dispatch, either complete the RFC package with generated
  schema, valid/invalid fixtures, CHANGELOG, and a CT-I-4 verify test, or do not land the
  `crates/contracts/**` T1 change in this milestone. Deferring CT-I-4 to an impl task is
  not acceptable for a T1-shape change because §4 explicitly requires it in the same RFC.

**C2 — Legacy no-header imputation is specified too broadly and can misclassify corrupt or foreign data as `OwnCapture`.**

- Evidence: `docs/rfc/CT-RFC-02-journal-provenance.md:81-84` says if parsing the first
  frame as `SegmentHeader` fails, the segment is treated as schema 1 with implied
  `OwnCapture`.
- Evidence: the only legacy RED case is a valid old-format segment
  (`crates/journal/tests/red_segments_epochs.rs:41-91`). There is no negative oracle for
  corrupt bytes, a headerless vendor import, a foreign old-format segment, or a malformed
  first frame.
- Why this blocks dev: the central risk of CT-RFC-02 is silent mixing of data epochs.
  A broad "header parse failed -> OwnCapture" rule is exactly a silent provenance
  assignment path. A dev can implement the RFC literally and classify a bad or foreign
  segment as our own capture.
- Required fix: make legacy imputation narrow and fail-closed. Acceptable shapes:
  add a magic/type discriminator for new segment headers and treat missing header as
  legacy only when the first frame strictly decodes as old `Event` and the segment matches
  the recognized pre-RFC legacy constraints; or keep a manifest/fingerprint for the
  existing 8.3 GB legacy segment. Add RED tests proving corrupt/foreign/headerless vendor
  segments error instead of receiving `own-legacy-pre-rfc02`.

### MAJOR

**M1 — E8 gap-statistics has no RED oracle.**

- Evidence: E8 promises `research/data-quality/gaps-<epoch>.json` and report linkage
  (`milestones/M-08-data-durability.md:51-53`).
- Evidence: Task 5 requires gap statistics as part of research-cli work
  (`milestones/M-08-data-durability.md:79`).
- Evidence: `crates/research-cli/tests/red_stream_grid.rs:138-185` covers bounded memory,
  and `:181-234` covers partial in-memory equivalence. It never asserts a gaps artifact,
  gap counts, or report-time requirement.
- Required fix: add a sacred RED test that builds a journal with intentional
  `ConnDown/ConnUp` and wall-clock gaps, runs the research path, and asserts a deterministic
  `research/data-quality/gaps-<epoch>.json` payload. Also add a verify check so reports
  cannot omit the gap artifact.

**M2 — E7 recorder bounded-RSS is not covered by a recorder-level oracle.**

- Evidence: E7 promises a bounded-RSS recorder oracle (`milestones/M-08-data-durability.md:51`).
- Evidence: Task 4 explicitly includes recorder bounded-RSS
  (`milestones/M-08-data-durability.md:78`).
- Evidence: the milestone says E7 is covered by writer-path tests plus VPS eyes-on
  (`milestones/M-08-data-durability.md:111-114`), but those tests exercise `Journal::open_with`
  and `append`; they do not run recorder receive/write loops, channel behavior, venue fan-in,
  heartbeat handling, or any recorder-owned buffers.
- Required fix: add a recorder-level bounded-memory RED with a fake `EventKind` producer and
  counting allocator or equivalent RSS recorder. If the team intentionally wants E7 to be
  eyes-on only, remove it from RED/Task 4 acceptance and state that tradeoff explicitly.

**M3 — `red_stream_grid` equivalence is incomplete.**

- Evidence: `crates/research-cli/tests/red_stream_grid.rs:223-234` compares `params_hash`,
  `intents`, `fills`, `net_pnl_e8`, `turnover_e8`, and only the length of `returns`.
- Missing: return values, `sharpe`, `max_drawdown_e8`, `params`, and ledger side effects.
  A streamed implementation can alter the return series values, Sharpe, drawdown, or ledger
  records while still passing this equivalence oracle.
- Required fix: compare the full `CellResult` semantics: exact `returns` vector,
  `sharpe` within a named tolerance or exact deterministic value, `max_drawdown_e8`,
  `params`, and the ledger records/count/content written by both paths.

**M4 — Disk fail-closed oracle is useful but too easy to satisfy and misses the promised `Sys`/alert behavior.**

- Evidence: E4 requires alert + halt with explicit `Sys` event
  (`milestones/M-08-data-durability.md:48`).
- Evidence: Task 3 repeats `halt + Sys-событие + алерт`
  (`milestones/M-08-data-durability.md:77`).
- Evidence: the RED test only sets `min_free_bytes = u64::MAX` and asserts `append` returns
  `Err` (`crates/journal/tests/red_retention.rs:53-60`), then checks `free_bytes` is not a
  trivial stub (`:69-79`).
- Required fix: strengthen the oracle by using `free_bytes(dir) + 1` instead of only
  `u64::MAX`, asserting a specific storage-guard error, proving no event/frame/seq advance
  occurred after the failed append, and verifying the promised alert/`Sys` observable or
  removing that promise from E4/Task 3.

**M5 — `verify_M-08.sh` is a real gate, but it has false-positive/weak structural checks.**

- Evidence: the script has `set -euo pipefail`, an explicit failure aggregator, final verdict,
  and exit 1 on failures (`scripts/verify_M-08.sh:1-72`).
- Evidence: actual run returned `VERDICT: FAIL (9 провалов)`, `exit=1`.
- Evidence: `T11a` failed on a comment in `crates/journal/src/segments.rs:7`, not on a
  production hardcoded segment path. The grep is declared as "prod-path" but includes prose
  comments (`scripts/verify_M-08.sh:59`).
- Evidence: `T12` only greps for `needs: ci` anywhere in the YAML
  (`scripts/verify_M-08.sh:65`), which a comment or unrelated job could satisfy.
- Required fix: narrow `T11a` to real production constants/usages, not comments; parse
  `.github/workflows/deploy.yml` structurally enough to assert `jobs.deploy.needs` includes
  `ci`; add CT-I-4 schema/fixture checks from C1.

**M6 — Deploy is gated on CI, but the deploy script itself is not fully fail-closed.**

- Evidence: `deploy` has `needs: ci` (`.github/workflows/deploy.yml:57-60`), and the `ci`
  job blocks on non-success or timeout (`.github/workflows/deploy.yml:39-55`).
- Evidence: `workflow_dispatch` remains enabled (`.github/workflows/deploy.yml:12-22`), but
  manual runs still pass through the same `deploy.needs: ci` edge. I do not treat this as a
  CI-bypass by itself.
- Evidence: the SSH script uses `set -uo pipefail`, not `set -e`
  (`.github/workflows/deploy.yml:70-74`). If `git fetch` or `git reset` fails, the script can
  continue and run Docker against a stale VPS checkout.
- Required fix: use `set -euo pipefail` in the SSH script and split the fetch/reset commands
  so any failed checkout update aborts before `docker compose up`.

### MINOR / NOTES
