## §2 — Свои мутации и найденная слепая зона

Помимо четырёх заявленных, внесена **пятая мутация**: `snap.series.cvd_session_base.clear()`
в `snapshot_msg` (WS-путь), т.е. точно та же техника, что мутация 1, но на другом поле
`SeriesBundle`.

**Результат: ВСЕ 11 тестов M-46 остались GREEN.** На первый взгляд — пробитая слепая зона.
Проверено глубже (debug-print + чтение `crates/gateway/src/lib.rs:979-987`):

```rust
for (sid, session) in self.cvd {
    if session.base != 0 {                      // ← условие публикации
        cvd_session_base.push((sid, session.base));
    }
    ...
}
```

`cvd_session_base` заполняется ТОЛЬКО когда `session.base != 0` — а `base` становится
ненулевым ТОЛЬКО после эвикции внутрисессионных бакетов под `window_ms`. Замер (debug-print
на смешанной фикстуре O-1/O-2): `cvd_session_base.len() == 0` уже ДО моей мутации — очистка
пустого вектора ничего не меняет, отсюда ложное «прошло».

**Настоящая находка не в этом факте, а в том, что он вскрывает структурно:**

- Единственный оракул, делающий **поэлементное сравнение WS==реплей по `cvd_session_base`**
  (assert на строке `red_ws_series_vs_replay.rs:333`), — это O-2. У O-2 ДВЕ фикстуры:
  смешанная (`window_ms: None`) и пустой журнал. **Ни одна не использует `window_ms: Some(...)`**,
  значит `session.base` НИКОГДА не становится ненулевым ни в одной из фикстур O-2 — сравнение
  технически присутствует в коде теста, но математически сравнивает `[] == []` всегда.
- Тест, который РЕАЛЬНО включает `window_ms: Some(5_000)` и достаточно данных для эвикции
  (`o5_bounded_window_shrinks_ws_payload`), проверяет ТОЛЬКО `ohlcv.len()` — не сверяется
  ни с реплеем, ни с `cvd_session_base` вообще.
- **Вывод: если WS-транспорт (не библиотека — конкретно `snapshot_msg`/push-цикл) начнёт
  терять/искажать `cvd_session_base` ИМЕННО в windowed-режиме (прод всегда в windowed-режиме:
  `GATEWAY_WINDOW_MS=60000`), ни один из семи оракулов M-46 этого не заметит.** Библиотечный
  уровень защищён (`red_gateway_window.rs::cvd_base_survives_window_eviction` в `crates/gateway/
  tests/`), но это проверяет ПРАВИЛЬНОСТЬ РЕДЬЮСЕРА, не то, что WS-обёртка честно передаёт
  результат наружу — а именно это и есть предмет M-46 (граница «библиотека → провод»,
  `gateway-ws-contract.md` §6, последний абзац).

**Соразмерность.** Это НЕ дыра калибра «WS отдаёт неверные данные о деньгах» — `cvd_session_base`
служебное поле (сам milestone его так помечает в таблице §2), не визуализируется напрямую.
Но CVD — визуализируемая серия, и `cvd_session_base` — её internal state для правильного
continuation при повторном подключении/резюме. Транспортный баг здесь дал бы неверный CVD
после реконнекта в windowed-режиме на длинной прод-сессии — тихо, без сигнала.

Также попробовано (без эффекта / не воспроизвело новых слепых зон):
- реордер элементов внутри `depth_series`/`heatmap` — ловится `assert_eq!` на `Vec` (порядок
  учитывается), O-2 краснеет;
- аналогичная точечная порча `vp_session_max_time_s` (та же техника) — НЕ слепая зона: это
  поле ненулевое уже на смешанной фикстуре без окна (посессионное, не оконное), O-2 реально
  сравнивает непустые значения и поймал бы порчу.

## §4 — `verify_M-46.sh`

- Никакого `cmd && echo PASS || echo FAIL` — везде `if cmd; then pass; else fail; fi` с
  агрегирующим счётчиком `FAILS` и `exit 1` при `FAILS>0`. Соответствует `gates.md` §3.
- `set -uo pipefail` (без `-e`) — осознанно, чтобы скрипт продолжал после первого FAIL и
  собрал ПОЛНЫЙ список нарушений, а не остановился на первом. Это ДОПУСТИМАЯ альтернатива
  по `gates.md` §3 («ИЛИ явный агрегатор с FAIL-счётчиком»).
- T8/T9 лично прогнаны и красные СЕЙЧАС ПО СУЩЕСТВУ (бинаря `wsprobe` физически нет —
  `ls crates/gateway-serve/src/bin/` → каталога нет), не по опечатке скрипта.
- **Найдено расхождение с CI (парity, `gates.md` §3, «урок M-45 T2b»):** `ci.yml` гоняет
  `cargo clippy --all-targets --all-features -- -D warnings`; `verify_M-46.sh` T2 —
  `cargo clippy --workspace --all-targets -- -D warnings` (БЕЗ `--all-features`). Проверено:
  `grep -rn "^\[features\]"` по всем `Cargo.toml` в `crates/` → пусто, в проекте СЕЙЧАС нет
  ни одного объявленного feature-флага, поэтому флаг сейчас не даёт разницы. Это NOTE, не
  REJECT: расхождение текстуальное, не функциональное, ПОКА в workspace нет фич.
- **Найдено:** `verify_M-46.sh` не гоняет `cargo test --workspace`/`--all` (в отличие от
  `ci.yml`) — только `cargo build --workspace` (T1, компиляция) + три ТОЧЕЧНЫХ файла тестов
  (T3/T5/T6). Если реализация задачи 1 (`wsprobe`/правки `gateway-serve/src/**`) случайно
  зарегрессирует один из 5 УЖЕ СУЩЕСТВУЮЩИХ sacred-тестов (`red_jwt_verify.rs`,
  `red_serve_passthrough.rs`, `red_serve_window_wiring.rs`, `red_serve_consumes_checkpoint.rs`,
  `red_timeframe_guard_startup.rs`) или `smoke_ws.rs`, `verify_M-46.sh` этого НЕ увидит —
  только последующий `cargo test --workspace` reviewer'а (`testing.md`, обязателен «перед
  PR-time») или CI поймает. Backstop есть, но не в ЭТОМ гейте, вопреки заявленной цели
  «паритет с CI». NOTE, не REJECT (backstop существует и обязателен по процессу).

## §5 — Чего в наборе нет (по чек-листу из инвокации)

| Кандидат | Обязателен для M-46? | Комментарий |
|---|---|---|
| Slow-consumer (клиент не читает) | Нет | Push-цикл на `select!` шлёт `sink.send(...).await` внутри своей же таски — блокировка ждёт именно ЭТОГО клиента, не глобальная (по одной таске на соединение, без общего состояния). Заслуживает отдельного milestone/TD-заметки об операторском поведении при зависшем клиенте (накопление незакрытых task), но не входит в периметр «read-path корректен по данным» — это про ресурсы/DoS, не про правильность серий. |
| Одновременные подключения | Нет для ЭТОГО milestone'а | Явно упомянуто как открытый вопрос в `gateway-ws-contract.md` §10.5 (TD-044 в разборе). Ни один оракул M-46 не проверяет 2+ клиентов. Соразмерно оставить вне периметра — M-46 про корректность ОДНОГО потока данных, не про многопользовательскую ёмкость. |
| Рост журнала во время снапшота | Частично закрыто | O-3 буквально это и делает: журнал дописывается ПОСЛЕ подключения (`append_more` во время открытой сессии), push-цикл обязан догнать. Это ближайший аналог. |
| `Selector` с несколькими `bands` | Нет | Все фикстуры M-46 используют `bands: vec![0.001]` (одна полоса). Библиотечный уровень (`red_heatmap.rs`, `red_gateway_export_v2.rs` и т.д.) покрывает множественные полосы отдельно; для ТРАНСПОРТНОГО сравнения WS==реплей многополосный случай не проверен, но раз сравнение поэлементное и общее (не завязано на число полос), риск невысок. NOTE, не блокер. |
| Символ/venue, отсутствующие в журнале | Нет | Не проверено по WS explicit, но `GATEWAY_VENUE`/`GATEWAY_SYMBOL` — конфиг сервера (один процесс = одна пара), несовпадающий журнал дал бы пустые серии — вырожденный случай O-1's «пусто с причиной», низкий риск. |
| Очень большой `Frame`/`Snapshot` (байтовый размер) | Не покрыто, отмечено как открытый вопрос уже в `gateway-ws-contract.md` §10.3 | Сервер вызывает `accept_hdr_async(stream, callback)` БЕЗ явного `WebSocketConfig` (`grep` подтвердил — ни `max_message_size`, ни `WebSocketConfig` в `gateway-serve/src/lib.rs`), значит действуют дефолты `tungstenite` (обычно десятки MiB). Прод сейчас (`heatmap len=1697`) далёк от этого лимита, но задача 5 (sidecar) — единственное место, где это реально проверится не-игрушечным журналом. NOTE для architect'а: явно включить это в чек-лист задачи 5 close-out. |

Ничего из перечисленного не квалифицируется как REJECT-уровневый пробел: это либо
намеренно вне периметра (multi-client, multi-band), либо уже частично покрыто (рост
журнала — O-3), либо отложено на sidecar-прогон задачи 5 (byte-size, прод-масштаб).

## §6 — Вердикт и соразмерность

**NOTE.**

Обоснование по критерию из инвокации («REJECT оправдан только если дефект пропустит в
прод реальную ошибку read-path»): ни одна личная мутация не прошла незамеченной там, где

единственная РЕАЛЬНАЯ дыра, но she бьёт по служебному полю, а не по видимой пользователю
цифре, и есть backstop на библиотечном уровне (`red_gateway_window.rs`). Это не «оракул
зелёный против сломанной реализации» read-path в смысле продуктового обещания — это
конкретный, узкий, называемый пробел транспортного слоя.

### Обязательный перечень для architect (mechanical appendix перед dev, не re-цикл критика)

1. Добавить в O-2 (или отдельным тестом того же файла) фикстуру с `window_ms: Some(...)`,
   достаточную для внутрисессионной эвикции (аналогично `o5_bounded_window_shrinks_ws_payload`,
   но со сверкой ПОЛНОГО `series` против `gateway::snapshot` с тем же `window_ms` в `Selector`),
   чтобы `cvd_session_base` реально сравнивался на непустом значении. Это закрывает находку §2.
2. (Опционально, не блокирует dev) Явно пометить в задаче 5 (sidecar-прогон), что
   close-out обязан включить фактический байтовый размер первого прод-`Snapshot` — уже
   отмечено как открытый вопрос в `gateway-ws-contract.md` §10.3, но не привязано к
   конкретной acceptance-строке задачи 5 в milestone-файле.
3. (Опционально, cosmetic) Синхронизировать `verify_M-46.sh` T2 с `ci.yml`
   (`--all-features`) — нулевой практический эффект сейчас (фич нет), но текстуальное
   расхождение имеет свойство накапливаться.

Ни один из пунктов не требует повторного цикла критика — architect может внести правку
№1 (единственную содержательную) механически и передать dev вместе с остальным набором,
либо явно принять риск (служебное поле, backstop на библиотечном уровне) и передать
