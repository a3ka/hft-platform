## Findings

### MAJOR

**M1 - R2 still does not pin lower-cursor failure or returned coverage monotonicity.**

Evidence:
- The current implementation still has the M-38b guard: if an existing checkpoint cursor `c` is greater than requested `upto`, `advance_to` returns `Err`: `crates/gateway/src/lib.rs:2163-2172`.
- The rev3 test intentionally discards the result of lower-cursor `advance_to`: `crates/gateway/tests/red_checkpoint_bootstrap_truncated.rs:595-603`.
- The same test only asserts unchanged checkpoint directory bytes: `crates/gateway/tests/red_checkpoint_bootstrap_truncated.rs:604-614`.
- The production binary treats `Ok(c)` as success and publishes `c.upto_seq` to `covered_through_seq`: `crates/gateway/src/bin/gateway-checkpoint.rs:266-300`.

Impact: an implementation can replace the current `Err` with `Ok(low)` and leave the checkpoint file unchanged. `advance_to_lower_cursor_does_not_regress_checkpoint` still passes, but `gateway-checkpoint --cursor=<low>` exits 0 and writes lower coverage. That is exactly the regression class the test message names at `crates/gateway/tests/red_checkpoint_bootstrap_truncated.rs:609-611`, but the oracle does not observe it.

Required fix: assert the lower-cursor call returns `Err` before checking the checkpoint fingerprint. Alternatively, if the intended contract is changed to allow `Ok(no-op)`, then assert the returned cursor is the already-covered high cursor and add a binary-level oracle that `covered_through_seq` never moves backward after a high checkpoint. The simpler and current-code-aligned fix is the C-033 version: `Err` plus no byte change.
