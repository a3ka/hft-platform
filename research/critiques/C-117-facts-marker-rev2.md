### F-12 · REJECT — стаб S16: MERGE_HEAD-проводка `check_facts_sha` не запиннена, а комментарий её ОБЕЩАЕТ

`scripts/verify_design_claims.sh:738` заявляет: механика переиспользована «включая
MERGE_HEAD внутри --merge-preview». Код (`:791` → `canonical_refs`, `:1026`) это делает,
но НИ ОДИН сценарий пробы не строит merge-состояние с маркером — S16 (только `HEAD`)
проходит 53/53. Радиус воспроизведён фикстурой: ветка, отставшая от main; на main —
маркированный план с ревизией X (только через сторону слияния); `git merge --no-commit
--no-ff` (состояние merge-preview: `merge-base --is-ancestor X HEAD` → rc=1):

```
честный барьер: exit=0  PASS [H-FACTS-SHA] проверено 1 — все ревизии входят в историю HEAD/MERGE_HEAD
стаб S16:       exit=1  FAIL [H-FACTS-SHA] plans/on-main.md: ... НЕ входит в историю HEAD (орфан/несмёрженная ветка)
```

Ложное красное — ровно класс «блокирует ВСЕ merge'и репозитория», которым `A-010` §H
мотивирует направление отказа; и ровно режим (`--merge-preview`), в котором джоб гоняет
предмет чаще всего. «Документ говорит, проба не проверяет» — тот же класс, что F-5.

**Условие снятия:** сценарий «маркер называет ревизию, входящую в историю ТОЛЬКО через
MERGE_HEAD» → у честного PASS, exit=0. Рецепт фикстуры: база → ветка → коммит X на main →
маркированный план с X на main → checkout ветки → `git -c user.name=… merge --no-commit
--no-ff main` → прогон барьера на каталоге. Идентичность в merge обязательна даже при
`--no-commit` (проверено: без неё rc=128).

### F-18 · CONCERNS — не-UTF-8 байт в голове: документ с ВАЛИДНЫМ маркером молча выпадает из ВСЕХ проверок

`_facts_head_scan:656` глотает `UnicodeDecodeError` → `(False, None)`; NOTE-проверка
(`:844`) глотает его же. Замер: план с валидным маркером в строке 1, байтом `0x96` в
строке 2 и мёртвой ссылкой:

```
D5: exit=0, 0 упоминаний файла — ни опт-ина, ни FAIL «НЕ распарсен», ни NOTE, ни setup-сигнала
```

Python декодирует чтение чанком: битый байт строки 2 валит итерацию до отдачи строки 1,
маркер не виден вовсе. Это «молчаливый даунгрейд» — класс, устранение которого эта ветка
объявила своим достижением (F-1, вторая половина), — воспроизводимый одним символом,
вставленным из cp1251-буфера. Направление опасное: тихое ложное зелёное.

**Условие снятия:** `except`-ветка для файла в plans-зоне не имеет права быть тихой —
минимум FAIL/NOTE «файл не читается как UTF-8, проверка маркера невозможна»; сценарий с
битым байтом в голове.

### F-21 · CONCERNS — refs-дизъюнкция запиннена только с MERGE_HEAD-стороны

H-FACTS-19 пиннит «ревизия через MERGE_HEAD → не FAIL», но в merge-состоянии дизъюнкция

приостановлен, маркер называет ревизию СТОРОНЫ ВЕТКИ (PR, который везёт и фактуру, и её
ревизию — живой кейс этой самой ветки):

```

стаб S21: exit=1 FAIL [H-FACTS-SHA] …plans/on-branch.md — ложное красное
```

предок объединения ↔ предок хотя бы одного ref'а, стаб СУЖАЕТ множество). Код честного
барьера корректен. Потому CONCERNS, не REJECT.

### F-23 · CONCERNS — байт вне UTF-8 в ТЕЛЕ файла: остаток молча не судится при зелёном H-FACTS-SHA

### F-24 · NOTE — chmod-000: полная тишина, и комментарий `_head_is_utf8` утверждает покрытие, которого нет

потому NOTE, не CONCERNS. Но комментарий обязан перестать утверждать несуществующее
покрытие: это микро-«изображение гейта» в одну строку.

**Условие снятия:** либо OSError → тот же FAIL-исход, что нечитаемая голова, либо
