### Phase 3 — Oracle Integrity

REJECT. Two promised invariants are not pinned by RED:

#### B1 — Missing RED for `next.first_seq == 0` fail-open in checkpoint coverage

`retention_plan` and `retention_execute` compute `last_seq` as `next.header.first_seq.saturating_sub(1)` (`crates/journal/src/segments.rs:1651`, `1832`). A declared legacy segment always gets synthetic `first_seq = 0` (`segments.rs:509-512`) and `declare_legacy` does not restrict `LegacySegmentDecl.file_name` to `segment-00000000.jrnl` (`segments.rs:697-705`; `contracts/src/lib.rs:56-64`).

That makes the bad shape reachable at the API/valid-manifest level: if a final candidate segment is followed by a declared legacy segment at a higher index, `last_seq` becomes `0`, so `covered_through_seq = 0` is accepted as covered and the predecessor can be pruned while it still contains events with `seq > 0`. This violates C-030 R1 in the fail-open direction.

Architect's rationale that "legacy exists only at index 0, so it has no predecessor" is historically true for the old prod writer, but it is not enforced by the contract or the code path being changed. M-40 explicitly references TD-030, and this is the exact `first_seq=0` trap already documented in `red_stream_from.rs`.

Required repair: add a RED in the M-40 set (or explicitly narrow/enforce the contract) that constructs a declared legacy segment as the next visible segment after a prunable candidate and proves `covered=0` does not put the predecessor in `offload_and_prune`. The fixture must assert the legacy segment is real (`schema_version == SCHEMA_VERSION_PRE_HEADER`, `header.first_seq == 0`) so it cannot regress into the old C-030 placebo class.

#### B2 — Task #4 promises `retention_execute` same-enumerator behavior, but `rt_z_4` only tests a healthy catalog

The milestone task says `retention_execute` must use the same enumeration as `retention_plan` because current `segments(_dir).unwrap_or_default()` collapses coverage audit when one foreign/corrupt file is present. The committed `rt_z_4_apply_offloads_and_prunes_compacted_segments` runs Apply on healthy `.zst` only. It does not add a foreign/corrupt segment and does not prove that `pruned_without_checkpoint_coverage` remains truthful under that degraded directory.

Impact: an implementation can fix R2/R2b and still leave `segments(_dir).unwrap_or_default()` at `segments.rs:1825`; current M-40 tests would not necessarily catch the operator-audit lie called out by task #4. This is the same class as "oracle green for a reason other than the named invariant".

Required repair: extend `rt_z_4` or add a new RED with one bogus/foreign segment in the directory, full checkpoint coverage, and at least one healthy `.zst` pruned. Assert `failed` is empty for healthy candidates, `pruned`/`freed_bytes` are truthful, and `pruned_without_checkpoint_coverage` is empty. That directly pins the `unwrap_or_default()` defect.

#### N1 — `rt_z_7` should bind `offload_only` to the listed `.zst` candidates

`rt_z_7` runs the real binary, which is the right observation point. Its assertions are weaker than its text: it separately checks `stdout.contains(".jrnl.zst")` and `stdout.contains("offload_only")`. A future output that prints `.zst` only under `skipped` and an empty/count-only `offload_only` header can satisfy those substrings without proving that offload-only candidates are named in their own bucket.

This is advisory because B1/B2 already block dispatch. Recommended repair: parse or section-check stdout so at least one `segment-*.jrnl.zst` appears under the `offload_only` section in the no-checkpoint dry-run case.
