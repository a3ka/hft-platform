## 1. Главный вопрос — закрывает ли D-1 атаку C-049? Да, для futures-крейта. Обходимость O-8 не найдена.

### 1.1 Обход (A) из C-049 закрыт структурно, не только текстом

C-049 §1.2(A) — внешний `if symbol == "BTCUSDT" { l2delta_emission_for(...) }` ПЕРЕД вызовом
решающей функции. Прочитан весь путь `run()` → `on_ws_text` → `apply_session_effect`:

```
crates/venue-binance-futures/src/lib.rs:1102   for eff in session.on_ws_text(&text) {
crates/venue-binance-futures/src/lib.rs:1166       SessionEffect::Emit(md) => tx.send(EventKind::Md(md)).await.is_ok(),
```

`apply_session_effect` пересылает `Emit` в `tx` **безусловно**, без повторной фильтрации по
символу. Значит единственное место, где может жить хардкод-гейт на пути к журналу, —
**внутри `on_ws_text`**, до `effects.push(SessionEffect::Emit(md))`. O-8 зовёт именно
`on_ws_text` с реальным wire-текстом и считает `Emit`-эффекты — гейту в принципе негде
спрятаться ВНЕ зоны видимости оракула на этом пути. Это отличается от C-048/C-049, где
оракулы дёргали `l2delta_emission_for`/`l2delta_event` напрямую, а реальный обработчик
никогда не вызывался ни одним тестом.

### 1.2 Проверено, что O-8 не проходит против «параметр есть, но игнорируется»

Отдельный класс обхода, не разобранный явно в C-049, но естественный следующий шаг:
`new_with_l2delta(subs, l2delta_allow)` мог бы **игнорировать** `l2delta_allow` и держать
хардкод внутри себя. Чтобы проверить это эмпирически (не умозрительно), я временно
подставил заглушки прямо в `src/lib.rs` worktree'а (НЕ коммит):

```rust
pub fn new_with_l2delta(subs: &[String], _l2delta_allow: &[String]) -> Self {
    Self::new(subs)  // параметр демонстративно игнорируется
}
```

Результат `cargo test -p venue-binance-futures --test red_l2delta_allowlist o8_`:


4 из 6 тестов (`o8_allowed_symbol_...`, `o8_lowercase_config_...`,
`o8_multiple_allowed_symbols_...`, `o8_emitted_payload_is_intact_...`) красные именно
потому, что игнорирование параметра расходится с ожидаемым поведением — O-8 ловит и этот
класс обхода, не только (A). Изменения отменены (`git checkout --
crates/venue-binance-futures/src/lib.rs`), рабочее дерево чистое (см. Done Block).

### 1.3 Единственный оставшийся необслуженный уровень — сама точка вызова `new_with_l2delta` в `run()` (env-wiring)

`run()` сегодня зовёт `FuturesSession::new(&symbols)` (без allow-list). После задачи #3b он
обязан звать `FuturesSession::new_with_l2delta(&symbols, &parse_capture_symbols(env::var(...).ok().as_deref()))`.
Теоретически возможен обход: `new_with_l2delta(&symbols, &["BTCUSDT".to_string()])` —
литерал прямо в вызове `run()`, минуя env. O-8 этого не поймает — он конструирует
`FuturesSession` напрямую в тесте, а не через `run()`.

Это ровно тот остаточный класс, который сам milestone-документ уже называл ДО C-048/C-049 и
сознательно оставил на глаза: «Чтение `env` схлопывается в однострочную обёртку на самом
верху (`connect`/`main`), проверяемую глазами» (§ «Разбор обязан быть чистой функцией»).
Раньше это было рискованно, потому что весь путь решения (branch по символу, конструкция
`symbols`) был размазан по многострочному обработчику с несколькими ветвями — теперь после
D-1 он сведён **ровно к одному вызову конструктора в `run()`**, синтаксически заметному:
`FuturesSession::new_with_l2delta(&symbols, &parse_capture_symbols(...))` vs
`FuturesSession::new_with_l2delta(&symbols, &["BTCUSDT".to_string()])` — разница в одну
подстроку на одной строке, ровно то, что reviewer способен поймать глазами при
Contract Block-scope/Done Block чтении диффа (`gates.md` §4). Соразмерно: дальше
ужесточать оракулом (интеграционный тест, реально спавнящий `run()` с моком WS и
проверкой env) — цена несоразмерна остатку риска для ОДНОЙ строки на самом верху функции,
которая уже была явно принятым остаточным классом до этого раунда. **Здесь — NOTE, не
REJECT**: reviewer обязан явно свериться с этой строкой в Done Block/диффе на PR-гейте.

## 3. Q2 — фикстура O-8 верна (только futures; спот — не применимо, оракула нет)

Сверено `ws_depth_text()` с `parse_depth_diff` (`crates/venue-binance-futures/src/lib.rs:882-905`):

| Поле фикстуры | `parse_depth_diff` читает | Совпадает |
|---|---|---|
| `stream = "{sym}@depth@100ms"` | диспетчер `stream.contains("@depth")` (`:635`) | да |
| `data.s` (upper) | `data.get("s")` (fallback — `stream.split('@')`) | да |
| `data.pu` (число) | `data.get("pu")?.as_u64()` — обязателен для futures | да |
| `data.U`/`data.u` (число) | `data.get("U")?.as_u64()`/`data.get("u")?.as_u64()` | да |
| `data.b`/`data.a` (`[["цена","размер"], …]`, строки) | `parse_diff_levels` — `as_str().parse()` | да |
| `data.E` | `data.get("E")...unwrap_or(0)` — необязательное | да |

Фикстура — той же формы, что реальный прод-парсер `venue-binance-futures`. RED, если
случится, будет по существу (отсутствие `new_with_l2delta`/делегирования), не по ложному
setup-провалу (класс `det_22` не воспроизведён).

**Отдельно проверен ложный сигнал компилятора, чтобы не спутать его с багом оракула.**
Сырой `cargo test` на текущем (нереализованном) коде даёт, среди прочего:
```
error[E0614]: type `u64` cannot be dereferenced
  --> .../red_l2delta_allowlist.rs:440:17
```
на `*first_update_id`/`*final_update_id` внутри `o8_emitted_payload_is_intact_...`. На
первый взгляд похоже на баг теста (несовпадение типов при `let ... = &md.payload else`).
Проверено эмпирически (compile-isolation проба §1.2, с застабленными недостающими
символами): после того, как остальные символы файла становятся разрешимыми, тест
**компилируется чисто**, `E0614` пропадает — это была каскадная ошибка typeck от
нерешённых имён выше по файлу (стандартное поведение rustc при множественных E0425 в одном
модуле), не самостоятельный дефект оракула. Не блокирует.
