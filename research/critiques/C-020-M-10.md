## Почему KILL сигнала принят (и почему дефекты его не воскрешают)

Пре-рег критерий фальсификации (`H-20260710`: «Net Sharpe ≤ 0.5 OOS → мёртв») сработал с
огромным запасом и подтверждён по НЕСКОЛЬКИМ независимым срезам:

- `oos_sharpe = −2.554` (best OOS-ячейка);
- **276/276** испытаний текущей эпохи ≤ 0 (max Sharpe семейства = **0.000**, ни одной
  положительной ячейки);
- walk-forward: **21/21** окон отрицательны (−1.33 … −15.55) — режима, где работает, нет;
- decay отрицателен на всех горизонтах (500/1000/2000/5000 мс);
- stress (×1.5 издержки, ×2 латентность) — глубоко отрицателен.

Все обнаруженные дефекты стека (ниже) либо занижают, либо завышают метрику, но **ни один не
способен превратить сигнал, отрицательный по всем 276 ячейкам/всем окнам/всем горизонтам, в
живой**. Направление стресса (латентность×2 → сильно ХУЖЕ) согласуется с механизмом из
H-карточки («edge быстро выедается издержками на мс-горизонте»), что говорит против
гипотезы «баг перевернул знак PnL». Поэтому KILL безопасно фиксируется как отрицательный
результат; повторный прогон ради переподтверждения Kill не требуется (экономия compute).

**Оговорка честности:** KILL принимается как «сигнал НЕ жизнеспособен на этих данных при
этих издержках», а НЕ как точное измерение PnL/Sharpe. Абсолютные величины отчёта
(см. B ниже) нефизичны и в решении не используются.

## A. ГЛАВНАЯ находка — KS-I-1 (ЯДРО M-10) фактически defeated (HIGH)

`report.rs::sharpe_se`:
```rust
fn sharpe_se(returns: &[f64], sharpe: f64) -> f64 {
    let observations = returns.len().max(1) as f64;         // ← ЧИСЛО ШАГОВЫХ доходностей
    (PERIODS_PER_YEAR / observations * (1.0 + 0.5 * sharpe * sharpe)).sqrt()
}
```
`se_sharpe` считается от **количества пошаговых доходностей** OOS-прогона (`returns.len()`),
а НЕ от **календарной длины окна**. На этом окне `returns.len() ≈ 1.45e4` шагов →
`se_sharpe = 0.272`.

Это прямо ПРОТИВОРЕЧИТ собственной посылке милестоуна (§Objective/KS-I-1): «SE годового Sharpe
≈ ±11 на 3–7 днях… на коротком окне se огромна → нижняя граница глубоко отрицательна → PASS
невозможен». Здесь окно = **0.353 дня**, а `se = 0.27` — **на ~1.5–2 порядка меньше** проектной
величины.

**Последствие (асимметричная цена ошибки):** гейт PASS в `classify_verdict` —
`sharpe − 2·se_sharpe > BAR(0.5)`. С `se = 0.27` порог PASS ≈ `sharpe > 1.04`. Любой сигнал с
годовым OOS-Sharpe > ~1.04 на 8-часовом окне (тривиально достижимо переобучением) получит
**ложный PASS** — ровно тот исход, который милестоун объявляет «АРХИТЕКТУРНО ЗАПРЕЩЁН». Здесь
ложный PASS не случился ТОЛЬКО потому, что `classify_verdict` раньше срабатывает на
`oos_sharpe ≤ 0.5 → Kill` (отрицательный Sharpe замаскировал сломанный se). На положительном
сигнале защита KS-I-1 не сработает.

**Почему RED это не поймал:** `red_killscreen.rs` тестирует КЛАССИФИКАТОР (даёт готовый
`se_sharpe` во входе → проверяет гейт), но НЕ пинит МАСШТАБ функции `sharpe_se`. Дефект живёт
в слепом пятне между «классификатор протестирован» и «se посчитан честно» — тот же класс, что
happy-path-фикстура из `.claude/rules/testing.md`. Это зона architect (RED-first), не моя и не
research-dev самоправкой.
