## Findings

### F-065-1 — BLOCKER — RED-проба пропускает range-wide/HEAD-only token реализацию

`milestones/M-60a-docs-freeze.md:23-25` требует, чтобы коммит, трогающий зону замка,
нёс `FOUNDER-APPROVED: <причина>` в **своём** теле. Но `scripts/tests/red_docs_freeze.sh`
проверяет только один порядок "чужого token": token в первом вне-зонном коммите, затем
locked-коммит без token (`scripts/tests/red_docs_freeze.sh:119-124`). Обратный порядок
не проверен: сначала locked-коммит без token, потом unrelated token-коммит. Также FR-9
проверяет только merge без token (`scripts/tests/red_docs_freeze.sh:146-153`), но не
side locked commit под merge commit с token.

Я написал временный barrier, который:

1. ищет locked path в `git diff <base>..HEAD`;
2. проверяет только body HEAD-коммита на `^FOUNDER-APPROVED: .{12,}`;
3. не проверяет каждый commit диапазона.

Этот barrier проходит текущую RED-пробу:

```text
$ BARRIER=/tmp/m60a-check-head-body-only.sh bash scripts/tests/red_docs_freeze.sh; echo red_exit=$?
── Замок процессного слоя (M-60 G0): 9 сценариев ──
барьер: /tmp/m60a-check-head-body-only.sh

PASS  FR-1 правка .claude/rules без токена заблокирована
PASS  FR-2 правка с разрешением founder'а проходит
PASS  FR-3 правка вне зоны замка не трогается
PASS  FR-4 токен с пустой причиной отвергнут
PASS  FR-5 токен действует только на свой коммит
PASS  FR-6 .claude/agents под замком
PASS  FR-7 docs/04-workflow.md под замком
PASS  FR-8 zero-SHA база: fail-closed
PASS  FR-8b пустая база: fail-closed
PASS  FR-9 merge не является лазейкой

VERDICT: PASS (10/10) — замок держит при ТОЙ ЖЕ проводке, какой его зовёт CI
red_exit=0
```

Но тот же barrier пропускает два locked-обхода:

```text
$ # locked commit without token, then unrelated docs commit with valid token
late_token_hole_exit=0

$ # side locked commit without token, then merge commit with valid token
f2872fd merge with token
bdf1714 side locked change without token
tokened_merge_hole_exit=0
```

Это не спор о forgeable founder-token. Это более низкий дефект: oracle не пиннит
собственный контракт "token в том же commit". Explicit residual-risk признание на
`milestones/M-60a-docs-freeze.md:70-72` достаточно для угрозы "любой committer может
солгать в body"; оно НЕ достаточно для пропуска реализации, которая даже не связывает
token с нужным commit.

Required fix: добавить RED-сценарии:

- locked commit без token → поздний unrelated commit с `FOUNDER-APPROVED` ⇒ FAIL;
- side locked commit без token → merge commit с `FOUNDER-APPROVED` ⇒ FAIL;
- deletion/rename locked path без same-commit token ⇒ FAIL, либо явно документировать
  fail-closed/blocked модель для merge deletion как у `check_protected_artifacts.sh`.

### F-065-2 — BLOCKER — W-парсер всё ещё принимает неподключённый workflow

M-60a заявляет закрытие `C-064` F-064-2 через разбор workflow вместо grep
(`milestones/M-60a-docs-freeze.md:67-68`, `scripts/verify_M-60a.sh:7-13`). Парсер стал
лучше, но всё ещё принимает две неподключённые формы.

Первая: `job_running()` принимает любую YAML-list строку с именем скрипта, потому что
условие включает `^\s+-\s` (`scripts/verify_M-60a.sh:92-94`). Поэтому строка
`- name: scripts/check_docs_freeze.sh` считается исполнением.

Raw reproduction:

```text
$ python3 <W-parser> /tmp/m60a-ci-name-only-*.yml
PASS  W scripts/check_docs_freeze.sh исполняется джобом(ами): docs-freeze
PASS  W scripts/tests/red_docs_freeze.sh исполняется джобом(ами): docs-freeze
PASS  W все джобы замка в status-check.needs: docs-freeze
exit=0
parser_exit=0
```

Вторая: при `if: always()` сам `needs:` не блокирует итоговый status-check; блокирует
только shell-условие, проверяющее `needs.<job>.result`. Текущий CI именно так устроен:
`status-check` имеет `if: always()` и затем вручную проверяет results
(`.github/workflows/ci.yml:128-136`). M-60a парсер проверяет наличие job id в body
`status-check`, но не проверяет, что shell-условие включает этот job result
(`scripts/verify_M-60a.sh:105-116`).

Raw reproduction с реальными `run:` строками и не-блокирующим `status-check`:

```text
$ python3 <W-parser> /tmp/m60a-ci-status-ok-*.yml
PASS  W scripts/check_docs_freeze.sh исполняется джобом(ами): docs-freeze
PASS  W scripts/tests/red_docs_freeze.sh исполняется джобом(ами): docs-freeze
PASS  W все джобы замка в status-check.needs: docs-freeze
status_check_body=    runs-on: ubuntu-latest     needs: [docs-freeze]     if: always()     steps:       - run: echo All checks passed
exit=0
parser_exit=0
```

Required fix: парсить YAML-структуру, а не строки. Проверять именно `steps[*].run`
для `bash scripts/check_docs_freeze.sh` и `bash scripts/tests/red_docs_freeze.sh`; `name:`
не должен считаться запуском. Для `status-check` либо убрать `if: always()` и требовать
required individual jobs, либо проверять, что итоговый shell condition содержит
`${{ needs.<job>.result }}` для каждого job замка.

### F-065-3 — MAJOR — зона замка молча пропускает live carrier процесса

Ядро зоны M-60a корректное: `.claude/rules/**`, `.claude/agents/**`, `CLAUDE.md`,
`docs/04-workflow.md` (`milestones/M-60a-docs-freeze.md:19-21`). `docs/DESIGN.md` и
`docs/fa/*` исключены правильно: это архитектура/safety-документы с маршрутом
`gates.md` §9, а не общий process-freeze.

Забытый процессный carrier: `.claude/wrappers/**`. В audited tree есть
`.claude/wrappers/dispatch-mandate.md` и `.claude/wrappers/pi-dev.sh`; `dispatch-mandate.md`
инжектится в pi-агентов как "обязательный контракт" (`.claude/wrappers/pi-dev.sh:117-126`),
а сам mandate содержит BINDING/STOP/push/Done Block правила (`.claude/wrappers/dispatch-mandate.md:1-59`).
M-60 umbrella уже признаёт carrier существующим и process-relevant
(`milestones/M-60-mechanisms.md:101-132`).

Это не обязательно должно расширять M-60a lock прямо сейчас: можно оставить wrappers в
deferred risk, если founder хочет узкий prose lock. Но сейчас M-60a не называет это
исключение в §5/§7, и будущий reader получит ложное ощущение, что весь процессный слой
закрыт.

Required fix: либо включить `.claude/wrappers/**` в lock zone, либо добавить явный
deferred-risk пункт: "process launcher/mandate carrier outside M-60a lock; covered by
future mechanism / founder decision".

## Answers To Requested Questions

1. **Зубы пробы.** Подтверждены: always-0 ⇒ `FAIL (8)`, always-1 ⇒ `FAIL (2)`, оба
   `exit=1`. Расхождения с заявленными 8/2 нет.
2. **Что проба не ловит.** Главный bypass — HEAD/range-wide token implementation:
   проба PASS, замок не работает для earlier locked commit, late unrelated token и
   tokened merge. Raw proof выше в F-065-1.
3. **F-064-6.** Явное признание "token = audit trace, not founder proof" достаточно
   только как residual risk против malicious committer. Не достаточно для M-60a gate:
   oracle обязан доказать same-commit binding, иначе dev может реализовать не тот lock.
4. **Зона замка.** Лишнего в core zone не вижу. `docs/DESIGN.md` и `docs/fa/*`
   исключены правильно. Забыто или должно быть явно deferred: `.claude/wrappers/**`.
5. **W parser.** Положительный контроль reproduced:
   `scripts/check_protected_artifacts.sh` и его probe найдены в `protected-artifacts`,
   `status-check.needs contains protected-artifacts: True`. Отрицательный контроль
   reproduced: `scripts/check_docs_freeze.sh: НЕ НАЙДЕН`. Третий случай: `name:`-only
   и non-blocking `status-check` оба дают false PASS.
6. **Самореференция.** Концептуально не circular: `milestones/M-60a-docs-freeze.md:46-47`
   ставит норму `gates.md` §11 после зелёных задач 1-2. Текущий audited diff ещё не
   содержит `.claude/rules/gates.md`, поэтому self-lock пока является acceptance intent,
   не выполненным фактом. После F-065-1/F-065-2 fixed S-step должен проверять same-commit
   token на commit, который добавит §11.
