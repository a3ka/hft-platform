## Verdict justification

## Findings

### R1 — RETENTION COUPLING IS MISSING; CHOOSE STRICT SKIP-REPORT SEMANTICS

**Severity:** MAJOR, blocks dev dispatch.

`docs/06` defines retention as governed movement, not silent deletion: old segments go COLD,
the journal remains immortal, and free-space pressure must not silently drop data
(`docs/06-data-layer-and-storage.md:60-72`). M-38b explicitly asks critic to decide the
checkpoint-retention coupling (`milestones/M-38b-checkpoint-reducer.md:245-249`), but the
committed tasks and verify gate do not enforce it:

- Allowed path for `crates/journal/src/segments.rs` is only `stream_from` + counters
  (`milestones/M-38b-checkpoint-reducer.md:150`).
- Existing retention `Apply` prunes every `plan.offload_and_prune` segment after cold-copy proof,
  with no checkpoint coverage condition (`crates/journal/src/segments.rs:1571-1582`).
- `verify_M-38b.sh` has no retention/checkpoint coverage test or grep canary
  (`scripts/verify_M-38b.sh:26-33`, `67-72`).

**Decision:** make the coupling strict at prune time, with an explicit skip report. A segment may
be pruned from HOT/WARM only if a checkpoint coverage artifact proves `checkpoint.cursor >=
segment.last_seq` for the configured gateway selector/epoch-filter envelope, and the checkpoint
validation semantics survive covered-prefix pruning. Otherwise retention must keep the local
segment and report `skipped_no_checkpoint_coverage` (or equivalent) in the retention report.

Why strict: without this, retention can remove the local prefix while gateway has no valid covered
state. Worse, M-38b's `journal_lineage` is specified as a hash over segment headers
(`milestones/M-38b-checkpoint-reducer.md:108-112`); pruning covered prefix segments changes the
visible header set unless a retained header manifest / suffix-lineage rule is designed. The
current plan does not define that interaction.

**Suggested fix:** add a RED that builds a checkpoint past a segment boundary, simulates covered
prefix pruning (or makes the prefix unreadable), and proves:

1. `snapshot_from_checkpoint` still returns the same bytes as full replay computed before pruning;
2. it decodes only the tail;
3. no old segment is opened;
4. if checkpoint coverage is absent, retention reports skip and does not prune.

If `journal` must not know selectors, put the coverage manifest/check in the `gateway-checkpoint`
ops path and have retention consume only a selector-agnostic "covered through seq" proof/report.
But the artifact set needs an executable rule before dev starts.

### R2 — `red_stream_from` LEGACY CASE IS A PLACEBO

**Severity:** MAJOR, blocks dev dispatch.

M-38b specifies that legacy segments with synthetic `first_seq == 0` must never be skipped
(`milestones/M-38b-checkpoint-reducer.md:116-119`). The RED file repeats this requirement
(`crates/journal/tests/red_stream_from.rs:16-23`), but the actual test named
`legacy_segment_is_never_skipped` creates a normal journal and asserts `legacy_count == 0`
(`crates/journal/tests/red_stream_from.rs:216-229`). It then checks ordinary v2 stream
completeness and only asserts that segment 0 has `first_seq == 0`
(`crates/journal/tests/red_stream_from.rs:231-245`).

An implementation that skips any segment with `header.first_seq <= after_seq` without checking
`schema_version` can still pass this test on the constructed fixture and fail on real legacy
segments. That is exactly the class the comments say the oracle must prevent.

**Suggested fix:** create an actual legacy/headerless fixture (using the existing legacy manifest
machinery or a committed historical fixture) and assert that `stream_from(..., Some(after))`
does not skip it. If constructing legacy in this test is impossible, remove the claim and make
the legacy behavior a separate explicit RED before dev dispatch.

### R3 — THE TWO CHECKPOINT FORCINGS ARE NOT SUFFICIENT AGAINST HIDDEN FULL REPLAY

**Severity:** MAJOR, blocks dev dispatch unless R1's prefix-prune RED is added.

The two stated forcings catch the most likely wrong implementation:

- `foreign_checkpoint_changes_output` proves a valid checkpoint is actually consumed
  (`crates/gateway/tests/red_checkpoint_byte_identity.rs:316-371`).
- `red_checkpoint_resource_bound` proves reported `ReadStats` are small near the tail and honest
  when no checkpoint exists (`crates/gateway/tests/red_checkpoint_resource_bound.rs:97-174`).

However, there is still a passing implementation that does not solve TD-044: load enough of the
checkpoint to perturb output for the foreign-checkpoint test, perform a full replay from START
for normal correctness/validation, and return tail-sized `ReadStats` collected from a separate
`stream_from` call. The current tests observe returned stats, not actual old-segment access.

This is not a request for wall-clock or allocator tests. The deterministic fix is the same as R1:
after checkpoint creation, make covered old segments unavailable in the test. Then hidden full
replay cannot pass while a real checkpoint+tail implementation still can.

### N1 — Reducer field list is complete, with one clarification needed

**Severity:** NOTE.

Actual `Reducer` fields are `selector`, `ohlcv`, `cvd`, `vwap`, `depth`, `vp`,
`session_max_time_s`, `book`, `heatmap_buckets`, `bubbles`, `at_ms`
(`crates/gateway/src/lib.rs:501-532`). The milestone lists every mutable state field
(`milestones/M-38b-checkpoint-reducer.md:36-48`).

`selector` is not a state field if the checkpoint header stores `selector_fingerprint` and
`snapshot_from_checkpoint` reconstructs the reducer with the caller-provided selector after
fingerprint validation (`milestones/M-38b-checkpoint-reducer.md:54-55`, `102-106`). Clarify this
explicitly so dev does not serialize a stale selector copy by accident while thinking the table
omitted a field.

### N2 — `journal_lineage` is correctly narrow for compaction, but incomplete for pruning

**Severity:** NOTE, tied to R1.

For compaction alone, the proposed lineage tuple `(index, epoch_id, source, first_seq)` is not too
wide: it intentionally excludes `created_wall_ms` and file size, which change under `.jrnl ->
.jrnl.zst` compaction while the events remain identical
(`milestones/M-38b-checkpoint-reducer.md:108-112`). The residual risk that lineage is not a
content hash is named honestly (`milestones/M-38b-checkpoint-reducer.md:212-215`), and the
foreign-checkpoint test deliberately exercises that trust envelope.

The unresolved part is not compaction; it is local prefix pruning. Once retention removes covered
segments, a lineage over "currently visible segment headers" is no longer the same input. R1 must
define whether lineage is suffix-only, backed by a retained covered-prefix manifest, or guarded by
strict skip-report retention.

## Direct answers to architect's four checks

1. **Forcing sufficiency:** not sufficient as committed. It catches ordinary checkpoint-ignore and
   `stream().filter` implementations, but a hidden full replay plus fake tail stats can still pass.
   Add a prefix-pruned/unreadable-history RED.
2. **Reducer state fields:** no mutable state field is missing. `selector` is config, covered by
   fingerprint, but the milestone should say that explicitly.
3. **Retention coupling:** strict. No local prune without checkpoint coverage through the pruned
   segment's last seq, or explicit skip report with no prune. Current artifacts do not enforce this.
4. **`journal_lineage`:** not too broad for compaction and the residual content-substitution risk is
   honestly named. It needs pruning semantics before this plan is dispatchable.

## Required revision before re-critic

1. Add checkpoint-retention RED coverage and update M-38b tasks/allowed paths/verify accordingly.
2. Replace the placebo legacy `stream_from` test with an actual legacy/headerless fixture test.
3. Add the prefix-pruned or unreadable-history checkpoint test to close hidden full replay.
4. Clarify `selector` is not serialized state; it is validated by fingerprint and supplied by caller.

After those artifact changes are committed, re-dispatch critic. Do not dispatch `engine-dev` yet.
