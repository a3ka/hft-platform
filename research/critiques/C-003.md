# C-003 — Contract-RFC Gate — CT-RFC-01 market-data expansion

**Date:** 2026-07-11
**RFC:** `docs/contract-rfc/CT-RFC-01-market-data-expansion.md`
**Gate:** `.claude/rules/gates.md` §1.1 / §5, `docs/05-contract-layer.md` §4
**Scope:** RFC-document review only. `crates/contracts/**` was not modified.

## Verdict

**PASS**

## Verdict Justification

CT-RFC-01 satisfies the contract-RFC gate for an additive market-data expansion.
The proposed `Venue` and `MdPayload` variants are appended after the existing
variants, the fixture requirements cover old-journal compatibility and new-form
roundtrip, the exhaustive-match blast radius is explicit enough for M-06 dev work,
and the journal-first decision keeps derived analytics out of T1.

## Checks

### 1. Additivity / postcard compatibility

PASS. Current code has `Venue = [Binance, Hyperliquid]` at
`crates/contracts/src/lib.rs:46-49` and `MdPayload = [Trade, L2Snapshot, Funding]`
at `crates/contracts/src/lib.rs:78-94`. The RFC appends `BinanceFutures` after
`Hyperliquid` and appends `OpenInterest`, `Liquidation`, `MarginRate` after
`Funding` (`CT-RFC-01:23-53`). That preserves old postcard discriminants:
`Venue` old indexes 0..1 and `MdPayload` old indexes 0..2 remain unchanged.

### 2. CT fixture sufficiency

PASS. The required fixture set is sufficient for this RFC class:

- old pre-change segment roundtrip for `Trade` / `L2Snapshot` / `Funding`
- new-variant serde + postcard roundtrip for all three new payloads plus
  `Venue::BinanceFutures`
- single-definition canary for `enum MdPayload` and `enum Venue`

This directly covers CT-I-1 and CT-I-3, and the new-variant roundtrip is enough
for the additive wire-form claim. Important implementation constraint: the
old-fixture must be committed as static bytes produced before the enum change,
not generated by the post-change code.

### 3. Blast radius / M-06 ownership

PASS. The RFC correctly assigns consumer updates to M-06 dev work, not to the
architect-side contract landing (`CT-RFC-01:83-97`). Static scan confirms the
listed exhaustive or behavior-relevant sites cover the current surface:

- `crates/sim/src/exchange.rs:223-276` exhaustively matches `MdPayload`.
- `crates/research-cli/src/bin/latency_probe.rs:34-38` exhaustively matches
  `Venue`, and `:107-111` exhaustively matches `MdPayload`.
- `crates/book/src/lib.rs:190-197` and `crates/signals/src/obi.rs:84-87`
  currently ignore non-L2 payloads and are correctly named for explicit
  ignore-arm cleanup.
- journal/book examples are included in the RFC's `examples` bucket.
- tests are correctly left to architect together with CT fixtures.

M-06 must make those ignore arms explicit, not broad wildcard sinks, especially
for `OpenInterest`, `Liquidation`, and `MarginRate`.

### 4. Journal-first derivations

PASS. Keeping funding-breadth, CVD, and basis out of T1 is the right boundary.
The platform's design says the journal is the raw event stream and downstream
state is a deterministic function of that stream. `Funding` already exists as
per-symbol T1; trades already carry side/price/size for CVD; basis can be derived
from spot/futures raw market data. Promoting those derived analytics to T1 now
would mix strategy/research outputs into the wire-format layer.

### 5. `SCHEMA_VERSION` 0 -> 1

PASS. `docs/05-contract-layer.md:48-56` requires a schema-version bump for T1
shape changes, and this is the first additive journal schema expansion after
`SCHEMA_VERSION = 0` (`crates/contracts/src/lib.rs:13-14`). The bump does not
endanger old segment decoding because old enum discriminants remain fixed.

### 6. `HyperliquidPerp` omission

PASS. Do not add `HyperliquidPerp` in this RFC. Current Hyperliquid adapter emits
`Venue::Hyperliquid` for perp `l2Book`/`trades`; adding `HyperliquidPerp` would
create a duplicate semantic venue or force a rename. The RFC's choice preserves
additive compatibility and leaves `HyperliquidSpot` as the future additive
variant if that market is actually needed.

## Non-blocking Notes

- The RFC headings cite `contracts/src/lib.rs`; the real path is
  `crates/contracts/src/lib.rs`. This is documentation hygiene, not a gate
  failure because the same RFC later correctly names `crates/contracts`.
- `Liquidation.side` is described as "ликвидируемая сторона". M-06 should preserve
  that meaning in parser tests so downstream CVD/liquidation-flow derivations do
  not flip sign by interpreting it as aggressor trade side.

## Confidence

High. Review used the RFC, gates, contract governance, current `crates/contracts`
definitions, and a static scan of all current `Venue` / `MdPayload` match sites.
