## Б-1 (БЛОКЕР). Якорь `^HEAD^1` включается по СУЩЕСТВОВАНИЮ `HEAD^2`, а не по ОРИЕНТАЦИИ — sync-merge-вершина ветки выключает барьер молча

**Где:** `scripts/check_gate_meta.sh:137-140` — `git rev-parse -q --verify 'HEAD^2' ⇒
EXCL_MAIN=( "^HEAD^1" )`. Предпосылка «HEAD^1 — main-сторона ПО ПОСТРОЕНИЮ» верна только для
двух строителей (merge-ref GitHub'а, `gh pr merge`); барьер же применяет её к ЛЮБОМУ HEAD
с двумя родителями.

**Демонстрация (фикстура T4).** Ветка: APPROVE-вердикт (ah=B0), затем правка
`scripts/verify_M-99.sh` БЕЗ токена — живое нарушение subject-lock. Вершина ветки —
штатный `git merge main` (sync): `HEAD^1` = сторона ВЕТКИ, `HEAD^2` = main.

```
$ git checkout feat; git merge --no-ff "$MT" -m "git merge main (sync) — ВЕРШИНА ветки"
HEAD^1=1b5ca72 (ветка); HEAD^2=4d225e0=main
$ EVENT_NAME=pull_request PR_BASE_SHA=$B0 PUSH_BEFORE=$B0 bash scripts/check_gate_meta.sh   # e88dfe9
VERDICT: PASS — вердиктов проверено: 0, ...        ← ложное ЗЕЛЁНОЕ; вердикт ветки ВЫПАЛ из суда
$ EVENT_NAME= bash scripts/check_gate_meta.sh $B0                                            # ручная прод-форма
VERDICT: PASS — вердиктов проверено: 0, ...
```

Обе ПРЕЖНИЕ редакции нарушение ловят — это регрессия, а не старый предел:

```
$ ... bash barrier_r1.sh   (1f53a7f)  → FAIL C-999: subject-lock ... scripts/verify_M-99.sh; VERDICT: FAIL (1)
$ ... bash barrier_main.sh (92f6e65)  → FAIL C-999: subject-lock ...; VERDICT: FAIL (1)
```

**Почему это прод-форма, а не экзотика.**
1. Шапка самого барьера (`check_gate_meta.sh:47-50`) называет ручной прогон с позиционной
   базой ПРОД-ФОРМОЙ ВЫЗОВА — ровно та форма, что выше зеленеет.
2. `scripts/verify_M-60b.sh:130-137` («R: ПРОД-ФОРМА ... то же, что джоб gate-meta») гоняет
   обе event-формы на ГОЛОМ ЧЕКАУТЕ ветки — то есть именно на branch-tip, где sync-merge —
   рутина долгоживущего PR. В этом состоянии паритет-шаг R судит 0 вердиктов и зелен, тогда
   как CI-джоб на merge-ref судит по-настоящему: расхождение «verify зелен / CI красен» —
   ровно тот класс, против которого шаг R заведён (его собственный комментарий).
3. Локальные реплеи с `EVENT_NAME=pull_request` — штатный инструмент этого же трека
   (`C-128` построен на них) — на sync-merge-вершине судят пустоту.
4. Опасность именно МОЛЧАЛИВАЯ: «вердиктов проверено: 0» не отличим от честного «в диапазоне
   нет вердиктов»; предупреждения об активации якоря барьер не печатает.

В CI-формах (pull_request merge-ref; push-в-main через `gh pr merge`) ориентация случайно
правильная — но барьер её НЕ ПРОВЕРЯЕТ, а предполагает; T5 (push-в-main, нарушение на
влитой ветке) подтверждён: FAIL (1) — там регрессии нет.

**Условие снятия.** Якорь применяется только когда main-сторонность `HEAD^1` ПРОВЕРЕНА либо
громко объявлена: минимум — (а) активация печатается строкой («HEAD^2 существует ⇒ HEAD^1
принят за main-сторону; исключено N коммитов»), чтобы 0 вердиктов перестал быть молчанием;
(б) RED-сценарий формы T4 (вершина ветки = sync-merge, нарушение на ветке), КРАСНЫЙ против
`e88dfe9` и зелёный против фикса. Какой дискриминатор ориентации выбрать (проверка, что
`HEAD^2`-сторона содержит судимые вердикты; сверка `HEAD^1` с ref базы; отключение якоря вне
event-форм) — конструкция architect'а, не адверсария; замечу лишь, что `BASE`-предок есть у
ОБЕИХ сторон и дискриминатором не является.

## Б-2 (БЛОКЕР по гейту трека §5.2). Фильтр выбора вердиктов — несущий и НЕ запиннен ни одним сценарием

**Где:** `scripts/check_gate_meta.sh:219-226` — петля, пропускающая в суд только вердикты из
`OWN_FILES`. **Мутант mutD:** строка 223 (`printf ... | grep -qxF ... || continue`) заменена
на no-op — фильтр пропускает всё, как до фикса.

```
$ BARRIER=mutD.sh bash scripts/tests/red_gate_meta.sh | tail -1
VERDICT: PASS (41/41)                       ← мутация ВЫЖИЛА: потребитель ничем не запиннен
```

Фильтр при этом несущий, что доказано двумя способами.

**Реальная форма — реплей PR #60 13:15 (stale base `37d9697`, merge `a41a736` в `92f6e65`) под mutD:**

```
FAIL  research/critiques/C-123-...: subject-lock — ... 29 путей класса «гейт»
FAIL  research/reviews/R-108-...:  subject-lock — ... 29 путей
VERDICT: FAIL (2)
```

— исторический ложный красный возвращается ЦЕЛИКОМ при обоих исправленных якорях: чужие
вердикты, приехавшие в суд через устаревшую базу, запираются на СОБСТВЕННЫХ (легальных)
правках гейт-класса веткой. То есть закрытие Б-1 круга 1 держится не только на якорях, но и
на этом фильтре — а проба пиннит якоря (GM-16d) и не пиннит фильтр.

**Минимальная форма (фикстура md2):** ветка — свой REJECT + правка гейта (штатный круг
исправлений), база — чужой PASS-вердикт `R-foreign.md`:

```
$ e88dfe9:  VERDICT: PASS — вердиктов проверено: 1     ← чужой вердикт не судится
$ mutD:     FAIL R-foreign.md: subject-lock — тронут класс «гейт»: scripts/verify_M-99.sh
            VERDICT: FAIL (1)                           ← ложный красный
```

`harness-track.md` §5.2: «мутационный контроль: нейтрализация каждой проверки роняет свой
сценарий» — условие merge, и для проверки, введённой ЭТИМ ЖЕ коммитом, оно не выполнено.

**Условие снятия.** RED-сценарий формы md2 (чужой проходной вердикт в базе + легальная правка
гейт-класса веткой), зелёный против `e88dfe9` и КРАСНЫЙ против mutD-редакции; прогон обоих
направлений — в теле коммита.

## N-3 (minor). `-s ours`: лог-семантика красит дерево, которое ничего не изменило

Фикстура M3-c2: ветка вливает носитель правки гейта через `git merge -s ours` — дерево
относительно базы НЕ изменилось (`git diff --quiet` подтверждён), но барьер красен: touched
считается по логу коммитов, а коммиты гейт трогали. Не регрессия (r1 ведёт себя так же;
двухточечная main-редакция была зелёной) и защитная сторона ошибки; но семантика «судим
коммиты, не итоговое дерево» нигде не названа. Строка в комментарий §2bis — достаточно.

## N-4 (minor). Комментарий §2bis о `push` фактически неверен

`check_gate_meta.sh:133-134`: «на `push` второго родителя нет, множество пусто, семантика
прежняя». Ложно для push-в-`main`: КАЖДЫЙ merge PR (`gh pr merge --merge`) даёт HEAD с
`HEAD^2`, якорь активен на каждом прод-push'е. Эффект нейтрален, пока `PUSH_BEFORE = HEAD^1`
(штатный одиночный merge; T5: нарушение ловится, FAIL (1)), и вреден в батче из ≥2 merge за
один push (`^HEAD^1` исключит работу первого PR) — при защите ветки батч недостижим, потому
minor. Комментарий обязан описывать факт: на push якорь АКТИВЕН и совпадает с базой.

## N-5 (minor). Четвёртый потребитель диапазона — проверка ОТСУТСТВИЯ — остался без якорей, и это нигде не названо

`check_gate_meta.sh:352`: absence-петля судит ВСЕ merge-коммиты `BASE..HEAD` без `^HEAD^1`;
на stale-base merge-ref в суд попадают ЧУЖИЕ main-merge'и. Практически безвредно (их
вердикт — в их же дереве, повторный суд зелен), но §2bis объявляет «всё, что судит
subject-lock, обязано быть работой ветки», не оговаривая, что absence-проверка сознательно
живёт на широком диапазоне. Строка-оговорка в комментарий absence-блока.
