## §2 — Пункт 1. Критерий §3bis: ГОДЕН, с тремя поправками

**Это проверяемое утверждение о классе реализаций, а не переименованный список случаев** —
но только там, где множество значений оси конечно и обосновано предметом. Оси 1 (статусы
git: M/A/D/R), 2 (типы события = триггеры `on:` в `ci.yml`, замер: только `push` и
`pull_request`) и 4 (перечень путей зоны) — именно такие: их значения перечислимы не
воображением, а самим git/CI. Утверждение «каждое значение покрыто нарушением и осью —
легитимный случай» проверяется механически.

**Правило остановки работает.** Доказательство — не рассуждение, а эта работа: я нашёл
шесть дыр (§4), и каждую ОБЯЗАН был классифицировать по оси и значению — и смог. Ни одна
находка не потребовала двигать планку неформализуемо; каждая либо (i) дыра в матрице, либо
(ii) новая ось. Разница с кругами 1–4 ровно в этом: там каждая находка открывала
неограниченное «а ещё вот так», здесь — закрытый список работ. Признак конца цикла
объективен: матрица покрыта, опровержение без оси+значения не принимается.

**Поправка 1 — ось 3 в текущей формулировке не ось, а мешок.** «Прямой коммит ·
side+merge · недостоверная база» — не перечень значений, выведенный из предмета: 4 из 6
моих находок живут именно здесь (порядок токена, не-предок, evil merge — и реверт-пара как
пограничный случай, §4.5). Лечится выводом значений из КВАНТОРА инварианта: «для КАЖДОГО
коммита диапазона, чей дифф трогает зону, токен в ЕГО теле» распадается на конечные
отрицания — (а) диапазон вычислен неверно (база: zero-SHA / пустая / не-предок), (б) коммит
пропущен обходом (merge-собственный дифф), (в) токен в чужом коммите (оба порядка + тело
merge). Значения, выведенные из грамматики инварианта, конечны; значения, выведенные из
воображения обходов, — нет. Спека §3bis.2 переписывает строку оси 3 в этом виде.

**Поправка 2 — значение оси обязано быть атомарным, или покрытие считается по вариантам.**
«Токен в чужом коммите диапазона» — класс с двумя порядками; rev4 покрыл один (A3C:
токен-позже), и матрица показывала зелёное, пока реализация `earlytok` (§4.3) не прошла всю
пробу. Формулировка для §3bis.3(1): значение покрыто, когда сценарии исчерпывают его
известные варианты; непокрытый вариант = находка категории (i).

**Поправка 3 — манифест сверяет пробу с самой собой, а не со спекой.** Замер: спека §3bis.2
объявляет значение «не-предок» (строка 87) — в манифесте пробы его НЕТ; спека §4 до сих пор
говорит «15 сценариев» и `EXPECTED_SCENARIOS` (строки 165–166, 211) при фактических 17 и
манифесте. Это C-067 F-3 этажом выше: состав сверяется, но не с первоисточником. Фикс:
таблица §3bis.2 спеки — единственный источник осей/значений; манифест пробы обязан
сверяться с ней (греп по спеке или дублирование таблицы с проверкой равенства), и §4 спеки
приводится в соответствие rev4+.

Может ли планка двигаться дальше, как двигалась? Классификация (i)/(ii)/(iii) — единственный
оставшийся сустав субъективности. Закрываю его маршрутом: спор о категории находки решает
арбитр ОДНИМ сообщением по уже существующему контексту (продолжение этого разбора), а не
новым кругом architect↔critic.

## §3 — Пункт 2. Решение (б) по W-шагу: ВЕРНО — и с двумя обязательными поправками

**По существу architect прав, и фактическая база сильнее, чем он заявил.** Утверждение
«красное блокирует merge» недоказуемо из содержимого репозитория — блокировку включает
branch protection, настройка GitHub, а не файл. Мой замер добавляет решающий факт:

```text
$ gh api repos/a3ka/hft-platform/branches/main/protection
HTTP 403: "Upgrade to GitHub Pro or make this repository public to enable this feature."
```

Branch protection на этом репозитории **недоступен в принципе** (private, free-план).
Четыре круга ужесточали статическое доказательство утверждения, которое сегодня не может
быть истинным ни при какой настройке. Пятое ужесточение регулярки было бы бессмысленно
дважды: факт не в файлах И механизм не существует. Вынос за границу гейта с TD MAJOR —
единственно корректный маршрут; лестница «ещё одна форма спуфа» закрыта этим решением
навсегда.

**Поправка 1 — TD-запись обязана нести факт 403 и границу C.** «Branch protection обязан
требовать status-check» сегодня невыполнимо действием reviewer'а: проверять нечего.
Реальное решение — founder'а: платить / открыть репозиторий / принять, что CI —
сигнализация, а не барьер, и замок enforce'ится дисциплиной push-протокола плюс пост-фактум
красным CI на main. TD-запись формулируется как решение границы C с этими тремя опциями,
а не как «проверить настройку».

**Поправка 2 — предусловие 3 в rev4 НЕ прибито; закрыт claim, не дефект.** Замер: rev4-парсер
против фикстуры C-067 (`exit 1` в шаге, отключённом `if: ${{ false }}`):

```text
PASS  W docs-freeze: в needs И в сверке needs.docs-freeze.result — предусловия 2-3 выполнены
exit=0
```

Workflow, не удовлетворяющий предусловию 3 фактически, объявлен его выполнившим. F-067-2
остаётся открытой находкой. Правильный класс оракула — тот, что уже записан в
`testing.md` («проверка по ВЫЗОВУ, а не по тексту»): **исполнить** guard. Извлечь
безусловные run-шаги `status-check`, подставить `needs.<job>.result=failure`, исполнить
bash, требовать exit≠0; шаг с невычислимым `if` консервативно НЕ исполняется (fail-closed).
Осуществимость доказана прототипом (§8.4): реальный `ci.yml` — ВЫПОЛНЕНО (guard падает на
failure), обе спуф-фикстуры C-066/C-067 — НЕ ВЫПОЛНЕНО. Один ход закрывает весь класс
текстовых форм: после перехода на исполнение находка против W принимается ТОЛЬКО как
исполняемый контрпример (guard, выходящий нулём при подставленном failure), не как новая
текстовая форма.

## §6 — Пункт 5. Процессный дефект: пять механизмов

1. **Критерий достаточности не был назван ДО круга 1.** Игра «предъяви обход» без матрицы
   не имеет конца по построению — критик выигрывает её всегда, и каждый его выигрыш был
   по существу верным (все находки C-064–C-067 фактические). Виновата не сторона, а
   отсутствие правила. Фикс: RED-набор процессного/механического барьера обязан нести
   инвариант-от-результата + оси + правило остановки С ПЕРВОГО КОММИТА; первый круг
   критика бьёт сперва по перечню осей, потом по матрице. (Это правка `testing.md` —
   пойдёт через сам замок, когда тот встанет; до того — обычный маршрут §9.)
2. **Предписания вердиктов читались как достаточные условия, будучи необходимыми.**
   R-038 замерил: rev N+1 буквально реализует Required fix круга N и отвергается кругом
   N+1. Фикс: Required fix обязан либо называть критерий достаточности, либо явно писать
   «необходимое, не достаточное» — тогда architect не строит на нём ложных ожиданий.
3. **Триггер §0 сработал на C-066 и не был исполнен** — четвёртый круг состоялся. Правило
   есть, механики нет. Фикс: pre-flight мандата критика — счёт существующих вердиктов по
   предмету (`ls research/critiques/C-*-<milestone>*`); ≥2 REJECT → мандат не выдаётся,
   предмет к арбитру. Одна строка в шаблоне мандата.
4. **Перепись набора теряла покрытие, и никто не делал scenario-diff.** rev4 потерял
   rev3 FR-5 (порядок токена) на «улучшающем» круге — найдено только здесь (§4.3). Фикс:
   перепись пробы обязана нести таблицу соответствия старое→новое; потерянный сценарий
   без named-обоснования = находка.

## §10 — Воспроизведение (эталон и мутанты)

Эталонный барьер (все мутанты — однострочные отклонения от него, названные в скобках):

```bash
#!/usr/bin/env bash
set -uo pipefail
ZERO=0000000000000000000000000000000000000000
case "${EVENT_NAME:-}" in
  push)         BASE="${PUSH_BEFORE:-}";;
  pull_request) BASE="${PR_BASE_SHA:-}";;
  *)            exit 1;;
esac
[ -n "$BASE" ] || exit 1
[ "$BASE" != "$ZERO" ] || exit 1
git cat-file -e "$BASE" 2>/dev/null || exit 1
git merge-base --is-ancestor "$BASE" HEAD 2>/dev/null || exit 1
in_zone() { case "$1" in
  .claude/rules/*|.claude/agents/*|.claude/wrappers/*|CLAUDE.md|docs/04-workflow.md) return 0;;
  *) return 1;; esac; }
tok() { git log -1 --format='%b' "$1" | grep -qE '^FOUNDER-APPROVED: .{12,}'; }
touches() {
  local st p1 p2
  while IFS=$'\t' read -r st p1 p2; do
    [ -z "${st:-}" ] && continue
    case "$st" in
      R*) { in_zone "$p1" || in_zone "${p2:-}"; } && return 0;;
      *)  in_zone "$p1" && return 0;;
    esac
  done < <(git show --format= --name-status -M "$1")
  return 1
}
for c in $(git rev-list "$BASE..HEAD"); do
  if touches "$c"; then tok "$c" || exit 1; fi
done
exit 0
```

Мутанты: `showgrep` — tok() через `git show "$1" | grep -qE 'FOUNDER-APPROVED: .{12,}'`;
`subjtok` — `--format='%s%n%b'`; `earlytok` — обход `rev-list --reverse` с флагом
`seen`-токена, зона без своего токена пропускается при `seen=1`; `existsbase` — строка
`merge-base --is-ancestor` удалена; `treediff` — `git diff-tree -r -M --no-commit-id
--name-status` вместо `git show` (молчит на merge); `overbroad` — первый паттерн зоны
заменён на `.claude/*`. Фикстуры D1–D6 — §8.3, строение названо в тексте каждой демонстрации;
все повторяются из mk_repo-заготовки пробы + один коммит (D4: `reset --hard`; D6:
`merge --no-commit` + правка зоны + commit).

Эти шесть мутантов передаются architect'у как обязательная батарея rev5 (§5.2):
проба rev5 обязана быть красной против каждого.
