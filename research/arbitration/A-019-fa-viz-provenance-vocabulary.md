## §1. Вопрос 1 — ФАКТ: что код выдаёт на самом деле

Каждое утверждение снято лично в дереве `e84477a`, `crates/gateway/src/lib.rs`:

```text
$ grep -n 'deep_thr\|prov_str\|fn depth_provenance_label\|depth_provenance_label(' crates/gateway/src/lib.rs
1106:  depth_band_provenance: depth_provenance_label(row.band_pct_e8, row.side, reach),
1211:  let deep_thr = (mid as f64 * 0.013) as i64; // 1.3% от mid
1212:  let prov_str = "diff-reconstructed".to_string();
1228:  depth_band_provenance: deep.then(|| prov_str.clone()),   # bid-цикл
1244:  depth_band_provenance: deep.then(|| prov_str.clone()),   # ask-цикл

```

**Установленный факт — производителя провенанса ДВА, литералов НЕ два, у COB метки нет:**

1. **`DepthRow`** (`:239-248`, поле `:248`) получает метку через
   `depth_provenance_label(band, side, reach)` (`:1363`, вызов `:1106`) — функция ТРЁХ величин.
   Деп-исходы ТРИ: `"diff-reconstructed, liveness=confirmed"` (bid в охвате, `:1382`),
   `"diff-reconstructed, liveness=unconfirmed"` (ask в охвате, `:1382`),
   `"not-observed band=… reach=…"` (за охватом, `:1375`); плюс `None` для ≤1.3 %.
2. **`HeatmapCell`** (`:210-216`, поле `:215`) получает метку ДРУГИМ путём: константа
   `prov_str = "diff-reconstructed"` (`:1212`), вешается по ОДНОЙ ширине
   (`deep = dist > deep_thr`, `:1222`/`:1238`) на `:1228` и `:1244` — без стороны и без
   охвата, содержимое неизменно.
3. **`CobLevel`** (`:221-225`) провенанса **не несёт вовсе**: поля нет, конструкция COB
   (`:1249+`) никакой метки не ставит.

**Отсюда вердикты по спорным формулировкам `b8432c0`:**

- «**литерала ДВА**» — **ЛОЖНО** при любом потребительском счёте: рантайм-словарь deep-меток —
  **четыре** различные строки (три от депт-пути + одна плоская heatmap); формат-литералов в
  коде три (`:1212`, `:1375`, `:1382`). Число «два» верно ТОЛЬКО для счёта
  **путей-производителей** — и именно так факт и надлежит называть.
- «**heatmap/COB** метка ставится только по ширине» — **ЛОЖНО для COB** (метки нет) и
  **ВЕРНО для heatmap**. Приписывание COB метки, которой нет, — новое ложное утверждение
  того же класса, что снимала вся правка PR #96.
- Ядро находки architect'а — heatmap ставит метку только по ширине, без стороны и охвата,
  и это РАСХОДИТСЯ со словарём депт-серии в одной выдаче — **ВЕРНО и уже закартировано**:
  это дословно карточка **`TD-161`** (`TECH-DEBT.md:94`, Ф4, MINOR). Молчание о факте —
  дефект; называться он обязан как факт двух производителей + `TD-161`, а не как «два
  литерала» и не как свойство COB.
- **Существенное усиление, найденное этим арбитражем:** окно heatmap не независимо —
  `w = max(selector.bands)` (`:1192`). Значит исполнение `П-014` п.4 (смена `GATEWAY_BANDS`
  на канонический набор) РАСШИРИТ и heatmap-окно, и deep-ячейки с ширинной меткой начнут
  реально эмиттиться. Сегодня (`GATEWAY_BANDS=0.001`) deep-ячеек heatmap в проде нет —
  порог `deep_thr = 1.3 %` недостижим при окне 0.1 %. Факт связки обязан стоять в FA рядом
  с `TD-161`: он превращает MINOR-рассогласование в вопрос, который ВСТАНЕТ при включении.

**По вопросу 1 прав критик** (`C-149` B-2): формулировка `b8432c0` недопустима. Точное
описание — §3 ниже.

## §2. Вопрос 2 — ГРАНИЦА `П-014`: «(а) не закрыто для heatmap» писать нельзя

Тело `П-014` прочитано целиком (`docs/PENDING-SIGNATURE.md:749-801`). Установлено:

1. **Предмет подписи** — «полосы глубины ВКЛЮЧАЮТСЯ, различение сторон обязательно»:
   решение о ВЫДАЧЕ депт-полос глубже 1.3 % (`GATEWAY_BANDS`). Дословная цитата founder'а —
   про стороны ПОЛОС: «Отдаём обе стороны, но каждая несёт свою метку достоверности…».
2. **Пункт 1 обязательств реализации** («метка достоверности посторонне, а не только по
   глубине») сам называет свой предмет: «сегодняшний `depth_band_provenance`
   (`crates/gateway/src/lib.rs:1035`) смотрит ТОЛЬКО на глубину полосы
   (`row.band_pct_e8 > 1_300_000`)» — `row.band_pct_e8` есть поле `DepthRow`; на момент
   подписи `:1035` был сайтом метки депт-серии. Основание чисел — M-58, замер живости
   ПОЛОС. Heatmap и COB в тексте `П-014` не упомянуты ни разу.
3. Следовательно, предусловие (а) — требование к метке **депт-серии**. Фраза «(а) `П-014`
   … НЕ закрыто для heatmap» приписывает подписанному решению обязательство, которого в нём
   нет, — это **РАСШИРЕНИЕ подписанного решения**, и оно architect'у не принадлежит
   (`gates.md` §0.1: арбитр и architect решают «как правильно», founder — «чего мы хотим»;
   объём собственной подписи founder'а — его воля). Критик прав и здесь.
4. **Но вопрос, вскрытый architect'ом, реален** — из-за связки `w = max(bands)` (§1 п.4)
   включение полос по п.4 создаст deep-ячейки heatmap со «слепой» меткой. Легитимные
   маршруты, БЕЗ расширения `П-014`:
   - **инженерная последовательность** — milestone-спека исполнения п.4 (смена
     `GATEWAY_BANDS`) вправе включить закрытие `TD-161` в свой состав как обычную задачу
     (авторство architect'а, обычные гейты). Это спека РЕАЛИЗАЦИИ, а не дописывание подписи;
   - **воля founder'а** — если ставить heatmap-метку УСЛОВИЕМ включения (то есть двигать
     границу подписанного), это вопрос в очередь `PENDING-SIGNATURE`, решает founder.
   Что НЕЛЬЗЯ — писать в несущем FA, будто `П-014` уже содержит heatmap-предусловие.

## §3. Решение: точная замена (architect применяет механически)

Оба ханка — `docs/fa/viz-backend.md`, редакция ветки `e84477a`. Ни нового инварианта, ни
решения о доме `GS-I`/`GW-I`, ни расширения `П-014` замена не вносит.

**Ханк 1 — §4, врезка «ЛИТЕРАЛА ДВА…» (строки `:95-101`) заменяется целиком на:**

```markdown
- **⚠️ ПРОИЗВОДИТЕЛЯ МЕТКИ ДВА, И ОСВЕДОМЛЁННОСТЬ У НИХ РАЗНАЯ (`C-148` B-2 → `A-019`).**
  Сказанное выше — про **депт-серию** (`DepthRow`): `depth_provenance_label(band, side,
  reach)` — три deep-исхода (`liveness=confirmed|unconfirmed` по стороне в охвате,
  `not-observed band=… reach=…` за охватом). **Второй производитель — heatmap**
  (`HeatmapCell.depth_band_provenance`): метка ставится **только по ширине** —
  `crates/gateway/src/lib.rs:1211-1212` (`deep_thr = mid * 0.013`;
  `prov_str = "diff-reconstructed"`), вешается на `:1228`/`:1244` как `deep.then(…)` — без
  стороны и без охвата, одним неизменным значением. **COB метки не несёт вовсе:** `CobLevel`
  (`:221-225`) — только `side`/`price_e8`/`size_e8`. Итого словарь, видимый потребителю, —
  четыре разные строки от двух путей; рассогласование словаря в одной выдаче — **`TD-161`**
  (Ф4, MINOR). Оно перестанет быть теоретическим при включении полос: окно heatmap —
  `max(GATEWAY_BANDS)` (`:1192`), так что исполнение `П-014` п.4 расширит и heatmap, и его
  deep-ячейки выйдут в выдачу с ширинной меткой. Факт сегодняшнего кода, названный здесь,
  а не задача этого документа; предусловием `П-014` он НЕ является (`A-019` §2).
```
