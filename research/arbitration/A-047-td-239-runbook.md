## §1 — Находки `R-231`: верны ли (замер)

### B-1 — верна. В ветке отката маркер печатается ДО установщика

```
$ sed -n 301,316p .github/workflows/deploy.yml | grep -vE '^\s*#'
301  echo "=== healthy (recorder + gateway-serve) — deployed $(git rev-parse --short HEAD) ==="
305  bash deploy/bin/install-watchdog.sh || { echo "=== WATCHDOG INSTALL FAILED ===" >&2; exit 1; }
306  docker image prune -f
307  else
308  echo "=== DEPLOY FAILED — logs + rollback to $(git rev-parse --short "$PREV") ==="
309  docker logs hft-recorder --tail 50 || true
310  docker logs hft-gateway-serve --tail 50 || true
311  git reset --hard -q "$PREV"
312  docker compose up -d --build recorder gateway-serve
315  bash deploy/bin/install-watchdog.sh || true
316  exit 1
```

`deploy/README.md:150-154` формулирует правило «НИКАКОЙ ошибки docker перед маркером
`=== WATCHDOG INSTALL FAILED ===` от `deploy.yml:305` (или `=== DEPLOY FAILED ===` от
`deploy.yml:308`) — единственный признак пустого файла». Для `else`-ветки это ложно дважды:
(а) `DEPLOY FAILED` (`:308`) печатается ДО вызова установщика (`:315`), значит перед ним
вывода установщика нет ни в одном исходе; (б) после установщика маркера нет вовсе
(`|| true` `:315`, затем `exit 1` `:316`). Больше того: в `else`-ветке успех установки и
«пустой файл» (`install-watchdog.sh:100-101`) ОБА молчат — из лога Actions исход установки в
ветке отката **не определим в принципе**. Это надо сказать в runbook'е прямо, а не чинить
формулу.

Дополнительный факт, который сторона не называла и который инструкция §4 учитывает:
после `git reset --hard -q "$PREV"` (`:311`) строка `:315` исполняет `install-watchdog.sh`
из дерева `$PREV`, а не из деплоимой ревизии — bash читает файл в момент вызова. Ссылки
`install-watchdog.sh:NN` в описании ветки отката относятся к ПРЕДЫДУЩЕЙ ревизии и могут не
совпасть с текущей. Runbook в этой ветке ссылок на строки установщика давать не должен.

## §2 — Маршрут против третьего круга

**Сужение + `файл:строка` — принимается как ФОРМА текста, но механизмом не считается.**
Основание — замер этого же предмета: в rev2 (`3db4615`) все ссылки `файл:строка` были верны
(таблица `R-231` «Сверка»), и REJECT всё равно состоялся — на утверждении о ПОРЯДКЕ вывода,
которое ссылками не выражается. `файл:строка` помогает reviewer'у открыть источник за секунду;
оно не мешает автору неверно пересказать открытое. Плюс само число строки — утверждение о
коде со своим окном годности (следующая правка `deploy.yml` сдвинет `:305`).

**Класс воспроизведён трижды — проза запрещена.** `R-222` N-2 (три утверждения, завели
`TD-239`), `R-227` (три новых в фиксе), `R-231` (одно новое в фиксе фикса). По
`binding-requires-mechanism.md` «после третьего повторения одного класса писать прозу
ЗАПРЕЩЕНО: либо механизируй, либо признай остаточный риск явной записью». Делаются ОБЕ вещи,
с названной границей каждой:

1. **Механизм — узкая проверка маркеров, и она оправдана.** Предел назван честно: из девяти
   находок двух кругов она поймала бы две — исходный `WATCHDOG INSTALL OK` (`TD-239`) и
   `R-231` N-1 — и НЕ поймала бы `R-227` B-1/B-2/B-3/N-1/N-2 и `R-231` B-1/N-2. Но именно
   эти две — самые дорогие для оператора: маркер в runbook'е существует для копирования в
   `grep` по логу, и несуществующий маркер даёт пустой результат, который оператор читает
   как «этого не случилось». Нарратив оператор хотя бы перечитает; пустой grep — нет.
   Стоимость — десятки строк bash + проба на 4-5 сценариев; корпус маркеров сегодня —
   шесть уникальных строк в `deploy/README.md`, три из них печатает Rust
   (`crates/journal/src/bin/journal-retention.rs:414,569,620`), значит область поиска —
   весь репозиторий минус документы (`deploy/README.md`, `docs/`, `research/`, реестры),
   а не только `deploy/** + .github/workflows/**`, как предлагал architect: иначе
   `=== план ретеншена ===` (`README:358`) станет ложным FAIL с первого прогона.
   Второе требование к конструкции: сравнивать ПРЕФИКС маркера до первого `…`/`<`/`$`,
   иначе легитимная цитата `README:122` (`… rollback to … ===`) тоже красная. Третье —
   анти-плацебо: проба обязана содержать сценарий «маркера в коде нет → FAIL» и
   «маркер есть только в самом README → FAIL» (иначе README подтверждает сам себя).

   **Где жить:** шаг в `scripts/verify_delivery_M-08.sh` рядом с `D6` (`:257-261`), потому
   что (а) это уже гейт runbook'а доставки и `D6` — ровно та проверка, которая, по `R-227`
   §«Класс», «к истинности §0a слепа по построению»; (б) джоб `delivery` (`ci.yml:37-45`)
   входит в агрегат `All checks passed` (`ci.yml:628`) — высшая строка таблицы силы
   механизмов, без правки агрегата. Отдельный `check_*.sh` + новый джоб — лишняя проводка
   ради шести строк. Проба — `scripts/tests/red_verify_delivery_*.sh` по образцу
   существующих.

   **Когда:** НЕ в круге 3 `TD-239`. `scripts/verify_*.sh` и `scripts/tests/**` — зона
   architect'а (sacred), engine-dev туда не пишет; смешать текстовую правку с новым
   гейтом в одной ветке — значит снова держать мелкий фикс заложником большого круга
   (критик по `gates.md` §9 на харнесс-правку). Маршрут: `docs/workflow/harness-track.md`
   («Fable строит — Terra ломает»), отдельная ветка, со ссылкой на это решение. До его
   приземления остаточный риск назван записью (п.2 ниже), а не замолчан.

2. **Запись остаточного риска — обязательна при close-out `TD-239`.** Reviewer (владелец
   `TECH-DEBT.md`) заводит карточку: «утверждения runbook'ов о поведении кода, не
   выраженные маркером (порядок вывода, какие команды что печатают, форма вызова),
   оракула не имеют; проверка — чтение reviewer'ом с открытием каждого `файл:строка`;
   маркерная часть закрывается harness-track'ом по `A-047` §2». Это не четвёртый абзац
   прозы, а то, что правило прямо разрешает как альтернативу механизму, — с указанием,
   какая половина класса всё же механизируется.

**Почему не «общий оракул правды» и не FACTS-маркер.** Общий оракул «текст ↔ код» —
суждение о смысле, его нет и изображать не надо. Маркер `<!-- FACTS: audited_head=… -->`
с датировкой через `verify_design_claims.sh` сегодня ограничен `docs/plans/**`
(`verify_design_claims.sh:726,954`); расширять его на `deploy/README.md` — отдельное
решение, и датировка дрейф ОБЪЯВЛЯЕТ, а не ловит (`A-010` H-5). Для runbook'а, который
читают в момент тревоги, «датировано, но ложно» мало чем лучше «ложно».
