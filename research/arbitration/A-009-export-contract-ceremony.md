### 0.1 История формы выгрузки — ВСЕ переходы версии, не «коммиты, где слово встречается»

Замер, названный в мандате (`git log -S'GATEWAY_SCHEMA_VERSION'`), даёт **7 коммитов, но не
7 версий**: `-S` ловит изменение ЧИСЛА вхождений строки, а не значения константы. Четыре из
семи найденных им коммитов версию не меняли вовсе (`2;→2;`, `7;→7;`, `8;→8;`). Правильный
замер — проследить ЗНАЧЕНИЕ по всем коммитам файла в `main`:

```
$ git log --reverse --format='%h|%ad|%s' --date=short origin/main -- crates/gateway/src/lib.rs \
    | while IFS='|' read -r h d s; do v=$(git show $h:crates/gateway/src/lib.rs \
    | grep -m1 'GATEWAY_SCHEMA_VERSION: *u32 *=' | sed 's/.*= *//;s/;//'); echo "$h|$d|$v|$s"; done \
    | awk -F'|' '$3!=p {print $1"  "$2"  v="p" -> v="$3"   "$4; p=$3}'

45dd6be  2026-07-22  v= -> v=2   feat(M-22): task #1 — gateway contract-skeleton + GW-I-1..6 RED oracles [architect]
9623d9b  2026-07-22  v=2 -> v=3  feat(M-20): task #3 — merge VWAP frames and bump schema v3 [engine-dev]
c4241ed  2026-07-23  v=3 -> v=4  feat(M-24): task #3 — … SeriesBundle.volume_profile + schema 3→4 [engine-dev]
ebc98fe  2026-07-23  v=4 -> v=5  feat(M-23): task #2-3 — book-dep + L2Delta/Heatmap/COB, schema 4→5 [engine-dev]
ef21fec  2026-07-26  v=5 -> v=6  feat(M-36): tasks #1-3 — VWAP all-time (VB-I-6 reversal) + schema bump 5->6 [engine-dev]
870ab0e  2026-07-27  v=6 -> v=7  feat(M-38a): task #9 — bump GATEWAY_SCHEMA_VERSION 6->7
c895c7f  2026-07-28  v=7 -> v=8  feat(M-48): task #1-#4 — … + GATEWAY_SCHEMA_VERSION 8
```

**Шесть переходов после рождения формы, все — за СЕМЬ дней (22–28 июля). С 28.07 версия
стоит на 8: двадцать дней, 14 коммитов в файл, ноль изменений формы.**

```
$ git log --oneline c895c7f..origin/main -- crates/gateway/src/lib.rs | wc -l
14
$ git diff c895c7f origin/main -- crates/gateway/src/lib.rs | grep -E '^[-+] *pub [a-z_]+:'
+    pub events_scanned: u64
+    pub segment_meta_ops: u64
```
Оба новых поля — в `ReadStats` (`crates/gateway/src/lib.rs:1942-1957`), которого НЕТ в
`Snapshot` (проверено: `sed -n '/pub struct Snapshot/,/^}/p'` — поля `schema_version`,
`selector`, `cursor`, `series`, `history_start_seq`, `history_truncated`). Bump не требовался
и правильно не сделан — **тихих смен формы после v8 нет.**

Частота, которую `П-012` просит замерить, — **не «единицы» и не «десятки», а ВСПЛЕСК**:
~1 изменение в день, пока строились серии кокпита, и полный штиль после. Это меняет вопрос:
церемония будет платиться не равномерно, а пачкой в те недели, когда идёт продуктовая работа —
ровно тогда, когда она дороже всего.

### 0.4 Критерий, записанный в `П-012`, свой худший случай ПРОПУСКАЕТ

`docs/PENDING-SIGNATURE.md:552-553` (редакция `d704bc5`):
> «Признак ломающего — существующий потребитель перестаёт разбирать сообщение прежней версии;
> проверяется roundtrip-тестом старой версии, а не мнением.»

Приложим к замеру: на `v5→v6` потребитель разбирает сообщение прекрасно. Roundtrip-тест
зелёный. По этому критерию M-36 — **аддитивное**, RFC не нужен. Между тем именно его
собственный план architect'а называет болезнью, ради которой затевается миграция:

```
$ sed -n '342p' docs/plans/plan-design-migration.md
| **К1** | … | **Кросс-языковая граница №1 SaaS.** Уже дала non-additive смену формы (v6→v7)
и **смену СЕМАНТИКИ при неизменной форме** (v5→v6 VWAP) без RFC и без миграционной заметки —
ровно болезнь hft-core-rs (несовместимые wire-форматы), только в зачаточной стадии | **P0** |
```

Классификатор, пропускающий класс, ради которого он вводится, — не классификатор.
**Это, а не «частота», решает развилку.**

`VB-I-4` (`docs/fa/viz-backend.md:118`) объявляет «export v2 аддитивен: старые консюмеры v1 не
ломаются» — и за шесть переходов это утверждение было ложным дважды, не будучи опровергнутым
ни одним прогоном.

### 0.5 Экспортная форма ВОССТАНОВИМА; журнал — нет. Это и есть настоящая ось


Единственная персистентная копия экспортной формы — чекпоинт (`CKPT_SCHEMA_VERSION = 1`,

Отсюда: обоснование RAW-гейта (`gates.md` §1: «ошибка проявляется через МЕСЯЦЫ и стоит
переписывания всего накопленного… цена умножается на прошедшее время») для экспортных форм

Но обратная сторона названа честно: у консюмера **нет компилятора на своей стороне**
(`docs/plans/plan-design-migration.md:330` — «расхождение обнаружит пользователь»), и
консюмер этот — вне нашего дерева (`research/exports/format.md:6`: «`code2alpha` Fastify +
lightweight-charts v5 (founder-фронт; вне нашего дерева)»). Значит цена ошибки экспорта —
не потеря данных, а **молча неверные цифры на экране**. Церемония обязана целиться в
ОБНАРУЖЕНИЕ, а не в прозу.

## §1. Разбор развилки

### Что в развилке сформулировано верно

Постановка `П-012` схватывает настоящий риск: «норма, блокирующая рост, не исполняется, а
обходится — и тогда теряется вся церемония, включая ту её часть, что защищает журнал». Это
верно и подтверждено замером 0.7. Верна и интуиция, что журнал и выдача — разные по цене
ошибки сущности; §0.5 даёт этому механическое основание, которого в записи не было.

### Что сформулировано неверно

**Ошибка первая — ось.** Развилка построена по оси «сколько церемонии» (много/мало/частично).
Замер говорит, что различие между журналом и выдачей — не в КОЛИЧЕСТВЕ церемонии, а в том,
КАКОЙ АРТЕФАКТ несущий. Для журнала несёт **миграционная заметка** (§4 п.4): старые записи
обязаны читаться навсегда, вывести их заново неоткуда. Для выдачи миграционная заметка почти
бесполезна (форма пересоздаётся реплеем, чекпоинт сам себя выбрасывает — §0.5), зато несёт
**обнаружение молчаливой подмены смысла**, которого сегодня нет ни в каком виде.

**Ошибка вторая — классификатор.** Критерий «ломающее = перестаёт разбираться» отвергнут в
§0.4: он объявляет аддитивным ровно тот переход, который причинил вред. Хуже: он подан как
машинно-проверяемый («roundtrip-тестом, а не мнением»), то есть создаёт ложную уверенность.

**Ошибка третья — умолчание о цене переезда.** Обсуждается цена RFC, но не названы три
следствия переезда, которые дороже (см. Р-7): путевой Block-C начнёт авто-реджектить колонки
кокпита; `scope-guard` передаёт владение колонками от engine-dev к architect; две версионные
шкалы противоречат друг другу и обязаны быть слиты.

### Варианты по отдельности

- **(б) — отклоняется.** Не потому что «дороже» (это оценка), а по замеру 0.6: ~250 строк
  документа плюс круг сильного критика на каждую колонку, при том что аддитивная колонка
  физически не способна сломать консюмера (§0.3). Церемония тратится там, где риска нет, и
  этим обесценивается там, где он есть.
- **(в) — отклоняется как инвертированное.** §0.8: под церемонию переносится часть, не
  менявшаяся ни разу, а изменчивая остаётся вне. Дополнительно (в) технически несвязно:
  `ServeMsg` типизирован через `Snapshot`/`Frame`, а те — через `SeriesBundle`; перенести
  конверт «без бандла» — значит либо тянуть весь граф, либо оставить в `contracts` тип,
  ссылающийся наружу, что убивает саму цель («формы объявлены в одном месте», CT-I-7).
- **(а) — принимается по КОНСТРУКЦИИ и отвергается по КРИТЕРИЮ.** Два класса внутри одного
  крейта — верно (§0.5 даёт основание прочнее, чем «частота»). Критерий — заменяется.

## §2. РЕШЕНИЕ

**Принимается вариант (а′): два класса строгости внутри `crates/contracts`, различаемые
НЕСУЩИМ АРТЕФАКТОМ, с машинным классификатором вместо декларации автора, и с послаблением,
вступающим в силу только после того, как классификатор зелёный.**

Обязательно к исполнению обеими сторонами (`gates.md` §0).

### Р-1. Два класса — ДА. Основание — восстановимость, а не частота

- **Класс 1 — журнальное T1** (`Event`/`EventKind`, `SegmentHeader`, `Ctl(ParamChange)`,
  `Decision`, `SignalRegistry`): без изменений — полный contract-RFC (`05-contract-layer` §4,
  все 7 пунктов) на КАЖДОЕ изменение, включая аддитивное, плюс RAW-гейт. Несущий артефакт —
  миграционная заметка. Основание прежнее и оно верно: журнал невыводим ни из чего.
- **Класс 2 — формы провода/выгрузки** (`Snapshot`, `Frame`, `SeriesBundle`, `ServeMsg`,
  `Selector`, `Cursor`, строковые типы серий): восстановимы реплеем, персистентная копия
  самоинвалидируется (§0.5). Несущий артефакт — **golden-фикстура версии**, не проза.

### Р-2. Критерий «ломающего» из `П-012` ОТМЕНЯЕТСЯ

Формулировка «существующий потребитель перестаёт разбирать сообщение прежней версии;
проверяется roundtrip-тестом» из `docs/PENDING-SIGNATURE.md:552-553` изымается: замер §0.4
показывает, что она пропускает `v5→v6`. Ссылка на roundtrip как на доказательство создаёт
ложную уверенность и потому вреднее отсутствия критерия.

### Р-3. Класс изменения объявляет ПРОГОН, а не автор

Вводится golden-фикстура на версию — механизм, уже спроектированный architect'ом и лежащий
в плане без срока (`docs/plans/plan-design-migration.md:388`, `CT-I-15`): замороженный вход
(кусок журнала прод-формы) → замороженные байты бандла для КАЖДОЙ живой версии.

Правило классификации:

| наблюдение прогона | класс | церемония |
|---|---|---|

### Р-4. Послабление УСЛОВНО и fail-closed

До зелёного `CT-I-15` у класса 2 нет классификатора; неизвестный вход → строгий режим

### Р-5. Bump — на КАЖДОЕ изменение формы; правило «аддитивное без bump» отменяется

`research/exports/format.md:8-9` предписывает не бампать аддитивное. Отменяется при слиянии
шкал: версия — единственный признак, по которому консюмер отличает два разных сообщения, и
она же ключ инвалидации чекпоинта (§0.5). Дёшево (одна цифра), наблюдаемо, механизируемо.
«Без RFC» относится к ЦЕРЕМОНИИ, не к версии — их смешение и породило спор.

Одновременно вводится обратный сторож: **изменение формы БЕЗ bump'а — красный CI**. Сегодня
этого барьера нет; то, что после v8 тихих изменений не случилось (§0.1), — везение, а не
механизм.

### Р-6. Граница классов обязана быть выражена ПУТЁМ

Все механические барьеры проекта работают по путям (`check_docs_freeze.sh:61-66` — `case` по
шаблонам путей; Block-C — «правки `crates/contracts/**`»; `scope-guard` — таблица путей).

мнение через один milestone. Поэтому классы обязаны лечь в РАЗНЫЕ каталоги, например
`crates/contracts/src/journal/**` (класс 1) и `crates/contracts/src/wire/**` (класс 2), и все

## §4. Что уходит founder'у — человеческим языком

### Сначала — о чём вообще спор

Программа считает цифры и отдаёт их на экран. Набор того, что отдаётся, — это список: цена,
объём, средняя цена, профиль объёма и так далее. Спор — о том, насколько тяжёлой должна быть
процедура, когда этот список меняется.

**Что происходит сегодня, когда экрану нужна новая колонка** (скажем, «ликвидации»).
Программист добавляет одну строчку в описание списка, увеличивает номер версии на единицу,
коммитит. Полдня работы. Ничего сломать он при этом физически не может: старая страница про
новую колонку не знает и молча её пропускает — так устроен формат.

**Что произойдёт после переезда этих форм в «строгий» раздел, если ничего не менять в
правилах.** То же самое действие превращается в: отдельный документ на ~250 строк, набор
контрольных примеров, заметка «как читать старое», запись в журнал изменений — и
обязательный круг проверки самой дорогой моделью. Вместо полудня — два-три дня плюс дорогой
прогон. На каждую колонку. Это и есть та развилка, которую вам показали.

**А вот что действительно опасно и чего сегодня не ловит ничто.** В июле уже был такой
случай: колонка «средняя цена» перестала обнуляться в полночь и стала считаться от начала
всей истории. Ни одной строчки в описании формы не поменялось. Страница продолжила рисовать
график — просто цифры стали означать другое. Ни один тест не покраснел, никто ничего не
заметил. Таких случаев за неделю июля было два из шести изменений.

**Моё инженерное решение:** дорогую процедуру вешаем на смену СМЫСЛА, дешёвую — на
добавление новой колонки. И решает не человек своим мнением («мне кажется, это безобидно»),
а тест: мы замораживаем «эталонный кусок данных → эталонный ответ» и, если после правки
ответ разошёлся, а список колонок не менялся, — значит поменялся смысл, включается дорогая
процедура. Забыть или ошибиться нельзя: краснеет автоматически. Пока такого теста нет —
режим строгий для всего; это условие, а не пожелание.

Ваша подпись на это не нужна: это вопрос «как правильно», и он решён.

### Вопрос 1 — единственный, который обязаны решить вы

**С какого момента мы обязаны не ломать ЧУЖОЙ экран?**

Сегодня экран один и он ваш. Если мы поменяем смысл цифры, вы это увидите и мы починим
страницу в тот же день — мы обновляем обе стороны одновременно.

Когда доступ начнут покупать, экранов станут тысячи, и они обновляются не тогда, когда мы
выкладываем новую версию. Человек может держать открытой вчерашнюю страницу неделю.

Вопрос: **обещаем ли мы платящему клиенту, что его СТАРАЯ страница продолжит показывать
ПРАВИЛЬНЫЕ цифры после нашего обновления — и с какой даты это обещание начинает
действовать?**

Что зависит от ответа (и почему это не инженерный вопрос):

- **«Обещаем»** — значит программа обязана уметь отдавать одновременно НЕСКОЛЬКО версий
  выдачи: и сегодняшнюю, и вчерашнюю, и позавчерашнюю. Это отдельная и немаленькая работа,
  и её надо планировать заранее — задним числом она сильно дороже.
- **«Не обещаем, обновление одномоментное»** — тогда старая страница при нашем обновлении
  должна честно сказать «версия устарела, обновите», а не показывать неверные числа. Это
  дёшево, но это видимое пользователю неудобство.
- **«Пока не обещаем, начнём обещать с даты X»** — самый вероятный ответ; тогда назовите
  примерный ориентир (например, «с первого платящего клиента»), и мы заложим работу к нему.

Это обещание продукта и цена его нарушения — доверие покупателя. Инженерной правоты тут нет,
поэтому решаю не я.

### Вопрос 2 — маленький, но требует вашей строки

Два служебных файла с правилами (кто чего имеет право касаться и что робот-ревьюер
отклоняет автоматически) придётся поправить — иначе после переезда КАЖДАЯ новая колонка на
экране будет автоматически отклоняться, а писать её сможет только самый дорогой агент вместо
обычного программиста. Правки чисто механические, существа дела не меняют.

Эти файлы заперты: любое изменение обязано нести вашу строку-разрешение — так устроен замок,
который вы же ставили. Нужна фраза примерно такая:

> «Разрешаю поправить правила доступа и авто-отклонения ради переезда форм выдачи.»

Без неё правка физически не вливается, и решение останется на бумаге.

## §5. Риски решения — названы честно

1. **Golden-фикстура ловит смену смысла ТОЛЬКО на замороженном входе.** Смена смысла в ветке,
   которую фикстура не проходит (другой инструмент, редкое состояние книги, пустая сессия),
   пройдёт молча — ровно как сегодня. Смягчение обязательное, не факультативное: вход
   снимается с прода замером (`testing.md`) и включает деградированные случаи. Полноты это не
   даёт; я не выдаю механизм за доказательство.
2. **Ложные срабатывания.** Исправление БАГА тоже разошьёт golden. Это не дефект, а цена:
   автор обязан осознанно перезаписать эталон. Но если перезапись станет рутинным жестом,
   механизм выродится в кнопку «согласен». Сторож, который я называю и НЕ механизирую
   (`COGNITIVE-ONLY`): перезапись golden — ОТДЕЛЬНЫЙ коммит, называющий класс правки, и она
   запрещена в одном коммите с правкой реализации. Кандидат на настоящую механизацию —
   барьер «диф трогает и `src`, и `tests/golden/` в одном коммите → FAIL».
3. **Два класса — это две двери, и вторая может стать проходным двором.** Ровно тот риск,
   который назвала запись `П-012` про (б), только зеркальный: не «обойдут строгое», а
   «сложат в мягкий класс лишнее». Защита — Р-6 (класс = путь, а не мнение) и то, что
   перенос типа между каталогами сам по себе есть изменение формы, то есть виден в дифе.
4. **Решение опирается на замер СЕМИ дней активной разработки.** Всплеск 22–28 июля мог быть
   нетипичным (рождение кокпита). Если следующий продуктовый рывок даст другой профиль —
   например, ломающих больше, чем аддитивных, — послабление теряет смысл и (б) становится
   правильным. Точка пересмотра называется явно: **после `M-25` пересчитать 0.1/0.2 тем же
   способом**; если ломающих окажется больше половины, вернуться к этому вердикту.
5. **Я не проверял `code2alpha`** — репозиторий вне дерева. Все утверждения о консюмере взяты
   из наших документов (`research/exports/format.md:6`, `plan-design-migration.md:330,342`).
   Если фронт устроен иначе (например, жёстко сверяет номер версии и отказывается при
   несовпадении), меняется оценка §0.3 «аддитивное безвредно» — но НЕ решение: класс
   семантики от этого только опаснее.
6. **Ответ founder'а на вопрос 1 может обесценить часть решения.** Если обещание
