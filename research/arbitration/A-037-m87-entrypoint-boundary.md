## РЕШЕНИЕ КОРОТКО

1. **Критик прав по существу R2/E2, и это дефект КОНСТРУКЦИИ набора, а не изложения.**
   `crates/gateway/tests/red_m87_cold_path_reads_nothing.rs` пиннит на ОБЩЕЙ функции
   `LiveReducer::resume` поведение, ПРОТИВОПОЛОЖНОЕ двум другим sacred-оракулам того же
   корпуса на той же функции и том же классе входа — одному существующему
   (`red_frames_seek_bound.rs::resume_without_checkpoint_reports_full_replay`) и одному из
   ЭТОГО ЖЕ набора (`red_m87_admission.rs::form_payload_bytes_are_counted_at_all`). Набор
   невыполним против самого себя: `cargo test --all` не позеленеет никогда, либо позеленеет
   правкой общей библиотеки, которую §10 спеки запрещает, а `A-033` D-2 признал негодной.
   Файл в нынешней форме из `M-87` **ИЗЫМАЕТСЯ**; четыре состояния слепка переезжают в
   транспортный крейт (§4 D-1).
2. **Architect прав в том, что предохранитель живёт в транспорте**, и WS-оракул написан
   правильно по МЕСТУ. Но по СРЕДСТВУ он недостаточен: единственное доказательство «журнал не
   читался» — самоотчётный счётчик того же кода. План `scale-program` §15.1, на который
   ссылается сама спека, требует **подставного читателя**, и я замером показал, что он
   строится на уровне фикстуры без участия dev'а (§3.4). Ловушка — обязательное условие
   диспетчеризации (§5 У-1).
3. **Критик ошибся в факте E1**: утверждение «валидатор отвергает `timeframe_ms: 1` как
   `invalid_selector`» ЛОЖНО по исполнению (§3.2) — все три ступени входа его ПРИНИМАЮТ.
   Оракул `c5_entry_unbounded_profile_is_refused` тестирует ровно «валидный вообще, но вне
   профиля» и остаётся. Остальное в E1 (литералы `ServingCounters` из четырёх полей против
   шести в §4.1; `policy()` построена и не передана серверу; объявленные `CallBudget`/
   `BudgetStop`/`Cancel`/`ServingSlots` без единого оракула) — верно и обязательно к
   исправлению (§5 У-3..У-5).
4. **Оба утверждения об обходимости гейта верны одновременно** и не противоречат друг другу:
   удаление строки `smoke_ws.rs` роняет шаг 10 (мутация architect'а ПОДТВЕРЖДЕНА), а строка с
   именем файла и ПУСТЫМ решением шаг не роняет (ложно-зелёный ПОДТВЕРЖДЁН); шаг 9 зеленеет от
   `cpus:`/`memory:` под `labels:` (§3.5). Оба шага чинятся (§5 У-8).
5. **Граница с `A-033` сформулирована проверяемо** (§4 D-1): библиотека расчёта в `M-87`
   меняется ТОЛЬКО аддитивно, и это предъявляется одной командой — ни один существующий файл

## §1 — Предмет спора и позиции сторон

**Спор.** Оракул `crates/gateway/tests/red_m87_cold_path_reads_nothing.rs` зовёт
`gateway::LiveReducer::resume` напрямую и требует, чтобы при отсутствующем, повреждённом и
несовместимом слепке он декодировал НОЛЬ событий, а при отставшем — докормил не более
`TAIL_BUDGET = 16` через `pump`.

**Критик (`C-234` R2 → `C-236` E2):** это обходит единственную точку, которая должна защищать
публичный запрос; GREEN достижим либо без подключения допуска вовсе, либо правкой общей
библиотеки — конструкция `M-84`, признанная негодной `A-033`. Запретный список §10 не снимает
противоречие, а лишь называет его.

**Architect:** предохранитель живёт в транспорте; несущий оракул — `red_m87_entrypoint.rs`,
поднимающий реальный сервер; библиотечный файл — проверка четырёх состояний слепка «на уровне
библиотеки», в спеке названная недостаточной в одиночку; правка общего валидатора и
`LiveReducer` запрещена §10 шестью строками.

Три sacred-оракула, одна публичная функция, один класс входа (пустой каталог слепков):
первый требует `events_decoded == N`, второй — `events_decoded == 0`, третий — «байт прочитано

«читать байты, не декодируя», то есть ровно тем, что план §15.1 называет «дорогая работа
произошла, счётчик нулевой» и запрещает считать доказательством. `§16.1` называет первый
«ПЕРЕНОСИТСЯ на worker-путь», но тест зовёт библиотечную функцию напрямую — у него нет
«пути», и переносить нечего; критик в E4 прав.

Состояния 2–3 того же файла требуют, чтобы `resume` НЕ откатывался в rebuild при мусоре в
файле слепка — а `read_checkpoint` сегодня делает именно это по построению:

```text
$ awk 'NR>=4166 && NR<=4171' crates/gateway/src/lib.rs
        if !ckpt_path.exists() {
            return Ok(None); // отсутствует — silent rebuild; никакой рекурсии
        …  Err(_) => return Ok(None), // silent rebuild
```

и §10 спеки запрещает «менять fallback чекпоинта и семантику его отказа» со ссылкой на
`VB-I-11`. Состояние 4 требует, чтобы `pump(…, 64)` остановился на 16 — при том, что `pump`
по контракту дренирует ВЕСЬ backlog (`lib.rs:4662-4667`), и §10 запрещает менять `pump`.
Итог: **все четыре ассерта файла выполнимы только правкой того, что тот же набор запрещает.**

### 3.4. Подставной читатель СТРОИТСЯ на уровне фикстуры — доказано исполнением

Вопрос, от которого зависит У-1: может ли architect построить ловушку §15.1 без правки кода
и без участия dev'а. Проба (одноразовое дерево, удалена): журнал из 2 000 сделок,
`max_segment_bytes = 8 КиБ` → 13 сегментов; 64 байта в СЕРЕДИНЕ `segment-00000000.jrnl`
инвертированы (заголовок сегмента цел, остальные сегменты целы).

```text
$ cargo test -p gateway --test zz_arb_probe_trap -- --nocapture 2>&1 | grep ARB-PROBE
ARB-PROBE segments=13 first=Some("segment-00000000.jrnl")
ARB-PROBE control cold resume on intact journal => is_ok=true
ARB-PROBE cold resume on TRAP journal => Err("frame crc mismatch")
ARB-PROBE checkpoint::advance on TRAP journal => Err("frame crc mismatch")
test result: ok. 1 passed; 0 failed
```

Прод-путь чтения (`journal::stream`, `segments.rs:1733`) строг к CRC: порча полезной
нагрузки → `Err`, не байт-ресинк (ресинк — только у офлайн `recover`, `:876-879`). Значит
на WS-уровне ловушка ЛОВИТ: холодный запрос над таким журналом при подключённом допуске
получает `not_ready`, а при чтении журнала ДО допуска — `invalid_selector: resume failed:
frame crc mismatch` (форма ошибки `lib.rs:868-877`). Контрольный сценарий §14.1 —
`checkpoint::advance` на том же каталоге — краснеет, то есть ловушка предъявляет себя сама.
Тёплый путь ловушкой не задевается: слепок строится ДО порчи, `resume` со слепком журнал
не читает (`lib.rs:4571`, `ReadStats::default()` `:4574`), хвост живёт в целых сегментах.

Утверждение спеки §14.1 «конкретная форма ловушки выбирается dev'ом» — **неверно по
зонам**: фикстура sacred-теста — зона architect'а, и, как показано, она ему доступна.

### D-1. Граница «транспорт ↔ библиотека» — ПРОВЕРЯЕМАЯ формулировка

**Норма.** В `M-87` библиотека расчёта (`crates/gateway/src/**`) меняется ТОЛЬКО
АДДИТИВНО: новые публичные функции, поля и типы допустимы (`ReadStats.payload_bytes_read`;

которая по политике или по состоянию слепка ОТКАЗЫВАЕТ запросу, — живёт в

```text
#     пин «библиотечный resume без слепка по-прежнему честно реплеит»
$ cargo test -p gateway 2>&1 | grep -E '^test result' | awk '{p+=$4; f+=$6} END {print "passed="p" failed="f}'
failed=0
```

Почему это и есть граница `A-033`: там гвард в `gateway::validate_selector` уронил 209 из

делает такую правку НЕВЫПОЛНИМОЙ по построению — любой не-аддитивный сдвиг библиотеки
краснит существующий sacred-тест, который dev править не вправе. Правило проверяется без
чтения кода.

**Следствие 1 — `red_m87_cold_path_reads_nothing.rs` изымается из `M-87` в нынешней

охраняется, но удаление называется в коммите поимённо). Его содержание переезжает:

**Следствие 3 — `readiness` смотрит на слепок, но НЕ на `LiveReducer::resume`.** Функция

ОТДЕЛЬНЫЙ бюджет, план §15.1). Что именно считать «описью» и как читать хвост без
полезной нагрузки — решение architect'а в спеке, но с оракулом-ловушкой оно становится
проверяемым: ловушка в сегменте 0 не должна ронять `readiness`.

## §5 — ОБЯЗАТЕЛЬНЫЕ УСЛОВИЯ диспетчеризации dev'а (все, не «по возможности»)

**У-1. Ловушка на точке входа (план §15.1, `testing.md` свойство 3).** `red_m87_entrypoint.rs`
несёт оракул над журналом-ловушкой из §3.4 для ЧЕТЫРЁХ состояний слепка: холодный WS-запрос
получает НАЗВАННЫЙ исход (`not_ready`/`warming`), а не `invalid_selector`/`resume failed`;
контрольный сценарий в ТОМ ЖЕ файле — `gateway::checkpoint::advance` на том же каталоге
возвращает `Err` (ловушка предъявляет себя; иначе набор объявляет setup несостоявшимся).
Для отставшего слепка ловушка ставится в первый сегмент ПОСЛЕ курсора слепка. Тёплый путь
над журналом с ловушкой в сегменте 0 обслуживается (`snapshot`) — это одновременно пин
«тёплый путь не трогает голову». Счётчик `journal_payload_bytes_read` ОСТАЁТСЯ вторым
признаком, но получает позитивный контроль: обслуженный запрос с непустым хвостом сверх
слепка увеличивает счётчик (иначе «никогда не инкрементировать» проходит C1).

**У-2. Библиотечный файл изъят, четыре состояния переехали** — D-1, следствия 1–3.

**У-3. Политика ЯВНО передаётся серверу, который поднимает тест.** `ServeConfig` получает
поле (или `bind` — билдер) с `AdmissionPolicy`; фикстура `config()` его заполняет; `policy()`
не остаётся неиспользованной. Одиннадцать sacred-файлов с литералом `ServeConfig {`
правит architect тем же коммитом, строка в §16.1. Прод-источник политики назван в спеке
(D-5).

**У-4. Литералы `ServingCounters` совпадают с §4.1** (шесть полей) — либо §4.1 сужается до
четырёх, а `journal_payload_bytes_read`/`slots_in_flight` объявляются отдельно; форма
«дословно» не может расходиться с оракулом, который против неё компилируется.

**У-5. Каждый тип §4.1 имеет оракул или вычёркивается из «дословно».** Минимум:
- `CallBudget`/`BudgetStop`: исчерпание `max_events` и `max_payload_bytes` на докормке хвоста
  ⇒ `overloaded` на WS, `BudgetStop` назван; `max_output_bytes` — переиспользование
  `enforce_response_limit` (`П-020`), не второй предел; `max_wall_ms` — не критерий оракула
  (§5 п.1, остаётся продовым предохранителем); `max_state_bytes` — либо оракул на границе
  ресурса, либо явная запись в §11 «предел объявлен, оракула нет».
- `Cancel`: юнит-оракул в транспорте — признак, взведённый после k порций, останавливает
  ограниченный обработчик с `BudgetStop::Cancelled` до конца хвоста; порция = один вызов
  `pump` библиотеки (её не трогаем).
- `ServingSlots`: см. У-6.

**У-6. C4 детерминирован.** Нынешний `c4_*` принимает и `overloaded`, и `snapshot`
(`:393-397`) и снимает `slots_in_flight` без синхронизации с началом работы (`:384`) —
он не может упасть против «слот освобождён по таймауту» и может упасть по гонке. Требуется
ЗАЩЁЛКА, удерживающая первую работу в полёте наблюдаемо (форма — выбор architect'а: журнал,
чтение которого блокируется до отпускания тестом; или иной механизм с тем же свойством), при
которой второй запрос ОБЯЗАН получить `overloaded`, `slots_in_flight == 1` снят при
удержанной защёлке, а после отпускания слот освобождается. Никаких «либо».

**У-7. C9 различает позиции конструкцией фикстуры.** Слепок строится, затем журнал
дописывается, затем сервер поднимается: обязана выполняться СТРОГАЯ `snapshot_ms <
source_ms` и запрос обслужен. Одна общая константа на четыре поля этот тест не проходит.
C6: снятие `serving_counters()` до/после реального WS-запроса ДОСТАТОЧНО для `OPS-I-10`
(продюсер на реальном пути инкрементирует) — критик здесь перечитал норму; но поверхность
ЭКСПОРТА наружу процесса (чем ops/тревога читают счётчики, `PL-I-8`: алерт живёт вне
машины) спека не называет вовсе — назвать и дать один оракул продовой формы, либо явная
TD «built-not-wired» MAJOR по `gates.md` §4 DoD.

**У-8. Гейт.** Шаг 10: решение ищется В ТОЙ ЖЕ строке таблицы, что имя файла, и обязано
содержать один из токенов `ПЕРЕНОСИТСЯ|НЕ ЗАТРАГИВАЕТСЯ|УДАЛЯЕТСЯ` (M-10b/M-10c должны
краснеть); отдельная проверка на два тест-уровневых решения D-4 (`o5`,
`resume_without_checkpoint…`) по имени теста. Шаг 9: считаются ТОЛЬКО ключи уровня сервиса
(отступ ровно 4 пробела) либо `deploy.resources.limits.*`; блоки `labels:`/`environment:`
исключены (M-9a должна краснеть). Шаг «библиотека аддитивна» — команды D-1(а)/(б) как два
шага гейта. Мутационный раздел спеки предъявляет M-10a, M-10b, M-9a, M-9b прогоном.

**У-9. Спека.** §14 таблица: `red_m87_cold_path_reads_nothing.rs` снят; §14.1 «форму ловушки
выбирает dev» → «ловушка — фикстура architect'а, форма — §3.4 этого решения»; §16.1 — D-4;

уже названы). Ссылка на `A-037` в §18.
