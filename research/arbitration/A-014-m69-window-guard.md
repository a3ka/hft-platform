# A-014 — M-69 window guard: арбитраж после трёх кругов

**Арбитр:** независимый Fable-агент со свежим контекстом (`gates.md` §0). **Триггер:** §0
п.2 — три круга по одному предмету (`C-099` REJECT → `C-100` REJECT → `C-104` REJECT).
**Стороны:** architect (автор набора M-69) ↔ critic. Решение обязательно к исполнению
обеими сторонами.

Живой инвариант тронутого модуля (M-66): **VB-I-10** (`docs/fa/viz-backend.md` §5) —
`window_ms=Some(W)` ограничивает память окном, `None` — только легитимный offline.
FA крейтов `gateway`/`gateway-serve` не существует — это уже названный долг
(`docs/workflow/reading-map.md` §2, строка «derive / recorder / gateway-serve»), сюда
только подтверждается.

## §2. По пунктам `C-104` — кто прав

### B-6 (`DESIGN.md:924`, GW-I «в оракулах = 12») — критик ПРАВ

Воспроизведено арбитром на ветке: `bash scripts/verify_design_claims.sh` →
`FAIL [2-ПОКРЫТИЕ] §22: GW-I … strict=13, loose=13`, `VERDICT: FAIL (1)`. Джоб в CI —
`.github/workflows/ci.yml:244` — входит в агрегат, значит даже GREEN-реализация не
вольётся, пока строка не синхронизирована. Красное создано самим набором M-69 (два новых
оракула несут `GW-I-14`).

**Решение:** architect правит строку GW-I в `DESIGN.md` §22 (`12 → 13`) в этом же
plan-time наборе и добавляет `docs/DESIGN.md` в Allowed paths (architect-only). Это
изложение, не форма (§9-триггеры: инварианты/границы/фазы не меняются — меняется счётчик,
синхронизируемый механизмом); но `docs/DESIGN.md` входит в зону перепроверки §9 — как её
закрыть без лишнего круга, см. §5.

### B-7 (фактура сообщает будущее как факт) — критик ПРАВ по существу, НЕ ПРАВ в требовании нового механизма

Факт воспроизведён: `docs/plans/gateway-ws-contract.md:132` и `:351-359` («асимметрия…
**закрыта** milestone'ом M-69», действующая политика fail-closed) — при том, что на HEAD
`crates/gateway-serve/src/lib.rs:740-744` всё ещё `s.trim().parse::<i64>().ok()`, а
`crates/gateway/src/lib.rs:1751-1764` (`validate_selector`) не смотрит `window_ms` вовсе.
Документ сам назван «фактура для RED-оракулов» и не помечен историческим ⇒ ложь на этой
ревизии тиражируема (класс `TD-155`). Требование `C-099` B-3 обновить фактуру в том же
наборе НЕ предписывало прошедшего времени — конфликт B-3↔B-7 мнимый: удовлетворяются оба
формулировкой, различающей ДЕЙСТВУЮЩЕЕ поведение и ЦЕЛЕВУЮ политику.

**Решение:** architect переформулирует обе записи так, чтобы они были правдивы на
RED-ревизии: политика названа как нормативная цель M-69 (задачи #1–#4), текущее поведение
названо дефектом (R7). Позитивный grep-шаг verify task #5 такую формулировку продолжает
находить — verify не меняется. После GREEN dev'а флип формулировки к свершившемуся факту
делает architect (путь architect-owned по Allowed paths) ДО PR-time; reviewer проверяет
правдивость на дереве слияния штатной нормой `gates.md` §8.

**Вторая половина условия `C-104` («добавить проверку, не позволяющую фактуре опережать
реализацию») — ОТКЛОНЕНА.** Это новый харнесс-механизм: `П-017` A2 (заморозка нового
харнесса), A3 (мораторий: вердикт:код уже 80:14 за 14 суток), ограничитель 2 §3bis
(барьер обязан называть УЖЕ СЛУЧИВШИЙСЯ инцидент `TD-NNN`; здесь класс пойман самим
гейтом на первом же случае — инцидента нет). Повторится третий раз — механизировать по
`binding-requires-mechanism.md`, не раньше.

### B-8 (необъявленный красный шаг acceptance) — критик ПРАВ по факту, фикс — одна строка спеки

## §3. Стоит ли предмет продолжения — ДА

1. **Дефект живой и CRIT.** Воспроизведён арбитром на HEAD: единственная ручка памяти
   live-кокпита глотает мусор/переполнение/минус в unbounded — режим двух прод-инцидентов
   (`TD-020`/`TD-039`); классификация R7 CRIT (`docs/08-arch-improvement-roadmap.md:35`);
   `PL-I-5` (`DESIGN.md` §22) требует обратного. Значение приходит из внешнего `.env`
   через `${...:-}` без задержки где-либо.
2. **Конструкция не оспорена ни одним из трёх кругов.** Двухточечный гвард
   (старт + `validate_selector`) и канонизация offline (`unset`/`""`/`"0"` → `None`)
   стоят с круга 1; все 8 блокеров — синхронизация носителей и оформление. Спор о
   «как правильно» отсутствует — остались правки на ~15 строк доков/спеки.
3. **CT-RFC-09 делает библиотечный гвард нужнее, а не лишним:** при переезде селектора из
   env в параметры WS-сессии (Ф2) `validate_selector` становится центральным
   предусловием для КЛИЕНТСКИХ значений.
4. **Ограничители §3bis — числами.** (1) Бюджет: харнесс-вклад M-69 = 85 строк
   (`verify_M-69.sh`; по Р-2 уезжает в архив при close-out); RED-оракулы (575 строк) —
   тестовая сторона продукта, в замере харнесса 19 318 строк они не считались; impl-остаток
   ~30–60 строк. (2) Инцидент назван: `TD-020`/`TD-039`, даты в карточках. (3) Носители:
   политика GW-I-14 живёт уже в шести местах (код ×2, док-комментарий, фактура, §22-счётчик,
   спека+verify) — ровно это дало два круга carrier-sync; НОВЫХ носителей не заводить,
   отклонение второй половины B-7 — следствие этого же ограничителя.
5. Закрытие предмета долгом было бы дороже: принятый sacred RED-набор выброшен, CRIT-дефект
   остаётся латентным, а остаток работы меньше уже потраченного на спор.
