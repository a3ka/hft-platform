## 1. Вопрос 1 — закрыт ли КЛАСС. Ответ: ДА (замером, не чтением дифа)

Класс спора: «страж разрушительного пути при негодном входе не ужесточается, а отключается».
Батарея (все — песочницы с `wt-fresh` (target свежий) и `wt-idle` (target −10ч), pgrep-стаб):

```
=== пороги-входы (ожидание: ОТКАЗ, кэш цел) ===
вход=٣ / ３ / ¹ / 3ч / -1 / '' / ' 3' / '3 ' / $'\t3' / 0x10 / 2#101 / 1e3 / +0
     / 9223372036854775808 / 99999999999999999999 / 000099999999999999999999
     / 'a[$(touch /tmp/arb008-PWNED)]'
→ ВСЕ: rc=2, удалений=0, fresh=ЦЕЛ idle=ЦЕЛ
(инъекция через арифметику: не сработала, файла нет — IDLE_H не входит в $(( )):
 grep по скрипту даёт только строки 55, 85, 89, 135 `[` и 142 echo)

=== валидные-краевые (семантика верна) ===

=== локали ===  LC_ALL=C / C.utf8 / en_US.utf8, вход ٣ → rc=2, целы (bash 5.2, globasciiranges on)

=== формы === --reclaim=3 / '-- --reclaim' / '3 --reclaim' / '--reclaim -- 3' → rc=2, целы
              --reclaim --reclaim → идемпотентно (дефолт 2ч); --reclaim-dry --reclaim 3 → DRY липнет
              (безопасное направление: «сухость» не снимается молча)
=== будущий mtime === touch -d tomorrow + --reclaim 0 → «KEEP-CACHE wt-idle — молчит -24ч» — цел
```

Ни один вход не отключил страж. Прежние дыры воспроизведены против прежних версий и закрыты в
текущей (см. §2 — против `b228369` проба красна 8/11, против `9fc43df` — 2/11, против HEAD 11/11).

### Найдено ВНЕ спорного класса (мандат требовал искать агрессивно — предъявляю)

**1.1 (существенное) — усечение пути с пробелом даёт `rm -rf` по каталогу ВНЕ worktree-списка.**
`scripts/gc_worktrees.sh:97,115,152` — `awk '/^worktree /{print $2}'` режет путь по первому пробелу.
Песочница: worktree `…/wt space` (target свежий) + децой-каталог `…/wt/target` (НЕ worktree, −10ч):

```
RECLAIMED  wt — 1MB (кэш; cargo пересоберёт)      ← децой /…/wt/target СНЕСЁН — его нет в списке
KEEP-CACHE wt-fresh …                              ← настоящий кэш «wt space/target» НЕ ТРОНУТ
```

Это НЕ спорный класс (страж не отключён — он применён к чужому объекту), и это известный
carry-over: R-055 N-6 → R-058 N-3, оба круга осознанно оставили NOTE. Но R-055 даунгрейдил его
на основании «практически прикрыто `[ -d "$wt/target" ]`» — **этот тезис опровергнут**: `[ -d ]`
удовлетворяется любым децоем. Новый факт против старой оценки. Вероятность сегодня низкая
(0 из 48 деревьев хоста имеют пробел в пути; конвенция имён — `/tmp/hft-<role>-<milestone>`),
но скрипт теперь предписано гонять рутинно и в момент паники (диск >85 %). Судьба — §5.1.

**1.2 (NOTE, патологический) — `stat`, вернувший ПУСТО при rc=0, превращает mtime в эпоху-0.**
Пустая переменная в `$(( now - m ))` равна нулю → «молчит ~490000ч» → снос свежего кэша
(воспроизведено stat-стабом). С настоящим GNU/busybox `stat -c %Y` недостижимо: отказ уходит в
`|| echo "$now"` → idle=0 → KEEP (fail-safe). Дешёвый пояс: `case "$m" in ''|*[!0-9]*) m=$now;; esac`.

**1.3 (NOTE, патологический) — отсутствие `pgrep` в PATH делает страж живой сборки fail-open:**
`pgrep … || true`-семантика строки 105 трактует «команда не найдена (127)» как «сборки нет» —
реальный снос при живом cargo прошёл (замер с PATH без pgrep). Страж — courtesy (защищает от
невнятного падения сборки), не страж работы; на хосте и ubuntu-runner pgrep есть.

**Итог В-1: 0 экземпляров спорного класса; 1 переквалификация известного дефекта соседнего
класса (1.1); 2 патологические характеризации (1.2, 1.3).**

## 2. Вопрос 2 — конструкция «два независимых барьера». Ответ: ВЕРНА, доказана мутационно

Проба `red_gc_reclaim_args.sh` против четырёх версий скрипта (приём `GC_UNDER_TEST`, тот же,
каким предъявлялся круг 3):

```
HEAD 39277c4                      → VERDICT: PASS (11/11)
9fc43df (круг 2)                  → FAIL (2/11): OVERFLOW «20 цифр» (свежий СНЕСЁН — дыра R-058
                                    реальна) + setup-guard CLASS-SECOND-BARRIER (мутация не
                                    применилась к старой форме функции — отказ, а не тихая зелень)
b228369 (круг 0)                  → FAIL (8/11): 4×BAD-THRESHOLD, UNKNOWN-FLAG, DRY-PLUS-RECLAIM,
                                    OVERFLOW, CLASS-SECOND-BARRIER
мутант A (валидация → return 0)   → FAIL (5/11): 3ч/3h/2.5/OVERFLOW — кэши ЦЕЛЫ (держит инверсия),
                                    но «-1»: СВЕЖИЙ И СОСТАРЕННЫЙ СНЕСЕНЫ
мутант B (инверсия → ! [ -lt ])   → FAIL (1/11): ровно CLASS-SECOND-BARRIER
```

Разбор по пунктам мандата:

- **(а) «валидация совпадает с потребителем по построению» — ДА.** `validate_threshold`
  (`gc_worktrees.sh:70-74`) содержит `[ "$1" -ge 0 ] 2>/dev/null` — тот же `test`, что и
  потребитель `:135`; множество допустимого совпадает тождественно. Замер границы: intmax
  (19 цифр) принят и работает, intmax+1 и 20 цифр — отказ. Ведущие нули — десятичные в обоих
  местах (007 ≡ 7): расхождения представлений нет.
- **(б) «любая неудача вычисления уходит в KEEP» — ДА.** Мутант A: `3ч`/переполнение при
  ВЫКЛЮЧЕННОЙ валидации не удаляют (rc=0, кэши целы). Будущий mtime (idle=−24) — KEEP.
- **Оговорка про `-1` — ТОЧНА и теперь измерена, а не заявлена:** мутант A на `-1` сносит оба
  кэша — `[ idle -ge -1 ]` истинно всегда, инверсия семантически-верно-разобранный-но-неверный
  вход не ловит. Против него работает только валидация — причём двухслойно: и глоб (`-` не
  цифра), и числовая строка (`[ "-1" -ge 0 ]` ложно). Уточнение к формулировке architect'а
  в его пользу.
- **Третье подмножество, не покрытое НИ ОДНИМ барьером:** единственный найденный представитель —
  валидный `0` («снести всё молчащее»). Осознанно разрешён скрипту (нужен пробе как позитивный
  контроль CONTROL-REACHABLE), запрещён текстом правила (`branch-hygiene.md` п.3) — честный
  `COGNITIVE-ONLY`, зафиксированный ещё R-058 N-2. Иных представителей батарея не нашла:
  непарсибельное ловят оба барьера, отрицательное — валидация, за-intmax — оба.
- **Каждый барьер отдельно пиннится пробой:** выключение валидации роняет 5 сценариев,
  возврат инверсии — ровно CLASS-SECOND-BARRIER. Ответ на «что пришлось ослабить рядом»
  (`testing.md`, второй вопрос мутации): ничего — INTMAX-сценарий сторожит, что валидация
  не стала строже потребителя.

Барьеры действительно два, действительно независимы, и проба удерживает оба. Блокер R-058
Б-1rev2 снят по существу, а не по букве.

## 3. Вопрос 3 — методологический. Ответ: (i) с одной обязательной поправкой из (ii)

**Находки настоящие — все три блокера воспроизводимы** (R-055 Б-1: `3ч` сносил кэш при живой
сборке; Б-2: рекомендованная правилом команда в названный правилом момент не убирала ничего;
R-058 Б-1rev2: 20 цифр — свежий кэш СНЕСЁН, воспроизведено против `9fc43df`). Придирок нет;
цена находок — чужая работа агентов и часы пересборки на хосте, где этот скрипт запускают
руками в момент «диск кончился». Гейт §9 к предмету применён по букве (правка везла
`.claude/rules/**`) и по духу (единственный ручной разрушительный путь проекта).

**Но круг 2→3 был предотвратим, и вот где именно.** R-055 Б-1 дал условие снятия с примером
`case "$IDLE_H" in ''|*[!0-9]*) …` — и architect реализовал БУКВАЛЬНО эту форму: текстовую
проверку, не спросив «каким парсером порог ПОТРЕБЛЯЕТСЯ и совпадают ли множества допустимого».
Оракул круга 2 покрыл ровно четыре формы из перечня рецензента и ни одной за его пределами.
Это и есть «фикс экземпляра вместо класса» — не как черта характера, а как повторяемая ошибка
формы: **условие снятия рецензента — нижняя граница фикса, а не его спецификация.** Круг 3
сделал ровно то, что было нужно на круге 2 (парсер=потребитель + инверсия + мутант в пробе), —
то есть architect произвёл правильную форму сам, на круг позже, чем мог. При правильной форме
круга 2 спор закрылся бы в два круга.

**Обязанность architect'а на будущее (исполнимая, проверяемая):** фикс стража по вердикту
начинается с называния ПОТРЕБИТЕЛЯ значения и сверки множеств допустимого проверки и
потребителя; RED-оракул на находку обязан содержать минимум один сценарий ЗА пределами
перечня вердикта (adversarial extension). Второй симптом того же класса виден в A-007
(M-61, тот же день, пять кругов, «класс причины повторился семь раз») — это паттерн метода,
не случайность одной ветки.

**(iii) отклоняю.** «Инструмент уборки диска» здесь — скрипт с `rm -rf`, которому новая норма
предписывает рутинные запуски по памяти и под давлением. Не депозит и не журнал — но
единственный ручной разрушительный путь проекта; двухкруговая цена находок R-055/R-058 ниже
цены одного снесённого кэша при трёх живых `cargo` (замер R-055: 8.8–9.5 GB на дерево).
Одно «но» в сторону (iii), и оно адресовано founder'у в §4: сам `scripts/gc_worktrees.sh`
формально ВНЕ всех защитных зон (не sacred, не `check_*`/`verify_*`/`tests/**` из §9, не §11) —
гейт поймал его только потому, что рядом в коммите ехал файл правил. Защита сработала по
попутчику, а не по предмету.

## 4. Вопрос 4 — процедурный: предложения founder'у (§0.1 — не решения)

1. **Порог применимости §9 по «важности предмета» не вводить.** Этот кейс — контрпример:
   «скрипт уборки» оказался разрушительным путём, и это стало видно только ПОД гейтом.
2. **Узаконить норму сходимости повторного круга:** первый круг ищет по всей площади; круг N+1
   проверяет (а) условие снятия предъявленным прогоном в обе стороны и (б) СМЕЖНУЮ границу
   того же класса — но не открывает поиск заново по всей площади. R-058 фактически так и
   работал (нашёл соседнюю границу того же класса, не новую тему) — практика уже есть, нормы
   нет. Свежесть контекста проверяющего сохранить: сужается мандат, не независимость.
3. **Закрыть дыру зонирования по СОДЕРЖАНИЮ, а не по имени файла:** скрипт, несущий
   разрушительную операцию (`rm -rf`, `git worktree remove --force`, `git push --delete`, …),
   входит в зону обязательной перепроверки §9 независимо от того, как называется. Сегодня
   `gc_worktrees.sh` не покрыт ни одним паттерном зоны.
4. **Одна строка в `testing.md`** (§«Исправление по вердикту тоже требует оракула»): «оракул на
   находку обязан содержать сценарий за пределами перечня вердикта». Дёшево и бьёт ровно в
   класс, из-за которого случился круг 3 — и, судя по A-007, не только здесь.
