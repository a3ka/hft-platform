## 3. Где детерминизм может ломаться, но не проверяется (главная находка)

### 3.1 `crates/sim/src/exchange.rs:240` — HashMap-итерация по активным ордерам на общем trade-тике (КРИТИЧНО)

```rust
// crates/sim/src/exchange.rs
active: HashMap<u64, SimOrder>,               // строка 51
...
for (id, order) in self.active.iter_mut() {   // строка 240, внутри MdPayload::Trade
    ...
    fills.push(SimFill { order_id: *id, ... });
}
```

`self.active` — `HashMap<u64, SimOrder>`, БЕЗ отсортированной итерации. `CLAUDE.md`
(«Операционные принципы», Journal-first + детерминизм) явно запрещает именно это: «в
доменном коде — никакого недетерминизма (нет wall-clock/`rand()`/итерации по HashMap без
сортировки в редьюсерах)». `BacktestExchange` — доменный редьюсер симулятора (crate `sim`,
FA §I инвариант `SM-I-2`: «Детерминизм при фиксированных (journal, seed): одинаковый реплей
… даёт одинаковый `FillDecision` — реплеится»).

Rust `std::collections::HashMap` использует `RandomState` — случайный хэш-seed, генерируемый
заново на каждый запуск процесса (не детерминирован между процессами; см. документацию
`std::collections::hash_map::RandomState`). Значит: если на ОДНОМ trade-тике **два и более**
maker-ордера проходят фильтр (`order.intent.venue == md.venue && order.intent.symbol ==
md.symbol && order.intent.kind == OrderKind::Maker`), порядок обработки — а значит порядок
элементов в возвращаемом `Vec<SimFill>` — МЕНЯЕТСЯ между запусками одного и того же процесса
на одном и том же журнале+seed.

**Проверено, что единственный существующий RED-оракул на этот путь этого не ловит:**
`crates/sim/tests/red_sim.rs::run_scenario` (используется в `test_replay_deterministic_
given_seed`) вызывает `ex.submit(...)` **РОВНО ОДИН РАЗ** (строки 224-252) — в `self.active`
никогда не оказывается больше одного элемента одновременно, поэтому `HashMap`-итерация
тривиально детерминирована (единственный порядок для множества из 1 элемента) и тест НЕ
МОЖЕТ обнаружить проблему при любой реализации. Это ровно класс дефекта, который проект сам
называет «Фикстура «счастливого пути»» в `.claude/rules/testing.md` (закреплено 2026-07-14,
пункт чек-листа «2. Множественность. Два и более элемента в одном такте... — там, где наивная
реализация считает «один»»). Здесь наивная реализация буквально одна и есть, и чек-лист по
множественности не пройден.

**Прослежено дальше по потребителям `Vec<SimFill>`:**
- `crates/sim/src/strategy_backtest.rs:90-123` (канонический публичный путь `StrategyBacktest
  ::run`) и его продублированное тело `crates/research-cli/src/grid.rs:355-392`
  (`CellRunner::feed`, стриминговый путь) — ОБА гоняют `for sim_fill in &new_fills { ...
  strategy.on_fill(&report); ... self.cash_e8 += cash_delta; ... }` **в порядке `new_fills`**,
  то есть в HashMap-порядке.
- `self.fills_out.extend(new_fills)` (`grid.rs:392`, аналогично в `strategy_backtest.rs:123`) —
  сохраняет филлы В ЭТОМ ЖЕ недетерминированном порядке в отчётный `Vec<SimFill>`.
- Для ТЕКУЩЕЙ реализации `DirectionalStrategy::on_fill` (`crates/strategy/src/lib.rs:249-258`)
  агрегатный финансовый исход (позиция, cash) СЛУЧАЙНО оказывается порядково-инвариантным:
  `positions[instrument] += signed` — целочисленное сложение коммутативно, а все филлы одного
  `Trade`-события относятся к ОДНОМУ инструменту (фильтр по venue+symbol перед филлом), так
  что финальная позиция и cash действительно не зависят от порядка. **Но это случайное
  свойство КОНКРЕТНОЙ реализации стратегии, а не структурная гарантия**: ничто в типах/тестах
  не запрещает будущей стратегии иметь порядково-чувствительный `on_fill` (например,
  «последняя цена входа», трейлинг-стоп по хронологии филлов, скользящее среднее с весом по
  порядку). Более того, ДАЖЕ СЕЙЧАС нарушается более узкое, но реальное обещание продукта:
  «форензика любого убытка, аудит каждого цента» (`docs/DESIGN.md` §1) — при двух одновременных
  филлах разных ордеров оператор, реплеящий журнал ДВАЖДЫ, увидит `order_id` в разном порядке
  в `fills_out`/аудиторском выводе, то есть ответ на вопрос «какой из двух моих ордеров
  исполнился первым» будет НЕ бит-идентичен между прогонами — прямое нарушение заявленного
  тезиса «replay(journal) == реальность бит-в-бит», а не абстрактный риск.
- Нет НИ ОДНОГО RED-теста (`grep -rn "on_fill" crates/*/tests/*.rs` — только `crates/sim/
  tests/red_strategy_backtest.rs` и `crates/research-cli/tests/red_grid_strategy.rs`, ни один
  не строит сценарий с 2+ одновременно активными ордерами одного инструмента, исполняющимися
  на одном trade-тике), который бы либо (а) закрывал это тестом на равенство `Vec<SimFill>`
  между прогонами при 2+ ордерах, либо (б) фиксировал явный контракт сортировки (например,
  по `order_id` или по `submitted_seq`) в самой реализации.

**Почему это самое опасное место:** это единственная находка в ходе аудита, где нарушение
БУКВАЛЬНО совпадает с явным запретом `CLAUDE.md` («итерации по HashMap без сортировки в
редьюсерах») И задевает именно тот путь (fills → equity/strategy state → отчёт), для которого
проект уже один раз ловил родственный класс бага постфактум (M-07 equity-curve, «оракул
проверял кривую там, где на событии был РОВНО один филл» — тот же паттерн «happy-path
фикстура», тот же слой кода, тот же класс дефекта «множественность», просто другое
проявление).

## 4. Реплей на прод-масштабе

**Не проверялся тестами.** Максимум зафиксированного N в тестовом наборе журнала —
`60_000` событий (`crates/journal/tests/red_restore_next_seq_bounded.rs:91`); "prodscale"-
файлы (`red_tail_integrity_prodscale.rs`, `red_tail_integrity_operator_prodscale.rs`)
останавливают генерацию по РАЗМЕРУ файла (чуть больше 4 MiB окна скана, с потолком-guard'ом
`n < 5_000_000` СОБЫТИЙ, который есть только как предохранитель фикстуры, а не факт
достигнутого N) — они целенаправленно проверяют ОДНУ границу ресурса (`JR-I-8` — окно
хвостового скана при restore), а не полный bit-identical replay на прод-объёме.

Прод-объём — задокументирован отдельно (`docs/PENDING-SIGNATURE.md:55`: «журнал в 137+ млн
событий»; `docs/SESSION-HANDOFF.md:67`: `next_seq 137 579 079`; `PROJECT-STATE.md:2014-2015`:
рост сегментов в реальном времени под нагрузкой) — но НИ ОДИН тест не берёт сегмент такого
масштаба (десятки/сотни млн событий, ~1 GiB+ на сегмент) и не гоняет полный `replay`/`stream`
дважды с побайтовым сравнением состояния. `.claude/rules/testing.md` требует именно этого
для sacred I/O-путей («Прод-масштаб для sacred I/O-путей», TD-011-урок) — по факту требование
выполнено ТОЛЬКО для узкой границы ресурса (tail-scan), не для самого bit-identical-replay
инварианта целиком.

Отдельно: единственная проверка НАСТОЯЩЕГО прод-журнала (не тестовой фикстуры) — sha256
слепок сегмента до/после деплоя (`docs/DESIGN-v2.md`/reviewer §8 eyes-on, коммит `24ae6ed`:
«legacy-сегмент цел байт-в-байт... полный sha256 15 GB совпал до/после деплоя») — это
проверка НЕИЗМЕННОСТИ файла на диске (что деплой не тронул старые байты), а НЕ проверка того,
что `replay()` ДВАЖДЫ примененный к этому файлу даёт одинаковое ПРИКЛАДНОЕ состояние
(книги/проекции/equity). Разные вещи, легко перепутать как «доказательство DET-I-1 на проде» —
это не так.

## 5. Проекции — производные vs инкрементальные

`docs/DESIGN-v2.md` §4 объявляет `PL-I-1`: «любая проекция пересобирается реплеем бит-в-бит
воспроизводимо (расширение DET-I-1 на проекции)», статус в §12 — PENDING (весь блок `PL-I-*`
маркирован как будущие RED-оракулы, кроме отмеченных).

Единственная проекция, где incremental-vs-replay параллелизм РЕАЛЬНО проверен —
**gateway (кокпит-агрегаты)**: `crates/gateway/tests/red_gateway_live_eq_replay.rs`
(`GW-I-3`/`GW-I-4`) целенаправленно кодирует именно вопрос задания п.5 — «если проекция
считается инкрементально в рантайме, а при реплее — заново, совпадут ли результаты
бит-в-бит?» — и делает это ХОРОШО: фикстура включает асимметрию (меняется только bid-сторона),
множественность (2 сделки в одном бакете, разрезанные курсором) и границу сегмента — то есть
проходит собственный чек-лист проекта из `testing.md` (в отличие от §3.1). Плюс
`red_checkpoint_byte_identity.rs`/`red_checkpoint_is_cache.rs` добивают инвариант побайтовой
идемпотентности чекпоинта.

Что НЕ проверено для остальных проекций/производных состояний:
- **`crates/book`** (реконструированная книга) — нет теста, сравнивающего книгу, полученную
  incremental-применением дельт в реальном времени, с книгой, пересобранной ПОЛНЫМ replay'ем
  того же потока с нуля (`red_l2delta_apply.rs` проверяет корректность применения дельт как
  таковых, не incremental-vs-batch тождество).
- **`crates/sim`/`crates/portfolio`/`crates/strategy`** (equity/позиции) — см. §3.1: помимо
  находки про HashMap, здесь также нет отдельного теста «пересчёт equity-curve с нуля из
  журнала == equity-curve, накопленная инкрементально по мере поступления событий» (что
  является частным случаем `PL-I-1`, если/когда equity станет проекцией уровня платформы, а
  не только research-cli отчётом).
- **WARM/COLD-проекции** (`docs/DESIGN-v2.md` §4, ClickHouse/Parquet-класс) — статус `[ПЛАН]`,
  оракулов по конструкции нет (ничего не реализовано, значит и проверять пока нечего — не
  дефект, а честно объявленный будущий периметр).
