| | опубликовано | честно |

| цена сессии | 9.8 MiB | 6.3 MiB (данные документа) / 5.7 MiB (мой замер) |

### 2.2 `finish_ref` не дублирует `finish` — ✅ PASS (главное требование задачи)

Проверено по коду, не по отчёту. Формула существует **ровно в одном месте**:

```rust
fn finish(self) -> SeriesBundle { self.finish_ref() }          // тонкая обёртка
fn finish_ref(&self) -> SeriesBundle { /* вся формула здесь */ }
fn finish_with_at(self) -> (SeriesBundle, i64)      { (self.finish(), at_ms) }
fn finish_ref_with_at(&self) -> (SeriesBundle, i64) { (self.finish_ref(), self.at_ms) }
```

Владеющие дубликаты не оставлены, а **удалены**: `VolumeProfileAcc::into_rows(self)` →
`vp_rows(&self)` (единственный метод, не пара); `compute_vp_row`, `build_heatmap_and_cob`,
`build_volume_bubbles` переведены на `&BTreeMap` — у ОБОИХ вызывающих. Двум копиям формул
разойтись негде. Это ровно то, что требовалось, и сделано правильным способом (сужение
сигнатур до ссылок), а не копипастой с `&`.

Ключевая строка (`crates/gateway/src/lib.rs`, `LiveReducer::snapshot`):

```rust
- let (series, _at_ms) = self.full.clone().finish_with_at();
+ let (series, _at_ms) = self.full.finish_ref_with_at();
```

### 2.4 O-2 больше не покрывает то, что заявляет — ⚠️ INFO (следствие правильной реализации)

Заголовок O-2: «`finish_ref(&self)` поэлементно равен `finish(self)` — дешевле не значит
иначе», и в §2 milestone'а O-2 указан оракулом задачи #1. Докстринг обосновывает
нетавтологичность так: эталон идёт «через `gateway::snapshot`, который внутри идёт
потребляющим `finish`».

После корректного выполнения задачи #1 это перестало быть правдой. Трасса:

```
gateway::snapshot → reduce_event_stream → reducer.finish_with_at() → finish(self) → finish_ref()
LiveReducer::snapshot                    → self.full.finish_ref_with_at()          → finish_ref()
```

Оба пути сходятся в ОДНО тело. Равенство `finish` ≡ `finish_ref` теперь верно по
построению и непроверяемо в принципе — оракул для задачи #1 стал вакуумным ровно потому,
что задача #1 сделана правильным способом (делегирование вместо дублирования).

Это НЕ повод что-то менять в коде: содержательное покрытие у O-2 осталось и оно ценное —
он сверяет **состояние, накопленное живым путём** (`resume` + `pump`), с **состоянием,
накопленным полным реплеем журнала**. Это разные пути, и они по-прежнему могут разойтись.
Неточна только формулировка того, что оракул доказывает. Правка докстринга и колонки
«Оракул» в §2 milestone'а — за architect'ом (оба файла sacred).

### 3.4 Что эти числа говорят — **КРИТЕРИЙ НЕ ВЫПОЛНЕН**

**Backlog перестал быть значимым слагаемым, но не потому, что стало быстро.** Точка 3 —
решающая: backlog **509 событий** (практически ноль, снято через 18 s после чекпоинта) даёт
**1834–3555 ms**. При backlog'е в 75 раз большем (38 122) — **1837–2679 ms**. Разброс ВНУТРИ
одной точки (1834…3555) перекрывает разницу МЕЖДУ точками. Формальная подгонка это и
показывает — модель «константа + наклон» на таких данных вырождается:

```
$ fit.py "46363:3711,1901,3658" "38122:2679,1837,1845" "509:2742,3555,1834"
МНК по медианам: константа = 2565 ms, наклон = 6.47 мкс/событие
  для сравнения — ДО M-54:  250 ms + 6.67 мкс/событие

КРИТЕРИЙ: константа <= ~300 ms -> НЕТ; наклон ~1.7 мкс/соб -> НЕТ
ИТОГ: КРИТЕРИЙ НЕ ВЫПОЛНЕН
```

Числу «наклон 6.47» верить не надо — он вытянут разбросом, а не сигналом. Честная
формулировка: **при CPU 0 % и любом backlog'е в диапазоне 509…46 363 подключение стоит
1.8–3.7 s.** Это хуже и целевых ≈250 ms, и замеренных в `R-029` post-M-54 654 ms.

**Что M-56 всё-таки сделал — и это подтверждено.** Клон исчез не только по коду, но и по

(`R-029` фиксировал 91.6 MiB после M-54, и связывал их именно с

**Но пользовательская цель — нет.** Ровно та же ситуация, что reviewer описывал в `R-029`

### 3.5 Куда смотреть (дефект описан, фикс НЕ проектируется — `gates.md` §4)

Замер `R-029` (post-M-54, 654 ms) и мой (post-M-56, ~2.5 s) сняты **при разном размере
открытого сегмента журнала**, и это единственная систематическая разница, которую я нашёл:

```
$ ls -l .../segments/ | tail -3
-rw-r--r-- 1073737798 Aug  3 18:25 segment-00000166.jrnl   # закрыт в 18:25
-rw-r--r--  571453906 Aug  3 21:01 segment-00000167.jrnl   # открыт, 571 MB и растёт
```

Сегменты закрываются по 1 GiB примерно раз в 3.5 ч (165 → 14:55, 166 → 18:25). Замеры
`R-029` снимались около 19:0x–19:3x, когда сегмент 167 только начался (по темпу роста —
порядка 50–150 MB). К моему замеру он вырос до **571 MB, то есть в ~4–6 раз**; латентность
выросла в ~3–5 раз. Порядки совпадают.

**Это ГИПОТЕЗА, а не установленный факт** — я её не подтверждал контрольным экспериментом
(для этого нужен замер сразу после ротации сегмента, то есть через ~2 ч ожидания, либо стенд).
Называю её потому, что она (а) объясняет все три точки без подгонки, (б) объясняет, почему
«константа» вообще не константа, и (в) **ровно предсказана в документах, которые эта же
сессия влила в `main`**: `DESIGN.md` §16.2 шаг 3 — «устранение per-tick пересканирования …
**срочно** — прод деградирует уже при 1–2 зрителях, **а к сегменту в 1 GiB и при одном**».

Практическое следствие для методики: **«константа подключения» не воспроизводима без
фиксации размера открытого сегмента.** Замеры `R-029` и `R-030` формально соблюдают
протокол §16.3 (CPU, backlog, число клиентов записаны), но сравнивать их между собой
нельзя — условие, которое доминирует, в протоколе не перечислено. Это дыра в самом
протоколе, и её стоит закрыть тем же способом, каким закрывали CPU.
