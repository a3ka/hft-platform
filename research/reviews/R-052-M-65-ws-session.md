## 4. БЛОКЕРЫ

### Б-1 (BLOCKER, подтверждён замером) — мультиплекса нет: кадры получает РОВНО ОДНА подписка соединения

**Где:** `crates/gateway-serve/src/lib.rs:942-961` (v1-путь) и `:1283-1303` (гибридный
legacy+v1 путь).

```rust
_ = push_tick.tick(), if pending.is_none() => {
    if let Some((id, _)) = inner.subs.iter().next().map(|(k, _)| (k.clone(), ())) {   // ← ОДНА
```

На тик берётся `subs.iter().next()` — ПЕРВАЯ по итерации `HashMap` подписка, и удерживается
единственный слот `pending`. Остальные подписки соединения не пампятся никогда: они получают
свой `snapshot` при `subscribe` и после этого молчат. Комментарий на `:1281-1282` называет это
«round-robin между subs определяется HashMap-итерацией» — round-robin'а здесь нет, а порядок
`HashMap` не является выбором вообще.

**Замер** (зонд `probe2`, две подписки на одном соединении, окно 5 c):

```
[probe2] за 5 c кадров: a=21, b=0 (сообщений всего 23)
```

**Что нарушено:** Objective milestone'а; §4.1 («что клиент получает, определяется его текущим
множеством подписок»); ось 2, значение `две независимые подписки`; `CT-RFC-09` §2.4 п.3
(«дальше шлёт `frame` по новому селектору» — для непампящейся подписки не выполняется даже
после смены селектора).

**Почему `O-2` этого не поймал:** он собирает сообщения за 2 c и проверяет, что среди них
встречаются оба `sub`. `snapshot` приходит обеим подпискам немедленно — assert выполняется
до того, как вопрос о кадрах вообще ставится. Оракул проверяет присутствие идентификатора,
а не независимость ПОТОКОВ.

### Б-2 (BLOCKER, подтверждён замером) — `draining_ids` есть вечное надгробие: снятый id глушит любую будущую подписку с тем же id

**Где:** `lib.rs:786` (пометка ставится БЕЗУСЛОВНО) против `lib.rs:983` (единственное место,
где она снимается — при завершении pump'а этого же id).

```rust
inner.draining_ids.insert(id_str.clone());          // :786 — всегда
let was_known = inner.subs.remove(&id_str).is_some();
...
if inner.draining_ids.remove(&sub_id) { drop(sub); continue; }   // :983 — только в pump-completion
```

На НЕрасовом пути (подписка в карте, pump не в полёте) pump с этим id больше никогда не
завершится — пометка живёт до конца соединения. Дальше:

1. клиент подписывается тем же id повторно → `add` проходит, `subs_count += 1` (`:761`),
   `snapshot` уходит;
2. первый же завершившийся pump этого sub'а попадает в ветку `:983` → результат отброшен,
   **sub НЕ возвращён в карту** → подписка исчезает молча;
3. `subs_count` при этом не уменьшается — место под лимитом 16 потеряно навсегда.

**Замер** (зонд `probe1`, в соединении в каждый момент РОВНО ОДНА подписка — конфаундинг Б-1
снят намеренно, первая редакция зонда была им испорчена и я её переделал):

```
[probe1]  контроль: кадров по id 'x' при ПЕРВОЙ подписке за 2 c = 9
[probe1]  после unsubscribe('x') + re-subscribe('x'): snapshot=1, frame=0 за 4 c
[probe1b] кадров по СВЕЖЕМУ id 'y' после unsubscribe('x') за 3 c = 13   ← соединение живо
```

Контр-проверка `probe1b` обязательна: без неё «ноль кадров» объяснялось бы смертью соединения,
а не адресной пометкой по id.

**Что нарушено:** ось 8, значения `unsubscribe не освобождает место под лимитом` и (по
следствию) `unsubscribe не прекращает поток` в обратную сторону — поток прекращается у того,
кто на него подписан; §4.1 в обе стороны.

**Почему `O-10` этого не поймал:** он переиспользует место под лимитом ДРУГИМИ id (`f0..f13`)
и никогда не подписывается снятым `gone` заново. Значение оси «место освобождено и
ПЕРЕИСПОЛЬЗУЕМО» проверено только на свежих идентификаторах.

### Б-3 (BLOCKER) — в провод введён кадр, которого нет в контракте, и он несёт `at_ms: 0`

**Где:** `lib.rs:1024-1045`.

```rust
let heartbeat = GFrame { schema_version: …, from: new_cursor, to: new_cursor,
                         delta: SeriesBundle::default(), at_ms: 0 };
```

На КАЖДЫЙ тик (250 мс), помимо реальных кадров, клиенту уходит синтетический `frame` с пустой
дельтой и нулевым временем. `CT-RFC-09` §2.3 знает ровно три типа сообщений и говорит про
кадр «Frame как сегодня»; heartbeat — новая семантика на проводе, введённая реализацией.
Мотив назван в самом коде (`:882-889`): «Архитектор-sacred тесты ждут периодической отдачи
кадров (хоть и пустых)». Это правка контракта под оракул, а спека §5 прямо запрещает менять
нормативную часть RFC: «расхождение реализации со спекой чинится правкой РЕАЛИЗАЦИИ».

**Цена, названная числами:** (i) клиент, читающий `at_ms`, получает 1970-01-01 — величина не
«пустая», а ЛОЖНАЯ; (ii) 4 сообщения/с на каждое соединение при цели 10 000 одновременных
подключений — против egress-стены, названной в `DESIGN.md` §16 условием существования цели.

**Границу reviewer↔architect не переступаю** (`gates.md` §4): фикс не проектирую. Развилка —
архитектурная: либо фикстура набора порождает события (и heartbeat не нужен вовсе), либо
heartbeat вводится в `CT-RFC-09` отдельным типом сообщения через RFC-путь. Решает architect.

## 5. НАХОДКИ уровня MAJOR (merge не блокируют по отдельности, но входят в условие APPROVED)

### М-1 — механизм `generation` мёртв по построению

`session.rs:59-80` документирует: «0 при создании, +1 при switch, +1 при remove». В `lib.rs`
`generation` присваивается только литералом `0` (`:654`, `:731`) и **не инкрементируется
нигде** (`grep -n "generation" lib.rs | grep '+=\|wrapping_add'` → пусто). Значит ветка
`Some(cg) if cg != sub.generation` (`:992-999`), объявленная защитой от switch'а во время
pump'а, недостижима.

Следствие, выведенное из кода и замером НЕ подтверждённое: `subscribe` с существующим id,
пришедший, пока sub изъят из карты pump-задачей (`:944`), не увидит его через
`contains_key` (`:635`) и уйдёт по ветке ADD — `subs_count += 1` двойным счётом, а вернувшийся
pump положит СТАРЫЙ sub поверх нового (`:1005`/`:1010`), т.е. кадры прежнего селектора после
нового снапшота (ось 1, §2.4).

**Честно про предел моего замера:** зонд 3 (12 попыток `unsubscribe` вплотную к границам
тиков) дал **0 попаданий из 12** — окно pump'а на фикстуре из 17 событий ничтожно. Гипотеза о
рассинхроне остаётся ГИПОТЕЗОЙ; на проде то же окно есть чтение журнала с сегментом ~1 GiB.
Записываю как код-уровневую находку, а не как доказанный дефект.

### М-2 — `session::Session` не на пути: 130 строк параллельной реализации

`Session::new` не вызывается нигде в дереве (`grep -rn "Session::new" crates/` — ни одного
попадания для `session::Session`). Используются только ассоциированная `validate_selector_local`
и структура `Sub`. То есть инварианты, записанные в шапке `session.rs` («число subs ≤ max_subs»,
«удаление освобождает место СРАЗУ», «generation +1»), к исполняемому коду отношения не имеют:
их дублирует `lib.rs` — и, как показывают Б-2 и М-1, дублирует ИНАЧЕ. Это ровно класс
built-not-wired из `gates.md` §4 (случай `LiveReducer` M-38b→M-53), с отягчающим: мёртвый
модуль не молчит, а УТВЕРЖДАЕТ гарантии, которых на пути нет. Следующий, кто будет чинить
Б-2, начнёт с `session.rs` и не найдёт там дефекта.
