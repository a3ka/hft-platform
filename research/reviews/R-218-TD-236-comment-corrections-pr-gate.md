## §6 — Б-1 (БЛОКЕР): правка ввела НОВОЕ ложное утверждение на том же месте

**Файл:** `crates/gateway-serve/src/lib.rs:2372-2374` (вершина `05ed925`).

**Что написано после правки:**

```rust
// M-91 (задача 1, §1 I-1, §3, §5): успех засчитан ПОСЛЕ отправки снимка,
// не раньше — симметрично с v1-путём (`handle_v1_message`, в `spawn_blocking`
// после `resume` ADD/SWITCH). Здесь `send` вернул `Ok` ⇒ кадр сдан в сокет ОС
```

**Почему это ложь — замером на той же вершине.** В v1-пути `inc_successes` стоит в двух
местах, и ОБА — ПОСЛЕ `sink.send(...).await` и ВНЕ `spawn_blocking`:

```
$ git show 05ed925:crates/gateway-serve/src/lib.rs | sed -n '1474,1477p'     # SWITCH
                    if sink.send(Message::Text(snap_text)).await.is_err() {
                        return Err("client disconnected during switch snapshot send".to_string());
                    }
                    metrics::inc_successes(inner.counters.as_ref());

$ git show 05ed925:crates/gateway-serve/src/lib.rs | sed -n '1622,1625p'     # ADD
                if sink.send(Message::Text(snap_text)).await.is_err() {
                    return Err("client disconnected during snapshot send".to_string());
                }
                metrics::inc_successes(inner.counters.as_ref());
```

`spawn_blocking`-замыкания ADD/SWITCH закрываются ЗАДОЛГО до этих строк (`:1376`/`:1497`
открываются, результат берётся `match`'ем); `.await` на `sink.send` в sync-замыкании
невозможен в принципе. Внутри `spawn_blocking` после `resume` живёт ДРУГОЙ счётчик —
`add_journal_payload_bytes` (`:1405` и `:1555`), и комментарии v1 рядом с ним прямо
запрещают трогать там успех: «Метрика УЖЕ инкрементирована внутри `spawn_blocking` —
здесь дублировать нельзя… это двойной счёт» (`:1616-1621`).

**Комментарий стал внутренне противоречивым:** первая фраза говорит «успех засчитан
ПОСЛЕ отправки снимка», вторая — что в v1 это сделано «в `spawn_blocking` после `resume`»,
то есть ДО отправки. Читатель, сверяющий legacy-путь с v1 по этому указателю, приходит к
месту, где успех считать ЗАПРЕЩЕНО.

**Как это получилось — видно из истории, и это важно для фикса.** Прежняя (неверная)
ссылка указывала на `:1410`/`:1558`, а на тех строках до правки лежало:

```
$ git show 81132e1:crates/gateway-serve/src/lib.rs | sed -n '1405,1408p'
                            metrics::add_journal_payload_bytes(
                                counters_for_resume.as_ref(),
                                stats.payload_bytes_read,
                            );
```

То есть исполнитель открыл устаревший номер строки, увидел `add_journal_payload_bytes`
внутри `spawn_blocking` и перевёл В ИМЕНА **не ту цель**, вместо того чтобы найти
настоящий `inc_successes`.

**Факт, который был назван в закрываемой карточке и проигнорирован.** `TD-236` пункт (в)
(`TECH-DEBT.md:210`) перечисляет верные адреса буквально: «`:1477`/`:1625`
(`inc_successes`)». Правка, цель которой — точность, разошлась с собственным мандатом.

**Почему БЛОКЕР, а не замечание с новой карточкой.** Предмет этого PR — именно
достоверность комментариев. Влить правку, вводящую ложь ТОГО ЖЕ КЛАССА на ТОМ ЖЕ месте,
и завести на неё вторую карточку — значит заменить закрытие долга его переименованием.
Прежняя форма (устаревший номер) читалась как «ссылка протухла»; новая выглядит
авторитетно и уводит читателя в место, где инвариант обратный. Это РЕГРЕСС относительно
`81132e1`, а не неполное улучшение. Норма: `testing.md` §«Спека правки существующего кода»
— «Исправление по вердикту тоже требует оракула».

**Фикс я не проектирую** (`gates.md` §4, граница reviewer↔architect). Описываю дефект и
воспроизведение; формулировку выбирает исполнитель, верные адреса симметрии —
`:1477` (SWITCH) и `:1625` (ADD), оба после `sink.send(...).await`.

первым (либо в одном PR), либо на этом круге ссылку не менять.
