## БЛОКИРУЮЩЕЕ

### Б-5 (НОВАЯ). Сторож сбоя источника мёртв: `PIPESTATUS` затирается присваиванием

**Где:** `deploy/bin/journal-offsite-cron.sh:320-321`.

```
320  rsync_rc=${PIPESTATUS[1]:-0}
321  find_rc=${PIPESTATUS[0]:-0}
```

В bash `PIPESTATUS` переустанавливается ПОСЛЕ КАЖДОЙ команды, включая простое присваивание.
Строка 320 — команда; к строке 321 массив уже равен `(0)`. Замер, обе среды:

```
$ bash -c '( exit 3 ) | ( cat >/dev/null; exit 0 )
           rsync_rc=${PIPESTATUS[1]:-0}; find_rc=${PIPESTATUS[0]:-0}
           echo "rsync_rc=$rsync_rc find_rc=$find_rc"'
rsync_rc=0 find_rc=0            ← локально, bash 5.2.21; исправно было бы find_rc=3

$ ssh <прод> bash …             (тот же фрагмент)
ПРОД bash 5.3.9(1)-release: rsync_rc=0 find_rc=0
```

Поэтому ветка 329-332 — **мёртвый код**: `find_rc` не бывает ≠ 0, alert «rsync не запускался:
find exit=N» не возникает НИКОГДА. При этом комментарий 305-311 объявляет этот механизм
существующим («Дополнительный catch добавляет лов find-сбоя в alert, не дожидаясь»). То есть
это `TD-138`-класс в третий раз в этом же файле — но теперь не в прозе, а в исполняемом коде.

**Воспроизведение — прогон ПРОД-ФОРМЫ скрипта со стабами** (`find` падает, `rsync` чист,
предполётный `ssh` ок), сырой вывод:

```
$ PATH=<стабы>:$PATH JOURNAL_OFFSITE_SRC=… bash deploy/bin/journal-offsite-cron.sh
SCRIPT_EXIT=0
--- ALERT-ФАЙЛ ---            ALERT-ФАЙЛА НЕТ
--- LAST-SUCCESS ---          2026-08-30T16:08:00Z
--- ЛОГ ---                   2026-08-30T16:08:00Z OK duration=0s
```

`find` вернул `1`, не отдав ни одного файла; скопировано ноль; скрипт отчитался **OK**,
поставил свежий маркер успеха и погасил бы существующий alert (`rm -f "${ALERT_FILE}"`,
строка 351).

**Мутационный контроль, оба вопроса (`testing.md`).** Чиню РОВНО две строки — снимок массива
`_st=("${PIPESTATUS[@]}")` — и прогоняю три сценария:

| сценарий | ревизия `13af519` | те же две строки исправлены |
|---|---|---|
| **A.** `find=141` (штатный SIGPIPE), `rsync=0` — ждём OK | exit=0, alert нет, маркер есть ✔ | exit=0, alert нет, маркер есть ✔ |
| **B.** `find=0`, `rsync=12` (обрыв связи) — ждём ALERT | exit=12, alert ЕСТЬ, маркера нет ✔ | exit=12, alert ЕСТЬ, маркера нет ✔ |
| **C.** `find=1` (сбой источника), `rsync=0` — ждём ALERT | **exit=0, alert НЕТ, маркер ЕСТЬ ✘** | exit=1, alert ЕСТЬ, маркера нет ✔ |

Строка A — обратная мутация: развязка `SIGPIPE 141` (`R-151` `Н-3`, `П-024`), ради которой
снимали `pipefail`, фиксом НЕ ослабляется. Строка B — граница находки: сбои самого `rsync`
ловятся и сейчас, находка ими не про них. Находка ровно в C и только в C.

**Почему это блокер, а не замечание.**

1. **Достижимость не гипотетическая.** `find` выходит с 1, когда файл исчезает между `readdir`
   и `stat`. На этом проде компакция (03:50) переписывает `.jrnl` → `.jrnl.zst` и удаляет
   исходники, а копия ходит каждый час, в том числе 04:22 — TOCTOU-гонка встроена в
   расписание. Итог такого тика: скопирована ЧАСТЬ файлов, в логе `OK`, маркер свежий.
2. **Ложь именно в наблюдаемости.** `journal-offsite.last-success` — единственный
   предполагаемый вход для сторожа (`R-151` `Н-4`: `ops-watchdog` про offsite ещё не знает).
   Маркер, обновляемый при нулевом копировании, обманет и человека, и будущий watchdog.
   Это дословно запрещённое состояние «(а) копия устарела, а никто не знает» из
   **собственного «Инварианта достаточности» M-73**, и класс `OPS-I-8` (`docs/fa/ops.md:476`).
3. **Асимметрия цены.** Предмет — единственная офсайт-копия журнала; снапшоты коробки
   ВЫКЛЮЧЕНЫ (`П-023`), restore-drill (`OPS-I-3`) не проводился ни разу. Ошибка в сторожё
   бэкапа обнаруживается в момент восстановления, то есть в худший возможный.
4. **Гейт этого не ловит и не может.** `verify_M-73.sh` (180 строк) судит argv и тексты;
   конвейер `find|rsync` он не исполняет ни в одном шаге — проверено грепом по всем 17 `chk`.
   Зелёные 17/17 к находке не относятся.

**Требуется:**

1. **engine-dev** — снять состояние конвейера ОДНИМ снимком до любых присваиваний:
   `_st=("${PIPESTATUS[@]}")`, дальше читать `${_st[0]}`/`${_st[1]}`. Две строки; семантику
   141-развязки и `set -u` не трогать.
2. **architect** (зона `scripts/verify_*.sh` sacred) — оракул НА САМУ НАХОДКУ
   (`testing.md`: «Исправление по вердикту тоже требует оракула»). Форма проверена мной и
   стоит дёшево: прогон обёртки со стаб-`PATH` в трёх сценариях A/B/C выше с ассертами на
   `exit`, наличие alert-файла и ОТСУТСТВИЕ `last-success`. Это же закрывает свойство 4
   целостности гейта — «наблюдает ОТСУТСТВИЕ, не только сбой».
3. Повторный прогон на проде НЕ требую отдельным пунктом: правка меняет только путь ошибки,
   а зелёный путь предъявлен выше замером. Достаточно одного прогона исправленной ревизии с
