## 1. Блокирующая находка

### F-1 · BLOCKER · `.claude/rules/gates.md` §9 — удалено требование `risk-critic` на документы safety-пути

**Что было** (`origin/main:.claude/rules/gates.md:441-442`):

> **risk-critic** дополнительно обязателен, если документ трогает safety-путь: `docs/fa/risk.md`,
> `fa/killswitch.md`, `fa/oms.md`, RK-I-*/INTG-I-*, анти-оверфит гейт (§6).

**Что стало:** на ветке этого требования нет нигде. `grep -n "risk-critic"
.claude/rules/gates.md` даёт 11 вхождений, все — про КОД (§5 RISK-BLOCK: `crates/risk/**`,
`crates/killswitch/**`, `crates/oms/**`, `crates/venue-*/**`, `crates/contracts/**`) и про
RAW-гейт критика. Ни одно не покрывает правку ДОКУМЕНТА.

**Почему это блокер, а не примечание.** Требование §5 сегодня вакуумно:

```
$ ls crates/ | grep -E "^(risk|killswitch|oms)$"
крейтов risk/killswitch/oms НЕТ
$ grep -c "RK-I-" docs/fa/risk.md docs/fa/killswitch.md docs/fa/oms.md
docs/fa/risk.md:34   docs/fa/killswitch.md:8   docs/fa/oms.md:5
```

Риск-инварианты существуют ИСКЛЮЧИТЕЛЬНО как текст в `docs/fa/*`. §5 привязан к путям
`crates/**`, которых нет, — ему нечего блокировать (это же зафиксировал `R-031` §C.6:
«RISK-BLOCK сейчас вакуумен… сработала стадия, а не процесс»). Удалённый пункт §9 был
ЕДИНСТВЕННЫМ живым требованием risk-critic во всём наборе правил.

Практическое следствие после merge: правка `docs/fa/risk.md`, ослабляющая `RK-I-3`
(«неизвестный инструмент → Reject»), проходит с одним critic'ом на средней модели — а когда
крейт `risk` появится, он будет написан по этому уже ослабленному документу. Ровно тот
класс, ради которого RISK-BLOCK и заведён: цена ошибки асимметрична и отложена.

**Почему это выход за мандат.** `A-003` не упоминает этот пункт ни разу:

```
$ grep -n "fa/risk\|safety-путь\|killswitch" research/arbitration/A-003-rules-vs-workflow.md
(пусто)
```

`A-003` #16 перечисляет к удалению поимённо: «класс A "всё, включая `.claude/rules` и любую
строку", маршрут architect→reviewer на каждую правку, класс-таксономию, петлю самоправки,
ретро-раздел». Пункт про risk-critic в этот список не входит и к таксономии A/B не
относится — он уехал как сопутствующий текст при переписывании раздела.

**Подтверждение независимым следом.** `docs/SESSION-HANDOFF.md:264` (живой документ,
веткой не правился) до сих пор ссылается на это требование:
`4. **DOC-гейт (gates.md §9, класс A):** critic → **risk-critic** (обязателен: трогаем …`.
После merge ссылка указывает на несуществующую норму.

**Условие снятия:** вернуть требование в §9 отдельной строкой (формулировка `main` рабочая;
привязка «класс A» из неё убирается, т.к. таксономии больше нет). Проверка снятия:
`grep -n "safety-путь" .claude/rules/gates.md` — непусто.

### F-3 · MAJOR · противоречие о git-личности не устранено — оно переехало, а не исчезло

Ветка вводит в `branch-hygiene.md:24-28`:

Два файла правил, инжектируемые в одну сессию, предписывают противоположное. `A-003` §5
формулирует однозначно: «Git-identity предписания (**все три места**) — удалить»; §1 #27

п.6/п.7), третье осталось.

```
$ git grep -nE "noreply\.local|user\.name" -- .claude/
.claude/wrappers/pi-dev.sh:95: git config --worktree user.email "${ROLE}@noreply.local"
.claude/wrappers/pi-dev.sh:96: git config --worktree user.name  "${ROLE}"
.claude/wrappers/pi-dev.sh:104: [ "$IDENT_EMAIL" = "${ROLE}@noreply.local" ] || { echo "DRY-RUN FAIL: identity=$IDENT_EMAIL"; FAIL=1; }
```

Бутстрап dev-агента не просто ставит ролевую личность — он **валит DRY-RUN**, если её нет.
То есть агент, выполняющий новое правило branch-hygiene, не пройдёт собственный бутстрап.

## 6.2 F-10 — мутационная перепроверка (делал сам, не со слов)

Расширение сделано в ДВУХ местах, и это важно: `is_protected` решает, что защищено, а список
путей в `git ls-tree` решает, что вообще попадает в множество кандидатов. Расширить одно без

Обе половины несущие. Зеркало `is_protected` в пробе

## 6.3 Оценка решения по F-10 (запрошена отдельно)

**Согласен с расширением барьера, а не сужением текста.** Основания:

1. `research/reviews/R-NNN.md` — не документация, а **условие merge** по `gates.md` §4.
   Артефакт, которым гейт открывается, не может быть молча удаляемым: иначе гейт снимается
   задним числом тем же коммитом, который его нарушает. Это ровно механика `R-031`.
2. `research/arbitration/A-NNN.md` — решения, обязательные к исполнению обеими сторонами
   (`gates.md` §0). Тот же класс.
3. Прежняя асимметрия (защищены критики, не защищены вердикты и арбитраж) — не замысел, а
   хронология: барьер написан 07-14, практика `research/reviews/` появилась 07-31,
   арбитраж — позже. Сужение текста законсервировало бы случайность.

**Ложных срабатываний на легитимных операциях не нашёл** — проверял на стенде, не рассуждением:

```
переименование внутри research/reviews  → NOTE «остался под защитой», exit=0
правка содержимого вердикта             → OK, exit=0
переезд research/reviews → research/archive (из-под защиты) → FAIL, exit=1
```

Последнее — не ложное срабатывание, а верное поведение: увод артефакта из-под защиты и есть
исчезновение по критерию «результат, а не способ», и для него существует штатный выход
`ALLOW-ARTIFACT-DELETE`. Вложенные пути покрыты: в `case`-глобе `*` матчит `/`, поэтому
`research/reviews/2026/R-001.md` защищён.

Осознанное следствие, которое стоит назвать вслух: reviewer теперь не может бесшумно отозвать
собственный вердикт — только дополнить или удалить с явным override. Для аудит-трейла это
правильно, и я принимаю это применительно к себе (вердикт круга 1 в этом файле оставлен
нетронутым именно поэтому).

**Не блокирует, на будущее:** `research/reports/` остаётся незащищённым. Считаю верным —
отчёты дев-агентов это рабочий продукт, а не артефакт гейта; но именно поэтому формулировка
F-2 в `branch-hygiene.md` п.9, опирающаяся на этот факт, обязана пережить следующую компрессию.
