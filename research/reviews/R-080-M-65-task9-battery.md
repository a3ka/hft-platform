## 5. Что именно доказано — и чем

### 5.1 Мутация уходит в КОПИЮ дерева, прод-исходники целы

Не по чтению кода, а по результату: **после полного прогона батареи рабочее дерево чисто.**

```
$ git status --porcelain      # после verify_M-65.sh с шагом F2 внутри
(пусто)
```

Конструктивно это держится на `copy_tree()` (`git ls-files -z | tar` → `${WORK}/mutant-<name>`)
и на том, что `apply_mutant` вызывается ТОЛЬКО как `(cd "${tree}" && apply_mutant …)` — пути
внутри относительные.

### 5.2 Изоляция сборки — есть, и она не бесплатна

Каждый прогон получает свой `CARGO_TARGET_DIR` (`${WORK}/target-<name>`), то есть исполняется
СВОЙ бинарь, а не чужой — это то, ради чего каталог заводится. Цена замерена, а не оценена:
**пиковый след 15.45 ГБ** (`du -sb` раз в 30 с; 14 каталогов сборки не удаляются по ходу).
См. Н-5.

### 5.3 Сверка множеств — строгая, в обе стороны

`sets_equal()` считает `comm -23` (меньше объявленного) и `comm -13` (больше объявленного) и
требует обе разности пустыми; при расхождении печатает обе. Это выполняет требование §4.5
«ни больше, ни меньше», а не его половину.

### 5.4 Адресность: мутант убит ТЕМ оракулом, который держит его ось (сверка моя, ручная)

### Н-3 (NOTE — fail-closed setup) — у мутанта с НЕСКОЛЬКИМИ подстановками возвращается статус только ПОСЛЕДНЕЙ

**Где:** `red_ws_session_battery.sh:163-303` (`apply_mutant`), мутанты `crosstalk` (три
подстановки) и `emptyframe` (две). `replace_once` fail-closed каждая по отдельности (`perl`
считает совпадения, `exit 7` при `count != 1`), но `apply_mutant` возвращает статус ПОСЛЕДНЕЙ
команды `case`-ветки, а `set -e` внутри нет.

**Замер на РЕАЛЬНОМ коде батареи** (функции загружены из самого файла, подстановки применены к
копии `lib.rs`):

```
A: сломана ПЕРВАЯ подстановка emptyframe, вторая цела
replacement count=0
apply_mutant rc=0            ← батарея считает setup состоявшимся

B (контроль): сломана ВТОРАЯ, первая цела
replacement count=0
apply_mutant rc=7            ← fail-closed срабатывает только на последней
```

**Насколько это опасно сегодня — говорю честно:** для обоих сегодняшних многошаговых мутантов
частичная подстановка ловится ниже по течению, и я это НЕ прогонял, а вывожу из текста
(поэтому — NOTE, а не блокер): в случае A вставленный блок ссылается на `new_cursor`, тогда как
связывание осталось `_new_cursor`, и `frames.push` идёт по немутабельному связыванию — это
E0425/E0596, то есть шаг «мутант не компилируется». Но правило §4.5 «несработавшая подстановка
— отказ батареи, а не строка в логе» держится сейчас не механизмом, а совпадением; следующий
мутант с независимыми подстановками провалится молча.
**Фикс:** `replace_once … || return $?` на каждой подстановке (либо `set -e` в теле функции).

### Н-3bis (NOTE — латентный) — kill по таймауту неотличим от kill по ассерту

`run_one_mutant` записывает тест в наблюдаемый kill-set по `rc != 0`; `timeout 90` даёт
`rc=124`, и такой «kill» попадёт в множество наравне с честным падением ассерта. Сегодня
безвредно (§5.5: все проверенные убийства — `panicked at`), но батарея, объявляющая власть
оракула, обязана отличать «оракул отверг» от «оракул не дождался»: второе означает, что
kill-set пиннит длительность, а не инвариант. **Фикс:** отдельная ветка `rc=124` → `fail` с
явным «SETUP/таймаут», а не молчаливый зачёт в kill-set.

### Н-4 (NOTE — точность заявленного предела) — «предел покрытия, названный явно» назван неполно

**Факт:** без мутанта остаются **семь** значений-нарушений §4.2, из них назван один:

| ось | значение без мутанта |
|---|---|
| 2 | `кадры идут только одной подписке из нескольких` |
| 3 | `неизвестная операция молча игнорируется` (мутант есть только на версию) |
| 4 | `кадр в полёте приходит после смены` |
| 5 | `отказ одной подписки глушит соседнюю` |
| 8 | `unsubscribe неизвестного id молчит` ← единственный названный |
| 8 | `снятый id не подписывается повторно` |

Плюс **оракул `o5`** (переходный режим §2.5 — подписанное founder'ом решение, на нём стоят
