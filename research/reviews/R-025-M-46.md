## Задача #5 — SIDECAR-ПРОГОН ПРОТИВ ЖИВОГО ПРОДА (выполнена reviewer'ом)

Способ — sidecar в сетевом namespace целевого контейнера (`gateway-serve` слушает loopback внутри
контейнера; `ports`/`expose` у сервиса нет ⇒ ssh-туннель не подключился бы никуда):

```

  --entrypoint /usr/local/bin/wsprobe hft-platform-recorder:local \

```

Образ на VPS содержит бинарь (Deploy `691ff77` собрал образ до падения на шаге пересоздания
контейнеров):

```

```

### Попытка 1 — документированный путь `--secret` ПРОВАЛИЛСЯ → `TD-084`

```
$ wsprobe --url ws://127.0.0.1:8080 --secret '<GATEWAY_JWT_SECRET с VPS>' …
wsprobe: error: сервер отказал в авторизации: invalid token

# лог сервера в тот же момент:
2026-08-03T09:37:44Z DEBUG gateway_serve::server: rejected: invalid token (bad sig / wrong key / malformed)
```

Причина — **расхождение вывода ключа между харнессом и сервером**:

- сервер, `crates/gateway-serve/src/lib.rs:629`:
  `decoding_key: DecodingKey::from_secret(secret.as_bytes())` — **сырые UTF-8 байты** env-строки;
- `wsprobe`, `parse_secret` (`src/bin/wsprobe.rs:155-158`):
  `let is_hex = !s.is_empty() && s.len().is_multiple_of(2) && s.chars().all(|c| c.is_ascii_hexdigit()); if is_hex { /* hex-декод */ }`

Прод-секрет — 64 hex-символа ⇒ `wsprobe` подписывает 32 декодированными байтами, сервер проверяет
64 ASCII-байтами ⇒ подпись не сходится всегда. Ветка `--secret` **не может** аутентифицироваться
против сервера, чей секрет выглядит как hex (типовой случай сгенерированного секрета).

Почему не поймали раньше: `--self-test` использует `SELF_TEST_SECRET = b"wsprobe-self-test-secret"`
(`src/bin/wsprobe.rs:292`) — **не-hex строку**, hex-ветка в гейте не исполняется ни разу.
Ровно «фикстура счастливого пути — дефект оракула» (`.claude/rules/testing.md`).

Побочно: при отказе авторизации `wsprobe` всё равно создал `snapshot.json` (25 байт) — артефакт-обманка.

### ГЛАВНАЯ НАХОДКА — `TD-083`: любое WS-подключение намертво заклинивает прод-gateway

Симптом обнаружен как «`frames_received=0`», развёрнут до корневой причины.

**Воспроизведение — детерминированное, 100%:**

```
# 1) чистый старт
$ docker restart hft-gateway-serve && sleep 20
$ docker ps  → hft-gateway-serve  Up 20 seconds (healthy)
$ docker stats --no-stream → hft-gateway-serve 0.00%
$ CLOSE_WAIT = 0

# 2) РОВНО ОДНО клиентское подключение, клиент штатно отключается
$ wsprobe … --frames 5 --seconds 12
wsprobe: schema_version=8 … latency_first_snapshot_ms=7877 frames_received=0

# 3) через 5 s ПОСЛЕ ухода клиента
$ docker stats --no-stream → hft-gateway-serve 100.30%
$ CLOSE_WAIT = 2

# 4) состояние не проходит само: спустя 4 мин
$ docker stats --no-stream → hft-gateway-serve 100.26%
$ CLOSE_WAIT = 10          ← накапливается (healthcheck каждые 30 s)
$ docker exec hft-gateway-serve sh -c 'ls /proc/1/task | wc -l' → 1
$ docker ps → Up 23 minutes (healthy)        ← ЗЕЛЁНЫЙ

# 5) НОВЫЙ клиент подключиться уже не может — дважды подряд
$ wsprobe … → wsprobe: error: connect timeout после 30s
$ wsprobe … → wsprobe: error: connect timeout после 30s
# в логе сервера НЕТ ни "ws auth ok", ни "rejected" — accept-loop не исполняется вовсе
```

**Корневая причина — две сцепленные:**

1. **`frames_since` читает журнал с ГОЛОВЫ на каждом тике push-цикла.**
   `crates/gateway/src/lib.rs:1772`:
   ```rust
   let mut stream = journal::stream(dir, filter)?;                 // ← от НАЧАЛА журнала
   let (delta, cursor, consumed, at_ms, _) =
       reduce_event_stream(&mut stream, sel, after, Cursor::LATEST, max_events)?;
   ```
   Ср. `snapshot_from_checkpoint`, `crates/gateway/src/lib.rs:1885`:
   ```rust
   let mut stream = journal::stream_from(dir, filter.clone(), ckpt_cursor.upto_seq)?;  // ← seek
   ```
   **Фикс M-38b (GW-I-11, «прод-замер до фикса: первый Snapshot 409.74 s при >21 GiB прочитанного
   на КАЖДОЕ подключение») был применён к snapshot-пути и НЕ применён к live-push-пути.**
   На проде до курсора надо промотать ≈139M событий (`history_start_seq=16049334` →
   `cursor≈155000630`); при измеренной скорости декодирования 1 675 358 событий / 8.7 s
   ≈ 190k событий/с это ≈**12 минут на ОДИН тик**, который планируется каждые 250 ms
   (`PUSH_INTERVAL_MS`, `gateway-serve/src/lib.rs:388`).

2. **Однопоточный рантайм + синхронный вызов внутри async-таска.**
   `crates/gateway-serve/src/main.rs:17`: `#[tokio::main(flavor = "current_thread")]`
   (подтверждено на проде: `/proc/1/task | wc -l` = **1**). `serve::frames_msgs(...)` —
   синхронный блокирующий journal-read, вызванный прямо в `tokio::select!` без
   `spawn_blocking`. Он монополизирует единственный поток рантайма.

**Следствия (все наблюдались):**

- **live-push молчит навсегда** — `frames_received=0`; панель будет показывать застывший снапшот;
- **accept-loop не исполняется** ⇒ ни один следующий клиент не подключится (два connect-timeout
  подряд, в логе — тишина);
- **уход клиента не детектируется**: `stream.next()` не поллится (нет точки await), а
  `sink.send(...).is_err()` — единственная вторая ветка выхода — достигается **только когда есть
  кадры**; кадров нет ⇒ ни одна ветка не срабатывает ⇒ **таск течёт вечно, сокет висит в
  CLOSE_WAIT, ядро горит на 100%**;
- **healthcheck остаётся зелёным**: `timeout 2 bash -c '</dev/tcp/127.0.0.1/8080'`
  (`docker-compose.yml:149`) удовлетворяется ядром из listen-backlog, даже когда приложение
  никогда не вызывает `accept()`. Контейнер `(healthy)` при функционально мёртвом сервисе.

Это буквально сценарий, о котором предупреждает `gates.md` §8: «rollback ловит падение
healthcheck, но не тихую деградацию». И это **невозможно поймать на фикстурах**: на журнале в
сотни байт `frames_since` от головы отрабатывает за микросекунды, поэтому O-3
(`red_ws_frames_converge_to_latest`) зелёный и остаётся зелёным. `.claude/rules/testing.md`
требует прод-масштабный кейс для sacred-оракулов I/O-пути (урок TD-011,
`crates/journal/tests/red_open_bounded.rs`) — у M-46 такого оракула на push-путь нет.

**Границу reviewer↔architect не нарушаю** (`gates.md` §4): дефект описан и воспроизведён,
дизайн фикса и RED-оракул на регресс — зона architect. Кода не трогал.
