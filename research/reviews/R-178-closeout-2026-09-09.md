## §3 — КОРЕНЬ НЕРАБОТАЮЩЕГО РЕТЕНШЕНА: воспроизведён самостоятельно (read-only)

Мандат назвал корень; я его не принял на слово, а исполнил. Вызов взят **прод-формой** —
cron зовёт ровно `docker compose run --rm journal-retention`
(`deploy/bin/journal-retention-cron.sh:27`, `RETENTION_RUNNER`).

```text
$ ssh прод 'docker run --rm -v hft-platform_gateway-ckpt:/ckpt:ro alpine cat /ckpt/covered_through_seq'
521855745                                        ← артефакт ЕСТЬ, свеж

$ ssh прод 'cd /root/hft-platform && docker compose run --rm --entrypoint sh journal-retention -c "ls -la /ckpt"'
 Container hft-platform-journal-retention-run-9a235a5cceb4 Created
ls: cannot access '/ckpt': No such file or directory
rc=2                                             ← у уборщика его НЕТ
```

**Обе стороны композиции исправны по отдельности — рвётся связь.** Producer публикует
(`docker-compose.yml:213` `--coverage-out=/ckpt/covered_through_seq`), consumer запрашивает
(`journal-retention-cron.sh:81` `--checkpoint-coverage="${RETENTION_CHECKPOINT_COVERAGE}"`,
дефолт `:42` — тот же путь). **Пути совпадают.** Не хватает одной строки в `volumes`:

```text
$ git show origin/main:docker-compose.yml | sed -n '70,79p'
      - journal-data:/journal:ro
      - "${JOURNAL_COLD_DIR:-/mnt/journal-cold}:/cold"      ← и всё; gateway-ckpt НЕТ
```

**Механизм отказа прочитан в коде.** `journal-retention.rs:345` — файла нет ⇒ `covered = None`;
`segments.rs:3633-3644` — ветка «True fail-closed», ВСЕ кандидаты уходят в `offload_only` со
строкой `checkpoint coverage artifact absent`. **Поведение правильное:** fail-closed сработал
как задумано. Дефект — в топологии, а не в коде.

**Следствие, замеренное в проде:**

```text
$ grep -c 'checkpoint coverage artifact absent' /var/log/hft/journal-retention.log   → 7678
$ grep -c 'pruned: 0'                          /var/log/hft/journal-retention.log   → 56
$ grep -n  'pruned: [1-9]'                     /var/log/hft/journal-retention.log   → (пусто)
=== отчёт ===  mode=DryRun  offloaded: 0  pruned: 0  failed: 0  freed_bytes: 0
```

### §3.1 — Уточнение, без которого вывод был бы неверным (расхождение с формулировкой мандата)

Мандат пишет: «том не смонтирован ⇒ fail-closed ⇒ **не удалялось НИЧЕГО** с момента
постройки». Вывод верен, но **причина названа не полностью, и в такой форме утверждение
логически избыточно.** Причин ДВЕ, и они независимы:

- **(а)** `RETENTION_MODE=dry-run` (`/etc/cron.d/hft-journal-retention:41`) — намеренный
  выключатель. **Он один объясняет отсутствие удалений ПОЛНОСТЬЮ**, при любом состоянии тома.
- **(б)** отсутствующее монтирование.

Если бы дефектом было только (б), «ничего не удалялось» всё равно было бы правдой из-за (а) —
значит эта формулировка дефект (б) НЕ доказывает. **Настоящий вред (б) в другом и он больше:**
пустым оказывался **ПЛАН**, а не только исполнение. `dry-run` — единственный наблюдатель
готовности — ежедневно печатал `freed_bytes: 0`, что читается как «удалять нечего», хотя
означало «уборщик ослеп». Перевод в `apply` в таком состоянии не освободил бы ни байта, **но
выглядел бы исполненным.** Дефект глушит собственный индикатор — поэтому MAJOR.
Обратная сторона предъявлена замером 08.09 (`П-028`): холостой прогон с ПОДКЛЮЧЁННЫМ томом дал
осмысленный план (187 сегментов), отказ исчез.

Формулировка карточки `TD-202` написана по этому уточнению, а не по мандату.
