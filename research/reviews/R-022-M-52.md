### F-2 (MAJOR, доставка) — TD-067 закрыт НАПОЛОВИНУ: режим есть в образе, но не в ops-поверхности; канарейка это не ловит

Задача 7 milestone'а прямо назначает «ручную проверку reviewer'ом» — вот она. Runbook
(`docs/ops-journal-tail-unreadable.md`, Шаг 7) даёт оператору команду:

```bash
docker compose run --rm --entrypoint journal-retention recorder \
  --dir=/journal --mode=replay-digest
```

Она обходит ШТАТНЫЙ ops-сервис и запускает бинарь через сервис `recorder`. Причина
обнаруживается в `docker-compose.yml`:

```yaml
  journal-retention:
    entrypoint: ["/usr/local/bin/journal-retention"]
    volumes:
      - journal-data:/journal:ro        # <-- RO
```

А режим `replay-digest` **пишет** `journal.replay-digest.json` в `args.dir` (= `/journal`)
и при неудаче записи возвращает `ExitCode::from(1)`. Значит естественная инвокация
`docker compose run --rm journal-retention --mode=replay-digest` (та, что описана в
комментариях compose и в `deploy/README.md` для всех прочих режимов) **упадёт с exit 1** —
режим требует RW, сервис сидит на RO.

В проекте уже есть прецедент и явно записанное правило для этого случая — сервис
`journal-compaction`, заведённый ОТДЕЛЬНО ровно потому, что «режим `--mode compact`
третьего бинаря требует RW на `/journal` …, а retention сидит на RO». Для четвёртого
режима такой сервис НЕ заведён.

**Почему это не поймал гейт.** `verify_M-52.sh` T5 проверяет `Dockerfile` («бинарь
собирается и копируется в образ») и НЕ проверяет `docker-compose.yml`. Греп по дереву:
`replay-digest` не упоминается ни в одном `*.yml`. То есть канарейка «доставлено в прод»
доказывает наличие бинаря в образе, но не возможность его позвать штатным путём — а TD-067
и был заведён ровно как «класс TD-020: библиотека без оператора». Половина того же разрыва
воспроизведена на этаж выше.

**Проект уже знает этот урок дословно** — `deploy/README.md`, строки 3-4:

```text
> «Cargo test GREEN» ≠ «функция существует в проде». Бинарь `journal-retention`
> написан, R1-R7 GREEN (операторский ретеншен) и 9/9 compaction GREEN — но без
```

и там же зафиксирован полный комплект доставки операторского режима: бинарь в образе →

### F-3 (MINOR, код) — `recover()` остался ЧЕТВЁРТЫМ путём сшивки без guard'а

JR-I-11 называет три пути (`read_all`, `stream`/`stream_from`, `readable_floor`) — dev
покрыл ровно их, к реализации претензии нет. Но `journal::recover` (`crates/journal/src/lib.rs:462`)
сшивает каталог по индексу тем же `segments::iter_segments_sorted`, БЕЗ guard'а:

```rust
pub fn recover(dir: impl AsRef<Path>) -> io::Result<Vec<Event>> {
    let segs = segments::iter_segments_sorted(dir)?;   // <- guard'а нет
    for seg in segs { out.extend(segments::read_segment_events(&seg, false)?); }
```

Симптом: на re-stitch'нутом каталоге `recover` вернёт ТИХИЙ беспорядок seq
(`[0,1,2,3,4,7,5,6]` — та самая probe C-018 rev2, ради которой заведён TD-030), тогда как
`read_all` рядом откажет. Это офлайн-инструмент восстановления прод-журнала — то есть
путь, которым пользуются РОВНО в инциденте, когда сегменты и переставляют.

Смягчающее (замер, не предположение): `recover` не вызывается ни из одного `crates/*/src`
(греп по дереву) — «библиотека без оператора», класс TD-020. Порча из неё в журнал не
уходит (функция read-only, возвращает `Vec<Event>`), цена — ложный отчёт диагностики.

Отдельно: док-комментарий `recover` уже сегодня врёт — «Чужой/незадекларированный
безголовый сегмент — `Err` (через `list_segments`)», хотя функция идёт через
`iter_segments_sorted`, а не `list_segments`. Дефект ДОкоммитный (не внесён M-52).
**Зона:** architect (контракт JR-I-11 не назвал путь; оракул — RED-first).

### F-4 (MINOR, код) — guard применяется ДО фильтра эпох, а не после

`stream_from` (`segments.rs:1008`) сначала зовёт `segments(dir)` — где guard проверяет ВЕСЬ
каталог, — и только потом применяет `filter.accepts`. Следствие: каталог, в котором
намеренно смешаны эпохи с независимой нумерацией seq (`EpochFilter::Explicit` —
«осознанное смешение», `DataSource::Vendor`/`Synthetic`), станет нечитаемым ЦЕЛИКОМ,
включая `stream(dir, OwnCaptureOnly)`, который эти сегменты и так отбросил бы.

Guard проверяет строго больше, чем нужно самому `stream_from` (тому достаточно
монотонности ВЫБРАННОГО подмножества — на ней стоит его же расчёт
`last_seq = next_first - 1`).

Сегодня латентно и НЕ ломает ничего: на проде одна эпоха (замер §7), фикстур со
смешанной нумерацией в дереве нет (иначе крейт был бы красным). Всплывёт при первом
импорте вендорских данных в живой каталог.
**Зона:** architect (формулировка JR-I-11 — «каталог» без квалификации по эпохе).

### F-5 (MINOR, процесс) — бандл `tasks #1-#5` одним коммитом: частично оправдан, но не полностью

`commit-discipline.md`: «одна задача = минимум один коммит; бандл на несколько задач =
авто-reject». Формально нарушено. По существу разбор такой:

- **Задачи 1→2→3 неразделимы.** Введение бюджета меняет СИГНАТУРЫ (`ScanOutcome`,
  `VerifyOutcome`, `tolerant_max_seq_from_start`, `resync_max_seq`, `verify_large_frame`):
  коммит «только константа» не компилируется осмысленно, а задача 3 — парный vantage
  (`wb_3`/`wb_4`), собственного кода не имеет.
- **Задачи 4→5 неразделимы.** Guard БЕЗ carve-out'а на пустой сегмент роняет 6 тестов
  `crates/gateway` (доказано прогоном прототипа, §Разбор 5a milestone'а) — то есть коммит
  «guard без carve-out» оставил бы дерево красным, что запрещено §8 («main всегда зелёный»).
- **А вот 1-3 и 4-5 РАЗДЕЛИМЫ.** Это два независимых механизма, закрывающих два разных
  долга (TD-052 и TD-030), без общего кода: бюджет живёт в `resync`-ветке, guard — в
  `check_first_seq_monotonic`. Их следовало развести на два коммита.

**Названная цена, а не абстракция:** guard встал на ПРОД-путь чтения
(`segments()` ⇒ `stream` ⇒ `gateway-serve`) и является самой рискованной частью M-52 —
именно он может ОТКАЗАТЬ в чтении боевого каталога. Из-за бандла откатить его отдельно от
бюджета нельзя: `git revert a0b73b1` снимет обе защиты разом. Это делает §8 не
формальностью, а единственной страховкой (см. §7).

**Решение: НЕ авто-reject.** Обоснование: (а) 4 из 5 задач физически неразделимы без
красного дерева; (б) аудит-трейл присутствует и разделён по механизмам внутри тела коммита
(мутационные пруфы даны отдельно для бюджета и для guard'а); (в) reject означал бы
переписывание истории уже запушенной общей ветки — самостоятельный риск по
`branch-hygiene.md` — при НУЛЕВОМ изменении проверяемого артефакта. Нарушение фиксируется
как процессная находка с названной ценой, а не аннулируется.

### F-6 (NOTE, документ-против-замера) — обоснование carve-out 1 в milestone'е фактически неверно для ТЕКУЩЕГО прода

Milestone (§Замер прод-формы, §Разбор 4) утверждает: «`journal.legacy.json` **лежит на

```text

{

```

Legacy-сегментов на проде НЕТ ни одного. Более того, `segment-00000000` удалён ретеншеном

### F-7 (NOTE, наблюдение) — бюджет ограничивает работу с точностью до ×2

`resync_max_seq`, приняв крупный фрейм, догоняет основной поток `skip_forward(&mut r, to_skip)`
(`segments.rs:2031`) — эти байты читаются/раздекодируются, но в бюджет НЕ списываются
(списан был проход side-верификации того же фрейма). Оценка сверху: на каждый принятый
фрейм несписанное ≤ списанному, значит суммарная работа ≤ 2 × `READABLE_FLOOR_WORK_BUDGET_BYTES`.
Инвариант JR-I-10 («ограничена единой именованной константой») формально держится — 2×
константы есть константа, — но заявленная величина потолка вдвое ниже фактической.
Действия не требует; зафиксировано, чтобы следующий замер не был сюрпризом.
