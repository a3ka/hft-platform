## 1. Снимает ли правка заявленное противоречие — ДА; тупика не осталось

Старое состояние: §9 «правка → перепроверка → push» удерживал push, §8 «Push на origin ПЕРЕД
handoff — hard-precondition» его требовал: handoff проверяющему был невозможен без нарушения
одной из норм. Новая редакция разводит их по ОБЪЕКТАМ: §8 получает «она удерживает push в
`main`, но НЕ push ветки», §9 — «Предмет гейта живёт на ВЕТКЕ, и ветка пушится НЕМЕДЛЕННО.
Удержание до перепроверки касается ТОЛЬКО `main`». Стандартный путь исполним: коммит на ветку →
push ветки (удовлетворяет §8) → перепроверка по origin-ветке → push в `main` (удовлетворяет §9).

Края:

**(а) Правка касается только файлов в `main`, ветки нет.** Тупика НЕТ — те же коммиты пушатся
под именем ветки (`git push origin main:docs/<topic>`, SHA не меняются), после перепроверки
`main` уходит fast-forward. Но механика в тексте НЕ НАЗВАНА — правило предполагает, что предмет
рождён на ветке. По собственной доктрине проекта («пробел в спеке реализация заполняет
по-своему», `testing.md`) агент с коммитами на локальном `main` может заполнить пробел любым из
двух старых нарушений: держать push (снова §8) или пушить `main` сразу (снова §9). → NOTE-2.

**(б) Предмет в зоне замка §11.** Согласуется. Токен `FOUNDER-APPROVED` — покоммитный, живёт в
теле с рождения; ветку с токенированным коммитом пушить можно, вход в `main` проверяется
барьером по диапазону — тот же коммит проходит. Замер CI-триггеров:

```
$ sed -n '3,8p' .github/workflows/ci.yml
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
```

На push ветки CI (включая `docs-freeze`) НЕ запускается вовсе — механической проверки ветка не
проходит, но замок охраняет вход в `main`, и новая норма этот вход не открывает. Нетокенированный
зонный коммит на ветке возможен и ничем не флагуется — его ловит перепроверка (§9, пункт (б)
«замок §11») до `main`. Композиция целостна. → наблюдение OBS-1 (слепое пятно CI на ветках —
предсуществующее, норма лишь увеличивает трафик через него).

**(в) Правка процессного слоя не-architect'ом.** `PROJECT-STATE.md` и `TECH-DEBT.md` в зону §9
НЕ входят (зона: `CLAUDE.md` · `.claude/**` · `docs/04-workflow.md` · `docs/DESIGN.md` ·
`docs/0[0-9]-*.md` · `docs/fa/**` · `milestones/BACKLOG.md` · `docs/PENDING-SIGNATURE.md`) —
close-out reviewer'а не гейтится, нового тупика нет. Если close-out трогает `BACKLOG`/
`PENDING-SIGNATURE` — перепроверка применяется, но это введено базовой нормой `a1d334f` (уже в
`main`), не этим коммитом; `8bda73d` делает её ИСПОЛНИМЕЕ (ветку пушить можно). Рекурсии нет:
вердикты ложатся в `research/reviews/**` — вне зоны.

## 3. Замок §11 — токен есть, барьер зелёный НА ПРОД-ФОРМЕ

```
$ git log -1 --format=%B 8bda73d | grep 'FOUNDER-APPROVED'
FOUNDER-APPROVED: развести §8 и §9 — предмет гейта на ветке, удержание только main, 11.08
len=71   (≥12)
```

⚠️ Мандатная форма команды из общего чекаута ВАКУУМНА: скрипт строит диапазон `${BASE}..HEAD`
по HEAD чекаута, а HEAD `main` = `200e313` = `8bda73d~1` ⇒ диапазон пуст ⇒ exit=0 ни о чём.
Прод-форма (CI ставит HEAD на запушенный коммит) воспроизведена в detached worktree:

```
$ git worktree add --detach <scratchpad>/wt-8bda73d 8bda73d
$ git rev-list 200e313..8bda73d | wc -l
1                                                ← диапазон НЕ пуст
$ EVENT_NAME=push PUSH_BEFORE=200e313f… bash scripts/check_docs_freeze.sh
exit=0                                           ← per-commit токен-чек пройден
$ git worktree remove <…>/wt-8bda73d             ← прибрано
```

## 6. Новые классы отказа — блокирующих нет, два наблюдения

**OBS-1 (слепое пятно CI на ветках).** `on.push.branches: [main]` — push ветки не гоняет ни
`docs-freeze`, ни остальные джобы; нетокенированный/красный зонный коммит живёт на origin-ветке
незамеченным до входа в `main`. Предсуществующее свойство CI, норма лишь направляет в него
больше трафика; замок охраняет ровно то, что обещает (`main`). Механизировать нечем без смены
триггеров CI — по стандарту §11 это честный `COGNITIVE-ONLY`-остаток.

**OBS-2 (накопление веток).** Веток origin уже 14, включая мёртвые с июля
(`feat/M-10-r001-obi`); норма добавляет ветку на каждую уставную правку, обязанность удаления
после merge не названа (аналог рекультивации worktree из `branch-hygiene.md` для веток
отсутствует). Рост линейный и дешёвый, но ненаблюдаемый долг. Готовая формулировка — ниже.

Расхождение ветки с `main` при долгой перепроверке закрыто существующей нормой §8
(merge-preview) и пунктом (а) самого §9 — конфликта нет (см. §4).

читатель, пошедший по адресу «R-047 про П-012», найдёт находку о push-диапазоне, не о ссылке.
Готовая правка (§9, замена одного предложения):
> …этот класс сработал ТРИЖДЫ: незапушенный коммит каждый раз давал законную находку — висячая
> ссылка документа (`C-075` M1), чужой непроверенный коммит в push-диапазоне (`R-047` §2 (i),
> про `791df27`/`П-012`), устаревший `origin` при фиксе, живущем локально (`R-049` B-1).

**NOTE-2 (край (а) — механика для коммитов, рождённых на `main`, не названа).** Готовая правка
(§9, одно предложение после «касается ТОЛЬКО `main`»):
> Коммиты, уже сидящие на локальном `main`, публикуются те же — под именем ветки
> (`git push origin main:docs/<topic>`); `main` уходит fast-forward после перепроверки.

**NOTE-3 (OBS-2 — судьба ветки после merge не названа).** Готовая правка (§9, одно
предложение):
> После входа правки в `main` ветка предмета удаляется тем, кто мержил
> (`git push origin --delete <branch>`); ветка — носитель предмета на время гейта, не архив.

Замечание к мандатам (вне предмета, для оркестратора): (1) мандатная форма команды барьера из
общего чекаута вакуумна, когда родитель предмета = HEAD чекаута — прод-форма требует HEAD на
предмете (см. §3); (2) этот вердикт по мандату закоммичен на локальный `main` БЕЗ push — до
push следующий агент его в `origin` не увидит; сама норма §9 предписывает вердикту ветку
предмета. Удержание зафиксировано здесь явно.
