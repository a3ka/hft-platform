## Б-1 (БЛОКЕР) — неверное ребро вызова guard'а, в ДВУХ файлах ветки

**Где.**
1. `docs/fa/journal.md` (коммит `94ebce0`, приписка к `JR-I-11`): «guard прогоняется в
   момент ПОСТРОЕНИЯ и КАЖДОГО обновления кеша — `SegmentCatalog::refresh` зовёт
   `validate_like_full_path` (одна именованная точка…), а тот — `check_first_seq_monotonic`».
2. `docs/SESSION-HANDOFF.md` §0bis (коммит `8264969`, раздел «ЗАКРЫТО 14.08», пункт
   `TD-138`): «guard наследуется через `refresh` → `validate_like_full_path`».

**Факт по коду** (`crates/journal/src/segments.rs`, дерево слияния ≡ ветка, база не ушла):

- `SegmentCatalog::refresh` (`:552-563`) зовёт `segments_counted` (`:554`) +
  `scan_dir_layout`. Вызова `validate_like_full_path` в его теле НЕТ; guard наследуется
  через `segments_counted`, завершающийся `check_first_seq_monotonic` (`:1287`).
- `validate_like_full_path` (`:527`) вызывается РОВНО ОДИН раз — из ИНКРЕМЕНТАЛЬНОЙ ветки
  `is_fresh` (`:426`), перед коммитом дифа в кеш (`self.file_names = cur_names`, `:427`).

Воспроизведение одной командой:
```
$ grep -n "validate_like_full_path\|segments_counted" crates/journal/src/segments.rs | grep -v '^\s*//'
199:        let segments = segments_counted(dir, &mut ops)?;      # open
426:        self.validate_like_full_path(dir, &mut ops)?;         # is_fresh, инкремент — ЕДИНСТВЕННЫЙ вызов
527:    fn validate_like_full_path(...)                           # определение
554:        let segments = segments_counted(dir, &mut ops)?;      # refresh
1287:   check_first_seq_monotonic(&candidates, ...)               # хвост segments_counted
```

**Что при этом ВЕРНО** (и потому это правка двух предложений, а не пересмотр):
- вывод инварианта верен: guard идёт при построении и КАЖДОМ обновлении кеша, тремя рёбрами
  (`open`→`segments_counted`→guard; `is_fresh`-инкремент→`validate_like_full_path`→guard;
  `refresh`→`segments_counted`→guard);
- тёплый такт guard не трогает — верно (`is_fresh` `:241`: `cur_names == self.file_names` →
  ранний `Ok((true, ops))` без guard'а), и обоснование «`is_fresh` доказывает неизменность
  состава» для этого пути точное;
- `validate_like_full_path` — якорь батареи мутантов — верно (док-комментарий `:515-521`);
- прод ходит через `stream_from_at_with_catalog` — верно (`crates/gateway/src/lib.rs:3150`);
- `SM-11`/`SM-11c` существуют и пиннят заявленное
  (`crates/gateway/tests/red_catalog_equivalence.rs:696,982`);
- счётчики имён из тела коммита (3/5/9/10/11/12) сходятся при `grep -c`;
- `stream_from_at` на `:1947` — верно.

**Почему блокер, а не NOTE.** Это в точности класс `TD-138`: «документ называет механизм,
который не исполняется». Прежняя редакция стала ложной номерами строк, потом механизмом;
новая ложна ребром вызова — с первого дня. Хуже: ветка ПРОТИВОРЕЧИТ САМА СЕБЕ — спека
`milestones/M-62-segment-metadata.md`, задача 15 (коммит `bcf3f06` этой же ветки), называет
механизм ПРАВИЛЬНО: «ИНКРЕМЕНТАЛЬНАЯ ветка наследует ПРОВЕРКИ полного пути одним именованным
вызовом (`validate_like_full_path`)». Тот же правильный текст — в §0 «Ранее» строки M-62.
Мандат перепроверки называл этот случай явно: ошибка в механизме — блокер.

**Условие APPROVED.** В обоих файлах заменить ребро на фактическое, например: «guard
