## БЛОКЕР Б-1 — компакция ОДНОГО сегмента стирает его из кеша сессии (тихая потеря событий)

**Где:** `crates/journal/src/segments.rs:286-299` (инкрементальная ветка `is_fresh`).

Порядок операций: сперва цикл по `added` кладёт новый `SegmentInfo` в `self.segments`
(`:286-293`), затем цикл по `removed` удаляет ПО ИНДЕКСУ
`self.segments.retain(|s| s.index != idx)` (`:294-299`). При компакции `segment-N.jrnl` →
`segment-N.jrnl.zst` индекс у добавленного и удалённого **ОДИН И ТОТ ЖЕ** (`:290-291` это
прямо признаёт), поэтому `retain` сносит и только что добавленную `.zst`-запись. Сегмент
исчезает из кеша целиком.

Самоизлечения нет: `is_fresh` возвращает `true` и переписывает `self.file_names` (`:302`),
поэтому следующий тик расхождения уже не увидит — испорченный кеш живёт до конца сессии.

**Замер (сырой вывод, §Done Block):**
```
[A] компакция ОДНОГО сегмента (index=1)
[A] is_fresh=true ops=6  (fresh=true ⇒ пошла ИНКРЕМЕНТАЛЬНАЯ ветка)
[A] truth (journal::list_segments) = [0, 1, 2, 3, 4, 5, 6, 7]
[A] cache (SegmentCatalog)         = [0, 2, 3, 4, 5, 6, 7]
```

**Достижимость на проде:** ночная компакция (cron 03:50) идёт посегментно —
`compact_closed_segments` зовёт `compact_segment` в цикле, а между двумя вызовами лежит целый
такт живой сессии (250 мс). Отставшая сессия (catch-up после чекпоинта) недосчитается всех
событий этого сегмента — «тихая деградация при зелёном healthcheck», класс `TD-031`,
дословно названный в §7 спеки как то, ради чего M-62 вводит guard.

## БЛОКЕР Б-2 — промежуточное состояние компакции даёт ДУБЛЬ индекса (обход `D-COMP-1`)

**Где:** там же, `segments.rs:286-293`; правило, которое обходится, — `dedup_indexed_paths`
(`segments.rs:907-923`, «при коллизии по индексу побеждает СЫРОЙ `.jrnl`, `.zst`
игнорируется»).

`compact_segment` шагом 6 делает `rename .tmp → .zst`, и только шагом 7 удаляет оригинал
(`segments.rs:3964-3972`). Комментарий там же: «Между шагом 6 и 7 на диске лежат ОБА файла …
**минуты** до окончания операции». Тик, попавший в это окно, видит `added=[.zst]`,
`removed=[]` ⇒ инкрементальная ветка кладёт `.zst` РЯДОМ с уже лежащей `.jrnl` того же
индекса. Дедупликация не зовётся — это единственный путь, обходящий общий хелпер.

**Замер:**
```
[B] is_fresh=true ops=6
[B] truth (D-COMP-1: при коллизии побеждает RAW) = [0, 1, 2, 3, 4, 5, 6, 7]
[B] cache                                        = [0, 1, 1, 2, 3, 4, 5, 6, 7]
```

Это ровно тот дефект, который на PR-гейте M-08 (rev 9) был блокером и породил сам хелпер:
«3000 событий читалось как 3172, и `DET-I-1` молча нарушался» (`segments.rs:907-923`). Сессия
получит события сегмента ДВАЖДЫ.

## БЛОКЕР Б-3 — любой новый НЕ-сегментный файл в каталоге роняет `pump()` сессии

**Где:** `segments.rs:286-288` — `classify_segment` зовётся на КАЖДОЕ новое имя без фильтра
`parse_segment_index_any`; сам `classify_segment` на не-сегментном имени возвращает
`Err("not a segment file")` (`segments.rs:791-792`). Ошибка не гасится:
`stream_from_at_with_catalog` пробрасывает `cat.is_fresh(dir)?` (`segments.rs:1753`) ⇒
`LiveReducer::pump` (`gateway/src/lib.rs:3150`) возвращает `Err`.

До M-62 такие файлы были безвредны: `dedup_indexed_paths` их просто не выбирает.
