## Что в этой работе сделано ХОРОШО (фиксирую, чтобы не потерялось при переделке)

Это не «плохая ветка» — это в основном добротная ветка с двумя дырами в критических местах.

- **Прод-реальность сверена точно.** Форма heartbeat'а совпадает с тем, что recorder пишет
  байт-в-байт; имена контейнеров (`hft-recorder`, `hft-gateway-serve`) и cron-маркеров
  (`compaction`/`gateway-checkpoint`/`retention.last-success` в `/var/lib/hft`) — ровно те, что
  на VPS. Ни одного «придуманного» пути.
- **Ложных тревог на здоровом проде нет.** Прогон бинаря на СЕГОДНЯШНЕМ heartbeat'е и реальных
  маркерах: `норма, ни одно условие не сработало` (сырой вывод — RUN 1 ниже).
- **Транспорт без токена действительно безопасен** — не паникует, не ошибается, честно логирует
  «не сконфигурирован» (проверено и тестом, и живым запуском).
- **Чистые функции / I/O разделены дисциплинированно** — часы и данные параметрами,
  `SystemTime::now()` только в бинаре. Детерминизм соблюдён.
- **Парность «здоровый вход → None»** есть у КАЖДОГО детектора + сводный
  `fully_healthy_snapshot_yields_zero_alerts_across_every_check` — требование задачи §1 по букве
  выполнено.
- Хардкоженых секретов нет; fmt/clippy чисто; 115 тестов крейта зелёные.

Дыры — не в детекторах поштучно, а в **слое, который их склеивает** (бинарь), и в **обработке
ошибки транспорта**. Ровно там, где тестов нет вообще.

## Блокеры

### F-1 — BLOCKER. `WD-SEQ-STALLED` выключается интервалом cron'а; тихая деградация не ловится

**Файлы:** `crates/ops/src/bin/ops-watchdog.rs:169-198` (оркестрация) +
`crates/ops/src/watchdog.rs:260-264` (анти-флап-гейт).

**Механика.** `check_seq_stalled` при `gap_ms < thr.seq_stall_min_gap_ms` (60 с) возвращает `None`
— «слишком рано судить». Но вызывающий в `run_heartbeat_checks` **безусловно** двигает базу
сравнения:

```rust
state.prev_heartbeat = Some(hb);      // ops-watchdog.rs:197
state.prev_check_ms = Some(now_ms);   // ops-watchdog.rs:198
```

База обновляется даже тогда, когда вердикт был «не смог оценить». Значит `gap_ms` на следующем
прогоне равен интервалу cron'а — и если интервал < 60 с, `gap_ms` **никогда** не дорастает до
порога. Детектор не «шумит реже» — он не срабатывает вообще.

```
### Тот же простой, но интервал 5 минут (как в runbook'е):
[CRITICAL] WD-SEQ-STALLED — next_seq не вырос за 300050 мс (140764910 → 140764910) — ... (тихая деградация, healthcheck её не ловит)
```

Пять симулированных минут полностью вставшего сбора при 30-секундном cron'е — **десять раз
«норма»**. При 5-минутном — срабатывает.

**Почему это блокер, а не NOTE.**
- Это ЕДИНСТВЕННЫЙ детектор задачи §2 («самый опасный класс») — остальные ловят падение
  процесса, которое и так видно.
- Интервал cron'а — **не часть контракта кода**: runbook его лишь *предлагает*
  (`docs/runbooks/alerting.md:57`), а `scripts/watchdog_cron.sh` строку крона не устанавливает
  (комментарий `:12`). Оператор, который поставит `*/1` или `*/2` «чтобы узнавать быстрее»,
  получит **противоположный** эффект и ни одного сигнала об этом.
- Порог `seq_stall_min_gap_ms` = 60 000 при рекомендованном интервале 300 000 — запас всего 5×
  в одну сторону и 0× в другую; ничто не мешает интервалу уехать.
- Отказ **тихий**: watchdog печатает «норма», т.е. выглядит работающим. Это в точности та
  «шумная тишина наоборот», ради которой служба и пишется.

**Смежное следствие (см. F-5):** тот же `None` дополнительно СТИРАЕТ дедуп-память ключа.

### F-2 — BLOCKER. `TELEGRAM_BOT_TOKEN` попадает в лог cron'а при сетевой ошибке

**Файлы:** `crates/ops/src/transport.rs:102-108`, `crates/ops/src/bin/ops-watchdog.rs:91-93`.

Токен вшит в URL (это требование Telegram Bot API, само по себе нормально):

```rust
let url = format!("https://api.telegram.org/bot{token}/sendMessage");   // transport.rs:102
...
.send()
.map_err(|e| TransportError::Http(e.to_string()))?;                     // transport.rs:108
```

`reqwest::Error::to_string()` **дописывает URL целиком**. Проверено по исходнику
`reqwest-0.12.28/src/error.rs:267-269`:

```rust
if let Some(url) = &self.inner.url {
    write!(f, " for url ({url})")?;
}
```

Дальше строка уходит в stderr бинаря (`ops-watchdog.rs:92`), а обёртка перенаправляет stderr в
файл: `"${WATCHDOG_BIN}" >>"${LOG}" 2>&1` (`scripts/watchdog_cron.sh:43`, `LOG` по умолчанию
`/var/log/hft/watchdog.log`).

**Воспроизведение (сырой вывод, зонд reviewer'а, в репозиторий не коммитился):**

```
PROBE Display = error sending request for url (https://api.telegram.org.invalid/bot1234567890:AAHsuperSECRETtokenVALUE/sendMessage)
```

Токен виден целиком. Триггер — не экзотика: DNS, TLS-хендшейк, таймаут 10 с, обрыв сети. Сторож
работает круглосуточно, т.е. рано или поздно это произойдёт, и произойдёт именно тогда, когда
логи будут читать внимательно (инцидент). Путь 401/403 от API безопасен (там форматируется
`status` + `body`, `transport.rs:112-114`) — течёт **только** транспортная ошибка, и это легко
не заметить глазами.

Требование задачи §4 («ни токена, ни chat_id в коде и в логах») по второй половине НЕ выполнено.
Хардкода в коде действительно нет — `grep -rni "telegram\|token\|chat_id\|secret\|api_key"` по
`crates/ops/src/`, `scripts/`, `docs/runbooks/` даёт только имена переменных окружения и
комментарии.

### F-3 — ложная тревога по диску во время ночной компакции/ретеншена

**Файл:** `crates/ops/src/watchdog.rs:306-337`.

Прогноз строится по производной **между двумя соседними сэмплами** (5 минут), без сглаживания и
без нижней границы по абсолютному запасу. Любой всплеск записи в одно окно масштабируется на
сутки.

Замер на РЕАЛЬНЫХ прод-числах (`free=83.1 ГБ`, `min_free=10.7 ГБ`, запас 72.4 ГБ):

```
убыль 40 МБ за 5 мин -> нет алерта
убыль 100 МБ за 5 мин -> [WARNING] WD-DISK-LOW — диск кончится через ~57.5ч ... (~341 КБ/с)
убыль 300 МБ за 5 мин -> [CRITICAL] WD-DISK-LOW — диск кончится через ~19.1ч ... (~1022 КБ/с)
убыль 1000 МБ за 5 мин -> [CRITICAL] WD-DISK-LOW — диск кончится через ~5.7ч ... (~3407 КБ/с)
```

Базовый темп, измеренный автором на проде, — ~117 КБ/с. WARNING наступает уже на 341 КБ/с
(≈3× базы), CRITICAL — на ~1 МБ/с. Компакция (`deploy/bin/journal-compaction-cron.sh`, 03:50 UTC)
и ретеншен (04:07 UTC) пишут `.zst`-копии сегментов по 1 ГиБ — 300 МБ за пять минут для них
рядовая величина. Ожидаемый результат: **CRITICAL «диск кончится через 19 часов» при 82.8 ГБ
свободных, ночью, каждые сутки.** Это ровно тот механизм, которым алертинг убивают: пара таких
ночей — и сообщения перестают читать.

Ни один тест этого не ловит: `disk_projects_critical_hours_from_measured_decline_rate`
(`red_ops_watchdog.rs:172-195`) подбирает `headroom` ПОД желаемый вердикт, вместо того чтобы
взять прод-запас 72 ГБ и спросить, что будет при всплеске. Это фикстура «счастливого пути»
в чистом виде — тот самый класс, что закреплён в `.claude/rules/testing.md` после M-07/M-08.

## Ответы на вопросы мандата

1. **Ложные тревоги.** Парный тест «здоровый вход → не срабатывает» есть у КАЖДОГО детектора
   (по 1-3 на детектор) + сводный `fully_healthy_snapshot_yields_zero_alerts_across_every_check`.
   На живом проде — ноль алертов (RUN 1). Пороги heartbeat (60 с/180 с) и cron (26 ч/48 ч)
   обоснованы замером/конвенцией корректно: 10-секундный тик recorder'а взят из кода,
   60 с синхронизировано с docker-healthcheck, 26 ч — из `journal-retention-cron.sh`. **Но
   диск-пороги обоснованы замером УСТАНОВИВШЕГОСЯ режима (117 КБ/с) и не проверены против
   всплеска** — см. F-3, это и есть реальный генератор ложных тревог.
2. **Пропуск тихой деградации.** Детектор существует и на 5-минутном окне работает — проверено
   живьём. **Но выключается при интервале cron'а < 60 с, молча** — F-1, блокер.
3. **Транспорт без токена.** Не падает, не паникует, возвращает `Ok`, логирует «не
