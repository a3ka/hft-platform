## §В-1 (главный). «Окно просмотра НЕ фиксируем» — собирается ли КАЖДЫЙ ряд из более мелкого

Два факта кода, от которых зависит весь ответ:

- **Все ряды с временной осью ключуются ОДНИМ бакетом селектора** — `bucket_time_s`
  (`crates/gateway/src/lib.rs:1183-1190`: `ts.div_euclid(timeframe_ms) * timeframe_ms / 1000`).
  Значит опорный уровень плана — самый мелкий таймфрейм каталога (1 s); всё грубее
  СОБИРАЕТСЯ из него, если ряд алгебраически это допускает. `GW-I-10` (`86_400_000 %
  timeframe_ms == 0`, `session.rs:97`) гарантирует, что все девять таймфреймов плана
  (1s…1d) выровнены к суткам, а суточная сессия (`utc_session_id`, `:263`) никогда не
  пересекает грубый бакет — сессионные ряды не рвутся при укрупнении.
- **Окно `window_ms` — ЭВИКЦИЯ, не семантика** (`evict_window_state`, `:1122-1181`): для
  бакетных рядов — `retain(t >= lo)`, для сессионных — фолд в `base` (CVD) и whole-session
  drop (VP/CVD по `session_max_time_s[sid] < lo`). То есть «свободное окно» = «не эвиктить
  раньше, чем просит самый широкий клиент» + вычислять `cvd_session_base`/`vp_session_max_time_s`
  ПО ЗАПРОСУ из мелкого состояния. Автор плана прав в постановке: сменить окно — сменить
  набор блоков, не состояние.

### В-1.8 — heatmap: семантика ячейки ФАКТИЧЕСКИ расходится между двумя путями, и это предъявлено прогоном

Мандат спрашивает: last / max / time-weighted? Ответ по коду — **ни одно из трёх, а два
разных**:

- путь `finish` (полный реплей, `snapshot`): ячейка = уровень КНИГИ НА ЗАКРЫТИЕ бакета;
  уровень, снятый до закрытия, ОТСУТСТВУЕТ (`:2228` фильтрует `size <= 0`);
- путь кадров (`pump` → `book_series_in` `:1908-1918` → `Snapshot::apply` → `merge_heatmap`
  `:2735-2744`): ячейка = ПОСЛЕДНЕЕ ПОЛОЖИТЕЛЬНОЕ наблюдение по ключу `(time_s, side, price)`;
  удаление уровня НЕ ПРЕДСТАВИМО (ячейки нулевого размера не эмитятся), поэтому уровень,
  снятый между двумя кадрами одного бакета, остаётся у клиента навсегда.

Проба (scratch-тест в worktree, файл удалён, не коммитился — `*/tests/` не моя зона в
этом мандате): журнал из `L2Snapshot` (bid 64990:5, 64980:3; ask 65010:4, 65020:2) и
`L2Delta` через 300 мс в ТОМ ЖЕ бакете (bid 64990→9, ask 65010→0); прод-путь
`LiveReducer::resume` (без слепка) → `pump(max_events=1)` → `Snapshot::apply` всех кадров;
эталон — `gateway::snapshot(LATEST)`:

**Следствие для плана.** «Глубина/heatmap — ЯВНО выбранная статистика (close | extrema |

## §В-2. Порядок поставок

раз на ключ за тик». Предупреждение об `Arc<Mutex<LiveReducer>>` верно: `pump` берёт
`&mut self` и мутирует `full` (`:4654`), а `Sub.live: Option<LiveReducer>` уезжает в
замыкание целиком (`session.rs:54-59`).

**Улучшение:** S1 → S1a (SCALE-05, до S2) + S1b (SCALE-06/07, вместе с bump S3).

## §В-5. `DET-I-1` и условие `View(Materialized(E<=C)) == View(Replay(E<=C))`

Плавающая точка — НЕ угроза: `f64` живёт только в функциях МГНОВЕННОГО состояния книги
(пороги полос `:1352`, окно heatmap `:2196-2197`, `band_pct_e8` `:2231`), ни один
аккумулятор не суммирует `f64` (`grep -n f64 crates/gateway/src/lib.rs` — только `band`,
`reach`, `window_frac`, `mid_f`). VWAP/VP — `i128`, OHLCV/CVD/bubbles — `i64`. Регруппировка
этих сумм точна.

Угрозы — три, и все семантические:

1. **Срез E имеет ДВА конца, план называет один.** VWAP — «от старта курсора» (`VB-I-6`),
   и старт = «самый ранний seq, доступный под `EpochFilter`» (`VB-I-11`, `history_start_seq`
   пересится из слепка `:3542`, на no-ckpt пути — первое видимое событие `:4596-4600`).
   Retention-prune между материализацией и реплеем меняет E СЛЕВА ⇒ `Replay` даст другой
   VWAP при том же C. Условие плана обязано звучать `View(Materialized(E[s..C])) ==
   View(Replay(E[s..C]))` с `s = history_start_seq`, и manifest блока (SCALE-15 «source cut»)
   обязан нести ОБА среза. `VB-I-11` уже это требует для честности выдачи — план должен
   унаследовать.
2. **Heatmap — §В-1.8:** объединение ячеек ≠ замена множества; материализованный вид,
   собранный из кадров, УЖЕ отличается от реплея на прод-пути. Для приёмки SCALE-21 это
   значит: четырёхстороннее равенство (replay / из слепка / материализованное / собранное
   клиентом) по heatmap сегодня НЕ выполняется, и первым оракулом SCALE-21 должен стать
   ровно тот scratch-сценарий (снятие уровня внутри бакета между кадрами).
3. **Каденция и незакрытый интервал.** С `depth_cadence_ms` последний незакрытый интервал
   НЕ эмитится ни на live, ни на replay (`maybe_commit_depth_interval` `:1660-1680`, комментарий
   «единственный согласованный выбор — НЕ эмитить», `R-141` Б-2). Рядом с ним «нативный»
   ряд (без каденции) точку в текущем бакете ИМЕЕТ. Если клиент собирает 10-секундную
   каденцию из нативного ряда сам (S3/S4 «частота доставки отделена от обработки»), он
   получит на одну точку больше, чем сервер с `depth_cadence_ms=10000`. Правило «интервал,
   содержащий `at`, не отдаётся» должно быть записано в SCALE-13 как часть определения
   ряда, иначе `собранное клиентом ≠ материализованное` по построению.

Что это значит для приёмки: три оракула SCALE-21 названы выше поимённо; без них равенство
проверяет только счастливый путь. Прод-каденция сегодня `GATEWAY_DEPTH_CADENCE_MS=1000`
(`docker-compose.yml:165`) при `timeframe_ms=1000` (`:135`) — оба совпадают, и п.3 на проде
пока не различим; различим он станет ровно при появлении каталога таймфреймов.

## §В-6. Достаточно ли SCALE-02 против реального дефекта

Факт подтверждён: pump и resume уходят в `spawn_blocking` (`:843`, `:938`, `:1217`, `:1468`,
`:1831`); уход клиента детектируется ветками `stream.next()` (`:1145/:1155`, `:1633/:1647`)
и функция сессии ВОЗВРАЩАЕТСЯ, а `JoinHandle` блокирующей задачи просто бросается —
`abort()` на blocking-задачу в tokio не прерывает уже исполняемое замыкание, и ни одного
`abort`/флага в коде нет (`grep` → 0). Наблюдение прода 20.09 объясняется кодом полностью.

**Точки для кооперативной проверки СУЩЕСТВУЮТ и естественны:**
- `pump` — граница батча `batch_consumed == max_events` (`:4788`): один `AtomicBool`/`&dyn
  Fn() -> bool` в сигнатуре, проверка раз в 256 событий, выход с сохранением
  `cursor`/`full_applied_seq` (двухпозиционная конструкция `R-143` уже делает возврат с
  границы безопасным — «останавливает на безопасной границе и сохраняет позицию» плана
  выполнимо без новой механики);
- `resume` без слепка — цикл `for event in &mut stream` (`:4594`) — тот же флаг раз в N
  событий; ПОСЛЕ SCALE-01 этот путь с serving исчезает, и точка нужна только worker'у;
- legacy-setup — `loop { live.pump(..) }` (`:1519-1530`) — между итерациями.

**Достаточно ли?** Против ДЕФЕКТА — да, при трёх условиях, которых в SCALE-02 нет или они
названы не тем словом:
1. флаг отмены живёт в объекте, который переживает возврат функции сессии, и взводится в
   `Drop` сессии — иначе «между порциями» не у кого спросить;
2. «timeout не освобождает слот» механически = permit `tokio::sync::Semaphore`, ВЛАДЕЕМЫЙ
   блокирующим замыканием и отпускаемый его `Drop`, а не `await`-ом снаружи; семафора
   сегодня нет (`grep` → 0), это НОВЫЙ объект, не проверка;
3. **бюджет по памяти кадров:** `pump` копит `Vec<Frame>` до полного дренажа (`:4833`,
   `:4898`) — SCALE-02 ограничивает «события, байты, выход, время», но не ЧИСЛО КАДРОВ на
   вызов; при stale-слепке в 15 минут (cron `*/15`) это ~125 000 событий ≈ 500 кадров —
   терпимо, при промахе слепка — весь журнал. После SCALE-01 промаха на serving нет, но
   ограничение на кадры за вызов дешевле оставить.

**Отдельный процесс (SCALE-18) для S0 НЕ нужен** — но одна строка `cpus:` в compose (§В-3)
нужна сейчас: recorder уже в отдельном контейнере (`docker ps` — два контейнера), и
единственное, чем hot gateway может ему навредить, — CPU-конкуренция, которую cgroup
режет без кода.
