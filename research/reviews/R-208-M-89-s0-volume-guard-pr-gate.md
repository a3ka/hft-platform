## Б-1 — БЛОКЕР. Байты каждого `pump` не доходят до счётчика ЭКЗЕМПЛЯРА; сердцебиение публикует величину, в которую реальное чтение не входит

**Где.** `crates/gateway-serve/src/lib.rs:1824`, `:2162`, `:2439`:

```rust
// M-89 (задача #4, `I-4`): per-pump push байт в счётчик экземпляра.
metrics::add_journal_payload_bytes_pub(pump_stats.payload_bytes_read);
```

`add_journal_payload_bytes_pub` (`crates/gateway-serve/src/metrics.rs:105-107`) пишет
ТОЛЬКО в процессный `JOURNAL_BYTES_GLOBAL`. Ручка экземпляра в этих же телах ДОСТУПНА, и это
проверено по области видимости, а не предположено:

- `:2162` и `:2254` — одно тело `run_authorized_session` (`:1990`), и `counters` там
  параметр функции (`:1994`); строка `:2254` этот параметр и использует;
- `:1824` — тело `run_v1_session_loop` (`:1662`), где ручка достаётся как
  `inner.counters.clone()` (`:1281`, там она и берётся для `counters_for_resume`);
- `:2439` — тот же приём, что `:1824`.

То есть выбор `_pub` — не следствие недоступности ручки. Комментарий на всех трёх местах
утверждает ровно обратное тому, что делает строка под ним.

**Чем это плохо.**

1. Сердцебиение (`lib.rs:560` `counters.as_ref().map(|c| c.snapshot())`, `:572`
   `"journal_payload_bytes_read": snap.journal_payload_bytes_read`) берёт величину из
   ручки ЭКЗЕМПЛЯРА. Значит наружу процесса уходит число, в которое байты, прочитанные
   `pump`'ами, НЕ ВХОДЯТ никогда — растёт оно только от `resume`. `I-6` объявляет
   «счётчики + свежесть наружу процесса», `TD-220` заведён ровно про это; поставка
   доставляет файл, но не величину.
2. `TD-224` по существу не закрыт: три точки пути выдачи по-прежнему двигают процессный
   атомик, то есть причина, по которой оракулы `M-87` ходят под `SERIAL`, жива.

**Почему набор этого не поймал — по построению, а не по невезению.**

- `v` (`crates/gateway-serve/tests/red_m89_read_volume_truth.rs:261,296`) читает
  ПРОЦЕССНЫЙ `serving_counters()`; там обе прибавки складываются, и разницы «экземпляр
  или процесс» не видно.
- `i1`/`i2` (`red_m89_counters_instance.rs:246,277`) читают ручку, но требуют лишь
  `journal_payload_bytes_read > 0` и «после > до» — это даёт уже один `resume`.

Нужен оракул, судящий ручку ЭКЗЕМПЛЯРА ПОСЛЕ `pump`'ов: «ручка выросла РОВНО на сумму
`ReadStats.payload_bytes_read` всех `pump`'ов сессии». Дизайн оракула — зона architect'а
(`gates.md` §4, граница reviewer↔architect); здесь описан дефект, не фикс.

## Б-2 — БЛОКЕР. Warm-`resume` кормит счётчик СИНТЕТИКОЙ; опись каталога с горячего пути не ушла, а подорожала; хвост учитывается дважды

**Где.** `crates/gateway/src/lib.rs:5149-5153`:

```rust
let tail_bytes_read = tail_bytes_after_cursor(dir, cursor.upto_seq.unwrap_or(0));
let stats = ReadStats { payload_bytes_read: ckpt_bytes_read.saturating_add(tail_bytes_read), .. };
```

`tail_bytes_after_cursor` (`:3898`) — тонкая обёртка над `journal::tail_bytes_for_dir`
(`crates/journal/src/segments.rs:3326`), которая на КАЖДОМ warm-`resume`:

- зовёт `segments(dir)` (`segments.rs:1252` → `load_manifest` + `dedup_indexed_paths` +
  `classify_segment` на каждый сегмент, то есть read_dir + заголовки);
- дополнительно открывает активный сегмент и читает 64 КиБ хвоста
  (`cheap_tail_last_seq_pub`), затем открывает его ВТОРОЙ раз ради `header_end`;
- возвращает **оценку** `tail_events × avg`, где `avg = (size_bytes − header_end) /
  (last_seq − first_seq + 1)`.

**Против чего.**

- `§4.1`: «`payload_bytes_read` заполняется ИЗ `EventStream::payload_bytes_read()` на ВСЕХ
  путях … warm-`resume` — байты файла слепка». Здесь к байтам слепка добавлена оценка
  байт, которые ЕЩЁ НЕ ПРОЧИТАНЫ.
- `§10` (запретный список), дословно: «кормить счётчик байт чем-либо, кроме
  `EventStream::payload_bytes_read()` (синтетика, дубликат в транспорте)».
- `§7`/задача 3: «`payload_bytes_after_cursor` удаляется — **с ним уходит `read_dir` +
  заголовки на каждую выдачу**». Ушло ИМЯ; вызов остался и стал дороже на открытие файла
  и 64 КиБ чтения.
- Дубликат: те же байты хвоста прибавляются второй раз, когда `pump` их реально прочитает
  (`lib.rs:1824/2162/2439` → тот же `JOURNAL_BYTES_GLOBAL`).

**Гейт утверждает обратное ИМЕНЕМ.** `scripts/verify_M-89.sh:418-420`:

```sh
PBAC=$(grep -c 'payload_bytes_after_cursor' "$GW" || true)
...  pass "task3: payload_bytes_after_cursor удалён — read_dir+заголовки ушли с горячего пути"
```

Это проверка имени, а не свойства — ровно тот класс, от которого §6 спеки предостерегает
для `TD-219` («Оракул против ОТСУТСТВИЯ вызова проверял бы имя; `s1` проверяет РАБОТУ»).

**Почему `v` зелен.** Его эталон — реплика ТОГО ЖЕ пути: `replica()` зовёт
`LiveReducer::resume` (`red_m89_read_volume_truth.rs:199-201`) и берёт её
`rs.payload_bytes_read` как `R`. И синтетика, и двойной счёт присутствуют в ОБЕИХ частях
равенства `counter == R + P1 + n·P2` — зависимый эталон (`testing.md`: «оракул `X == Y`
невалиден, если `Y` вычисляется через `X`»). `b1`…`b7` точность держат, но они меряют
`EventStream` в `crates/journal`, а синтез живёт в `crates/gateway` и ими не покрыт.

Класс — рецидив `R-201` Б-2 («warm-путь отчитывался о 92 ГБ прочитанных там, где не читал
ничего»): величина уменьшилась, свойство «отчитываемся о непрочитанном» осталось.
