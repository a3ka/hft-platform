## 2. B-1 — BLOCKER: ОТКАЗАВШИЙ `pump` оставляет состояние продвинутым, а курсор — нет; повторный вызов складывает те же события ЗАНОВО (`VB-I-2`)

### Что

`LiveReducer::pump` (`crates/gateway/src/lib.rs:3397-3517`) применяет каждое событие к
ПЕРСИСТЕНТНОМУ аккумулятору **до** проверки предела:

```
crates/gateway/src/lib.rs:3490   self.full.apply(&event);          // ← персистентное состояние
crates/gateway/src/lib.rs:3495   self.vwap.sum_pv = batch.vwap.sum_pv;
crates/gateway/src/lib.rs:3475   enforce_response_limit(&delta, effective_max_response_bytes())?;   // ← Err на границе batch'а
crates/gateway/src/lib.rs:3511   enforce_response_limit(&delta, effective_max_response_bytes())?;   // ← Err на финальном batch'е
crates/gateway/src/lib.rs:3515   self.cursor = cursor;             // ← НЕДОСТИЖИМО при Err
```

`?` уносит управление ДО `self.cursor = cursor`. Итог отказа: `self.full` и `self.vwap`
продвинуты, `self.cursor` — нет. Следующий вызов стартует с того же `self.cursor.upto_seq`,
фильтр «уже учтено» (`:3460`) не срабатывает, и **те же события складываются в аккумулятор
повторно**.

### Почему это доходит до клиента, а не остаётся внутри

Прод-вызыватели отказ `pump` **не считают фатальным и переиспользуют тот же `LiveReducer`**:

```
crates/gateway-serve/src/lib.rs:1356   "v1 LiveReducer::pump failed — sub продолжит молча"
crates/gateway-serve/src/lib.rs:1365   sub.live = Some(live);        ← повреждённый редьюсер возвращён в карту
crates/gateway-serve/src/lib.rs:1793   "LiveReducer::pump failed (журнал недоступен) — соединение продолжается…"
crates/gateway-serve/src/lib.rs:1795   continue;                          ← следующий тик повторит тот же диапазон
```

Каждый последующий кадр засевается ПОВРЕЖДЁННОЙ суммой (`:3452`/`:3479`
`batch.vwap.sum_pv = self.vwap.sum_pv`), то есть враньё уезжает клиенту не только снимком, но
и потоком кадров. Расхождение необратимо и монотонно растёт.
