## Находка 1 — БЛОКЕР. JR-I-8 не держится для сырого сегмента больше `TAIL_SCAN_CHUNK`

**Где**
- `crates/journal/src/segments.rs:1258` — `let read_size = (file_size as usize).min(TAIL_SCAN_CHUNK);`
- `crates/journal/src/segments.rs:1270` — `let mut had_header = false;`
- `crates/journal/src/segments.rs:1297` — `had_header = true;` (только внутри ветки `buf.starts_with(&SEGMENT_MAGIC)`)
- `crates/journal/src/segments.rs:1342` — `if last_valid_seq.is_none() && had_header {` — новый отказ по JR-I-8
- `crates/journal/src/lib.rs:52` — `pub(crate) const TAIL_SCAN_CHUNK: usize = 4 * 1024 * 1024;`

**Симптом.** Хвостовой скан читает последние ≤4 MiB файла. Если сырой сегмент БОЛЬШЕ 4 MiB,
`buf` начинается не с нуля, магии в нём нет ⇒ `had_header == false` ⇒ страж на строке 1342
НЕ СРАБАТЫВАЕТ ⇒ `tail_last_seq_of` возвращает `Ok(None)` ⇒ `resolve_next_seq_with`
(`segments.rs:1359`) отдаёт `meta_seq` (при restore мета отсутствует ⇒ 0) ⇒ `open_with = Ok`
и запись идёт в уже занятый диапазон `seq`. Это дословно тот дефект, который M-49 закрывает,
— он остался жив для файлов прод-размера.

**Почему это прод-масштаб, а не экзотика**
- `crates/journal/src/segments.rs:41` — `DEFAULT_MAX_SEGMENT_BYTES = 1 GiB`; recorder берёт
  дефолт (`crates/recorder/src/main.rs:475` → `WriterConfig::own_capture`). Активный сырой
  сегмент на проде на три порядка больше окна скана.
- Фикстуры ВСЕГО набора оракулов: `crates/journal/tests/red_tail_integrity.rs:59` и
  `crates/journal/tests/red_tail_integrity_operator.rs:46` — `max_segment_bytes: 8 * 1024`.
  То есть проверена ИСКЛЮЧИТЕЛЬНО ветка `had_header == true`. Это прямое нарушение
  `.claude/rules/testing.md` §«Прод-масштаб для sacred I/O-путей (урок TD-011)»: оракул
  sacred I/O-пути (`journal open`) обязан включать прод-масштабный кейс. Тот же класс, что
  TD-011, где 2.65 GiB прод-сегмент не был виден крошечным фикстурам.

**Воспроизведение (запущено reviewer'ом на `14626ac`)**

Временный probe в `crates/journal/tests/` (НЕ коммитился, удалён; текст — в конце файла):
сырой сегмент 9 981 613 B (> 4 MiB), история `seq 0..199999`, `journal.meta` удалена,
последние 5 MiB забиты `0x5A` (заголовок и почти вся история целы).

Тот же вход при `max_segment_bytes = 8 KiB` (как в `ti_3`) даёт `Err` — фикстура-масштаб

(заголовок цел и совпадает с cfg), то есть новые события с `seq`, начинающимся заново,
дописываются В ТОТ ЖЕ повреждённый файл — дубли `seq` внутри одного сегмента.

**Условие APPROVED.** Решение — за architect'ом (`gates.md` §4: reviewer описывает дефект,
не проектирует фикс). Приемлемы оба исхода, третьего нет:
1. закрыть класс и запиннить его оракулом ПРОД-МАСШТАБА (сегмент > `TAIL_SCAN_CHUNK`), либо
2. осознанно сузить JR-I-8 и НАЗВАТЬ ограничение в §«Известное ограничение» + отдельный TD,

Не приемлемо — мерж с текущей формулировкой спеки, где этот случай числится покрытым.

## Находка 2 — NOTE (TD-кандидат). `readable_max_seq` грузит сегменты целиком в RAM

**Где:** `crates/journal/src/segments.rs:1413-1421`, вызов `read_segment_events(&p, false)`
на строке 1416 в цикле по всем сегментам каталога.

`read_segment_events` (`segments.rs:317`) для raw-tolerant и для `.zst` собирает ВСЕ события
сегмента в `Vec<Event>` (в zst-ветке ещё и весь распакованный `data` в память — комментарий
в самом коде на строках 327-331 это признаёт: «на проде не используется»). После M-49
он используется на операторском пути: `resolve_next_seq_or_declared` → `readable_max_seq`.
При прод-размерах (1 GiB сегмент) это не-ограниченная память ровно в тот момент, когда
оператор вытаскивает узел из инцидента; отказ будет громкий (OOM/kill), не тихий, поэтому
NOTE, а не блокер. Класс — TD-011 (`red_open_bounded` был написан именно против этого).
Оракулом не покрыто: `op_2` работает на 8 KiB фикстурах.

use journal::{EpochFilter, Journal, WriterConfig};

const T0: i64 = 1_752_000_000_000;

fn cfg() -> WriterConfig {
    WriterConfig {
        max_segment_bytes: 512 * 1024 * 1024,
        min_free_bytes: 0,
        source: DataSource::OwnCapture,
        provenance: "reviewer probe".to_string(),
        epoch_id: "own-test".to_string(),
    }
}

fn trade(i: u64) -> EventKind {
    EventKind::md(
        Venue::Binance,
        "BTCUSDT",
        MdPayload::Trade {
            price: contracts::to_fixed(65_000.0) + i as i64,
            size: contracts::to_fixed(0.01),
            side: Side::Buy,
            ts_exch_ms: T0 + i as i64,
        },
    )

fn readable_max_seq(dir: &std::path::Path) -> Option<u64> {
    journal::stream(dir, EpochFilter::All)
        .ok()?
        .filter_map(|e| e.ok())
        .map(|e| e.seq)
        .max()
}

#[test]
fn probe_large_raw_segment_corrupt_tail_window() {
    let dir = tempfile::tempdir().expect("dir");
    {
        let mut j = Journal::open_with(dir.path(), cfg()).expect("open_with");
        for i in 0..200_000u64 {
            j.append(trade(i)).expect("append");
        }
        j.flush().expect("flush");
    }
    let _ = std::fs::remove_file(dir.path().join("journal.meta"));
    let p = dir.path().join("segment-00000000.jrnl");
    let size = std::fs::metadata(&p).expect("meta").len();
    assert!(size > 6 * 1024 * 1024, "фикстура: нужен сегмент > 6 MiB, получено {size}");
    let history_max = readable_max_seq(dir.path()).expect("история читается");

    let mut bytes = std::fs::read(&p).expect("read");
    let from = bytes.len() - 5 * 1024 * 1024;
    for b in bytes[from..].iter_mut() {
        *b = 0x5A;

    std::fs::write(&p, &bytes).expect("write");

    match Journal::open_with(dir.path(), cfg()) {
        Ok(mut j) => {
            j.append(trade(9_999_999)).expect("append");
            j.flush().expect("flush");

            let written = readable_max_seq(dir.path()).unwrap_or(0);

                 диапазон (история до {history_max}, после записи {written})"
            );
        }
        Err(e) => eprintln!("контракт соблюдён: {e}"),
    }
}
